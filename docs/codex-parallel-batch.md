## C9 — T79：124 个验收驱动仍无聚合执行器（你上批自己标了 ⬜）

主线独立复核过你的自报：**124 个驱动、`run_vf_01_acceptance.py` 全仓零命中、无任何聚合器**。确认没做。

这条的难点不在写一个 runner，在**判断哪些驱动应该被谁执行**。分类判据（来自当初的调查）：

- 被 npm script 点名的 **37** 个；
- 被真 subprocess 执行的 **4** 个；
- **只被读源码从不执行的 48 个**——这类最隐蔽：`.test.mjs` / `test_*.py` 只 `readFile` 驱动源码做文本断言，**绿的是「源码长这样」不是「能跑通」**。实证过：`run_t3_12` 在读者下全绿、真执行时 exit=1；
- **零执行者的 35** 个。

**不要一口气给 124 个都接上执行器**——很多需要真实资源（签名包、云凭据、Windows GUI），硬接只会让门禁长期红着然后被人忽略。要的是：**每个驱动都有一个明确的归属结论**（谁执行 / 为什么现在不能执行 / 需要什么条件才能执行），能接的接上，接不上的把条件写清楚。

那 48 个「只被读源码」的要特别处理：**要么让它们真执行，要么把那些文本断言标注清楚它们证明的到底是什么**——现在它们看起来像在证明驱动能用。
