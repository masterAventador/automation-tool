# 产品补全路线图 · 2026-07-27 起

**这份文档回答一个问题：从现在这个 Demo，到"运营者能把每天的活交给它"，中间缺什么、按什么顺序补。**

优先级由产品负责人 2026-07-27 定：**一键生成视频最高**。其余顺序按"离目标产品还差多少"排，不按工程难度。

判据一律是代码实现痕迹，不采信台账、文档声称或代码里的枚举映射表。每条都给出可复核的证据位置。

---

## P0 · 一键生成视频（AI 一句话出片，走 hyperframes 路线）

**这是最高优先级。** 它现在能出片，但出的不是产品想要的片子。

### P0-0　目标形态与路线选择（2026-07-27 与产品负责人讨论后确定）

**理想状态**（负责人表述）：把模板与零件的说明喂给 AI，AI 先向用户问清楚要做什么类型的视频、多长、什么风格，收集够了再决定——用现有模板还是自己新写一套 HTML，动效是复用现有 134 个还是自己重写，或者混合。都定了之后剩下就是生成。

**这个方向最终是对的，但落地顺序不是按难易排，而是按依赖排：先把「AI 熟练使用零件」做成主路径，再把「AI 自己写」作为逃生舱补上。** 理由三条，都有据可查：

1. **模型会压倒性地倒向自己写。** T92 记录的正是这个：当模型可以自由输出 `composition_html` 时，7543 字节的回答里 5315 字节是它在敲 markup。给它"可用零件也可自写"的选择，而它对 HTML+GSAP 远比对这 134 个零件熟悉，结果必然是零件永远用不上——等于回到 T92 之前，慢且每次都是新代码。**默认倾向必须是复用，缺口才补写；反过来设计，复用不会发生。**
2. **零件是验证过的，现写的每份都是首次运行。** 目录里 100 个带官方预览，意味着在真实渲染里站得住。一键出片场景下用户不会逐帧检查，**方差比上限更致命**。
3. **有一块实打实的工程被 T92 拿走了，得先还回来。** `lint_composition` / `check_composition` 现在判的是本机模板输出，**没有修复轮**。要让 AI 写 HTML，必须重建「模型输出 → 门禁 → 带错误回抛让模型改 → 再检」这个环节，并重新设计安全边界：现在靠 `escape_untrusted_text` 让文案贡献不出任何 ASCII 字面量，而 AI 写的 HTML 本身就是代码，这条防线形状完全不同，要靠沙箱预算 + 门禁兜。这不该和「让零件用起来」捆在一起做。

**因此 P0-1 拆成三步，依赖顺序不可颠倒：**

| 步骤 | 做什么 | 为什么排这个位置 |
|---|---|---|
| **P0-1a 编排层（主路径）** | AI 拿零件目录说明 + 用户需求，决定用哪些零件、怎么排布、什么节奏，只输出零件 id 与参数 | 地基。AI 必须先能熟练用零件，才谈得上判断「什么时候零件不够」 |
| **P0-1b 需求澄清（可跳过）** | AI 动手前亮出它的判断供用户确认或修改 | 依赖 1a：没有零件能力，AI 的"判断"无从表达 |
| **P0-1c 逃生舱（兜底）** | 零件覆盖不到时允许 AI 补写片段，过门禁 + 修复轮 + 沙箱 | 依赖 1a 建立的默认倾向，否则它会变成主路径 |

**关于需求澄清的陷阱**：这个入口的卖点就是"一句话"，强制问答会把它变成表单——而"固定模板手工制作"入口已经在做表单的事了。建议形态是**一句话直接出片，但 AI 把判断亮出来**（"我理解你要一条 30 秒的产品介绍，走展览黄风格，开场标题动效、中间三段数据卡片"），用户可直接确认，也可改一句再出。想聊的能聊，不想聊的一句话走完，同时让 AI 的决策变得可见可纠正。

### P0-1a　编排层：让模型真正用上 134 个动效零件（主路径）

**现状**：`composition_template.py` 里对 registry 零件**零引用**。片子结构是 4 个写死的 layout：`SCENE_LAYOUTS = ("title", "points", "flow", "stat")`。134 个零件（109 blocks + 25 components，见 `contracts/video/motion-catalog-ui.v1.json`）一个都没进合成。

**根因不是疏漏，是一次有意的取舍**（`composition_template.py` 文件头、`docs/development/T92.md`）：模型原本输出第四个字段 `composition_html`——完整 DOM + CSS + GSAP timeline，实测 7543 字节回答里占 5315 字节。改成"本机生成 markup、模型只写文案"后快 2.4 倍，代价是**结构从每部现编变成 4 选 1**。

**建议的第三条路**：模型既不写原始 markup，也不退回固定 layout，而是**从冻结目录里挑零件并编排**——输出零件 id + 参数（几百字节，速度接近现在），由本机按 id 组装。这才是 hyperframes 作为"AI 工具箱"的设计意图。

**骨架已经在了**，不是从零开始：

- 零件目录已冻结：`contracts/quality/motion-catalog.v1.json`，`agent.py:142` 的 `_load_locked_catalog_part_ids()` 已经在读它；
- agent 侧已有 `catalog_parts` 字段与校验：`entry.py:202-203`（`catalog purposes missing`、`catalog_parts must be locked catalog ids`）；
- 缺的是**组装那一段**：把 `catalog_parts` 真正翻译成合成文档里的零件实例。

**要连带解决的两个约束**（它们是 T92 把 markup 收回本机时一起接手的）：

1. `lint_composition` / `check_composition` 两道门禁现在判的是本机模板的输出，**没有修复轮**——零件组装出的文档一旦触发门禁就是用户简报的硬失败；
2. `escape_untrusted_text` 保证文案不能写出源码。零件参数若接受用户/模型文本，必须走同一条转义，否则这道防线会被绕开。

**判据**：同一句简报连出三条片子，`DESIGN.json` 里的 `catalog_parts` 各不相同，且渲染出的 mp4 在视觉上确实不同；关掉零件组装时能回退到现有 4 layout 且不报错。

**喂给模型什么——2026-07-27 探针已经把这件事测掉了，结论是好消息**：

只给「英文 `title` + 中文 `category`」（目录当前仅有的信息），两个模型都选出了合法且合理的组合：

| | qwen3.7-max | deepseek-v4-pro |
|---|---|---|
| 风格模板 | `blue-professional` ✅ | `blue-professional` ✅ **独立选出同一个** |
| 零件合法率 | 4/4 | 5/5 |
| 编造 id | 0 | 0 |

核对所选零件的真实分类，与模型陈述的用途完全吻合（`caption-kinetic-slam`→【字幕】、`ui-3d-reveal`→【产品与案例展示】、`data-chart`→【数据与地图】）。**"目录说明够不够模型判断"这个最大的不确定性已被排除**，剩下的是纯工程。

**但仍要补三个字段**，因为 P0-1d 的实测显示模型会因为看不到时长而严重超预算：上游 `vendor/hyperframes/registry/blocks/<name>/registry-item.json` 里本来就有 `description`（英文一句话说明）、`tags`、`duration`，冻结目录时只摘了 `name/title/category` 把它们丢掉了。补回成本极低。

12 套 style preset 无需补——`motion-style-presets.v1.json` 已有中文 `displayName` 与 `summary`（如"展览黄：纸张质感、深蓝文字和黄色光晕，适合文化与品牌叙事"），实测两个模型都据此选对。

### P0-1b　需求澄清轮（可跳过，不阻断一句话）

AI 在动手前把它的判断亮出来供确认或修改，形态见 P0-0。**判据**：不确认也能出片（默认路径不变长）；确认界面里改风格或片长，产出确实跟着变。

### P0-1c　逃生舱：零件不够时允许 AI 补写（兜底，非主路径）

**前置**：P0-1a 已建立"优先复用"的默认倾向。

**必须同时具备三样，缺一不可**：

1. **修复轮**——模型输出 → `lint_composition`/`check_composition` → 不过则把具体错误回抛给模型重写 → 再检。这是 T92 拿走的东西，要还回来；
2. **安全边界重设计**——`escape_untrusted_text` 那套（让文案贡献不出任何 ASCII 字面量）对"AI 写的代码"不适用，需要靠 `motion-render-sandbox-budget.v1.json` 的沙箱预算 + 门禁扫描来兜；
3. **可观测的选择**——`DESIGN.json` 要记录每一段是"复用零件"还是"AI 补写"，否则无法回答"这条片子为什么慢/为什么怪"。

**判据**：构造一个零件库明显覆盖不到的需求，AI 走补写路径且产物过门禁；同一需求在零件够用时不触发补写。

### P0-1d　时间轴必须有一个主宰（实测发现，比想象中要紧）

**2026-07-27 探针实测**：把 12 套 preset 与 134 个零件交给模型为一句话简报做编排，两个模型都选出了**合法且合理**的组合（零编造、分类与用途吻合），但**总时长双双超出沙箱上限 70% 以上**：

```
渲染沙箱硬上限          20 秒（SANDBOX_FRAMES_MAXIMUM 600 帧 / 30fps）
当前一句话入口固定      3 段 × 4 秒 = 12 秒

qwen3.7-max     4 个零件   34.0 秒   ❌
deepseek-v4-pro 5 个零件   36.3 秒   ❌
```

原因是**模型不知道零件有多长**——`data-chart` 单个 15 秒、`ui-3d-reveal` 13 秒，而 `lt-bold-block` 只有 4.8 秒。现有系统按「段数 × 每段固定秒数」算，隐含假设是每段等长，这个假设在用零件之后不成立。

**另有两处必须先处理**：

1. **部分零件没有 `duration` 字段**（实测 `caption-kinetic-slam`、`caption-editorial-emphasis` 均为 null），编排时不能假定它一定存在；
2. **上游其实提供了描述、标签和时长**，是我们冻结目录时丢掉的——`vendor/hyperframes/registry/blocks/<name>/registry-item.json` 里有 `description`、`tags`、`duration`、`dimensions`，而 `contracts/quality/motion-catalog.v1.json` 只摘了 `name/title/category`。**补回这三项是 P0-1a 的前置**，成本极低，收益是模型能按预算选而不是盲选。

**三个时长来源必须定主次**：画面（零件 duration）、语音（TTS 念完的实际秒数）、总预算（沙箱上限）。

**建议：语音主导，画面跟随。** 理由是 TTS 时长客观可测（合成完即知），而"把文案裁短以塞进画面"直接损伤内容且用户听得出来。

流程顺序有硬约束：

1. 模型写文案 + 选零件；
2. **先合成 TTS**，拿到每段语音真实秒数——必须在渲染之前；
3. 每段实际时长取 `max(语音时长, 零件 duration)`——语音没念完不切镜头，画面没播完也不切；
4. 总和超预算则回头压缩：减段、换更短的零件、或让模型改短文案；
5. 渲染时零件在自己的 duration 内播完，**剩余时间保持末帧而不是拉慢动效**——语音 8 秒配 5.5 秒动效，拉慢会拖沓，保持末帧更自然。

**判据**：给定一句话，产出的 mp4 里每段语音都在本段内说完；总时长等于各段 `max()` 之和；超预算时在渲染前就被拒绝并说明原因，而不是渲染完才发现。

### P0-1e　20 秒上限撑不起产品形态（需要产品决策）

`totalSecondsMaximum: 20` 来自渲染沙箱 `SANDBOX_FRAMES_MAXIMUM = 600` 帧（600 / 30fps）。而运营者在抖音、小红书发的短视频通常 **30 到 60 秒**。

**也就是说这条链路目前在物理上做不出一条正常长度的口播视频。** 接上 TTS 之后这个矛盾会立刻显性化：旁白说不完两句话就到顶。

**这不是 bug，是当初为渲染安全定的预算**，改它要付代价，方向有三个，需要产品定：

| 方向 | 代价 |
|---|---|
| 提高帧数上限 | 渲染时间与内存线性上涨；`renderWallMillisPerFrame` 400ms 意味着 60 秒片子约 12 分钟渲染 |
| 降低帧率（30 → 24 或 15） | 同样帧数换更长时间，但动效流畅度下降，字幕类零件影响最明显 |
| 分段渲染后拼接 | 单段仍受 600 帧限制，但总长不受限；代价是要处理段间衔接、音画同步累积误差，以及 ffmpeg 拼接这一层新的失败面 |

**建议倾向分段渲染**：它是唯一不牺牲画质也不线性放大单次渲染风险的路径，而项目已经有自编译 ffmpeg（`media-toolchain`）具备拼接能力。但它引入的音画同步累积误差需要在 P0-1d 的时间轴模型里一并设计，不能事后补。

### P0-2　片长可控，去掉写死的 12 秒

**现状**：`MOTION_BRIEF_FILM_SECONDS = beatCountDefault × secondsPerBeatDefault`，界面文案自己写着"这个入口暂时不能改片长；需要别的长度请用下面的固定模板手工制作"。

**注意原设计的顾虑是成立的**（`motion-one-sentence.ts` 注释）：不从句子里解析"三分钟"，因为模型解析错了就是片长错了而用户不知道为什么。**所以要加的是显式片长控件，不是让模型猜。**

**判据**：一句话入口能选片长，产出 mp4 的实际时长与所选一致；超出 `MOTION_DURATION_LIMITS` 上限时在提交前就拒绝，不是渲染完才失败。

### P0-3　给动效成片接上声音

**现状**：动效链路（`motion_authoring/` + `motion-*.ts`）**零音频痕迹**——没有配音、没有背景音、没有音效。

**TTS 其实已经买好放着了**：`edge-tts 7.2.7` 与 `azure-cognitiveservices-speech 1.41.1` 已打进素材成片 Worker 包（`contracts/quality/material-video-worker-package.v1.json`），只是那条链路没通，能力闲置。

**要决定的**：动效成片是复用素材 Worker 里的 TTS（跨 Worker 调用，多一层进程边界），还是在动效链路里单独接一份（多一份依赖与体积）。**建议前者**——同一个能力不做两份，与"单一构建路径"一致。

**判据**：一句话产出的 mp4 有可听的旁白，字幕/文案与旁白同源；静音是可选项而非默认。

### P0-4　打通智能素材成片（moneyprinterturbo）

**产品意图**（负责人 2026-07-27 澄清）：上游自带一套 WebUI，它必然已经对接好自己的逻辑，所以**不重做界面，直接把它展示出来**，用户在里面改时长等参数就能出片。入口 `open_material_video_studio`（`lib.rs:312`）打开的正是这个外部 URL 窗口——方向是对的。

**现状要分两层看，别混为一谈：**

**第一层「窗口点不动」——已修，但用户还没拿到修复。** 负责人报的症状是"弹了新窗口，里面的东西都点不动，没法实验能不能生成"。这就是 T108：上游 `webui/Main.py:1209` 每个会话首帧调 `tour.start()`（driver.js 引导层），给 body 加 `.driver-active`，其 `*{pointer-events:none}` 关掉整页；**而产品自己的注入脚本把气泡与遮罩 `display:none` 了，用户没有任何办法结束引导**，类名永不摘除。WebUI 每次换随机端口即新 origin，localStorage 每次为空，**每次打开必然复现**。

修复 `cadb047`（07-27 02:07）：样式表里 `body.driver-active *` 恢复 `pointer-events: auto !important`——driver.js 那条规则没有 `!important`，所以产品规则压得住，即使上游以后改了 storage key 也不会再变成死窗口。真实 Tauri 窗口验收报告 `driverActive: false`、`subjectPointerEvents: "auto"`，走的是完整用户路径并真的点击输入。

**关键时间差**：负责人试的是 07-26 的包，**不含这个 02:07 的修复**。07-27 之后出的包都含。

**第二层「能不能真生成视频」——仍然无人验证。** T108 的验收止步于"能点"，没有继续走到出片。台账在 Demo 选型时的原话是"生成侧已实测产出会动的 mp4，而**素材线一次都没走通过**"——那是在窗口可交互之前的结论，现在前提变了，**这条线到底通不通是未知，不是已知不通**。

**它真正的门槛**：这条线要 4 个外部依赖串联（模型、TTS、素材源、字幕），而动效线只要 1 个。Demo 选型时这是决定性理由，现在仍然成立——但那是"配置成本高"，不等于"走不通"。

**下一步是一次实验，不是一轮开发**：用 07-27 之后的包打开这个窗口，在上游 WebUI 里配齐参数走一次完整生成，看卡在哪个依赖上。这个结果决定后面是"补配置引导"还是"真要改集成方式"。

**它值得打通的原因**：产品要的"根据热点生成自己的视频"更接近**带实拍素材的口播视频**，而不是文字动效 / 数据可视化。动效线做不出前者。

**判据**：从一句话到带旁白与实拍素材的 mp4，全链路在正式包里跑通一次，产物能进发布工作区。

## P1 · 感知能力：读得进来

**这是产品设想里缺失最彻底的一整类能力**，也是运营者每天最耗时的部分。

**现状**：全仓库在执行器与领域层搜 `unread` / `inbox` / `未读` / `收到`，**零匹配**。现有的全是"发出去"：

- 私信 `direct_message_action.py`：`wait_for_profile_ready` → `enter_conversation` → 发送，是**主动触达**；
- 评论 `comment_action.py`：对候选目标（别人的视频）发表，是**主动评论**。

**缺的三件**（缺一件后面两件都不成立）：

1. **读收到的私信**——收件箱列表、未读标记、会话上下文抽取；
2. **读自己视频下的评论**——通知/消息中心、区分新旧、定位到具体作品；
3. **在此之上的回复动作**——回复与主动发起是两个动作，回执、幂等键、失败矩阵都不同。

**判据**：能列出"当前有几条未读私信/新评论"，并对其中一条完成回复且在平台侧可见；重复执行不会重复回复（幂等）。

## P2 · 调度器：把"工具"变成"员工"

**现状**：控制面**没有任何定时触发机制**。搜遍 `control_plane/`，`BackgroundTasks`/`apscheduler`/`celery`/常驻循环一个都没有。唯一命中 "schedule" 关键词的 `action_risk_policy.py:63` 是**风控最小间隔**，不是调度。

**影响**：产品设想的"每天自动抓热点、自动回复"目前全部要人打开 App 手动创建任务。这是"工具"与"AI 员工"的分界线。

**要连带想清楚的**：现有风控（任务级/每日硬上限、最小间隔、连续失败熔断、一键紧停）是为"人触发"设计的。调度器上来后，**熔断与紧停必须能压住调度器**，否则夜间无人值守时一次页面改版就会把配额烧光甚至触发平台风控。

**判据**：配一条"每天 9 点抓一次热点"，关掉 App 再打开，任务按计划执行过且记录完整；紧急停止能立刻掐断后续排期。

## P3 · 平台横向扩展

**现状**（域名反查，有实现必然出现）：

```
douyin.com    12 个文件      bilibili.com   5 个文件
xiaohongshu.com  0           kuaishou.com   0           channels.weixin.qq.com  0
```

执行器侧文件数：抖音 22 个，其余平台 0。`PublishMechanism` 把快手/小红书/视频号标为 `DEFERRED`（注释：deferred means no entry point exists），与实现一致。

**好消息**：抖音那套是按可复制结构写的——页面定位（`*_page.py`）、动作编排（`*_action.py`）、频控、结果解析分层清楚，`page_anchors.py` / `page_version.py` 还专门处理页面改版。第二个平台的成本应显著低于第一个。

**建议顺序**：小红书 → 快手 → 视频号。理由是内容形态与抖音最接近、运营者重合度最高。视频号放最后，因为它与微信生态绑定，可能与 P5 的技术选型互相影响。

**判据**：新平台至少覆盖登录态保持、发布、评论三件，且共用同一套任务/事件/风控骨架，不新开一套。

## P4 · 视频剪辑接线

**现状**：有壳无芯。`VideoEditingWorkbench.tsx` **842 行** UI 完整；数据存 **localStorage**（`automation-tool.video-editing.local-draft.v1`）；后端 `api/` 下**没有任何 video_editing 端点**——领域层（`domain/video_editing.py`、`aliyun_ims_editing_*.py`）与 Provider 抽象都写了，**没有一条 HTTP 路由把它暴露出去**。提交必然 fail closed。

代码注释自己写着：`the cloud editing provider chain (VE-04+) is not connected yet... there are no editing jobs and submission always fails closed as unavailable.`

**这是全项目投入产出比最高的一块**：领域层、Provider 抽象、一致性契约、842 行 UI 都在，缺的只是中间那段接线——API 端点 + 网关从 local 切到真实实现 + 任务状态回流。

**判据**：从剪辑工作台提交一个任务，阿里云 IMS 真实返回成片，产物出现在成片列表并可发布。

## P5 · 微信自动化：另一条腿

**现状**：**零痕迹**。`weixin.qq.com` 0 个文件；`WeChat.exe`、`微信.app`、`uiautomation`、`pywinauto`、`AXUIElement` 全部零匹配。代码里唯一沾"微信"的是 `PublishPlatform.WECHAT_CHANNELS`，那是**视频号**这个发布目标，与控制微信客户端无关。

**必须先定技术路线再谈排期**：现有 RPA 全建在 Playwright + 内置 Chromium 上，而微信客户端自动化是**桌面 UI 自动化**——Windows 上 UIAutomation、macOS 上 Accessibility API。这是另一套技术栈、另一套权限模型（macOS 要辅助功能授权）、另一套失败矩阵（窗口焦点、多开、版本升级导致控件树变化）。**不能按"再加一个平台 Adapter"估算。**

**还要先回答的产品问题**：自动通过好友申请、自动打招呼、自动回复聊天，这些动作的风险等级远高于公开平台的评论——微信对自动化的容忍度、账号封禁风险、以及用户是否接受 App 操作自己的私人微信，都要先有结论。

**判据**：在真实微信客户端上完成一次"通过好友申请 → 发打招呼 → 回复一条消息"，且全程可见、可人工接管、可紧急停止。

## P6 · AI 编排入口

**现状**：前端 `features/` 下没有任何对话/助手页面。唯一的模型入口是动效创作 agent（`VideoStudio.tsx:1375` "Hand a one-sentence brief to the authoring agent"）。

也就是说 **AI 目前只能"把一句话变成一条视频"，不能"帮你决定该做什么"**。产品设想里的 AI 员工——读热点定选题、读私信定怎么回、编排一天的工作——还没有落点。

**它排在最后不是因为不重要，而是因为它依赖前面**：没有 P1 的感知能力，AI 读不到东西；没有 P2 的调度器，AI 的决定无法执行。**这三条合起来才是"AI 员工"，单独做 P6 只会得到一个聊天框。**
