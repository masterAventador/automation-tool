#### PC-07 补充：TTS 供应商与接入形态

每段旁白合成为音频并测出真实秒数，且必须在渲染之前拿到——顺序反了就只能事后发现说不完。**供应商已定（产品负责人 2026-07-27）：走已接入的阿里百炼，先随便挑一个够前沿的把 MVP 跑通，不为选型发散。** 建议 pin `qwen3-tts-instruct-flash-2026-01-26`（非 realtime，我们要的是文件不是流；`instruct` 档为将来的语气控制留门）。

实调百炼列出 231 个模型，TTS 三家可选：`qwen3-tts-*`（flash / instruct / vc 声音克隆 / vd）、`MiniMax/speech-2.8-hd|turbo`、`qwen-tts-2025-05-22`。**小米 MiMo 只有 `xiaomi/mimo-v2.5-pro` 一个，是文本模型不是 TTS。**「同一句话分段用不同语气」这个能力待验证，归后续，不阻塞 MVP。

排除的选项：`edge-tts` 与 `azure-cognitiveservices-speech` 已在素材成片 Worker 包里闲置，但端点在国外、国内可达性不稳；`faster-whisper` 是本地模型但它是 ASR 不是 TTS；本地 TTS（Kokoro/ChatTTS/GPT-SoVITS）安装包净增 300 MB 起，留给「用户明确要求离线」的场景。

**接入形态很轻**：上游 hyperframes 引擎不管 TTS——音频在它的合成模型里就是标准 `<audio>` clip，TTS 在它的 `media-use` skill 里走外部服务产出本地文件。而我们的 `worker.mjs` 对 audio 零引用（逐帧截图，音频不经过 HTML），A 路线又是分段渲染 + ffmpeg 拼接，**旁白天然就是 ffmpeg 的另一条输入轨**。只需在 `bailian-model-catalog.v1.json` 加一个 `voiceover` 用途，与现有 `script` / `video_creative` 走同一网关。

#### PC-13 补充：中文字体实测与定案

离线包现有 18 个字体全是拉丁、中文 0 个，中文靠系统兜底 → 跨平台不一致（违反 BM-16 确定性）且 23 个零件设计丢失。字体必须**构建期下载、锁摘要、进安装包**，运行时取用一律不可接受（国内用户访问不了 Google）。需给出实测净增 MB；基线是现有离线字体资产 1 MB。**查证已完成（见 `docs/development/PC-13.md`）：同名 `@font-face` + `unicode-range` 在内置 Chromium 149 上成立，但必须按零件请求的每个 `(family, weight)` 逐条声明——只声明 400 或 `100 900` 都会掉回系统字体；推荐一个 Noto Sans SC 可变 woff2。**产品负责人 2026-07-27 定：取全字符集 7.42 MB（占 dmg +1.59%），不取 GBK/GB2312**——省下的 1.84 MB 换来的是用户名字里有个「璟」就显示豆腐块，且渲染成功、门禁全绿、无任何报错。可变字体下字重数量不影响体积。**

**同次定下扩大范围：顺带修拉丁那 78 个。** 实测 134 个零件里 78 个（58%）今天连拉丁字母都在吃系统兜底（61 个写了具名字体却从不加载 `@font-face`，17 个一个都没写），对照组里 `#lt-tag` 报 `SpaceMono-Bold` 且 `isCustomFont: false`——那是探针机器 `~/Library/Fonts` 里的，不是产品带的。**BM-16 要挡的跨机器漂移今天已经在拉丁字母上发生了**，而修它和注入 CJK 是同一处改动，分开做等于改两遍。注意其中点名的 `SF Pro`/`Menlo`（苹果）与 `Consolas`/`Courier New`（微软）**不可再分发**，需逐个定替代并记录取舍。

落地已知工作：按 `(family, weight)` 逐条声明（Chromium 先按字重分桶再解析 `unicode-range`，漏一条就偶发掉字体）、`fontFamilies` 权利归属从「按家族」改「按 artifact」、构建期新增 fonttools+brotli 生成合并 woff2（Google 只按 101 子集分发而 `SANDBOX_ASSETS_MAXIMUM=128` 装不下）、Windows 复测。

## P0 · 一键生成视频（AI 一句话出片，走 hyperframes 路线）

**这是最高优先级。** 它现在能出片，但出的不是产品想要的片子。

### P0-0　目标形态与路线选择（2026-07-27 与产品负责人讨论后确定）

**理想状态**（负责人表述）：把模板与零件的说明喂给 AI，AI 先向用户问清楚要做什么类型的视频、多长、什么风格，收集够了再决定——用现有模板还是自己新写一套 HTML，动效是复用现有 134 个还是自己重写，或者混合。都定了之后剩下就是生成。

**这个方向最终是对的，但落地顺序不是按难易排，而是按依赖排：先把「AI 熟练使用零件」做成主路径，再把「AI 自己写」作为逃生舱补上。** 理由三条，都有据可查：

1. **模型会压倒性地倒向自己写。** T92 记录的正是这个：当模型可以自由输出 `composition_html` 时，7543 字节的回答里 5315 字节是它在敲 markup。给它"可用零件也可自写"的选择，而它对 HTML+GSAP 远比对这 134 个零件熟悉，结果必然是零件永远用不上——等于回到 T92 之前，慢且每次都是新代码。**默认倾向必须是复用，缺口才补写；反过来设计，复用不会发生。**
2. **零件是验证过的，现写的每份都是首次运行。** 目录里 100 个带官方预览，意味着在真实渲染里站得住。一键出片场景下用户不会逐帧检查，**方差比上限更致命**。
3. **有一块实打实的工程被 T92 拿走了，得先还回来。** `lint_composition` / `check_composition` 现在判的是本机模板输出，**没有修复轮**。要让 AI 写 HTML，必须重建「模型输出 → 门禁 → 带错误回抛让模型改 → 再检」这个环节，并重新设计安全边界：现在靠 `escape_untrusted_text` 让文案贡献不出任何 ASCII 字面量，而 AI 写的 HTML 本身就是代码，这条防线形状完全不同，要靠沙箱预算 + 门禁兜。这不该和「让零件用起来」捆在一起做。

**因此 P0-1 拆成三步，依赖顺序不可颠倒：**

| 步骤 | 做什么 | 为什么排这个位置 |
|---|---|---|
| **P0-1a 编排层（主路径）** | AI 拿零件目录说明 + 用户需求，决定用哪些零件、怎么排布、什么节奏，只输出零件 id 与参数 | 地基。AI 必须先能熟练用零件，才谈得上判断「什么时候零件不够」 |
| **P0-1b 需求澄清（可跳过）** | AI 动手前亮出它的判断供用户确认或修改 | 依赖 1a：没有零件能力，AI 的"判断"无从表达 |
| **P0-1c 逃生舱（兜底）** | 零件覆盖不到时允许 AI 补写片段，过门禁 + 修复轮 + 沙箱 | 依赖 1a 建立的默认倾向，否则它会变成主路径 |

**关于需求澄清的陷阱**：这个入口的卖点就是"一句话"，强制问答会把它变成表单——而"固定模板手工制作"入口已经在做表单的事了。建议形态是**一句话直接出片，但 AI 把判断亮出来**（"我理解你要一条 30 秒的产品介绍，走展览黄风格，开场标题动效、中间三段数据卡片"），用户可直接确认，也可改一句再出。想聊的能聊，不想聊的一句话走完，同时让 AI 的决策变得可见可纠正。

### P0-1a　编排层：让模型真正用上 134 个动效零件（主路径）

**现状**：`composition_template.py` 里对 registry 零件**零引用**。片子结构是 4 个写死的 layout：`SCENE_LAYOUTS = ("title", "points", "flow", "stat")`。134 个零件（109 blocks + 25 components，见 `contracts/video/motion-catalog-ui.v1.json`）一个都没进合成。

**根因不是疏漏，是一次有意的取舍**（`composition_template.py` 文件头、`docs/development/T92.md`）：模型原本输出第四个字段 `composition_html`——完整 DOM + CSS + GSAP timeline，实测 7543 字节回答里占 5315 字节。改成"本机生成 markup、模型只写文案"后快 2.4 倍，代价是**结构从每部现编变成 4 选 1**。

**建议的第三条路**：模型既不写原始 markup，也不退回固定 layout，而是**从冻结目录里挑零件并编排**——输出零件 id + 参数（几百字节，速度接近现在），由本机按 id 组装。这才是 hyperframes 作为"AI 工具箱"的设计意图。

**骨架已经在了**，不是从零开始：

- 零件目录已冻结：`contracts/quality/motion-catalog.v1.json`，`agent.py:142` 的 `_load_locked_catalog_part_ids()` 已经在读它；
- agent 侧已有 `catalog_parts` 字段与校验：`entry.py:202-203`（`catalog purposes missing`、`catalog_parts must be locked catalog ids`）；
- 缺的是**组装那一段**：把 `catalog_parts` 真正翻译成合成文档里的零件实例。

### P0-1a′　「组装」到底是什么——2026-07-27 打开零件源码后的三个更正

上面那句「把 `catalog_parts` 翻译成零件实例」写得太轻，它隐含了一个当时没验证的前提：零件是可以填参数的组件。**打开源码后这个前提是错的**，下面三条推翻并替换它。

**一、零件没有参数接口，文案是写死的。**

134 个里只有 6 个带 `params`，而这 6 个一共 12 个参数**全部是颜色**（`--bg-color`、`--text-color`）。没有任何文本参数机制。而按可见文本节点统计，**125 个零件里带写死的英文文案**——`ui-3d-reveal` 78 段、`vfx-portal` 38 段、`vfx-liquid-background` 41 段；完全没有可见文案的只有 9 个（`grain-overlay`、`motion-blur`、`shimmer-sweep`、`parallax-zoom` 这类纯视觉）。

上游自己的解法在 `skills/hyperframes-registry/SKILL.md` 里：`hyperframes add <name>` 把零件 HTML 装进项目，**然后由 AI 直接改那份 HTML**。

**这条路我们不走，理由是算术不是原则。** T92 不是立规矩说模型不许碰 HTML，它是一次实测出来的性能取舍：模型吐字速率恒定约 4.5 KB/s，一句话出片的墙钟时间基本等于模型打字时间，把 markup 收回本机后编排耗时中位数从 87.0 秒降到 36.9 秒。而零件动辄 13 KB（`data-chart`）起，光重吐一份就是 3 秒，一条片子用 4～5 个零件就把整条链路拖回 T92 之前，还得把 T92 顺手拿掉的修复轮重建起来。

**本机做文案槽替换的代价则是一次性的**：建一张槽位表，之后每次出片模型只吐几十字节的文案字符串。所以主路径走槽位表；而「让 AI 补写」（P0-1c 逃生舱）随时可以加回来，只是不该当主路径。

**所以要用零件承载用户内容，必须本机做结构化文案槽替换**——预先登记每个零件的可替换文案位置，模型只吐字符串，本机替换并继续走 `escape_untrusted_text`。这是新增的前置（PC-02、PC-03），原路线图里没有，因为当时以为零件可参数化。具体怎么建、哪些零件能建、塞长塞短会怎样，见 P0-1a″ 到 P0-1a⁵ 四节。

**二、上游有原生的子合成机制，不用改上游一个字。**

宿主合成里放一个 div 引用零件文件即可（`skills/hyperframes-registry/references/wiring-blocks.md`）：

```html
<div data-composition-id="data-chart"
     data-composition-src="compositions/data-chart.html"
     data-start="2" data-duration="15" data-track-index="1"
     data-width="1920" data-height="1080"></div>
```

上游 runtime 负责加载子合成、找到它自己的 `window.__timelines` 注册、**按 `data-start` 偏移与宿主时间轴同步 seek**。宿主的 GSAP 代码完全不需要引用零件的时间轴。

**三、但我们的渲染器没有实现它。**

`workers/motion_composition/worker.mjs` 是本项目自己写的 CDP worker，只驱动顶层 `window.__timelines`，不认 `data-composition-src`。所以这个机制目前对我们不生效。

#### 由此定下的路线（产品负责人 2026-07-27 选 A）

| | 做什么 | 得到什么 | 代价 |
|---|---|---|---|
| **A（选定）** | 每个零件按它自己的原生尺寸单独渲成 mp4 片段，再 ffmpeg 拼接 | 零件本身就是合法的独立合成，**现有 worker 直接能渲**，不需要实现子合成；顺带解掉 20 秒上限（见 P0-1e） | 只能顺序播放，做不到同屏叠加；要处理拼接的编码一致性与音画同步累积误差 |
| **B（以后）** | 在 worker 里按上游契约实现 `data-composition-src` 解析与同步 seek | 真正的合成：叠加、定位、同屏多零件（例如数据图表 + 下三分之一身份条同框） | 解不了 20 秒上限；worker 要新增子合成加载与偏移 seek |

**两者不冲突：A 解片长，B 解叠加。先 A，等确实需要同屏叠加时再补 B。**

### P0-1a″　零件不是成品镜头，30 个转场是演示页（2026-07-27 实测）

定下 A 之后曾打算「先小后大」：小 = 零件只当点缀、不换文案，文案继续由本机 4 layout 模板画。**打开零件源码后这个切法是错的**，原因和结论都在下面。

**30 个转场零件全是演示页，不是镜头。** 原样渲染出来的画面是：

```
SCENE A | SCENE B
Chromatic Radial Split
Prompt
"use chromatic radial split shader transition"
RGB channels separate and converge radially. From-scene splits outward…
```

它展示的是「这个转场技术长什么样」，中间那两块 SCENE A / SCENE B 是占位面板。要真的用它，得把转场机制搬到你自己的两个场景之间——**那正是「让 AI 写 HTML」才做得到的事**（P0-1c 逃生舱）。而这 30 个恰恰就是原计划里「最安全、可以原样用」的那批。**所以「不换文案就能用」不成立。**

同一批实测里露出了正确的切法：

```
caption-kinetic-slam  组件   "Kinetic Slam"                                → 1 槽
lt-bold-block         4.8s   "Maya Chen" / "Host · Neuroscientist"          → 2 槽，含义一目了然
logo-outro            6s     "Nothing great is made alone." / "figma.com"   → 2~3 槽
flowchart             12s    "Should I learn to code?" / "Yes" / "Start with Pythom"…  → 约 9 槽
ui-3d-reveal          13s    整个假 App 界面                                 → 78 段文本
```

**决定一个零件好不好用的是它有几个文案槽，不是它属于点缀还是内容。** `lt-bold-block` 是点缀型，但两个槽的含义清清楚楚，换成「张三 / 主播·神经科学家」立刻可用；`flowchart` 是内容型，九个槽也都对得上；而转场零件槽位再少也没用，因为要替的不是文字是机制。

**但「按槽位数量分批」也是错的**，见下一节——那份统计只数 DOM 文本节点，而文案未必在 DOM 里。

### P0-1a⁗　塞长文案会怎样——分三层，一层比一层难发现（产品负责人 2026-07-27 提问后实测）

问题是「往槽里塞特别长或特别短的文本会不会有问题」。会，而且最要命的那层没有任何门禁能发现。

```
动画会读元素实际尺寸（文案一变动画就变）   55 / 134
带某种字号自适应（长文案自动缩，有下限）    32 / 134
两者都没有（最脆）                        73 / 134
```

**第一层 · 排版（看得出来）。** 73 个零件既不测尺寸也不自适应，固定字号配固定容器。`lt-bold-block` 是典型：

```css
.lt-name    { font-size: 58px }      /* 写死 */
.lt-tagwrap { overflow: hidden }     /* 超出直接裁掉 */
```

**长了不是难看，是看不见**——被裁掉。有自适应的 32 个也有下限，`caption-kinetic-slam` 的 `fitFontSize` 缩到基准的 45% 就停，再长照样溢出。

**第二层 · 动画（不容易看出来）。** 55 个零件的动画读 `offsetWidth` / `getBoundingClientRect` / `measureText`，文案长度一变，位移量、擦除宽度、缩放中心跟着变。结果是「感觉不对」，没有报错。

**第三层 · 时长（完全看不出来，最危险）。** JS 数据型零件的时间轴是按原文案编排的：

```js
var WORDS = [ {text:"Every", start:0.0, end:0.3}, … 28 个词，各带时间戳 ];
var KEYWORDS = new Set([8, 12, 15, 24, 27]);   // 关键词按下标高亮
```

`data-duration="8"` 就是这些时间戳推出来的。换成 10 个词 → 动画 3 秒播完 → **后面 5 秒是静止画面**；换成 40 个词 → 后面的词根本没时间播。而 `check_composition` 只断言 `data-duration` 与声明一致，这两种情况它都认为正常。**现有门禁一条都发现不了。** 太短还额外错位关键词高亮——`KEYWORDS` 是下标，词数一变就高亮到别的词上。

**由此定下槽位表必须记的三样**（只记文本是不够的）：文案在哪（DOM 文本节点 / JS 数据结构）、长度**上下限**（不只是上限）、**是否参与时间轴**（换了要不要重算时长）。

### P0-1a⁵　真正的分批标准：按文案存放形态

上一节的原因，「按槽位数量分批」作废——那份统计只数 DOM 文本节点，而 **15 个字幕零件全是 JS 注入型（DOM 里 0 段文本）**，扫到的 `Kinetic Slam` 是 `<title>`。它们不是最容易的那批，是最难的。

实测的真实形态分布：

形态分布（PC-02 已冻结进 `contracts/video/motion-part-usability.v1.json`，由门禁从源码重算）：

| 形态 | 零件数 | 处置 |
|---|---:|---|
| **DOM 型** | 52 | 文案在文本节点里，槽位方案直接成立 |
| 混合 | 42 | 一部分在 DOM 一部分在 JS，逐个判 |
| JS 注入型 | 28 | 文案与时间轴都在脚本里，换它≈改代码 → 归 P0-1c 逃生舱 |
| 纯视觉 | 12 | 没有文案，直接可用 |

**注意这些数字与本节上文的粗测不同**（54/47/23/10）：上面那组是正则扫全文件数出来的，PC-02 改用**将来真正做替换的那个解析器**（`part_document.py`）重算，统计与替换按构造一致。差距本身就是不该用粗测下结论的证据。

再叠上「转场是演示页」这一条（30 个转场里 25 个是 DOM 型，形态没问题，是语义把它们排除的），得到最终分批：

```
first     36    非转场的 DOM 型与纯视觉 → 建槽位表（PC-03）
second    40    混合型 → 只给 DOM 那部分开槽（PC-12）

```

**修订后的先小后大**：先给 first 的 36 个建槽位表，跑通 A 路线的渲染与拼接，出一条真能看的片子；再逐个判 second 的 40 个。

**但 419 个可见文本节点不等于 419 个槽。** 这 36 个的可见节点合计 419，分布极不均：26 个零件 ≤5 个节点（下三分之一、简单卡片，理想形态），长尾是 `ui-3d-reveal` 136、`vpn-youtube-spot` 50、`vfx-portal` 45、`app-showcase` 38——**那些是假 UI 的布景文字，不是该替换的文案**。槽位表要筛，不能照单全开。

第一批的风险画像倒是很干净：36 个里只有 4 个 `lengthSensitive`、4 个 `autoFitsFontSize`、3 个 `latinDisplayDesign`。

### P0-1a‴　槽位表怎么建：沿用 BM-13 的 overlay 思路，不碰 submodule

不改零件源码。规则第 6 条要求 `vendor/hyperframes` 只能按锁定 commit 作只读 submodule 存在，`scripts/check_third_party_sources.py` 会因工作树脏判红——但更重要的是**没必要，这个仓库已经解过一次同样的问题**。

BM-13 给零件去品牌时同样要「改零件里的字但不能碰 submodule」，做法是 overlay：`contracts/quality/motion-asset-overlay.v1.json` 覆盖 70 个零件、121 条商标文本替换规则（`apple` → `星云科技`、`hyperframes` → `动效画布`），由 `build_motion_catalog_release.py` 在构建期合成一棵只读发布树。**「往零件里塞我们自己的字」这条链路是通的、跑过的、有门禁守着的。**

文案槽是同一条路，但改两处：overlay 是**构建期、全局、按字符串匹配**，文案要**运行期、按位置**——每次出片都不同，且换的是整句而非一个词。

```
只读发布树的零件 HTML → 按槽位表替换 → 写进本次 RenderJob 工作区的临时副本 → 渲染
                                             （发布树自始至终只读）
```

**定位用「文本节点序号 + 原文逐字」双锚，不用 CSS 选择器：**

```json
{
  "name": "lt-bold-block",
  "sourceSha256": "…",
  "slots": [
    {"index": 1, "original": "Maya Chen", "maxChars": 9, "role": "姓名"},
    {"index": 2, "original": "Host · Neuroscientist", "maxChars": 21, "role": "身份"}
  ]
}
```

替换时按文档顺序枚举文本节点，第 `index` 个必须逐字等于 `original`，否则失败关闭。理由是它自校验：原文对不上就说明我们对这份文档结构的理解是错的，当场判红，而不是静默替到别处去——选择器做不到这一点。零件文件的 sha256 已被目录门禁锁着，上游一升级槽位表就必须重生成，这道门禁是现成的。

**三条硬边界，不是以后能优化掉的：**

1. **`<script>` / `<style>` 里不开槽。** `data-chart` 的数据是 script 里的数组——**图表数值换不了，只能换标题和图例**。这是内容型零件表达力的真实天花板；
2. **长度。** 零件按原文长度排版，`"Monthly Revenue vs. Conversion Rate"` 34 字符换成 40 字中文会炸版。槽位必须带字数预算并喂给模型当约束，同现在的 `MAX_BEAT_HEADLINE_CHARS`；
3. **字体。** 零件用 Libre Baskerville 这类拉丁字体，塞中文会 fallback。BM-12 本地化过字体，但**离线包里有没有中文字体尚未查证**——这是典型的「技术全绿、用户一看很丑」，必须在建表前查掉。

文案仍走 `escape_untrusted_text`：每个 ASCII 字符变成数字字符引用，在 HTML 文本节点与 SVG `<text>` 里渲染一致，且贡献不出任何 ASCII 字面量。

**要连带解决的两个约束**（它们是 T92 把 markup 收回本机时一起接手的）：

1. `lint_composition` / `check_composition` 两道门禁现在判的是本机模板的输出，**没有修复轮**——零件组装出的文档一旦触发门禁就是用户简报的硬失败；
2. `escape_untrusted_text` 保证文案不能写出源码。零件参数若接受用户/模型文本，必须走同一条转义，否则这道防线会被绕开。

**判据**：同一句简报连出三条片子，`DESIGN.json` 里的 `catalog_parts` 各不相同，且渲染出的 mp4 在视觉上确实不同；关掉零件组装时能回退到现有 4 layout 且不报错。

**喂给模型什么——2026-07-27 探针已经把这件事测掉了，结论是好消息**：

只给「英文 `title` + 中文 `category`」（目录当前仅有的信息），两个模型都选出了合法且合理的组合：

| | qwen3.7-max | deepseek-v4-pro |
|---|---|---|
| 风格模板 | `blue-professional` ✅ | `blue-professional` ✅ **独立选出同一个** |
| 零件合法率 | 4/4 | 5/5 |
| 编造 id | 0 | 0 |

核对所选零件的真实分类，与模型陈述的用途完全吻合（`caption-kinetic-slam`→【字幕】、`ui-3d-reveal`→【产品与案例展示】、`data-chart`→【数据与地图】）。**"目录说明够不够模型判断"这个最大的不确定性已被排除**，剩下的是纯工程。

**但仍要补三个字段**，因为 P0-1d 的实测显示模型会因为看不到时长而严重超预算：上游 `vendor/hyperframes/registry/blocks/<name>/registry-item.json` 里本来就有 `description`（英文一句话说明）、`tags`、`duration`，冻结目录时只摘了 `name/title/category` 把它们丢掉了。补回成本极低。

12 套 style preset 无需补——`motion-style-presets.v1.json` 已有中文 `displayName` 与 `summary`（如"展览黄：纸张质感、深蓝文字和黄色光晕，适合文化与品牌叙事"），实测两个模型都据此选对。

### P0-1b　需求澄清轮（可跳过，不阻断一句话）

AI 在动手前把它的判断亮出来供确认或修改，形态见 P0-0。**判据**：不确认也能出片（默认路径不变长）；确认界面里改风格或片长，产出确实跟着变。

### P0-1c　逃生舱：零件不够时允许 AI 补写（兜底，非主路径）

**前置**：P0-1a 已建立"优先复用"的默认倾向。

**必须同时具备三样，缺一不可**：

1. **修复轮**——模型输出 → `lint_composition`/`check_composition` → 不过则把具体错误回抛给模型重写 → 再检。这是 T92 拿走的东西，要还回来；
2. **安全边界重设计**——`escape_untrusted_text` 那套（让文案贡献不出任何 ASCII 字面量）对"AI 写的代码"不适用，需要靠 `motion-render-sandbox-budget.v1.json` 的沙箱预算 + 门禁扫描来兜；
3. **可观测的选择**——`DESIGN.json` 要记录每一段是"复用零件"还是"AI 补写"，否则无法回答"这条片子为什么慢/为什么怪"。

**判据**：构造一个零件库明显覆盖不到的需求，AI 走补写路径且产物过门禁；同一需求在零件够用时不触发补写。

### P0-1d　时间轴必须有一个主宰（实测发现，比想象中要紧）

**2026-07-27 探针实测**：把 12 套 preset 与 134 个零件交给模型为一句话简报做编排，两个模型都选出了**合法且合理**的组合（零编造、分类与用途吻合），但**总时长双双超出沙箱上限 70% 以上**：

```
渲染沙箱硬上限          20 秒（SANDBOX_FRAMES_MAXIMUM 600 帧 / 30fps）
当前一句话入口固定      3 段 × 4 秒 = 12 秒

qwen3.7-max     4 个零件   34.0 秒   ❌
deepseek-v4-pro 5 个零件   36.3 秒   ❌
```

原因是**模型不知道零件有多长**——`data-chart` 单个 15 秒、`ui-3d-reveal` 13 秒，而 `lt-bold-block` 只有 4.8 秒。现有系统按「段数 × 每段固定秒数」算，隐含假设是每段等长，这个假设在用零件之后不成立。

**但"总时长 = 各零件时长之和"同样是错的**（产品负责人 2026-07-27 纠正，此处按纠正后的模型重写）：那等于让动效决定镜头长度。动效的作用是让画面内容出现时不生硬，**是点缀**，播完停在末帧等着即可；它不该决定这一镜停多久，但它确实是个约束——**动效没播完就切走看着很难受**。

正确的模型是：

```
镜头时长 = max(这段话说完要多久, 动效播完要多久)
总时长   = Σ 各镜头时长
```

即**内容主导、动效兜底**：语音 8 秒配 5.5 秒动效 → 8 秒（动效播完停住）；语音 3 秒配 5.5 秒动效 → 5.5 秒（等动效播完）。

### P0-1d′　零件其实有两类，目录里没有区分（编排质量的关键）

上面的"播完停住"策略只对一类零件成立。实测数据把这条界线画得很清楚：

| 零件 | 时长 | 性质 |
|---|---|---|
| `caption-kinetic-slam` | 无 | **点缀型**：字幕入场 |
| `lt-bold-block` | 4.8 秒 | 点缀型：身份条 |
| `logo-outro` | 6 秒 | 点缀型：品牌收尾 |
| `ui-3d-reveal` | 13 秒 | **内容型**：3D 逐步展开 |
| `flowchart` | 12 秒 | 内容型：决策树逐节点绘制 |
| `data-chart` | 15 秒 | 内容型：图表逐条展开 |

**内容型零件的动效本身就是信息**，"播完停住"不成立——不能让图表画到一半停住，也不能旁白说完 5 秒就切走、观众连图都没看全。这类零件里，**旁白要配合动效节奏来写**（写长些，或留白让观众看图），而不是反过来。

**所以模型选零件时要判断的是两件事**：这一段是「说话配点缀」（语音主导，挑短的点缀即可），还是「展示内容」（动效承载信息，文案配合它）。

**目录里目前没有这个维度**：`category` 分的是题材（字幕／数据与地图／产品展示），不是功能（点缀／内容）。这是 P0-1a 补字段时要一并加的。

**自动分档的可行性已经用全量数据验证过**（134 个零件按上游 `duration` 分档）：

| 档位 | 数量 | 实际构成 | 判定 |
|---|---:|---|---|
| 无 `duration` | 25 | 全是 `caption-*` 字幕与文字效果 | 点缀型 |
| ≤6 秒 | 40 | 全是转场（zoom / warp / dissolve / split） | 点缀型 |
| 6–10 秒 | 15 | `code-morph`、`news-ticker`、部分产品展示 | **待人工判定** |
| >10 秒 | 54 | `code-snippet-*` 代码演示、数据图表类 | 内容型 |

分档结果与 `category` 高度一致——无时长的全是字幕、≤6 秒的全是转场，这两类天然是"让画面出现不生硬"的点缀；>10 秒的全是动效本身在逐步呈现信息的。

**所以用 `category` + `duration` 双判据，119 个（89%）可自动分档，只剩 15 个中间地带需要人工看一眼。** 不必一开始就人工标注 134 条。

**另有两处必须先处理**：

1. ~~**部分零件没有 `duration` 字段**（实测 `caption-kinetic-slam`、`caption-editorial-emphasis` 均为 null），编排时不能假定它一定存在；~~
   **PC-01 全量核对后更正**：不是「部分零件漏填」，而是 block/component 的结构差异——`duration` 与 `dimensions` present 的恰好是 109 个 block。上游定义里 block 是自带画布与时间轴的独立子合成，component 是贴进宿主的片段，两者都没有。**所以 25 个 component 天然属于点缀型，分档问题只存在于 109 个 block 之间**，需要人工判的中间地带也随之缩小；
2. **上游其实提供了描述、标签和时长**，是我们冻结目录时丢掉的——`vendor/hyperframes/registry/blocks/<name>/registry-item.json` 里有 `description`、`tags`、`duration`、`dimensions`，而 `contracts/quality/motion-catalog.v1.json` 只摘了 `name/title/category`。**补回这三项是 P0-1a 的前置**，成本极低，收益是模型能按预算选而不是盲选。

**三个时长来源必须定主次**：画面（零件 duration）、语音（TTS 念完的实际秒数）、总预算（沙箱上限）。

**建议：语音主导，画面跟随。** 理由是 TTS 时长客观可测（合成完即知），而"把文案裁短以塞进画面"直接损伤内容且用户听得出来。

流程顺序有硬约束：

1. 模型写文案 + 选零件；
2. **先合成 TTS**，拿到每段语音真实秒数——必须在渲染之前；
3. 每段实际时长取 `max(语音时长, 零件 duration)`——语音没念完不切镜头，画面没播完也不切；
4. 总和超预算则回头压缩：减段、换更短的零件、或让模型改短文案；
5. 渲染时零件在自己的 duration 内播完，**剩余时间保持末帧而不是拉慢动效**——语音 8 秒配 5.5 秒动效，拉慢会拖沓，保持末帧更自然。

**判据**：给定一句话，产出的 mp4 里每段语音都在本段内说完；总时长等于各段 `max()` 之和；超预算时在渲染前就被拒绝并说明原因，而不是渲染完才发现。

### P0-1e　20 秒上限撑不起产品形态（需要产品决策）

`totalSecondsMaximum: 20` 来自渲染沙箱 `SANDBOX_FRAMES_MAXIMUM = 600` 帧（600 / 30fps）。而运营者在抖音、小红书发的短视频通常 **30 到 60 秒**。

**也就是说这条链路目前在物理上做不出一条正常长度的口播视频。** 接上 TTS 之后这个矛盾会立刻显性化：旁白说不完两句话就到顶。

**这不是 bug，是当初为渲染安全定的预算**，改它要付代价，方向有三个，需要产品定：

| 方向 | 代价 |
|---|---|
| 提高帧数上限 | 渲染时间与内存线性上涨；`renderWallMillisPerFrame` 400ms 意味着 60 秒片子约 12 分钟渲染 |
| 降低帧率（30 → 24 或 15） | 同样帧数换更长时间，但动效流畅度下降，字幕类零件影响最明显 |
| 分段渲染后拼接 | 单段仍受 600 帧限制，但总长不受限；代价是要处理段间衔接、音画同步累积误差，以及 ffmpeg 拼接这一层新的失败面 |

**建议倾向分段渲染**：它是唯一不牺牲画质也不线性放大单次渲染风险的路径，而项目已经有自编译 ffmpeg（`media-toolchain`）具备拼接能力。但它引入的音画同步累积误差需要在 P0-1d 的时间轴模型里一并设计，不能事后补。

#### 已定的做法（产品负责人 2026-07-27）

**先按默认值跑通 MVP，再逐步加上限并实测性能依赖**，找到用户可接受的范围；若放宽后确实慢，就在提交前告诉用户"这条大约要等多久"，让他自己决定。

这个顺序是对的，但有三件事必须一起考虑：

**一、600 帧不是随便定的，它是从 300 秒墙钟倒推的。** 契约里没写这个理由，但算一下就清楚（`renderWallSecondsBase: 30` + `renderWallMillisPerFrame: 400`）：

```
12 秒 =  360 帧 → 174 秒（2.9 分钟）  ✅
20 秒 =  600 帧 → 270 秒（4.5 分钟）  ✅  ← 当前上限，距 300 秒墙钟仅余 30 秒
30 秒 =  900 帧 → 390 秒（6.5 分钟）  ❌ 超墙钟 90 秒
60 秒 = 1800 帧 → 750 秒（12.5 分钟） ❌ 超墙钟 450 秒
```

**所以只提 `SANDBOX_FRAMES_MAXIMUM` 而不提 `wallClockSecondsMaximum`，用户遇到的不是「慢」，是渲染被 stall guard 杀掉、直接失败。** 两个数必须一起调。代价是 stall guard 会变钝：原本 5 分钟无进展即判挂死，放宽到 15 分钟意味着真挂死时用户要多等 10 分钟——这是放宽片长的隐性成本，值得在放宽时同步给渲染加进度心跳，让"慢"和"死"能被区分。

**二、渲染耗时预估可以直接给用户看**，公式已经在契约里，选完片长就能算——"这条 60 秒的片子大约需要 12 分钟"。比事后转圈强，也符合负责人的想法。

**三、`640×360` 已提到 1280×720（2026-07-27 已落地，`35e552a`）。**

做法不是放大舞台，而是 `deviceScaleFactor: 2`：CSS 舞台仍是 640×360（`composition_template` 的整套排版都是为它写的），浏览器以 2 倍分辨率重新光栅化，**布局规则一行未动**。契约新增 `deviceScaleFactor` / `outputWidth` / `outputHeight`，以后上 1080p 把系数改成 3 即可。

实测：包内真实 Chromium 渲染真实零件，factor 2 的每帧开销落在 factor 1 的跑动噪声内，**接近免费**；factor 3 也在预算内，但成本不是像素的线性函数，再提要重测。真实验收 BM-08 通过，ffprobe 从产物读出 `h264 1280×720 / 30fps / 90 帧`。

顺带补掉两处无人看守的手抄常量（`worker.mjs` 的视口、BM-08 写死的期望帧尺寸），现在都从契约派生。

**原始记录（决策依据，保留）：** `workers/motion_composition/worker.mjs:31-32` 定死渲染视口为 `640×360`，而上游零件的设计尺寸是 `1920×1080`（`registry-item.json` 的 `dimensions`）。

- 20 秒的片子**还能发**，只是短；
- 640×360 横屏发到抖音／小红书**基本没法看**（那边是 1080×1920 竖屏）。

按默认值跑通 MVP 没问题，但**在拿给用户试用之前分辨率要先解决**——否则 MVP 验证到的是"链路能跑通"，验证不到"这东西有用"：用户的反馈会全部集中在画质上，真正想验的编排质量反而看不到。

**两个数吃同一份预算**：提分辨率让每帧变慢（0.4 秒/帧会涨），提帧数让总帧数变多，双方都撞 `wallClockSecondsMaximum: 300` 与 `cpuSecondsAbsoluteMaximum: 2400`。因此"测试对电脑性能有多依赖"这一步应当**同时测两个维度**，用同一份预算去比哪个更值得花。

### P0-2　片长可控，去掉写死的 12 秒

**现状**：`MOTION_BRIEF_FILM_SECONDS = beatCountDefault × secondsPerBeatDefault`，界面文案自己写着"这个入口暂时不能改片长；需要别的长度请用下面的固定模板手工制作"。

### P0-3　给动效成片接上声音

**现状**：动效链路（`motion_authoring/` + `motion-*.ts`）**零音频痕迹**——没有配音、没有背景音、没有音效。

**判据**：一句话产出的 mp4 有可听的旁白，字幕/文案与旁白同源；静音是可选项而非默认。

## P4 · 视频剪辑接线

**现状**：有壳无芯。`VideoEditingWorkbench.tsx` **842 行** UI 完整；数据存 **localStorage**（`automation-tool.video-editing.local-draft.v1`）；后端 `api/` 下**没有任何 video_editing 端点**——领域层（`domain/video_editing.py`、`aliyun_ims_editing_*.py`）与 Provider 抽象都写了，**没有一条 HTTP 路由把它暴露出去**。提交必然 fail closed。

代码注释自己写着：`the cloud editing provider chain (VE-04+) is not connected yet... there are no editing jobs and submission always fails closed as unavailable.`

**这是全项目投入产出比最高的一块**：领域层、Provider 抽象、一致性契约、842 行 UI 都在，缺的只是中间那段接线——API 端点 + 网关从 local 切到真实实现 + 任务状态回流。

**判据**：从剪辑工作台提交一个任务，阿里云 IMS 真实返回成片，产物出现在成片列表并可发布。

## P5 · 微信自动化：另一条腿

**现状**：**零痕迹**。`weixin.qq.com` 0 个文件；`WeChat.exe`、`微信.app`、`uiautomation`、`pywinauto`、`AXUIElement` 全部零匹配。代码里唯一沾"微信"的是 `PublishPlatform.WECHAT_CHANNELS`，那是**视频号**这个发布目标，与控制微信客户端无关。

**必须先定技术路线再谈排期**：现有 RPA 全建在 Playwright + 内置 Chromium 上，而微信客户端自动化是**桌面 UI 自动化**——Windows 上 UIAutomation、macOS 上 Accessibility API。这是另一套技术栈、另一套权限模型（macOS 要辅助功能授权）、另一套失败矩阵（窗口焦点、多开、版本升级导致控件树变化）。**不能按"再加一个平台 Adapter"估算。**

**还要先回答的产品问题**：自动通过好友申请、自动打招呼、自动回复聊天，这些动作的风险等级远高于公开平台的评论——微信对自动化的容忍度、账号封禁风险、以及用户是否接受 App 操作自己的私人微信，都要先有结论。

**判据**：在真实微信客户端上完成一次"通过好友申请 → 发打招呼 → 回复一条消息"，且全程可见、可人工接管、可紧急停止。

## P6 · AI 编排入口

**现状**：前端 `features/` 下没有任何对话/助手页面。唯一的模型入口是动效创作 agent（`VideoStudio.tsx:1375` "Hand a one-sentence brief to the authoring agent"）。

也就是说 **AI 目前只能"把一句话变成一条视频"，不能"帮你决定该做什么"**。产品设想里的 AI 员工——读热点定选题、读私信定怎么回、编排一天的工作——还没有落点。

**它排在最后不是因为不重要，而是因为它依赖前面**：没有 P1 的感知能力，AI 读不到东西；没有 P2 的调度器，AI 的决定无法执行。**这三条合起来才是"AI 员工"，单独做 P6 只会得到一个聊天框。**
