## 0. 一句话结论

**「同名 `@font-face` + `unicode-range` 让汉字走中文字体」这条路在内置 Chromium 149 上成立，
不需要改 `vendor/hyperframes` 一个字节**——但成立的条件比预期严格一条：
**必须按零件实际请求的每一个 `(family, font-weight)` 组合各声明一条 CJK face**，
只声明 400、或声明 `font-weight: 100 900` 变量区间，**都不生效**，字还是掉回系统字体。

推荐形态：**一个 Noto Sans SC 可变字体 woff2 + 按零件扫描出的 (family, weight) 逐条声明**。
一个文件覆盖全部 7 个字重，实测两个字重的字形确实不同（不是假粗）。

体积（净增，安装包基线 `.local/release/release-package.json` 记录的 dmg 490,943,549 字节）：

| 覆盖档 | 单文件 woff2 | 占 dmg | 离线字体资产由 1.01 MB 变成 |
| --- | --- | --- | --- |
| GB2312（6,763 汉字） | 2,043,768 B（1.95 MB） | +0.42% | 2.96 MB（×2.9） |
| GBK（20,902 汉字） | 5,846,260 B（5.58 MB） | +1.19% | 6.59 MB（×6.4） |
| 全字符集（30,890 码点） | 7,782,440 B（7.42 MB） | +1.59% | 8.43 MB（×8.2） |

**建议取全字符集或 GBK，不建议 GB2312。** 理由在第 6 节：GB2312 缺的不是生僻字，是人名常用字。

## 1. 先纠正一件事：跨平台不一致比想的严重，而且不只是中文的问题

原始判断是「中文靠系统兜底 → 跨平台不一致」。全量扫过 134 个零件后，事实更糟：

```
134 个零件
├── 56 个   上游 <link> 了 Google Fonts 的 css2（离线目录里其中 54 个重写成了本地 CSS，
│           parallax-zoom / parallax-unzoom 的引用落在冻结文件清单之外）
├── 61 个   CSS 里写了具名字体，但整份文档从不加载任何 @font-face
└── 17 个   一个具名字体都没写，直接吃 body 默认
```

**也就是说 78 个零件（58%）今天连拉丁字母都在吃系统兜底**，不只是汉字。
被点名却从未装车的字体包括 `Archivo Black`（3 个零件）、`League Gothic`（2）、
`Oswald`、`Impact`、`Arial Black`、`Barlow Condensed`、`SF Pro Display`/`SF Pro Text`（12）、
`Menlo`/`Monaco`/`Consolas`/`Courier New`（各 24）、`Segoe UI`（13）、`Helvetica`（13）。

这一条在本次实测里有直接证据。对照组 A（今天的行为）渲染 `lt-bold-block`，
`#lt-tag` 的拉丁字符报的是 `SpaceMono-Bold` 且 `isCustomFont: false`——
**那是本机 `~/Library/Fonts` 里装着的 SpaceMono-Bold.ttf（Powerline 字体包带的），不是产品带的。**
换一台没装的机器，同一个零件的同一行字就是另一个字形。这正是 BM-16「同输入同版本出同结果」
要挡的那类漂移，而它今天已经在了。

**本任务只解决汉字那一半。** 拉丁那 78 个零件要不要一起补齐字体，是另一个决策，见第 8 节。

## 3. 实测：内置 Chromium 到底怎么选 face

环境：`.local/desktop-e2e/embedded-browser/macos-arm64/…/Google Chrome for Testing`，
`Chrome/149.0.7827.55`，用 `worker.mjs` 生产渲染会话的同一组 flag
（`--headless --remote-debugging-pipe --disable-lcd-text --disable-font-subpixel-positioning
--force-color-profile=srgb --proxy-server=127.0.0.1:9` …）。

被测零件：`lt-bold-block`，取自离线目录的**未经修改**副本，只把两个文本节点换成中文：
`Maya Chen` → `星云科技 Nebula`，`Host · Neuroscientist` → `主持人 · 神经科学家`。
视口 1920×1080，时间轴 seek 到 2.0 s。

测的是 `CSS.getPlatformFontsForNode`——浏览器逐元素报告**哪个物理字体画了几个字形**。
这个数字没真跑过写不出来。

零件自己的 CSS 请求：`#lt-name` = `"Archivo Black"` / 400，`#lt-tag` = `"Space Mono"` / 700。

| 变体 | 注入了什么 | `#lt-name`（400） | `#lt-tag`（700） |
| --- | --- | --- | --- |
| **A 对照** | 什么都不注入 | PingFang SC Regular ×11（含拉丁） | 系统 Space Mono Bold ×3 + PingFang SC Semibold ×8 |
| **B** | 拉丁 400/700 + CJK@**400** | PingFang ×7 + **Noto Sans SC ×4** ✅ | Space Mono Bold ×3 + **PingFang SC Semibold ×8** ❌ |
| **C** | B + CJK@**700** | 同 B ✅ | Space Mono Bold ×3 + **Noto Sans SC ×8** ✅ |
| **D** | 可变字体，声明 `font-weight: 100 900` | PingFang ×7 + Noto ×4 ✅ | **PingFang SC Semibold ×8** ❌ |
| **E** | 同一个 400 文件，分别声明成 400 和 700 | ✅ | **Noto ×8** ✅（但字重是 Regular，见下） |
| **F 推荐** | 一个可变 woff2，按零件的 (family,weight) 逐条声明 | ✅ `NotoSansSC-Thin_Regular` ×4 | ✅ `NotoSansSC-Thin_Bold` ×8 |

原始 JSON 在 `.local/embedded-browser-video-studio/pc-13-evidence/reports/variant-*.json`。

### 3.1 关键发现：字重分桶发生在 unicode-range 之前

B 和 D 是本次最有价值的两个失败。按 CSS Fonts 规范的字面读法，
应该先用 `unicode-range` 筛出覆盖该码点的 face，再在其中做字重匹配——
**Chromium 149 不是这么做的**：它先按 (weight, width, slope) 把同名家族的 face 分桶，
选中最匹配请求字重的那个桶，**再**在桶内解析 `unicode-range`。

于是在变体 B 里，家族 `Space Mono` 有三条 face：拉丁@400、拉丁@700、CJK@400。
元素请求 700 → 命中 {700} 桶 → 桶里只有拉丁 face → 汉字无覆盖 → **直接掉系统兜底，
根本不回头看 {400} 桶里那条能覆盖汉字的 CJK face**。
`document.fonts` 的状态是直接证据：变体 B 的 `Space Mono/400`（CJK 那条）始终是 `unloaded`，
浏览器压根没打算用它。

变体 D 说明 `font-weight: 100 900` 也救不了：变量区间 face 一样输给精确 `700` 的 face。
（`#lt-name` 那侧 D 是成功的——因为 `Archivo Black` 家族只有那一条 face，桶唯一。）

**结论：CJK face 必须按零件实际请求的字重逐条声明。** 这条如果漏掉，
就会出现「大部分零件中文正常、少数零件中文莫名其妙掉回系统字体」这种极难归因的偶发问题。

### 3.2 一个可变字体文件能不能供全部字重：能

变体 E 证明「同一个静态 400 文件声明成 700」技术上能命中，但渲染出来是 Regular 粗细——
浏览器相信了 face 的自述，不做合成加粗，于是拉丁是 Bold、汉字是 Regular，视觉打架。

正解是可变字体。单独做了一次对照（`render/weight-check.png`）：
同一个 `nssc-variable-full.woff2`，只声明 400 和 700 两条 face，渲染同一串汉字，
Chromium 分别报告 `NotoSansSC-Thin_Regular` 与 `NotoSansSC-Thin_Bold`
（`_Regular`/`_Bold` 后缀是 Chromium 给**派生变体实例**的命名，证明 wght 轴确实被设到了 400 和 700），
图上两行字的笔画粗细肉眼可辨。

> `postScriptName` 里的 `NotoSansSC-Thin` 是可变字体默认实例的名字（wght 轴默认值 100），
> 不代表渲染成了 Thin；后缀才是实际用到的实例。

## 6. 体积：全部实测数字

### 6.1 为什么不能直接用 Google 的分发形态

Google Fonts 把 Noto Sans SC 切成 **101 个 unicode-range 子集**分发。在线场景下浏览器按需只取几个；
离线全量落盘则一个都不能少（用户可能打任何字）。实测总量：

| 形态 | 文件数 | 字节 |
| --- | --- | --- |
| wght 400 | 101 | 2,410,336（2.30 MB） |
| wght 500 | 101 | 2,441,496（2.33 MB） |
| wght 700 | 101 | 2,461,436（2.35 MB） |
| wght 900 | 101 | 2,429,544（2.32 MB） |
| 可变 100..900 | 101 | 4,514,816（4.31 MB） |
| （参考）Noto Serif SC 700 | 101 | 3,256,008（3.11 MB） |

这些数字看着比单文件小，但**覆盖也小**：101 个子集的码点并集只有 **15,605 个**，
而完整字体的 cmap 是 **30,890 个**。不是同一件商品。

**真正的否决理由是硬限制，不是体积**：`workers/motion_composition/worker.mjs:56`
`SANDBOX_ASSETS_MAXIMUM = 128`，第 345 行 `allowedAssets.length > SANDBOX_ASSETS_MAXIMUM` 直接拒绝。
**101 个子集一个字重就吃掉 128 个名额里的 101 个，两个字重（202）直接被门禁打回。**
合并成一个文件只占 1 个名额。

### 6.2 单文件 woff2（自己从锁定的上游 TTF 构建）

| 覆盖档 | 码点 | 字形 | 静态 400 | 静态 700 | **可变 100–900** |
| --- | --- | --- | --- | --- | --- |
| GB2312 + 基础标点 | 7,728 | 8,382 | 1,080,924 B | 1,108,140 B | **2,043,768 B（1.95 MB）** |
| Google Web SC 同覆盖 | 15,728 | 14,425 | 1,963,224 B | 2,014,276 B | **3,664,824 B（3.49 MB）** |
| GBK + 基础标点 | 22,056 | 22,741 | 3,134,624 B | 3,220,516 B | **5,846,260 B（5.58 MB）** |
| 全字符集 | 30,890 | 31,036 | 4,193,128 B | 4,314,792 B | **7,782,440 B（7.42 MB）** |

只要用可变字体，**字重数量不影响体积**——7 个字重和 1 个字重是同一个文件。
若走静态实例，每多一个字重就多付一份（400 + 700 ≈ 8.4 MB，比可变全字符集还贵）。
这是选可变字体的第二个理由（第一个是 3.2 节的真字重）。

## 7. 裁字集的代价（这一节请产品负责人重点看）

裁到 GB2312 只要 1.95 MB，很诱人。代价是**生僻字变豆腐块**，而 GB2312 的「生僻」判定很宽：

从人名、网络用语里随手取 56 个字，GB2312 缺 **23** 个：

```
镕 璟 玥 頔 喆 沄 燚 靐 囧 溦 珺 婳 昫 骉 犇 皛 龘 兲 巭 嘦 嫑 覅 烎
```

`璟`、`玥`、`喆`、`珺`、`婳`、`犇`、`镕` 全是真实人名用字；`囧` 是网络常用字。
运营口播稿、嘉宾姓名、品牌名撞上其中任何一个，画面上就是一个方框，而且**没有任何环节会报错**——
渲染成功、门禁全绿、片子里一个豆腐块。

量化差距：URO 区汉字 GBK 覆盖 20,902 个，GB2312 只覆盖 6,763 个，**差 14,139 个**。

**建议：取全字符集（7.42 MB，+1.59%）。** 理由是这 5.5 MB 的差价买的是
「永远不会出现豆腐块」这个确定性，而本产品的输出是要发到公开平台的成片，
出一次豆腐块的品牌代价远超 5 MB 安装包。若产品负责人认为必须省，GBK（5.58 MB）是次优——
它覆盖 20,902 个 URO 汉字，上面 23 个缺字里除 `靐/骉/皛/龘/巭` 等极端造字外都在。
**不建议 GB2312。**

## 8. 落地方案与还没做的事

### 8.1 注入点：应该在 RenderJob 工作区副本，不是离线目录的 CSS

有两个可选注入点：

| 方案 | 覆盖 | 代价 |
| --- | --- | --- |
| 往 `stylesheets` 的 face 列表里加 CJK face | 只有那 56 个 `<link>` 了字体 CSS 的零件 | **零代码改动**，纯契约数据 |
| 渲染期往工作区副本注入生成的 `<style>` | 全部 134 个 | 需要在文案替换那一步顺手生成 |

推荐第二个：78 个零件根本没有 `<link>`，第一个方案够不着它们；
而且 PC-03 已经定了「替换发生在运行期写入 RenderJob 工作区的副本」，
CJK face 的生成天然属于同一步——扫零件 CSS 拿到 `(family, weight)` 对，逐条生成 `@font-face`。

生成量很小，实测 134 个零件的 `(family, weight)` 对：**中位数 2、均值 2.8、最多 18**
（`transitions-distortion` / `transitions-grid`），全目录并集 70 对，
出现过的字重只有 300/400/500/600/700/800/900 七个。每个零件几百字节 CSS。

`allowedAssets` 只需 +1（那一个 woff2）。`agent.py:lint_composition` 对 `url(...)` 的
`undeclared_asset` 检查不看扩展名，woff2 只要在工作区资产清单里就放行。

### 8.2 构建期怎么拿到那个文件

这里有一个必须正视的代价：**合并版 woff2 没有现成的下载地址**。
现有锁清单要求每个 artifact 有 `downloadUrl`（`test_offline_motion_catalog.py` 断言
`startswith("https://")`）。Google 只按 101 子集分发，jsDelivr 的 `@fontsource` 同理。
所以只能：

1. 把**上游可变 TTF**（17,772,300 B，第 5 节的 pin）作为 artifact 锁进清单；
2. 在 `build_offline_motion_catalog.py` 里加一步：用 fonttools + brotli 把它子集化并转 woff2；
3. 产物摘要由既有的 `generated.aggregateSha256` 重算比对覆盖，门禁仍然可重算。

代价是**新增构建期依赖 fonttools + brotli**，且构建机需要能跑它。
本次实测用的就是这条链路（fonttools 4.63.0），单档位耗时 10–35 秒。

### 8.3 契约还要动三处

`test_offline_motion_catalog.py` 对 face 有三条断言，加中文时都会撞上：

- `face["subset"] in lock["keptFontSubsets"]` → 要把 `chinese-simplified` 加进 `keptFontSubsets`；
- `face["artifactPath"] in artifact_paths` → woff2 要作为 artifact 入清单；
- `face["family"] in lock_families` → **这条是设计冲突**：`fontFamilies` 是「家族名 → 许可证」的映射，
  而我们要做的恰恰是「`Anton` 这个家族名下挂一份 Noto 的字节」。
  硬塞会让权利台账说谎（`Anton` 的 `licenseFileSha256` 指向 anton 的 OFL，字节却是 Noto 的）。
  **权利归属需要从「按家族」改成「按 artifact」**，否则 BM-12 那套权利审计会失真。
  这一处是本任务发现的、原计划里没有的工作量。

### 8.4 没做什么

- **没有改任何契约。** `offline-motion-dependencies.v1.json`、`motion-asset-overlay.v1.json`
  一字未动。覆盖档位是产品决策，等拍板；
- **没有碰 `vendor/hyperframes`。** `git status` 里 submodule 干净；
- **没有解决拉丁那一半。** 78 个零件的具名拉丁字体仍未装车，它们的英文今天仍随机器变化。
  要不要一起补，需要单独评估——粗算 `Archivo Black`、`League Gothic`、`Oswald`、
  `Barlow Condensed` 等几个 OFL 字体加起来在百 KB 量级，比中文便宜得多；
  `Menlo`/`SF Pro`/`Segoe UI`/`Helvetica` 是系统专有字体，不能再分发，只能换字或接受；
- **没有处理那 17 个不写 `font-family` 的零件。** 它们吃 `sans-serif` 默认，
  要让它们确定就得替它们指定字体，那等于改设计，需要单独决定；
- **没有覆盖 Windows。** 本次全部在 macOS 上测。字重分桶是 Blink 的字体匹配逻辑、与平台无关，
  但系统兜底字体（微软雅黑 vs 苹方）显然不同，落地任务需要在 Windows 上复测一遍变体 A 与 F。
