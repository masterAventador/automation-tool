# T130 动作授权私钥两端各生成一把，而且没有任何东西会发现

日期：2026-07-27
状态：**配置已对齐，防复发门禁未做**（后者才是这条登记的目的）
执行：真实云主机 `49.233.213.109`（客户 Demo 环境），未改任何产品代码。

---

## 1. 怎么发现的

给这台服务器出 Demo 包时，顺手核对"服务端持有的私钥"与"包里编译的公钥"是否配对：

```
服务端 /run/secrets 私钥派生的公钥   V-k9YXpPSuWBu0SB3Untnsn6t294W4qQf9ZVh2E1wbg
包里编译进去的公钥                   gfJEBEJ9s-IlbyNfXamYsWLgODkeInRoHQsoNNGPDyk
```

**不是一对。** 服务端用它签发动作授权 token，App 用包内公钥验签——两端对不上，包装上去也签不出它接受的动作授权。

**最险的地方是它完全不报错**：`/api/v1/health` 200、`/api/v1/version` 200、账号能登、两个容器 healthy，全绿。要发现它只能主动去比对公钥。

## 2. 根因

`deploy/cloud/deploy_cloud_demo.py:394`

```python
ensure("actionAuthorizationPrivateKey", lambda: base64url(secrets.token_bytes(32)))
```

部署器把它和数据库口令、Pepper、指纹密钥一视同仁：**缺失时随机生成一把**。但它和那些不同——**它是唯一一把两端都要用的密钥**，另一端在打包机上。

`docs/development/FIX-customer-demo-package-build.md` 写过"同一份文件既喂构建（取公钥）又投递到服务端 Secret"，但那是一句描述，**没有任何脚本或门禁执行它**，于是从来没人做过。

**波及范围不止新包**：首台 Mac 07-27 09:29 出的那个 469 MB 包，编译的也是 `gfJEBEJ9s-…`，对这台服务器同样无效。

## 3. 本次已做

| 动作 | 证据 |
|---|---|
| 备份服务端密钥文件 | `/etc/automation-tool-demo/secrets.json.bak-20260727T115450` |
| 换成运维保管的那把 | 私钥全程只走 stdin，不进 argv、不进 shell history、不进日志 |
| 重新投递并重启 | `DEPLOY_EXTRA_ARGS=--skip-build deploy/cloud/deploy.sh`，`DEPLOY_EXIT=0` |
| 复核 | 容器内 `/run/secrets/action-authorization-private-key` 派生公钥 = `gfJEBEJ9s-IlbyNfXamYsWLgODkeInRoHQsoNNGPDyk` = 包内公钥，逐位一致 |
| 服务仍健康 | `https://at.xuanbai.tech/api/v1/health` 200 |

**换密钥的代价为零**：`action_risk_authorizations` 与 `action_risk_results` 都是 0 条，从来没签发过。若非空则旧 token 会全部失效。

投递方法与核对方法已写进 `deploy/cloud/README.md` §5。

## 4. 未做（这条登记的目的）

文档挡不住下一次——换台机器部署、或有人重建 `secrets.json`，同样的漂移会再来一次，而且照样全绿。

**该做的是门禁**：部署器在启动 Control Plane 之前，比对"服务端私钥派生出的公钥"与"本次要服务的那个包所声明的动作授权公钥"，不一致即拒绝部署。

这要求部署侧能知道包声明了什么公钥——最直接的做法是让出包把它写进一份可投递的清单（`build_release_package.py` 已经在日志里报告这个公钥），部署时读它比对。具体形态待设计。
