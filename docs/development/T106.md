# T106 — 五个「我们自己写错了」不再被说成「你的描述太抽象」

> 日期：2026-07-27
> 分支：`refusal-surface`（基点 `6fd7d87`）
> 状态：**✅ 已完成**
> 前置：T90b（把失败原因分类落在 `contracts/video/motion-authoring-refusal.v1.json`，Python 与 Rust 都从它读、不留第二份）

## 一、要解决的是什么

台账登记的是四个 token：`agent_workspace_required`、`agent_workflow_reference_required`、
`agent_not_a_motionauthoringtools_instance`、`agent_tool_surface_does_not_match_the_closed_allowlist`。

它们分别是：工作区没传进去、锁定的工作流引用没传进去、tools 参数类型不对、工具面和闭集
对不上。四个都在 `MotionAuthoringAgent.__init__` / `verify_closed_tool_surface` 里，
**用户输入的任何东西都到不了这些分支**——`entry.py` 先把请求校验成 `AuthoringWorkspace`，
再自己把这些对象构造出来。所以它们只可能意味着我们发了一个有 bug 的版本。

而它们全都从拒绝通道出去，界面照着 `authoring_refused` 那条文案说
「请换一句更具体的描述后重试」。这正是 T90 划清的那条线的另一副面孔：
**我们的缺陷，用用户的错来措辞。** 用户既改不动它，那句被要求重写的描述也从头到尾没被读过。

### 排查中发现的第五个

`agent_tools_require_an_authoringworkspace` 是同一族的第五个。
`MotionAuthoringTools(...)` 的生产调用点只有 `entry.py:459` 一处，传的永远是上一行刚校验
通过的 `AuthoringWorkspace`（其余调用点全在 `scripts/test_motion_authoring_agent.py` 和
`scripts/run_bm_05_acceptance.py` 这些测试/验收脚本里）。判据与前四个逐字相同，漏掉它等于
让同一个 bug 在同一个文件里活下来，所以一并纳入，本记录第五节列了证据。

## 二、结论：新增一个类，而不是新增一套机制

T90b 已经把机制建好了。`nonRefusalOutcomes` 是「哪些 token 不是拒绝」的分类表，
Python（`entry.py:53` 的 `_load_refusal_contract`）和 Rust（`motion_video_studio.rs:36`
的 `include_str!`）读同一份文件。所以这条任务落在契约本身：**把这五个 token 归到正确的类里。**
没有新建第二份表，没有新增字段。

新增的类叫 `executor_defect`，报的码是 `authoring_crashed`。

### 为什么不并进已有的 `app_request_invalid`

两个类今天报同一个码，用户的下一步动作也一样（重试）。合并看起来更省。不合并的理由是：
**类名同时就是子进程写在协议里的 `status`**（T90b 的设计，见该记录第二节）。
`app_request_invalid` 是一句关于「请求」的断言——App 送来的请求不合法。
把一个我们自己接错线的构造函数标成 `app_request_invalid`，等于往 App 唯一用来推理的那个
字段里写进一句假话。这份契约存在的全部原因就是「贴错标签会把人支去修错的地方」。

而且合并之后不可逆：今后要区分（例如内部缺陷单独上报），信息已经没了。
不合并的代价是一个名字。

Rust 侧 `code_for_non_refusal_class` 的 `_ => authoring_crashed()` 兜底已经覆盖新类，
所以生产代码里没有加 match 分支——`app_request_invalid` 本来也走的这条兜底。
真正需要显式登记的是测试里的 `expected_code_for_class`：它对不认识的类直接 panic，
这才是「契约加了类而 Rust 没跟上」会当场红掉的门禁。

## 五、真实边界

- 五个 token 由**真实调用**产生，不是 monkeypatch 出来的字符串：
  `MotionAuthoringAgent(workspace=<非 AuthoringWorkspace>, ...)`、
  `MotionAuthoringAgent(workflow=<非 WorkflowReference>, ...)`、
  `verify_closed_tool_surface(<非 tools>)`、
  `verify_closed_tool_surface(<多一个公开方法的子类>)`、
  `MotionAuthoringTools(<非 workspace>)`；
- Rust 侧每个断言都真的 spawn 一个子进程，让它把协议文档写到 stdout 再非零退出，
  走的是 `run_motion_authoring` 这条生产路径，不是进程内直调分类函数；
- 用户可见的那句话没有改：这五个 token 现在落到 `authoring_crashed`，
  用的是它原本就有的文案「是我们这边出错了，请重试」。
  `VideoStudio.test.tsx` 里既有的两条用例继续守着「只有 `authoring_refused` 才准说换一句」。

## 六、失败矩阵

| 情况 | 行为 |
|---|---|
| 旧打包子进程把这五个 token 写在 `status: "rejected"` 上 | Rust 以 token 为证据判类 → `authoring_crashed`，不再是 `authoring_refused`（用例覆盖） |
| 新子进程写 `status: "executor_defect"` | 同上，`authoring_crashed`（用例覆盖） |
| status 与 reason 属于不同类（自相矛盾的答复） | 既有用例 `an_answer_that_contradicts_itself_is_reported_as_our_failure`：判给我们，绝不判给用户 |
| 契约新增类而 Rust 没跟上 | `expected_code_for_class` 直接 panic，`every_non_refusal_reason_in_the_contract_reaches_its_own_code` 当场红 |
| 同一 token 同时出现在两个类 | Python `_outcomes_are_declared` 与 Rust `outcomes_are_declared` 都判重叠即整份契约失效（既有） |
| 契约里 token 拼错 | 后端用例第一条断言 `produced == expected` 会红：真实 guard 产出的 token 与契约对不上 |
| 只认识 `rejected` 的旧 App 收到 `executor_defect` | 退回「我们没能完成」，方向正确（T90b 既有设计） |
