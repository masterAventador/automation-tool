## 1. 破在哪

AI-first 改版（`c4d0d14`）把单一的工作台标题换成了分区标题，并把视频工作台挪到分段
控件后面。

**Playwright 那 78 条用例毫发无伤**，因为 `frontend/e2e/navigation.ts` 早就把路线收进
了一个模块，改版那一提交顺手更新了它。

**WebdriverIO 这 48 条里有 46 条把路线手写了一遍**——
`//li[contains(@class,'ant-menu-item')…工作台]` 接 `h2=RPA 运营工作台`——所以一次改版
把它们一起打断了。没人看见，因为**没有任何门禁成批跑这个套件**：每条 spec 由各自的
`run_*_acceptance.py` 驱动，坏掉的那条只有下次谁需要那项验收时才会撞见。

## 2. 两种破法，第二种才是要命的

| | 处数 | 后果 |
| --- | --- | --- |
| 正向断言消失的标题 | 44 | 下次谁跑谁看见红，吵但诚实 |
| **反向**断言「工作台不该出现」 | 5 | **永远绿** |

第二种是这样的句子：

```ts
assert.doesNotMatch(await bodyText(), /RPA 运营工作台|atas1|atrs1/);
```

它是「未登录 / 实例被吊销时不得进工作台」的那道闸。那个字符串现在产品里根本不存在，
所以**即使工作台整个挂在屏幕上，这条断言也照样通过**。

一道不可能失败的闸，比没有闸更糟：它在报告一种它并不提供的安全。

## 3. 修法：一个模块，加一条把它钉住的链

新增 `frontend/e2e-tauri/navigation.ts`，与 Playwright 那份对应：
`waitForStartup` / `openWorkbenchSection` / `openVideoStudio` / `openMaterialVideoStudio` /
`openVideoEditing` / `openPublishingWorkspace` / `openAutomationRuns` / `openTaskCreate` /
`openSettings`，外加 `workbenchIsMounted` 与 `WORKBENCH_MARKERS`——后两个专门给反向断言用，
问的是 shell 本身而不是某个会被改掉的标题字符串。

46 条 spec 全部改走这个模块。

**门禁 `scripts/test_desktop_e2e_navigation.py`（已在 `run_script_tests.py` 的自动发现里）**
守四条：

1. 模块必须存在；
2. 没有 spec 再提那个消失的标题（正向必红、反向必绿，两种都不许）；
3. 没有 spec 自己手写侧边栏 XPath；
4. **两个模块必须命名同一批目的地与分段**。

第 4 条是让它不再腐烂的那条链：Playwright 套件是**真的在跑的**，侧边栏一改名它就红，
这条门禁再逼着桌面模块跟上。桌面套件自己做不到这一点——它没有成批运行的入口。

## 4. 顺带修的失效锚点

改版动的不止导航：

- `新建任务` 曾是侧边栏入口，现在是 自动化 → `新建运营任务` 按钮（9 处）；
- `视频剪辑` 曾是独立入口，现在是 创作 下的 `轻量剪辑` 分段（1 处）；
- `h2=视频制作` 没有了，创作页现在是 h3 的方式名（4 处）；
- `设置与诊断` 作为菜单项已改名 `设置`（页面标题里仍在，没动）。

**第一轮说「这类失效锚点为 0」是错的，审查逐文件核出至少 5 处仍在**：
`diagnostic-export.spec.ts:13` 与 `executor-lifecycle.spec.ts:40` 的 `h2=设置与诊断`
（产品现在渲染 `设置`）、两处 `h2=平台状态`（现在是 `账号与平台`）、
`plain-language-comprehension.spec.ts:202` 的 `h2=视频剪辑`（已无此标题）。
第一处尤其明显：它就在我本轮改的 `openSettings()` 的**下一行**——改了导航、
没改紧跟着的断言。这些已在第二轮修掉。

## 5. 我自己犯的错（三次，都在这一项里）

#### 5.1 批量替换把断言方向搞反

批量脚本按 `assert.doesNotMatch(await bodyText(), /` 这个形状插入新断言，
**而原文只有三处 regex 里真的提到工作台**。于是两处被插到了「登录成功之后」和
「已登录、断言登录页不该出现」的分支里——**断言方向正好反了**。

编译能过、lint 能过、门禁能过，只有肉眼看 diff 才发现。已把那两个账号 spec 整个回退，
五处逐个手工改。

这条记在这里，是因为它正是本条线反复栽的那个形状的又一次：一个看起来安全的批量替换，
在少数分支上改变了语义，而所有机械检查都是绿的。

**同一个错误当天犯了第二次**：给八处等待自动补导航时，脚本把 `openAutomationRuns()`
插到了「点击『查看运行详情』之后」——那次点击本身已经导航到详情页，再插一次是走回列表。
也是肉眼看 diff 才发现。**结论：这种改动不能用形状匹配批量做，只能逐文件判断。**

### 5.2 我报了一条根本没通过的验收

上一轮我说「CQ-01 也通过了」。**它没有。** 它在 `pnpm build:tauri:video-studio-test`
那一步失败，退出码 1，日志末尾是完整的 traceback。

我看到的「通过」是日志**中段**属于另一个门禁（品牌用语扫描）的两行绿字，
而我把命令写成了 `cmd > log 2>&1; echo "exit=$?"`——**harness 报的是 `echo` 的退出码**，
永远是 0。两个错误叠在一起，就把一次失败读成了成功。

改法有两条，都做了：命令不再拼 `; echo`，退出码直接由被测命令决定；
以及把这次的真实结论写进本文件，不留一条假的绿。

### 5.3 我的「tsc ok」一整天都是空的

CQ-01 那次失败的**真正原因**是 T21 引入的三个类型错误
（`material-video-studio-gateway.test.ts` 里 `modelThinking` 成了必填而调用点没跟上）。

它们躲过了我每次改动后都跑的 `npx tsc --noEmit -p tsconfig.json`——因为
`frontend/tsconfig.json` 是 solution 文件（`"files": []` + 两个 references），
`-p` 它等于**编译一个空文件列表**，退出 0、无输出，和「整个前端类型干净」
长得一模一样。正式入口是 `tsc -b`，仓库里每个 `build:*` 脚本用的都是它。

已加门禁 `scripts/test_typecheck_entrypoint.py`：任何文档、脚本、CI 配置里
再出现 `tsc -p tsconfig.json` 就红。它同时断言那份 solution 配置**确实**是空的——
哪天有人给它加了 `include`，这条门禁该被重写而不是继续守一条不再描述现实的规则。

## 7. 真实边界 — 这一项**没有**证明什么

**46 条里只有 2 条真在 App 上跑过。** 其余 44 条做到的是：不再引用已经消失的界面，
类型与 lint 干净，导航走共享模块。**它们能不能通过，仍然是未知的**——每条都要各自的
验收脚本、真实服务和数分钟起步的时间，其中若干条还需要真实平台账号。

改版可能还改了这些 spec 断言的**流程**而不只是**字符串**，那种失效没有任何机械手段
能查出来，只有真跑才知道。

所以状态是 `🔍 待验收`，不是完成。补验收的办法是把这些 `run_*_acceptance.py` 逐个跑通，
那是一件按项排期的事，不该塞进这一项假装做完了。

### 9.1 一条是产品真缺陷：强制更新只有打开设置才看得见

`update-ui` 开机后等「发现新版本 0.2.0」，25 秒没等到。不是 spec 过期。

`AppUpdateCenter` 的设计是**提示 Modal 无条件渲染**，`showSettings` 只额外加一张
管理卡——它挂在哪里，提示就只能在哪里弹。改版把它挪进了 `WorkbenchShell` 的
`showingSettings ? … : …` 那一支，于是提示的可见性被绑在「用户此刻正好在设置页」上。

可选更新如此已经不好，**强制更新如此是真问题**：用户可以永远不打开设置，
而那条更新的语义正是「不更新就不能继续用」。

已修：不在设置页时外壳自己挂一份 `showSettings={false}`，任一时刻只有一个实例。
组件层补了两条复现（可选 + 强制），并在真实 App 上由 `run_h8_21` 两个场景验收通过。

**这条修复过程里我自己差点埋一个假绿**：断言方式在红绿之间改过（Ant 的 Modal 会
留一个隐藏预渲染节点，要取最后一个并等过动画），所以最初那次红**不能**算这次绿的
对照。撤掉产品修复、重跑**新**断言、确认仍红，控制实验才算成立（规则 §8.3）。

### 9.2 四处是 spec 断言了产品不再有的东西

| 处 | 断言 | 现实 |
| --- | --- | --- |
| `video-studio.spec.ts:17` | `打开完整制作界面` 渲染为禁用态 | 按钮已不存在 |
| `video-creation-methods.spec.ts:58` | 同上 | 同上 |
| `video-creation-methods.spec.ts` 十个 `dt` 标签 | 各出现两次 | 取到 0——改版把十行对比收进了每张卡片的折叠面板，默认收起 |

前两处同源：`OperationsWorkspace` 是唯一渲染 `VideoStudio` 的地方，且**无条件**传
`embedded`，整个打开器被换成一条提示。

第三处的展开逻辑**没有在 spec 里再写一份**，抽进了 `navigation.ts` 的
`openCreationMethodCards`——`plain-language-comprehension.spec.ts` 已经为同一件事
付过一次代价，两份手写路线正是本任务存在的理由。helper 里锁住了两个已付学费的坑：
`card.$("//…")` 从文档根搜（第二次循环会把第一张卡又合上，必须 `.//`），
以及折叠有动画（点击返回那一刻行还不在 DOM 里）。

### 9.3 一处是期望取错了契约小节

`run_bm_08_acceptance.py` 量的是**成片**，读的却是「单次渲染的画布」
（640×360 @2 = 1280×720），而 PC-18 之后成片有自己的声明（1920×1080）。

讽刺的是这个脚本自己的注释写着：

> The frame size this acceptance expects is derived, never restated. Hard-coding
> it here is what made this run red after the canvas contract raised its device
> scale factor: the render was correct and the expectation was stale.

**它确实在派生——派生自错误的那一节。** 「不要写死」不蕴含「派生就对了」，
派生源同样会过期，只是过期得更隐蔽。

## 10. 顺带查出的一个产品状态，未擅自处理

`VideoStudio` 的非 embedded 分支（`打开完整制作界面` 按钮 + 整套打开独立界面的
流程）已经是**不可达死代码**——唯一的渲染点无条件传 `embedded`。而 embedded 那支
自己写着「当前真实内嵌服务尚未接入」。

也就是说**「智能素材成片」现在两头都通不了**。按「代码删除规范」死代码该删，
但删哪一头取决于产品打算走内嵌还是独立窗口，属产品决策，已记录待定。

### 10.1 它已经把一条验收堵死了（2026-07-29 补）

`run_im_05_acceptance.py` 跑 `material-video-webui.spec.ts` 时红在
`section[aria-label='视频制作工作区']` 找不到。表面看是这条 spec 停在设置页、
没导航到创作页——**但把导航补上也过不了**，因为它下一步要点的正是
`打开完整制作界面`。

**这条 spec 存在的全部目的，就是验证「智能素材成片的 WebUI 能从产品入口打开」。**
那个入口现在不存在。所以它不是写坏了，是**它要验的能力没有入口**。

因此这条**不改 spec**。把断言改成迁就现状，等于把「这个功能用户够不着」这件事
从红色改写成绿色——正是本任务 §2 记的那种「一道不可能失败的闸比没有闸更糟」。
它保持红，直到产品决定「智能素材成片」走内嵌还是走独立窗口。

**这也是本轮补验收最有价值的一条**：它把一个原本只是「死代码，待定」的观察，
变成了「有一条产品能力目前无人可达，且有一条验收正在为此变红」。

## 11. 剩下的，以及为什么「谁跑这条 spec」本身要查一遍

48 条里 10 条已验，**38 条未验**。

排期前先撞到一件事：**同一套 spec 有三种被驱动的方式**，所以「这条 spec 归谁跑」
不能靠搜名字：

| 方式 | 例 |
| --- | --- |
| 验收脚本直接传 `--spec` | `run_bm_06` 一次带四条 |
| 验收脚本点名 wdio 配置 | `run_h8_21` → `wdio.update-ui.conf.ts` |
| 验收脚本调 pnpm 脚本，由它再指向配置 | `run_t3_19` → `pnpm test:task-lifecycle-tauri` → `wdio.task-lifecycle.conf.ts` |

第一次只搜 spec 名，48 条里只匹配上 12 条，于是误以为「36 条没被点名」。
把三条链路都跟一遍之后，**48 条全部有驱动**（`publishing` 与 `account-session`
只有 pnpm 脚本、没有 Python 驱动，但不是孤儿）。

**这正是 §1 那句「没有任何门禁成批跑这个套件」的机制性原因**：不是谁忘了写门禁，
是这套件根本没有一个能枚举全部成员的入口，连「谁跑谁」都得靠三种规则拼出来。

剩余 44 个待跑驱动已列成清单（覆盖 38 条未验 spec），按项排期。
其中 `run_h8_22_windows_package_acceptance` 属 Windows，本机跑不了；
`run_ve_04` 需要真实阿里云凭据。


## 12. 补验收第二轮（2026-07-29 下午）：又两类，一类是产品被改版顺带弄坏

按驱动记结果，不按 spec 记——一个驱动常带多条 spec，日志只报整体成败，
按 spec 计数会比实际观察到的更精确，那是编出来的精度。

**通过的驱动（11 个）**：`t36`、`cq_01`、`bm_15`、`h8_13`、`bm_08`、`bm_06`、
`h8_21`、`vf_05`、`ve_03`、`h8_16e`、`e4_14`、`t3_19`。

### 12.1 「改版换了默认落地页」是一个成批的形状

`t3_19` 与 `t3_16` 都栽在同一件事上：**开机或刷新之后，App 落在 AI 助理页**，
而 `Workbench` 只在运行记录页渲染。改版前这两条 spec 可以假定工作台就在眼前。

修法是按用户会走的路先导航过去。这两条要证的分别是「任务在重新加载之后仍然在」
与「工作台加载真实投影并能紧急停止」，**都不是「开机就停在工作台」**——所以补导航
没有削弱它们。

17 处 `browser.refresh()` 里，四处本来就有导航、两处是「刷新后不得挂载工作台」的
反向断言（那是对的），其余按跑出来的证据逐条处理，**不做预防性批量修改**。

### 12.2 产品被改版顺带弄坏的第二处：最近任务列表不可寻址

`t3_19` 刷新后要点开某一条具体任务，而列表里**既没有文本也没有属性指向它**。

把行名从 UUID 换成创建时刻（`07-29 12:01:54 的任务`）是对的——36 个字符说不出
这条任务是什么，`Workbench.test.tsx` 里有一条测试专门守着「列表文本不含 UUID」。
但**连机器可寻址性一起丢掉是副作用、不是本意**：自动化点不到某一条，排障时没法
让用户指认，而显示名是秒级的，**同一秒创建的两条任务连人也分不开**。

补惰性属性 `data-task-id`。没用 `aria-label`——那会**替换**读屏用户听到的可读名字，
等于把一个问题换成另一个。

### 12.3 我自己在这一条上多改了一处

看到「列表里没有 UUID 了」，就把 `task-lifecycle.spec.ts` 里两处按 UUID 的断言
**一起**改成按 `data-task-id` 找行。改错了一处：首轮实测的失败发生在**刷新之后**，
说明刷新**之前**那句是通过的、UUID 确实在那个阶段的页面上；改完反而找不到了。

形状是「看到一处坏了，就假定同形状的另一处也坏了，一起改」——**本条线今天第三次
栽在这上面**。前两次是 §5.1 记的批量脚本（断言方向搞反、导航插在已经导航过的点击
之后），这次是手工改的，**所以不是工具的问题，是判断的问题**。

已按证据回退：刷新前那处保持原样，只改刷新后那处。`t3_19` 随后 exit 0、13.3 秒通过。

### 12.4 定位过程里另外两条自己的错

- **先排除自己**：这批红都是在本轮改了更新提示挂载之后跑的，而没有改动前的对照。
  所以先撤掉自己的改动跑了一遍——照样红、同一个错——才开始查它本身。这一步不该省；
- **日志读错过一次**：把「正文是 AI 助理落地页」读成了「正文是空的」（文本在下一行），
  并据此推测过「页面没渲染或驱动挂错窗口」。推测的方向与真相完全不同，
  照着查会去翻启动链路和窗口绑定，全是死路。

### 12.5 更正：Task ID 没丢，是收在折叠面板里

§12.2 据 `t3_19` 判定「最近任务列表丢了机器可寻址性」，并补了 `data-task-id`。
查 `t3_16` 时读到「当前任务」卡自己的注释：

> 完整标识与它们同折：它是把任务与日志行对应起来的东西，而这是首屏最大的一张卡。

**UUID 一直在页面上**，收在「诊断信息」折叠面板里；收起的内容不进 `getText()`。
和「制作方式卡片十行对比」是同一个形状（§9.2）。所以 `t3_16` 的正解是展开它，
不是加属性——改完 exit 0、11.8 秒通过。

两处情况不同，结论要分开写：

| | UUID 在页面上吗 | 结论 |
| --- | --- | --- |
| 当前任务卡 | **在**，收在折叠面板里 | 展开就能读，不需要属性 |
| 最近任务列表 | **不在**（`Workbench.test.tsx` 有测试专门守着列表文本不含 UUID） | 无从指认某一行，`data-task-id` 成立 |

所以 §12.2 的结论**范围说大了**：准确的说法是「列表这一处没有句柄」，
不是「这个组件丢了可寻址性」。`data-task-id` 本身保留——`t3_19` 刷新后正是靠它
点开某一条，且秒级显示名区分不了同一秒创建的两条任务。

### 12.6 四次同一个根子

| 次 | 形状 |
| --- | --- |
| §5.1 批量脚本 | 看到一处该插反向断言，就按形状全插——两处方向插反了 |
| §5.1 第二次 | 看到八处该补导航，就全补——一处插在已经导航过的点击之后 |
| §12.3 手工 | 看到刷新后那处 UUID 没了，就把刷新前那处一起改——那处本来是通的 |
| §12.5 反向 | 看到列表这一处确实缺句柄，就推广成整个组件都缺——另一处只是折起来了 |

前三次是「由一处坏推断另一处坏」，第四次是「由一处缺推断整体缺」。
**根子是同一个：用一处的观察去推断另一处，而不是分别去看。**
工具不是原因——第三、四次都是手工做的。

## 14. 串行重跑：并行那轮的红有三分之一是我自己造的

判据与时间无关的用例可以并行；**判据本身就是时限的用例不能**——它们测的正是

真要并行跑这类用例，只有两条路：**要么给每条流独占的机器**，要么**跑完之后对红的
那些串行复核一遍**。本轮走的是第二条，代价是那 12 条各跑了两遍。


## 15. 第四个产品真缺陷：运行记录列表回不去（2026-07-29 晚）

`t3_18` 与 `h8_03` 在同一个形状上各红了多轮：「处理完任务 A 之后，任务 B 的行
不见了」。§14.1 时还归在「工作台没露出来」一族，诊断版 `waitForTaskRow` 落地后
一眼看穿——**页面根本不是列表，是上一条任务的详情页**。

真因是产品缺陷：`WorkbenchShell` 的 `selectedTaskId` 只有 `openTask` 一处写入、
**从不清空**，而运行记录页的渲染是「有选中就显示详情、否则显示列表」。用户只要
点开过任何一条任务，「查看运行记录」本次会话就永远停在那一条上，唯一出路是重启
App。`返回工作台` 只切了页、没清选中。

修复一行：onBack 时 `setSelectedTaskId(null)`。

### 15.1 复现测试自己走了三版，两版都是错的

| 版 | 错法 |
| --- | --- |
| 1 | 写了「没有任务数据就 return」——默认外壳恰好没有任务，**直接绿了，缺陷原封不动**。一条不可能失败的用例，正是本任务 §2 警告的那种 |
| 2 | 假 `streamTaskEvents` 立即 resolve，消费方不停重订阅，node 直接 heap OOM。**测试替身必须与真实现同语义**（只在 abort 时 resolve），项目规则写着，照抄才对 |
| 3 | 真红。修完全绿 |

### 15.2 至此 `t3_18` 一条 spec 扛了四层

落地页 → 列表行名换时间戳 → 顶栏同名「紧急停止」→ **运行记录回不去**。
前三层是 spec 跟不上改版，**第四层是改版本身弄坏了产品**。每一层都要修完上一层
才看得见，这就是「一条 spec 红了」和「一条 spec 的全部问题」之间的距离。

产品真缺陷累计四个：强制更新只有设置页可见、最近任务列表无句柄、七个驱动
import 破损、运行记录列表回不去。


## 16. 更正 §13.3/§14 对 bm_16 的定性，并收尾恢复族（2026-07-29 夜）

### 16.1 bm_16 不是产品问题，是 sweep 没跟上窗口语义

§13.3 把它归为「产品/渲染真问题」并猜测与 PC-12 记的「内容全靠脚本驱动」同源——
**两个都不对**。真因：

- PC-19 之后渲染段必须自带时间窗，而 BM-16 的逐项 sweep 一直用测试夹具默认的
  `[0, 3000ms]` 渲每一个零件；
- `apple-money-count` 声明 5 秒，数钱、闪绿、撒钱币都在后半段——**三秒窗里它
  真的是静止的**，静帧门禁拒得对；
- PC-19 之前这条 sweep 是 134/134 全过的（BM-16 台账记着），坐标对齐后一切自洽。

修法：sweep 按 `motion-catalog.v1.json` 声明的时长逐项开窗，25 个不声明时长的
component 回退 3 秒。12 风格与双跑确定性两处调用不动——它们一直是过的。

**门禁在这件事里是对的那一方**：它拒的确实是一段静止的画面。错的是问它的人
给错了窗口。

### 16.2 恢复族四条与 h8_04 同构，其中两条已顺带验绿

`h8_04`~`h8_07` 的「App exited before X / 等信号超时」全是下游症状：信号由 spec
在真实 App 里写，而 spec 先卡死在列表断言（正文等 UUID、按 UUID 点行），到不了
写信号那一行。四个文件逐个读过再改（`h8_04` 两个 phase 分开处理；`h8_06`/`h8_07`
的第二对断言在「重新检查」之后，过闸落回默认页要先导航——这不是推断，
`task-restart.spec.ts` 在同一条闸后本来就有这一步）。

**`h8_06`、`h8_07` 已经绿了**：batch14 串行执行到它们时 spec 修改已落盘，
wdio 读的是新文件，等于顺带完成验证。`h8_04`/`h8_05` 跑在修改之前，
与 `t3_20`、`b5_13`（并行混淆嫌疑）、`vf_07`（解释器已修）、`bm_16`（窗口已修）
一并排进串行验证批。


### 16.3 §16.1 的假设被验证否决了一半（2026-07-29 深夜）

按声明时长开窗后重跑：**`apple-money-count` 在完整的 [0, 5000ms] 窗里仍然渲出
静止帧。** 「窗口太短」解释不了它了。

窗口修复本身不回退——逐项 sweep 按零件自己的时长开窗在语义上是对的，与这个
零件治不治得好无关。但 §16.1 里「与 PC-12 的观察无关」说早了：**PC-12 那条
『唯一可见节点是 $0、脚本一启动就覆盖它』回到台面上**——如果这个零件的动画
完全由自己的脚本时钟驱动、不挂在可 seek 的时间轴上，那么确定性渲染的
seek 机制对它就是无效的，每一帧都是同一个状态。

PC-19 之前 sweep 全过而现在不过，两种可能都还活着：旧算法的采样恰好让
脚本时钟走了起来，或者中间某次 worker 改动（冻结表达式、虚拟时钟）改变了
脚本动画的处境。**分不出来就不写结论**——需要一个最小复现：单渲这个零件，
探它的 `__timelines` 与 seek 响应。在那之前 bm_16 保持红。
