## 1. 破在哪

AI-first 改版（`c4d0d14`）把单一的工作台标题换成了分区标题，并把视频工作台挪到分段
控件后面。

**Playwright 那 78 条用例毫发无伤**，因为 `frontend/e2e/navigation.ts` 早就把路线收进
了一个模块，改版那一提交顺手更新了它。

**WebdriverIO 这 48 条里有 46 条把路线手写了一遍**——
`//li[contains(@class,'ant-menu-item')…工作台]` 接 `h2=RPA 运营工作台`——所以一次改版
把它们一起打断了。没人看见，因为**没有任何门禁成批跑这个套件**：每条 spec 由各自的
`run_*_acceptance.py` 驱动，坏掉的那条只有下次谁需要那项验收时才会撞见。

## 2. 两种破法，第二种才是要命的

| | 处数 | 后果 |
| --- | --- | --- |
| 正向断言消失的标题 | 44 | 下次谁跑谁看见红，吵但诚实 |
| **反向**断言「工作台不该出现」 | 5 | **永远绿** |

第二种是这样的句子：

```ts
assert.doesNotMatch(await bodyText(), /RPA 运营工作台|atas1|atrs1/);
```

它是「未登录 / 实例被吊销时不得进工作台」的那道闸。那个字符串现在产品里根本不存在，
所以**即使工作台整个挂在屏幕上，这条断言也照样通过**。

一道不可能失败的闸，比没有闸更糟：它在报告一种它并不提供的安全。

## 3. 修法：一个模块，加一条把它钉住的链

新增 `frontend/e2e-tauri/navigation.ts`，与 Playwright 那份对应：
`waitForStartup` / `openWorkbenchSection` / `openVideoStudio` / `openMaterialVideoStudio` /
`openVideoEditing` / `openPublishingWorkspace` / `openAutomationRuns` / `openTaskCreate` /
`openSettings`，外加 `workbenchIsMounted` 与 `WORKBENCH_MARKERS`——后两个专门给反向断言用，
问的是 shell 本身而不是某个会被改掉的标题字符串。

46 条 spec 全部改走这个模块。

**门禁 `scripts/test_desktop_e2e_navigation.py`（已在 `run_script_tests.py` 的自动发现里）**
守四条：

1. 模块必须存在；
2. 没有 spec 再提那个消失的标题（正向必红、反向必绿，两种都不许）；
3. 没有 spec 自己手写侧边栏 XPath；
4. **两个模块必须命名同一批目的地与分段**。

第 4 条是让它不再腐烂的那条链：Playwright 套件是**真的在跑的**，侧边栏一改名它就红，
这条门禁再逼着桌面模块跟上。桌面套件自己做不到这一点——它没有成批运行的入口。

## 4. 顺带修的失效锚点

改版动的不止导航：

- `新建任务` 曾是侧边栏入口，现在是 自动化 → `新建运营任务` 按钮（9 处）；
- `视频剪辑` 曾是独立入口，现在是 创作 下的 `轻量剪辑` 分段（1 处）；
- `h2=视频制作` 没有了，创作页现在是 h3 的方式名（4 处）；
- `设置与诊断` 作为菜单项已改名 `设置`（页面标题里仍在，没动）。

**第一轮说「这类失效锚点为 0」是错的，审查逐文件核出至少 5 处仍在**：
`diagnostic-export.spec.ts:13` 与 `executor-lifecycle.spec.ts:40` 的 `h2=设置与诊断`
（产品现在渲染 `设置`）、两处 `h2=平台状态`（现在是 `账号与平台`）、
`plain-language-comprehension.spec.ts:202` 的 `h2=视频剪辑`（已无此标题）。
第一处尤其明显：它就在我本轮改的 `openSettings()` 的**下一行**——改了导航、
没改紧跟着的断言。这些已在第二轮修掉。

## 5. 我自己犯的错（三次，都在这一项里）

#### 5.1 批量替换把断言方向搞反

批量脚本按 `assert.doesNotMatch(await bodyText(), /` 这个形状插入新断言，
**而原文只有三处 regex 里真的提到工作台**。于是两处被插到了「登录成功之后」和
「已登录、断言登录页不该出现」的分支里——**断言方向正好反了**。

编译能过、lint 能过、门禁能过，只有肉眼看 diff 才发现。已把那两个账号 spec 整个回退，
五处逐个手工改。

这条记在这里，是因为它正是本条线反复栽的那个形状的又一次：一个看起来安全的批量替换，
在少数分支上改变了语义，而所有机械检查都是绿的。

**同一个错误当天犯了第二次**：给八处等待自动补导航时，脚本把 `openAutomationRuns()`
插到了「点击『查看运行详情』之后」——那次点击本身已经导航到详情页，再插一次是走回列表。
也是肉眼看 diff 才发现。**结论：这种改动不能用形状匹配批量做，只能逐文件判断。**

### 5.2 我报了一条根本没通过的验收

上一轮我说「CQ-01 也通过了」。**它没有。** 它在 `pnpm build:tauri:video-studio-test`
那一步失败，退出码 1，日志末尾是完整的 traceback。

我看到的「通过」是日志**中段**属于另一个门禁（品牌用语扫描）的两行绿字，
而我把命令写成了 `cmd > log 2>&1; echo "exit=$?"`——**harness 报的是 `echo` 的退出码**，
永远是 0。两个错误叠在一起，就把一次失败读成了成功。

改法有两条，都做了：命令不再拼 `; echo`，退出码直接由被测命令决定；
以及把这次的真实结论写进本文件，不留一条假的绿。

### 5.3 我的「tsc ok」一整天都是空的

CQ-01 那次失败的**真正原因**是 T21 引入的三个类型错误
（`material-video-studio-gateway.test.ts` 里 `modelThinking` 成了必填而调用点没跟上）。

它们躲过了我每次改动后都跑的 `npx tsc --noEmit -p tsconfig.json`——因为
`frontend/tsconfig.json` 是 solution 文件（`"files": []` + 两个 references），
`-p` 它等于**编译一个空文件列表**，退出 0、无输出，和「整个前端类型干净」
长得一模一样。正式入口是 `tsc -b`，仓库里每个 `build:*` 脚本用的都是它。

已加门禁 `scripts/test_typecheck_entrypoint.py`：任何文档、脚本、CI 配置里
再出现 `tsc -p tsconfig.json` 就红。它同时断言那份 solution 配置**确实**是空的——
哪天有人给它加了 `include`，这条门禁该被重写而不是继续守一条不再描述现实的规则。

### 6.1 CQ-01 从「构建就挂」到全过，一共五轮

这条 spec 是本轮改动最大的一个（自带 `openMenu` 已删、五个目的地名字全是已删除的入口），

| 轮次 | 结果 | 真因 |
| --- | --- | --- |

## 7. 真实边界 — 这一项**没有**证明什么

**46 条里只有 2 条真在 App 上跑过。** 其余 44 条做到的是：不再引用已经消失的界面，
类型与 lint 干净，导航走共享模块。**它们能不能通过，仍然是未知的**——每条都要各自的
验收脚本、真实服务和数分钟起步的时间，其中若干条还需要真实平台账号。

改版可能还改了这些 spec 断言的**流程**而不只是**字符串**，那种失效没有任何机械手段
能查出来，只有真跑才知道。

所以状态是 `🔍 待验收`，不是完成。补验收的办法是把这些 `run_*_acceptance.py` 逐个跑通，
那是一件按项排期的事，不该塞进这一项假装做完了。
