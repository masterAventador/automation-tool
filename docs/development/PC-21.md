## 1. 破在哪

AI-first 改版（`c4d0d14`）把单一的工作台标题换成了分区标题，并把视频工作台挪到分段
控件后面。

**Playwright 那 78 条用例毫发无伤**，因为 `frontend/e2e/navigation.ts` 早就把路线收进
了一个模块，改版那一提交顺手更新了它。

**WebdriverIO 这 48 条里有 46 条把路线手写了一遍**——
`//li[contains(@class,'ant-menu-item')…工作台]` 接 `h2=RPA 运营工作台`——所以一次改版
把它们一起打断了。没人看见，因为**没有任何门禁成批跑这个套件**：每条 spec 由各自的
`run_*_acceptance.py` 驱动，坏掉的那条只有下次谁需要那项验收时才会撞见。

## 2. 两种破法，第二种才是要命的

| | 处数 | 后果 |
| --- | --- | --- |
| 正向断言消失的标题 | 44 | 下次谁跑谁看见红，吵但诚实 |
| **反向**断言「工作台不该出现」 | 5 | **永远绿** |

第二种是这样的句子：

```ts
assert.doesNotMatch(await bodyText(), /RPA 运营工作台|atas1|atrs1/);
```

它是「未登录 / 实例被吊销时不得进工作台」的那道闸。那个字符串现在产品里根本不存在，
所以**即使工作台整个挂在屏幕上，这条断言也照样通过**。

一道不可能失败的闸，比没有闸更糟：它在报告一种它并不提供的安全。

## 3. 修法：一个模块，加一条把它钉住的链

新增 `frontend/e2e-tauri/navigation.ts`，与 Playwright 那份对应：
`waitForStartup` / `openWorkbenchSection` / `openVideoStudio` / `openMaterialVideoStudio` /
`openVideoEditing` / `openPublishingWorkspace` / `openAutomationRuns` / `openTaskCreate` /
`openSettings`，外加 `workbenchIsMounted` 与 `WORKBENCH_MARKERS`——后两个专门给反向断言用，
问的是 shell 本身而不是某个会被改掉的标题字符串。

46 条 spec 全部改走这个模块。

**门禁 `scripts/test_desktop_e2e_navigation.py`（已在 `run_script_tests.py` 的自动发现里）**
守四条：

1. 模块必须存在；
2. 没有 spec 再提那个消失的标题（正向必红、反向必绿，两种都不许）；
3. 没有 spec 自己手写侧边栏 XPath；
4. **两个模块必须命名同一批目的地与分段**。

第 4 条是让它不再腐烂的那条链：Playwright 套件是**真的在跑的**，侧边栏一改名它就红，
这条门禁再逼着桌面模块跟上。桌面套件自己做不到这一点——它没有成批运行的入口。

## 4. 顺带修的失效锚点

改版动的不止导航：

- `新建任务` 曾是侧边栏入口，现在是 自动化 → `新建运营任务` 按钮（9 处）；
- `视频剪辑` 曾是独立入口，现在是 创作 下的 `轻量剪辑` 分段（1 处）；
- `h2=视频制作` 没有了，创作页现在是 h3 的方式名（4 处）；
- `设置与诊断` 作为菜单项已改名 `设置`（页面标题里仍在，没动）。

**第一轮说「这类失效锚点为 0」是错的，审查逐文件核出至少 5 处仍在**：
`diagnostic-export.spec.ts:13` 与 `executor-lifecycle.spec.ts:40` 的 `h2=设置与诊断`
（产品现在渲染 `设置`）、两处 `h2=平台状态`（现在是 `账号与平台`）、
`plain-language-comprehension.spec.ts:202` 的 `h2=视频剪辑`（已无此标题）。
第一处尤其明显：它就在我本轮改的 `openSettings()` 的**下一行**——改了导航、
没改紧跟着的断言。这些已在第二轮修掉。

## 5. 我自己犯的错（三次，都在这一项里）

#### 5.1 批量替换把断言方向搞反

批量脚本按 `assert.doesNotMatch(await bodyText(), /` 这个形状插入新断言，
**而原文只有三处 regex 里真的提到工作台**。于是两处被插到了「登录成功之后」和
「已登录、断言登录页不该出现」的分支里——**断言方向正好反了**。

编译能过、lint 能过、门禁能过，只有肉眼看 diff 才发现。已把那两个账号 spec 整个回退，
五处逐个手工改。

这条记在这里，是因为它正是本条线反复栽的那个形状的又一次：一个看起来安全的批量替换，
在少数分支上改变了语义，而所有机械检查都是绿的。

**同一个错误当天犯了第二次**：给八处等待自动补导航时，脚本把 `openAutomationRuns()`
插到了「点击『查看运行详情』之后」——那次点击本身已经导航到详情页，再插一次是走回列表。
也是肉眼看 diff 才发现。**结论：这种改动不能用形状匹配批量做，只能逐文件判断。**

### 5.2 我报了一条根本没通过的验收

上一轮我说「CQ-01 也通过了」。**它没有。** 它在 `pnpm build:tauri:video-studio-test`
那一步失败，退出码 1，日志末尾是完整的 traceback。

我看到的「通过」是日志**中段**属于另一个门禁（品牌用语扫描）的两行绿字，
而我把命令写成了 `cmd > log 2>&1; echo "exit=$?"`——**harness 报的是 `echo` 的退出码**，
永远是 0。两个错误叠在一起，就把一次失败读成了成功。

改法有两条，都做了：命令不再拼 `; echo`，退出码直接由被测命令决定；
以及把这次的真实结论写进本文件，不留一条假的绿。

### 5.3 我的「tsc ok」一整天都是空的

CQ-01 那次失败的**真正原因**是 T21 引入的三个类型错误
（`material-video-studio-gateway.test.ts` 里 `modelThinking` 成了必填而调用点没跟上）。

它们躲过了我每次改动后都跑的 `npx tsc --noEmit -p tsconfig.json`——因为
`frontend/tsconfig.json` 是 solution 文件（`"files": []` + 两个 references），
`-p` 它等于**编译一个空文件列表**，退出 0、无输出，和「整个前端类型干净」
长得一模一样。正式入口是 `tsc -b`，仓库里每个 `build:*` 脚本用的都是它。

已加门禁 `scripts/test_typecheck_entrypoint.py`：任何文档、脚本、CI 配置里
再出现 `tsc -p tsconfig.json` 就红。它同时断言那份 solution 配置**确实**是空的——
哪天有人给它加了 `include`，这条门禁该被重写而不是继续守一条不再描述现实的规则。

## 7. 真实边界 — 这一项**没有**证明什么

**46 条里只有 2 条真在 App 上跑过。** 其余 44 条做到的是：不再引用已经消失的界面，
类型与 lint 干净，导航走共享模块。**它们能不能通过，仍然是未知的**——每条都要各自的
验收脚本、真实服务和数分钟起步的时间，其中若干条还需要真实平台账号。

改版可能还改了这些 spec 断言的**流程**而不只是**字符串**，那种失效没有任何机械手段
能查出来，只有真跑才知道。

所以状态是 `🔍 待验收`，不是完成。补验收的办法是把这些 `run_*_acceptance.py` 逐个跑通，
那是一件按项排期的事，不该塞进这一项假装做完了。

### 9.1 一条是产品真缺陷：强制更新只有打开设置才看得见

`update-ui` 开机后等「发现新版本 0.2.0」，25 秒没等到。不是 spec 过期。

`AppUpdateCenter` 的设计是**提示 Modal 无条件渲染**，`showSettings` 只额外加一张
管理卡——它挂在哪里，提示就只能在哪里弹。改版把它挪进了 `WorkbenchShell` 的
`showingSettings ? … : …` 那一支，于是提示的可见性被绑在「用户此刻正好在设置页」上。

可选更新如此已经不好，**强制更新如此是真问题**：用户可以永远不打开设置，
而那条更新的语义正是「不更新就不能继续用」。

已修：不在设置页时外壳自己挂一份 `showSettings={false}`，任一时刻只有一个实例。
组件层补了两条复现（可选 + 强制），并在真实 App 上由 `run_h8_21` 两个场景验收通过。

**这条修复过程里我自己差点埋一个假绿**：断言方式在红绿之间改过（Ant 的 Modal 会
留一个隐藏预渲染节点，要取最后一个并等过动画），所以最初那次红**不能**算这次绿的
对照。撤掉产品修复、重跑**新**断言、确认仍红，控制实验才算成立（规则 §8.3）。

### 9.2 四处是 spec 断言了产品不再有的东西

| 处 | 断言 | 现实 |
| --- | --- | --- |
| `video-studio.spec.ts:17` | `打开完整制作界面` 渲染为禁用态 | 按钮已不存在 |
| `video-creation-methods.spec.ts:58` | 同上 | 同上 |
| `video-creation-methods.spec.ts` 十个 `dt` 标签 | 各出现两次 | 取到 0——改版把十行对比收进了每张卡片的折叠面板，默认收起 |

前两处同源：`OperationsWorkspace` 是唯一渲染 `VideoStudio` 的地方，且**无条件**传
`embedded`，整个打开器被换成一条提示。

第三处的展开逻辑**没有在 spec 里再写一份**，抽进了 `navigation.ts` 的
`openCreationMethodCards`——`plain-language-comprehension.spec.ts` 已经为同一件事
付过一次代价，两份手写路线正是本任务存在的理由。helper 里锁住了两个已付学费的坑：
`card.$("//…")` 从文档根搜（第二次循环会把第一张卡又合上，必须 `.//`），
以及折叠有动画（点击返回那一刻行还不在 DOM 里）。

### 9.3 一处是期望取错了契约小节

`run_bm_08_acceptance.py` 量的是**成片**，读的却是「单次渲染的画布」
（640×360 @2 = 1280×720），而 PC-18 之后成片有自己的声明（1920×1080）。

讽刺的是这个脚本自己的注释写着：

> The frame size this acceptance expects is derived, never restated. Hard-coding
> it here is what made this run red after the canvas contract raised its device
> scale factor: the render was correct and the expectation was stale.

**它确实在派生——派生自错误的那一节。** 「不要写死」不蕴含「派生就对了」，
派生源同样会过期，只是过期得更隐蔽。

## 10. 顺带查出的一个产品状态，未擅自处理

`VideoStudio` 的非 embedded 分支（`打开完整制作界面` 按钮 + 整套打开独立界面的
流程）已经是**不可达死代码**——唯一的渲染点无条件传 `embedded`。而 embedded 那支
自己写着「当前真实内嵌服务尚未接入」。

也就是说**「智能素材成片」现在两头都通不了**。按「代码删除规范」死代码该删，
但删哪一头取决于产品打算走内嵌还是独立窗口，属产品决策，已记录待定。

### 10.1 它已经把一条验收堵死了（2026-07-29 补）

`run_im_05_acceptance.py` 跑 `material-video-webui.spec.ts` 时红在
`section[aria-label='视频制作工作区']` 找不到。表面看是这条 spec 停在设置页、
没导航到创作页——**但把导航补上也过不了**，因为它下一步要点的正是
`打开完整制作界面`。

**这条 spec 存在的全部目的，就是验证「智能素材成片的 WebUI 能从产品入口打开」。**
那个入口现在不存在。所以它不是写坏了，是**它要验的能力没有入口**。

因此这条**不改 spec**。把断言改成迁就现状，等于把「这个功能用户够不着」这件事
从红色改写成绿色——正是本任务 §2 记的那种「一道不可能失败的闸比没有闸更糟」。
它保持红，直到产品决定「智能素材成片」走内嵌还是走独立窗口。

**这也是本轮补验收最有价值的一条**：它把一个原本只是「死代码，待定」的观察，
变成了「有一条产品能力目前无人可达，且有一条验收正在为此变红」。

## 11. 剩下的，以及为什么「谁跑这条 spec」本身要查一遍

48 条里 10 条已验，**38 条未验**。

排期前先撞到一件事：**同一套 spec 有三种被驱动的方式**，所以「这条 spec 归谁跑」
不能靠搜名字：

| 方式 | 例 |
| --- | --- |
| 验收脚本直接传 `--spec` | `run_bm_06` 一次带四条 |
| 验收脚本点名 wdio 配置 | `run_h8_21` → `wdio.update-ui.conf.ts` |
| 验收脚本调 pnpm 脚本，由它再指向配置 | `run_t3_19` → `pnpm test:task-lifecycle-tauri` → `wdio.task-lifecycle.conf.ts` |

第一次只搜 spec 名，48 条里只匹配上 12 条，于是误以为「36 条没被点名」。
把三条链路都跟一遍之后，**48 条全部有驱动**（`publishing` 与 `account-session`
只有 pnpm 脚本、没有 Python 驱动，但不是孤儿）。

**这正是 §1 那句「没有任何门禁成批跑这个套件」的机制性原因**：不是谁忘了写门禁，
是这套件根本没有一个能枚举全部成员的入口，连「谁跑谁」都得靠三种规则拼出来。

剩余 44 个待跑驱动已列成清单（覆盖 38 条未验 spec），按项排期。
其中 `run_h8_22_windows_package_acceptance` 属 Windows，本机跑不了；
`run_ve_04` 需要真实阿里云凭据。


## 12. 补验收第二轮（2026-07-29 下午）：又两类，一类是产品被改版顺带弄坏

按驱动记结果，不按 spec 记——一个驱动常带多条 spec，日志只报整体成败，
按 spec 计数会比实际观察到的更精确，那是编出来的精度。

**通过的驱动（11 个）**：`t36`、`cq_01`、`bm_15`、`h8_13`、`bm_08`、`bm_06`、
`h8_21`、`vf_05`、`ve_03`、`h8_16e`、`e4_14`、`t3_19`。

### 12.1 「改版换了默认落地页」是一个成批的形状

`t3_19` 与 `t3_16` 都栽在同一件事上：**开机或刷新之后，App 落在 AI 助理页**，
而 `Workbench` 只在运行记录页渲染。改版前这两条 spec 可以假定工作台就在眼前。

修法是按用户会走的路先导航过去。这两条要证的分别是「任务在重新加载之后仍然在」
与「工作台加载真实投影并能紧急停止」，**都不是「开机就停在工作台」**——所以补导航
没有削弱它们。

17 处 `browser.refresh()` 里，四处本来就有导航、两处是「刷新后不得挂载工作台」的
反向断言（那是对的），其余按跑出来的证据逐条处理，**不做预防性批量修改**。

### 12.2 产品被改版顺带弄坏的第二处：最近任务列表不可寻址

`t3_19` 刷新后要点开某一条具体任务，而列表里**既没有文本也没有属性指向它**。

把行名从 UUID 换成创建时刻（`07-29 12:01:54 的任务`）是对的——36 个字符说不出
这条任务是什么，`Workbench.test.tsx` 里有一条测试专门守着「列表文本不含 UUID」。
但**连机器可寻址性一起丢掉是副作用、不是本意**：自动化点不到某一条，排障时没法
让用户指认，而显示名是秒级的，**同一秒创建的两条任务连人也分不开**。

补惰性属性 `data-task-id`。没用 `aria-label`——那会**替换**读屏用户听到的可读名字，
等于把一个问题换成另一个。

### 12.3 我自己在这一条上多改了一处

看到「列表里没有 UUID 了」，就把 `task-lifecycle.spec.ts` 里两处按 UUID 的断言
**一起**改成按 `data-task-id` 找行。改错了一处：首轮实测的失败发生在**刷新之后**，
说明刷新**之前**那句是通过的、UUID 确实在那个阶段的页面上；改完反而找不到了。

形状是「看到一处坏了，就假定同形状的另一处也坏了，一起改」——**本条线今天第三次
栽在这上面**。前两次是 §5.1 记的批量脚本（断言方向搞反、导航插在已经导航过的点击
之后），这次是手工改的，**所以不是工具的问题，是判断的问题**。

已按证据回退：刷新前那处保持原样，只改刷新后那处。`t3_19` 随后 exit 0、13.3 秒通过。

### 12.4 定位过程里另外两条自己的错

- **先排除自己**：这批红都是在本轮改了更新提示挂载之后跑的，而没有改动前的对照。
  所以先撤掉自己的改动跑了一遍——照样红、同一个错——才开始查它本身。这一步不该省；
- **日志读错过一次**：把「正文是 AI 助理落地页」读成了「正文是空的」（文本在下一行），
  并据此推测过「页面没渲染或驱动挂错窗口」。推测的方向与真相完全不同，
  照着查会去翻启动链路和窗口绑定，全是死路。

### 12.5 更正：Task ID 没丢，是收在折叠面板里

§12.2 据 `t3_19` 判定「最近任务列表丢了机器可寻址性」，并补了 `data-task-id`。
查 `t3_16` 时读到「当前任务」卡自己的注释：

> 完整标识与它们同折：它是把任务与日志行对应起来的东西，而这是首屏最大的一张卡。

**UUID 一直在页面上**，收在「诊断信息」折叠面板里；收起的内容不进 `getText()`。
和「制作方式卡片十行对比」是同一个形状（§9.2）。所以 `t3_16` 的正解是展开它，
不是加属性——改完 exit 0、11.8 秒通过。

两处情况不同，结论要分开写：

| | UUID 在页面上吗 | 结论 |
| --- | --- | --- |
| 当前任务卡 | **在**，收在折叠面板里 | 展开就能读，不需要属性 |
| 最近任务列表 | **不在**（`Workbench.test.tsx` 有测试专门守着列表文本不含 UUID） | 无从指认某一行，`data-task-id` 成立 |

所以 §12.2 的结论**范围说大了**：准确的说法是「列表这一处没有句柄」，
不是「这个组件丢了可寻址性」。`data-task-id` 本身保留——`t3_19` 刷新后正是靠它
点开某一条，且秒级显示名区分不了同一秒创建的两条任务。

### 12.6 四次同一个根子

| 次 | 形状 |
| --- | --- |
| §5.1 批量脚本 | 看到一处该插反向断言，就按形状全插——两处方向插反了 |
| §5.1 第二次 | 看到八处该补导航，就全补——一处插在已经导航过的点击之后 |
| §12.3 手工 | 看到刷新后那处 UUID 没了，就把刷新前那处一起改——那处本来是通的 |
| §12.5 反向 | 看到列表这一处确实缺句柄，就推广成整个组件都缺——另一处只是折起来了 |

前三次是「由一处坏推断另一处坏」，第四次是「由一处缺推断整体缺」。
**根子是同一个：用一处的观察去推断另一处，而不是分别去看。**
工具不是原因——第三、四次都是手工做的。

## 15. 第四个产品真缺陷：运行记录列表回不去（2026-07-29 晚）

`t3_18` 与 `h8_03` 在同一个形状上各红了多轮：「处理完任务 A 之后，任务 B 的行
不见了」。§14.1 时还归在「工作台没露出来」一族，诊断版 `waitForTaskRow` 落地后

真因是产品缺陷：`WorkbenchShell` 的 `selectedTaskId` 只有 `openTask` 一处写入、
**从不清空**，而运行记录页的渲染是「有选中就显示详情、否则显示列表」。用户只要

App。`返回工作台` 只切了页、没清选中。

## 16. 更正 §13.3/§14 对 bm_16 的定性，并收尾恢复族（2026-07-29 夜）

### 16.1 bm_16 不是产品问题，是 sweep 没跟上窗口语义

§13.3 把它归为「产品/渲染真问题」并猜测与 PC-12 记的「内容全靠脚本驱动」同源——
**两个都不对**。真因：

- PC-19 之后渲染段必须自带时间窗，而 BM-16 的逐项 sweep 一直用测试夹具默认的
  `[0, 3000ms]` 渲每一个零件；
- `apple-money-count` 声明 5 秒，数钱、闪绿、撒钱币都在后半段——**三秒窗里它
  真的是静止的**，静帧门禁拒得对；
- PC-19 之前这条 sweep 是 134/134 全过的（BM-16 台账记着），坐标对齐后一切自洽。

修法：sweep 按 `motion-catalog.v1.json` 声明的时长逐项开窗，25 个不声明时长的
component 回退 3 秒。12 风格与双跑确定性两处调用不动——它们一直是过的。

**门禁在这件事里是对的那一方**：它拒的确实是一段静止的画面。错的是问它的人
给错了窗口。

### 16.2 恢复族四条与 h8_04 同构，其中两条已顺带验绿

`h8_04`~`h8_07` 的「App exited before X / 等信号超时」全是下游症状：信号由 spec
在真实 App 里写，而 spec 先卡死在列表断言（正文等 UUID、按 UUID 点行），到不了
写信号那一行。四个文件逐个读过再改（`h8_04` 两个 phase 分开处理；`h8_06`/`h8_07`
的第二对断言在「重新检查」之后，过闸落回默认页要先导航——这不是推断，
`task-restart.spec.ts` 在同一条闸后本来就有这一步）。

**`h8_06`、`h8_07` 已经绿了**：batch14 串行执行到它们时 spec 修改已落盘，
wdio 读的是新文件，等于顺带完成验证。`h8_04`/`h8_05` 跑在修改之前，
与 `t3_20`、`b5_13`（并行混淆嫌疑）、`vf_07`（解释器已修）、`bm_16`（窗口已修）
一并排进串行验证批。


### 16.3 §16.1 的假设被验证否决了一半（2026-07-29 深夜）

按声明时长开窗后重跑：**`apple-money-count` 在完整的 [0, 5000ms] 窗里仍然渲出
静止帧。** 「窗口太短」解释不了它了。

窗口修复本身不回退——逐项 sweep 按零件自己的时长开窗在语义上是对的，与这个
零件治不治得好无关。但 §16.1 里「与 PC-12 的观察无关」说早了：**PC-12 那条
『唯一可见节点是 $0、脚本一启动就覆盖它』回到台面上**——如果这个零件的动画
完全由自己的脚本时钟驱动、不挂在可 seek 的时间轴上，那么确定性渲染的
seek 机制对它就是无效的，每一帧都是同一个状态。

PC-19 之前 sweep 全过而现在不过，两种可能都还活着：旧算法的采样恰好让
脚本时钟走了起来，或者中间某次 worker 改动（冻结表达式、虚拟时钟）改变了
脚本动画的处境。**分不出来就不写结论**——需要一个最小复现：单渲这个零件，
探它的 `__timelines` 与 seek 响应。在那之前 bm_16 保持红。


## 17. 第五个产品真缺陷：安全注销在登录处理开着时按下去会失败，且界面劝用户别重试

`b5_13` 一共剥了四层才到底。证据链（全部实测）：

| 时刻 | 事实 |
| --- | --- |
| 15:11:27 | Profile 标记创建（登录流程，合理） |
| 15:11:34.241 | 点「确认注销」 |
| 15:11:34.495 | 页面已显示「需要登录」——**整个登出 254ms** |
| 验收后置检查 | 标记原样在、Profile 目录活到 App 退出 |
| 警告原文 | **「抖音登录处理没有完成，这是本产品自身的问题，重新操作不会有效。请把下面的代码发给我们。故障代码：storage_unavailable」** |

`storage_unavailable` 在登出五步里只映射到「删 Profile」。也就是说：**登录处理的浏览器
还开着时点安全注销，删 Profile 一步失败，登录态原样留在盘上——而界面明确告诉用户
「重新操作不会有效」**。最坏的组合：既没删掉，又劝人别重试。

### 17.1 spec 此前为什么是绿的：空转等待

fixture 从未真正登录，登出**之前**页面就已写着「需要登录」——于是「登出后等
『需要登录』」这条断言无论命令成败都通过。命令失败留下的警告框没人断言。
**runner 的本地文件后置检查是整条链上唯一诚实的一环。**

已补：登出断言同时要求「无失败警告」，并在失败时打印警告原文。这条 spec 从此
保持红，直到产品修复——与 IM-05 同一条纪律，不把断言改软来造绿。

### 17.2 已收窄到、但未定位的

嫌疑集中在「紧停的杀进程是异步的，删 Profile 在锁持有者退出前就执行了」这一族；
但 App 侧租约在紧停里已显式释放，`remove_profile` 的三个子步骤（取移除锁 / renameat /
remove_dir_all）哪个返回了 `storage_unavailable`，静态分不出来。**留给修复任务的
第一步就是给这三个子步骤分错误码**——一个 `storage_unavailable` 盖三种失败，
正是这次要靠四轮插桩才找到位置的原因。

### 17.3 查案方法的账

这条用了四轮插桩（补 runner mtime 诊断 → 补警告原文 → 补墙钟时间戳 → 补空转洞），
每轮一次运行、每轮排除一族假设。对比 §12 之前「猜一层跑一轮」的方式，
四轮全是**带着问题去跑**，没有一轮是白跑的。

## 18. bm_16 收口：sweep 五层没跟上产品决定，然后是第六个产品真缺陷（2026-07-29）

### 18.1 §16.3 悬着的问题，答案是画布

§16.3 的最小复现做了：`apple-money-count` 在完整 [0, 5000ms] 窗里静止，
**不是**脚本时钟失效——是 sweep 沿用夹具默认的 640×360 模板画布，而零件的
舞台是 1920×1080。控制实验（同一零件、同一批 seek 点、只换视口）：
1920×1080 下五个 seek 点五个不同摘要，640×360 下前三秒同一张——模板画布
看到的是零件舞台的一个静止角落。PC-12 的嫌疑排除，PC-05 的规则
（渲染画布随请求走，零件渲在自己声明的舞台上）适用于 sweep。

### 18.2 五层 sweep 修复，同一句话：夹具默认 vs 产品决定

每层都是「sweep 用夹具默认值渲染，而产品早已另有决定」，逐轮推进

| --- | --- | --- | --- |
| 时间窗 | [0, 3000ms] | PC-19：段自带时间窗 | 按目录声明时长开窗（§16.1） |
| 画布 | 640×360 模板 | PC-05：渲在零件声明的舞台 | 按目录 dimensions、deviceScaleFactor=1 |
| component | 必须动 | PC-01：无时间轴，静止即真相 | 渲 1 帧（低于静帧比较下限） |
| 白名单 | 整树拷贝 | PC-05/PC-13：按引用收集，128 上限 | 抽 `referenced_assets` 单源遍历，产品拷贝器共用（executor 1319→1320 绿） |

的全部默认值对着产品语义审一遍，而不是一轮撞一层——§12 的静态审计教训
在自己脚本上又学了一次。

### 18.3 第六个产品真缺陷：渲染沙箱里 WebGL 是死的

第五轮（五修叠加）推进到 item 20/134，`chromatic-radial-split` 报
`render_static_frames`。这项声明 4 秒 / 1920×1080、不引用任何视频——五层修复
对它全部生效，帧仍然全同。

根因在零件文档自己的降级分支：它全部动画挂在 WebGL 上，`if (!gl)` 时装的是
**空的** paused timeline，页面完全静止。而 worker 两处启动 Chromium 都带
`--disable-gpu`，Chromium 149 在无 GPU 时连 SwiftShader 软件 WebGL 也拒绝，
除非显式 `--enable-unsafe-swiftshader`（Playwright 自己的 driver 就带这行，
`coreBundle.js` 里两处）。

对照实验（同一锁定 Chromium 149.0.7827.55，`ignore_default_args` 全关、
逐字传 worker 参数，只差一个旗标）：

```
worker-args-exact:        WEBGL_PROBE: null
worker-args+swiftshader:  WEBGL_PROBE: ok renderer=ANGLE (Google, Vulkan 1.3.0
                          (SwiftShader Device (LLVM 10.0.0)), SwiftShader driver)
```

波及面：134 项里 **16 项 `getContext("webgl")`**（16 个转场/特效类：
chromatic-radial-split、cinematic-zoom、cross-warp-morph、domain-warp-dissolve、
flash-through-white、glitch、gravitational-lens、light-leak、ridged-burn、
ripple-waves、sdf-iris、swirl-vortex、thermal-distortion、vfx-magnetic、
vfx-text-cursor、whip-pan），在产品里全渲不出动画。**sweep 与静帧门禁都是
对的那一方**：拦下的确实是一段静止画面，错在启动参数掐死了 WebGL。

修复（TDD）：

- RED：`test_motion_video_worker.py` 新增旗标配对断言（每个 `--disable-gpu`
  必须配 `--enable-unsafe-swiftshader`），实跑红
  `AssertionError: … 2 vs 0`；
- GREEN：worker.mjs 两处启动加旗标（沙箱处带注释：SwiftShader 仍是 CPU
  光栅化，字节级确定性要求不受影响），门禁绿 `executed checks: 4`;
- 行为验证：真实 worker + 锁定 Chromium 单渲该零件，
  `frames: 2 distinct: 2, blockedRequests: 0`——shader 转场动起来了。

六修叠加的第六轮全量 sweep 在跑，绿了才收口。

### 18.4 第七个产品真缺陷：worker 把「声明了时长」当成「可以 seek」的前提

第六轮（六修叠加）验证了 §18.3 的修复——item 20/21（WebGL 转场）通过——
推进到 item 29 `code-snippet-apple-terminal-basic` 再报 `render_static_frames`。

这项声明 12 秒 / 1920×1080，动画是逐字符打字（全靠 `tl.add(回调, 时间)`），
worker 也确实用 `seek(t, false)`（回调会触发）。真因在探针：

- 文档根节点只有 `data-composition-id`/`data-width`/`data-height`，
  **没有 `data-duration`**——发布树里 31 个零件如此（26 个 code-snippet 系列
  加 grid-pixelate-wipe、grain-overlay、parallax-zoom/unzoom 等）；
- worker 的 `seekableDuration` 要求「声明时长 > 0 **且** 有时间轴」，
  两个条件捆在一起；缺声明 → `seekableDuration=0` → **整个 seek 分支被跳过**，
  两帧都是初始状态的截屏 → 静帧闸拒绝。闸又一次是对的那一方。

产品路径同样中招：`write_part_working_copy` 不注入 `data-duration`，这 31 个
零件在产品里渲多帧同样全静。

修法是把两件独立的事分开：**能不能 seek 只取决于注册了时间轴**
（`seekableTimelineCount > 0`）；**能不能校验窗口越界**才取决于文档声明了
自己的长度（`seekableDuration > 0`，保持原样）。捆绑它们正是 worker 注释里
自己警告过的「下游合理默认」失败模式。

验证：真实 worker + 锁定 Chromium 单渲该零件 `frames: 2 distinct: 2`，
打字动画动起来了；`test_motion_video_worker.py` 4 项保持绿。

### 18.5 改打法：fail-fast 的洋葱一轮一层，先诊断后修复

连续七层每层一轮（约十几分钟一轮）之后，把验收 sweep 的 fail-fast 换成
一次性**全量诊断扫描**（`.local/bm16_survey_all.py`，单项失败不中断、
汇总清单；只是诊断工具，验收仍以 `run_bm_16_acceptance.py` 为准）。静态
预审出的两类新嫌疑一并交给它：8 个不注册 `__timelines` 的零件（seek 分支
进不去，CSS/rAF 动画的冻结语义存疑）、7 个在 `setTimeout`/load 回调里
延迟注册时间轴的零件（探针数到 0 的时序风险）。扫描结果出来一次修完，
再跑正式 sweep 收口。

## 19. h8_22_macos：打包 App 启动即 SIGABRT 的全案（2026-07-29）

### 19.1 诊断链：崩溃报告 → 直起抓 stderr → 读 tauri 源码，零轮盲跑

`SevereServiceError: Tauri app exited (signal=SIGABRT)` 只有壳。按「能读的先读」：

1. **macOS 崩溃报告已在盘上**（`automation-tool-desktop-2026-07-29-125216.ips`，
   与失败同分钟）：panic 撞上 `tao::did_finish_launching` 的 nounwind 边界
   （`panic_cannot_unwind` → abort），但 panic 消息只打 stderr，报告里没有；
2. **wdio 的 `captureBackendLogs: true` 早就开着但救不了**：service 的管道
   `parseLogLine(line)` 解析不了的行直接丢弃——Rust panic 消息正是这种。
   错误提示自己指的路（"Set captureBackendLogs..."）对崩溃场景是死的；
3. **用验收自己的构建函数出一个 0.1.0 包、绕过 wdio 直起二进制**，stderr 落文件：
   ```
   desktop fixed-event log unavailable
   thread 'main' panicked at tauri-2.11.5/src/app.rs:1425:
   Failed to setup app: error encountered during setup hook: unknown path
   ```
   （第一轮复现死在我自己漏抄 run() 的公钥注入——`configuration["plugins"]
   ["updater"]["pubkey"]`，报「Missing comment in public key」；补上即复现成功，
   exit -6。）

### 19.2 根因：三个事实的交点

- **tauri 源码**：`UnknownPath` 全部产自 path resolver；`resource_dir()` 把任何
  内部失败映射成它（desktop.rs:230）。macOS 实现是
  `exe_dir/../Resources` 做 **`canonicalize`——检查存在性**；
- **测试包**：h8_22 的 `Contents/` 只有 `_CodeSignature`/`Info.plist`/`MacOS`，
  **没有 Resources**——其 e2e 配置无 `resources` 无 `icon`，bundler 不建该目录；
- **时间线**：setup 里的 `resource_dir()` 调用（`EmbeddedBrowserAuthority`）是
  h8_22 上次通过（7632284）**之后**由 EB-07/EB-08 加的——产品从此要求启动时
  就能定位 Resources。

三方交点：EB 系列上线后，任何没有 Resources 目录的 .app 启动即 panic。
其余 40 条 E2E 不中招：它们跑未打包 debug 二进制，`resource_dir` 命中
`target/` + `.cargo-lock` 检查直接返回 exe 目录。Windows 版也不中招：
其 `resource_dir` 返回 exe 目录，永不失败——这解释了为何只红 macOS。

### 19.3 修复与验证

测试包配置补一个占位资源（把 e2e 配置文件自身 bundle 成
`h822-acceptance-marker.json`），使测试包结构与正式包一致（有 Resources）。
产品代码不动——「启动时 Resources 必须在」对正式包是合理不变量。

- GREEN：重建 0.1.0 直起，`exit code: None`（存活 30 秒被 SIGTERM），
  stderr 空；`Contents/Resources/h822-acceptance-marker.json` 实际在包内；
- 完整 h8_22 验收（三版本 + DMG + 全部 wdio 场景）后台重跑中，绿了才收口。

顺带的观察未立案先记录：正式包若 Resources 损坏/缺失，用户看到的也是
「启动即闪退 + unknown path」这种无从下手的失败形态；启动校验给出可读
错误属于产品体验问题，与 U9 门禁一起考虑。

### 19.4 第八个产品真缺陷：修复态下更新完全不可达（SIGABRT 修掉后顺势暴露）

测试包补上 Resources 后重跑，SIGABRT 消失、spec 前进到启动修复闸——缺执行器
资源的包被启动检查正确送进「打开本地修复工具」页，导航助手按其严格默认拒绝
（这正是 §12 里那条「不可能失败的闸」教训的反面成果）。顺着这个红读产品：

- `StartupGate` 修复态**替换掉**整个工作台，而 `AppUpdateCenter` 只挂在
  工作台 shell 里（h8_21 修的那一处）——**修复态下更新提示与手动检查都不存在**；
- 更新器替换的是整个安装的 .app（含资源），它本身就是损坏安装的标准自愈
  通道；把它排除在修复页外，等于用户装坏了只能手动重装，哪怕修好它的版本
  已经发布。与 h8_21 同族：更新的可见性又一次被绑在「用户此刻正好在哪」上。

修复（TDD，App 级测试先红后绿）：

- `StartupGate` 增加 `updateCenter` 槽位：修复页**收起**修复工具时挂提示版
  `AppUpdateCenter`，**展开**时由修复工具内的设置版接管（含「检查更新」）——
  沿用 h8_21 定下的「同一时刻恰好挂载一份」模式，不出现双 Modal；
- 修复工具的可用条件从「有 platformAdapter」放宽为「有 platformAdapter 或
  有 appUpdateGateway」，诊断面板单独用 platformAdapter 守；
- App.test.tsx 新增两条：修复页不点任何东西提示可达（稍后提醒按钮可用）、
  打开修复工具后「检查更新」在；App 13 条 + WorkbenchShell 27 条全绿；
- spec 侧 `waitForStartup({ allowRepair: true })` 显式声明走修复态（调用点
  可见，符合 navigation.ts 的严格默认设计），两处 `openSettings()` 换成按
  模式分派的 `openUpdateControls(mode)`——批量替换时形状匹配差点把 helper
  自己内部那句也换掉，按行号定点替换（§8.4 又一次）。

完整 h8_22 验收（五场景 + 真实升级替换二进制）后台重跑中，绿了才收口。

### 20.2 d6_10：runner 修复一轮兑现，「设备忙观察超时」其实是 fixture 接缝

runner 补输出透传后第一轮就拿到此前从未见过的三样东西：spec 真实失败点
（`task-discovery.spec.ts:67`，25 秒内真失败而非无声超时）、失败瞬间的页面
正文（App 停在「账号与平台」页）、以及 runner 自己的闸状态报告：

```
platform health = douyin: missing   （fixture 种的是 healthy）
gates = []
attempts = 两个任务的 attempt 全部 failed
```

链条：fixture 向服务端种 douyin=healthy → 第一个任务过闸、建 OFFERED
attempt → **App 侧真实上报把 health 覆写回 missing**（隐藏测试 App 本机
确实没有任何抖音 Profile，报的是实情）→ 健康降级把在途 attempt 判 failed →
第二个 start 在仓储第 2 步平台闸被拒（rejected），从未到达第 4 步忙判定 →
Rust 把 409 映射为 operation_unavailable，前端网关映射为 discovery_rejected，
`TaskRunDetails.onError` 按设计调用 `onPlatformLoginRequired()` 跳去账号与
平台页——这正是失败快照里页面的由来。

**产品各层行为全部正确**（App 报真话、服务端信最新、健康降级熔断在途任务、
前端把「平台条件不满足」引导去平台页）。错的是 fixture 的接缝：向服务端
种假健康，而产品里存在一个会说真话的上报者，谁晚谁赢——这场赛跑 fixture
必输。修复方向（待查清上报者身份与节奏后定）：要么让 App 侧观察到的本地
状态真实地健康（fixture 落地真实 Profile 痕迹），要么等首报落地后再种并
立即推进，若上报是周期性的则前者是唯一稳定解。

对照 §17.3 的方法账：这条从「Installation busy 观察超时」到全案定性只用了
一轮运行——因为可诊断性先行（输出透传 + 闸状态报告都在失败路径上自动打印），
而不是猜一层跑一轮。

### 20.3 d6_10 定性第二轮：不是接缝赛跑，是编排与生产 sidecar 结构性不相容

§20.2 的「种数据被覆写」模型被时间戳插桩**推翻**。带 created_at/updated_at 的
全量转储显示：

```
09:30:15.504 attempt A 创建   .546 命令 acknowledged（delivery_attempts=1）  .567 A failed
09:30:16.055 attempt B 创建成功（没撞忙——A 只活了 63ms）            .632 B failed
09:30:24     健康才被上报 missing（晚 8 秒，与忙判定无关）
```

- **命令被确认了**——App 随起的 sidecar 执行器就在线（control-plane-e2e 走生产
  链路），对无抖音登录的 discover 命令秒拒；
- **两个 start 都成功了**——竞争任务没撞忙，因为忙窗口只有 63 毫秒；
- 跳到账号与平台页是产品特性（发现因需登录失败自动打开处理页，正是 h8_16f
  的旅程 spec 在验证的行为）；
- 试了用产品的全局紧急停止先停 sidecar（真实用户动作、门禁改用
  `button.emergency-stop-button` 指名头部按钮）——**无效**：协作式停止保持
  连接、拒绝新工作、attempt 照样秒败。这个语义本身正确（§4.4：不静默排队）。
  该 spec 改动已按最小改动纪律回退，只保留 runner 插桩。

**终局定性**：d6_10 的编排（「runner 后启的 formal Executor 是唯一执行器，
attempt 会停在 OFFERED」）与生产 App 自带 sidecar 结构性不相容——忙观察和
收敛两个阶段的命令都会被 sidecar 抢走秒拒。产品每一层行为都对；是验收设计
的前提被生产链路的完善无声打破。

忙语义现有三层确定性覆盖：仓储 start 的忙判定（pytest）、Rust 423→
installation_busy 映射（cargo test）、TaskRunDetails 忙文案（组件测试）。
缺的只是「真实 App UI 里亲眼看到忙」这一层。候选方向（需决策）：
① 并入 h8_16f 式受控执行器包（sidecar 即 formal，发现由受控页面拖住，
忙窗口真实且可控）；② 受批准的测试专用 sidecar 暂停命令（增加测试面，
需对照单一构建路径规范三类例外评审）；③ 重划验收范围（UI 忙观察退出
d6_10，收敛链路改为直接面对 sidecar 的受控发现）。方法教训：两轮定性
都靠失败路径的自动转储，每轮一次运行；但第一轮的模型错了——**时间戳
没到手之前，因果顺序就是猜的**。
