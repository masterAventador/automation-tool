# T129 执行器候选里的 framework 永远签不出来，审计却放它过去

日期：2026-07-27
分支：`main`（基点 `e78007e`）
执行：本机 macOS（第二台 Mac，`/Users/aventador/sourceCode/automation-tool`）。改动只涉及 `macos_candidate.py` 与它的单测，未动打包脚本、未重新出包。

---

## 1. 结论先行

**这份载荷里的 framework 不可能既可签又可入，所以审计必须当场拒绝它。**

- 候选审计**禁止 symlink**（`audit_macos_executor_candidate` 逐条 `lstat`，遇 symlink 即拒），`build_macos_executor_candidate` 也因此用 `shutil.copytree(..., symlinks=False)` 把链接实体化。两者都是有意的；
- 而 framework 要被 codesign 认出来，**`Versions/Current` 必须是符号链接**；
- 两个要求不可兼得。所以执行器候选里出现 `.framework`，只可能是**解释器选错了**，不是产物哪里没修好。

原先的做法是试图"把 framework 修到能签"（删掉实体化产生的根别名），前提就是错的，**留着它是死代码**，已一并删除。

**这条缺陷的代价是真金白银**：2026-07-27 这台机器上，出包跑到 Developer ID 签名（约二十分钟处）才倒下，报的是

```
codesign failed: .../executor/automation-tool-executor/_internal/Python.framework:
bundle format is ambiguous (could be app or framework)
```

**这句话既不提解释器，也不提修法**，现场排查花掉的时间远超构建本身。

---

## 2. 判据是实测出来的，不是猜 codesign 的内部逻辑

在同一台机器上用真实 Mach-O（`/bin/echo`）造五种形状，逐个 `codesign --force --options runtime --sign <Developer ID>`：

| 形状 | 结构 | 结果 |
|---|---|---|
| A | 只有 `Versions/3.12/Python` | ❌ `bundle format unrecognized, invalid, or unsuitable` |
| B | A + 实体目录 `Versions/Current/Python` | ❌ 同上 |
| C | A + 顶层 `Resources/Info.plist` | ✅ 可签 |
| D | B + 顶层 `Resources/Info.plist`（**事故形状**） | ❌ |
| E | `Versions/Current`、顶层 `Python`/`Resources` 均为符号链接 | ✅ 可签 |

**只有 E 是真正合法的 framework**，而它要的正是审计禁止的 symlink。**C 是侥幸**——顶层的 `Info.plist` 让 codesign 把它当成老式 bundle 签了，签出来的东西语义不是 framework，不该依赖。其余三种直接失败。

真实产物（Homebrew `python@3.12` 经 PyInstaller + 实体化拷贝）落在 **D**。

对照实验还证实了一件事：把 D 的 `Versions/Current` 与顶层 `Resources` 恢复成符号链接后**立刻可签**，`codesign --verify --strict` 通过——所以"恢复符号链接"技术上可行，**但会撞审计**，不是这条路能走的方向。

---

## 3. 为什么另一台机器没撞到

同一份代码、同一个 PyInstaller 6.21.0，产出形态取决于**解释器布局**：

| 解释器 | 布局 | PyInstaller 产出 | 能否签 |
|---|---|---|---|
| Homebrew `python@3.12` | framework | `_internal/Python.framework` | ❌ |
| uv 托管 standalone CPython | `lib/libpython3.x.dylib` | `_internal/libpython3.12.dylib` | ✅ |

本机的现成对照组：**素材成片 Worker** 锁定 CPython 3.11.15（uv 托管），产出一直是 `libpython3.11.dylib`，从来没有过这个问题。首台机器出的包里执行器是 **293 个文件**，与本机换解释器后逐位相同——framework 布局会多出一截，所以那台用的也是 standalone 解释器。

Homebrew 那份源 framework 本身还是残缺的：`Versions/` 下只有 `3.12`，**没有 `Current` 符号链接**，顶层也没有 `Python`/`Resources`。PyInstaller 打包时会补出标准结构，随后被实体化拷贝铺平。

## 6. 真实边界

**两向都用真实材料 + 生产函数验，没有 mock：**

| 验证 | 材料 | 结果 |
|---|---|---|
| 不误伤 | 刚出包那份真实产物（`.local/release/build/executor/`，standalone 解释器所出） | ✅ 通过，293 文件 / 82 Mach-O——**与 DMG 卷内 `local-executor` 的计数一致，验的就是打进包的那份** |
| 会拒绝 | 同一份产物 + 真实的 `/opt/homebrew/opt/python@3.12/Frameworks/Python.framework` | ✅ 被拒 |

构建者会看到的整句：

```
macOS Executor candidate is rejected: _internal/Python.framework is a framework, which
this payload cannot carry: signing one requires Versions/Current to be a symlink, and
symlinks are refused here. Rebuild backend/.venv on a standalone CPython (uv-managed,
ships libpython*.dylib) rather than a framework-layout interpreter such as Homebrew
python@3.12 — see docs/macos-release-machine-setup.md
```

**没做的**：没有重新出一次包来验这条防御。理由是这条防御在生产路径上的位置就是 `audit_macos_executor_candidate`，而上表第一行用的正是真实出包产物跑真实审计函数；再出一次包只会重复验证"standalone 下不误伤"这同一件事，代价二十分钟。

**失败矩阵**（本任务适用的部分）：

| 情形 | 行为 |
|---|---|
| 候选内有 framework（任意形状） | 拒绝，信息点名路径与修法 |
| 候选内有 symlink | 拒绝（既有行为，未改动） |
| 候选内无 framework（standalone 解释器） | 通过，计数与出包产物一致 |
| 内置浏览器里的 Chromium framework | **不受影响**——它走 `build_staging` + `sign_tree(component="embedded-browser")`，保留 5 个符号链接、结构合法、正常签，与执行器候选是两条路径 |
