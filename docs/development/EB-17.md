## 判据的选择：为什么不只是"找一台干净机"

「干净机上没碰系统 Chrome」这个观察本身**是弱的**——机器上根本没有可碰的东西，
不碰是必然的，它证明不了产品的行为。真正有力的是另外两个方向：

1. **有系统浏览器却不碰它**。这台开发机装着 `/Applications/Google Chrome.app`，
   产品在这种条件下仍然只用包内 Chromium，才同时排除了「发现」和「回退」。
   这比干净机是**更强**的条件。
2. **产品里根本不存在系统浏览器的位置**。想回退，实现总得先写下它装在哪。
   有字面量不等于会用，但没有字面量就不可能去找——这是可回归的下界。

第 2 条一跑就把真问题抓出来了。

## 抓到的真实交付缺陷：正式包里带着 17 个系统浏览器下载器

包内 `playwright/driver/package/bin/` 下有上游自带的 17 个脚本：

```text
reinstall_chrome_stable_{mac,linux,win}    reinstall_chrome_beta_{mac,linux,win}
reinstall_msedge_{stable,beta,dev}_{mac,linux,win}
install_media_pack.ps1    install_webkit_wsl.ps1
```

作用就是**联网下载并安装系统浏览器**，三平台齐全。产品的硬约束是"不发现、选择、下载或
回退到系统浏览器"（CLAUDE.md 第 5 节），这些脚本进了正式包，等于在用户机器上留了一条
绕开该约束的现成路径——**即使产品自己从不调用它们**。它们与库代码性质不同：库代码要产品
显式去调才有影响，这些是可直接执行的下载器。

修法：`remove_browser_installer_scripts` 加进打包流程（`automation-tool-executor.spec`），
按"driver 的 bin 目录 + 安装脚本前缀"判定，不按文件名关键词——后者会误伤产品自己名字里
带 install 的文件。driver 本体一律保留，执行器要靠它驱动包内 Chromium。

## 判据分层：上游库不是产品的回退路径

排除安装脚本后重新打包，扫描仍然拒绝，命中 3 个文件，全在
`playwright/driver/package/lib/`（`coreBundle.js`、`serverRegistry.js`、
`tools/cli-client/registry.js`）。

这一次的判断不同：Playwright 支持 `channel="chrome"`，它的库里当然写着 Chrome 装在哪。
删不得——执行器要靠这个 driver 驱动包内 Chromium。产品的约束是"**产品自己**不去发现、
选择、回退"，不是"依赖库里不许出现这些字符串"。所以扫描排除上游产物目录
（`embedded-browser`、`playwright/driver`），上游库有没有被走到，靠运行期
不下载、不启动系统浏览器来证明，不靠字符串扫描。

两条判据因此是互补的，而不是一条被放宽：

| 判据 | 管什么 |
| --- | --- |
| `scan_package_for_system_browser_references` | 产品自己的代码与配置里有没有系统浏览器的位置 |
| `require_no_browser_installer_scripts` | 包里有没有现成的可执行下载器 |

四条运行期断言：

| 断言 | 怎么成立的 |
| --- | --- |
| 这台机器**确实装着**系统浏览器 | 脚本主动检查，不存在就**拒绝运行**——否则"没碰系统浏览器"退化成那个弱观察 |
| 启动的是包内那一个 | 可执行文件路径必须 `is_relative_to(包)`，且走生产的发行物 Manifest 解析 |
| 版本等于契约锁定值 | 浏览器自报 `149.0.7827.55`，与 `embedded-chromium-staging.v1.json` 一致 |
| 运行期没多出第二套浏览器 | 前后快照 `~/Library/Caches/ms-playwright` 与 `/Applications` 并对比 |
| 进程无残留 | 按包路径过滤进程表 |

**"要求系统浏览器存在"这条是刻意的**：如果哪天在一台没装 Chrome 的机器上跑，脚本会拒绝
而不是照常报通过——因为那时它证明的东西比它宣称的弱，必须由人来决定怎么记录。

## 真实边界

1. **运行期只覆盖浏览器这一层**：验证的是"正式包启动的是包内 Chromium、不多出第二套、
   无残留"。整个 App 的启动（Tauri 窗口、Sidecar、Control Plane 连接）没有在本脚本里走，
   那条链路由 EB-16 的 `installed_release_startup` 覆盖。
2. **未在真正的干净机上跑过**。本机装着 Chrome，用的是"有系统浏览器却不碰它"这个更强
   的条件；但"没有系统浏览器时照常启动"这一面还没验证过。脚本对此是**显式拒绝**而不是
   静默通过——在没有系统浏览器的机器上运行会直接失败并说明原因。
3. **只覆盖 macOS arm64**。Windows x86_64 正式包已在 2026-07-26 构建并完成安装/卸载，
   但同一套运行期判据没在 Windows 安装树上跑过。
4. **扫描是字符串层面的**。它证明"产品代码里没有系统浏览器的位置"，不证明"运行时一定
   不会去找"——后者要靠运行期证据，见第 1 条。
5. **真实账号部分全部未做**：扫码、搜索、受控动作、Browser Use 隔离演示、动效渲染。
