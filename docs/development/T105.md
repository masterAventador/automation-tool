> 日期：2026-07-27
> 分支：`cancel-message`（基点 `6fd7d87`）
> 状态：**🔍 待验收**（三层 RED→GREEN 全绿，含真实用户路径 Playwright 无头；正式签名包上的目视确认未做，缺口见第八节）

来源是 `docs/development/T101.md` 第七节第 5 条自己登记的：

> **本轮新查出的：用户取消渲染之后，从别的页面看仍是蓝点「正在进行中」。**
> …**本轮没修**：修它要动那条 info 消息的生命周期，而消息是单槽的（一条 `message` 服务所有
> 任务），在监视器里顺手 `dismiss` 会误清掉另一条任务的失败文案——多任务下的语义要单独设计。

## 一、结论先行：单槽 message **不改**，改的是侧边栏读错了东西

这条任务被交下来时带着一个设计问题：**这一族（T91 / T91b / T101 / 本条）攒够理由需要一个能表达
「哪条任务、什么终态」的结构了吗？**

答案是：**那个结构已经有了，是 T101 加的 `ownJobs[].outcome`。本条不是缺结构，是侧边栏一直没去读它。**

### 1. 缺陷的真身在判据上，不在消息生命周期上

```ts
// 修改前
if (current.pending !== null || current.message !== null) return "running";
```

`message` 是**制作页上的一条通告**（一个可关闭的 Alert），它回答不了「还有没有东西在跑」。
用它当「在跑」的判据，等于让侧边栏的正确性取决于页面上一条提示有没有被关掉。

而 T101 之后，「还有没有东西在跑」在 store 里已经有了准确答案：`pending`（提交还没回来）
加上 `ownJobs` 里 `outcome === "running"` 的任务——后者正是 `motionRunNeedsWatch`，也就是决定
监视器要不要转的那同一个事实。所以：

```ts
// 修改后
if (current.pending !== null || motionRunNeedsWatch(current)) return "running";
```

这一行既没有新建结构，也没有放宽任何判定——它比原来**更严**：原来「有一条提示在」就算在跑，
现在必须真的有一条运行欠着结果。

### 2. 那句 `message !== null` 是历史遗留，不是设计

T91 之前，这里是一个布尔：

```ts
export function motionRunNeedsAttention(current: MotionRunState): boolean {
  return current.pending !== null || current.message !== null;
}
```

T91 把它拆成 `failed` / `running` 时，`running` 那一支原样继承了这个析取式。当时是对的——
那时候 store 里除了 `message` 没有别的东西记得住「有一条结果他还没看过」。T101 加了 `outcome`
之后这句话就过期了，只是没人回来改。**本条改的是这个。**

### 3. 同一处判据的另一张脸（本轮新查出，一并修掉）

写 RED 时顺带钉了反方向的一条，实测确认：

> **渲染还在跑的时候关掉页面上那条 info 提示，侧边栏的标记会整个消失。**

制作页那条 Alert 是 `closable` 的，用户随手就能关。判据挂在提示上，关掉它就把标记一起关掉了——
而渲染还在跑、监视器也还在轮询。这比取消那半更坏：取消至少是用户自己知道的事，这一条是
**一条真的在跑的任务从屏幕上消失**。同一行代码改完两张脸一起没了，这正是「判据本来就选错了」
的证据，而不是两个巧合。

顺带还消掉了第三张脸（未单独写用例，但同一行覆盖）：两条任务、一条失败一条在跑，用户关掉失败
提示之后，原来会落到 `none`，即在跑那条也失去标记；现在落到 `running`。

### 4. 为什么 `failed` 那一支**继续**读 message，这不是没收拾干净

```ts
if (current.message?.tone === "error") return "failed";   // 保留
```

因为**编排阶段失败时任务压根不存在**——这是 T91 查证过的：原生侧 `submit_motion_video_brief`
把任务快照写在编排跑完之后，编排失败就没有快照，`ownJobs` 里也就没有对应条目。那次失败的唯一
落点就是这条消息。**任何以任务为键的结构都装不下它。**

所以最终形态是有理由的、不对称的：

| 分支 | 读什么 | 为什么 |
|---|---|---|
| `failed` | `message.tone` | 编排失败时没有任务可挂；渲染失败虽然有任务，但走同一条通告以免两套文案 |
| `unknown` / `finished` / `running` | 运行事实（`pending` / `outcome`） | 这三件事都是关于运行的，都有任务可挂 |

### 5. 那么单槽 message 到底有没有代价？有，如实记在第七节

多条任务同时失败时，第二条 `failMotionRun` 会**覆盖**第一条的文案，页面上只看得到一条。但：

- 侧边栏仍然正确（`failed`），没有说谎；
- **每条任务各自的失败原因本来就不在这条消息里**——它在任务卡上（`motionFailureAdvice(job.failureCode)`），
  `motion-run-watch.ts` 的注释明确写过这个分工：「Why it failed is on the job card on the studio page」。

也就是说 message 是**通告**，不是任务结果的记录；任务结果已经有两处权威记录（`ownJobs.outcome`
和原生快照）。再给它加一个 `Map<jobId, message>`，就是同一事实的第三份表示——项目规则明确禁止
（「禁止无证据的大范围重构和为假设性需求过早抽象」「同一个数字不许存在两处」的同一条精神）。

**所以：单槽保留。** 覆盖这件事登记为已知窗口，不在本任务顺手改。

### 6. 特别说明：没有在任何地方新增 `dismiss`

T101 拒绝顺手修的理由是「在监视器里 dismiss 会误清另一条任务的失败文案」。本轮**一个 dismiss 都
没加**——取消之后那条 info 通告仍然留在制作页上，用户可以自己关。理由是自洽性：那句话
（「已提交…编排完成，本机渲染开始了」）在写下的那一刻是真的，它是一句关于**已经发生过的提交**
的陈述，不是对当前状态的断言；而它旁边的任务卡此刻明明白白写着「已取消」。**要清它就必须判断
它属于哪条任务，那才是真的需要新结构——而那个需求本条并不成立。**

## 四、失败矩阵（本轮新增与相关行）

| 情形 | 现在的行为 |
|---|---|
| **用户取消渲染，人在别的页面** | **监视器 5 秒内观察到 `cancelled` → 侧边栏标记整个消失**（不是改成别的角标） |
| 取消之后、监视器还没轮询到的那 ≤5 秒 | 仍显示蓝点「正在进行中」——App 此刻确实还不知道，与失败那半同一形状，不算谎报 |
| **渲染还在跑，用户关掉页面上那条 info 提示** | **蓝点保留**（本轮修掉；原来会整个消失） |
| 两条任务，一条失败一条在跑，用户关掉失败提示 | 落到 `running`（原来落到 `none`，在跑那条一起失去标记） |

| 编排阶段失败（任务尚不存在） | 仍然是「失败」——该分支仍读 message，理由见第一节第 4 点 |
| 渲染成功 / 渲染失败 / 读不到 / 未提交过任何东西 | 与 T91b、T101 一致，未变（全量用例守着） |
| App 重启 | **不恢复**，未修，见 T101 ② |

**边界遵守情况**：`VideoStudio.tsx` **一行未改**；`motion-run-watch.ts` **一行未改**（取消这条

**一旦任务到达 `cancelled`，侧边栏不再替它说话。**

6. **本轮新登记：多条任务同时失败时，页面上那条通告会被后来的覆盖，只看得到一条。**
