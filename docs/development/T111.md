## 一、根因

`scripts/video_runtime_cache.py` 的 `contract_fingerprint()` 只对传进来的**文件**逐个摘要。
`scripts/prepare_video_runtime.py` 里三个产物各自声明自己的缓存键，其中
`material-video-worker` 只声明了两个契约 JSON，**没有声明 PyInstaller 冻结的那棵源码树**
`workers/material_montage/`。

后果是一条完整的静默失败链：T32 改掉素材成片里三个等于没音乐的背景音乐选项 →
提交进仓库 → 发版调用 `prepare_video_runtime.py` → 缓存比对两个契约 JSON，
两个都没变 → 缓存回答「仍然是最新的」→ 把改动之前冻结的旧二进制原样交出去。
**没有任何一步报错，没有任何一步说谎，用户拿到的就是修复前的包。**
T108 第九节对比两个产物实测到了这个结果，本任务修的是它的根因。

同一个文件里隔 13 行，`motion-video-worker` 声明了自己的源码而
`material-video-worker` 没有——这正是「只修被投诉的那一条」会漏掉其余两条的形状，
所以下面三条都判了一遍。

### 目录摘要要处理的三件事

1. **确定性排序**：`sorted(directory.rglob("*"))`，且条目名是**包内相对路径**而不是绝对路径——
   绝对路径会让每棵 worktree 算出不同的键，把「每机一份的共享缓存」变成「每个 checkout
   各跑一次 PyInstaller」。有专门用例 `test_the_same_package_in_another_checkout_fingerprints_the_same` 盯着。
2. **排除 `__pycache__` 与 `.pyc`/`.pyo`**：否则跑一次测试导入了这个包，就会让产物失效。
3. **新增文件也要让键变化**：摘要是「遍历当前树」而不是「按一份已知文件名清单取摘要」，
   所以新增、删除、改名都改变键。三个方向各有用例。

另外两处顺带的收口，都因为条目名从「文件基名」变成了「带 `/` 的相对路径」才成为必要：

- **名称冲突拒绝**：两个条目同名时键无法说清是哪一个变了，直接拒绝而不是猜。
- **名称长度分隔**：摘要是定长 64 位十六进制，名称却是变长的，不加边界时两组不同的
  输入集合可以拼出同一段字节流。这是 T74 `executor_package_input_digest` 已经采用的做法。

### 复用检查（写代码前先搜了）

  且位于一个会拖进大量桌面 E2E 机械的模块里，无法直接调用。**复用了它的做法**

## 五、门禁：下一次谁来发现

`test_no_build_driver_reads_a_repository_path_outside_its_cache_key`。

**为什么光有内容摘要不够。** 修完之后，改一个**已经在键里**的文件会被摘要抓到。
但这个缺陷有另一半形状：**构建脚本长出一个新输入，而没人把它加进键**——
这个新文件从来没被摘要过，摘要不可能发现它。事故当初就是这么发生的：
`workers/material_montage/` 一直存在，只是从来没进过那份清单。

**门禁做的事**：读每个产物的构建驱动脚本本身，把它文本里出现的每一个仓库路径
（`backend/` `contracts/` `frontend/` `scripts/` `vendor/` `workers/` 六个顶层目录下、
且在仓库中真实存在的）拿出来，要求每一个都被该产物的缓存键覆盖，
或者写进 `EXEMPT_BUILD_INPUTS` 并附上「它为什么改不动产物」的理由。
同时要求每个驱动脚本**自己**也在自己产物的键里。
覆盖的驱动：`build_video_media_toolchain.sh`、`write_video_media_toolchain_manifest.py`、
`build_motion_video_worker_candidate.py`、`build_material_video_worker_candidate.py`、
`material-video-worker.spec`、`subtitle_font_assets.py`。

**证明它真的会红（反证实验）**：在 `build_motion_video_worker_candidate.py` 末尾临时加一行
`NEW_INPUT = ROOT / "contracts/video/ffmpeg-toolchain.v1.json"`：

```
rc=1
+ ['contracts/video/ffmpeg-toolchain.v1.json'] : scripts/build_motion_video_worker_candidate.py
  reads these while building motion-video-worker, but they are not in its cache key
  and carry no recorded reason for being left out
```

实验后该文件已还原（`git diff` 对它为空）。

**门禁自己在开发过程中抓了一个真东西**：它把
`scripts/run_bm_02_acceptance.py` 报了出来——那是 `build_motion_video_worker_candidate.py`
最后一行 `SystemExit` 提示语里的字符串，是**调用方**不是输入。这条被写进
`EXEMPT_BUILD_INPUTS` 并附了理由。门禁故意做得吵：只要提到仓库路径就报，
消音的唯一办法是写下理由，这正是想要的。

**门禁抓不到什么**（如实登记，不假装覆盖）：

- 构建脚本用**拼出来的**路径读文件（如 `ROOT / some_variable`），文本里没有字面量；
- 通过 Python import 间接拉进来的模块——`subtitle_font_assets.py` 是手工列进
  `BUILD_DRIVERS` 的，不是自动跟踪 import 图得来的；
- `vendor/` 内部的变化——由 `check_third_party_sources.py` 另行守着 commit 一致性。

## 六、失败矩阵

| 情形 | 行为 |
| --- | --- |
| 源码包里某个文件被改 | 键变化 → 重建（本次事故） |
| 源码包里新增文件 | 键变化 → 重建 |
| 源码包里删除文件 | 键变化 → 重建 |
| 只是 import 了这个包（产生 `__pycache__`/`.pyc`） | 键不变 → 复用，不误伤 |
| 声明的源码包整个不见了 | `VideoRuntimeCacheRejected`，拒绝而不是当成「没变」 |
| 声明的源码包是空目录 | `VideoRuntimeCacheRejected: holds no files` |
| 包内出现软链 | `VideoRuntimeCacheRejected: symbolic link`——目标不在摘要范围内，字节可能悄悄变 |
| 两个输入条目同名 | `VideoRuntimeCacheRejected: share the cache key` |
| 同一份源码在另一棵 worktree | 键相同 → 共享缓存，不会每棵树各跑一次 PyInstaller |
| 包内文件权限拒绝读取 | `PermissionError` 向上抛，`ensure_cached` 不写 stamp——失败关闭，下次重建 |
| 构建中途失败 | 既有行为不变：删除半成品目录、不写 stamp |
| 构建脚本新增输入却没进键 | 第五节门禁报红 |

## 七、真实边界

- **本次改动使本机三个产物的缓存全部判定为失效**，实测（对比磁盘上真实 stamp 与新键）：

  ```
  media-toolchain:       stamped=a235f37a4c1b new=8d4f8f4acc42 -> REBUILD
  motion-video-worker:   stamped=58a18f6983b0 new=a0e5d55f41ec -> REBUILD
  material-video-worker: stamped=642c1c07eecd new=dd51583280ca -> REBUILD
  ```

  这是**生产决策函数在真实仓库文件与真实 stamp 上的求值**，不是构造出来的样本。
  对 `material-video-worker` 而言，这次重建正是一直被错误跳过的那一次。
  代价：每台机器一次性重跑三个构建，其中 ffmpeg 是从源码编译，**发版前需要预留时间**。

- **没有真的跑完整构建**。原因有两条：一是 material Worker 一次 PyInstaller 冻结约 20 分钟、
  motion 要下 Node 运行时、media toolchain 要编 ffmpeg；二是**这三个产物共用每机一份的缓存目录**，
  而主线随时可能在出正式包，`ensure_cached` 会先 `rmtree` 目标目录再构建，
  并发跑会破坏主线正在读取的产物。真正的重建发生在发版链路下一次调用
  `prepare_video_runtime.py` 时，那是该发生的地方。

- **生产同路径的部分做到了哪里**：`declared_inputs()` 调用的是**真实的 `prepare()`**，
  取的是它真正传给缓存的那份清单（而不是读一个常量），只把「构建」和「取字体」两步换成桩——
  因为被测的是键由什么构成，回答这个问题不该花一次 PyInstaller。
  既有用例 `test_the_worker_lands_where_the_rust_test_reads_it` 则是 subprocess 起真实 CLI，
  走真实 `prepare()` → `ensure_cached` → 对真实仓库文件算指纹 → 判定复用 → 安装，
  这条链路在新键下依然通过。

- **没有碰其他脚本**。改动只落在 `scripts/video_runtime_cache.py`、
  `scripts/prepare_video_runtime.py` 及这两者的测试。已确认全仓库没有第二处消费
  stamp 格式或指纹值的代码（`release_assembly` 按目录名读取，与键无关）。

- **未触碰 `vendor/`、`docs/demo-sprint-roadmap.md`**，未挂载任何 DMG，
  未把 `backend/.venv` 或 `frontend/node_modules` 软链到别处。
