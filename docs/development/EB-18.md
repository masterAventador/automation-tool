## 任务

把 `scripts/build_release_package.py --platform windows` 从「显式拒绝」变成唯一的
Windows 出包入口，并让三份重复的 `build_installer()` 收敛到它上面。

## 为什么这是一个任务而不是一行分支

macOS 侧 `build_release_package.py` 的存在理由写在它自己的模块 docstring 里：出包步骤
原先只活在 `run_eb_16_acceptance.py` 内部、没有第二个调用方，于是**验证路径与出厂路径
是两段不同的代码**，2026-07-26 出厂那段少带了三个资源，是用户发现的。

Windows 侧今天正处在那个状态，而且更重：

| | macOS | Windows |
| --- | --- | --- |
| 出包入口 | `build_release_package.py` | 无，埋在 `run_eb_16_windows_acceptance.py:558-618` |
| `--platform windows` | — | `build_release_package.py:1300` 直接抛 `this command builds macOS packages only` |
| 重复实现 | 0 | 3（EB-16-WIN 一份、`run_pc_16_windows_package_acceptance.py` 与 `run_le_23_windows_package_acceptance.py` 各一份 `build_installer()`） |
| 部署 Profile 通道 | 有 | **无**——`run_p9_04_acceptance.release_environment` 只有两个参数，Windows 根本出不了客户 Demo 包 |
| 发布身份 | `Info.plist` 的 `AutomationToolReleaseIdentity`，外层 Developer ID 封 | 无载体 |

后两行不是重构，是缺失的能力：**没有部署 Profile 通道就没有 Windows 客户包；没有发布
身份就没有 EB-11 Windows 验收**（`run_eb_11_formal_app_acceptance.py` 的
`read_signed_release_identity()` 是那把身份的唯一消费方）。

## RED

三条全部在本机（Windows 11 / `backend\.venv` Python 3.12.13）实跑，各自的报错就是缺口
本身，不是「断言没写对」：

```text
backend\.venv\Scripts\python.exe -m unittest scripts.test_build_release_package.WindowsReleaseTests
Ran 3 tests — FAILED (failures=2, errors=1)
```

**① `test_the_windows_platform_has_a_release_builder`**

```text
AssertionError: False is not true : --platform windows has no builder, so main() can only refuse it
```

**② `test_a_private_dependency_copy_does_not_depend_on_bin_cp`**

```text
File "scripts/build_release_package.py", line 1071, in _clone_snapshot_dependency
FileNotFoundError: [WinError 2] 系统找不到指定的文件。
```

`_clone_snapshot_dependency` 硬编码 `/bin/cp -c -p -R`（APFS `clonefile`）。本机实测
`shutil.which("cp") is None`、`os.path.exists("/bin/cp") is False`，所以它在**复制第一个
字节之前**就死了。这一步不是可选的：它给快照一份私有的 `frontend/node_modules`，
2026-08-04 就是因为它当时还是软链，pnpm 写穿到操作者那份，出包后 `npx vitest` 找不到自己。

**③ `test_the_snapshot_capability_reaches_a_child_on_this_host`**

```text
AssertionError: False is not true : the capability handoff is inlined and POSIX-only,
so no Windows release can carry a trustworthy source identity
```

底层事实实测：

```text
subprocess.run(..., pass_fds=(r,)) →
AssertionError: pass_fds not supported on Windows.
```

这一条最要紧。第 14 轮 Codex Review 之所以把两个公开环境变量换成一次性匿名管道，正是
因为公开那对可以让**普通可写 checkout 冒充已物化快照**。而 `pass_fds` 在 Windows 上
不存在——不是弱一点的通道，是**没有通道**。所以今天的 Windows 出包不可能携带可信的源码
身份，EB-11 Windows 也就没有可校验的包。

## 真实边界

- 本机无 Authenticode 证书（`BLOCKERS-2026-08-04.md` 记录两处证书库均为 0），所以本任务
  产出的包必然 `NotSigned`。这一点按 EB-16 Windows 既有做法**实测记录、不断言掉**；
- 因此 Windows 的发布身份载体不能照搬 macOS「写进 Info.plist 再由外层签名封住」那套。
  取什么载体、它能诚实宣称什么，属于本任务待定的设计点，不得先写成「等价于 macOS」。
