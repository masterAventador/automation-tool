## 0. 这一轮做完了什么

一个真零件，经产品自己的工作区写入器、产品自己的渲染沙箱、包内 Chromium 与包内
ffmpeg，渲成了一条 mp4，读数与零件声明逐位吻合。

## 1. 先解开的两个约束，都是量出来的

**一、渲染画布不能再是常量。** worker 里写死 640×360 是因为过去只渲一样东西——
`composition_template` 的输出，它整套字号体系为那张舞台而写。零件是自带画布的独立
合成：目录里 105 个声明 1920×1080，三个 1080×1920 竖屏，一个 1440×2560。把零件画在
模板舞台上得到的是它自己舞台的左上角，正是 `motion-render-canvas.v1.json` 的
`rationale.problem` 记着的那次事故。

改为随请求走，边界留契约：边长 320~2560、缩放 1~3、输出像素上限 3,686,400。
上限按乘积而非边长——否则 2560×2560 @3 会被放行，那是每帧 5900 万像素。

**二、沙箱资产上限 128，而共享依赖有 125 个文件。** 见 `PC-03.md` 11.4：改为按文档
实际引用拷贝后，工作区文件数从 127 降到最多 7。若不先解这条，任何零件渲染都会在
允许清单上被拒。

## 2. 真实渲染读数（ffprobe，从成片读出）

零件 `lt-bold-block`（下三分之一，2 个槽，声明 1920×1080 / 4.8 秒）：

```
worker.render.sandboxed   framesCaptured=144   outputBytes=2257286
chromiumMajor=149   blockedRequests=0 blockedNavigations=0 blockedDialogs=0

$ ffprobe 成片
codec_name=h264   width=1920   height=1080   pix_fmt=yuv420p
avg_frame_rate=30/1   nb_read_frames=144   duration=4.800000   size=25667
```

**尺寸等于零件声明的原生尺寸，帧数 = 声明时长 × 30，逐位吻合。**

单帧本身也量过：`frame-00001.png` 是 1920×1080，不是被放大出来的。

## 3. 没有静止尾巴

逐帧 SHA-256 比对 144 帧：

```
不同的帧 38   相邻变化 38 次
开头静止 4 帧（0.13s）   结尾静止 3 帧（0.10s）
```

结尾静止 0.1 秒，不构成静止尾巴。144 帧里 38 个不同帧是这个下三分之一自己的节奏
（入场后保持可读），不是 seek 失效——第 10 帧拍到的正是入场中途：卡片较小、名字淡入
中、黄条尚未展开成标签。

## 4. 长短文案对照：这一条推翻了路线图的记载

路线图 P0-1a⁗ 把 `lt-bold-block` 举为「排版层」的典型，说它
`font-size: 58px` 写死、`.lt-tagwrap { overflow: hidden }`，所以
**「长了不是难看，是看不见——被裁掉」**。

实测不是。同一零件换成 13 字姓名 + 24 字身份：

```
短文案  张三 / 主播·神经科学家                          卡片窄
长文案  欧阳明日复明日何其多张三丰 /
        资深短视频运营总监兼神经科学研究员与内容策略顾问   卡片跟着长开，无裁切
```

容器是自适应宽度的，`overflow: hidden` 只在子元素超过父元素计算宽度时才咬人，而这里
父元素跟着内容长。**真正的边界是画布宽度**，不是这条 CSS。

这不推翻「塞长文案会出事」这个结论本身——73 个零件确实既不测尺寸也不自适应，PC-14
的溢出实测仍然必要。推翻的是「按 CSS 静态判断哪个零件会裁切」这个方法：判据只能是
在真渲染里量 `scrollWidth > clientWidth`，而不是读样式表推断。

## 5. 中文在真渲染里显示正确（PC-13 的实际收口证据）

成片帧里 `张三` 与 `主播·神经科学家` 显示正常——不是豆腐块，也不是宿主机器的系统
字体，是包内那份 Noto Sans SC。字体 URL 经 `artifact_prefix` 修正后才成立，修正之前
18 个零件的字体引用全部解析不到（见 `PC-03.md` 11.4）。

## 6. 失败矩阵

| 情形 | 期望 | 实测 |
| --- | --- | --- |
| 规格缺 `canvas` | 拒绝 | 红（`render_sandbox_invalid`，三条真渲染用例同时抓到） |
| 画布超出契约边界 | 拒绝 | 由 `validCanvas` 与 Rust 侧 `VideoWorkerRenderCanvas::new` 双侧拒 |
| 画布边长合法但乘积超限 | 拒绝 | 两侧都按输出像素乘积判 |
| 零件请求的字体包内没有 | 拒绝 | `FontRequestUnmet`（PC-03） |
| 引用离开目录 | 拒绝 | `SlotAnchorRejected`（PC-03） |
| 每帧完全相同 | 判失败，不出静止片 | worker 既有的静止帧门禁，本次未触发 |

## 7. 还差什么

**产品入口尚未调用这条链。** 模型选出的 `catalog_parts` 要先被组装成镜头，才谈得上
渲哪几个零件——那是编排层（P0-1a）。本轮的渲染由一个驱动脚本发起，用的是产品自己的
worker、工作区写入器、包内 Chromium 与包内 ffmpeg，但**不是从正式 App 的用户入口进去
的**，按「生产同路径验收」只能算分层证据，故标 `🔍`。

## 8. 清理

驱动脚本与渲染产物都在临时目录，未进仓库。渲染结束后 Chromium 进程由 worker 自己
的生命周期管理，本轮无残留。
