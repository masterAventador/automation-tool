## 任务

客户 Demo 当天双击 `.dmg`、把图标拖进「应用程序」完成安装。要求挂载后能看到 App
图标和 `/Applications` 符号链接。

## 结论先行：原定的修改位置是无效的

任务原本计划在 `frontend/src-tauri/tauri.conf.json` 的 `bundle.macOS.dmg` 下补
`appPosition` / `applicationFolderPosition` / `windowSize`。**实测这条路径对本产品
完全不生效，本任务因此没有修改 `tauri.conf.json`。**

原因：本产品的发版 DMG 不是 Tauri bundler 产出的。

`scripts/build_release_package.py:239` 的构建只要 `.app`：

```text
pnpm exec tauri build --bundles app --config … --ci
```

`--bundles app` 意味着 Tauri 的 DMG bundler 从头到尾没有被调用。DMG 是随后在
`create_disk_image()`（同文件 :338）里用 hdiutil 手工生成的：

```python
"hdiutil", "create",
"-volname", application.stem,
"-srcfolder", os.fspath(application),   # ← 直接把 .app 当作源
"-fs", "HFS+", "-format", "UDZO", "-quiet",
```

`-srcfolder <某个 .app>` 生成的卷里**只有这一个 .app**，没有别的条目。所以
`bundle.macOS.dmg` 无论写得多正确都不会被任何代码读到——那是一段死配置。

这个先后顺序是有意设计的，不该改回 Tauri bundler：`.app` 必须先公证并 staple，
DMG 才能生成（`create_disk_image` 的注释写明了理由——只 staple DMG 的话，客户拖出来
的那份 App 不带票据）。Tauri bundler 在 build 阶段出 DMG，赶不上这个顺序。

## 证据：真实产物确认缺失

拿 2026-07-26 20:52 由正式发版路径产出的那个 DMG 直接挂载核对：

```text
hdiutil attach wt/release/.local/release/cargo-target/release/bundle/dmg/自动化运营工具_0.1.0.dmg \
  -nobrowse -readonly -mountpoint <挂载点>

总计 0
drwxr-xr-x@ 3 aventador staff 170 Jul 26 20:47 .
drwx------@ … ..
drwxr-xr-x@ 3 aventador staff 102 Jul 26 20:41 自动化运营工具.app
```

只有 App，没有 `Applications` 符号链接，也没有 `.background` / `.DS_Store`——即整个
Finder 布局步骤从未发生过。客户挂载后确实没有可拖拽的目标。问题属实。

## Tauri v2 字段名的核对来源（供以后参考）

字段名从本仓库锁定版本的 schema 里读出，不是凭印象：

- `frontend/node_modules/@tauri-apps/cli/config.schema.json`（CLI 2.11.4）
- 路径 `bundle.macOS.dmg` → `definitions.DmgConfig`
- 合法键只有五个：`background`、`windowPosition`、`windowSize`、`appPosition`、
  `applicationFolderPosition`；`Position` = `{x, y}`，`Size` = `{width, height}`

附带两点值得记下：

1. `DmgConfig` 是 `additionalProperties: false`，所以拼错的键会直接报错而不是被静默
   忽略——这一点和任务描述里的担心相反；
2. 三个布局键**本来就有默认值**（`windowSize` 660×400、`appPosition` {180,170}、
   `applicationFolderPosition` {480,170}）。也就是说，如果走 Tauri bundler，符号链接
   本来就会有：CLI 二进制内嵌的 `bundle_dmg.sh` 里
   `if [[ -n "$APPLICATION_LINK" ]]; then … ln -s /Applications "$MOUNT_DIR/Applications"`，
   而 `APPLICATION_LINK` 取自 `--app-drop-link` 的 x 坐标，默认 480 非空。
   本产品缺链接**不是因为没配置，而是因为压根没走那条产线**。

## RED

在 `frontend/tests/release-package-gate.test.mjs` 追加门禁（该文件已经负责对
`build_release_package.py` 的结构断言，故不另起新文件）：

```text
node --test tests/release-package-gate.test.mjs

✖ the mounted disk image gives the customer somewhere to drag the app
  AssertionError: the image must be built from a staging directory, not the bare .app
    actual: 'application'
    expected: 'application'
    operator: 'notStrictEqual'

ℹ pass 4  ℹ fail 1
```

断言失败而非 import/文件缺失，指向的正是生产代码把裸 `.app` 交给 `-srcfolder` 这一
事实。

为什么这条门禁必须存在：发版链路里最后一道 `require_distributable_release()` 只把
DMG 当作被隔离的下载物问 Gatekeeper「能不能打开」，**没有任何一步查看过卷内部的结构**。
缺符号链接不会被现有任何门禁拒绝，和本仓库此前「视频运行时缺失却全绿出厂」是同一类
缺口。

## GREEN：尚未达成，缺口明确

使其转 GREEN 的改动落在 `create_disk_image()` 内，即 `scripts/` 目录下。该目录本轮
由并行开发线占用，为避免合并冲突，本任务按约定未改动，改由集成方施加。

已验证可用的改法（`tempfile` 尚未在该文件导入，需一并补上）：

```python
    with tempfile.TemporaryDirectory(dir=output.parent) as staging_root:
        staging = Path(staging_root) / "image"
        staging.mkdir()
        # ditto 保留签名与已 staple 的票据
        run_checked(["ditto", os.fspath(application),
                     os.fspath(staging / application.name)])
        (staging / "Applications").symlink_to("/Applications")
        run_checked([
            "hdiutil", "create",
            "-volname", application.stem,
            "-srcfolder", os.fspath(staging),        # ← 交暂存目录，不是裸 .app
            "-fs", "HFS+", "-format", "UDZO", "-quiet",
            os.fspath(output),
        ])
```

### 这段改法已用真实 hdiutil 实测过（小体积替身，非推断）

用一个 ad-hoc 签名的小 `.app` 走完整条链路：

```text
# 复现现状：-srcfolder <裸 .app>
挂载根目录 → 只有 Demo.app                      ← 与真实发版 DMG 表现一致

# 改法：暂存目录 + 符号链接
lrwxr-xr-x@ 1 … Applications -> /Applications
drwxr-xr-x@ 3 … Signed.app

# 卷内 .app 的签名仍然有效
codesign --verify --strict --verbose=2 <挂载点>/Signed.app
  valid on disk
  satisfies its Designated Requirement
```

签名在 `ditto` 之后、以及进入 DMG 之后都保持有效——这是这条改法的关键风险点（`.app`
是先公证 staple 再成像的），已验证通过。`cp -c -p -R`（APFS clonefile）同样保签名，
510 MB 近乎瞬时，若嫌 `ditto` 拷贝慢可换用。

## 真实边界

- **未在真实发版 DMG 上核对**。缺的就是这一件事：修复落地后重新出包，然后
  `hdiutil attach` → `ls -la` 确认 `Applications -> /Applications` → `hdiutil detach`。
  本任务只完成了配置定位、门禁测试与改法实测，不足以宣称完成，故标 `🔍 待验收`。
- 上面的 hdiutil 实测用的是小体积替身 App，证明的是**成像机制**，不是本产品那个
  510 MB 产物。
- 窗口尺寸、图标坐标、背景图这类观感项本任务未处理。hdiutil 手工成像不带 Finder
  布局，若要图标定位需另行注入 `.DS_Store`，属独立任务。
