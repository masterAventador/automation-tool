## 0. 为什么开这个任务

PC-03 做完替换实现后要接线，接线前先核了一遍「零件在用户那个包里到底在不在」。**不在。**

三条互相独立的证据：

```
1. 签名公证过的 .app 内零件 HTML 计数 = 0
   Contents/Resources/ 只有五个目录：
     embedded-browser 336 / local-executor 293 / material-video-worker 2107 /
     media-toolchain 8 / motion-video-worker 4
2. grep -rn "motion-catalog-release|releaseRoot" --include=*.py --include=*.rs
     只有 scripts/ 命中；backend/src 与 frontend/src-tauri 一个读取点都没有
3. Rust 侧唯一的运行时播种 seed_authoring_runtime 只放 gsap.min.js 一个文件
```

发布树 46 MB / 338 文件至今**只是开发机 `.local/` 下的构建产物**。

这不是新功能，是规则「单一构建路径」点名的既有缺口：

> **每一项运行时依赖都必须有生产装配路径**，并有门禁在产出可分发产物之前拒绝缺失的包。

自检那三问，第二问就答不上来：「这个功能依赖的每一样东西，在用户那个包里真的存在吗？我打开包看过吗？」——打开看过了，没有。

## 1. 单一事实源已经在，加一行就够

`contracts/quality/release-package-resources.v1.json` 的 `$comment` 自己写着：

> Single source: `scripts/release_assembly.py` derives VIDEO_RUNTIME_RESOURCES from the
> video entries, `frontend/scripts/audit-production-package.mjs` derives its
> required-resource assertion from all of them, and
> `scripts/check_release_package_wiring.py` derives the release wiring gate from the same
> file. **Adding a resource here is what makes every one** …

所以不新建第二份清单，往这份里加第六项。

**`category` 不能用 `video`。** 那三项的含义是「由 `prepare_video_runtime.py` 构建、缓存在
`~/Library/Caches/automation-tool-build`」，而零件树由 `build_motion_catalog_release.py`
产出、落在 `.local/motion-catalog-release/`，构建与缓存都是另一条。混进 `video` 会让
`VIDEO_RUNTIME_RESOURCES` 把它当成视频运行时去缓存目录里找，找不到。新开 `catalog` 一档。

## 2. RED

声明资源之后，派生门禁立刻点名缺谁负责装：

```
$ backend/.venv/bin/python scripts/check_release_package_wiring.py

bundler leaves out: missing ['motion-catalog'], unexpected []

```

`frontend/scripts/audit-production-package.mjs` 同时变红。

**这条 RED 的形状值得记**：不是「我写了个测试断言零件在包里」，而是**在单一事实源里声明
一项资源，三个消费方自己发现没人负责它**。清单与实现之间的一致性由派生保证，不靠谁记得。

## 3. 一处产品取舍：装 134 个还是只装能用的

倾向**整棵树 134 个都装**，理由两条：

1. 发布树的聚合摘要锁在 `motion-catalog-release.v1.json` 里，是**整棵树一个数**。
   只装子集就得再锁一份子集摘要，等于第二份事实源；
2. PC-12 要给第二批 40 个混合型开槽，那时又得把它们装回去。

代价是 46 MB（dmg 现在 495 MB，约 +9%）。若日后确需瘦身，正确做法是让
`build_motion_catalog_release.py` 按 `motion-part-usability.v1.json` 的分批产出更小的发布树
并重算那一个聚合摘要，而不是在装配这一层挑文件。

## 4. 做法

单一事实源加第六项，**新开 `catalog` 类别**（理由见第 1 节），三个消费方自动跟进。

装配器走「改造现有的」而不是复制：`install_video_runtime` 拆出通用的
`install_packaged_resources`，`VIDEO_RUNTIME_RESOURCES` 与 `MOTION_CATALOG_RESOURCES`
都由 `resources_in_category()` 派生，共用同一个已经调试过的安装器（含失败时清除本次
已装树的回滚）。wiring 门禁的两处判定——「装配器该装什么」「谁构建这项资源」——
也从写死 `video` 改为按类别派生，后者变成 `CATEGORY_BUILDERS` 映射。

构建者新增 `stage_for_release()`：**暂存前先跑 `check_motion_catalog_release.verify_release`**。
暂存一棵未经校验的树，等于把「客户渲染的零件就是门禁检查过的零件」这个保证，
交给构建机磁盘上碰巧有什么。发布树是只读的，暂存副本改为可写，否则 bundler 装不进去。

顺带把按路径加载门禁模块的两处重复抽成 `load_gate()`。

## 6. 出包机的一条真实前置（实测踩到）

`stage_for_release` 按各自检出解析路径，所以**出包用的那棵树自己要有发布树**。
在 `wt/release` 里从头建时撞到：

```
download attempt 1/4 failed for https://fonts.gstatic.com/...figtree...woff2:
  [SSL: UNEXPECTED_EOF_WHILE_READING]
offline motion catalog build failed: download failed after 3 attempt(s)
```

`fonts.gstatic.com` 在国内不稳，主树那次是靠重试撞过去的。

**处置：从已建好的检出拷贝 `.local/offline-motion-deps`，再用目标树自己的门禁校验。**
这是可靠的——离线目录逐文件锁摘要，可信度来自校验而不是来自谁下载的：

```
$ backend/.venv/bin/python scripts/check_offline_motion_catalog.py
offline motion catalog is valid: 134 items, 411 files, 0 remote URLs
```

**这条要写进出包机文档**：一台新出包机若网络到不了 Google Fonts，只靠
`build_offline_motion_catalog.py` 会卡住，而错误信息指向的是下载而不是「换个办法拿」。

## 8.1 出包过程中抓到的一条真缺陷

装配好之后出包死在包内容审计：四个上游零件自带 `.wav` 音效（`soft-pulse`、
`ambient-tech`、`count-rise`、`route-chime`），撞上防「录屏、用户素材、凭据」进包的
媒体后缀黑名单。

**没有放宽媒体禁令，也没有给这棵树开目录级豁免**——那会变成「把文件放对文件夹就能
绕过」的清单，正是本项目在 `REVIEWED_` 清单与验收豁免清单上吃过亏的形状。改为：
媒体文件当且仅当**零件树自己的 manifest 记账过它**才放行。那棵树每个文件都有
SHA-256 在清单里、聚合摘要锁在契约里，所以放行的前提是「已经有东西声明过它」，
而不是「它在哪个目录」。段名、文件名禁令与内容标记扫描一律不变。

TDD 三条：清单记账过的 `.wav` 放行（先红）、塞一个清单没记的 `.wav` 仍拒、树外的
`.mp4` 仍拒。见 `frontend/tests/p9-05-release-bundle-audit.test.mjs`。

**顺带记一个当时未修的诊断缺陷**：`audit-release-bundle.mjs` 的二十多个拒绝点全部抛同一句
`Release bundle is rejected`，不说哪条规则、哪个文件。定位这次的问题只能靠栈帧行号加
逐条比对清单。按本项目对「响亮失败」的要求它不合格，当轮未顺手做；2026-07-30 已在
P9-05 审计边界补齐封闭原因与 bundle 相对路径，见 `docs/development/P9-05.md`。

### 8.4 本轮新识别的缺口：正式包自己没渲过零件

上面证到的是**包里有零件**与**缺了会被拒**。**没有证到的是：把这个正式包装上、
打开、走用户路径出一条用到零件的片子。**

PC-10 那次真出片用的是 debug 构建，资源由**同一个** `stage_for_release` 装配——
但 debug 的 `resource_dir()` 与 bundle 的 `Contents/Resources` 不是同一个位置。
布局若有差异，就会出现「debug 渲得出、正式包渲不出」，而这**正是本任务存在的
理由那一类事故**。用「同一个函数装的」去推断「所以正式包也行」，就是把推断当证据。

所以本任务仍是 `🔍 待验收`，剩两项：

1. 正式包装上后走用户路径出一条用零件的片子（macOS）；
2. Windows 包（见 8.2）。

### 8.5 macOS 剩余项的接线方案（2026-07-31 查明，下一段从这里接）

「正式包走用户路径出一条用零件的片子」的可自动化形态（正式公证包无 WebDriver、
无法自动驱动；辅助功能脚本无人值守撞 TCC 授权即卡死）：

- **构建形态**：bundle `.app`（`tauri build --bundles app` + 专用配置，仿
  `tauri.update-macos-package-e2e.conf.json` 的做法），资源装配走同一条
  release_assembly 链 → `Contents/Resources` 六项齐；与正式包的差异仅
  WebDriver 挂载 + 测试隐藏窗口（单一构建路径规则允许的第 1/2 类差异）。
  这补上的正是 T108 事故那一半：debug 平铺布局 ≠ bundle 布局，
  `resource_dir()` 的 canonicalize 只有真 bundle 才走到；
- **驱动**：新 `wdio.pc16-macos-package.conf.ts`（抄 `wdio.t36.conf.ts`，
  `appBinaryPath` 改从环境变量取 bundle 内二进制，同 `H822_MAC_APP_BINARY`
  机制），spec 直接复用 `e2e-tauri/motion-one-sentence.spec.ts`；
- **Runner**：`run_pc_16_macos_package_acceptance.py`，仿 `run_t36_acceptance.py`
  的前置（隔离 Postgres + Control Plane + 模型密钥从 `.local/secrets` 注入
  表单路径）+ 仿 `run_h8_22_macos_package_acceptance.py` 的 bundle 构建与
  二进制定位；验收断言留在 T36 同款终态（真 MP4 + ffprobe 读数 + 零件段）；
- **注意**：PC-14 接线后 authoring 请求带 `browserExecutable`，包内探针会真跑，
  一句话链路的耗时比 T36 当时更长，Mocha 预算按 t36 conf 的量级给；
- 完成后本任务 macOS 半闭环；Windows 包（§8.2）仍待 Windows 机。
