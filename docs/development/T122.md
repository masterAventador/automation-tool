执行：本机 macOS 开发 + `ssh winbox` 上的三轮真实测量。未在 Windows 上出包，未挂载任何 DMG。

## 1. 结论先行

任务给的用意是对的——**三处都在证明冻结产物自带依赖、不去借构建它的那台机器**，这条性质要留。但任务给的两个前提都被实测推翻，而且推翻的方向决定了修法：

**前提一（关于构建那一处）被证伪：`build_material_video_worker_candidate.py` 的最小环境不是拿来跑 PyInstaller 的。** PyInstaller 那次 `run(...)` 根本没传 `environment`（`scripts/build_material_video_worker_candidate.py:406`），继承的是完整开发者环境。`probe_environment()` 只出现在 503 / 531 行，跑的是**已经冻结出来的候选** `--probe` / `--probe-dependency`，外加 `run_im_02_acceptance.py:81` 同样跑冻结产物。所以不存在「构建需要工具链、测试不需要」的分歧——**三处意图一致**，详见 §3。

**前提二（关于 Windows 取值）被证伪，而且这条更要紧：`os.defpath` 的取值不是 Windows 上那个红的原因。** 实测证明，把 PATH 换成正确的 System32 取值，Windows 上**一行都不会变绿**。真正致命的是 `env={"PATH": ...}` 这个写法本身——它交给子进程的环境里**只有 PATH**，没有 `SystemRoot`，而 Winsock 通过 `%SystemRoot%` 解析它的服务提供程序目录。详见 §4。

**前提三（顺带）：POSIX 侧本来就没有缺陷。** 任务说 POSIX 上 `os.defpath` 是 `:/bin:/usr/bin`（带前导空项＝当前目录）。本机实测是 `/bin:/usr/bin`，没有空项。所以 POSIX 取值原样保留，迁移在 macOS 上是零行为变化——已由真实集成测试证明（§6）。

## 3. 三处意图是否一致：一致

三处（四个调用点）都是「**跑一个冻结好的可执行文件，把开发者环境拿掉**」。没有一处是在跑构建。核实方式是读调用链而不是读函数名——`probe_environment` 这个名字听起来像构建期探针，实际是产物探针。

所以共享一个取值不违反「不同的事实一份」——它就是同一个事实。

**不共享的部分也分清楚了**：`LANG=C.UTF-8` 和 `NO_PROXY=*` 是素材成片 Worker 自己的关切（字幕编码、别走环境里的代理），它们留在 `probe_environment()` 里叠加，没有被塞进共享值。

## 4. Windows 取值与依据

### 4.1 实测矩阵（winbox，`C:\WINDOWS`，CPython 3.14.0）

跑的是**真实 PyInstaller `--onedir` 产物**（临时 venv 装 PyInstaller、现冻一个开 socket 的探针）。用 `python.exe` 直接跑一遍得到逐格相同的结果。

| PATH | SystemRoot | 结果 |
|---|---|---|
| `.;C:\bin`（`os.defpath`） | 缺 | **红** `OSError: [WinError 10106]` |
| `.;C:\bin`（`os.defpath`） | 有 | 绿 |
| `""`（空） | 有 | 绿 |
| `%SystemRoot%\System32;%SystemRoot%;...\Wbem` | 缺 | **红** `OSError: [WinError 10106]` |
| `%SystemRoot%\System32;%SystemRoot%;...\Wbem` | 有 | 绿 |
| 继承完整环境 | 有 | 绿 |

**先读第四行再读第一行。** 取值正确、SystemRoot 缺失，照样红，报的是同一个错。10106 是 `WSAEPROVIDERFAILEDINIT`：Winsock 要通过 `%SystemRoot%` 找它的提供程序目录。

顺带测到的两件事：`C:\bin` 在 winbox 上 `os.path.isdir` 为 `False`（确实不存在）；不带 `TEMP`/`TMP` 时 `tempfile.gettempdir()` 返回 `C:\WINDOWS\Temp`，探针会往系统目录写东西。

### 4.2 所以修法必须是环境而不是 PATH 字符串

`frozen_artifact_environment()` 返回的是 dict 而不是一个 PATH 串，因为在 Windows 上决定产物能不能跑起来的那一项根本不是 PATH。Windows 分支：

```
PATH       = %SystemRoot%\System32;%SystemRoot%;%SystemRoot%\System32\Wbem
SystemRoot = %SystemRoot%
WINDIR     = %SystemRoot%
TEMP/TMP   = 有就带上
```

两者都缺时 **raise 而不是猜** `C:\Windows`——猜错的机器上会再生成一个长得像产品缺陷的失败。

### 4.3 为什么是 System32 三件套而不是空 PATH

实测空 PATH 也绿（矩阵第三行），而且更小。仍然选三件套：

1. 要画的界线是「**没有开发者装的东西**」，不是「什么都没有」。这三个目录是 Windows 自带的，里面不可能出现构建机上的 Python、uv、node、MSVC；
2. `run_p9_07_acceptance.py` 已经在同一台机器上跑着这个一模一样的取值。另起一个答案会让同一个问题在仓库里有两个；
3. 空 PATH 会让任何合理地按名字找系统自带工具的子进程静默失败，而那不是这条边界要拦的东西。

### 4.4 POSIX 取值

原样保留 `/bin:/usr/bin`（实测的 `os.defpath` 值），只是从「继承一个在 Windows 上是垃圾的常量」变成写死在模块里。POSIX 侧本次没有行为变化。
