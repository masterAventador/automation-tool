## 结论

原实现按 `debug_assertions` 在 AppData 与 Tauri Resources 之间选择执行器包，违反单一构建
路径规则。原提交把所有构建统一到
`resource_dir()/local-executor/package`，桌面验收也把测试用签名执行器装到同一资源布局。

## RED

- `must stage the signed Executor in the debug App resource root`

这两条分别证明产品查找路径存在构建模式分叉，以及验收驱动还在向旧的 AppData 位置装包。
原始终端 transcript 没有随提交入仓，本文件不补造更精确的命令输出。

## 失败矩阵

| 场景 | 证据与结果 |
| --- | --- |
| debug/release 构建路径漂移 | 单路径 Rust 静态门禁拒绝 |
| 驱动继续向 AppData 装包 | 验收装配门禁拒绝 |
| Resources 中缺包或包损坏 | 仍由既有签名执行器准备和启动门禁响亮失败 |
| 状态目录与程序包混放 | AppData 只保留状态，程序包只从 Resources 解析 |
| 正式签名安装包资源遗漏 | 不由本提交单独证明；归发布包资源审计与安装包验收 |

## 真实边界

本任务不是纯文本检查：后续隐藏 Tauri App 的视频驱动确实从 debug App 的生产资源布局启动了
签名执行器。不过它不能替代 macOS/Windows 正式签名安装包的资源复验，因此后者不在本文件中
冒充已完成。

也没有把执行器写回主工作树。
