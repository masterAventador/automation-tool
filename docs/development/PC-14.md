## 0. 判据被实测改写了

路线图原本写：替换后在 Chromium 里实测每个槽，`scrollWidth>clientWidth`、
`scrollHeight>clientHeight`，超了就是硬失败。

**实测（PC-17 的探针，包内 Chromium，seek 到末帧）：48 个槽里 14 个在自己的原始文案下
就纵向溢出。** 那是设计——遮罩式揭示本来就纵向裁切文字。

按原判据，一个字都没换之前就会拒掉三分之一的目录。

**所以判据改为「比原文多溢出了吗」**：`slot_budget.require_within_budget` 拿这次渲染
量到的溢出状态，对 `motion-part-slot-budget.v1.json` 里记下的基线比对，只有**新引入的**
溢出才算失败。

## 1. 拒绝必须说得出还剩多少地方

```
copy overflows slot 13 horizontally; the slot is 366px wide at 58px type,
and the part's own copy fits
```

只说「太长了」的拒绝，让模型去猜该短多少。带上容器宽度与字号，它才知道往哪个方向改。

## 2. 另一条被实测推翻的方法

PC-05 里记过：路线图把 `lt-bold-block` 举为「`font-size` 写死 + `overflow: hidden`，
长了会被裁掉看不见」的典型，而真渲染里容器跟着内容长开了，没有裁切。

**读样式表推断哪个零件会裁切这个方法本身不成立**，判据只能是在真渲染里量。
本任务的实现即按此建立。

## 4.6 探针接入 agent + ≤2 轮修复循环落地（2026-07-30）

先红后绿（10 条新单测，先跑确认 `slot_probe` 未知参数报 TypeError）：

1. **探针注入**：`MotionAuthoringAgent(slot_probe=...)`，`None`=不测（保持全部旧调用方行为），
   非可调用拒绝；
2. **同会话测量**（`_require_copy_fits_measured`）：装配后对每个「有冻结预算且本片写了文案」
   的零件段，用冻结原文回填同一批槽写 `catalog-baseline/` 基线副本（原始文档没有
   `data-motion-slot` 标记，必须经工作副本写入器打标），基线与替换两份文档**一次探针调用**
   送测——同一浏览器会话，驱动偏差自消；只判本片填过的槽；量不到、探针崩溃、读数条数不符
   一律 `slot overflow probe failed to measure` 关死，不许当通过；
3. **修复循环**：`author()` 里 compose→lint/check→snapshot→segments 包两轮。超槽时把
   `require_no_new_overflow` 攒齐的全部超槽详情（槽号/宽度/字号）回抛模型，只收
   `{"storyboard": ...}`，过 `require_repair_changed_only_copy` 后重写落盘重跑；
   第二轮仍超 → `copy overflows its slot after the repair round`。静态门禁失败仍然无修复轮
   （模板是本机确定性输出，模型看不见也修不了）；
4. **词表同步**：4 条新拒绝语进 `_AGENT_FIXED_REJECTION_BODIES` 与 refusal 契约
   （129 个 fixedReasons）；探针失败与接线缺陷归 `executor_defect`（不是用户句子的错，
   不许答成 refusal），协议违规（`repair response must carry the storyboard alone`）与
   修复后仍超按 refusal 处理（与 `first_response` 同族）；
5. `SlotProbeUnmeasured` 从 `SlotProbeRejected` 分出：溢出可修（值一轮模型），测量缺失
   不可修（花一轮模型让它改一段没问题的文案是答非所问）。

## 4.7 entry 接 browserExecutable + 真探针模块（2026-07-30）

先红（3 条 entry 用例 + 探针模块 ModuleNotFound）后绿：

1. **请求可选字段 `browserExecutable`**：缺失=不测（老 App 保持今天的行为，绝不当
   「量过且合格」）；空/非字符串 → `browser_executable_missing`；相对路径 →
   `browser_executable_not_absolute`。两个 token 进 refusal 契约（131 fixedReasons），
   归 `app_request_invalid`（App 拼错请求不是用户句子的错——注意 `catalog_root_*`
   是历史遗留才留在 refusal 里，新字段跟 `workspace_*` 的正确先例走）；
2. **真探针 `slot_probe_browser.PackagedSlotProbe`**：走 `BrowserRuntime`（执行器唯一
   Playwright 封装）+ App 授权的可执行路径（EB-07 语义），headless 强制；私有 Profile
   建在工作区 `slot-probe-profile/` 下随工作区删除；每份文档 file:// 加载 → 400ms →
   seek 全部 `window.__timelines` 到末帧（与预算探针同源的量法）→ 200ms →
   `SLOT_PROBE_JS` 读数；JS 字符串键归一为 int 键 bool 对。4 条单测含
   「页面失败也要停浏览器与驱动」；
3. entry 构造 agent 时按字段有无注入探针，用记录型假 agent 证明两种走向
   （有字段 → 可调用探针；无字段 → None）。

GREEN：`pytest backend/tests/unit`（3385 passed）、`scripts/test_motion_authoring_agent.py`
（102 passed）。

**续点（下一段从这里接）**：

- `author()` 把「storyboard 落盘 → compose → lint/check → snapshot →
  _segments_for」包进最多两轮的循环；`SlotProbeRejected` 时把超槽详情
  （槽号/宽度/字号来自 `require_no_new_overflow` 的消息）作为修复消息发给
  模型，只收 storyboard，过 `require_repair_changed_only_copy` 后重跑；
  第二轮仍超 → `_reject("copy overflows its slot after the repair round")`
  （记得同步词表，门禁会抓）；
- 探针注入：`MotionAuthoringAgent(slot_probe=...)`；探测时机在
  `_segments_for` 的 `assemble_film` 之后，对每个有 slot_budgets 且
  copy 非空的 part 段：基线文档=用冻结原文回填同一批槽（原文档**没有**
  data-motion-slot 标记，这是当天想明白的关键），
  `write_part_working_copy(directory="catalog-baseline", copy={i: slot.original})`；
  同一会话量两份；只对有冻结预算的槽执行判定（预算表 18 零件/48 槽，
  无预算的槽维持现状不测，记入证据）；
- 真探针实现：executor 的 browser_runtime Playwright + 包内 Chromium，
  entry.py 构造 agent 时接线；单测用假探针（现有 catalog_root 用例需补
  假探针参数）；
- **接线的第一决策点（2026-07-30 查明）**：执行器侧浏览器可执行路径由
  Rust 按命令授权传入（EB-07 语义，`browser_authority.py` 只存 Rust 授权
  的那一个），授权书（authoring）请求形状里没有它。真探针接线要么给
  authoring 请求加 `browserExecutable` 字段（Rust 调用方 → entry 校验 →
  契约三处同步），要么把探测挪回 App 侧 Rust（违背设计点 1「修复轮闭合在
  Python author() 内」）。倾向前者；找 Rust 侧发 authoring 文档的调用点
  从那里接。
- 真实验收：故意超长文案 → 拒绝并重来后成片正常（步骤 7）。
