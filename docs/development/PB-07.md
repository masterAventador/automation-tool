## 关键设计判断

### 一、发布机制不进 DTO

B站走官方接口、抖音开可见浏览器，这个区别决定**执行器做什么**，但不该决定
**App 渲染什么**——否则发布页会悄悄变成两个页面共用一个名字。契约里
`projectsMechanismToTheApp` 为 `false`，Rust 快照序列化与 TS Zod 边界两侧都有测试
断言投影里不出现 `browser_use` / `playwright` / `chromium` / `official_api`；
Zod 用 `.strict()` 把多余字段判为契约变更而不是默默吸收。

### 二、没配凭据的平台不隐藏也不报错

挂在列表里显示“待配置”，只是不给发起按钮。让整个发布模块因为一个平台没配好就起不来，
等于操作员连**已经能用**的那个平台也发不了。

### 三、派发之后不提供取消

本地已经没有可取消的东西。报一个“已取消”等于告诉操作员“没发出去”，而它可能已经
发出去了。结果不明确时同样不提供“重新发布”，只提示到平台自行核对。

### 四、租约语义在发布与登录上不同

登录到 `healthy` 就把浏览器还回去；发布前流程**就绪时必须继续持有**——那个填好的
表单页要等到操作员确认时还在。除就绪外的任何结果都释放，否则一个永远不会被兑现的
租约会把运营档案锁到 App 重启。

### 五、审计记录决策，不记录内容

标题与简介是内容，把它们复制进一份不断增长的记录只会扩大它们的存在范围。审计保留
确认标识，因为那正是把一次批准和它授权的那一次点击绑在一起的东西。TS 侧对审计条目
同样用 `.strict()`，多带一个 `title` 字段会被拒。

### 六、跨语言证明做了真正的钉死

Rust 命令帧的测试最初只用**我自己抄过来的**域常量重算 HMAC，这只能证明 Rust 自洽。
改为先用 Python 认证器对固定密钥算出实际证明值再钉进 Rust 测试，形成
「Rust 输出 == 独立重算 == Python 实际输出」三段断言。任何一侧改域或字段顺序都会在
测试里红，而不是变成用户机器上一条被拒的命令。

## 开发中修掉的自身缺陷

**一、`and_then` 串接租约释放跳过了错误路径**，导致命令失败时反而不释放。更要紧的是
租约**获取失败**也会走到释放逻辑，而获取失败的常见原因正是**别人正持有它**，释放等于
伸手去放别人的租约。改为把获取失败与执行失败彻底分开。

**二、效应体里同步 `setState`** 会触发级联渲染；改为在 `await` 之后写状态，并顺带补上
原本缺失的取消标志——组件卸载后到达的回答本来仍会写状态。

**三、执行器管理层三处 `execute_*_command` 是同一段三十行的三份拷贝**，本次再加两个会
变成第五份，先抽成共用的 `execute_command` 再接入。

## 失败矩阵

| 场景 | 结果 | 覆盖 |
| --- | --- | --- |
| 平台未配置凭据 | 列出并标“待配置”，模块照常可用 | Rust + 前端 |
| 平台未登录 | 标“待登录”，不给发起按钮 | Rust + 前端 |
| 发起两个支持平台之外的平台 | `UnknownPlatform` | Rust |
| 平台不可发布时发起 | `NotPublishable`，阶段不变 | Rust |
| 没有待确认却点确认 | `NoApprovalPending`，阶段不变 | Rust |
| 派发后取消 | `AlreadyDispatched`，界面不给取消按钮 | Rust + 前端 |
| 结果不明确 | 不可重试，提示自行核对 | Rust + 前端 |
| 确认文本不可读 / 确认标识非规范 | 到不了 App 就被拒 | Rust + 前端 |
| 快照泄漏发布机制 | 两侧都拒 | Rust + 前端 |
| 审计出现未登记步骤或夹带内容 | 拒 | 前端 |
| 桥读不出来 | 页面保持可用并可重试，不误报重复提交 | 前端 |
| 命令帧标识非规范 / 文案含控制字符 | 写入前即拒，不留半截帧 | Rust |
| 用别的命令族流程版本回包 | 拒 | Rust |
| 只有就绪的发布前流程保持运营档案 | 其余一律释放 | Rust |

## 正常用户路径验收

分两层，都已跑通。

**Playwright UI Harness（4 条，`e2e/ui-harness.spec.ts`）** 走完整用户路径：从左侧
「作品发布」进入 → 读到两个平台与各自适用性 → 对已就绪平台发起 → 临界点读到目标账号、
视频与文案 → 确认后看到终态。另覆盖结果不明确时不提供重新发布、确认前取消、以及全程
不出现上游技术名。这一层证明的是 **React 业务投影**，用的是受控测试 Adapter。

**真实 Tauri App（5 条，`e2e-tauri/publishing.spec.ts`）** 证明下面几层都证明不了的
那一件事：**操作员看到的平台适用性是桥自己去读会话得出的，不是页面自己声称的**。
下面每一层都注入替身，而替身让它报什么它就报什么；只有真实 App 经真实 WebView、
真实 IPC 打到真实 Rust 命令，才能确认这条判断确实在桥里。同时覆盖三条拒绝路径
（平台不可用、平台不受支持、无人等待的批准）与桥投影零机制泄漏。

**这一层没有覆盖的一条，如实记下**：在真实 App 里点击左侧导航进入发布页。该 debug 构建
停在启动环境门（“桌面运行环境需要处理”），因为本机没有暂存的执行器包与内置浏览器，
工作台根本不会挂载。导航路径由 UI Harness 覆盖；要在真实 App 里断言它，需要备好完整
启动环境。这条边界同时写在 spec 的文件注释里。

**两层都不发布任何东西。** 本机没有平台账号，链路走到"需要真实账号"那一步为止，
最后一步归 PB-08。

## 真实边界

1. **平台服务层三个新方法的管道仍未被测试覆盖**。它们需要一个真正跑起来的执行器进程，
   而桌面验收在未登录状态下走不到那里。因此把其中真正的判断抽成具名的
   `publish_keeps_the_browser` 单独断言，**管道部分至今没有验证过**，要等 PB-08 的真实
   账号链路。
2. **素材来源未接**：发起一次发布需要 Artifact 路径、摘要、标题与简介。发布页接收一个
   已选定的视频（`selectedVideo`），**没有选定视频时不显示发布按钮**；但从视频制作产物
   到这个选定视频的接线尚未建立，真实 App 里目前没有东西会填它。
3. **真实 App 的 UI 导航未验证**：见「正常用户路径验收」最后一段。
4. **没有真实平台验收**：B站无凭据、抖音无真实账号，全链路真实投稿归 PB-08。
5. **审计只在内存**：`PublishWorkspace` 是进程内状态，App 重启后审计清空。持久化审计
   属于产品审计需求，本任务没有做，也没有假装做了。
6. **`approve_publish` 用确认标识兼作发布任务标识**。发布页把 `publishJobId` 填成
   `confirmationId`，因为页面手里没有单独的任务标识。执行器按内容哈希判定至多一次，
   所以不影响正确性，但这是接线未完成留下的将就，随素材来源接线一并修正。
