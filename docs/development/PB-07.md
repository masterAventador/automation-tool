## 关键设计判断

### 一、发布机制不进 DTO

B站走官方接口、抖音开可见浏览器，这个区别决定**执行器做什么**，但不该决定
**App 渲染什么**——否则发布页会悄悄变成两个页面共用一个名字。契约里
`projectsMechanismToTheApp` 为 `false`，Rust 快照序列化与 TS Zod 边界两侧都有测试
断言投影里不出现 `browser_use` / `playwright` / `chromium` / `official_api`；
Zod 用 `.strict()` 把多余字段判为契约变更而不是默默吸收。

### 二、没配凭据的平台不隐藏也不报错

挂在列表里显示“待配置”，只是不给发起按钮。让整个发布模块因为一个平台没配好就起不来，
等于操作员连**已经能用**的那个平台也发不了。

### 三、派发之后不提供取消

本地已经没有可取消的东西。报一个“已取消”等于告诉操作员“没发出去”，而它可能已经
发出去了。结果不明确时同样不提供“重新发布”，只提示到平台自行核对。

### 四、租约语义在发布与登录上不同

登录到 `healthy` 就把浏览器还回去；发布前流程**就绪时必须继续持有**——那个填好的
表单页要等到操作员确认时还在。除就绪外的任何结果都释放，否则一个永远不会被兑现的
租约会把运营档案锁到 App 重启。

### 五、审计记录决策，不记录内容

标题与简介是内容，把它们复制进一份不断增长的记录只会扩大它们的存在范围。审计保留
确认标识，因为那正是把一次批准和它授权的那一次点击绑在一起的东西。TS 侧对审计条目
同样用 `.strict()`，多带一个 `title` 字段会被拒。

### 六、跨语言证明做了真正的钉死

Rust 命令帧的测试最初只用**我自己抄过来的**域常量重算 HMAC，这只能证明 Rust 自洽。
改为先用 Python 认证器对固定密钥算出实际证明值再钉进 Rust 测试，形成
「Rust 输出 == 独立重算 == Python 实际输出」三段断言。任何一侧改域或字段顺序都会在
测试里红，而不是变成用户机器上一条被拒的命令。

## 开发中修掉的自身缺陷

**一、`and_then` 串接租约释放跳过了错误路径**，导致命令失败时反而不释放。更要紧的是
租约**获取失败**也会走到释放逻辑，而获取失败的常见原因正是**别人正持有它**，释放等于
伸手去放别人的租约。改为把获取失败与执行失败彻底分开。

**二、效应体里同步 `setState`** 会触发级联渲染；改为在 `await` 之后写状态，并顺带补上
原本缺失的取消标志——组件卸载后到达的回答本来仍会写状态。

**三、执行器管理层三处 `execute_*_command` 是同一段三十行的三份拷贝**，本次再加两个会
变成第五份，先抽成共用的 `execute_command` 再接入。

## 真实边界

1. **平台服务层三个新方法的管道仍未被测试覆盖**。它们需要一个真正跑起来的执行器进程，
   而桌面验收在未登录状态下走不到那里。因此把其中真正的判断抽成具名的
   `publish_keeps_the_browser` 单独断言，**管道部分至今没有验证过**，要等 PB-08 的真实
   账号链路。
2. **素材来源未接**：发起一次发布需要 Artifact 路径、摘要、标题与简介。发布页接收一个
   已选定的视频（`selectedVideo`），**没有选定视频时不显示发布按钮**；但从视频制作产物
   到这个选定视频的接线尚未建立，真实 App 里目前没有东西会填它。
3. **真实 App 的 UI 导航未验证**：见「正常用户路径验收」最后一段。
4. **没有真实平台验收**：B站无凭据、抖音无真实账号，全链路真实投稿归 PB-08。
5. **审计只在内存**：`PublishWorkspace` 是进程内状态，App 重启后审计清空。持久化审计
   属于产品审计需求，本任务没有做，也没有假装做了。
6. **`approve_publish` 用确认标识兼作发布任务标识**。发布页把 `publishJobId` 填成
   `confirmationId`，因为页面手里没有单独的任务标识。执行器按内容哈希判定至多一次，
   所以不影响正确性，但这是接线未完成留下的将就，随素材来源接线一并修正。

## 补做：视频来源接线与三条同族缺陷（2026-07-26）

作为 PB-07 剩余范围补做，不新开任务 ID。完整记录见
`docs/development/FIX-publish-video-source-wiring.md`，这里只留结论与证据。

### 修掉的四条

1. **成片载荷没有扩展名，执行器一定会拒。** 成片存为 `<artifacts>/<id>/payload`，无后缀；
   执行器要求恰好一个 `.mp4`/`.mov`。**接线全做完点发布仍会每次失败，而 Rust 单测、
   UI Harness、Python 单测三层都发现不了**——每层都只面对自己的替身。修法是在 App 私有
   目录里暂存一份 `<artifactId>.mp4` 副本交给执行器，不放宽执行器任何现有判据。
   方案文档推荐的**硬链接方案实测不成立**：执行器要求 `st_nlink == 1`，硬链接会让原件和
   链接双双失格。
2. **平台分派硬编码走抖音。** `platform` 原来只决定「能不能发」，之后一路取抖音运营
   Profile、发 `PreflightDouyinPublish`。把 B站开关翻成 `true`，点「发布到B站」就会打开
   抖音运营档案跑抖音发布流程。改为 `PublishPlatform::route()` 穷举分派，B站明确返回
   「尚未接入」且**不碰浏览器与运营档案**。未翻 `PublishWorkspace::new(false)`。
3. **契约 `artifactPath` → `artifactId`。** 页面不再持有本机绝对路径，路径由 Rust 侧的
   工作区 store 解析，可发布集合收敛为 `role="rendered_video"` 且
   `media_type="video/mp4"` 的已登记 Artifact。
4. **撒谎文案。** 「配置后即可使用」承诺了全 App 做不到的事，改为「该平台的发布通道还在
   接入中」，并加测试断言旧措辞不再出现。

顺带修掉本文件「真实边界」第 6 条：**`publishJobId` 不再复用 `confirmationId`**。发布
任务标识由桥在 `begin_publish` 生成并持有，`approve_publish` 从状态取，页面不再传。

### 租约并发拒绝路径（2026-08-04 补齐）

`under_profile_lease` 的注释写着「第二个控制者要别的 Profile 时应被拒绝而不是被服务」，
但此前**没有任何测试走过那条 `return`**——已有覆盖全部落在「拿得到租约」的顺路径上。

这条分支有两件事必须同时成立，缺一件就等于把一次发布打进别人的页面：

1. 换一个 Profile 的请求被拒；
2. **这次拒绝不能碰已持有的那份租约**。`return` 走在释放逻辑之前正是为此，而这一点
   用「返回了错误」是断言不出来的，必须去看租约还在不在、还能不能用。

新增 `a_second_controller_asking_for_another_profile_is_refused_without_touching_the_held_lease`。

**放在 `src/executor_platform.rs` 的 in-src 测试模块而不是 `tests/`**：判据是
`platform_profile_lease` 这个私有字段——第 2 条只能通过它核对，集成测试看不见。
项目已有 24 个源文件用 in-src `#[cfg(test)]`，不是为本条新开的做法。

**用真实执行器进程**：租约只有在命令**成功**且状态要求留住浏览器时才会存活，
任何替身在这里都等于自己编造前提。桩由**开发签名者**签名（其公钥即
`DEVELOPMENT_EXECUTOR_VERIFYING_KEY`），所以包必须真的通过验签才起得来；
桩对预检以外、派发以外的任何命令直接 `raise`，被拒的那条请求真走到执行器就会当场看见。

四段断言，各自对应一条判据：

| 断言 | 它防的事 |
| --- | --- |
| 换 Profile → `ConfigurationInvalid` | 两个控制者同时拥有那一个可见运营浏览器 |
| 拒绝后租约仍是原来那个 id 与目录 | 失败路径伸手去放别人的租约 |
| 持有者拿同一 Profile 回来仍被服务 | 「一律拒绝」——那样前两条也会绿 |
| 派发拿到 `publish_verified` 且租约归还 | 拒绝把这条链路变成一把只能看的锁 |

**三条变异各自被不同断言抓住**（每条都实跑确认红）：

```text
✅ 被抓住  去掉拒绝、任何 Profile 都服务   → 第 1 条（桩 raise，收到 ProcessUnavailable）
✅ 被抓住  照样拒绝、但顺手释放别人的租约   → 第 2 条
✅ 被抓住  一律拒绝、连持有者自己也拒       → 第 3 条
```

**顺带修掉一处会让后来者踩的坑**：本模块的 `TemporaryAppData` 用未解析的
`std::env::temp_dir()`。Profile 目录逐级用 `O_NOFOLLOW` 打开，而 macOS 的 `$TMPDIR`
挂在 `/var` 这个符号链接下，未解析时 ELOOP，报出来的是 `UnsafeDirectory` ——
看着像权限问题，实际是路径没解析。`tests/browser_profiles.rs` 早就在 canonicalize，
本模块此前没用到 Profile 所以一直没暴露。

`cargo fmt --check` 干净（顺带补掉上一节遗留的一处格式）。
