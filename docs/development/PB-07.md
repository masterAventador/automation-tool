## 任务

把两条已经在后端跑通、但用户完全看不见的发布链路接到 App 上：

- 发布页**只展示 B站与抖音**两个平台；
- 平台适用性、授权、进度、审批、取消、失败、结果与审计走**同一套 DTO**，
  B站走官方接口、抖音走内置浏览器这件事不体现为两套界面模型；

- B站未配置凭据时显示可理解的**“待配置”**，而不是让整个发布模块启动失败。

## 起点事实

开工前核对过当前实际状态，避免按想象施工：

- PB-05/PB-06 只做到 **Python 执行器层**。`douyin.publish.preflight`、
  `douyin.publish.dispatch`、`douyin.publish.release` 三个本地命令族已经能跑，且执行器
  通过 `latest_receipt()` / `latest_approval()` / `latest_release()` 三个观察点暴露结果。

  `OpenDouyinLogin` / `RecheckDouyinLogin` / `CompleteDouyinLogout`，没有任何发布命令，
  也没有发布用的认证证明（发布帧的证明绑定的字段比登录帧多）。
- **前端一片空白**：`frontend/src/features/` 下没有发布模块，
  `frontend/src/platform/tauri/` 下没有发布网关。
- B站侧 PB-01～PB-04 已完成实现与契约，但真实凭据未提供，状态是“代码完成 / 待凭据验收”。
- `contracts/quality/publishing-capabilities.v1.json` 已经定义了平台与机制矩阵
  （bilibili=official_api、douyin=browser_use，其余三家 deferred/disabled），
  本任务的平台适用性直接以它为准，不另立一套。
