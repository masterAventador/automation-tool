## 0. 一句话结论

`docs/product-completion-roadmap.md` 现在有门禁了。两个台账共用的判定抽进
`scripts/roadmap_ledger.py`，专项门禁改为调用它、输出逐字不变。

## 1. 为什么要有

这份台账是手工维护的，而它暴露在一个**已经发生过**的失败下：另一条台账上曾有三个任务
实际早已完成——服务端数据、磁盘文件、真实出片都在——而表里仍写着「等用户做」，然后被
逐字复述给产品负责人当成事实。**没人能核对的台账比没有台账更糟，因为它会被相信。**

## 2. RED，抓到的是两个真缺陷不是假想

```
$ python3 scripts/test_product_completion_roadmap.py
AssertionError: scripts/check_product_completion_roadmap.py is missing
```

门禁写好后第一次运行，报出的是**当时真实存在的坏数据**：

```
$ python3 scripts/check_product_completion_roadmap.py
product completion ledger check failed: task row must have 5 fields, found 2
— a cell carrying a raw newline stops being a table row: | PC-07 | TTS 接入与逐段语音时长测量 | …
```

**PC-07 和 PC-13 两行的单元格里有裸换行**，markdown 已经不再把它们当表格行渲染，
而在 diff 里看起来完全正常。PC-07 是我写的，PC-13 是字体工作线写的，两处都没人察觉。
修法是把长说明搬到表下的「PC-07 补充」「PC-13 补充」两节，单元格只留一句。

修完之后门禁又报了第二条真的：

```
product completion ledger check failed: PC-13 evidence does not state the ledger status '🚧 实现中'
```

`docs/development/PC-13.md` 的状态行还写着「查证完成，待产品负责人拍板覆盖档位」——
写的时候准确，但产品负责人已经拍板，它过期了。**台账与证据互相说不同的话，正是这道门禁的靶心。**

第三条是我自己的判据太死：证据文件用了带编号的 `## 12. 文档`，而我要求顶格 `## 文档`。
要求本来是「有文档小节让读者知道这次还改了什么」，不是「按某种方式编号」，所以放宽正则而不是
去改那份文件。

## 4. 复用，而不是复制第二份

台账行的交付要求写的是「复用专项台账门禁的判定逻辑而不是复制一份」。做法是抽
`scripts/roadmap_ledger.py`，放进去的只有**与是哪个台账无关**的五条：

- 编号唯一；
- 依赖指向存在的任务，且不自依赖；
- 最多一个 `🧪 RED` / `🚧 实现中`；
- 状态过了 `⬜ 未开始` 的任务恰好一个可读的证据文件；
- 台账里不堆完成记录（一旦开始堆，就再没人能从表里读出还剩多少，而那是这张表存在的唯一理由）。

**留在各自门禁里的是真正不同的部分**：专项台账有 87 项的闭合清单（编号增减是漂移），
产品补全线的编号随发现新缺口而增长（增减是正常）；两边的证据文件格式也不是同一种文档，
不该被强行统一。

专项门禁改为调用共享模块后，**输出与改动前逐字一致**：

```
$ diff <(改前输出) <(改后输出)
输出完全一致
```

它自带的 self-test（重复任务、汇总漂移、两个激活任务、内联证据、旧台账复制、证据缺字段）
在改动后仍全部通过——那些 `expect_failure` 现在跑的就是共享模块里的判定。

## 5. 失败矩阵

`test_product_completion_roadmap.py` 六条，全部实测判红：

| 篡改 | 期望 |
| --- | --- |
| 重复的任务编号 | 红 |
| 两个任务同时处于激活状态 | 红 |
| 某行单元格被拆成两行（裸换行） | 红 |
| 依赖指向不存在的 `PC-99` | 红 |
| 台账里追加 `## RED` 完成记录 | 红 |
| 任务标成 `✅ 已完成` 但没有证据文件 | 红 |

门禁自身另有 self-test（重复任务、内联完成记录、拆行），只在校验真实台账时运行。

## 6. 有意不做的事

- **不校验固定清单。** 这条线随发现新缺口而增长，明天冒出 `PC-15` 是正常而不是漂移。
  闭合清单属于专项台账，那 87 项是一开始就划定的；
- **不重复判定证据深度。** 「用户可操作的任务必须有可外部核对的终态」已经由
  `scripts/check_acceptance_evidence_depth.py` 守着同一批文件，在这里再判一次会产生
  两个会各自漂移的「证据够不够」定义。这里只要求四样最低限度：日期行、与台账一致的状态、
  文档小节、64 KiB 上限。
