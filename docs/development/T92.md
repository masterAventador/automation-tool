# T92 — 把动效 HTML 从模型输出挪回本机模板

> 日期：2026-07-27
> 分支：`motion-template`（基点 `6fd7d87`）
> 状态：**已完成**。真实模型 + 真实内置 Chromium 端到端验收通过。

---

## 0. 一句话结论

模型不再写 HTML，只填结构化字段；画面由 `composition_template.py` 在本机绘制。
**同一时段背靠背实测：编排的模型耗时中位数 87.0 秒 → 36.9 秒（2.4 倍），
应答字节中位数 7,745 B → 2,429 B（3.2 倍），一次通过率 9/11 → 10/10。**

但下面这条必须先说清楚，因为它和任务书的预期不一致：

**没有降到「几十秒」量级的下限，也不可能降到。** T83 的「耗时 ∝ 模型写的字节数、
速率恒定 4.5 KB/s」是**线路字节**（含 SSE 封装与流式推理内容）的规律，不是正文字节的。
正文砍掉 3.2 倍，耗时只快 2.4 倍——差额是**推理时间，它不随正文缩短**。
实测模板版正文吐字速率只有 59 B/s（基线 134 B/s），说明这 36 秒里大部分时间模型
根本没在吐正文。**这一段是模型侧的地板，产品这边没有杠杆。**

## 1. 先查清楚模型实际都产出了什么（不是只看提示词）

唯一一份**真实成片**的合成还在用户正式 App 的数据目录里：

```
~/Library/Application Support/com.aventador.automationtool/profiles/demo-xuanbai/
  video-workspaces-v1/jobs/448e46df-.../work/composition.html   （10,182 B）
```

（只读复制到临时目录分析，**没有改动用户数据**。）

逐段拆开这份 5 段 12 秒的「RAGFlow 原理讲解」，模型真正用到的视觉词汇只有四类：

| 模型写的结构 | 出现处 |
| --- | --- |
| 大标题 + 副标题居中 | beat-1 开场、beat-5 收尾 |
| 角标 + 小标题 + 说明段 + **一排装饰件** | beat-2/3/4 |
| 装饰件形态一：emoji 图标格（📄 PDF / 📊 Excel …） | beat-2 |
| 装饰件形态二：等距圆点阵（向量化示意） | beat-3 |
| 装饰件形态三：方块 + 箭头串（用户提问 → 语义检索 → LLM 生成） | beat-4 |
| 动画：`tl.from` 位移/透明度 + `scale` 弹入 + 子元素 `stagger` | 全片 |

**两个决定设计的发现：**

1. **画面上的文案只存在于 `composition_html` 里。** `SCRIPT.json` 的 beats 是
   「第一步：深度文档解析」这种一句话大纲，`STORYBOARD.json` 的 `purpose` 是
   「讲解文档解析阶段：PDF/Word/表格等多格式深度解析」这种**导演备注**。
   两者都不是能直接上屏的成片文案。所以**只把 HTML 删掉、不加字段**，成片会退化成
   五张只有大纲短句的卡片——那是真的砍掉了表达力，不是「模板化」。
   → 因此分镜必须新增 `layout / headline / body / items` 四个字段承接屏幕文案。

2. **`catalog_parts` 完全没有进画面。** 那份真实合成里模型挑的 15 个零件
   （`caption-kinetic-slam`、`flowchart`、`data-chart` …）**一个都没有出现在 HTML 里**。
   与 `docs/development/FIX-motion-parts-selection-wiring.md` 的结论一致：今天没有任何
   代码能把零件 id 变成像素。本任务**保留**该字段（它的产品语义由那条 FIX 任务决定，
   不在本任务的授权内），但它是下一个可摘的果子，见 §7。

## 2. 模板的参数面，以及**放弃了什么表达力**

`backend/src/automation_tool/executor/motion_authoring/composition_template.py`
发布四种版式，覆盖上面归纳出的全部结构：

| layout | headline | body | items |
| --- | --- | --- | --- |
| `title` | 大标题（42px 居中） | 副标题 | 忽略 |
| `points` | 小标题 | 说明段 | 0~6 个并列要点小卡片 |
| `flow` | 小标题 | 说明段 | 0~6 个用箭头串起来的流程节点 |
| `stat` | 大数字/指标（66px） | 指标说明 | 忽略 |

配色来自 `DESIGN.json` 的 `primary_color` / `secondary_color`；节奏来自分镜自己的
`start_seconds` / `duration_seconds`。

### 明确放弃的表达力（这是交付的一部分，不是遗憾）

| 放弃了什么 | 之前长什么样 | 判断 |
| --- | --- | --- |
| **任意 CSS** | 每片自定义渐变、`bg-glow` 光晕球的位置与尺寸、逐片配色层次 | **接受。** 12 套锁定风格本来就是产品承诺的「统一观感」，逐片自由发挥与它冲突 |
| **任意 GSAP 编排** | 逐元素自选 ease（`back.out(2)` / `power3.out`）、自选 stagger 节奏、自定义时间点 | **接受。** 模板按版式给固定编排，观感稳定；代价是每支片子的动画节奏一样 |
| **临时发明的组件** | `vector-dots`（8 个圆点表示向量化）、`icon-grid`（emoji + 标签） | **部分损失。** `points` 的要点卡片能替代 `icon-grid` 的语义，但 emoji 图标和「圆点阵」这种为具体内容量身造的示意图**做不出来了** |
| **任意几何 / SVG / 图表** | 模型理论上可以画 SVG 折线、饼图 | **真损失，但从未观测到。** 唯一的真实样本没有用；`stat` 版式覆盖了「一个大数字」这个最常见诉求 |
| **`design.typography`** | 模型写的字体描述会影响它自己写的 CSS | **降级为纯说明字段。** 它仍写进 `DESIGN.json`，但不再影响画面。模板用系统字体栈 |
| **用户上传的 Logo 入画** | `brand_assets` 曾在提示词里作为可引用资源列出 | **实际零损失。** `lib.rs:746` 一直发的是 `"brandAssets": []`，一句话链路从来没有传过素材 |

**一句话：放弃的是「每支片子的结构自由」，换来的是速度、稳定性和可预测的观感。**
如果哪天要恢复某一类表达，正确的做法是**在模板里加第五种版式**，而不是把 HTML 还给模型。

## 5. 实测：改前 vs 改后

### 5.1 方法

计时器套在**代理本来就暴露的 `model_call` 注入点**外层（T83 用的同一个口子），
没有改产品代码、没有 monkey patch。基线用 `git show HEAD:...agent.py` 检出到临时目录
按同样方式跑，`contracts/` 与 `vendor/` 软链回本树。同一句 Brief、同一个 endpoint
（`qwen3.7-max-2026-06-08`）、同样 12 秒时长。密钥全程未打印、未落盘。

**基线与模板版**是**背靠背交替**跑的（`base-1, tpl-1, base-2, tpl-2, …`），
避免把服务端负载波动算到某一侧头上。

### 5.2 第一轮（7 对）：发现两个提示词收敛缺陷

| | n | 一次通过 | 模型秒 最小/中位/最大 | 应答字节中位 |
| --- | --- | --- | --- | --- |
| 基线 | 7 | 5 | 57.8 / 57.8 / 116.7 | 7,745 |
| 模板（提示词 v1） | 7 | **4** | 40.7 / 50.7 / 57.5 | 3,006 |

模板版**通过率反而更低**。看真实应答查明原因：

- `tpl-4` / `tpl-7`：`beat_id` 返回的是**整数** `1,2,3,4,5,6`，而解析器要
  `^[a-z0-9][a-z0-9-]{0,63}$`；
- `base-3` / `base-4`：`script.beats` 返回的是**对象数组**（`{beat_id,purpose,text}`），
  而解析器要纯字符串；
- `tpl-1`：`catalog_parts` 里有目录外的 id（这条是既有失败模式，与本次改动无关）。

前两条**是提示词没说、不是句子写得不好**——而它们全都以
「自动编排判定这次描述做不出来，请换一句更具体的描述后重试」到达用户，正是 T83
点名的误导。提示词是我这次重写的，收敛是我的责任，所以先补测试再补两句话
（**纯提示词、零输出成本**）：

- `script.beats 的每一条都是一句纯文本字符串，不是对象`
- `beat_id 是字符串，只能用小写字母、数字和连字符，例如 beat-1、beat-2`

### 5.3 第二轮（提示词 v2，10 次）+ 同时段基线（4 次）

| | n | 一次通过 | 模型秒 最小/中位/最大 | 应答字节中位 |
| --- | --- | --- | --- | --- |
| **基线（全部 11 次）** | 11 | 9 | 53.3 / **87.0** / **116.7** | **7,745** |
| **模板 v2（全部 10 次）** | 10 | **10** | 34.6 / **36.9** / **57.4** | **2,429** |
| 同时段基线（背靠背 4 对） | 4 | 4 | 87.0 / **102.8** / 104.6 | 7,765 |
| 同时段模板（背靠背 4 对） | 4 | 4 | 35.7 / **40.3** / 57.4 | 2,429 |

**结论（全部实测，不是估算）：**

- **模型耗时中位数 87.0 → 36.9 秒**（同时段背靠背口径 102.8 → 40.3 秒）；
- **最坏值 116.7 → 57.4 秒**；方差从 63 秒收窄到 23 秒；
- **应答字节 7,745 → 2,429 B（3.2 倍）**，且波动从 ±60% 收到 ±10%；
- **一次通过率 9/11 → 10/10**（提示词 v2 之后 0 次失败）；
- 本机开销 `localSeconds` 两侧都是 **0.00~0.01 秒**，与 T83 一致。

**为什么 3.2 倍的字节只换来 2.4 倍的时间：** 正文吐字速率两侧根本不同
（基线 7,745 B / 57.8 s ≈ 134 B/s，模板 2,429 B / 36.9 s ≈ 59 B/s）。
如果时间真的正比于正文，两个速率应该相等。**差额是推理时间，它不随正文缩短。**
T83 那条「4.5 KB/s 恒定」说的是含推理流的线路字节，不能用来预测正文变短后的耗时——
本任务把这条修正过来。

### 5.4 端到端影响（推算，需真实 App 复验）

T83 实测「提交→完成」= 编排 + 渲染，渲染稳定在 28~35 秒。按本轮编排中位数：

| | 编排 | 渲染 | 提交→完成 |
| --- | --- | --- | --- |
| 基线 | 87 s | ~33 s | **~120 s** |
| 模板 | 37 s | ~33 s | **~70 s** |

**这一行是算出来的，不是量出来的**——本轮验收在代理层，没有跑正式 App 的完整链路。
见 §9 遗留。

`tl.` 语句全部剥掉——运行时照常加载、时间轴照常注册、clip 区间照常声明——真实
Chromium 渲染结果：

```
EVENT: {"event":"worker.render.failed","reasonCode":"render_static_frames",...}
```

**模板主动避免静止的设计：** 每个 beat 都有一条跨越它整段时长的进度条 tween

只有入场动画的话，长 beat 的尾部会是一串完全相同的帧。

## 8. 失败矩阵

| 场景 | 行为 |
| --- | --- |
| 模型仍然返回 `composition_html` | 键集精确校验拒绝（`agent_first_response_must_carry_the_three_closed_fields`）。**不接受后丢弃**——那会让最慢的应答看起来像成功 |
| 模型给出模板没有的 `layout` | `agent_beat_layout_is_not_published` 拒绝。绝不「回退到默认版式」渲染一个没人审过的画面 |
| 分镜时间不铺满 0..时长（重叠 / 留空 / 不从 0 开始） | `agent_storyboard_beats_must_tile_the_film` 在**绘制之前**拒绝。以前是绘制之后由 `clip_coverage` 报出来，那会把分镜缺陷说成合成缺陷 |
| `headline` 为空 / 超长、`items` 超过 6 项 | 各自的 `agent_*_out_of_range` 拒绝，画面不会出现空卡片 |
| 文案里带 `https://`、`WebSocket`、`fetch(`、`new Date()`、`</script>` | **全部照常出片。** 文案里每一个 ASCII 字符都转成数字字符引用，浏览器渲染一模一样，但源码里形不成任何被禁子串，也形不成标签。这是必须做的：两道静态门禁都是**按源码文本子串**判定的，而修复轮已经没有了——一句讲 WebSocket 的 Brief 会把用户自己的句子拒掉 |
| 模板产出通不过静态门禁 | 直接拒绝，不再回合修复（模型看不见也修不了自己没写的文档），reason 带上具体 code |
| 运行时资产没被 App 播种进工作区 | `undeclared_asset` 拒绝（既有路径，未改动） |
| 合成整段不动 | 入口 `missing_animation_runtime` + 出口 `render_static_frames`，两道都实测有效 |
| 模型服务连不上 / 卡死 / 超时 | 未改动（`video_creation_model_transport_failed` / `_timed_out`） |
| `catalog_parts` 给出目录外 id | **既有失败模式，本次未改**。实测 18 次里命中 1 次，用户看到的仍是「请换一句更具体的描述」。见 §9 |

## 9. 遗留与我对自己这轮的怀疑

1. **没有跑正式 App 的完整用户路径。** 验收停在代理层 + 真实渲染 Worker。
   §5.4 的「提交→完成 ~70 秒」是**算出来的**。正式包链路（Rust → 执行器 → Worker）
   的 DTO 没有变化（应答仍是 `entryHtml/allowedAssets/frameCount/...`），
   但这不能替代真跑一次。**建议主线在合并后按 T83 的方式跑一次 App 路径复验。**

2. **`catalog_parts` 是下一个可摘的果子，但我没摘。** 它同时占着三宗罪：
   吐 15 个 id 的输出成本、把 134 个 id 塞进提示词的输入成本、以及实测 18 次里
   1 次的拒绝率——**而它对画面零影响**（§1 已复核）。没动的理由是
   `FIX-motion-parts-selection-wiring.md` 明确写着这条链的产品语义还没决定，
   删字段等于替主线做那个决定。**如果主线决定「零件暂不接入」，删掉它是纯赚。**

3. **样本量。** 基线 11 次、模板 10 次。T83 提醒过这个分布右尾没探到底，
   我这轮模板版最大值 57.4 秒也可能只是没抽到。**倍数结论（2.4x / 3.2x）比
   绝对值可信**，因为它来自同时段背靠背配对。

4. **一句 Brief、一个模型、一个时段。** 「用蓝色商务风做一段本周销售增长说明，三个要点」。
   换一句很短的、很怪的、或者信息量很大的句子会不会让模型挑错版式、写超长 headline，
   我没测。解析器有硬上限兜底（拒绝而不是画坏），但那是拒绝，不是好体验。

5. **观感我只看了源码和帧数，没有逐帧看画面。** 真实模型产出的合成经真实 Chromium
   渲染成功、4 帧、356 KB（对照：T86 那份静止废片 4 帧只有 5.8 KB），
   **但我没有把帧导出来逐张看过**。「能动、尺寸对、不空」是证到了，
   「好不好看」没有证据。

6. **两处本机模板并存。** 手工制作路径在 `motion_video_studio.rs::manual_composition`
   里另有一份 Rust 模板（不用 GSAP，自定义 `seek`，且**不经过** `lint/check` 两道门禁）。
   本任务没有合并它们——跨进程跨语言，且手工路径刻意不碰执行器与模型。
   **这是已知的重复，值得单独立项。**

7. **提示词删掉的那段 CDN 覆盖说明，是我判断它已无对象后删的。** 判据是模型不再产出
   HTML，所以没有标签可抄。但被钉住的示范文件**仍然逐字进系统提示词**——
   它教的是「怎么写合成骨架」，现在是无用甚至误导的输入。**我保留了它**，因为
   `load_locked_authoring_workflow` 同时是供应链摘要门禁（`installation_damaged`
   那一类 reason 全靠它），拆掉牵动面太大。**代价：约 4 KB 的无用提示词，
   以及模型仍有可能被它带偏去写 HTML**（实测 17 次没有发生一次，键集校验也会兜住）。
