# C4 跨脚本导入符号门禁与 BM-08 重写审计

> 日期：2026-07-26  
> 分支：`codex/batch-3`  
> 状态：实现与相关测试已通过；BM-08 审计发现两处未保留的防线，按交接要求只登记证据、未凭审计结论修改其行为。

## 目标与取舍

本任务防住这一类回归：`scripts/` 或 `backend/tests/` 写了
`from <本仓库 scripts 模块> import <名字>`，而提供方重写时删掉了那个名字。

`scripts/check_script_import_symbols.py` 只解析源码 AST，不 import 提供方。验收脚本在
import 阶段可能构建产物、启动服务或做其他重活，执行模块来检查命名空间会让门禁本身产生
副作用。门禁把以下直接模块作用域绑定视为真实符号：

- 函数、异步函数和类；
- 直接赋值、有值的带注解赋值及解构赋值（只有 `NAME: Type` 不会在运行时创建名字）；
- 模块作用域的 `import` / `from ... import ...` 绑定；
- Python 3.12 的 `type` 类型别名。

函数/类内部的名字不算模块符号。模块顶层控制流按运行时可达性合并：
常量真假分支取实际路径，未知条件只接受每条分支都绑定的名字；
循环、`match`、`try` 和可能吞异常的 `with` 会保守合并所有成功路径与中途状态，
`if TYPE_CHECKING:` 下只供类型检查器看的名字不会被误当成运行时必定可 import 的名字。

扫描范围由目录派生：

- 导入方：`scripts/**/*.py`、`backend/tests/**/*.py`；
- 提供方：`scripts/**/*.py`；
- 支持脚本目录放进 `sys.path` 后的短模块名，以及 `scripts.<模块>` 全名；
- 支持命名空间包形式的 `from scripts import 子模块`，子模块文件删除会直接报错；
- 只检查 `from ... import name`；外部依赖、普通 `import module` 和相对导入不在本门禁
  的符号级范围内。

测试文件命名为 `scripts/test_script_import_symbols.py`，无需修改
`scripts/run_script_tests.py`，其现有 `scripts/test_*.py` 派生发现会自动收录。

## RED

先加入测试，再提供最小的空结果桩。测试提供方故意只有 `EXISTING`，导入方同时请求
`DELETED_NAME`；实际运行：

```text
$ backend/.venv/bin/python scripts/test_script_import_symbols.py
FAIL check_a_deliberately_missing_name_is_reported_without_import_side_effects: the deliberate missing import must produce exactly one violation, got []
FAIL check_only_real_direct_module_bindings_satisfy_an_import: module binding scope drifted: []
ok   check_the_real_repository_has_no_broken_local_import_names
ok   check_this_test_is_auto_discovered_by_the_aggregate_runner
executed checks: 4
```

这是缺名断言本身失败，不是 ImportError、语法错误或待实现文件不存在。提供方夹带了一个
写哨兵文件的 import 副作用；GREEN 还会断言哨兵不存在。

独立审查随后补出三类反例，先扩测试得到第二次 RED：纯注解被错误接受，`if True` 和
未知条件双分支的模块绑定被漏报，`from scripts import deleted_provider` 未被检查。
实际结果为 6 项中 3 项失败；修检查器后才进入最终 GREEN。

第二轮独立审查继续用合成树发现控制流中途删除仍会假绿，且导入方的
`TYPE_CHECKING` / 常量假分支会被 `ast.walk` 误报。第三次 RED 为 8 项中 3 项失败，
分别固定字面量真值、`for`/`while`/`match`/`try`/`with` 的运行时删除，以及死分支
导入过滤。最终复审又补出 `except ... as NAME` 结束时自动删除别名、循环
`break`/`continue` 后不可达赋值两种假绿；第四次 RED 精确漏掉新增的三个名字，修订后才
得到下面的最终结果。

最后一轮复审再把异常藏进 `try` / `with` 内的嵌套 `if`，证明只记录直接子语句仍会漏掉
删除后的异常路径。第五次 RED 精确漏掉 `FROM_NESTED_TRY` 与
`FROM_NESTED_WITH`；最终实现让顺序分析在可达的 `raise` / `return` /
`break` / `continue` 处停止，并只在对应 `try`、`with` 或循环确实消费该控制效果时
继续外层路径。

覆盖的失败矩阵：

| 情形 | 结果 |
| --- | --- |
| 提供方删掉被导入名字 | 报导入方相对路径、行号、模块和缺失名字 |
| 提供方 import 会执行副作用 | 只解析 AST，哨兵文件未产生 |
| 名字只在函数、类、`TYPE_CHECKING` 或非必经分支内部 | 不冒充运行时必有模块符号，报告缺失 |
| 函数、类、常量、有值注解、解构、导入别名 | 识别为模块绑定；无值纯注解不算 |
| 控制流中途删除名字后异常被吞/循环结束 | 合并所有可能成功状态，不把末尾重新赋值冒充全路径事实 |
| `except ... as NAME` 覆盖旧模块名 | handler 结束按 Python 语义删除异常别名 |
| `break` / `continue` 后写着不可达赋值 | 循环路径在 abrupt completion 处停止，不接受死代码重绑 |
| 异常藏在 `try` / `with` 的嵌套分支 | 把可达的 abrupt completion 传播到直接语句边界，再由捕获/抑制层消费 |
| 导入只在 `TYPE_CHECKING`、`if False` 或其他静态假分支 | 不报告不可执行的导入 |
| `from scripts import 子模块` 的子模块文件被删除 | 报缺失，不因命名空间包跳过 |
| 新增 `test_*.py` 忘记登记 | runner 的派生发现自动收录，本测试自证可达 |
| 仓库当前已有断裂导入 | 真实树扫描失败；本次结果为零条 |

### 已确认没有保留的两道防线

#### 1. 缓存命中后不再复核视频运行时内容

旧 BM-08 在每次运行中执行 `ffmpeg -version` 并要求锁定版本。当前链路在
`video_runtime_cache.py:121-122` 看到目录与输入指纹 stamp 相符就直接返回；
`prepare_video_runtime.py:225-233` 安装后只要求声明文件存在且非空。仓库其实已有更完整的
`check_video_media_toolchain.py:405-505`，它会复核 Manifest 的每个文件摘要、FFmpeg/
FFprobe 精确版本、GPL/nonfree 标志和能力集，但 BM-08 当前没有调用这条候选校验。

用临时目录实际改写缓存 payload、保留 stamp 后再次调用缓存，结果为：

```text
payload=tampered builds=1
```

因此这不是“可能看起来有问题”：缓存输入变化会失效，但缓存内容在输入不变时被改写不会重建
或拒绝。对 Chromium 而言共享 harness 已做到每次逐文件复核；对 media toolchain 和
motion Worker 还没有同等证据。本任务不改这条链，避免把审计发现未经独立 RED 就混入 C4。

#### 2. 本次进程残留的自校验被删除

旧脚本结束时以本次 `run_root` 执行 `pgrep -f`，发现从该暂存根启动的 Chromium/Worker
仍存活就失败。生产资源改为固定 `target/debug` 布局后，`run_root` 和这段检查一起删除；
当前 `run_bm_08_acceptance.py:341-347` 在视频检查后直接成功返回，没有按本次运行 PID
集合或其他所有权标识复核浏览器/Worker 残留。

这只能证明“防线已删除”，不能据此声称“当前一定泄漏进程”。历史批次记录 BM-08 真实链路
为绿，但没有把该驱动完成后的进程集合写成可重复断言。新的固定资源路径也不能安全照抄旧
`pgrep`，否则会把其他并行 worktree 或用户进程混为本次所有物；若主线决定修，应先用本次
启动前后 PID 差集或显式所有权标识写 RED。

### 其余删除的分类

- `--archive` 参数随验收专用 Chromium 暂存路径一起取消，中央
  `embedded_browser_archives.archive_path()` 负责主检出/worktree 缓存定位，属于单一生产
  路径收口，不是用户产品行为；
- 临时 `run_root` 删除改为稳定、内容锁定的构建缓存，是 T74/T78 的复用目标；缓存目录不再
  按单次运行清理属于设计变化；
- Windows 的“本脚本只支持 macOS”包装器拒绝随生产运行时跨平台装配消失，是能力扩展；
- `CHROMIUM_CONTRACT`、`DEFAULT_ARCHIVES` 和 `_first_existing` 已在 `036c267` 移到
  `build_embedded_chromium_staging.py:28-63`。C4 新门禁会守住前两个被导入名字，但静态
  符号门禁不能证明 `_first_existing` 的双根选择行为；该行为仍应由独立测试负责。

- 这是提交前静态门禁，不是用户功能；不启动 App、浏览器、Docker、网络服务或真实平台，

  `.local`、未改 vendor、未下载依赖、未更新 submodule。
- 本任务没有修改 `run_bm_08_acceptance.py` 或任何产品行为。上面两条审计发现应由主线决定
  是否另立任务，以各自独立 RED 修复。
