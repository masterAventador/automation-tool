### 1.1 B5-04：废

四条独立证据指向同一结论，且没有一条是本批新造的：

1. **被测路径已不存在。** `f34e503`（EB-10，2026-07-24）删除了「在设置页选择受信任的系统

4. **仓库自己早就写明它该死。** `frontend/src-tauri/tests/single_build_path.rs` 的

### 1.2 H8-21：把唯一不重复的断言并进去，其余废

`scripts/run_h8_22_acceptance.py` 退役前只有 8 行，整个内容是
`run_h8_21_acceptance.run(wdio_config="wdio.update-ui.conf.ts")`。也就是说两条 spec 共享：

- 同一个 runner（TLS 更新源、artifact ledger、cache manifest、0700/0600 权限、
  forced-reopen 不重复下载、optional 恰好四次 production check——**全部外层证据都在 runner**）；
- 同一个隐藏 App 构建（`build:tauri:update-installation-test`）；
- 同样三个场景（`optional` / `forced-first` / `forced-reopen`，同一个 `H821_SCENARIO`）。

唯一差别是**怎么做决策**：`update-installation.spec.ts` 用
`core.invoke("decide_app_update")`，`update-ui.spec.ts` 点 `稍后提醒` / `跳过此版本` /
`立即安装` / `检查更新`。CLAUDE.md 第 8 节：直接内部 API/函数/Command 只能作为分层证据。
所以零点击那份是严格更弱的重复品。

`wdio.update-installation.conf.ts` 与 `wdio.update-ui.conf.ts` 逐行 diff 只差一行 `specs`。

**并进去的部分**（不是全丢）——把退役 spec 里 `update-ui.spec.ts` 尚未覆盖的四处断言迁入：

| 迁入的断言 | 原位置 |
| --- | --- |
| `listWindows() === ["main"]`（整条更新流程不得开第二个窗口） | `update-installation.spec.ts:38` |
| optional：`release.policy === "optional"` 与显式 `ready/prompt` | 同上 `:42-43` |
| forced-first：`release.version/policy === 0.2.0/forced` | 同上 `:72-74` |
| forced-reopen：`release.policy === "forced"` | 同上 `:79-81` |

**连带退役 `run_h8_22_acceptance.py` 与 `test:h8-22-app`**：删掉那一行参数之后它就是「无参调用
另一个脚本」，两个 npm 入口会把同一套三场景真实 App 验收各跑一遍。H8-22 的验收现在由
`pnpm test:h8-21-app` 提供，同一次运行同时是 H8-21 的验收；契约用例
`frontend/tests/h8-22-update-ui-contract.test.mjs` 已改钉这个 runner。

### 1.3 H8-20：修

先按「它守的东西是否被别处更好地覆盖」这条判据核对：**没有**。
`update-ui.spec.ts` 的更新源永远正常返回，从不制造中断的下载；H8-20 是全仓唯一
制造「启动时下载被截断」的验收：

- feed 第一次返回 4 字节里的前 2 字节后直接 `ConnectionError`；
- 第二次必须带 `Range: bytes=2-` + `If-Range: "artifact-v1"` 才给 206；
- runner 断言 `request_ledger` **恰好**是这两条，第三次检查必须命中缓存、不得再下载。

这属于 CLAUDE.md 第 9 节失败矩阵里的「断网 / 平台超时」与「幂等、重试上限」，且断点续传的
决定性证据在 runner 侧，spec 只负责把 App 驱动到那两个时刻。所以问题不是「守的东西没价值」，
而是**触发方式不合格**：原 spec 用 `core.invoke("check_app_update_now")` 触发恢复，
证明的是 Command 能用，不是用户够得着它。

改法是把驱动换成真实用户路径，断言不变、runner 一行不改：

```
点「设置与诊断」→ 等可见文案「暂时无法连接更新服务器，可稍后重试」
→ 点「检查更新」→ 等弹窗「发现新版本 0.2.0」（断点续传在此发生）
→ 点「稍后提醒」关掉挡住设置卡的弹窗 → 再点「检查更新」→ 必须仍是同一 release（缓存命中）
```

「稍后提醒 → 再检查」是缓存命中的用户路径版本，等价于原来第二次 `check_app_update_now`；
`run_h8_21_acceptance.py` 既有的 optional 场景已经实测过 defer→check 不会重新下载，
所以 runner 的 `request_ledger` 断言仍然成立。

失败态文案 `暂时无法连接更新服务器，可稍后重试` 来自
`AppUpdateCenter.tsx:56-57`，是 `transport_unavailable` 的用户可见投影——这条断言顺带把
「可自愈的失败必须以中性提示态呈现、不能吓用户」也钉住了，原 spec 只看 IPC 时看不到它。


**RED-2**（只删 spec/config、还没解 runner 硬编码时）——这次专门验证新增的悬空门禁真的会
响，因为 T57b 担心的正是「直接删前端会造成确定性悬空」：

```
✖ no executor points at a WDIO entry that no longer exists
  + 'package.json:test:browser-settings-tauri -> run_b5_04_acceptance.py',
  + 'package.json:test:h8-22-app -> run_h8_22_acceptance.py',
  + 'scripts/run_h8_21_acceptance.py -> wdio.update-installation.conf.ts'
```

这三条正是原本会被漏掉的引用。原来的所有权门禁**不会**报它们：那条用例只遍历「现存的」
config 和 spec 去找 owner，一个指向已删除入口的 runner 不在遍历范围内，只有真跑桌面验收
时才会炸。悬空门禁扫 npm scripts、`scripts/*.py`（`test_*.py` 除外，它们造合成树，名字
是故意虚构的）和 wdio 配置里出现的 `wdio.*.conf.ts` / `e2e-tauri/*.spec.ts` / `run_*.py`，
要求每一个都真实存在。落地前先确认基线干净（无既有悬空），避免继承无关红灯。

## 4. 真实边界

### 4.1 两条改动过的 spec 目前拿不到真实桌面证据，原因不在本批

`run_h8_20_acceptance.py` 实跑（本批修改后）停在 spec 的**第一行**：

为了确定这是不是本批造成的，把 `frontend/e2e-tauri/update-download.spec.ts` 换回 `HEAD`

根因：`fb6d122`「让桌面验收加载生产组合入口」（2026-07-26 21:16）把

2026-07-26 21:16 起集体停在启动门禁前。`docs/development/desktop-e2e-remaining-specs.md`
记录的 07-26 上午实跑（H8-20/H8-21/H8-22 全绿）发生在该提交之前。

受影响的不止本批这两条：`update-download`、`update-ui`、`update-macos-package`、
`update-windows-package`、`diagnostic-export`、`model-service` 都在这一族。

因此本批两条 spec 改动按 CLAUDE.md 第 2.1 节记为 `🔍 待验收`：判定与静态门禁已完成，

## 5. 失败矩阵

| 场景 | 覆盖处 |
| --- | --- |
| 启动检查时下载被中途切断 | H8-20 feed 第一次响应截断，spec 断言用户看到可重试提示态 |
| 断点续传而非重新下载 | runner `request_ledger` 精确等于 `[无 Range, bytes=2-]` |
| 重复检查必须命中缓存 | spec「稍后提醒→再检查」后 release 不变，runner 断言无第三次 artifact 请求 |
| 传输凭据/URL/路径泄漏 | spec 断言 state JSON 与更新卡片文本都不含 `url/signature/path/http`；runner 断言 cache manifest 同样不含 |
| 可选更新的暂缓 / 跳过 / 装新版 | `update-ui.spec.ts` optional 场景，全部经真实按钮 |
| 强制更新不可跳过、Esc 不能关 | `update-ui.spec.ts` forced-first |
| 强更下次启动安装且不重复下载 | `update-ui.spec.ts` forced-reopen + runner `artifact_ledger` |
| 更新流程不得开第二个窗口 | 由退役 spec 并入 `update-ui.spec.ts` 的 `listWindows()` |
| 入口被删后 runner 悬空 | 新增悬空门禁，RED-2 实测捕获三条 |
| 已退役入口复活 | 三条 `assertMissing` / `assertMissingScript` 用例 |

前四行与「可选/强制」三行的真实桌面证据按 §4.1 记为 `🔍 待验收`；断言本身已写死在 spec 与
runner 里，等 `desktop-e2e` 族恢复可执行即可取证。
