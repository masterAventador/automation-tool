## 开工前【先定】

### 1. HTTP 错误分层

- 请求体或域构造拒绝：422；
- 可公开且调用方有明确动作的持久化失败：404 / 409 / 503；
- 四个 `...DataRejected`：500。它表示仓储的服务端调用方给错类型/状态，或数据库出现
  仓储不认识的约束，不是 HTTP 客户端可以通过改请求稳定修好的答案；
- 四个 `Invalid*Model`：500。它们表示既有数据库行在水合时被域拒绝；
- `DataRejected`、`Invalid*Model` 与未知异常原样上抛给全局 unexpected handler，
  由它记录异常并产出固定 `internal` 信封；不把 500 包成不会记录的 `AppError`。

T1 的动态词汇守卫必须发现四个应用模块全部 4 / 5 / 5 / 7 个持久化失败子类。新增失败类
若没有明确公开映射或明确内部失败归属，测试必须变红。

### 2. 修订冲突的公开形状

`PublicError` 增加可选、严格校验的 `details` 判别联合。首个成员：

```text
kind = timeline_revision_conflict.v1
currentRevision = 大于等于 1 的整数
```

其它错误不带 `details`。版本不得塞进 message。冲突后的 `currentRevision` 是再次读取到的
最新修订，允许比发生冲突的那一版更新。

### 3. 一个项目只能有一个 timeline 身份

采用数据库可强制的一对一身份表，不使用“先查没有再随机插入”：

- 新表 `editing_project_timelines`：`project_id` 为主键并外键指向项目，
  `timeline_id` 唯一；
- 第一次保存时间轴时用单条数据库写入争夺项目的 timeline 身份；并发首存只能有一个身份
  成功，失败方读取已存在身份后重建请求或答冲突；
- `timelines (project_id, timeline_id)` 增加复合外键指向该身份表，任何绕过 API 的写入
  也不能给同一项目制造第二个 timeline 身份；
- Timeline 仍是不可变修订，不增加 update；`EditingJob.update(previous, changed)` 的 CAS
  只由 LE-12 Worker 状态写回消费。

迁移、仓储方法名与并发 RED 在 T4 开始前再逐项写入该节，但身份方案不再重选。

## T2 项目路由与分页仓储

### 开工前定下的接口

- 路径固定为 `/api/v1/editing-projects`：`POST` 创建、`GET` 分页列表，
  `/api/v1/editing-projects/{project_id}` 只读详情；没有 update/delete；
- 创建体只承载 `title`、`output` 与 `captionStyle`。`projectId` 与 `createdAt` 由服务端
  生成；LE-01 前端旧 DTO 的 `sourceArtifactIds` 已被新领域模型淘汰，不把它带回 API；
- 公开快照逐字对应当前 `EditingProject`：`projectId/title/output/captionStyle/createdAt`，
  不虚构领域里不存在的 `updatedAt`；
- 列表默认 20 条、最多 100 条；仓储固定
  `created_at DESC, project_id DESC`，游标是同时携带两列的 canonical base64url JSON，
  非规范编码、重复键、未知字段、坏 UUID 或坏时间一律 422；
- App Session 认证沿用 `require_current_installation_access`。自审实际证明“只认证、
  不按 Installation 过滤”会让任一合法设备读取共享 Control Plane 上的全部项目，因此
  本子任务用迁移 `0040` 新增 `editing_project_installations` 所有权表：`project_id`
  主键保证一个项目只有一个 owner，两侧外键拒绝伪造身份，项目与 owner 同事务写入；
  项目领域对象保持不带认证信息，生产服务只消费按 Installation 限定的保存、详情和分页
  方法，跨 Installation 的详情统一 404、列表不出现外部项目。

### RED 目标

1. 真实 PostgreSQL 中四个项目使用同一 `created_at`，按两页读取时仍按 `project_id`
   总序排列且不重不漏；
2. OpenAPI 只暴露创建、列表、详情三个 App Session 保护操作；
3. 创建与查询返回严格公开快照，未知字段、非法画幅/字幕跨字段组合均为固定 422；
4. 不存在或非法 project id 为同一 404；重复创建为 409；数据库不可用为可重试 503；
5. 游标不透明且篡改、非 canonical 或形状漂移均为固定 422。

## T3 素材路由

### 开工前定下的接口与所有权

- 路径固定为 `/api/v1/editing-materials`：`POST` 登记；
  `GET /{material_id}` 按身份查询；集合 `GET` 用必填 `contentDigest` 做导入判重查询；
  `PUT /{material_id}/description` 更新描述。没有列表、删除或其它素材字段更新；
- 登记体逐字段承载当前 `Material` 快照，并由调用方提供 `materialId`，因为同一个身份还要
  登记进执行器侧 `MaterialPathRegistry`。请求与响应都不出现本机路径；所有请求模型
  `extra=forbid`，所以 `path`、`filePath`、`sourcePath`、`localPath`、`fileUri` 等
  路径形状字段都得到固定 422；
- 描述更新是按 `source` 判别的严格联合：`user` 只接受 `description`；`ai` 还接受
  `tags` 与 `describedAt`。当前快照已经是 `USER` 时，服务必须显式抛
  `MaterialDescriptionProtected`，不能把 `Material.with_ai_description()` 返回
  `self` 的静默保护误报成成功；仓储的原子 UPDATE 谓词继续兜住读取后发生的并发用户写；
  更新后重新读取并返回实际存储快照，调用方不能从“没有异常”推断自己提交的 AI 文本一定
  仍是最终值；
- App Session 不能只认证不授权。`materials.installation_id` 从建表起就是非空外键，
  `(installation_id, content_digest)` 唯一；同一文件可由两台 Installation 各自登记，
  跨设备详情与摘要查询均为 404，也不会共享随后可变的用户描述；
- 素材仓储只保留 `save/get/find_by_digest/update_description` 四个现行方法，每个方法
  都必须显式接收 `InstallationId`。不保留无 owner 入口、`NULL` 命名空间、旧方法、
  scoped 后缀别名或兼容适配器。

### RED 目标

1. OpenAPI 只暴露登记、两种查询与描述更新四个 App Session 保护操作；
2. 登记、ID 查询与摘要查询返回严格的当前域快照，任何路径形状或未知字段都固定 422；
3. 两台 Installation 可登记相同摘要，但详情、摘要和描述更新都互相不可见；
4. 用户描述往返后，AI 再写答 `material_description_protected` 409，既有文本不变；
5. 非法 UUID/摘要/枚举/数值/描述联合答固定 422；重复登记 409、查询缺失 404、
   数据库不可用 503。
