## ① 好消息也要送到（已修）

### 一、这条和 T91/T91b 修的是同一个形状，符号相反

T91 修的是「失败被伪装成进行中」，T91b 修的是「渲染阶段失败没人去查」。这一条是**同一个标记
说着不对的话**，只不过这次盖住的是好消息：监视器早就把任务标成结束了，`motionRunAttention` 却
只能落到 `running`，于是侧边栏继续挂一个无文字蓝点，悬停写着「视频制作正在进行中」——对一条
几分钟前就做完的片子，那句话是假的。

严重性确实低一档，理由要说准：**它不会让人白等一件已经死掉的事**。用户最终会回到那一页并看到
成片。但演示当天客户切走再切回来，看到「还在做」而其实早就做完，一样难看，而且它把「什么时候
能好」这个问题的答案从屏幕上拿掉了。

### 二、为什么是第五种，而不是复用现有四种

| 复用哪个 | 为什么不行 |
|---|---|
| `running`（蓝点） | 这就是现状，也就是缺陷本身 |
| `none`（不标记） | 成片没人看过就灭掉标记，等于把「有东西等你取」这件事藏起来；`forgetMotionJob` 之前它还欠着一次「去看」 |
| `failed` | 断言一件相反的事 |
| `unknown` | 断言「看不到」，而这里恰恰看得清清楚楚 |

所以是 `"finished"`。

### 三、呈现：绿色角标「完成」，悬停「视频制作做好了，去看成片」

**颜色不是随手挑的。** 现有三个有字角标里，`失败` 和 `未知` 都是角标默认的红——它们是两种
「有问题」。这一条不是问题，它是「有东西可以取」。**用户先看到颜色，才看到字**：一条做好的片子
也顶着红角标，会把每一次瞥向侧边栏都变成一次惊吓，用完几次之后他就不看这个角标了，那时四种
标记一起失效。绿色是这条消息的性质本身，不是装饰。

**宽度也不是随手定的。** 三个有字角标一律两个汉字。T91 和 T91b 都登记过同一个未验证项：232px
侧栏是否会把角标裁掉（jsdom 和 Playwright 的 `toBeVisible()` 都不判定裁剪）。写成两个字，
那个未决问题的答案对第三个角标同样适用；写宽一点就是在没答案的地方再加一个变量。

文案跟随已有的「去看看」句式，但落到页面上真实存在的那个按钮名：**去看成片**。

### 四、什么时候清掉——判据只有一条

**用户在制作页按下「去看成片」。** 那个按钮做的正是 `forgetMotionJob(renderJobId)` +
`dismissMotionRunMessage()`，也就是清掉页面上「『X』已经做好了」那条成功提示的同一个动作。

这里**故意没有第二条规则**：不看计时、不看用户有没有路过那一页、也不因为又提交了一条而清掉。
理由是自洽性——侧边栏的角标和页面上的提示由**同一次确认**、在**同一时刻**一起灭掉，两个界面
永远不会对同一件事说不同的话。而「两个界面对同一件事说法不一致」正是本条线从 T91 起一直在修
的病，新增一条独立的清理规则等于给它开一个新入口。

**会不会变成噪音？** 它是一个状态，不是一次通知：没有弹窗、没有 toast、不重复触发，只在那条
片子还没被打开时亮着。用户已经打开过的成片不会再亮第二次（记录被 `forgetMotionJob` 删掉了）。

代价说清楚：**用户回到页面、看见了成功提示、但没按按钮就走开，角标会留着。** 这是有意的——
页面上那条提示同样留着，两边一致，而且那条片子确实还没被打开过。

### 五、五种 attention 的排序，以及为什么

```
failed  >  unknown  >  finished  >  running  >  none
已知的坏结果   看不见     有东西可以取    有东西在跑    没事
```

一个角标只有一格，两件事同时成立时它必须拿出更要紧的那一件。

- `finished` 排在两个「有问题」之下：看不到一条已经存在的片子，用户最终会找到它；等一条已经
  死掉的片子，他会一直等下去。**已知的坏结果和「看不见」都是问题，做好了不是问题。**
- `finished` 排在 `running` 之上：它是这张表上**唯一一件用户现在就能动手的事**（片子在那儿，
  按钮在那儿），而 `running` 要求他什么都别做。

两件同时成立的具体例子（两条片子，一条失败一条做好）有用例守着，排序换一下就报红——见第六节
变异验证。

**这个排序的已知边界：** 提交第二条片子时，如果第一条做好了还没被打开，角标显示的是「完成」
而不是蓝点。两句话都是真的，但用户可能误读成「我刚提交的这条已经好了」。制作页上两条都看得见，
所以这是一次可能的误读而不是一次谎报；没有为它加特例，因为特例会把「角标说什么」重新变成依赖
上下文的判断。

## ② App 重启后本会话任务全部丢失（**查证完成，本轮不实现**）

### 一、先量代价：根治要动多少

根治方案是「原生快照带 `startedAt`」。实际查下来，**要加的不是一个字段，是两个**，而且这条
契约两头都是封死的。

#### 1. 要加两个字段，不是一个

`ownJobs` 里 App 自己记着三样东西，原生快照一样都没有：

| 字段 | 现在从哪来 | 快照里有吗 |
|---|---|---|
| `startedAt` | `settleMotionRun` 里的 `Date.now()` | ❌ |
| `filmSeconds` | 提交请求里的 `MOTION_BRIEF_FILM_SECONDS` 常量 / 草稿 | ❌ |
| `outcome` | 监视器观察到的终态 | 状态有，但「用户看过没有」没有 |

`frontend/src/features/video-studio/VideoStudio.tsx:165` 的 `motionJobTiming` 同时要
`startedAt` 和 `filmSeconds`（后者算渲染沙箱的停机上限）。只加 `startedAt`，重启后那句
「渲染超过 X 会自动停下」还是算不出来。

#### 2. 这条契约两头都拒绝多余字段——必须同版本一起发

- **Rust 侧**：`frontend/src-tauri/src/motion_video_studio.rs:624`
  `#[serde(rename_all = "camelCase", deny_unknown_fields)]`；
- **TS 侧**：`frontend/src/platform/tauri/material-video-studio-gateway.ts:106`
  `exactRecord(value, [...9 个键...])`，而 `exactRecord`（同文件 47 行）比的是
  **键集合完全相等**，多一个少一个都判 `protocol_mismatch`。

也就是说：新 Rust 配旧 TS，或旧 Rust 配新 TS，**每一次 `motionJobs()` 都抛异常**。而按 T91b
的设计，连续读不到就会让侧边栏翻成「未知」——一次没配好的发布，症状是整个视频制作功能的进度
读不到。

#### 3. 磁盘上已有的快照会挡住整张任务列表

快照是落盘的（`save_snapshot` / `load_snapshot`，checkpoint 名 `motion-render-job`）。加一个
必填字段之后，旧文件在 `serde_json::from_slice` 上失败 → `job_unavailable()`。而
`motion_video_studio.rs:1138` 的 `jobs()` 是这么写的：

```rust
for workspace in store.list_workspaces()... {
    if let Some(snapshot) = load_snapshot(store, &workspace)? {   // ← 这个 `?`
        result.push(snapshot);
    }
}
```

**一条解析不了的旧快照，用 `?` 把整个列表调用一起带走。** 所以必须配 `#[serde(default)]` 或
显式迁移，不能直接加字段。

#### 4. 波及面清点（已实测计数）

| 位置 | 数量 |
|---|---|
| Rust 结构体定义 | 1（`motion_video_studio.rs:626`） |
| Rust 构造点 | 2（`:833` 模板路径、`:1114` 一句话路径） |
| Rust `validate_snapshot` | 1 处，且要为新字段定义「什么算合法」 |
| Rust 序列化迁移 | 1 处决策（`serde(default)` / 版本号 / 迁移步骤） |
| TS 接口 | 1（`material-video-studio-gateway.ts:59`） |
| TS 校验器 | 2 处（`exactRecord` 键表 + 类型/范围判定） |
| TS 快照字面量（fixture） | **15 处 / 5 个文件**：`VideoStudio.test.tsx` 9、`material-video-studio-gateway.test.ts` 3、`WorkbenchShell.test.tsx` 1、`test-harness/video-studio.ts` 1、接口定义 1 |

#### 5. **最要紧的一条：`startedAt` 就算加了，也修不完这个洞**

`ownJobs` 承担的第三件事——**「这条片子用户看过没有」**——**在原理上就不可能来自渲染快照**。
它是关于「这台 App 告诉过这个人什么」的事实，不是关于渲染的事实。原生侧无论加几个字段都答不了。

具体后果：只加 `startedAt` + `filmSeconds`，重启后 App 能重新算钟、能重新盯任务，但
`VideoStudio.tsx:1456` 那条 `finishedOwnJobs` 的过滤条件（「只 announce 本会话启动的」）失去
依据。要么退化成「一条都不 announce」（等于现状），要么变成「所有 succeeded 都 announce」——
那会让历史上每一条成片在每次开 App 时都弹一遍「已经做好了」，比现在坏得多。

**所以根治不是「原生加个 startedAt」，是「原生加两个字段 + App 侧另外持久化一份确认记录」。**
T91 登记这一条时把它写成一个原生任务，从本轮查证看，那个描述是不完整的。

### 二、结论：本轮不做

理由按重要性排：

1. 它是**跨 Rust / TS 契约**的改动，两头封死、必须同版本发布，而本仓库当下有六条线在并行；
   本任务的边界也写明「任何 `.rs`（除非 ② 确实要动，动之前在文档里说清楚）」——查证结果是**不该动**；
2. 光加字段**并不闭环**（上面第 5 条），真做要连 App 侧的确认记录一起设计，那是一个独立任务；
3. 对演示的实际价值低：演示场景是「切走再切回」，同一次会话内，① 已经覆盖。

### 三、次优解，以及它**修不了什么**

不动契约的做法：**把 `ownJobs` 落到本地持久存储**（`localStorage`，`motion-run-store.ts` 内部，
不碰任何网关）。存的是 `{renderJobId, startedAt, filmSeconds, outcome}`——全是 UUID 和数字，
不含 Cookie、Token、用户文案或本机路径，不触犯项目的凭据存储规则（那条规则约束的是设备私钥和
账号 secret）。

**它能恢复的：**
- 重启前已经开始、重启后仍在跑的渲染 → 监视器重新盯上，钟也接得上（`startedAt` 是存下来的真值）；
- 重启前已经做好、用户还没按「去看成片」的片子 → 重启后角标仍是「完成」。

**它修不了的（必须一起说，否则它看起来像全解）：**

1. **编排阶段（2–3 分钟）中途关 App，无法恢复，而且这是这个洞里最大的一段。**
   `submit_motion_video_brief` 把整个编排跑在命令内部，App 一死命令跟着死，那次制作是真没了。
   而 `pending` **不能**持久化——存了它，重启后屏幕上会出现一个替一个已经不存在的运行走字的钟，
   那正是本条线一直在修的那种谎。**时间尺度上这一段是 2–3 分钟，本机渲染只有约 10 秒**，
   也就是说次优解恢复的是这个洞里较短的那一段。
2. **App 从来没记下过的任务，一条都恢复不了**：换机器、清过浏览器存储、WebView 存储被系统回收、
   或者干脆是别的安装写下的任务。原生侧有任务，App 侧没有对应记录，行为和今天完全一样。
3. **它会引入一个今天没有的新故障模式**，必须一起做掉才能算数：还原出来的任务如果在原生侧已经
   不存在（用户删过工作区、快照坏了），监视器现有逻辑会把它当成「读不到」，连续 3 次之后侧边栏
   永久显示「未知」。所以次优解必须包含一步「首次成功读取后与真实任务列表对账，对不上的直接丢掉」，
   否则它是在制造一个新的错报。
4. **它和产品已有的一个明确决定相冲突，需要先裁决。** `VideoStudio.tsx:1453` 写着
   「Only films this session started are announced. A finished job found on startup is not news.」
   把 `ownJobs` 跨重启保留，等于把「启动时发现的成片不算新闻」这条决定改成「昨天没点开的片子
   今天再提醒一次」。这可能是想要的，也可能是噪音——**这是产品判断，不该在一次修 bug 时顺手改掉。**

**一句话：** 次优解能接上「渲染中 / 已做好未确认」这两段，接不上编排中那 2–3 分钟（也就是窗口
最长的那段），且必须附带对账逻辑，还要先裁一个产品问题。它**不是**根治的廉价替代品，只是一段
不同的覆盖面。

## 四、失败矩阵（本轮新增与相关行）

| 情形 | 现在的行为 |
|---|---|
| 渲染成功，用户在别的页面 | **5 秒内侧边栏出现绿色「完成」文字**，悬停「视频制作做好了，去看成片」；可访问名变为「视频制作 完成」 |
| 用户回到页面按下「去看成片」 | 角标和页面上的成功提示同时灭掉（同一次 `forgetMotionJob`） |
| 用户回到页面看见提示但没按按钮就走开 | 角标留着——页面上那条提示同样留着，两边一致，片子确实还没被打开 |
| 用户自己取消了渲染任务 | 不显示「完成」；监视器停止（有用例 + 变异验证） |

| 一条做好、另一条在跑且读不到 | 显示「未知」——问题压过好消息 |

| `motionJobs()` 连续 3 次读不到 | 「未知」（T91b，未变） |
| 本会话没提交过任何东西 | 一个定时器都不建，`motionJobs()` 一次都不调（T91b，未变） |
| App 重启 | **不恢复**，本轮未修，见 ② |

## 七、仍然剩下的静默 / 错报窗口（如实登记）

T91b 那份登记很有用，照做。**本轮修掉了它的第 1 条**，其余仍在，另加两条本轮查出来的：

1. ~~成片做好、用户在别的页面时标记仍是「正在进行中」~~ → **本轮修掉**。
2. **编排阶段（2–3 分钟）挂死不返回时，从别的页面看仍然只有蓝点「正在进行中」。**（T91b 第 2 条，未变）
   严格说不是谎——原生命令确实还没返回，客户端分不出「慢」和「卡死」。参照物那句话只在制作页上。
3. **App 重启后不恢复。**（T91b 第 3 条）本轮完成查证，未实现，见 ②。**并且查明它比登记的更大：
   不是加一个 `startedAt` 就能收口。**
4. **角标是否被 232px 侧栏裁掉，仍未验证。**（T91b 第 4 条）T91、T91b 就 `失败` / `未知` 登记过；
   `完成` 同为两个汉字、同一位置，结论通用。按边界没有在 `frontend/e2e/` 下新增几何断言
   （T96 占着像素基准）。
5. **本轮新查出的：用户取消渲染之后，从别的页面看仍是蓝点「正在进行中」。**
   `settleMotionRun` 写下的那条 info 消息（「已提交…本机渲染开始了」）在取消后**没有任何东西去
   清它**，而 `motionRunAttention` 的 `running` 分支认 `message !== null`。所以取消一条渲染之后，
   侧边栏会一直说「正在进行中」，直到用户回到制作页手动关掉那条提示。
   形状与本条线一直在修的同族。**本轮没修**：修它要动那条 info 消息的生命周期，而消息是单槽的
   （一条 `message` 服务所有任务），在监视器里顺手 `dismiss` 会误清掉另一条任务的失败文案——
   多任务下的语义要单独设计。登记为独立任务的输入。
6. **本轮新查出的：两条片子并存时角标可能被误读。** 一条做好未确认 + 一条正在做 → 角标显示
   「完成」。两句话都是真的，但用户可能以为是新提交的那条好了。制作页上两条都看得见，所以是
   误读风险而非谎报。没有加特例，理由见第五节。
