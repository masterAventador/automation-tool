## T1 RED 目标

1. 生产生成器只接收路径无关的素材事实；实际源路径仅由 Worker 私有注册表解析，并在使用前后
   核对同一文件身份。视频必须先真实解码证明可用区间，不能把容器头 duration 当成逐帧完备。
2. 素材缺描述/镜头边界或缺人声分析时，生成器通过既有 LE-13/14 公开实现补齐；人工描述受
   保护，不得被 AI 覆盖。所有视觉素材在首次文案模型调用前完成输入和本机前置校验。
3. 无人声素材严格走“分句 → TTS 真时长 → 语义匹配 → 等长片段 → 唯一分配”；有人声视频
   按素材输入顺序形成原声段，不做 TTS、不参与文案素材候选。
4. TTS 文件只写入本机私有 generation workspace；调用方预分配的旁白 MaterialId 与内容摘要、
   时长等路径外事实一一绑定。成功返回 LE-16 `LocalEditingTimelineDraft` 和旁白登记计划，失败/
   取消不返回部分草稿。
5. 进度阶段与比例单调、封闭且可验；取消在模型调用之间、TTS 句间、素材解码/分析循环与最终
   发布前均可观察。取消、素材不足、素材过短、无相关素材、配置缺失、上游拒绝和本机失败使用
   固定产品错误，不携带 prompt、转写、MaterialId、路径、模型请求 ID 或 traceback。
6. 首次聚焦运行必须精确失败于 T1 生产编排模块/公开入口尚不存在；确认捕获力后才创建实现。

## T1 GREEN 与功能验收证据

- 新增 `smart_edit_generation` 封闭装配边界：混合原声/旁白、全原声免文案免 TTS、固定三类
  产品失败、单调阶段进度、协作取消、路径无关分析写回与旁白登记计划均由构造器约束。
- 新增 `smart_edit_media`：随包 FFmpeg 逐帧跑到流末尾，读取 `out_time_us` 形成真实可解码
  区间；容器声明 4 秒但实际只解出 0.4 秒时只发布 `[0, 400)`，不再冒充整段可用。
- 新增 `LocalSmartEditGenerationPipeline`：所有素材先完成注册表解析、完整 probe、不可变事实核对
  和视频解码，再允许第一次模型调用；人工描述不被覆盖，无声素材不会构造 VAD/ASR 下漏斗。
- TTS 在句间观察取消；第二句开始前取消会回滚第一句已生成文件，且不会调用第二次云端 TTS。
- T1 及 LE-13～16 相关专项回归：`401 passed`；严格 mypy 覆盖 8 个相关源/测试文件为
  `Success: no issues found`；Ruff check/format 全绿。
- 正式功能验收 `tests/integration/test_smart_edit_pipeline_real_media.py` 使用 App 随包
  FFmpeg/FFprobe 生成并探测 320×180、17 fps、2 秒 H.264 文件，再经真实注册表、完整逐帧
  解码和生产 prepare 管线，结果 `1 passed`，可解码区间精确为 `[0, 2000)`。

## T1 实现内审发现与修复

1. 分析写回计划最初只绑定 MaterialId，没有强制等于实际参与匹配的准备后快照；已增加完全
   一致性校验和反例，杜绝写回另一份描述/转写。
2. 本机 probe 等路径异常最初可能留在 Python `__context__`；已改成离开异常处理块后生成固定
   拒绝，并用含私密中文路径的 `OSError` 验证 cause/context 均为空。
3. 无声视频最初会提前构造可听语音分析工厂；已改成传入真正惰性下漏斗，`has_audio=false`
   时构造次数严格为 0。
4. 解码成功最初直接把容器 duration 当可用终点；已改为 FFmpeg 实际 `out_time_us`，短解码
   反例从错误 `[0, 4000)` 收紧为 `[0, 400)`。
5. 旁白登记最初没有单文件字节上限，也没有强制登记音频就是草稿实际引用音频；现已锁到
   `MAX_VOICEOVER_BYTES`，并校验唯一 sequence、MaterialId 和草稿引用顺序。
6. 提交级逐文件 Review 发现第一份素材调用视觉模型时，后续待理解素材可能还没有完成抽帧；
   已改为所有素材先完成 probe、解码和受控抽帧，再允许第一次模型调用，并加入双素材顺序反例。
7. 补齐图片素材专项路径：图片不进入视频解码或语音分析，用 1 ms 仅作为模型结果校验尺度，
   写回前丢弃该合成时长和镜头边界，Material 仍保持 `duration=None`、空镜头边界。

## T2 GREEN 与功能验收证据

- Worker bootstrap 只接受锁定百炼地址、三种在册模型和受约束 API key；智能剪辑 start、cancel、
  progress、prepared、commit、abort 与固定终态复用同一 HMAC 通道，单操作槽拒绝跨任务、乱序、
  重复终态和未知字段。
- 每个 job 只读 App 预建的 0700 私有目录，生产 pipeline 直接装配 LE-13～16 公开边界；生成结果
  与旁白先留在 staging，prepared 只发布路径无关 SHA-256。commit 前重新核对结果文档与每个旁白
  的 containment、类型、字节数和摘要，再一次性移动并原子登记；abort、取消、断连和 120 秒
  commit 超时均清理 request、result、workspace 和暂存映射。
- `MaterialPathRegistry.register_many` 在所有标识与文件通过校验后只替换一次 durable document；
  校验、替换或回滚任一步失败都不会暴露部分批次。异常、repr、stdout/stderr 只保留固定闭集，
  API key、prompt、转写、MaterialId、主机路径、模型请求 ID 和 traceback 均不越过私有边界。
- backend 本地编辑/素材/智能生成相关专项最终为 `769 passed`；Worker 网关、冻结准备和 motion
  workspace 兼容性脚本为 `202 tests OK (skipped=1)`；另有 motion entry/旁白/生成管线兼容回归
  `107 passed`。17 个变更 Python 文件通过 Ruff format，生产/测试关键面 Ruff check 全绿，8 个
  新增或核心变更源/测试文件严格 mypy 为 `Success: no issues found`。
- 真实 macOS arm64 冻结候选出厂审计为 `2139 files / 373334596 bytes / 116 dependencies /`
  `Python 3.11.15 / startup 12.952s`（`du` 361 MiB）；候选自身 `--probe`、
  `--probe-smart-edit-runtime` 和 `--probe-dependency local-editing-runtime` 全部返回 ready，真实加载
  NumPy 2.4.4、ONNX Runtime 1.23.2、随包 Silero 模型及许可证，不以源码环境冒充冻结验收。

## T2 实现内审发现与修复

1. 首轮逐文件审查发现普通本地渲染的兜底失败分支在接智能线程时被误删；已恢复固定
   `render_failed` 终态并复验原有本地剪辑回归。
2. job root 与 generated-materials 的父链最初可能经符号链接逃逸；已对真实路径、非 symlink、
   私有权限和 containment 逐层复核，并加入 job/generated root 反例。
3. 旁白摘要读取异常最初可能被当作校验通过；已改为默认无效，并用不可读摘要注入验证固定
   `commit_failed` 且异常链为空。
4. 注册表失败且 staging 回移也失败时，durable 音频最初可能残留；现会删除该 job 的 durable
   目录，并由双故障测试断言没有未登记文件。
5. 源码测试已绿但冻结 spec 最初没有 NumPy、ONNX Runtime、Silero 模型、许可证和百炼目录；
   已全部写入锁定依赖、spec、cache key 和候选自身运行时探测。
6. 首次真实构建发现 NumPy 2.5.1 不支持 Worker 的 Python 3.11，随后实测锁到 2.4.4；新增
   ONNX 依赖后安装分发数由 114 变成 116，也由真实 inventory 驱动更新，而非放宽审计。
7. smart worker 只为 workspace 误导入了完整浏览器动效 agent，冻结候选因此报
   `local-editing-runtime(MotionAuthoringRejected)`；已抽出轻量共享 workspace、把包入口改成惰性
   公开导出，并加冷启动门禁断言 smart import 不加载重型 agent。
8. 第二轮 Review 发现 prepared 后的非法旧 `worker.cancel` 会在严格协议拒绝后降级成 WebUI
   `worker.cancelled` 假成功；捕获性测试先红，现只有协议空闲时才允许 legacy fallback。
9. 第二轮 Review 还发现 prepared 后若 `result.json` 被替换，commit 只核对旁白仍会成功；现于
   移动和登记前重新核对私有结果文件的普通文件类型、目录边界、大小和 prepared SHA-256。

## T3 RED 目标

1. Control Plane 只接受路径无关、schema 严格且与当前 MaterialId/content digest 绑定的分析写回；
   AI 结果不得覆盖人工描述，过期素材快照、未知字段、跨项目 ID 和不完整语音事实必须拒绝。
2. 新生成旁白以调用方预分配 MaterialId、摘要、真实时长和受约束媒体事实批量登记；分析更新、
   旁白登记与生成结果确认必须位于一个仓储事务，任一冲突不得留下部分写入。
3. 内存仓储与 PostgreSQL 仓储使用同一乐观并发语义；并发素材变更、重复请求和失败重试可验，
   OpenAPI/DTO 与领域闭集同步，API 响应、日志和异常不得出现 Worker 路径或私有文案。
4. 首个 T3 聚焦测试必须精确失败于分析写回/旁白批量登记的 Control Plane 命令或端口尚不存在，
   确认捕获力后才创建实现。
