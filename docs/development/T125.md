### 1.1 为什么单靠 `prepare_startup_gate` 不够——这一族的 ④ 不能改端口

`prepare_startup_gate` 只覆盖 ①②③。④ 才是这一族真正的分界点：

```rust
// frontend/src-tauri/src/control_plane.rs:481-489
#[cfg(feature = "control-plane-e2e")]
fn configured_local_control_plane_origin() -> &'static str {
    option_env!("AUTOMATION_TOOL_CONTROL_PLANE_E2E_ORIGIN")
        .unwrap_or(DEFAULT_LOCAL_CONTROL_PLANE_ORIGIN)
}

#[cfg(not(feature = "control-plane-e2e"))]
const fn configured_local_control_plane_origin() -> &'static str {
    DEFAULT_LOCAL_CONTROL_PLANE_ORIGIN            // http://127.0.0.1:8765
}
```

**能配置的只有 `control-plane-e2e`。** 这六个全部用 `--features desktop-e2e` 构建，编译进去的
就是产品默认原点 `http://127.0.0.1:8765`——它们**没法**像 `control-plane-e2e` 那 32 个驱动一样
派生一个空闲端口，只能自己占住产品那一个。所以本任务加的是一个 harness，而不是往六个驱动里各
抄一段 `prepare_startup_gate`。

**没有改成 `--features control-plane-e2e` 绕开它**：`app_update_installation.rs:99,109,118,168`
四处以 `not(feature = "control-plane-e2e")` 分支，换 feature 会换掉更新安装这一族**正在被测的
那段代码**。

**六个都不需要数据库，这是本任务最省时间的一条判定。** 门禁对 Control Plane 只发两个请求：
`/api/v1/health` 与 `/api/v1/version`。`api/system.py:62-71` 里 `/health` 在
`database is None` 时**直接跳过连接探测**，`/version` 根本不碰持久化。所以给这六个套
`video_studio_startup_harness`（Docker PostgreSQL + 生产 Alembic 链 + 生产 uvicorn）是
**给一个什么都不存的族每条加几分钟**。新 harness 用生产的 `create_app(database=None)`——
路由、响应模型、脱敏中间件都是生产的那一套，`database=None` 是 `create_app` 的一等参数
（H8-20 自己的更新源服务器早就这么建），不是桩。

这条判定由 `check_the_health_control_plane_answers_the_product_contract` 钉住：它真起
`create_app(database=None)` 并断言 `/health` 与 `/version` 的完整契约，因为 App 的
`parse_system_version_response`（`control_plane.rs:583-600`）会逐字段比对两个响应，一个
返回 `200 {}` 的桩能骗过朴素探针、照样让门禁关着。

### 1.3 VF-05 是个特例，值得单说

`model-service.spec.ts:8-19` 的 `openSettings()` **本来就容忍被挡页**：找不到工作台标题时
它去点「打开本地修复工具」，而 `App.tsx:97-108` 的 `repairTools` 里正好有
`ModelServiceSettings`。也就是说这个驱动在坏掉的 App 上会「通过」。

那是严格更弱的路径：它证明的是**装坏了的用户**能在修复面板里配密钥，对**每个正常安装实际
使用的设置页**只字未证。接上 harness 之后被测的是工作台那条路径。这不是 T125 造成的行为变化，
是把它测的东西从弱路径换回正路径。

## 4. 真实边界

### 4.1 两个打包更新驱动没有接进来，理由写在门禁里

`run_h8_22_macos_package_acceptance.py` 与 `run_h8_22_windows_package_acceptance.py` 需要的
四样和另外四个**完全相同**，卡点不在驱动，在**打包**：

* 它们跑的是真正的 `.app`/`.exe` 包，资源目录在包内（`release_assembly.py:190` 的
  `Contents/Resources`），不是 `target/debug`；
* 更关键的是**更新器会在跑到一半时把整个 `.app` 换掉**（`optional-install` 场景之后是
  `verify-installed`，spec 第一行仍要求工作台）。换上去的那个包来自 `tauri build` 期间
  `createUpdaterArtifacts` 产出的 tarball。所以内置浏览器与签名 Executor 必须
  **进 `bundle.resources`**，而 `tauri.update-macos-package-e2e.conf.json` 现在只有
  `{"active": true, "targets": [...]}`；
* 构建后往安装副本里塞一份**会制造一个假绿**：第一个场景过，`verify-installed` 在更新后的包上
  挂掉。这正是本任务要终结的失效模式，所以没有那么做；
* 成本也不小：三次构建各多 ~340 MB 的复制与 tar；
* 而且**这次验不了**：macOS 那个要挂载 DMG（本轮明确不做），Windows 那个需要 Windows 机。

因此把它们登记成门禁里的 `REVIEWED_UNWIRED_DRIVERS`，每条写明具体阻塞点。门禁
`check_each_exemption_is_a_current_driver_carrying_a_written_blocker` 保证：豁免必须指向
真实存在的驱动、必须带够长的理由、**并且一旦它其实已经满足 harness 就立刻报错要求删豁免**。
这样这一层不会「整体绿」而其中两个仍然死在第一行。
