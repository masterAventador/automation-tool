日期：2026-07-27
分支：`cancel-confirm`（基点 `9c8a1fb`）

派单已经查实的前提在此确认：取消**确实会停掉渲染**，`workers/motion_composition/worker.mjs`

## 一、①的结论：改。而且它不只是「早了一帧」

**判定：`cancel()` 不应写终态，改为写「正在取消」这个新的非终态；终态 `Cancelled` 由那个
持有浏览器和编码器的执行线程写。**

派单给的三个选项里，选的是第三个（把「已请求取消」和「已确认取消」在状态上分开）。三条依据，
按分量从重到轻：

### 依据 1：这不是一个只有一帧的误差，它会**弄丢用户的成片**（有复现测试）

`advance()` 开头就有这一段：快照已经是终态时**直接返回、不再写入**。而 `cancel()` 原本立刻把
快照写成终态 `Cancelled`。于是渲染线程后面那句

```rust
let artifact = import_rendered_output(...)?;
advance(..., Succeeded, 100, Some(&artifact), None)?;   // ← 被静默丢弃
```

在竞态里会变成：FFmpeg 已经成功退出 → 用户在这一瞬按下取消 → 快照进终态 →
`import_rendered_output` **照常把 MP4 导入制品库** → `advance(Succeeded, …)` 命中终态提前返回，
**返回 Ok，没有任何报错**。

结果是磁盘上多了一个成片，而快照的 `artifactId` 是 `null`。成片页的取件方式是
`motionJobs.filter((job) => job.artifactId !== null)`——所以这个文件**列不出来、播不了、删不掉**，
但一直占着工作区配额。用户按了取消，得到的是「已取消」+ 一个他永远看不见的成片。

这正是 `CLAUDE.md` §4.4 那句话要挡的东西：宣称副作用已经停止，而它根本没停。它在这里不是抽象
原则，是一条会吞掉产物的真路径。复现见
`tests/motion_video_studio.rs::a_film_that_finished_before_the_executor_saw_the_cancel_is_not_lost`，
RED 输出在第三节。

### 依据 2：同一个仓库里的另一半已经是这么做的

`material_video_studio::cancel()`（`frontend/src-tauri/src/material_video_studio.rs:333`）
**只写标记文件，不碰快照**；终态来自执行器写下的 observation，由
`reconcile_active_observation` 收口。也就是说智能素材成片那条链路早就遵守 §4.4，
只有品牌动效这条没有。两条链路对同一件事有两套规矩，本身就是缺陷。

`tests/publish_workspace.rs::cancelling_after_the_click_is_refused_because_it_would_be_a_lie`
是同一条原则的第三处落地。

### 依据 3：为什么是新状态，而不是「命令什么都不写、界面自己记」

派单特意提醒别把体验做坏。`VideoStudio.tsx` 里 `act()` 调用完命令会立刻 `refresh()`，
之后每 2 秒轮询一次。如果命令什么都不写，用户按下取消后界面最长约 2 秒毫无变化——正是要避免的。

那能不能在 React 里记一个「我已经按过了」？**不能，而且理由就写在这个文件里**：studio 页面在
用户点击侧边栏其它入口时会被卸载（`VideoStudio.tsx:1286` 的注释解释了他们为此把 run 状态搬出组件
的原因），而一次渲染要几分钟。放在组件里的「正在取消」会在他切走再切回时消失，重启后同样消失，
于是他看到的是「正在合成视频」和一个再次邀请他点击的取消按钮。

`CLAUDE.md` §4.4 第一句就是「任务快照是刷新和重启恢复的权威来源」。所以「已请求取消」属于快照。

**代价与新增约束**：

- `MotionRenderJobStatus` 多一个 `Cancelling`（非终态）。App 从未发布，磁盘上不存在旧快照需要迁移；
- 进入 `Cancelling` 之后只允许走向终态。否则一个「命令落在检查之后」的在途阶段会把
  `正在取消` 覆写回 `正在合成视频`，并把取消按钮重新放回去；
- 重复按取消是同一个请求：写标记幂等，状态不变，不报错；
- 已经在 `Cancelling` 却又真的失败了的阶段，收口成 `Cancelled` 而不是 `制作失败`——用户已经
  放弃这次运行了，给他一个「制作失败，请重试」的建议是答非所问。

## 二、②的做法：契约单一来源，且**两种语言都不留字面量**

原状：`.automation-tool-cancel` 在 Rust（`MOTION_CANCEL_FILE`）和 worker.mjs
（`SANDBOX_CANCEL_FILE`）各写一份，互不相干。改错一处不会有任何东西报错。

参考 `contracts/video/motion-authoring-refusal.v1.json`（Python 与 Rust 同读一份）和
`contracts/video/motion-authoring-model-call.v1.json`（Python import 时读、TypeScript 直接 import
同一份）之后，这里**没有**照抄「两端各自读同一个 JSON」，因为读不到：worker 的分发包由
`scripts/build_motion_video_worker_candidate.py` 产出，内容被
`contracts/quality/release-package-resources.v1.json` 钉死为 `runtime/node` + `app/worker.mjs`
两项。让 worker 运行时去读 `contracts/` 就得把这份 JSON 也塞进包、进摘要清单、进
`prepare_video_runtime.py`、进各条验收脚本——而
`motion-authoring-model-call.test.mjs` 里那条「packaged Executor carries the contract it reads
at startup」测试的存在，正是因为这种事在本仓库已经翻过一次车。

**采用的是更强的形式：名字在运行时只存在一份，并且是传过去的。**
App 从 `contracts/video/motion-render-cancel-marker.v1.json` 读出名字，随渲染请求以
`cancelMarker` 字段发给 Worker——和这个请求里**已经**在传的 `entryHtml` 走同一条路（Worker 本来
就没有入口文件名的常量，它用调用方给的）。Worker 这边删掉常量，watch 的就是被告知的那个。
两份必须相等的副本，被换成了一个会传递的值：**Worker 没有自己的意见，也就无从与谁不一致。**

派单要求「改错就加载不了」，两个方向都是关闭的：

- Worker 侧 `validSandboxSpec` 用的是 `hasExactKeys`。不认识 `cancelMarker` 的 Worker 会
  **拒绝整次渲染**，而不是渲染一个取消不掉的任务；
- App 侧 `cancel_marker_file_name()` 在**构造渲染请求之前**解析契约（`lib.rs:823`），
  契约损坏或键改名 ⇒ 渲染起不来，而不是起一个无视取消按钮的渲染。

另外收紧了一处**新发现的边界**：`RenderJobSubmission.to_sandbox_spec`（编排侧）刻意不带这个字段，
并加了断言钉住。取消是 App 对自己子进程的控制通道，而那份 spec 由模型输出构造——让它来指定
「哪个文件能停掉渲染」，等于把决定取消按钮是否有效的那一个输入交出去。

## 四、「改一处会不会带动另一处」——实测三次变异

派单要求②的测试能真的抓住不一致，做了三次变异实测：

| 变异 | 结果 |
| --- | --- |
| 把 Worker 的 `cancelMarker` 从 `hasExactKeys` 里删掉、去掉校验 | 真 Worker 驱动 `scripts/test_motion_video_render_sandbox.py` **失败退出 1**（缺字段的 spec 被接受了，事件流随即错位）。断言确实咬得住 |
| 契约 `markerFileName` 改成 `.automation-tool-halt-render` | Rust 测试 **仍然通过**（写出的就是新名字），真 Worker 驱动 **仍然通过**；全仓 grep 旧名字 **0 命中**。即：改这一个值，两端一起跟着变，没有第二处要改 |
| 契约键改名 `markerFileName` → `markerFile`（模拟契约损坏） | Rust 测试 **失败**（`cancel_marker_file_name()` 返回 installation-damaged），而不是悄悄用了某个默认值 |

三次变异后均已还原，还原后重跑全绿。第一次变异中断留下的临时 RenderJob 目录导致下一次驱动
误报，已清理并复跑确认（`executed checks: 9`, exit 0）。

## 九、留给下一轮的一处（本次**未**做，避免夹带）

`run_motion_render_job` 里 `encode_motion_video` 的取消检查是 50ms 轮询，而渲染阶段的取消粒度是
「一帧」。两者都够快，本次没有改动，但如果以后单帧耗时显著变长（更大画布、更重的合成），
「按下取消到 Worker 真的停下」这段时间会变长——而现在这段时间是**有状态可看的**（`正在取消`），
不再是一句谎称已完成的终态。真要缩短，应作为独立任务处理，并且要有自己的 RED。
