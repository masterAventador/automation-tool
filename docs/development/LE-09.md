## 给 LE-20 的交接点（本节是本文件最重要的部分）

**今天没有任何东西把字体放进执行器包。** 执行器 spec 一个字体都不装，
所以冻结形态下 `resolve_font_file()` 必然解析到不存在的文件并 fail closed。
这不是缺陷，是本任务与 LE-20 的边界——但它正是 T108 事故与 `CLAUDE.md §9.2` 的形状
（验收全绿、用户拿到的包缺东西），所以必须留下可被门禁消费的钩子，而不是一句口头约定。

钩子是一个函数：

```python
from automation_tool.executor.captions.fonts import (
    REGISTERED_CAPTION_FONTS,
    packaged_relative_path,
)

for font_key in REGISTERED_CAPTION_FONTS:
    expected = package_root / packaged_relative_path(font_key)
    assert expected.is_file(), f"包内缺少字幕字体：{expected}"
```

LE-20 的出厂门禁就是这个平凡循环，**不需要知道 bundle 是什么、也不需要重新推导布局**。
这一点是有意的：布局在代码里只被陈述一次（`_packaged_bundle_directory`），
`resolve_font_file()` 与 `packaged_relative_path()` 都从它派生，并由
`test_a_frozen_run_resolves_exactly_the_packaged_relative_path` 把两者钉在一起。
如果 LE-20 在门禁里另写一份路径拼接，就又出现两处事实——那正是 T1 审查判出来
并已经修掉的那个问题。

当前布局（`fonts/<bundle>/<packagedName>`，相对包根）：

```text
fonts/material-video-worker/NotoSansCJKsc-Bold.ttf
fonts/material-video-worker/NotoSansCJKsc-Regular.ttf
fonts/motion-catalog-overlay/big-shoulders-display-latin.woff2
```

**为什么保留 `<bundle>/` 这一层**：`packagedName` 在权利登记里只在 bundle 内唯一，
不是全局唯一；更重要的是保留这一层之后，冻结态与源码态用的是**同一个查找形状**
（bundle → 根 → 文件名），差别只在根的取值。拍平会让冻结态变成「根 → 文件名」、
源码态仍是「bundle → 根 → 文件名」，两种形态的查找形状不同，那就不是配置值差异
而是代码路径分叉，属于单一构建路径规范禁止的形态。

LE-20 还需要注意：`material-video-worker` 那两个面**不在仓库里**，
由 `scripts/subtitle_font_assets.py::ensure_subtitle_fonts()` 构建期按 SHA-256 获取，
装配时要从构建缓存取；`motion-catalog-overlay` 那个面在仓库里，直接拷。
判别式见下一节。

## 字体现状与设计文档的偏差（已由 `cf5ae10` 更正进设计 §6.0）

设计文档原 §6.1 说「现有中文字体只有 Noto Sans SC 一个、可变字体、woff2，
在 `offline-motion-dependencies.v1.json` 里，覆盖到扩展 A，扩展 B 是豆腐块」。
在 `e53ef70` 上逐项核对，四点都与本仓库不符：

| 设计原文 | 实测 |
| --- | --- |
| 锁定 23 个字体家族 | **18 个** |
| 本机落地 143 个 woff2 分片 | 契约声明 **52 个**，合计 **1.0 MB**；`.local/offline-motion-deps/` 目录不存在 |
| 其中仅 Noto Sans SC 支持中文 | **18 个家族全是拉丁**，`keptFontSubsets` 是 `["latin","latin-ext"]`；`git grep -i "noto.sans.sc"`（排除 vendor）只命中文档与测试，无任何契约或生产代码 |

旁证：52 个 woff2 合计 1.0 MB，而一个覆盖 3 万汉字的字体单文件就是 10 MB 量级，

`notofonts/noto-cjk` 的 `Sans2.004`，构建期取到
`~/Library/Caches/automation-tool-build/subtitle-fonts/`。来龙去脉见
`docs/development/FIX-open-source-font-replacement.md`。

**这对 LE-20 有直接影响**：设计 §6.2 的候选表建立在「需要 Plangothic 补扩展 B～J」之上，
而实测现有字体已覆盖扩展 B。LE-20 的选型需要基于这个事实重估，本任务不替它决定。

## 验收判据：为什么「PNG 非空」不算数（已更正进台账 LE-09 行）

台账原文要求「产出 PNG 并断言像素尺寸与非空」。实测证明非空断言对豆腐块零捕捉力：

```text
Noto Sans CJK SC 渲染 U+1F600（不在 cmap）:
    nonzero_px=1226，与该字体 .notdef 位图逐字节相同   ← 画出实心方框
BeVietnamPro     渲染 U+4E2D（不在 cmap）:
    nonzero_px=0                                      ← 什么都不画
```

**豆腐块有墨、缺字无墨，非空断言两头都抓不住。** 正确判据是与 `.notdef` 位图差分
（`font.getmask(chr(0x10FFFF))`，U+10FFFF 保证不在任何 cmap 中）。
这也是上游 `vendor/moneyprinterturbo/app/services/video.py::subtitle_font_supports_text`
用的办法。T5 的验收按三层断言：像素尺寸 + 有墨 + 与 `.notdef` 差分。

## 缺字且整条链都没有 → fail closed

抛异常，带**码位**（`U+1F600`）不带原文（`CLAUDE.md §7`：页面原文不得进普通日志），
不留半成品文件。不画替代符号，理由三条：

1. 本项目已就同类问题决策过并写进文档——`FIX-open-source-font-replacement.md:216`：
   「不回退到系统字体，也不跳过字幕——那两条路都会产出『看起来完成、中文全是方框』的视频，
   正是要防的静默失败。」画替代符号是同一类静默失败的第三条路；
2. 上一节的实测证明画替代符号不可检测：一旦允许 `.notdef` 画出去，
   下游所有断言（PNG 非空、尺寸正确、ffprobe 帧数正确）**全部照常通过**，
   而用户拿到一片方框；
3. 失败在这一层可被精确定位，上层 LE-16/LE-19 能据此给出可行动提示。

代价如实登记：用户在字幕里打一个 emoji 会让整次渲染失败。缓解归 LE-20（扩覆盖面），
调用层也可选择先做字符清洗。

### 一处注释错误，实测后改掉

原注释写「`\Z` 而不是 `$`，因为 `$` 会放过 `noto-sans-cjk-sc-bold\n`」。实测：

```text
with fullmatch:  $ -> False   \Z -> False
with match:      $ -> True    \Z -> False
```

**在 `fullmatch` 下两者等价**，原注释陈述的机制是错的。真正的理由是
`\Z` 让守卫不依赖调用动词（正是上游 `e53ef70` 提交信息说的「守卫不再依赖调用动词」）。
注释已按实测改写。

这条是变异自证时发现的：`\Z → $` 变异体**不是**被结尾换行用例杀掉的。
原因是那条换行用例走 `fullmatch`，而 `fullmatch` 下两个锚点等价，**任何 `fullmatch`
用例都不可能覆盖这个差异**。当时唯一杀掉它的是「与上游模式逐字相等」那条用例。

后续补强（`975a8bd`）：只靠字面量比对是用一个常量测另一个常量——它会红，
但红的信息是「有人改了这个字符串」，不是「守卫失效了」。因此增加一条直接陈述
`\Z` 所提供属性的用例，故意用 `match` 而非 `fullmatch` 调用：

```python
assert FONT_KEY_PATTERN.match("noto\n") is None
```

**现在 `\Z → $` 由两条用例开火**（实测 2 failed / 49 passed）：
`test_the_pattern_matches_the_control_plane_contract` 报告字符串被改，
`test_the_guard_holds_even_when_called_with_match` 报告守卫失效。两条报告的不是同一件事，
都保留。结尾换行用例仍然不开火，理由如上——这一点没有变。

### T3 审查补测（`db425bb`）

RED：[1] `TypeError: 'NoneType' object is not iterable`（从生产入口 `glyph_coverage()` 触发）；
[3] 6 failed，缺 `CaptionTextRejected`。
GREEN：89 passed；本包覆盖率 **100%（116 stmts / 38 branch / 0 partial）**。

三条 Important，两条是**我那张边界形态表漏了的形态**（已补进下表第 8、9 行），
一条是用例覆盖不到位。全部先本地复现再修。

- **[1] `getBestCmap()` 返回 `None` 时抛未处理的 `TypeError`。** 复现：把合成面的唯一子表
  改成 `(3,0)` symbol 编码，`getBestCmap()` 返回 `None`，`frozenset(None)` 直接崩。
  **这正是那四条 except 存在的理由所在的形状**——「覆盖判定深处冒出未处理异常，
  而不是一条字体错误」。走 TDD：先看到 `TypeError`，加 `None` 检查后变成
  `CaptionFontUnavailable`。用例带前提断言（先断言 fontTools 真的应答 `None`），
  否则夹具没造出该状态时它也会绿；
- **[2] `.notdef` 往返用例只钉住 format 4，而 docstring 声称两条路都钉。** 复现：原夹具
  `inked=[ord("A")]` 是纯 BMP，实测产出子表 `[4, 4]`，**format 12 根本没跑到**。
  而 format 12 正是承载随包 CJK 面全部 2590 个 astral 码位的那张表——只在它上面发生的回归
  会让 astral 字符被判为覆盖、实际画出豆腐块，恰是整个设计要防的那件事。
  改夹具为 `inked=[ord("A"), 0x20BB7]` 产出 `[4, 4, 12]`，并加一条前提断言
  `formats == {4, 12}` 保证这条用例不会悄悄退回只测 format 4。
  注意 astral 的 `.notdef` 只能塞进 format 12 子表，塞进 format 4 会 `OverflowError`；
- **[3] 换行符不在任一面的覆盖集内，而「换行」正是 LE-09 自己的交付范围。** 见下表第 9 行。
  这不是已提交代码的缺陷（今天没有生产调用方），是**同一任务内两个子任务之间的接口前置条件没定**。
  决定：**在这一层强制，而不是只写进 docstring**——理由正是审查对第 5 行的批评，
  「只写假设而没有任何地方强制」等于没有。若 T4 的换行实现把整段多行文本交给
  `segment_runs`，现在会立刻得到一条说清楚「先切行」的错误，而不是一条指向字体的错误。

### cmap 判定的边界形态：想到的全部列出

并行线的教训是「样本选得不够坏，实测出来的结论就是错的」。下面是本任务想到的
全部形态，逐条标注处理方式；未处理的写明原因。

| # | 形态 | 实际语义 | 处理 |
| --- | --- | --- | --- |
| 1 | **映射存在但字形无轮廓**（空格） | **算覆盖** | 已测。这是「看起来不覆盖、实际覆盖」的那一类：若按有没有墨判定，**每个空格都会被判缺字**并压进 fallback 链，全是空格的字幕还会 fail closed。实测两个真实面都把 U+0020 映到零轮廓字形 |
| 2 | **基本平面以外的码位**（>U+FFFF） | 覆盖，但需 format 12 | 已测。format 4 编不下астral 码位；实测真实 Noto CJK 有 **2590** 个 astral 码位，`𠮷`（U+20BB7）映到真实字形 |
| 3 | **码位映射到 `.notdef`** | **无法存在** | 已钉。format 4 里「映射到字形 0」与「没有映射」是同一批字节，fontTools 在 format 4 与 12 两条路上都在写出时丢弃它。因此不加过滤分支——那会是不可达死码；改为一条往返用例钉住这个假设 |
| 4 | **多个 cmap 子表互相矛盾** | `getBestCmap()` 只取其一 | 已实测未单测。Noto CJK 有 **6 个**子表（format 4/12/14/6 跨三个 platform），Big Shoulders 有 2 个；两者 **union == best、冲突 0、被 `getBestCmap()` 丢掉的码位 0**。**留给 T5 在真实面上钉住这个等式**，比合成一个现实中不存在的矛盾字体更有意义 |
| 5 | **format 14（Unicode 变体序列）** | `getBestCmap()` 不返回 | **已知限制，不处理**。Noto CJK 带 format 14。带变体选择符的序列不算覆盖，含它的字幕 fail closed。**触发面比原先写的大得多**：原记「首期字幕是纯文本」——那只是对输入的假设，没有任何地方强制。实测 `U+2764`（❤ 基码位）与 `U+FE0F` 双双不覆盖，也就是**用户从手机键盘粘一个爱心，整条字幕就被拒**。行为仍是有意的（静默画错字形更糟），但缓解归 LE-20 扩覆盖面，或调用层先做字符清洗 |
| 6 | **可变字体的实例化差异** | cmap 不随实例变化 | 已实测无风险。Big Shoulders 是可变字体，覆盖集与 `wght` 无关；实例化只影响字形轮廓，不影响 cmap |
| 7 | **cmap 指向字形表里不存在的名字** | 畸形字体 | 不单独测。fontTools 读取时抛错，落进同一个 `CaptionFontUnavailable` 处理器，已由 TTLibError / KeyError 两条用例覆盖该处理器 |
| 8 | **有 cmap 表但无 Unicode 子表** | `getBestCmap()` 返回 **`None`** | **T3 审查判出，我这张表原先漏了**。它与第 7 行「没有 cmap 表」不同：这一种能解析、能应答，**应答的是 `None`**，而 `frozenset(None)` 抛 `TypeError`——不在四条 except 里，是唯一一种崩溃而不是给出明确错误的形态。已修并测：`(3,0)` symbol 面（图标字体的常见形态），且**随包 Noto CJK 自己就带一个非 Unicode 的 `(1,25)` 子表**。今天注册表封闭在 3 个面所以不可达，但**LE-20 的交付内容就是扩字体**，新登记一个图标面即触发 |
| 9 | **控制字符（C0 与 DEL）** | 任何面都不覆盖 | **T3 审查判出**。`\n`、`\t` 是排版指令不是字形。原先它们会以 `no packaged face draws U+000A` 返回——**把调用方没切行的问题说成字体问题**。已改为 `CaptionTextRejected` 并给出准确消息。**选择拒绝而不是跳过**：跳过会把 `"a\nb"` 渲染成 `"ab"`，一条错的字幕却仍然出图、尺寸正确、下游断言全过，正是本模块要防的静默失败。**两个区间的四个端点都有用例**：C0 的 `U+0000`/`U+001F`、C1 的 `U+0080`/`U+009F` 各有拒绝用例，越界一格的 `U+0020` 与 `U+00A0` 各有专属的「画得出来」用例（三个随包面都覆盖这两个字符）。把范围写成 `range(0x00, 0x21)` 或 `range(0x80, 0xA1)` 会分别吞掉空格与 NBSP，两条变异各自只被对应那条用例杀掉 |

## 后续 task 的固定动作：新增区间或枚举，必须有两端端点用例

**同一个形态在 2026-07-29 一天内、跨两条工作线出现了三次。三次的作者都报了「变异全杀」，
三次都属实——问题不在杀伤率，在于变异集本身漏掉了端点：**

| # | 新增的边界 | 存活的变异 | 为什么没人抓到 |
| --- | --- | --- | --- |
| 1 | 本线 C0 区间 `range(0x00, 0x20)` | `range(0x00, 0x1F)` | 没有 `U+001F` 端点用例 |
| 2 | 另一条线 `font_px > output.height` | `height → width` | 拒绝用例用的是**正方形**画幅，两个字段没有区分度 |
| 3 | 本线 C1 区间 `range(0x80, 0xA0)` | `range(0x80, 0xA1)` | 上端点无人守；97 条用例一条都不红，而它会拒掉三个面都覆盖的 NBSP |

**因此从本轮起，本线每新增一个区间、枚举或维度，必须同时交付：**

1. **两端端点各一条用例**——区间内的最小值与最大值都要被断言落在区间内
   （C1 的 `U+0080` 与 `U+009F`）；
2. **一条「越界一格」的对照用例**——区间外紧邻的那个值要被断言落在区间外，
   且这个值必须是**真的会被用到**的东西（`U+0020` 之于 C0、`U+00A0` 之于 C1，
   两者都是随包面确实覆盖、字幕里确实出现的字符）；
3. **三个变异实跑**：上界 +1、上界 −1、下界 +1，各自被**对的那条**用例杀掉，
   而不是被旁条误伤。多字段的维度（宽/高、起/止）另加一条「字段互换」变异，
   并且夹具里两个字段的取值**必须不同**——正方形画幅让互换变异恒等于原式。

**判据不是「变异全杀」，是变异集本身覆盖到了每个端点。** 行覆盖对这一类完全无感：
`codepoint in UNDRAWABLE_CODEPOINTS` 只有一行、一个分支，端点写错写对都是同一行同一支，
所以 100% 覆盖率与端点是否被验证之间没有任何关系（`CLAUDE.md §8.3` 的同族问题）。
