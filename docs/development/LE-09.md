## 给 LE-20 的交接点（本节是本文件最重要的部分）

**今天没有任何东西把字体放进执行器包。** 执行器 spec 一个字体都不装，
所以冻结形态下 `resolve_font_file()` 必然解析到不存在的文件并 fail closed
（**这句只对「文件缺失」成立**——文件在但损坏或不可读走的是另一条路，
`de8d1c1` 上那条路是 fail **open**，见修复轮 C1；现已堵死）。
这不是缺陷，是本任务与 LE-20 的边界——但它正是 T108 事故与 `CLAUDE.md §9.2` 的形状
（验收全绿、用户拿到的包缺东西），所以必须留下可被门禁消费的钩子，而不是一句口头约定。

钩子是一个函数：

```python
from automation_tool.executor.captions.fonts import (
    REGISTERED_CAPTION_FONTS,
    packaged_relative_path,
)

for font_key in REGISTERED_CAPTION_FONTS:
    expected = package_root / packaged_relative_path(font_key)
    assert expected.is_file(), f"包内缺少字幕字体：{expected}"
```

LE-20 的出厂门禁就是这个平凡循环，**不需要知道 bundle 是什么、也不需要重新推导布局**。
这一点是有意的：布局在代码里只被陈述一次（`_packaged_bundle_directory`），
`resolve_font_file()` 与 `packaged_relative_path()` 都从它派生，并由
`test_a_frozen_run_resolves_exactly_the_packaged_relative_path` 把两者钉在一起。
如果 LE-20 在门禁里另写一份路径拼接，就又出现两处事实——那正是 T1 审查判出来
并已经修掉的那个问题。

当前布局（`fonts/<bundle>/<packagedName>`，相对包根）：

```text
fonts/material-video-worker/NotoSansCJKsc-Bold.ttf
fonts/material-video-worker/NotoSansCJKsc-Regular.ttf
fonts/motion-catalog-overlay/big-shoulders-display-latin.woff2
```

**为什么保留 `<bundle>/` 这一层**：`packagedName` 在权利登记里只在 bundle 内唯一，
不是全局唯一；更重要的是保留这一层之后，冻结态与源码态用的是**同一个查找形状**
（bundle → 根 → 文件名），差别只在根的取值。拍平会让冻结态变成「根 → 文件名」、
源码态仍是「bundle → 根 → 文件名」，两种形态的查找形状不同，那就不是配置值差异
而是代码路径分叉，属于单一构建路径规范禁止的形态。

LE-20 还需要注意：`material-video-worker` 那两个面**不在仓库里**，
由 `scripts/subtitle_font_assets.py::ensure_subtitle_fonts()` 构建期按 SHA-256 获取，
装配时要从构建缓存取；`motion-catalog-overlay` 那个面在仓库里，直接拷。
判别式见下一节。

**三条只有加字体时才会踩到的约束（T4a 修复轮登记）：**

1. **「装进去了」和「装对了」是两回事。** 上面那个循环只断言文件在包里。文件在、
   但字节损坏或权限不可读时，`ImageFont.truetype` 会拿 basename 去系统字体目录里搜，
   把用户磁盘上的同名字体画进视频——这条已在 `_load_face` 里堵死（比对 `face.path`），
   但**门禁那边最好也顺手打开一次**：`packaged_relative_path()` 只保证路径，
   打得开是另一件事。而权利清单和字体注册表是同一份，所以画错面 = 印进未授权字体；
2. **字重实例名是逐字节匹配。** 可变面必须带一个名字**恰好**是 `Bold` 的命名实例
   （`render.PINNED_WEIGHT_INSTANCE`）。命名成 `bold`、`SemiBold`、`Bold Italic`
   的面会被直接拒绝——fail closed 且消息说得清，但你会在加字体的当天撞上它。
   今天在册的那个可变面（Big Shoulders Display）带 9 个实例，`Bold` 在里面；
3. **截断的字体现在会被收口成 `CaptionFontUnavailable`**，不再是裸 `AssertionError`。
   部分下载和构建中断都会产生截断文件，而按 SHA-256 取字体这条链路上，
   摘要校验是唯一挡住它的东西——LE-20 装配时不要跳过校验。

## 验收判据：为什么「PNG 非空」不算数（已更正进台账 LE-09 行）

台账原文要求「产出 PNG 并断言像素尺寸与非空」。实测证明非空断言对豆腐块零捕捉力：

```text
Noto Sans CJK SC 渲染 U+1F600（不在 cmap）:
    nonzero_px=1226，与该字体 .notdef 位图逐字节相同   ← 画出实心方框
BeVietnamPro     渲染 U+4E2D（不在 cmap）:
    nonzero_px=0                                      ← 什么都不画
```

**豆腐块有墨、缺字无墨，非空断言两头都抓不住。** 正确判据是与 `.notdef` 位图差分
（`font.getmask(chr(0x10FFFF))`，U+10FFFF 保证不在任何 cmap 中）。
这也是上游 `vendor/moneyprinterturbo/app/services/video.py::subtitle_font_supports_text`
用的办法。T5 的验收按三层断言：像素尺寸 + 有墨 + 与 `.notdef` 差分。
**T5 已落地**，见「真实面上的端到端验收」一节：12 个字形墨块与三面 `.notdef` 比对，相同的 0 个。

### 一处注释错误，实测后改掉

原注释写「`\Z` 而不是 `$`，因为 `$` 会放过 `noto-sans-cjk-sc-bold\n`」。实测：

```text
with fullmatch:  $ -> False   \Z -> False
with match:      $ -> True    \Z -> False
```

**在 `fullmatch` 下两者等价**，原注释陈述的机制是错的。真正的理由是
`\Z` 让守卫不依赖调用动词（正是上游 `e53ef70` 提交信息说的「守卫不再依赖调用动词」）。
注释已按实测改写。

这条是变异自证时发现的：`\Z → $` 变异体**不是**被结尾换行用例杀掉的。
原因是那条换行用例走 `fullmatch`，而 `fullmatch` 下两个锚点等价，**任何 `fullmatch`
用例都不可能覆盖这个差异**。当时唯一杀掉它的是「与上游模式逐字相等」那条用例。

后续补强（`975a8bd`）：只靠字面量比对是用一个常量测另一个常量——它会红，
但红的信息是「有人改了这个字符串」，不是「守卫失效了」。因此增加一条直接陈述
`\Z` 所提供属性的用例，故意用 `match` 而非 `fullmatch` 调用：

```python
assert FONT_KEY_PATTERN.match("noto\n") is None
```

**现在 `\Z → $` 由两条用例开火**（实测 2 failed / 49 passed）：
`test_the_pattern_matches_the_control_plane_contract` 报告字符串被改，
`test_the_guard_holds_even_when_called_with_match` 报告守卫失效。两条报告的不是同一件事，
都保留。结尾换行用例仍然不开火，理由如上——这一点没有变。

### 可变字体：实测推翻了计划的做法，保留了计划的结论

计划 §0.2 写「该 woff2 是可变字体，`wght` 默认 100，PIL 不设轴渲染 Thin，
实现里用 `set_variation_by_axes` 设到可读字重」。逐条实测（Pillow 12.3.0 / FreeType 2.14.3，
`raqm` 未启用）：

| 问题 | 实测结果 |
| --- | --- |
| `big-shoulders-display-latin.woff2` 是可变字体吗 | 是。`fvar` 一根 `wght` 轴，`min/default/max = 100/100/900`，9 个命名实例 Thin…Black |
| 默认落在哪个实例 | **Thin**。`ImageFont.truetype()` 后 `getname()` 给 `('Big Shoulders Display Thin', 'Regular')`，48 px 下 `ABCDEFG` 只有 **663** 个墨点；显式设 Thin 得到同样的 663 |
| `get_variation_names()` 返回什么 | `[b'Thin', b'ExtraLight', b'Light', b'Regular', b'Medium', b'SemiBold', b'Bold', b'ExtraBold', b'Black']` |
| 静态面上问同样的问题 | 三个变体 API（`get_variation_names` / `set_variation_by_name` / `set_variation_by_axes`）在 `NotoSansCJKsc-Bold.ttf` 上一律 `OSError: invalid argument` |
| `set_variation_by_name` 能用吗 | 能。设 Bold 后墨点 663 → **2984**，`getname()` 的样式名变成 `'Bold'` |
| 缺 `libraqm` 有影响吗 | 无。raqm 管的是文字整形，变体轴走 FreeType 的 MM/var，本机 `raqm=False` 下全部正常 |

**结论：计划的判断（默认 Thin，需要修正）成立，计划的做法（`set_variation_by_axes`）不采用。**
理由是两个 API 的失败方式不同，实测：

```text
set_variation_by_axes([])         -> 静默接受，墨点仍是 663（什么都没发生）
set_variation_by_axes([700, 700]) -> 静默接受（面只有一根轴）
set_variation_by_name(b"Nope")    -> ValueError: b'Nope' is not in list
```

**一个会悄悄不发生的修正，不如一个会喊出来的。** 所以用 `set_variation_by_name("Bold")`，
并且在调用前自己查一遍命名实例是否存在——存在就设，不存在抛 `CaptionFontUnavailable`
点名 font_key（PIL 原生答的是裸 `ValueError`，会以「既不是字体问题也不是样式问题」的形态
冒到渲染器外面，正是 T3 那个 `frozenset(None) → TypeError` 的形状）。今天的闭集造不出这种面，
但**扩字体正是 LE-20 的交付内容**。

选 Bold 而不是 Regular：默认中文面就是 `noto-sans-cjk-sc-bold`，拉丁 fallback 与它并排出现在
同一行里，字重不一致会被看成渲染故障。

**Thin 为什么必须修**：它与豆腐块同类——有墨、尺寸正确、下游断言全过，而用户读不清。
本文件「验收判据」一节论证过非空断言对豆腐块零捕捉力，Thin 是同一个盲区的另一半。

另外两条实测，都写进了代码注释作为「不做某事」的依据：

- **面不做记忆化**。`ImageFont.truetype` 打开两种随包格式各 **0.6–0.7 ms**（含 17 MB 的 CJK 面，
  FreeType 是 mmap 不是读盘），没有可买的东西；而 `glyph_coverage` 记忆化是因为它那 25 ms
  的 cmap 读取要按「每字符每面」付。反过来共享是有代价的：字号与变体实例都存在 face 对象上，
  两个调用方拿同一个对象就是共享同一套设置；
- **`_load_face` 自己校验 font_px**。PIL 对 `size=0` 抛裸 `ValueError`、对 `size=3000` 照单全收，
  两种都不是本层该冒出去的形态。校验放在解析文件**之前**，这样「调用方给错尺寸」的答复
  不取决于那个面装没装上（用例用会爆炸的 `bundle_root` 钉住这个顺序）。

#### C1（Critical）随包字体不可读时，画出来的是**用户磁盘上的字体**

`ImageFont.truetype` 捕获自己的 `OSError`，然后拿 basename 去平台字体目录里搜
（macOS `/Library/Fonts`、`/System/Library/Fonts`、`~/Library/Fonts` 递归；
Windows `%WINDIR%\fonts`；Linux XDG），搜到就返回那个面。所以
`render.py` 里的 `except OSError` **只有在搜不到时才触发**。本轮独立复现，
三种破坏方式各拿到同一个诱饵面、`face.path` 全都不是请求的那个路径：

| 随包面状态 | `getname()` | `face.path` |
| --- | --- | --- |
| 字节损坏 | `('TotallyUnrelatedUserFont', 'Black')` | 诱饵路径 |
| 存在但 `mode 000` | 同上 | 诱饵路径 |
| 截断 | 同上 | 诱饵路径 |

三重后果：**它证伪了本模块自己写下的不变式**（`_load_face` 那段"路径来自注册表"
的论证对 `resolve_font_file` 成立、对整个函数不成立——解析出的路径在失败时被丢弃）；
**权利暴露**（`REGISTERED_CAPTION_FONTS` 同时是 `asset-rights-policy.v1.json` 的
权利清单，`defaultDecision: "deny"`，替换成用户随便装的字体等于把未授权字体印进
客户视频）；**它把冻结态的 fail closed 变成 fail open**，与 `CLAUDE.md §5`
"不发现、不选择、不回退到系统资源"是同一形状——而本文件交接点一节原先只论证了
**缺失**那一半（`is_file()` 守卫），存在但损坏或不可读的面走的是另一条路。

修法：加载后比对 `face.path != path`。保留路径传参而不改用文件对象，是为了不让
17 MB 的 CJK 面被读进内存（PIL 传文件对象会走 `load_from_bytes` 全量读盘，而
mmap 路径实测只要 0.6–0.7 ms）。比对是精确的且不碰文件系统：PIL 把构造时收到的
参数原样存进 `self.path`，走 basename 搜索回来的那个面带的是它 walk 出来的 `str`，
不是这里给的 `Path`。

**原来那两条用例是环境依赖的绿**——`[garbage]`、`[empty]` 之所以通过，只因为这台机器的
搜索目录里恰好没有 `NotoSansCJKsc-Bold.ttf`（实测 `~/Library/Fonts` 267 个字体、
`/System/Library/Fonts` 372 个文件），而**扩字体正是 LE-20 的活**。所以：

- 那两条现在把用户级搜索目录重定向到空目录（`HOME` / `WINDIR` / `XDG_DATA_HOME` +
  `XDG_DATA_DIRS`），并加一条前提断言"PIL 此时确实抛 `OSError`"，它们守的是
  `except OSError` 那一支；
- 新增 `test_a_face_that_will_not_load_is_not_replaced_by_an_installed_one`
  **自己造撞车条件**：把一个有效面写进那个被重定向的目录，前提断言先确认 PIL
  真的换了面（`face.path` 与请求路径不同），再断言 `CaptionFontUnavailable`。
  这条用例在装了零个字体和装了几百个字体的机器上含义相同。

**收口轮补两条精度更正**（复审点名，都不改行为，只把记录改准）：

- **重定向在 macOS 上只盖住三分之一。** PIL 的 darwin 分支是
  `["/Library/Fonts", "/System/Library/Fonts", expanduser("~/Library/Fonts")]`，
  **只有第三个跟 `HOME` 走**，前两个是硬编码、照样被 walk。所以上面第一条不能读成
  "环境依赖已消除"：**造撞车那条不受影响**（它只要求 PIL 换了面，而它自己的前提断言
  把这一点说死了），**`[garbage]`/`[empty]` 两条仍是环境依赖的**。变的是依赖的方向——
  最大的一处来源（本机 `~/Library/Fonts` 267 个）已经挪开，而万一系统目录里真有同名面，
  那条前提断言会**炸红并指名道姓**，不会让用例静默改走另一条分支。彻底消除要靠假造
  `sys.platform`，那是用"测一个没在跑的平台"换确定性，不划算；
- **那条 `pytest.raises(OSError)` 前提断言对生产代码零捕获力。** 实测删掉它仍
  171 passed，本轮 49 个变异体里也没有任何一个是被它杀的——它守的是**环境漂移**
  而不是代码。位置没问题，但记录里得写清楚，别让它冒充一条有捕获力的断言
  （本文件反复讲"测试红了 ≠ 那条断言有捕获力"，这是同一件事的另一面）。

#### I2（Important）`glyph_coverage` 在截断字体上让裸 `AssertionError` 逃出

`except (TTLibError, KeyError, OSError, ImportError)` 枚不全。实测：

| --- | --- |

### 三个第三方调用的实测结论（本轮的「守卫缺席」补查）

T4a 那条 Critical 是变异测不出来的：**变异只能施加在存在的代码上，守卫缺席时没有代码可变**。
本轮按那条方法论逐个追问「这个调用失败时到底给什么」，结论如下，全部在
Pillow 12.3.0 / FreeType 2.14.3（`raqm=False`）上实跑：

| 追问 | 实测 | 本单据此做了什么 |
| --- | --- | --- |
| `draw.text("")` | 不抛异常，直接返回 | 空文本走不到这里，`splitlines()` 给空列表时先拒 |
| `textbbox("")` | `(0, 0, 0, 0)`；**带 `stroke_width=3` 时给 `(-3, -3, 3, 3)`** | 一个空串也能量出 6×6 的框——「量得出尺寸」不等于「有东西」，所以判据落在墨上而不是尺寸上 |
| 纯空格行 | `textbbox` 给 `(0, 5, 102, 39)`，有宽度、零墨；`draw.text` 不抛 | 画完查 `getbbox()`，无墨即拒（`CaptionTextRejected`） |
| 超长行（20000 字符） | `textbbox` 39.3 ms，宽 **680000 px**；画到 400 px 画布上不抛不报，直接画在界外 | 断行把行宽压在画幅内，行数由「整块高过画幅」那条守卫压住，两个方向都有界 |
| `Image.new((0, 0))` | 成功 | — |
| 在 0×0 画布上 `save` | `ValueError: cannot write empty image`，**不留文件** | 这是「既不是字体问题也不是样式问题」的第三方异常形态，由空文本与无墨两条守卫堵在前面 |
| `save` 到 mode 500 目录 | `PermissionError` errno 13，不留文件 | `mkstemp` 先撞上，收成 `CaptionOutputUnavailable` |
| `save` 到不存在的父目录 | `FileNotFoundError` errno 2 | 同上 |
| `save` 到没有后缀的路径且不传 `format` | `ValueError: unknown file extension` | 工作文件名由 `mkstemp` 给，所以 `format="PNG"` 显式传；后缀也给了 `.png`，两道都留着 |
| 磁盘满（写到 200 字节后抛 errno 28） | **留下 200 字节的半个文件**，`Image.open` 报 `image file is truncated` | 这是本单选原子落盘的直接理由：直接写目的地会把上一版好字幕换成一个读不出来的文件 |
| `stroke_width` 向内还是向外 | **向外**。`textbbox` 四边各 `+stroke`；实测画出来的 alpha 包围盒 stroke=0 `(104, 66, 129, 100)` → stroke=8 `(96, 58, 137, 108)`，四边各外扩 8 | 画布四边各留 `stroke_px`，否则描边被裁 |

### 排版的每个决定与它的依据

**1. 切分用 `str.splitlines()` 本身，Tab 按行展开而不是拒绝。**
拒绝也说得通（`segment_runs` 就是这么做的），但字幕里的 Tab 几乎都是从文档粘来的，
为它整条 fail closed 换不到任何安全性——而缺字画豆腐块换得到，两件事不同类。
展开成空格保留了 Tab 要的那段间隔，**不是丢弃**（丢弃会把一行悄悄缩短，正是本包处处在防的形状）。
**展开必须在切分之后逐行做**：`str.expandtabs` 只在 `\n` 与 `\r` 处重置列计数，
而 `splitlines()` 还在 `U+0085`、`U+2028`、`U+2029` 处断行——整段一起展开会让这三个分隔符
之后那一行的制表位整体偏一格。这条由 `test_a_tab_stop_is_counted_from_the_start_of_its_own_line`
用 `U+2028` 与 `\n` 的对照钉住。

**2. 画布是紧贴文本的，不是整帧。** 字幕在画面里的位置是 overlay 那一步的事，
而那一步本来就握着画幅。整帧画布会把「下边距」这个本该属于 `CaptionStyle` 的参数
就地发明一个出来。画幅在本层承三件事：字号不得高过它、断行宽度从它减边距得来、
整块不得高过它。

**3. 每行在画布内居中。** 画布宽度等于最宽的那一行，所以其余各行的对齐只有这里能定；
多行字幕左对齐会被看成排版故障。

**4. 两遍绘制：先画所有描边，再画所有填充。** 实测（随包 Noto Sans CJK SC）：

| 文本 | stroke | 一遍（白 / 黑） | 两遍（白 / 黑） | 单次 PIL 调用参照 |
| --- | --- | --- | --- | --- |
| `AV` | 20 | **640** / 5897 | 909 / 5598 | 909 / 5598 |
| `mm` | 20 | **1006** / 6881 | 1202 / 6639 | 1202 / 6639 |
| `il` | 12 | **347** / 2447 | 506 / 2310 | 506 / 2310 |
| `中文` | 20 | **1288** / 8295 | 1496 / 8071 | 1496 / 8071 |
| `AB` | 8 | **1029** / 2352 | 1051 / 2335 | 1051 / 2335 |
| `我们` | 12 | **1724** / 5586 | 1850 / 5443 | 1850 / 5443 |

一遍绘制时后一段的描边会盖掉前一段的字面，`AV` 在 stroke 20 下 909 个填充像素只剩 640。
**两遍绘制与「整行一次 PIL 调用」逐字节相同**，一遍不是。这不是洁癖：段边界就是换面的地方，
而换面正是 fallback 链每次生效的地方。
**stroke 为 0 时第一遍必须整个跳过**，不能只是把宽度传 0——零宽描边照样把字面画成描边色，
填充叠上去会与底下混合，实测多出 73 个暗像素、白像素从 1322 掉到 1051。

**5. 先渲内存、再写工作文件、再 `os.replace` 到目的地。** 依据是上表磁盘满那一行：
PIL 把写进去的字节留在原地且不删。工作文件建在目的地**同一个目录**里，所以改名不跨文件系统；
失败、异常、中断三条路都在 `finally` 语义下把它删掉。中断原样透传，不收成
`CaptionOutputUnavailable`——理由与 `glyph_coverage` 那条相同：一个停不下来的渲染比一次失败更糟。

**6. fallback 链在这一层推导，不作为参数传入。** 样式只点一个面，字幕要几个面由它的字符决定，
所以顺序总得有人定。定在这里，调用方就不会在流水线里各自发明一套 fallback 策略。
顺序是「样式自己的面，然后注册表其余的面按登记顺序」。

### 新增守卫的端点纪律

本线的固定动作：两端端点 + 越界一格 + 两个方向的变异实跑，夹具非正方形。

| 守卫 | 接受端点 | 越界一格（拒绝） | 备注 |
| --- | --- | --- | --- |
| `frame_width` ∈ [128, 4096] | 128、4096 | 127、4097 | 消息点名字段，`frame_height` 各有一条对称用例 |
| `frame_height` ∈ [128, 4096] | 128、4096 | 127、4097 | 同上 |

### 验收判据：与 `.notdef` 位图差分，逐个字形

台账明令的判据落在
`test_every_drawn_glyph_differs_from_the_notdef_box`：把 PNG 的墨按「先分行、再分列」
切成一块块，每块裁到自己的包围盒，然后与**每个在册面**画 `U+10FFFF` 得到的位图逐字节比对；
参照图由用例自己用一次 `ImageDraw.text` 画出来，颜色写字面量，**不读被测模块的常量**
（M34 那条教训：断言读了它要钉的常量，常量一改断言跟着动）。四种文本各一组：
多行 CJK、CJK + 拉丁混排（触发 fallback 分段）、含空格、含 NBSP。

合成面的 `.notdef` 本轮**必须有墨**（一个与字干形状不同的实心方块）。原来的合成面
`.notdef` 是空的，那样比对的是一张白纸，「画了个空」也能通过——而随包 CJK 面
在 48 px 下为一个画不出的字画 **966** 个墨点，那才是真实形态。

空白字符（空格、NBSP）不走这条判据：它们本来就没有墨，对它们有意义的断言是
「占位但不画」，由 `a_blank_character_advances_the_line_without_drawing` 用宽度差钉住。

### T4b 修复轮（`1c046f5`）：1 Critical + 3 Important

> spec 审查逐条通过（两处偏离获批：画幅两参做成关键字参数、
> 空白字符改用宽度差而不是差分判据）；代码质量审查判 1 Critical + 3 Important，
> **两个审查者各自独立收敛到同一条 C1**。

#### C1（Critical）画布高度读了末行的 ascent，几何上要的是首行的

```python
baseline = float(stroke + lines[0].ascent)                       # 首行顶边钉在 y=0
height   = 2*stroke + sum(steps[:-1]) + lines[-1].ascent + ...   # 却按末行的 ascent 量
```

绘制从**首行**基线往下走，所以画布要装的是「首行 ascent + 各步进 + 末行 descent」。
写成末行 ascent 就差出 `a₀ − aₙ`：**首行比末行高时，末行从底下被静默裁掉**——
不抛异常、尺寸也没有一处不对，只是少了降部。

本地先复现再修（度量分歧夹具 `中\nA`，CJK 面 `900/−300`、拉丁面 `720/−40`）：
末行墨高 **36 行、下沿 136 恰好等于画布高度 136**（贴边即被裁），
修正式后 43 行、下沿 143 < 145。
（这三个数在交付时写成 28/128/128，是复审判出的 D1：拿夹具重跑取的真值是 36/136/136，
修正式那半 43/143/145 原本就对。）

**随包真实面上同样复现，读数如下**（`big-shoulders-display` 作样式面、上面压一行中文，
两个面的 ascent/descent 实测为 `63/16` 与 `54/12`）：

| | 画布 | 末行墨高 | 末行墨的下沿 |
| --- | --- | --- | --- |
| 缺陷式 | 261×185 | **54 px** | 第 184 行 = 画布最后一行（贴边即被裁） |
| 修正式 | 261×194 | **62 px** | 第 192 行，下方还空 1 行（193） |

差的 8 px 正是 p / y / g 的降部连描边。同一条 `happy pygmy` 单独成片时墨高也是 62 px，
即「上面多一行就少一截」这个说法可以直接核对。

**为什么交付轮 116 条全绿**：所有多行用例两行同面同 ascent，两个式子是同一个数；
唯一双面度量不同的用例是**单行**。夹具在被测维度无区分度——这是本线第五次踩同一形态。
**为什么今天没炸**：随包三个面在 48 px 下 `aₙ + dₙ − a₀` 只余 +3 px；
扫 12–200 px 全区间，**13/14 px 处余量恰好为 0**，而 LE-20 的交付物就是加面，
任何 `ascent + descent` 偏小的拉丁面立刻翻成裁切。

同一处的第二个存活变异：把绘制起点的 `lines[0].ascent` 也改成 `lines[-1]`，同样全绿——
**三行代码里的整套「多行 + 混合度量」竖直几何，55 个变异一个没覆盖。**
补的用例同时钉两端：首行墨的下沿必须等于 `2×stroke + 首行 ascent`（顶），
末行墨高不得因为上面多了一行而变小、且下沿必须小于画布高度（底）。

连带确认：「整块不得高过画幅」那条守卫用的就是这个 `height`，修正后它比的是真实所需高度，
原先在混合度量下会**低估**——端点用例（画幅足够大时量出的真实高度 / 该高度 −1）随之仍然成立。

**修完之后按同一维度扫一遍，又抓出第三个存活变异**：把式子末尾的 `lines[-1].descent`
换成 `lines[0].descent` 仍然全绿。它不裁切，方向相反——画布**多留**一截底边，
而字幕若按自己 PNG 的下沿定位，就会整体往上飘 `d₀ − dₙ`。补的断言不重述算式，
只说一句语义：末行墨迹下方留白，必须与该面单行成片时留的一样多。
`descent` 与 `ascent` 两端现在各有一条用例。

**本轮最重要的一个结论，也是对派工单的一处细化：**
派工单枚举的缺口全是**读数**，它并没有主张过机制无人守；
下面这条是把「读数」与「机制」分开之后才看清的，不是派工单说错了什么。
派工单说那些实测结论「没有任何用例会在它们退化时变红」。跑完 BEFORE 一栏才看清，
这句话**对读数成立、对机制不成立**——M1～M6、M8 七个生产代码变异体**在 T5 之前就已经
被合成面用例杀掉了**，本单加的是第二个、跑在真实面上的 killer。真正一个 killer 都没有的
是**资产本身的事实**（格式魔数、覆盖读数、astral 计数、可变面墨量、raqm），
它们的退化**没法用生产代码变异体表达**——换字体不是改代码。所以这一类的捕获力
只能由两种证据说明：用例侧翻转（M9/M10，BEFORE 必然 SURVIVED 因为文件还不存在），
以及上一节那次**真实的字体替换**。后者是本轮唯一一次"资产退化"的真实注入，
也正是它抓出了 Bold/Regular 那个缺口。

M7（`math.ceil` → `int`）与 T4b 的 P15 是同一个变异体，结论也相同：本机字宽恒为整数，
两个函数恒等。**T5 让这个结论第一次有了守卫**——不是守 `math.ceil` 本身
（它仍然测不出来），而是守它的**前提**：`test_this_pillow_lays_text_out_without_libraqm`
与 `test_every_advance_is_a_whole_number`。装了 libraqm 的 Pillow 上这两条会红，
那时 M7/P15/R7 三个"真等价体"判定都要重审。

#### Q1（Important）`.notdef` 差分只抓得住整篇 tofu，抓不到局部

审查判得对，而且比我原来写的更严重。实测把验收文本里**每一个**字符轮流换成一个未覆盖
码位（共 48 个位置），页面级判据**只抓到 2 个，漏掉 46 个**——那 2 个恰好是旁边有空格、
方框因此单独成块的位置。成因是聚类：墨块按「墨列的连续段」切，而验收样式带 4 px 描边
让相邻字粘连，**45 个可画字符只切出 12 块**；多字粘成的一块永远不可能与单字参照逐字节
相等，所以 `cluster not in notdef` 对局部 tofu 恒真。去掉描边也不解决：stroke 0 时
45 个字符切出 46 块（有的字形墨有竖向断口，被切成两块）。

**修法选的是「下沉到 run/字符粒度」**（审查给的三条里的第一条），理由是另外两条都治不了根：
改 stroke 0 只把 12 块变成 46 块，仍与 45 对不上；让参照按同样粘连度生成，等于要预先知道
哪些字会粘在一起，那是把渲染器的几何又推导一遍。新用例
`no_single_character_of_the_caption_is_drawn_as_tofu` 走**渲染器自己那条链**
（`_fallback_chain` → `segment_runs` 选面），逐字符问「这个面画这个字」与「这个面画一个
它没有的码位」是否同形，并钉住字符数 51 防止分段悄悄少算。

页面级那条**保留并改名**为 `the_drawn_page_is_not_a_page_of_tofu`，docstring 写明射程

重新推导「应该画成什么」。

## 给 T4 的接口约束（复审给出，T4 照此实现）

> T4a 登记：第 1、2 条落在 T4b 头上（本单不做切分与排版），已抄进 `render.py` 的模块 docstring；
