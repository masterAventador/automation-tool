# NOTE `74fb282` 混入了未在说明中提及的改动

> 日期：2026-07-26
>
> 性质：提交纪律问题，非代码缺陷。如实记录，不改写历史。

## 发生了什么

`74fb282`（视频工作台三项修复）显式 `git add` 了 `frontend/src-tauri/src/lib.rs`，
而当时有一个并行子代理正在同一文件上消除构建期分叉。结果该文件 220 行改动
（98 增 122 删）被一并提交，**而那条提交的说明只写了段数时长、零件中文名与包审计
符号链接判据，完全没有提到构建期分叉**。

被扫入的是「消除测试构建对生产行为路径的分叉」中的第 1～5 处：

| 处 | 内容 |
| --- | --- |
| 1 | 启动环境检查在测试构建下无条件返回三项就绪 |
| 2 | 控制服务健康检查硬编码可用 |
| 3 | 动效 Worker 来源枚举按 feature 分叉 |
| 4 | 动效 Worker 路径解析从环境变量读取 |
| 5 | 动效 Worker 启动方式分两条 match 臂 |

其余两处（素材 Worker 路径覆盖、发布工作台状态类型门控）与全部新增测试留在工作树，
随 `780abce` 提交并在说明中完整交代。

## 为什么会发生

并行子代理与主会话同时改同一个文件时，主会话按文件名精确 `git add` **仍然不安全**——
精确点名解决的是「别把不相关的文件带上」，解决不了「这个文件里有别人还没写完的改动」。

这是同类错误第二次发生。上一次是 `7739540` 用 `git add -A` 扫入两个在途脚本
（见 `NOTE-7739540-mixed-commit.md`），当时得出的教训是「有并行子代理时不能用
`git add -A`」——**这条教训不够，真正的判据是「有并行子代理正在改的文件，一律不提交」**，
与用什么方式 add 无关。

## 影响

- 代码本身没有问题：`780abce` 提交时全量复验，Rust 328 项测试通过，四种 feature
  组合均可编译，`single_build_path` 防复发测试 7 项通过；
- 可回滚性受损：单独回滚 `74fb282` 会同时撤掉五处构建期分叉的消除，而那与该提交
  说明的三件事无关。若需回滚，必须逐 hunk 处理。

## 不改写历史的理由

`74fb282` 之后已有 4 个提交叠在上面，rebase 的风险高于这条记录的收益；且改写后
这次纪律问题就不留痕迹了，而它正是需要被记住的那类问题。

## 采取的措施

1. 本文件；
2. `780abce` 的提交说明显式指向本文件；
3. 判据更正为：**并行子代理正在修改的文件，主会话一律不提交，无论用何种方式暂存。**
