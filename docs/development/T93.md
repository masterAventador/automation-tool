## 现象（T88 实测，本次复现）

首页最大那张「当前任务」卡的正文，和「最近任务」每一行的可点标题：

```
当前任务  查看运行详情 全局紧急停止
Task ID da7eba9b-1653-405b-8faf-49fda258a259  状态 运行中  Revision 3  事件水位 2
最近任务
af2a327b-ece6-4381-8864-c237e7c976f4  已成功
da7eba9b-1653-405b-8faf-49fda258a259  运行中
```

这段是本次 RED 里 Playwright 从 `.workbench-content` 直接读出来的 `textContent`，
不是转述，见下面「RED」。

## 查证一：`Revision` 与「事件水位」是不是有意放在首页的

`CLAUDE.md` 4.4 主张「任务快照是刷新和重启恢复的权威来源，实时事件只构建前端投影」。
这两个计数器确实是这条主张的观测点——`revision` 是快照的权威版本号，
`lastEventSequence` 是事件流投影追到了哪。所以问题不是「该不该留」，而是
「留在首页正文，还是留在够得着的地方」。

三条证据指向后者：

1. **这条主张约束的是行为，不是展示。** 4.4 全文讲的是恢复来源、状态转换、事件字段和
   幂等，没有一句要求把计数器渲染到界面上。把它们摆出来不构成对该主张的实现，
   移走也不构成违反。
2. **任务运行详情页已经在展示这两个字段**，`TaskRunDetails.tsx:522-525`
   的「运行概览」卡里 `事件水位` 与 `Revision` 并排，旁边还有开始时间和更新时间。
   也就是说，佐证这条架构主张的界面本来就在——从首页移走不会让它消失，只是从
   「客户第一眼」挪到「操作者去查的那一页」。
3. **没有任何测试或验收依赖它们出现在工作台上。**
   `grep -rn "事件水位" frontend/src frontend/e2e frontend/e2e-tauri` 只有两处命中：
   `TaskRunDetails.tsx:522` 和 `Workbench.tsx:276`（即本次改的这处），
   两个 `.spec.ts` 目录都没有引用。

**结论：不删，降级。** 折进「诊断信息」折叠区，和完整 Task ID 放在一起——
Task ID 一起进去的理由是它的唯一用途就是和日志对账，属于同一类事实。
折叠区默认收起，antd 的 `Collapse` 在展开前不渲染面板内容，所以它确实不占正文。

## 查证二：`TaskSnapshot` 到底有没有可用的标题字段

T88 的结论是「没有标题字段，要显示关键词得先动后端契约」。**独立核实，结论一致**，
三条命令：

1. 后端契约本身（不是前端的镜像）：

   ```
   $ python3 -c "
   import json
   d=json.load(open('contracts/openapi/control-plane.v1.json'))
   schemas=d['components']['schemas']
   for k in sorted(schemas):
       if 'Task' in k:
           print('==',k, '->', sorted(schemas[k].get('properties',{}).keys()))
   "

   == TaskResponse -> ['createdAt', 'lastEventSequence', 'revision', 'status', 'taskId', 'updatedAt']
   == TaskListResponse -> ['items', 'nextCursor']
   == TaskCreateRequest -> ['action', 'finalConfirmationRequired', 'maximumIntervalSeconds',
                            'messageTemplate', 'minimumIntervalSeconds', 'previewRequired',
                            'searchKeyword', 'targetLimit', 'template']
   ```

   关键词 `searchKeyword` **只在创建请求里**，任务查询响应 `TaskResponse` 不带它。

2. 关键词落在哪张表：

   ```
   $ grep -rn "search_keyword" backend/ | grep -v tests
   backend/migrations/versions/20260718_0013_douyin_search_exposure_definitions.py:31:
       sa.Column("search_keyword", sa.String(), nullable=False),
   ```

   它在 `douyin_search_exposure_definitions`，是一张独立的定义表。任务查询端点没有
   join 它，所以要在列表里显示关键词，得改后端查询、改 `TaskResponse`、改
   OpenAPI、再改前端 schema——不是小改。

3. 前端这一侧也确实关死了：`frontend/src/api/control-plane/task-projections.ts`
   的 `taskSnapshotSchema` 是 `.strict()` 的，字段就是
   `taskId / status / revision / lastEventSequence / createdAt / updatedAt`。
   就算后端多返回一个字段，`.strict()` 也会判 `protocol_mismatch` 拒掉。

**所以按指示退一步用 `createdAt`。** 上一条线没判断错。

一点补充（上一条线没提，但影响取舍）：**用到秒，不是分。**
「07-26 21:33 的任务」在同一分钟内建两个任务时会产出两行一模一样的文字，
那本身是个缺陷。真实后端里一个用户填两次表单撞进同一秒基本不可能，撞进同一分钟
则完全可能。所以格式定为 `MM-DD HH:mm:ss 的任务`。

`createdAt` 读不出来时回落到 Task ID：生产路径上快照都过 Zod，读不出来不该发生，
但万一发生，`NaN-NaN NaN:NaN:NaN 的任务` 出现在客户第一屏比现状更糟，
而回落到 Task ID 至少不比改之前差。

- 折叠头的可访问名是 `"collapsed 诊断信息"`——antd 给展开箭头挂了 `aria-label`，

## 失败矩阵

| 情况 | 行为 | 覆盖 |
| --- | --- | --- |
| 没有运行中的任务 | 卡片仍是「还没有运行中的任务」空态，不渲染折叠区 | 空态分支代码未改，折叠区在结构上就位于非空分支内；建任务之前的 `agent-browser snapshot -i` 里只有「查看运行详情」「全局紧急停止」两个 disabled 按钮，没有「诊断信息」。**无自动化用例**，这一条是观察，不是断言 |
| `createdAt` 读不出来 | 回落到 Task ID，不渲染 `NaN` | `falls back to the identifier when a Task has no readable creation time` |
| 同一分钟内建多个任务 | 秒级精度，行文字不重复 | 改后实测两行相差 1 秒，各不相同 |
| 列表与实时投影不一致 | 不受影响，`projectedTasks` 合并逻辑未动 | 既有 `uses the newer live projection…` / `refreshes the recent Task list…` 仍绿 |
| 网关失败 | 仍是不泄漏底层错误的重试态 | 既有 `shows a fixed retryable state…` 仍绿 |
