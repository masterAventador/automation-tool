# T107 — 「超过允许的最长等待时间」变成「连续 6 分」

> 日期：2026-07-27
> 分支：`refusal-surface`（基点 `6fd7d87`）
> 状态：**✅ 已完成**
> 前置：T90b（`authoring_model_timed_out` 这个码本身；当时自报了这处缺口，见 `docs/development/T90b.md` 第八节 (c)）

## 一、要解决的是什么

模型接上之后不再说话，等多久算等够，这个数只活在
`backend/src/automation_tool/executor/motion_authoring/agent.py` 的
`MODEL_TIMEOUT_SECONDS: Final = 360` 一处（实测确认，与台账描述一致）。

于是卡片只能说「超过**允许的最长等待时间**都没有再返回内容」。这句话没有给用户任何可用的
信息：判断不了刚才那次是等够了才失败还是别的原因，也判断不了下次值不值得再等。
把「6 分」直接敲进文案会立刻产生第二份手抄副本——这个预算第一次被调，App 报的数就和
Executor 真正遵守的数对不上了，而且没有任何东西会发现。

**本任务的判据不是「把常量搬个地方」，是「同一个事实不许存在两份，其中一份是手抄的」。**

## 二、做法：契约持有数，两边都读它

沿用项目里已有的强形式（`motion-storyboard-duration.v1` + `motion-one-sentence-brief.v1`）：
**一份 JSON 持有数，Python 在 import 时读它，TypeScript 直接 import 它，谁都不留副本。**

不采用 `motion-render-sandbox-budget.v1` 那种「各语言各写一份字面量 + 正则门禁比对」的弱形式，
因为那本身就还是多份，只是有人守着。

- 新增 `contracts/video/motion-authoring-model-call.v1.json`，字段 `streamIdleTimeoutSeconds: 360`；
- `agent.py` 新增 `_load_model_stream_idle_timeout_seconds()`，形状与既有的
  `_load_maximum_duration_seconds()` 一致（fail closed：读不到 / 走样都抛）；
  `MODEL_TIMEOUT_SECONDS` 由它产出，不再是字面量；
- 新增 `frontend/src/features/video-studio/motion-model-call.ts`，import 同一份 JSON，
  并复用**已有的** `motionSpokenDuration()`（`motion-duration.ts`）把秒数写成产品里一贯的说法；
- `VideoStudio.tsx` 的 `authoring_model_timed_out` 文案改成模板串，把那个值嵌进去。

### 为什么新开一个模块而不是塞进现有的两个

先查过现有可复用资源：`motion-duration.ts` 是「片子多长」，`motion-one-sentence.ts` 是
「一句话需求的边界」。模型调用的等待预算既不是片长也不是输入边界，塞进任何一个都会让那个
模块变成两件事的家。格式化本身没有新写——直接用了 `motionSpokenDuration`。

### 为什么 `MAX_MODEL_TIMEOUT_SECONDS = 3600` 留在 agent.py

它是构造参数的校验上限，只有一处、没有第二份、界面也不需要说它。搬它属于顺手扩范围。
新 loader 用它做区间校验，所以两者仍然只有一个来源。

### 中途被既有门禁挡下一次（真实回归）

新 loader 抛的两条 `MotionAuthoringRejected` 消息没有对应的封闭 token，
`test_every_fixed_upstream_rejection_has_its_own_closed_reason_token` 当场红。这条门禁做对了事：
它用 AST 扫 `agent.py` / `entry.py` 里所有固定拒绝消息，要求每条都有自己的线上 token。
补了 `agent_model_call_contract_drifted` 与 `agent_model_call_contract_is_unreadable`，
并按既有惯例（同 `agent_storyboard_duration_contract_*`）归入 `installation_damaged`——
打包进来的契约读不出来或走样，是安装坏了，不是用户的描述有问题。

## 五、真实边界

**改契约 → 两侧同时跟着变**，实测（把 `streamIdleTimeoutSeconds` 临时改成 174 再跑）：

| | 360 | 改成 174 |
|---|---|---|
| Executor 实际用的 `agent.MODEL_TIMEOUT_SECONDS` | 360 | 174 |
| 卡片真实渲染出的那句话 | 连续 **6 分**没有再返回内容 | 连续 **2 分 54 秒**没有再返回内容 |

卡片那一侧不是读源码判断的：断言 `toContain(\`连续 ${motionSpokenDuration(契约值)}没有再返回内容\`)`
跑在真实渲染出来的 `role="alert"` 文本上，两次都通过。验证完已还原 360 并复核 Executor 报回 360。

## 六、失败矩阵

| 情况 | 行为 |
|---|---|
| 契约文件缺失 / 不是 JSON | `agent_model_call_contract_is_unreadable`，fail closed；归 `installation_damaged` |
| `schemaVersion` / `policy` 不对，或秒数不是整数、不在 `1..MAX_MODEL_TIMEOUT_SECONDS` | `agent_model_call_contract_drifted`，同上 |
| 有人在 `agent.py` 把字面量写回来 | `motion-authoring-model-call.test.mjs` 第一条断言红 |
| 有人在 TS 侧或文案里把数字敲死 | 同文件的 `doesNotMatch(\b<秒数>\b)` 两条断言红 |
| 有人把契约调了但文案没跟上 | `VideoStudio.test.tsx` 那条 `toContain` 红（上一节实测） |
| 契约没进安装包 | 第三条用例红。**这条是本任务里最要紧的一条**：`agent.py` 在 import 时就读它，包里缺了不是超时才失败，而是 Executor 根本起不来，而且只在用户那边发生——源码检出里这个文件永远躺在仓库里。已同步加进 `backend/automation-tool-executor.spec`（该 spec 本身对缺文件 fail closed）和 `scripts/test_desktop_e2e_prerequisites.py` 的打包输入清单 |
| 整个编排子进程超时（不是模型静默） | 仍走 `authoring_timed_out`，与本数无关；契约的 `wholeResponseIsNotBoundedHere` 写明了不在这里重述 |
