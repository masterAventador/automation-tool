## 5. 两个需要用户知道的环境问题

### 5.1 media-toolchain 造不出来 —— 这条真的挡人

`prepare_video_runtime.py` → `_build_media_toolchain`（`:133`）跑 `bash scripts/build_video_media_toolchain.sh windows-x86_64 <dest>`。

两层原因，逐层剥出来的：

1. 第一次直接失败 `FileNotFoundError: [WinError 2]`，因为 **`bash` 不在 PATH**。机器上其实有：`C:\Program Files\Git\bin\bash.exe`（Git 装在 `C:\Program Files\Git\cmd`，`bin` 没进 PATH）。
2. 把 Git 的 `bin` 前置进 PATH 后重跑，脚本能启动、能下载，但仍失败。**真实原因被吞了**——`prepare_video_runtime.py:144` 只取 `splitlines()[-8:]`，而 curl 的进度条正好占满最后 8 行，于是报错里只有进度条。直接跑 builder 才拿到那一行：

```
No working C compiler found.
```

即 Windows 上构建 ffmpeg 需要 MSYS2/MinGW 工具链（机器上留有 `.local\vf04-msys2` 与 `msys2-base-x86_64-20260611.sfx.exe`，说明以前是这么装的，但当前 bash 环境里没有可用 gcc）。

**为什么这条挡人**：`scripts/run_eb_16_windows_acceptance.py:557` 会调 `prepare_video_runtime(platform="windows")`，`:575` 还要 `require_packaged_video_runtime`。**Windows 出包链路必过这一步**，所以现在 winbox 上出不了包。

**已有一份现成产物可考虑复用**：`.local\vf04-windows-20260724-r5\media-toolchain\bin\ffmpeg.exe`（19,269,632 字节，07-24 构建）。当前缓存键与它对不上所以没被复用；是否可直接喂给 `--install-into` 需要按 `video_runtime_cache` 的键规则确认，本次未擅自改缓存。

> 顺带记一笔产品外缺陷：`prepare_video_runtime.py:144` 的 `[-8:]` 是又一处「吞掉构建真实原因」，与台账里 T75 / `ce45efd` 同族。curl 进度条能把真错顶出窗口，这次就是这么被藏住的。

### 5.2 uv 的版本无关 junction 是坏的

`tools/browser-use-contract/.venv` 与 `tools/shared-browser-validation/.venv` 的 `pyvenv.cfg` 都写着
`home = E:\DevTools\uv\python\cpython-3.12-windows-x86_64-none`，而该目录是一个指向 `cpython-3.12.13-windows-x86_64-none` 的 **Junction**，遍历后为空 → `uv trampoline failed to spawn Python child process`。

`backend\.venv` 写的是**真实**目录 `cpython-3.12.13-...`，所以 backend pytest 完全不受影响。

**排除了「这是 SSH 会话的锁」这个解释**：在同一会话里用 `mklink /J` 新建一个指向**同一目标**的 junction，`dir` 能正常读到 `python.exe`。所以是那个 junction 本身坏了，不是会话不能穿越 junction。

**尝试过修但没修好，如实记录**：`uv sync --project ... --locked --python <真实解释器绝对路径>` 退出码 **0**，但重建后的 `pyvenv.cfg` **仍写回那个 junction 路径**，trampoline 依旧失败（复验过，不是没看）。uv 坚持用版本无关目录。要根治得修 `E:\DevTools\uv\python` 下那个 junction 本身（属项目之外的共享工具目录，本次未动）。

不挡 T7：受影响的只有 4 个 browser-use 契约脚本测试。
