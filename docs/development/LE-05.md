### 两个「主动查」点的实测结论

用一次性探针（跑完即删）对真实 PostgreSQL 18.4 + asyncpg 0.31.0 + SQLAlchemy 2.0.51 实测：

1. **唯一冲突抛什么**：`sqlalchemy.exc.IntegrityError`（`SQLAlchemyError` 的子类），
   `.orig` 是 asyncpg 适配后的 `IntegrityError`，底层 `asyncpg.exceptions.UniqueViolationError`，
   `orig.sqlstate == "23505"`。集成测试里把 23505 钉住了。
2. **TIMESTAMPTZ 读回的 tzinfo**：`datetime.timezone.utc`，且 `tzinfo is UTC` 为真，
   微秒完整保留（`123456` 原样回来）。**但零偏移不等于 UTC**——域层
   `_validate_timestamp` 只检查 `utcoffset() == 0`，任何零偏移时区都能过，所以
   「水合后 tzinfo 是 UTC」不能靠域层保证。`_hydrate` 显式 `.astimezone(UTC)`，
   并由一条单元用例（喂 `+08:00` 的行）钉住——去掉这句话该用例即红。

### 与计划不符的一处，依据是实测

计划决策 8 与失败矩阵都写 `except SQLAlchemyError: raise <模块>Rejected from None`。
**这一句挡不住「库不可达」**：探针实测，连接被拒时冒出来的是
`ConnectionRefusedError`（`OSError`），来自 asyncio 的 connect 调用；asyncpg 方言只包装
asyncpg 自己的异常，所以它原样穿过 `except SQLAlchemyError`，把 host 和 port 带给调用方。

`session.py:53` 的 `check_connection` 早就捕的是 `(OSError, SQLAlchemyError, TimeoutError)`
——本仓库已经知道这件事，只是仓储层没跟上。本 task 按 `(OSError, SQLAlchemyError)` 捕
（`TimeoutError` 自 3.10 起是 `OSError` 子类，第三项是冗余的）。变异实测：改回只捕
`SQLAlchemyError`，`test_an_unreachable_database_is_refused_without_leaking_the_connection`
立刻红。

**连带发现（本 task 未改）**：`workbench_metrics_repository.py` 等只捕 `SQLAlchemyError`
的既有仓储都有同一个缺口。它们的单元用例是用注入的 `SQLAlchemyError` 验的，没有一条
用真实拒绝连接走过，所以缺口至今没被照出来。归属其各自模块，另立任务。

### 表为什么没有 CHECK 约束

值域上下界留在 `editing_project.py`，表只承担类型、主键与 NOT NULL。理由写在迁移
docstring 里：一是上下界是 LE-04 的资产，SQL 里再抄一份就多一处要同步；二是 SQL 只能
表达其中一个子集（`stroke_px * 2 < font_px`、`font_px <= output_height` 是跨字段的，
「已 trim、无控制字符」没法写成像样的 check），一套残缺的约束会让人以为数据库在校验，
而真正承重的守卫是仓储过构造器水合。跨聚合根不变式是另一回事，按决策 5 进 0038/0039 的
复合外键与部分唯一索引。

### 失败矩阵（本 task 适用行）

| 场景 | 落点 |
| --- | --- |
| 重复请求 | 重复 `save` 被主键拒绝，且不是 upsert；裸 INSERT 违例注入证明拦截在数据库 |
| 多实例竞争 | 仓储不做「先查后插」，两个并发调用都由主键拒绝其一 |
| 断连 / 库不可达 | 真实拒绝连接 → `Rejected`，traceback 不含连接串 |
| 敏感信息泄漏 | 异常消息固定、丢弃入参；`from None` 抑制上下文，由 traceback 渲染断言钉住 |
| 非法数据持久化面 | 库里的非法行在水合处被域构造器拒绝，不返回对象 |
