### 两个「主动查」点的实测结论

用一次性探针（跑完即删）对真实 PostgreSQL 18.4 + asyncpg 0.31.0 + SQLAlchemy 2.0.51 实测：

1. **唯一冲突抛什么**：`sqlalchemy.exc.IntegrityError`（`SQLAlchemyError` 的子类），
   `.orig` 是 asyncpg 适配后的 `IntegrityError`，底层 `asyncpg.exceptions.UniqueViolationError`，
   `orig.sqlstate == "23505"`。集成测试里把 23505 钉住了。
2. **TIMESTAMPTZ 读回的 tzinfo**：`datetime.timezone.utc`，且 `tzinfo is UTC` 为真，
   微秒完整保留（`123456` 原样回来）。**但零偏移不等于 UTC**——域层
   `_validate_timestamp` 只检查 `utcoffset() == 0`，任何零偏移时区都能过，所以
   「水合后 tzinfo 是 UTC」不能靠域层保证，由 `_timestamp()` 显式归一并有用例钉住。

### 与计划不符的三处，依据都是实测

**一、决策 8 的 `except SQLAlchemyError` 挡不住「库不可达」。** 连接被拒时冒出来的是
`ConnectionRefusedError`（`OSError`），来自 asyncio 的 connect 调用；asyncpg 方言只包装
asyncpg 自己的异常，所以它原样穿过那个 except，把 host 和 port 带给调用方。
`session.py:53` 早就捕 `(OSError, SQLAlchemyError, TimeoutError)`（第三项冗余，
`TimeoutError` 自 3.10 起是 `OSError` 子类，已实测 MRO）；house 另有五处
`(OSError, SQLAlchemyError)` 先例。

**二、握手之后还有一整类异常在漏——这是首轮漏掉的，由审查实测补上。** 上面查到
`ConnectionRefusedError` 就停了，那只是**握手前**。认证阶段的失败是
`asyncpg.exceptions.InvalidPasswordError`，消息里带角色名与库名。asyncpg 0.31.0 实测
MRO：

```
InvalidPasswordError       → InvalidAuthorizationSpecificationError → PostgresError → PostgresMessage → Exception
InsufficientPrivilegeError → SyntaxOrAccessError                    → PostgresError → …
InvalidCatalogNameError    → PostgresError → …
TooManyConnectionsError    → InsufficientResourcesError             → PostgresError → …
```

四个类里**只有 `InvalidCatalogNameError` 直接继承 `PostgresError`**，其余三个各自隔了
一层中间类——所以按任何单个具名基类去接都会漏掉一部分，共同点只有 `PostgresError`
这条脊和「`OSError`、`SQLAlchemyError` 都不在 MRO 上」。其中
**`TooManyConnectionsError`——连接池打满是生产常态，不是配置错误**。按
`bilibili_publish_repository.py:158-163` 补 catch-all 尾巴。

这段 MRO 首轮在四处文档里写成了「只有 `PostgresError → Exception`」，漏掉中间两层，
由复审实测更正。**教训在这里出现了两次**：第一次是「查过一次第三方异常面」不等于
「查全了」（握手前后是两个阶段）；第二次是记录这条教训的那段文字本身又把第三方异常面
写错了一遍。结论没受影响（catch-all 接得住全部四个），错的只是解释。

**三、计划指定的 house 范例选错了。** `workbench_metrics_repository.py` 是只读投影，
没有重复键路径，一个 `Rejected` 够用；带 `save` 的仓储照抄它，会把「已存在」
「不存在」「库挂了」压成同一个异常。按 `customer_account_repository.py:162-165`
的两分法拆成四类，命名对齐 `customer_accounts.py`。这不是可选的整洁度问题：
T4 的三条不变式全部经 `IntegrityError` 浮出，LE-06 紧接着要分 409/404/503。

以上三处已在计划 `docs/superpowers/plans/2026-07-29-le-05-persistence.md` 决策 8 就地更正。

### 水合的顺序：先验后归一

`.astimezone(UTC)` 放在构造器**之前**是个洗白守卫的写法，首轮就是这么写的：对 naive
时间戳它不报错，而是按宿主机时区重新解释、把瞬间平移一个时区偏移，然后交出一个
完全合法的 aware 对象——域层本来会拒绝 naive，被这一步洗过去了。`None` 与文本更糟，
直接从仓储内部抛裸 `AttributeError`。而 asyncpg 对 TIMESTAMPTZ 本来就还 UTC，
**这句对真实列全是 no-op，唯一净效果就是削弱守卫**。T2 的 `described_at` 可空，
照抄即活路径。现在 `_timestamp()` 只对「已经 aware」的值做归一，其余原样交给构造器
拒绝，四种形状各有一条用例。

### 失败矩阵（本 task 适用行）

| 场景 | 落点 |
| --- | --- |
| 重复请求 | 重复 `save` → `AlreadyRegistered`，且不是 upsert；裸 INSERT 违例注入证明拦截在数据库 |
| 多实例竞争 | 仓储不做「先查后插」，两个并发调用都由主键拒绝其一 |
| 断连 / 库不可达 | 真实拒绝连接 → `Unavailable`，traceback 不含连接串 |
| 认证失败 / 权限不足 / 连接数上限 | 真实错密码 → `Unavailable`，traceback 不含角色名 |
| 敏感信息泄漏 | 四个异常消息全部固定、构造器不收参数；`from None` 抑制上下文，由 traceback 渲染断言钉住 |
| 非法数据持久化面 | 四种非法行 + 非 v4 UUID 在水合处被拒，不返回对象 |

### 三个「主动查」点的实测结论

一次性探针（`tests/integration/test_zzprobe_le05_t2_facts.py`，跑完即删，未进提交）
对真实 PostgreSQL 18.4 + asyncpg 0.31.0 + SQLAlchemy 2.0.51 实测：

1. **asyncpg 对 JSONB 列返回什么类型。** 派工单问的是「str？dict？取决于 codec 注册」。
   实测：**SQLAlchemy 的 asyncpg 方言已经注册了 JSON codec，取回来的是解析好的
   Python 对象，永远不是文本**——JSON 数组是 `list`，JSON 对象是 `dict`。
   具体读数：

   ```
   segments type=<class 'list'> value=[[0, 1000], [2000, 3000]]
     inner type=<class 'list'>
   tags     type=<class 'list'> value=['户外', '露营']
   empty tuple -> []      (<class 'list'>)
   object-not-array -> {'not': 'an array'} (<class 'dict'>)
   ```

   写入方向：Python 的 `tuple` 和嵌套 `tuple` 都能直接序列化成 JSON 数组，
   不需要先转 `list`（仓储仍显式转 `list`，因为那是列里真实存的形状，
   让 `_column_values` 的读者不必先去查编码器接不接受 tuple）。
   **所以水合必须把 `list of list` 转回 `tuple of tuple`**，否则域构造器直接拒
   （`not isinstance(segment, tuple)`）。这也是本表是全库第一张 JSONB 表的直接后果：
   `schema.py` 此前没有任何 JSON 列，没有先例可抄。

2. **`CHAR(64)` 是 `bpchar`，会补空格。** 实测存 `'short'` 取回来是
   `'short' + 59 个空格`（`len=64`），而且 `= 'short'` 仍然匹配到它
   （原生 SQL 与 SQLAlchemy Core 各测一次，都匹配 1 行）——空白填充比较会忽略尾部空格。
   对经仓储写入的摘要两者都不生效（域侧只接受 64 位小写十六进制，没有可填充的余量，
   也不会有尾部空格），但它给了一条免费的「表接受、域拒绝」注入形状：补白后的值不是
   十六进制，水合当场拒绝。已有独立用例钉住这个填充事实，换成 `varchar` 会红。

3. **可空 `TIMESTAMPTZ` 取回来是 `None`，带偏移的时间戳被 asyncpg 归一成 UTC。**
   `'...+08'::timestamptz` 存进去取出来是 `tzinfo=datetime.timezone.utc` 的等值时刻。
   这与 T1 对 `created_at` 的结论一致，区别只在 `None` 这一侧，见下一节。

### `[null]` 方向重判：T1 的交接说的是对的

T1 那条参数化用例里的 `None` 期望「被拒绝」，因为 `editing_projects.created_at`
是 NOT NULL。`materials.described_at` 可空，`None` 是它的合法值。逐字照抄会得到一条
方向反了的断言，而且**照抄实现之后它还会通过**——两边一起错、测试仍绿。

本 task 的做法：

- `normalise_timestamp()` 一行没改。它本来就对「不是 aware datetime 的东西」原样透传，
  对 `None` 就是交给构造器判。改的是构造器那侧的期望；
- 参数化用例拆成两组：`None` 单独一组，**断言水合出 `described_at=None`**，
  并且给了两种都合法的行形状（从没被描述过：`ai_description=None` + 源 `ai`；
  用户自己写的：源 `user` + 有描述无时间）——只写一种的话，「USER 源必须没有
  described_at」这条域规则就没被这条用例碰到；
- naive / 文本 / 数字仍然拒绝，`ids=["naive", "text", "number"]`，`null` 从这一组移出。

集成层也各有一条真行用例（`NULL_DESCRIBED_AT_ROWS`），不是只在单元层用 stub 证。

### UNIQUE 的夹具区分度：两条约束各自被单独钉住

T1 因为所有夹具共用一个 `created_at`，让「主键换成 `UNIQUE(created_at)`」的变异体活了下来。
本表有两条唯一约束（`pk_materials` 与 `uq_materials_content_digest`），所以两个夹具在
**两维上各自独立变化**：`DIGEST_ONE`/`DIGEST_TWO` 无共同前缀，`material_id` 各自新生成。

违例注入用三条裸 INSERT，一条只动一维：

| 注入行 | 只可能被谁拒 |
| --- | --- |
| 同 `material_id`、不同 digest | 只有主键 |
| 不同 `material_id`、同 digest | 只有唯一索引 |
| 两维都不同 | 谁都不该拒——这一条防「约束过宽，靠拒绝一切通过前两条」 |

前两条同时断言 `sqlstate == "23505"` 与**约束名出现在驱动消息里**，因为交换两条约束的

### AST 边界测试：为什么选显式豁免，而不是把水合搬进 `material.py`

计划决策 9 给了两条路，要求「按侵入性小的定，写明理由」。**选了显式豁免**，
而且豁免的粒度是 `(文件, 函数名)` 而不是整个文件：`material_repository.py` 的
`_hydrate` 里可以构造 `Material`，同一个文件的其他任何地方都不行。

否掉「搬进 `material.py`」的理由是写出来之后才看清的：那样等于在**这条规则要保护的那个
模块里**放一个公开的第二构造器。任何人都能从任何地方调它，直达规则想拦的那组字段组合，
而守卫连可匹配的名字都没有了——豁免一个函数留下的口子，比它替代的那个小。

顺带的正当性：水合确实是唯一「从零件装配」正确的地方——库里的行不是「一个被描述过的
素材正在被重新描述」，而是一个正在被重新构成的素材，而且它必须过构造器，因为行是输入不是真理。

**守卫查三件事**，能力边界写在测试文件的模块 docstring 里，没有含糊过去：

1. 调用 `Material(...)`（`Name` 与 `Attribute` 两种形态）——**精确匹配名字，不是子串**。
   包里真有 `BilibiliPublishMaterial` 和 `OpaqueBearerMaterial`，`endswith` 会把它们
   永远报成违例，专门有一条用例钉住这两个不被误报；
2. 导入了 `Material` 的模块里出现的任何 `replace(...)` 调用；
3. 第一个实参名字里带 `material` 的 `replace(...)`，无论有没有导入——这一条覆盖
   `replace(material, ...)` 这个不需要导入的现实形状。

**明确记录的盲区**：一个模块拿到 `Material`、从不写这个类名、又用别的变量名传给
`replace`，静态检查抓不到。没有任何静态手段能抓到；把盲区写出来是比假装它不存在更诚实的选择。

**自证**：5 段合成违例源码（直接构造、限定名构造、导入后 replace、不导入 replace、
`dataclasses.replace`）各断言检查函数返回非空；3 段合法源码断言返回空。这 9 条在
实现还不存在时就已经跑绿——「只对现状绿」的守卫和「什么都不报」的守卫从外面看一模一样。
另有两条：豁免的目标函数必须真实存在（否则豁免会变成永久免票），
以及**去掉豁免时那个文件必须变成违例**（否则豁免可以被删掉而无人察觉，说明扫描根本没到那个文件）。

扫描范围只有 `backend/src`。测试可以自由构造 `Material`——领域对象本来就是这么测的，
范围放宽会让 LE-02 自己那套用例全部违规。

### Q1 陈旧快照能把 AI 描述盖到用户头上——结构性缺口，真实 PG 已复现

**审查者是对的，首轮那句 docstring 是错的。** 原文写「Whether the rewrite is allowed at
all was decided before this point, by `Material.with_ai_description`」——`with_ai_description`
看的是**调用方手里的快照**，不是库里那一行。完整链路，每一步都走正规方法：

1. 某个 describe 流程 `get` 出素材，此时 `description_source` 是 `AI`；
2. 用户在这期间写了自己的描述，`with_user_description` → `update_description`，库里变 `user`；
3. describe 流程拿着**第 1 步那个快照**调 `with_ai_description`——快照说 AI，
   所以域方法不返回 `self`，老老实实交出一个改好的对象；
4. `update_description` 无条件写入。用户的字没了，`description_source` 翻回 `ai`。

没有人构造 `Material`，没有人调 `replace`，所以 AST 守卫无话可说；域守卫被满足了，
因为它看的那个对象**确实**说自己是 AI。**AST 挡构造、域挡快照，没人挡 update。**

**拦截做成 UPDATE 里的谓词，而不是 Python 里的判断**，理由和 `save` 不做「先查后插」
是同一条：读一行再决定，在低一层有一模一样的缺陷——两个 describe 流程都读到 `ai`，
都往下走。只有数据库一次只看一条语句。

语义定死如下：

| 传入 material 的 source | UPDATE 附加谓词 | 理由 |
| --- | --- | --- |
| `AI` | `description_source != 'user'` | 模型不得盖用户 |
| `USER` | 不附加 | 用户改自己的描述永远允许 |

`rowcount == 0` 于是有两个含义，**用同一个事务里的一次后续 SELECT 消歧**：

- 查不到行 → `MaterialNotFound`；
- 查得到行 → `MaterialDescriptionProtected`（**新异常，进四类词汇体系变五类**）。

**「同一事务所以只有这两种」这句话是错的，已被真实 PG 推翻。** 首轮把它当成修复形状的
中心理由写进了源码注释和用例 docstring——后人最会引用的两个位置。实测：连接跑在
`read committed` 下，**每条语句各取一次新快照**；UPDATE 之后、SELECT 之前另一个连接
DELETE 并提交，同事务的 SELECT 读出 `ROW_VISIBLE=False`。同事务只省了一次连接池取用，
没有让两种情况穷尽；换 session 会误报的场景，同 session 一样误报。

诚实的版本（源码与用例 docstring 两处都已改成这个）：**保护决策由 UPDATE 谓词一条语句
单独做完**，后续 SELECT 只是尽力消歧，可被并发抢跑。那个窗口里两种答案都安全——行真被
删了答 `NotFound` 是实话，行还在且归用户答 `Protected` 是实话，会错的只是「并发删除」
这一种情形的标签，而两个标签对调用方是同一个意思：停。**塌成一个才是不安全的**。

**不能沿用 `NotFound`**：LE-06 要对这两种分别答 409 与 404，LE-13 要区分「素材没了，
别重试」和「有人接管了这个字段，别再写」。用例里专门断言
`not isinstance(captured.value, MaterialNotFound)`——**它挡的是「把 `Protected` 写成
`NotFound` 的子类」这种塌回**（那样写 `pytest.raises(Protected)` 照旧绿，而调用方
`except MaterialNotFound` 会把它一并吞掉）。首轮这里写的理由是「两者同基类所以必要」，
**那条理由不成立**：兄弟类不会让 `raises(Protected)` 失效。复审实测：这个变异只被这条
断言和失败词汇守卫抓到。

`test_a_stale_snapshot_cannot_walk_an_ai_description_over_the_users`，真实 PG 上逐步复现
上面四步，断言拿到 `Protected`、用户描述保留、`description_source` 仍是 `user`。
修前它红在「没有 `MaterialDescriptionProtected` 这个名字」（`ImportError`，单元与集成各一次）。

### Q2 AST 守卫漏别名构造：能补的补掉，补不动的登记

审查者实测七种绕过，四种 MISSED：`as M`、`as _Mat`、`Rebuild = Material`，以及链式
`A = Material; B = A`。**而首轮我自己在 `_imports_protected_class` 的注释里写过
「别名导入是那种用过才暴露的洞」——`replace` 那一侧照着做了，构造这一侧没有。**

修法：构造匹配从「比对字面 `Material`」改成「比对**这个模块实际绑定到该类的所有本地名**」：

- `ImportFrom` 里 `alias.name == "Material"` 的取 `asname or name`；
- 简单赋值 `Y = X` **跟到不动点**而不是一层——停在一层，两行就能绕过，读完规则的人立刻想得到；
- `Attribute` 形态（`material_module.Material(...)`）仍按属性名匹配，因为它拼的就是类名本身。

RED：把四种别名形态加进合成违例语料，跑出 `4 failed, 12 passed`，失败的正好是这四条。

第二条尤其难看：**先给属性绑个名字反而躲掉，而直接调它会被抓**——正是我自陈要堵的

2. **解包/容器绑定**——`Rebuild, = (Material,)`。可补但不值得，见上；
3. **模块不导入类名、变量名也不带 material 时的 `replace`**。静态无解。

三条各有一条 `test_a_name_this_technique_cannot_resolve_is_a_recorded_blind_spot`

去把模块 docstring 的盲区清单同步删掉那一条**。断言一个洞存在听着奇怪，但它把边界变成
