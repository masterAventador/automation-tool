### 两个「主动查」点的实测结论

用一次性探针（跑完即删）对真实 PostgreSQL 18.4 + asyncpg 0.31.0 + SQLAlchemy 2.0.51 实测：

1. **唯一冲突抛什么**：`sqlalchemy.exc.IntegrityError`（`SQLAlchemyError` 的子类），
   `.orig` 是 asyncpg 适配后的 `IntegrityError`，底层 `asyncpg.exceptions.UniqueViolationError`，
   `orig.sqlstate == "23505"`。集成测试里把 23505 钉住了。
2. **TIMESTAMPTZ 读回的 tzinfo**：`datetime.timezone.utc`，且 `tzinfo is UTC` 为真，
   微秒完整保留（`123456` 原样回来）。**但零偏移不等于 UTC**——域层
   `_validate_timestamp` 只检查 `utcoffset() == 0`，任何零偏移时区都能过，所以
   「水合后 tzinfo 是 UTC」不能靠域层保证，由 `_timestamp()` 显式归一并有用例钉住。

### 与计划不符的三处，依据都是实测

**一、决策 8 的 `except SQLAlchemyError` 挡不住「库不可达」。** 连接被拒时冒出来的是
`ConnectionRefusedError`（`OSError`），来自 asyncio 的 connect 调用；asyncpg 方言只包装
asyncpg 自己的异常，所以它原样穿过那个 except，把 host 和 port 带给调用方。
`session.py:53` 早就捕 `(OSError, SQLAlchemyError, TimeoutError)`（第三项冗余，
`TimeoutError` 自 3.10 起是 `OSError` 子类，已实测 MRO）；house 另有五处
`(OSError, SQLAlchemyError)` 先例。

**二、握手之后还有一整类异常在漏——这是首轮漏掉的，由审查实测补上。** 上面查到
`ConnectionRefusedError` 就停了，那只是**握手前**。认证阶段的失败是
`asyncpg.exceptions.InvalidPasswordError`，消息里带角色名与库名。asyncpg 0.31.0 实测
MRO：

```
InvalidPasswordError       → InvalidAuthorizationSpecificationError → PostgresError → PostgresMessage → Exception
InsufficientPrivilegeError → SyntaxOrAccessError                    → PostgresError → …
InvalidCatalogNameError    → PostgresError → …
TooManyConnectionsError    → InsufficientResourcesError             → PostgresError → …
```

四个类里**只有 `InvalidCatalogNameError` 直接继承 `PostgresError`**，其余三个各自隔了
一层中间类——所以按任何单个具名基类去接都会漏掉一部分，共同点只有 `PostgresError`
这条脊和「`OSError`、`SQLAlchemyError` 都不在 MRO 上」。其中
**`TooManyConnectionsError`——连接池打满是生产常态，不是配置错误**。按
`bilibili_publish_repository.py:158-163` 补 catch-all 尾巴。

这段 MRO 首轮在四处文档里写成了「只有 `PostgresError → Exception`」，漏掉中间两层，
由复审实测更正。**教训在这里出现了两次**：第一次是「查过一次第三方异常面」不等于
「查全了」（握手前后是两个阶段）；第二次是记录这条教训的那段文字本身又把第三方异常面
写错了一遍。结论没受影响（catch-all 接得住全部四个），错的只是解释。

**三、计划指定的 house 范例选错了。** `workbench_metrics_repository.py` 是只读投影，
没有重复键路径，一个 `Rejected` 够用；带 `save` 的仓储照抄它，会把「已存在」
「不存在」「库挂了」压成同一个异常。按 `customer_account_repository.py:162-165`
的两分法拆成四类，命名对齐 `customer_accounts.py`。这不是可选的整洁度问题：
T4 的三条不变式全部经 `IntegrityError` 浮出，LE-06 紧接着要分 409/404/503。

以上三处已在计划 `docs/superpowers/plans/2026-07-29-le-05-persistence.md` 决策 8 就地更正。

### 水合的顺序：先验后归一

`.astimezone(UTC)` 放在构造器**之前**是个洗白守卫的写法，首轮就是这么写的：对 naive
时间戳它不报错，而是按宿主机时区重新解释、把瞬间平移一个时区偏移，然后交出一个
完全合法的 aware 对象——域层本来会拒绝 naive，被这一步洗过去了。`None` 与文本更糟，
直接从仓储内部抛裸 `AttributeError`。而 asyncpg 对 TIMESTAMPTZ 本来就还 UTC，
**这句对真实列全是 no-op，唯一净效果就是削弱守卫**。T2 的 `described_at` 可空，
照抄即活路径。现在 `_timestamp()` 只对「已经 aware」的值做归一，其余原样交给构造器
拒绝，四种形状各有一条用例。

### 失败矩阵（本 task 适用行）

| 场景 | 落点 |
| --- | --- |
| 重复请求 | 重复 `save` → `AlreadyRegistered`，且不是 upsert；裸 INSERT 违例注入证明拦截在数据库 |
| 多实例竞争 | 仓储不做「先查后插」，两个并发调用都由主键拒绝其一 |
| 断连 / 库不可达 | 真实拒绝连接 → `Unavailable`，traceback 不含连接串 |

### 三个「主动查」点的实测结论

一次性探针（`tests/integration/test_zzprobe_le05_t2_facts.py`，跑完即删，未进提交）
对真实 PostgreSQL 18.4 + asyncpg 0.31.0 + SQLAlchemy 2.0.51 实测：

1. **asyncpg 对 JSONB 列返回什么类型。** 派工单问的是「str？dict？取决于 codec 注册」。
   实测：**SQLAlchemy 的 asyncpg 方言已经注册了 JSON codec，取回来的是解析好的
   Python 对象，永远不是文本**——JSON 数组是 `list`，JSON 对象是 `dict`。
   具体读数：

   ```
   segments type=<class 'list'> value=[[0, 1000], [2000, 3000]]
     inner type=<class 'list'>
   tags     type=<class 'list'> value=['户外', '露营']
   empty tuple -> []      (<class 'list'>)
   object-not-array -> {'not': 'an array'} (<class 'dict'>)
   ```

   写入方向：Python 的 `tuple` 和嵌套 `tuple` 都能直接序列化成 JSON 数组，
   不需要先转 `list`（仓储仍显式转 `list`，因为那是列里真实存的形状，
   让 `_column_values` 的读者不必先去查编码器接不接受 tuple）。
   **所以水合必须把 `list of list` 转回 `tuple of tuple`**，否则域构造器直接拒
   （`not isinstance(segment, tuple)`）。这也是本表是全库第一张 JSONB 表的直接后果：
   `schema.py` 此前没有任何 JSON 列，没有先例可抄。

2. **`CHAR(64)` 是 `bpchar`，会补空格。** 实测存 `'short'` 取回来是
   `'short' + 59 个空格`（`len=64`），而且 `= 'short'` 仍然匹配到它
   （原生 SQL 与 SQLAlchemy Core 各测一次，都匹配 1 行）——空白填充比较会忽略尾部空格。
   对经仓储写入的摘要两者都不生效（域侧只接受 64 位小写十六进制，没有可填充的余量，
   也不会有尾部空格），但它给了一条免费的「表接受、域拒绝」注入形状：补白后的值不是
   十六进制，水合当场拒绝。已有独立用例钉住这个填充事实，换成 `varchar` 会红。

3. **可空 `TIMESTAMPTZ` 取回来是 `None`，带偏移的时间戳被 asyncpg 归一成 UTC。**
   `'...+08'::timestamptz` 存进去取出来是 `tzinfo=datetime.timezone.utc` 的等值时刻。
   这与 T1 对 `created_at` 的结论一致，区别只在 `None` 这一侧，见下一节。

### `[null]` 方向重判：T1 的交接说的是对的

T1 那条参数化用例里的 `None` 期望「被拒绝」，因为 `editing_projects.created_at`
是 NOT NULL。`materials.described_at` 可空，`None` 是它的合法值。逐字照抄会得到一条
方向反了的断言，而且**照抄实现之后它还会通过**——两边一起错、测试仍绿。

本 task 的做法：

- `normalise_timestamp()` 一行没改。它本来就对「不是 aware datetime 的东西」原样透传，
  对 `None` 就是交给构造器判。改的是构造器那侧的期望；
- 参数化用例拆成两组：`None` 单独一组，**断言水合出 `described_at=None`**，
  并且给了两种都合法的行形状（从没被描述过：`ai_description=None` + 源 `ai`；
  用户自己写的：源 `user` + 有描述无时间）——只写一种的话，「USER 源必须没有
  described_at」这条域规则就没被这条用例碰到；
- naive / 文本 / 数字仍然拒绝，`ids=["naive", "text", "number"]`，`null` 从这一组移出。

集成层也各有一条真行用例（`NULL_DESCRIBED_AT_ROWS`），不是只在单元层用 stub 证。

### UNIQUE 的夹具区分度：两条约束各自被单独钉住

T1 因为所有夹具共用一个 `created_at`，让「主键换成 `UNIQUE(created_at)`」的变异体活了下来。
本表有两条唯一约束（`pk_materials` 与 `uq_materials_content_digest`），所以两个夹具在
**两维上各自独立变化**：`DIGEST_ONE`/`DIGEST_TWO` 无共同前缀，`material_id` 各自新生成。

违例注入用三条裸 INSERT，一条只动一维：

| --- | --- |
| 同 `material_id`、不同 digest | 只有主键 |
| 不同 `material_id`、同 digest | 只有唯一索引 |
| 两维都不同 | 谁都不该拒——这一条防「约束过宽，靠拒绝一切通过前两条」 |

前两条同时断言 `sqlstate == "23505"` 与**约束名出现在驱动消息里**，因为交换两条约束的

### AST 边界测试：为什么选显式豁免，而不是把水合搬进 `material.py`

计划决策 9 给了两条路，要求「按侵入性小的定，写明理由」。**选了显式豁免**，
而且豁免的粒度是 `(文件, 函数名)` 而不是整个文件：`material_repository.py` 的
`_hydrate` 里可以构造 `Material`，同一个文件的其他任何地方都不行。

否掉「搬进 `material.py`」的理由是写出来之后才看清的：那样等于在**这条规则要保护的那个
模块里**放一个公开的第二构造器。任何人都能从任何地方调它，直达规则想拦的那组字段组合，
而守卫连可匹配的名字都没有了——豁免一个函数留下的口子，比它替代的那个小。

顺带的正当性：水合确实是唯一「从零件装配」正确的地方——库里的行不是「一个被描述过的
素材正在被重新描述」，而是一个正在被重新构成的素材，而且它必须过构造器，因为行是输入不是真理。

**守卫查三件事**，能力边界写在测试文件的模块 docstring 里，没有含糊过去：

1. 调用 `Material(...)`（`Name` 与 `Attribute` 两种形态）——**精确匹配名字，不是子串**。
   包里真有 `BilibiliPublishMaterial` 和 `OpaqueBearerMaterial`，`endswith` 会把它们
   永远报成违例，专门有一条用例钉住这两个不被误报；
2. 导入了 `Material` 的模块里出现的任何 `replace(...)` 调用；
3. 第一个实参名字里带 `material` 的 `replace(...)`，无论有没有导入——这一条覆盖
   `replace(material, ...)` 这个不需要导入的现实形状。

**明确记录的盲区**：一个模块拿到 `Material`、从不写这个类名、又用别的变量名传给
`replace`，静态检查抓不到。没有任何静态手段能抓到；把盲区写出来是比假装它不存在更诚实的选择。

**自证**：5 段合成违例源码（直接构造、限定名构造、导入后 replace、不导入 replace、
`dataclasses.replace`）各断言检查函数返回非空；3 段合法源码断言返回空。这 9 条在
实现还不存在时就已经跑绿——「只对现状绿」的守卫和「什么都不报」的守卫从外面看一模一样。
另有两条：豁免的目标函数必须真实存在（否则豁免会变成永久免票），
以及**去掉豁免时那个文件必须变成违例**（否则豁免可以被删掉而无人察觉，说明扫描根本没到那个文件）。

扫描范围只有 `backend/src`。测试可以自由构造 `Material`——领域对象本来就是这么测的，
范围放宽会让 LE-02 自己那套用例全部违规。

### Q1 陈旧快照能把 AI 描述盖到用户头上——结构性缺口，真实 PG 已复现

**审查者是对的，首轮那句 docstring 是错的。** 原文写「Whether the rewrite is allowed at
all was decided before this point, by `Material.with_ai_description`」——`with_ai_description`
看的是**调用方手里的快照**，不是库里那一行。完整链路，每一步都走正规方法：

1. 某个 describe 流程 `get` 出素材，此时 `description_source` 是 `AI`；
2. 用户在这期间写了自己的描述，`with_user_description` → `update_description`，库里变 `user`；
3. describe 流程拿着**第 1 步那个快照**调 `with_ai_description`——快照说 AI，
   所以域方法不返回 `self`，老老实实交出一个改好的对象；
4. `update_description` 无条件写入。用户的字没了，`description_source` 翻回 `ai`。

没有人构造 `Material`，没有人调 `replace`，所以 AST 守卫无话可说；域守卫被满足了，
因为它看的那个对象**确实**说自己是 AI。**AST 挡构造、域挡快照，没人挡 update。**

**拦截做成 UPDATE 里的谓词，而不是 Python 里的判断**，理由和 `save` 不做「先查后插」
是同一条：读一行再决定，在低一层有一模一样的缺陷——两个 describe 流程都读到 `ai`，
都往下走。只有数据库一次只看一条语句。

语义定死如下：

| 传入 material 的 source | UPDATE 附加谓词 | 理由 |
| --- | --- | --- |
| `AI` | `description_source != 'user'` | 模型不得盖用户 |
| `USER` | 不附加 | 用户改自己的描述永远允许 |

`rowcount == 0` 于是有两个含义，**用同一个事务里的一次后续 SELECT 消歧**：

- 查不到行 → `MaterialNotFound`；
- 查得到行 → `MaterialDescriptionProtected`（**新异常，进四类词汇体系变五类**）。

**「同一事务所以只有这两种」这句话是错的，已被真实 PG 推翻。** 首轮把它当成修复形状的
中心理由写进了源码注释和用例 docstring——后人最会引用的两个位置。实测：连接跑在
`read committed` 下，**每条语句各取一次新快照**；UPDATE 之后、SELECT 之前另一个连接
DELETE 并提交，同事务的 SELECT 读出 `ROW_VISIBLE=False`。同事务只省了一次连接池取用，
没有让两种情况穷尽；换 session 会误报的场景，同 session 一样误报。

诚实的版本（源码与用例 docstring 两处都已改成这个）：**保护决策由 UPDATE 谓词一条语句
单独做完**，后续 SELECT 只是尽力消歧，可被并发抢跑。那个窗口里两种答案都安全——行真被
删了答 `NotFound` 是实话，行还在且归用户答 `Protected` 是实话，会错的只是「并发删除」
这一种情形的标签，而两个标签对调用方是同一个意思：停。**塌成一个才是不安全的**。

**不能沿用 `NotFound`**：LE-06 要对这两种分别答 409 与 404，LE-13 要区分「素材没了，
别重试」和「有人接管了这个字段，别再写」。用例里专门断言
`not isinstance(captured.value, MaterialNotFound)`——**它挡的是「把 `Protected` 写成
`NotFound` 的子类」这种塌回**（那样写 `pytest.raises(Protected)` 照旧绿，而调用方
`except MaterialNotFound` 会把它一并吞掉）。首轮这里写的理由是「两者同基类所以必要」，
**那条理由不成立**：兄弟类不会让 `raises(Protected)` 失效。复审实测：这个变异只被这条
断言和失败词汇守卫抓到。

**RED**：新增
`test_a_stale_snapshot_cannot_walk_an_ai_description_over_the_users`，真实 PG 上逐步复现
上面四步，断言拿到 `Protected`、用户描述保留、`description_source` 仍是 `user`。
修前它红在「没有 `MaterialDescriptionProtected` 这个名字」（`ImportError`，单元与集成各一次）。

**顺带修掉一条一直在演示该 bug 的旧用例。**

而且一直是绿的。改成按真实顺序（先模型、后用户），并在 docstring 里写明反序不是疏忽、

### 六个「主动查」点的实测结论

一次性探针（`tests/integration/test_zzprobe_le05_t3_facts.py`，跑完即删，未进提交）
对真实 PostgreSQL 18.4 + asyncpg 0.31.0 + SQLAlchemy 2.0.51 实测，两轮：

1. **外键违例的异常面。** `IntegrityError`，`.orig.sqlstate == '23503'`，驱动消息带约束名，
   **DETAIL 行逐字引用找不到的键值**（`Key (a, b, c)=(...) is not present in table ...`）。
   所以 `from None` 在这条路径上不是形式——那串值就是调用方刚传进来的 `project_id`。
   复合主键违例是 `'23505'`，同样带约束名。两者都只能靠 SQLSTATE 区分，这是仓储把一个
   `IntegrityError` 分成三种答案的唯一依据。

2. **`IntegrityError.orig` 可以是 `None`。** `IntegrityError("stmt", None, None).orig is None`
   实测成立，`getattr(None, "sqlstate", None)` 是 `None`。所以取 SQLSTATE 必须走 `getattr`，
   直接 `error.orig.sqlstate` 会从仓储内部抛 `AttributeError`。有独立用例钉住。

3. **超键唯一约束永远不会是唯一的拒绝者。** 造一行同时违反 PK 与超键 UNIQUE 的数据，
   PostgreSQL 报的是 **`pk_le05_probe_parent`**（主键）。这是结构决定的：超键的列是主键列的
   超集，任何违反超键的行必然先违反主键。**所以违例注入无法证明这条约束存在**，
   派工单要求的「存在性断言」是唯一可行的形式——本 task 把它做得比名字更强，见下一条。

4. **三列 UNIQUE 确实能当复合外键的靶子。** 直接建了一张带
   `foreign key (a, b, c) references parent (a, b, c)` 的表，PostgreSQL 接受。这验证的是
   决策 3/5 的可行性本身。集成用例照这个做法写：**真的建一张探针表把复合外键声明上去**，
   建完立刻 drop。靶子缺失或列不对时 PostgreSQL 会报
   `there is no unique constraint matching given keys`——正是 T4 否则要现场撞上的那个失败。
   断言名字只能证明「有个叫这个名的东西」，建外键证明的是**T4 需要的那个性质**。

5. **JSONB 交回来是解析好的对象树，四层都是。** `list` → `dict` → `list` → `dict`
   （tracks → track → clips → clip），transition 也是 `dict`，JSON `null` 是 `None`。
   与 T2 对扁平数组的结论一致，只是深了两层。**另外 jsonb 会重排键**（实测
   `{"z":1,"a":2,"bb":3}` 存回来是 `{'a': 2, 'z': 1, 'bb': 3}`，按长度再按字节序），
   所以不能拿它跟带顺序的表示比——Python 的 dict 相等本来就不看顺序，本 task 的断言不受影响，
   但值得记一笔：**存进去的字节和取出来的不是同一串**。

6. **JSON 把 `-6` 和 `-6.0` 当两种东西，而域只接受 `float`。** 实测 `-6` 取回是 `int`，
   `-6.0` 取回是 `float`；`TimelineClip._validate_gain` 写的是 `type(self.gain_db) is not float`。
   **这条是本 task 最容易埋雷的地方**：一个「顺手把整数音量归一成 `-6`」的序列化器会写出
   一条谁都读不回来的行，而它在只用非整数音量（`-3.5`）的夹具下永远不会暴露。所以主夹具里
   专门放了一个 `-6.0`，集成层断言取回来的 `type(...) is float`，变异 M16 钉住它。

### `revision` 的上界：域没有，列有，本 task 只钉住现状不假装修好

域对 `revision` 只要求 `>= 1`，没有上界；列是 `integer`，上界 2³¹−1。实测越界一格
（`2**31`）的行为：**asyncpg 在语句发出前就拒绝参数**，抛自己的 `DataError`
（`value out of int32 range`），SQLAlchemy 包成普通 `DBAPIError`——是 `SQLAlchemyError`
但**不是** `IntegrityError`，于是落进 `(OSError, SQLAlchemyError)` 那条，答成
`TimelinePersistenceUnavailable`。

**这个答案是错方向的**：它让调用方去重试一件永远不会成功的事。没有在本 task 修，理由是
修法要么给域加上界（改 LE-03 的域对象，超出 T3 范围），要么在仓储里按 SQLSTATE `22000`
分流（`22000` 是「data exception」的总类，拿它当判据比问题本身更危险）。而触发它需要同一条
时间轴累积二十一亿个修订，靠自增达不到。

处置：**两端都写成用例**——`2**31 - 1` 正常往返，`2**31` 断言当前答成 `Unavailable`，
用例 docstring 写明「这条断言哪天红了，说明上界被收口了，该删的是这份遗留说明而不是这条用例」。
登记在下面「遗留」第 1 条。

### 「先 get、内存判、再写回」这条通用检查：T3 没有这种方法，但理由不是「用不上」

| `latest_revision` | 只读；**取最大值交给 `ORDER BY ... DESC LIMIT 1`**，不是读全部再在 Python 里挑 | —— |

`latest_revision` 那一条值得单列：把所有修订读回来再 `max()` 今天也能跑对，但它是同一个形状的

### 键集必须逐字相等，而不是「取到的字段够用就行」

三层文档都要求 `document.keys()` 与域 dataclass 的字段名**完全相等**，不多不少，
键集从 `dataclasses.fields()` 读而不是手写一份。多出来的键直接拒绝。

理由不是洁癖，是 `.get()` 的静默面：**`TimelineClip` 九个字段里有四个的合法值就是 `None`**。
一个把 `gain_db` 拼错成 `gan_db` 的行，用 `.get()` 读出来是「没有音量」——在画面轨上完全合法，
于是水合出一个域接受、但和存进去的东西不是一回事的对象。这正是本仓库反复记的那类失败：
不是报错，是安静地返回一个看起来对的值。

反过来，缺键这一侧其实不靠键集也能拦住（构造器会拒 `None`），**键集唯一独有的战果是「多余的键」**
——变异 M3/M4/M5 三条各自只被对应的 `extra-key` 用例杀掉，这一点在用例 docstring 里写明了，
免得后人以为这个检查在挡缺键。

### 拒绝夹具必须「去掉那一处毛病就是合法的」

本 task 的拒绝用例全部按这条构造，因为反例太容易写：包装本身非法的话，用例不管被测代码做什么
都是绿的。两处具体的坑，都是写的时候当场发现并改掉的：

1. **转场用例最初放在画面轨的第一个片段上。** 第一个片段没有前一段可叠，
   `_validate_layout` 里 `overlap >= previous_tail`（`previous_tail` 初值 0）会拒掉**任何**转场，
   与文档形状无关。九条转场用例会全绿，而 `_transition` 整个可以是空实现。改成放在第二个片段，
   并单独加一条控制用例断言「同一个包装装上合法转场必须水合成功」；
2. **片段用例的行 `duration_ms` 最初固定 13200，而单轨只到 6000。** 聚合根会因为
   「声明长度 ≠ 画面轨终点」拒掉一切，同样掩盖 `_clip`。改成让包装的 `duration_ms` 跟着轨道走。

集成层的 `REFUSED_ROWS` 同理，每一条的 `duration_ms` 都按那条自己的轨道算，并按
**「只有哪一层看得见」**分了三组：只有轨道能看见的（画面轨有洞、转场吃穿前一段、
第二次转场重复吃同一段、音频轨乱序、轨内 `clip_id` 重复、字幕片段挂素材、旁白片段没音量）、
只有聚合根能看见的（声明长度对不上画面轨、根本没有画面轨、两条轨同种、两条轨同 id、
某片段越过时间轴末尾）、以及任何 CHECK 都写不出来的（空轨列表、长度两端越界一格）。

其中**「第二次转场重复吃同一段」是最该留下的一条**：它只被
`previous_tail`（剩余尾巴）这种写法拒绝。若把规则写成拿前一段的原始 `duration_ms` 比，
这一行会被接受，而中间那段只剩 1000ms 的片段会被两个转场吃干净。域对象的注释专门讲了这件事，
现在有一行数据钉住它。

### 五个「主动查」点的实测结论

一次性探针（`tests/integration/test_zzprobe_le05_t4_facts.py`，跑完即删，未进提交）
对真实 PostgreSQL 18.4 + asyncpg 0.31.0 + SQLAlchemy 2.0.51 实测，两轮：

1. **约束名不在 `error.orig` 上，在它的 `__cause__` 上。** 这一条推翻了 T3 交接里
   「只能从驱动消息里取名字」的做法。实测 `error.orig` 是 SQLAlchemy 的
   `AsyncAdapt_asyncpg_dbapi.IntegrityError`，属性面只有 `args`、`pgcode`、`sqlstate`
   ——`constraint_name` 在它 `__cause__` 指向的 asyncpg `UniqueViolationError` 上，
   且与 `detail` 是**两个独立字段**：

   ```text
   orig dir            ['add_note', 'args', 'pgcode', 'sqlstate', 'with_traceback']
   cause type          <class 'asyncpg.exceptions.UniqueViolationError'>
   cause constraint_name  'uq_le05_probe_queued'
   cause detail           'Key (tl)=(2222...-2222) already exists.'
   ```

   所以取名字**根本不用碰消息**，键值那一串不会被顺手带出来。交接说的「代价是那条消息
   同时带着 DETAIL 的键值」在这条路径上不成立。降级方向是安全的：某天 SQLAlchemy 不再
   串 `__cause__`，取到 `None`，落到 `EditingJobDataRejected`——说得更少，而不是说错。
   M3 钉住这一跳（把 `getattr` 从 `__cause__` 改回 `error.orig`，KILLED）。
2. **部分唯一索引与主键撞同一个 `23505`**，实测两者 SQLSTATE 逐字相同，只有约束名不同
   （`pk_le05_probe` / `uq_le05_probe_queued`）。交接对这一点的判断成立。
3. **CHECK 是 `23514`，复合外键是 `23503`**，且 `23503` 的 DETAIL 一次引用三个键值
   （`Key (timeline_id, timeline_revision, project_id)=(...) is not present in table "timelines"`）
   ——这是本表泄漏面最大的一条，集成用例专门断言这三个值都不出现在渲染结果里。
4. **`Index` 的谓词读法。** `index.dialect_options["postgresql"]["where"]` 交回
   `BinaryExpression`；`compile(compile_kwargs={"literal_binds": True})` 渲染成
   `editing_jobs.status = 'queued'`。**不带 `literal_binds` 渲染成 `status = :status_1`**
   ——字面量藏进绑定参数，换成任何别的状态都比出来相等，门禁等于没写。
5. **空 `IN` 列表是合法且恒假的**：`in_([])` 渲染成 `status IN (NULL) AND (1 != 1)`。
   这条决定了 `QUEUED` 的空前驱集不需要特判（见下面「`update` 的第二条谓词」）。

### `update` 的第二条谓词：`updated_at` 单独挡不住，实测

计划与交接都只要求 `WHERE updated_at < :new`。**只有这一条时有一条真实的数据丢失路径，
本 task 实测复现，并加了第二条谓词堵上。**

`EditingJob` 自己的 docstring 就写了这个场景（LE-12 的对账遍历）。三步全部走正规方法：

1. worker 拿到一个 CANCELLING 的作业——取消是协作式的，仍可能跑完——成功，写
   `SUCCEEDED` + artifact，时间 `t2`；
2. 对账遍历手里还是第 1 步之前那个 **CANCELLING 快照**，判定作业被遗弃，调
   `fail(WORKER_LOST)`，时间 `t3 > t2`；
3. `CANCELLING -> FAILED` 是合法边，域对象照单全收；`t3 > t2`，**时间谓词放行**。

结果是一条已经出片的记录被标成失败、产物成孤儿。这与 T2 Q1 是同一族：
**状态机判的是调用方手里的快照，不是库里那一行**，而 T2 收口时定的判据正是
「那个检查是不是数据库一次只看一条语句时做的」。

修法：谓词加一条 `status IN (<该目标状态的合法前驱>)`，前驱集**从
`EditingJobStateMachine.can_transition` 推导**而不是手写第二份图——手写的那份会在
边一变时静默漂移，且漂移方向危险（多留一个前驱 = 放一条非法转换进库）。
`QUEUED` 的前驱集是空元组，于是任何把作业写回队列的 update 匹配不到行，这与域里
「没有回到 QUEUED 的边」是同一句话；空 `IN` 恒假由第 5 条实测保证。

**答案仍是 `EditingJobStale`，不新增第八个类**：两条谓词说的是同一件事——你手里的
快照不再是库里那一行，重新读一次再决定。合并成一个不是偷懒，是它们对调用方是同一个动作。

变异 M9（删掉状态谓词）由 `test_a_stale_snapshot_cannot_undo_a_render_that_already_finished`
杀掉；M10/M11（前驱集恒真 / 反向读图）由推导表的用例杀掉。

**这是对计划 T4 节的一处扩写而不是推翻**：计划写的「`updated_at` 必须前进」原样保留，
「幂等重放靠状态机不靠仓储」也保留——相等的时间戳仍然拒绝。加的是库侧那一半，
因为域侧那一半按定义看不见库里的行。

### `update` 为什么写全列，以及它没有解决的那个问题

`_column_values` 一个函数同时供 `save` 和 `update`，理由是 T2 在 `_description_values`
上写过的那条：两份列集会在域加字段时漂移，且漂移方向是「插入时存了、之后每次更新都
静默丢掉」。把身份列写成它们自己的值不花任何代价，而复合外键在 UPDATE 上一样会重查，
所以它们改不成不存在的东西。

**没解决的**：一个自己构造 `EditingJob`（不经 `get`）的调用方，可以把作业改指到**另一条
同样存在**的时间轴修订上。外键仍然拦得住不存在的目标，部分索引仍然拦得住占用中的
QUEUED 槽位，所以不是安全洞，但它确实是「全列更新」买单的那一项。**没有在本 task 收窄**：
正规路径（`get` → 转换方法 → `update`）永远不改这四列，所以不存在 T2 Q1 那种「不需要
误用就发生」的形态；而把身份列挪进 `WHERE` 会给 `rowcount == 0` 加上第三种含义，
把消歧弄得更糊。登记在下面「遗留」第 1 条。

### 「行不存在 vs 被谓词拒」：区分，理由与 T2 的 Protected 同型

`rowcount == 0` 两种含义，用一次后续 SELECT 消歧：查不到行 → `EditingJobNotFound`；
查得到 → `EditingJobStale`。

**照 T2 收口轮的更正表述写，不复制被推翻的那句**：保护由 UPDATE 那一条语句单独做完，
后续 SELECT 只是尽力消歧、可被并发抢跑（`read committed` 下每条语句各取新快照，
同事务也一样）。那个窗口里两种答案都安全，都是「停下来重读」。

**值得分**：LE-06 要对这两种分别答 404 与 409。塌成 `NotFound` 会告诉调用方一个正在跑的
作业不存在——这正是不安全的那个方向。M13/M14（两边各塌一次）都被杀。

### 三条不变式的违例注入证据

### 与计划/派工单不同的四处，依据都是实测或既有先例

**一、失败词汇是七个类，不是四个。** 三个「写被拒了」（`AlreadyRegistered`、
`RevisionAlreadyQueued`、`TimelineRevisionMissing`）+ 两个「更新没落」（`NotFound`、
`Stale`）+ 两个通用（`DataRejected`、`Unavailable`）。多出来的都是本表**可变**带来的：
前四张表没有 `update`，也就没有 `Stale`，更没有「同一个 `23505` 要分两种」。
**①和②合成一个 `TimelineRevisionMissing`**，因为一条复合外键拒的时候 PostgreSQL 不说
是哪一半——分成两个就得靠猜，而「那条时间轴、那个项目、那个编号的修订不存在」这句话
两种情况下都是真的，且指向同一个修法。

**二、约束名走 asyncpg 的结构化字段，不走驱动消息。** T3 交接说「必须看约束名，而约束名
在驱动消息里」，实测那是 `error.orig.__cause__` 上的一个独立属性，与 `detail` 分开——
见主动查第 1 条。这是把交接的做法改好，不是绕开它。

**三、`status`/`failure_code` 用 `String(16)`/`String(32)` 而不是计划字面写的 `TEXT`。**
沿用 T2 的既有形状（`materials.kind`、`description_source` 都是 `String(16)`），
并补一条单元用例断言两个枚举各自最长成员放得下——两侧都从各自的定义读，不产生第三份副本。
S7 钉这个方向。

**四、`update` 多一条状态谓词。** 见上面单独一节，附实测复现的数据丢失路径。

### 失败矩阵（本 task 适用行）

| 场景 | 落点 |
| --- | --- |
| 重复请求 | 同 `job_id` 第二次 `save` → `AlreadyRegistered`，且不是 upsert（事后比对整行）；同修订第二个 QUEUED → `RevisionAlreadyQueued` |
| 多实例竞争 | 仓储不做任何「先查后插/先读后判」；主键、复合外键、部分唯一索引、两条 UPDATE 谓词全在数据库一侧；三条不变式各有裸 INSERT 违例注入证明拦截在数据库 |
| 非法状态转换的持久化面 | 非法 status/failure_code 串在水合处被拒；**陈旧快照驱动的非法转换在 UPDATE 谓词处被拒**（真实 PG 复现整条链路） |
| 跨聚合根引用不存在 | 复合外键拒 →`TimelineRevisionMissing`；补齐引用后同一条数据落库成功（证明拒的是引用本身） |
| 幂等 / 重放 | 相等 `updated_at` 拒绝（贴边界，两侧各一格）；重放判定归状态机不归仓储 |
| 结果不确定 / 静默失败 | `rowcount == 0` 不塌成一种答案，后续 SELECT 消歧并写明可被并发抢跑；坏掉的序列化器原样传播而不是伪装成 `Unavailable`（`save`/`update` 各一条） |
| 断连 / 库不可达 | 真实拒绝连接 → `Unavailable`，traceback 不含连接串（三个方法各一条） |
| 认证失败 / 权限不足 / 连接数上限 | 真实错密码 → `Unavailable`，traceback 不含角色名（三个方法各一条） |
| 敏感信息泄漏 | 七个异常消息固定、构造器不收参数；`from None` 由 traceback 渲染断言钉住；复合外键的 DETAIL 一次带三个键值，专门断言项目与时间轴 id 都不出现 |
