## 0. 一句话结论

`contracts/quality/motion-catalog.v1.json` 的 134 项每项补上上游 `registry-item.json` 的
`description` / `tags` / `duration` / `dimensions`，逐字复制、由门禁重算比对，漂移即红。

## 1. 为什么缺

这份目录是 BM-11 为**权利审计**冻结的，那次审计需要的是身份和摘要，所以只摘了
`name` / `type` / `path` / `title` / `category` / `officialPreview` / `files`。

编排模型读的是同一份清单，但要回答另一个问题——**这一段该用哪个零件、它会跑多久**。
2026-07-27 探针实测：只给英文 `title` + 中文 `category`，两个模型选出的零件都合法且分类吻合，
但总时长双双超出 20 秒沙箱预算 70% 以上（qwen3.7-max 4 个零件 34.0 秒、deepseek-v4-pro
5 个零件 36.3 秒）。原因就是清单里没有任何地方写着 `data-chart` 是 15 秒而 `lt-bold-block` 是 4.8 秒。

## 2. 一个纠正：`duration` 缺失不是零件的个体差异，是 block/component 的结构差异

路线图原文写「部分零件没有 `duration` 字段（实测 `caption-kinetic-slam`、
`caption-editorial-emphasis` 均为 null）」，读起来像是上游漏填。全量核对后不是：

```
description  134 / 134   str，21–218 字符，无空值
tags         134 / 134   list，最多 8 个，去重后 138 个
duration     109 / 134   int 95 + float 14，4–24 秒
dimensions   109 / 134   {width, height}，全部 1920×1080
```

109 正是 block 的数量。上游 `skills/hyperframes-registry/SKILL.md` 写明：block 是独立子合成，
自带画布与时间轴；component 是贴进宿主的片段，两者都没有。**所以 25 个 component 没有
`duration`/`dimensions` 是设计，不是遗漏。**

因此契约里对 component 显式写 `null` 而不是省略键——调用方要能区分「它本来就没有自己的画布」
和「我们忘了记」。门禁对形状翻转失败关闭：block 缺时长、component 多出时长，都判红。

新增 `assert_authoring_fields()`：对 134 项逐项打开

## 4. GREEN

`scripts/check_motion_catalog.py` 新增 `authoring_facts()`，在扫描时校验并输出这四个字段。
它是**重算**而不是读取——`--write` 生成的内容与门禁比对的内容出自同一个函数，所以上游
submodule 一升级，两边一起变，不存在「契约里留着上一版描述」的中间态。

```
$ python3 scripts/check_motion_catalog.py --write
$ python3 scripts/check_motion_catalog.py
motion catalog and rights ledger are valid: 134 items (109 blocks / 25 components,
100 official previews), 125 with runtime remote dependencies,
conclusions={'cleared': 7, 'needs_asset_replacement': 2, 'needs_localization': 57,
'needs_localization_and_asset_replacement': 68}
EXIT=0

$ python3 scripts/test_motion_catalog.py
motion catalog tests passed: app-showcase tamper matrix rejected
executed checks: 12
EXIT=0
```

契约 103,086 字节 → 145,097 字节（+42,011 B，+41%）。这份契约随 Executor 一起冻进安装包
（`agent.py:_resource_root()` 从 `sys._MEIPASS` 读它），所以这 41 KB 是真实的包体成本。

## 5. 失败矩阵

篡改矩阵从 9 条加到 12 条，新增三条都是「有键但内容是假的」——只断言键存在的测试会全部放过：

| 篡改 | 期望 |
| --- | --- |
| 把某项 `description` 改成一句听起来对的转述 | 门禁红 |
| 把某个 block 的 `duration` 改成 999 | 门禁红 |
| 给某个 component 塞一个 `duration` | 门禁红 |

三条实测均判红。另外 `authoring_facts()` 本身对上游侧失败关闭：描述为空、tags 不是非空字符串
列表、block 时长非正、`dimensions` 键集不是 `{width, height}` 或非正整数、component 出现
时长或画布，逐条 `fail()`。

## 6. 真实边界与下游影响

四个消费方逐个核实：

| `check_offline_motion_catalog` | PASS |
| `check_motion_asset_overlay` | PASS |
| `check_motion_catalog_release` | 需要更新输入 pin，见下 |

`contracts/video/motion-catalog-release.v1.json` 把目录契约的 sha256 锁为输入，目录一改就漂：
`5f80274…` → `5d09399…`，已更新。

**产物本身未受影响，这是静态确认的而不是「跑了一遍没事」**：
`build_motion_catalog_release.py:_compose_item()` 只读 `item["name"]` 与 `item["files"][].path`，
新增的四个字段一处都没读，所以 `generated`（fileCount 310 / aggregate `38160d1c…`）不变。

**本机无法端到端复核这一条**：`check_motion_catalog_release.py` 需要 `.local/` 下的离线暂存与
发布构建，两者在本机都不存在。用 `git stash` 验证过它**在本次改动前就是红的**，失败原因同为
`release manifest.json is missing; run the release build first`——即本次改动没有让它从绿变红。
真正跑通这道门禁需要先跑离线依赖构建，留给需要出包的那次。

## 7. 没做什么

- **没有改 prompt。** `agent.py:_first_message_contract()` 现在仍然把 134 个裸 id 塞给模型；
  把这些字段真正喂进去是 PC-04；
- **没有做点缀型/内容型分档。** 那是 PC-03，且本任务的数据把它的判据修正了：
  25 个 component 天然是点缀（贴进宿主的片段），分档问题只存在于 109 个 block 之间；
- **没有碰文案替换。** 零件的文案写死在 HTML 里且只有 6 个零件带 params（12 个全是颜色），
  那是 PC-02。
