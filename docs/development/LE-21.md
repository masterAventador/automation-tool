## T1 矩阵与 Executor 故障注入

状态：已完成

唯一矩阵为 `contracts/quality/local-video-editing-failure-matrix.v1.json`。七个场景按
Roadmap 顺序固定公开结果，并只能引用仓库内可执行的 pytest 或 cargo test；门禁
会核对严格根字段/场景字段、runner、文件后缀、仓库相对路径和真实函数声明，文档
段落不能冒充测试证据。

### TDD

RED：先加入 `scripts/test_le21_failure_matrix.py`，首次运行失败为：

```text
FileNotFoundError: contracts/quality/local-video-editing-failure-matrix.v1.json
```

Green：补齐矩阵和三类原先不够精确的注入后：

- 素材在批准后、渲染前被删除，固定归 `source_changed`，不创建产物；
- `ENOSPC` 与 `EACCES` 分别注入工作文件分配点，均固定归
  `workspace_unusable`，不泄露异常上下文、不留半成品；Rust 再把该 Worker 码投影
  为 `resource_exhausted`，而不是误报素材损坏；
- 启动真实睡眠子进程并令 deadline 立即到期，确认 `_ProcessTimedOut` 返回前子进程
  已退出；执行层另确认固定 `timed_out` 且清掉 partial output。

专项结果：矩阵 gate 3 项、`test_visual_render_execution.py` 82 项全部通过。

## T2 Rust ledger 与真实 Worker 生命周期

状态：已完成

macOS 上运行 Unix 权限专项、跨平台 ledger 与真实 lifecycle：

```text
local_editing_job_ledger: 9 passed
local_editing_job_ledger_platform: 4 passed
local_editing_lifecycle_platform: 5 passed
```

后一组不是状态机假对象：它启动真实 Python Worker、完成带 HMAC 的 loopback 握手，
再分别制造协作取消、紧急停止、首代进程崩溃和 App 组件退出/重建。验收终态为：

- queued/running 两种取消竞争都只落一次 `cancelled`；
- 协作取消后 Worker 仍活着，紧停后进程确实消失；
- 首代 Worker 被杀后只恢复一次，generation 与 recovery attempts 均为 1；
- App 组件退出会停止旧 Worker；新组件从私有 checkpoint 恢复 running job，不重新
  create/dispatch，最终成功且 recovery attempts 仍为 1。

## Code Review

结构化审查发现并修复三项：

1. 初版矩阵 gate 没拒绝额外字段，也没绑定 runner 与 `.py`/`.rs` 文件类型；现已
   严格校验，避免一个普通字符串或错语言文件冒充可执行证据。
2. 真实超时测试若未来回归，断言失败时可能把测试子进程留在机器上；测试现在用
   `finally` 兜底清理，但断言仍发生在兜底前，继续能捕获生产代码没有先停进程的
   回归。
3. Windows 首轮执行 `local_editing_job_ledger.rs` 得到 `running 0 tests`：文件被
   顶格 `#![cfg(unix)]` 屏蔽，原矩阵只查锚点文本会把它误算为跨平台证据。门禁现
   拒绝整个 binary 被平台 cfg 屏蔽的 Rust 证据；资源失败投影与两种取消竞争已移
   入 `local_editing_job_ledger_platform.rs`，macOS 实际执行 4 项。

修复后复验矩阵 3 项、Executor 82 项、Rust 9+4+5 项以及 Ruff/格式检查，复审无待
修 finding。

## T3 Windows 真机与 LE 收口

状态：已完成

Windows 首轮矩阵 3 项、Executor 82 项、跨平台 ledger 4 项、真实 lifecycle 5 项
已通过。完整 integration 首轮在 PostgreSQL session fixture 失败：共享 helper 强制
Windows 调用 `initdb`，而真机只有已运行的 Docker Desktop。曾尝试安装原生工具，
但 Chocolatey 下载停滞、winget 的 EDB installer 又因临时目录写入失败退出；两次
均未安装服务或工具，pending/partial、此次 winget/installer 日志和临时目录已删除，
共享 Chocolatey 日志中的自动生成密码参数已原位脱敏，未脱敏模式计数为 0。

这里不以跳过数据库测试收口，而是对共享 helper 做 TDD：先要求“Windows 三个原生
工具全部不存在时使用隔离 Docker Compose”，RED 为
`initdb is required for native Windows PostgreSQL acceptance`。Green 后采用三态：

- `initdb`、`pg_ctl`、`createdb` 全部存在：保持原生 Windows 临时集群；
- 三者全部不存在：使用与其他平台相同的 Compose `up --wait` / `down --volumes`；
- 只存在一部分：固定报 `partially installed`，不让损坏安装被 Docker 掩盖。

helper 5 个分支/诊断测试、Ruff 与格式检查通过。Code Review 发现并修复 shebang
文件模式、过时 `noqa`、嵌套 context manager，并补齐“完整工具链仍走原生”防回归
测试；复审无待修 finding。

Docker Desktop 在 SSH 登录态下不能调用桌面凭据助手。第二轮 TDD 因此要求 Compose
的 `up`/`down` 共用一个临时 `DOCKER_CONFIG`，不修改调用方环境且退出后删除；真机又
证明完全空的配置仍会回退到凭据助手，所以配置中显式声明 Docker Hub 匿名 `auths`。
专项 5 项和 Windows 真实 `postgres:18.4-bookworm` 拉取均通过。

数据库启动后，Windows 全集成暴露三项平台差异，均按 RED→GREEN 和逐项 Review 最小
修复：

- PCM 的句柄 `ctime_ns` 与路径 `ctime_ns` 不一致，改用两者一致的 Windows
  `birthtime_ns`，其余设备、inode、类型、大小和 mtime 校验不变；
- Windows 文本模式把 PCM 中的 `0x1a` 当作 EOF，读取句柄加入 `O_BINARY`；两个真实
  FFmpeg/VAD 测试复验为 `2 passed`；
- 独立进程组收到 `CTRL_BREAK_EVENT` 后 Uvicorn 正常清理但返回 3；只在停止函数确认
  进程仍存活且亲自发送 Break 后接受该返回码，仍继续核对端口释放与零残留进程。真实
  PostgreSQL + Uvicorn 用户 API 往返复验为 `1 passed`。

Windows 最终运行除 LE20 所属 PyInstaller 完整候选构建外的整个 integration 目录，
结果为 `459 passed, 29 skipped`；排除项没有被记作 LE21 通过，仍由 LE20 的正式候选包
验收持有。连同矩阵 3、Executor 82、Rust ledger 4 和真实 lifecycle 5 项，七个场景均
有可执行的双平台证据。最终 Review 无待修 finding。
