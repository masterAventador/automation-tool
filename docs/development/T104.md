## 结论先行

**内置 Chromium 没有踩 07-26 那个 entitlements 坑。** 07-26 20:52 那个已签名已公证的正式包里，
Chromium 在包内那一份被真实拉起、真实求值，`[1,2,3].map(n => n * 2).join("-")` 返回 `2-4-6`，
渲染进程确实起来了。这不是读 entitlements 推断的，是跑出来的。

覆盖率从**「11 个里跑了 2 个」变成「11 个里跑了 5 个」**，剩下 6 个逐条列名打印，不再是一个匿名的数字。

门禁能真的红：**在一台只改了渲染进程 helper 的 `allow-jit` 授权、其余字节完全相同的 Chromium 上，
门禁退出码 1**；同一棵树补回 `allow-jit` 就退出 0。变量被隔离到了单独一项授权上。

## 一、为什么原来那道门禁碰不到 Chromium

`check_packaged_javascript_runtimes.py` 按**文件名** `node` 找运行时。内置 Chromium 不叫 `node`，
所以从来不在扫描范围里。脚本自己把这件事印在每次输出里（「其余——内置 Chromium 也在内——没有被执行过」），
诚实，但那行字本身不构成检查。

## 二、探针为什么用 CDP，不用 `--dump-dom`

先试了最省事的办法：`--headless --dump-dom` 加一段写进 DOM 的 JS。**它挂住不返回。**

这里差点得出错误结论。**做了对照组**：拿本机 Playwright 自己那份 Chromium
（`~/Library/Caches/ms-playwright/chromium-1228`，**同一版本 149.0.7827.55**，未经本项目签名）
跑完全相同的命令 —— **同样挂住**。

所以 `--dump-dom` 在 Chrome 149 的 new headless 下不可用，**与包无关**。
如果没跑这个对照组，这里会变成一份「内置 Chromium 疑似损坏」的错误报告。

改用 CDP：`--remote-debugging-port=0` → 读 `DevToolsActivePort` → WebSocket → `Runtime.evaluate`。
这是 Playwright 驱动它的同一条路，也是唯一能把**值**从渲染进程 V8 取回来的调用。
WebSocket 客户端只用标准库手写（约 90 行）：门禁在打包期跑，那时不保证存在装了 Playwright 的虚拟环境，
**跑不起来的门禁等于没有门禁**。

探针表达式用 `[1,2,3].map(n => n * 2).join("-")` 而不是常量：箭头函数加数组方法，
答案只可能来自一个活着的 V8。

### 第二轮 RED（失败信息质量，2 项）

第一版实现跑通后，在真包上造出来的红是这样一句：

```

```

**这重犯了 07-26 那个错误的一半。** 当时 `capture_output=True` 把 V8 的 abort 信息吞了，
真实原因是人手工重跑同一条命令才拿到的。我的第一版用管道，而管道只有进程退出后才能读；
浏览器如果是挂住而不是退出，它的解释就跟着管道一起丢了 —— 而且未被读取的管道写满 64 KB 会**把被测进程本身卡死**。

补了两条测试。这里有个坑值得记下来：`test_output_survives_a_browser_that_had_to_be_terminated`
第一次写成 `exec sleep 30`，**它绿了——但是绿错了**：`communicate(timeout=30)` 正好等到夹具自己睡醒，
整轮测试因此耗时 34 秒。把夹具改成 `sleep 600`（**故意长于门禁里所有超时**）之后才是真红：

```

  endpoint within 2s; it is running but unable to serve a page. the browser
```

改成**写日志文件而不是管道**（任何时刻都可读，也不会写满卡死），并把负返回码翻译成信号名。

## 四、真包上的红绿（正式包那一份，不是构建期暂存目录）

用 07-26 20:52 那个 DMG，`hdiutil attach -readonly -nobrowse` 只读挂载。

| # | 对象 | 退出码 | 关键输出 |
| --- | --- | --- | --- |
| 1 | **正式包**（DMG 内 `.app`） | **0** | `the embedded browser evaluated [1,2,3].map(n => n * 2).join("-") to '2-4-6' using 3 binaries` |
| 2 | **对照**：渲染 helper 重签，**带** `allow-jit` | **0** | 同上 |
| 3 | **故意造坏**：渲染 helper 重签，**去掉** `allow-jit` | **1** | `exit -9: the browser was killed by signal 9 (SIGKILL). the browser produced no output` |

第 3 条的红，逐字如下：

```
packaged JavaScript runtime check failed: a runtime in this package cannot evaluate an expression.
  <BUNDLE>/.../Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing
    exit -9: the browser was killed by signal 9 (SIGKILL). the browser produced no output
```

第 2、3 两棵树**除了渲染进程 helper 那一项 entitlement 之外逐字节相同**，所以这条红确实归因于 `allow-jit`。

### 造坏的过程走了三次弯路，记下来免得重走

| 做法 | 结果 | 为什么不能用 |
| --- | --- | --- |
| `codesign --deep` 整个 app，去 entitlements | 破/对照**都** SIGKILL | `--deep` 毁掉嵌套封签；macOS 直接杀进程，把待测变量盖住了 |
| 按 `release_assembly.signable_nodes` 顺序逐个重签（先 ad-hoc，后真 Developer ID） | 破/对照**都** SIGKILL | 签名 `--verify --deep --strict` 显示有效，仍被杀；重签整棵 Chrome 树本身就会破坏它 |
| **只重签渲染 helper 一个 `.app`** | 对照 0 / 破 1 | ✅ 变量隔离成功 |

对照组是这里的关键：前两次如果只跑「破」的那一棵，会得到一个**看起来完全正确的红**，
然后据此宣称「门禁抓住了 JIT 缺失」——而实际上它抓的是签名被我自己弄坏了。

## 五、覆盖率：从 2/11 到 5/11，且剩下的逐条列名

正式包上的实际输出：

```
11 binaries are granted allow-jit; this gate exercised 5 of them by evaluating an
expression. 6 not exercised — a JIT grant that never runs is a claim nobody checked:
      .../Helpers/Google Chrome for Testing Helper (Alerts).app/.../Helper (Alerts)
      .../Helpers/Google Chrome for Testing Helper (GPU).app/.../Helper (GPU)
      .../Helpers/app_mode_loader
      .../Helpers/chrome_crashpad_handler
      .../Helpers/web_app_shortcut_copier
      .../local-executor/package/automation-tool-executor
```

新覆盖的 3 个是**测出来的不是假设的**：探针求值成功后，趁浏览器还活着从 `ps` 拉进程树，
按可执行文件路径记录**真正跑起来的**二进制（浏览器主进程、`Helper`、`Helper (Renderer)`）。
「渲染进程跑了」和「我们启动了一个通常会拉起渲染进程的东西」是两件事，这里取前者。

剩下 6 个为什么没跑，逐条说明：

| 二进制 | 为什么没被求值 | 判断 |
| --- | --- | --- |
| `Helper (Renderer)` 之外的 `Helper (GPU)` | 无头模式下这次没有拉起独立 GPU 进程 | **有价值但不划算**：强行逼它起来会让打包期门禁变脆；且 GPU 进程的 JIT 缺失表现为降级而非整条 RPA 死亡 |
| `Helper (Alerts)` | 只在弹原生对话框时才起 | 无头下不可达；不影响 RPA 主链路 |
| `app_mode_loader`、`web_app_shortcut_copier` | Chrome 的 PWA/快捷方式工具，本产品从不调用 | **本来就不该求值** |
| `chrome_crashpad_handler` | 崩溃上报器，不含 JS 引擎 | **本来就不该求值**；它带 `allow-jit` 只是因为 Chrome 给全部 helper 统一签发 |
| `automation-tool-executor` | PyInstaller 打的 Python，CPython 不 JIT | **本来就不该求值**；该授权属于预防性配置 |

也就是说：**6 个里有 4 个属于「按设计不需要求值」**，真正还缺覆盖的是 GPU helper 一个，
Alerts helper 属于无头下不可达。这个判断写在这里，是为了让下一个人能推翻它，而不是让他重新发现它。

## 七、失败矩阵

| 情形 | 行为 |
| --- | --- |
| 包里没有内置浏览器 | **判失败**。扫描不到东西不等于通过——本仓库每一次静默事故都是这个形状 |
| 浏览器是软链 / 丢了可执行位 | 各自判失败并说明，不静默跳过 |
| 浏览器启动即退出 | 报退出码 + 日志内容 |
| 浏览器起来了但一直不开 DevTools | 90 秒后判失败，**并带上它此前写过的日志**（这是第二轮 RED 修的） |
| 浏览器被信号杀死 | 翻译成 `killed by signal 9 (SIGKILL)`，不留 `-9` 给人自己查 |
| 求值抛异常 / 返回值不对 | 报实际值与期望值 |
| 进程清理 | 成功、失败、超时、异常四条路径都走 `finally`：`terminate` → 超时 `kill` → `pkill -f <本次唯一临时目录>` → 删目录。`pkill` 模式是本次运行独有的临时路径，只可能命中自己拉起的子进程 |

## 八、边界与未尽事项

- **只在 macOS 上验过。** Windows 的内置 Chromium 链路未覆盖，探针里的 `ps` 进程树和信号名都是
  POSIX 写法。Windows 需要单独任务，标 `🔍 待验收`；
- **无头**：探针固定传 `--headless`，符合项目「自动化不得弹窗打断用户」的硬要求。全程未出现可见窗口；
- 主证据用的是 07-26 20:52 那个包（界面落后但包结构与签名为真）。**已在更新的包上复核过**：
  07-27 01:16 由 `wt/release` 那条并发线新构建、`flags=0x10000(runtime)` 的正式 `.app`，
  门禁同样退出 0，同样 `2-4-6`、同样 5/11。两个不同时间、不同构建的正式包结论一致。
