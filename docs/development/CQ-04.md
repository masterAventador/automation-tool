## CQ-04 独有的增量：台账不许虚标

作为终验，它必须能回答"这 87 项里哪些是真完成的"。AV-04 的门禁检查字段齐全、计数一致、
只有一个活跃任务——它检查不到**内容与状态是否相符**：一个任务完全可以字段写全、状态标
`🔍 待验收`，而「遗留项」小节只有一个空表头，读的人无从判断它离完成还差多远。

所以补了这条判据，并对全部 87 项实跑。

## 判据被实测收窄了四轮，每一轮都是判据错而不是台账错

| 轮次 | 报出 | 追下来是什么 |
| --- | ---: | --- |
| 1 | 20 处 | 解析器只认两列表格，三列（项/状态/归属）整张读成空 |
| 2 | 18 处 | 只认表格，列表写法（`- 🔍 **待凭据**：…`）整节读成空 |
| 3 | 26 处 | 穷举"未做/待凭据/…"判未闭合，漏掉没想到的"待加固"；且把**下游承接说明**（"BU-04：把租约接进执法点"）当成本任务的缺口 |
| 4 | 4 处 | 只认无序列表，有序列表（`1. **…**`）和散文段落又读成空 |
| 5 | **0 处** | 改成问格式无关的问题后 |

结论有两条：

1. **判据不该去解析格式**。本仓库的遗留项至少有五种写法（两列表格、三列表格、无序列表、
   有序列表、散文段落），每修一次就冒出一种新的。最终问的是格式无关的问题——那一节里
   有没有实质文字。
2. **"已完成不该有遗留项"这条判不了**。本仓库的「遗留项」既写本任务的缺口，也写下游承接。
   第三轮 `✅ 已完成` 一侧报出的 22 处几乎全是后者。判据分不清就不判——**一条会稳定误报
   的门禁比没有门禁更糟，它会训练人忽略它**。硬要判就得改台账约定（承接说明另开小节），
   那要动 76 个文件，价值不抵成本。

**先怀疑自己的检查器，再怀疑被检查的东西。** 如果第一轮就信了那 20 处，我会去"修"20 个
根本没问题的台账。

## 又一次自己的假绿

给格式无关判据补了 3 个测试，跑出来还是 `11 passed`——因为我把新测试类追加到了
`if __name__ == "__main__": unittest.main()` **之后**，模块执行到那一行就开始跑测试，
后面的类还没定义。移到前面才是 14 项。

**这是同一种错误在本次会话里第二次犯**（上一次是把测试写成类风格而文件用函数风格）。
两次都靠"测试数量对不上"发现。看见绿先数数量。

## B站实现完整性逐项核对（2026-08-04）

CQ-04 的定义写着「B站……无凭据则核对**完整实现、Mock/契约证据和 `待凭据验收` 状态**」。
上一轮只做了「状态与证据自洽」的台账扫描，本轮逐项核对这三件事。

### 一、`待凭据验收` 状态名副其实 ✅

`contracts/publishing/bilibili-open-api.v1.json` 的 `pending_credential_verification`
列了 11 项，逐条读过——**每一项都确实只有真实账号才能验**：控制台 scope 清单、数值限流
配额、refresh_token 有效期、`addit_info.state` 完整取值、标题 79/80 的真实判定、沙盒与
正式环境差异、白名单影响、全链路扫码换 token、未开放浏览稿件的 `ptime`、Webhook 真实
推送与签名核验、`viewlist` 真实分页行为。

**没有一项是「本机能验而没验」的**，这个状态名副其实。

### 二、Mock/契约证据 ✅

- 10 个 B站 单测文件（签名、投稿守卫、对账、基础设施守卫、查询守卫、运行时、API、
  bootstrap、素材、发布）；
- 66 份契约夹具，含大量**拒绝路径**样例（简介 251 字、封面 http、转载缺来源、原创带
  来源、格式错误的 state 等）。

证据形态与厚度都对得上「无凭据时可达的最高标准」。

### 三、完整实现 ❌ 发现一处真实缺口

按「契约声明的每个端点是否都有消费方」逐个核对（判据取字段名而非 URL 字面量——
代码从契约读 URL，这是单一事实源的正确做法，硬编码反而是错的）：

| 端点 | 消费方 |
| --- | --- |
| `refresh_token_url`、`upload_init_url`、`part_upload_url`、`upload_complete_url`、`small_file_upload_url`、`cover_upload_url`、`archive_add_url`、`archive_view_url`、`archive_viewlist_url` | ✅ 各 1 处 |
| `authorize_pc_url`、`token_url` | 无 —— **有意**：授权码换 token 由用户在开放平台控制台完成后把凭据填进设置页，产品不实现 OAuth 授权页跳转 |
| **`type_list_url`** | **无 —— 这是缺口** |

**缺口内容**：契约写明 `submission.tid_from_type_list_only: true`，即投稿分区 ID 只能
来自 `type/list` 接口。而全仓没有任何一处调用它：`tid` 由用户在设置页
（`BilibiliServiceSettings.tsx:140`）手填进一个 `InputNumber min={1}`，后端
（`api/bilibili_publishing.py:70`）只校验 `Field(gt=0)`。

**用户可见后果**：产品不知道哪些分区 ID 合法，也无法给用户一份可选列表。填错的分区要
一直等到**真实投稿时**才由平台拒绝——而那正是 CLAUDE.md 反复要防的「失败推迟到最贵的
时刻」。涉及 `type_list`/分区的测试全仓 **0 处**，所以既有测试也照不出它。

**本轮不修**：按 §2 的阶段边界，这不是「当前功能不可用」也不是已复现 bug 导致的阻塞
（B站 整条链路本来就在等凭据），属于登记后延后处理的范围。修法明确——调 `type/list`
拉回分区树，设置页改成选择器，后端按拉回的集合校验 `tid`；需要凭据才能取到真实分区树，
因此天然与 B站 真实验收同批做。

### 结论

三件事里两件成立，一件发现真实缺口并已登记。**本条遗留项从「未做」改为「已做，发现
一处缺口」**——缺口本身随 B站 凭据到位后与真实投稿同批修复验收。
