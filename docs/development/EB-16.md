### RED-2 既有审计脚本不覆盖首发包形态（3 项失败）

实现模块后同一命令 `Ran 20 tests ... FAILED (failures=3)`：

含义：`audit-release-bundle.mjs` 不接受内置浏览器子树声明（内置 Chromium 带上游
symlink，整包扫描必然拒绝）；`audit-production-package.mjs` 不拒绝隐藏测试窗口配置
`"visible":false`，也不拒绝 WebDriver 驱动标记。

### RED-3 真实产物暴露的真实缺陷（本任务最重要的一条）

第一次真实 `tauri build` 出包后，包内容门禁对**真实产物**失败：

```text
[EB-16] Built application: .../release/bundle/macos/自动化运营工具.app
check_embedded_browser_package.PackageRejected: release package rejected:
embedded browser distribution rejected: symlink entry drifted
```

实测定位（真实产物内部文件）：

```text
暂存树： 331 files, 5 symlinks, 343MB
包内树： 334 files, 0 symlinks，.app 总计 761MB
包内 Framework 目录只剩 Versions/ 与一份 230,463,104 bytes 的实体二进制，
Resources / Libraries / Helpers 三个符号链接全部丢失
codesign --verify --strict "…/Google Chrome for Testing.app"
  → code has no resources but signature indicates they must be present
```

结论：**Tauri bundler 的 `bundle.resources` 复制会跟随并丢弃符号链接**，把 Chrome
for Testing 的 macOS Framework 结构拆坏、重复了 230MB 框架二进制、并使上游代码签名
失效。这样的包在用户机上会被生产 Rust 解析器（EB-06）判为“浏览器组件损坏”，启动门禁
直接拦在工作台之前。若只做配置断言或脚本检查，这个缺陷不会暴露。

### RED-4 独立审查复审暴露的门禁绕过（合并前修复）

第一轮实现把"跳过内置浏览器子树"绑定成了**调用方声明式**：只有传 `--embedded-browser`
才跑逐文件摘要门禁。独立审查指出并实测复现了绕过——包里有内置浏览器、树里没有符号链接
（正是 RED-3 那个 bundler 解引用形态，也是所有 Windows 目标的常态）、不传参数：

```text
python3.12 scripts/test_embedded_browser_package.py \
  ReleaseBundleAuditTests.test_a_packaged_browser_always_runs_the_digest_gate
AssertionError: 0 == 0 : [P9-05] Release bundle audit passed: 5 files, 46 bytes
```

即：**摘要门禁一次都没跑，退出码 0**。macOS 上看起来"绑死了"纯属巧合——上游 Chromium
带符号链接，整树扫描必然拒绝。当时仓库里 5 个调用点只有 `run_eb_16_acceptance.py`
传了该参数，其余 4 个（`run_p9_03/04/06/07_acceptance.py`）都没传，而 Windows 目标
设计上就没有符号链接，因此 Windows 发布审计**永远不会**被动触发门禁。

修复：绑定改成基于**资源存在性**——`auditReleaseBundle` 自己按平台推导唯一合法位置
（`Contents/Resources/embedded-browser` / `embedded-browser`）并 `lstat` 探测，存在即
强制执行摘要门禁；`--embedded-browser` 降级为只能"确认"该位置，不再是开关。`lstat`
只有 `ENOENT` 才视为"本包不含浏览器"，权限或 I/O 错误一律拒绝，不退化成跳过。

## 失败矩阵

- **打包器语义**：符号链接被跟随/丢弃 → 摘要门禁拒绝，发布装配器改为自行装入（RED-3）；
- **多套浏览器**：包内出现第二个目标根、第二个浏览器可执行文件、`ms-playwright`
  目录或 headless shell → 拒绝；体积上限（420 MiB 浏览器树）本身也拦住“混入第二个
  架构”；
- **包内容泄漏**：WebDriver 二进制/插件符号、调试端口环境变量、开发源、测试凭据、
  测试专用命令、隐藏测试窗口配置 → 拒绝；
- **完整性**：包内浏览器文件内容与 Manifest 不一致、缺失、多出、符号链接漂移、可执行文件
  缺失 → 拒绝；**信任根边界见「真实边界」一节**——期望摘要来自树内未签名文档，该门禁是
  构建完整性/损坏检测，不是对抗性防篡改；
- **平台/架构**：目标与平台不匹配、非本目标包 → 拒绝；
- **安装介质**：DMG 校验和、只读挂载、安装后逐文件重新核对，任一不一致 → 失败；
- **签名**：外层封章覆盖最终包内容（装配后必须重新签名，否则 `codesign --verify`
  会因资源新增而失败）；内层上游签名必须原样保留（一旦重签，EB-05 逐文件摘要立即
  失效——这条冲突已登记进遗留项）；
- **门禁被绕过**：路径豁免与摘要门禁机制绑定，任一调用方给出 `--embedded-browser`
  都会连带执行摘要门禁；清单里的目标字段非法、子树不在唯一合法位置、门禁不通过、
  解释器不可用，四种情况全部拒绝豁免；
- **用户数据**：启动阶段只使用本次运行的临时 `HOME`，用户真实 App 数据目录不读不写；
  运行前后 inode 与条目数不一致即判失败；
- **装配失败**：装入中途失败会删除半成品目录并把原始异常抛出，重跑不需要人工清理；
- **失败路径清理**：挂载点在 `attach` 失败时也不会用 `detach` 的二次异常掩盖真实原因；
  安装目录与挂载点在任何一步失败后都会被清理；包内浏览器探针先按本次 Profile 终止
  整个进程树再断言零残留；
- **进程与残留**：退出后无引用安装目录的进程、无 Launch Services 注册；卸载后安装目录
  为空；首次运行创建的私有数据逐条清除；
- **端口与资源隔离**：8765 与数据库端口先检查再使用，Compose project/容器/卷全部带
  `automation-tool-eb16-<pid>` 前缀，结束即 `down --volumes`。

## 正常用户路径验收

用户路径 = 拿到 `.dmg` → 挂载 → 把 App 拖进应用目录 → 双击运行 → 用完退出 → 删除
App。本任务按这条路径真实走通：真实 DMG 校验/挂载/拷贝安装、真实执行已安装 App 主程序
（macOS Launch Services 记为前台 GUI 应用）、真实首次运行初始化、真实退出、真实删除。

未能覆盖的一段：**读取 App 窗口里渲染出来的工作台画面**。本机自动化进程没有被授予
macOS「屏幕录制」与「辅助功能」权限，`screencapture` 只能拿到桌面壁纸（已实测确认，
截图中不含任何窗口），因此无法用截图或控件树断言“工作台页面已显示”，也无法模拟点击各
个页面。作为替代，本任务用真实 HTTP + 生产 Rust 逻辑两路证据把这一段夹住：一路是已安装
App 经生产网络桥发出的真实启动检查请求；一路是对已安装产物运行生产启动门禁逻辑，确认
四项输入全部 `Ready`（启动门禁只有全部就绪才会挂载工作台）。完整“看见并点开工作台各
页面”归入遗留项，由 EB-17 干净机纵向验收在可授权的环境中闭合。

## 真实边界

- **Tauri bundler 会跟随符号链接**：这是本任务在真实产物上发现的真实边界，直接决定了
  内置 Chromium 不能走 `bundle.resources`，必须由发布装配器保留符号链接装入并重新封章；
- **上游 Chrome for Testing 没有 bundle 级代码封章**：官方归档里没有任何
  `_CodeSignature`，`codesign --verify` 对那个嵌套 `.app` 必然报
  “code has no resources but signature indicates they must be present”。它的代码签名
  是 Mach-O 内嵌的 `adhoc, linker-signed`。因此外层不能用 `--deep` 校验，内层只能按
  Mach-O 逐个校验（本任务采用把二进制复制到 bundle 外再 `codesign --verify` 的方式）；
- **重签内层与摘要 Manifest 冲突**：Developer ID + 公证要求包内所有可执行代码由本方
  身份签名，而重签会改写 Mach-O，使 EB-05 的逐文件 SHA-256 全部失效。正确解法是把
  签名提前到暂存阶段（先签、后算摘要），属签名凭据任务，已登记遗留；
- **首发包里没有产品账号/Installation**：工作台的数据查询在 Rust 网络桥内先要
  `exchange_device_session`，全新安装没有设备凭据时会在发出 HTTP 之前就失败，因此
  Control Plane 上观测不到 `/api/v1/workbench/*`。这不是包缺陷，是首期本地 Profile
  的既有形态；已据此把验收断言改为“启动检查真实请求 + 启动门禁输入全 Ready”，并把
  完整工作台数据链路留给 EB-17/U9；
- **签名身份**：本机没有 Apple Developer ID 证书与公证凭据，全程 ad-hoc
  （`signingIdentity: "-"`），断言里显式禁止出现 Developer ID / Apple Distribution，
  避免把 ad-hoc 结果冒充正式签名；
- **合并配置是推导产物，不是 Tauri 真正用的那份**：`run_eb_16_acceptance.py` 的
  `merge_configuration` 是普通递归字典合并，而 Tauri v2 的 `--config` 用 JSON Merge Patch
  （RFC 7386）——`null` 表示**删除键**、数组整体替换。当前 overlay 里没有 `null`，两者结果
  等价，所以本次断言成立；但 overlay 一旦出现 `null`，这份推导配置就会与真实构建配置静默
  漂移。要根除只能让 Tauri 自己吐出最终合并配置；
- **摘要门禁的信任根只到"构建完整性"，不到"对抗性防篡改"**：`verify_distribution` 的每个
  文件期望摘要来自 `staging/distribution-manifest.v1.json`——**一份位于被审计树内部、未经
  签名的文档**；`enforce_archive_lock` 校验的 `archive_sha256` 又是仓库契约里的公开常量。
  因此"改一个文件 + 重算它在 Manifest 里的 sha256/size + 照抄公开的 archive_sha256"这条
  路径可以通过门禁（独立审查已实测复现）。它能可靠拦住本任务真正要防的东西——bundler
  解引用符号链接（RED-3）、DMG 往返丢失、构建损坏、包错目标、混入第二套浏览器——因为这些
  都不会同步重算 Manifest。要升级成对抗性防篡改，必须给 Manifest 一个树外可信锚点：把每个
  target 的 Manifest 摘要（或 entries 的 Merkle 根）锁进
  `contracts/browser/embedded-chromium-staging.v1.json`，或复用项目既有的
  `executor-manifest.v1.sig` 那套 Ed25519 签名机制。本机只有 `macos-arm64` 的锁定归档，
  无法为三个 target 同时算出并锁定该锚点，已登记遗留项；
- **只覆盖 macOS arm64**：本机是 Apple Silicon，不做交叉打包；
- **主二进制字节标记的边界**：Tauri 会把整个前端产物编进主二进制，对它做无上下文子串
  匹配（例如 `"visible":false`、`chromedriver`）随时可能被第三方 JSON/locale 命中，
  造成难以定位的发版硬失败。因此隐藏测试窗口改由**实际用于构建的合并配置**做结构化
  校验，其余驱动名改由包内文件名门禁覆盖，字节标记只保留假阳性最低的 `tauri-driver`；
- **本轮回归发现的两处既有失败（与本任务无关，未夹带修复；均已在本任务之外单独修复）**：
  1. `python3.12 scripts/test_embedded_chromium_staging.py` 的
     `test_windows_target_stages_without_symlinks` 报
     `locked executable missing from staging`。已用 `git stash` 在改动前后各跑一次
     确认失败完全一致，属既有缺陷。**根因与修复（提交 `30826cd`，独立于本任务）**：
     测试合成归档的可执行位判定只覆盖 macOS 可执行名，`chrome.exe` 被写成 `0o644`，
     提取后不带执行位而被生产门禁正确拒绝。实测真实锁定归档 `chrome.exe` 为
     `0o100777`、`chrome.dll` 为 `0o100666`，fixture 已改为忠实反映该语义。该缺陷只在
     macOS 暴露：Windows 的 `st_mode` 对普通文件恒返回 `0o777`，执行位始终存在；
  2. `pnpm --dir frontend test:contracts` 211 通过 / 1 失败：`B5-08 owns one
