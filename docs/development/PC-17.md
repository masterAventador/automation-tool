## 0. 为什么判据是像素不是字数

同样九个字符：汉字约 9em、`iiiiiiiii` 约 2.3em、`WWWWWWWWW` 约 12em。
**用字数表达的上限，会随写进去的是什么而变成三个不同的上限。**
所以每槽记的是**容器可用像素宽度 + 该处字号**。

## 1. 探针踩到的第一个坑：不能在动效播放中途量

第一版探针加载页面后等 400ms 就量，结果：

```
容器可用宽度 -13 ~ 724 px      ← 负宽度
原始文案下纵向溢出 14 个槽
```

**负宽度是元素还缩在零附近**——量的是一帧没人看得到的画面。
改为先把零件自己的时间轴 `seek` 到末尾（与渲染 worker 同一个调用）再量：

```
容器可用宽度 53 ~ 724 px       ← 负值消失
字号 13 ~ 92 px
```

## 2. 第二个发现：14 个槽在原文下就纵向溢出

seek 到稳定点之后，这 14 个仍然溢出。那是**设计**——遮罩式揭示本来就纵向裁切文字。

**所以 PC-14 的溢出判据不能是「是否溢出」**，那会在一个字都没换之前就拒掉三分之一的
目录。只能是「**比原文多溢出了吗**」，而这需要把基线记下来。

`baselineOverflowsX/Y` 就是为这件事存在的。

## 4. 角色标注：本轮判定为不必要，理由如下

路线图原话是「48 个槽给模型看时需要知道每个槽是什么。原文本身已经是很强的提示
（`Maya Chen` → 显然是姓名），所以这件可以最后做，甚至可能不需要」。

冻结的 48 条原文逐条读下来，确实如此——`Maya Chen`、`Host · Neuroscientist`、
`47.5K followers`、`figma.com`、`SFO`、`Prompt to replace this title`，每一条都自带
语义。**再加一层人工标注等于把同一个信息抄第二遍，而抄本会与原文漂移。**

若将来出现原文看不出用途的槽，再对那几条单独加标注，不必给 48 条都加。

## 5. 门禁自检（五种篡改）

| 篡改 | 结果 |
| --- | --- |
| 删掉一个已冻结的槽 | 拒绝 |
| 可用宽度改成 0 | 拒绝 |
| 原文与槽位表不符 | 拒绝 |
| 计数对不上 | 拒绝 |
| 基线溢出计数对不上 | 拒绝 |

门禁不重新测量（那需要浏览器），它守的是这份预算与冻结槽位表之间的对应关系——
两种腐烂方式：槽没了预算还在，槽在了预算没有。

## 6. 还差什么

**探针尚未接进任何自动流程**：改了槽位表或发布树之后要手工重跑一次。
更重的做法（把浏览器测量放进门禁）代价与收益还不匹配，等 PC-12 加第二批槽位时再评估。

## 7. 收口（2026-07-29）

第 6 节留了一条：「探针尚未接进任何自动流程，等 PC-12 加第二批槽位时再评估」。
PC-12 已经加完并重测，评估随之有了结论。

**两项交付物都已闭合：**

| 交付物 | 结论 |
| --- | --- |
| 像素预算探针 | 覆盖全部 **37 个零件 / 124 个槽**（`motion-part-slot-budget.v1.json` 的 `counts`），宽度 22~1840 px、字号 12~92 px，含 14 个基线纵向溢出的槽 |
| 每槽角色标注 | **判定不做**，理由见第 4 节：124 条原文逐条读下来都自带语义（`Maya Chen` 显然是姓名），再加一层标注等于抄第二遍，且两份会漂移 |

**探针保持手工重跑，这是有意的，不是欠账。** 把无头浏览器测量放进门禁的代价
（每次全量都要起浏览器、逐槽量六个时刻）与收益不匹配，而腐烂的两种形态已经被
现有门禁堵住了：

- 槽没了预算还在 / 槽在了预算没有 → `check_motion_part_slot_budget.py` 直接拒；
- 发布树里零件的 HTML 变了 → 渲染期 `render_part_working_copy` 会因锚点原文对不上
  抛 `SlotAnchorRejected`，**fail-closed，不是静默用旧预算**。

也就是说：预算过期的两条路径都会红，只是红在不同的地方。手工重跑不会被悄悄跳过。

### 7.1 预算的消费方仍未接上，那是 PC-14

`FilmSegment.slot_budgets` 已经带上了每段的预算，但 `require_within_budget`
目前**只有它自己的单测在调**——渲染路径上没有调用点。这不是本任务的缺口：
本任务交付的是「量出来并冻结」，用它去判溢出、超了回抛给模型改短，是 PC-14。
