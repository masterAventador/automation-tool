## 两条扫描线的分界，实测得出

最初写的是"静态扫描永远补不上可访问性树"，但注入验证时**第一次注入的泄漏静态扫描也抓到了**

## 原生源码为什么不能整文件扫

前端源码里出现上游项目名一律算违规，所以静态扫描读整个文件。Rust 与 Python 不同：
`HYPERFRAMES_FFMPEG_PATH` 是 Worker 的环境变量名，`skills/hyperframes-creative/frame-presets`
是素材根路径，`vendor/moneyprinterturbo` 是 Submodule 路径——CLAUDE.md 明确允许上游名出现在
代码、内部诊断和 SBOM 里。整文件扫会把这三处合法常量判成违规，唯一的"修法"是把词表放宽，
那等于把闸门拆了。

所以原生扫描换了判定口径：**只扫用户能读到的部分**，判据是机械的而不是"哪个模块算用户面"的主观判断——

1. **带中文的字符串字面量**＝运营文案或页面对象匹配的平台原文（Rust/Python 的标识符、
   路径和协议值都是 ASCII，这条把两者分开）；注释一律跳过，因为内部说明里写上游名是允许的；
2. **产物与导出文件名**＝落到用户磁盘上的文件。它不带中文，上一条看不见它；它也塞不进中文解释，
   所以只查上游名，不查未解释术语——对文件名要求"同句给出中文解释"是条不可能满足的规则。

## 已知误报：中文 docstring 被当成用户文案

原生扫描的判据是"带中文的字符串字面量＝用户可见文案"。docstring 也是字符串字面量，
所以一个中文写的技术说明会被要求给出术语的中文解释——2026-07-26 写
`pyinstaller_support.remove_browser_installer_scripts` 时实测撞上：docstring 里提到
`Chromium`，扫描要求改成"浏览器组件"。

当时的处理是把该 docstring 改回英文（与本仓库绝大多数 docstring 一致），不是放宽扫描。
但判据本身有缺陷：**内部技术文档不是用户文案**，这个误报会长期存在，并且会形成一个
错误的激励——逼人不敢用中文写技术注释。注释（`#` 开头）不受影响，只有 docstring 会。

修法是让扫描器识别 docstring（Python 里是模块/类/函数体内的第一个字符串字面量）并跳过。
没有在 CQ-02 内修，因为它需要自己的 RED，而当时 EB-17 正处于活跃任务位。
