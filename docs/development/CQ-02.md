**两种扫描的分界，实测过而不是想当然**。我最初写的是"静态扫描永远补不上可访问性树"，
但注入验证时发现**第一次注入的泄漏静态扫描也抓到了**——它会扫模板字面量里的常量部分。
换成一个值来自数据流、源码里根本不存在该字符串的可及名再试，结果才是决定性的：

| 注入的泄漏形态 | 静态扫描 | 运行时可访问性树扫描 |
| --- | --- | --- |
| 模板里的常量（`via Browser Use`） | 抓到 | 抓到 |
| **值来自数据流**（`via ${approval.videoSummary}`，值在运行时才有） | **50 文件全过** | **当场抓住** |

这才是必须新增运行时扫描的实际理由。

## 正常用户路径验收

运行时扫描本身就走真实用户路径：在 UI Harness 里逐页点击左侧导航进入 8 个页面，
再走完发布的发起 → 确认 → 终态，每一步都对**渲染后的**可访问性树取快照。
这一层证明的是 React 渲染结果；Rust 与后端产生的字符串见「遗留项」。

## 真实边界

1. **只覆盖 React 渲染结果**。Rust 侧（窗口标题、错误码文案）与后端（任务名、日志、
   产物文件名、导出内容）产生的用户可见字符串**都还没扫**，静态扫描根也不含
   `frontend/src-tauri/src` 与 `backend/src`。
2. **只在 UI Harness 里跑**，用的是受控测试 Adapter。真实数据（真实任务名、真实素材
   文件名）经过界面时会不会带出上游名，本任务没有验证。
3. **法务页白名单尚无对象**：契约声明了 `frontend/src/features/legal/third-party-software/**`，
   但该页面还不存在，白名单目前是空转的。
4. **词表是人工维护的**，新的上游依赖进来时要同步加词，没有机制强制这一点。
