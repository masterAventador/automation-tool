# LE-07 素材探测

用户可操作：是
证据类型：真实素材端到端读数（随包 ffprobe/ffmpeg 产出的判定、`stat` 读数与 sha256）

正式 App 的用户入口（导入素材 → 界面上看到时长/画幅/有无声音）属 LE-18，尚未接线，
所以本任务止于 `🔍 待验收`。已经到手的证据是**用户导入一个文件时这条链路真实产出什么**：
8 类真实素材逐格判定、13 个拒绝码逐个被真实文件触发、每条素材的事实真造出 `Material`。

LE-07 在 Local Executor 侧用随包 ffprobe/ffmpeg 读出一个源文件的事实——时长、分辨率、
编码、有无有效音频与响度、内容摘要——并保证这些事实**填得满 `Material` 且不含任何路径**。
路径与素材 ID 的映射留在本机，不上报 Control Plane。

不含把已验证路径下发给剪辑 Worker 的 Rust 装配（LE-12）。

### T1 代码质量审查（首轮不通过）与修复

**Critical 1：`ENAMETOOLONG` 逃逸成裸 `OSError`，完整私有路径进了异常消息。**

`_has_symlink_component(path)` 原本在 `try/except OSError` **之外**。而
`Path.is_symlink()` 只吞掉 `pathlib._IGNORED_ERRNOS = (ENOENT, ENOTDIR, EBADF, ELOOP)`，
**不含 `ENAMETOOLONG`**。实测复现（总长 369 字符，远在 4096 上限内，只是单个分量超过
`NAME_MAX` 255）：

```
BUG -> raw OSError errno 63
       private path leaked into message: True
```

两处后果：调用方按契约捕 `MaterialProbeRejected` 捕不到，失败关闭被绕过；异常消息带完整
本机私有路径，§7 被完整绕开——而本模块的固定文案 + 封闭拒绝码设计正是为了防这个。

**它此前被更早的判据遮蔽**：唯一构造超长分量的用例用的是 `"a" * 4097`，被总长上限先短路，
根本到不了软链那一行。新用例把单分量压到 300 字符、总长留在上限内，绕开遮蔽。

修法是把软链判据挪进 `try`：`_reject` 抛的是 `RuntimeError` 子类，不会被 `except OSError`
吞掉，所以软链拒绝仍按 `UNSAFE_PATH` 原样穿过，而 `is_symlink()`/`stat()` 的任何 `OSError`
统一落到 `UNREADABLE`。

补的两条用例先实跑见红（`OSError: [Errno 63] File name too long`），修完转绿。
变异体「软链判据挪回 `try` 之外」作为回归哨常驻。

## T2 ffprobe 读时长/分辨率/编码

**RED**：先写测试，实跑得到 `ImportError: cannot import name 'MAX_CODEC_NAME_CHARACTERS'`。

**GREEN**：71 passed。**覆盖率 156 语句 / 44 分支，100% 且 0 partial。**

### 三条实测结论如何落进实现

| 实测 | 实现 |
| --- | --- |
| 失败时 exit=1 而 stdout 是合法 JSON `{}` | **先判 returncode 再碰 stdout**；并有一条用例用「exit=1 + 完整合法负载」证明它，不判就会报出一条完全正常的 3 秒片 |
| stderr 带文件路径 | stderr 从不读回，异常消息固定为 `material probe rejected` |
| 图片没有 `duration` 键 | 判别用「键不存在」而非 duration==0；变异体把该判别反转会被 12 条用例杀掉 |

命令只用 `-show_entries`，不加 `-show_format`/`-show_streams`——两者会让选择变成叠加并把 `tags` 一起带出来，那是文件内攻击者可控的元数据。有专门用例断言 argv 里没有这两个开关且 entries 不含 `tags`。路径前有 `--` 分隔符，另有用例用 `-rf.mp4` 这种以短横开头的文件名钉住。

### 拒绝理由：不可区分的就不假装能区分

实测三种坏文件的结果**逐字相同**：

```
[notmedia.txt] exit=1 stdout={}
[corrupt.mp4]  exit=1 stdout={}
[empty.mp4]    exit=1 stdout={}
```

要分开「格式不支持」与「编码损坏」只能去匹配 ffmpeg 的英文诊断，既随版本与 locale 漂移，又正是 §7 禁止外传的那段文本。故合并为一个 `UNDECODABLE`，并在代码注释里写明依据。其余新增成员各自对应一个不同的用户动作：`NO_USABLE_STREAM`、`UNUSABLE_DURATION`、`TOO_LONG`、`UNUSABLE_FRAME_SIZE`、`FRAME_TOO_LARGE`、`PROBE_FAILED`。

### 与 `Material` 的形状对齐

音频素材的 `width`/`height` 产出 `None`（`Material` 禁止音频带画幅）；图片的 `duration_ms` 产出 `None`。时长与画幅上限镜像自 `material.py`，不 import——跨层一致性由 T7 的测试钉住。

### 变异自证（第一轮）：抽样 30 个，全杀（含 canary）

**首轮 6 个存活，全部是真实缺口，不是误报。** 逐条记录，因为其中一条正是方法论第 2 条点名的形态：

| 存活的变异体 | 为什么能活 | 补的用例 |
| --- | --- | --- |
| `len(stdout) > MAX` 整条删掉 | **这条护栏一个拒绝用例都没有**：超限负载是一串 `x`，本来就被 JSON 解析拒掉，删掉护栏结果不变 | 「合法 JSON 但超限 1 字节」——不删护栏才拒得掉 |

| `returncode != 0` → `> 0` | 没有被信号杀死的用例（Python 报负数） | 存根 `kill -9 $$`；`> 0` 会把 SIGKILL 读成成功 |

| `isinstance(stream, dict)` 删掉 | `streams` 里没有非对象元素的用例 | `["junk", 7, None, {...}]` |
| `os.access(R_OK)` 删掉 | 没有「是正规文件但不可读」的用例 | `chmod 000` |

其余 24 个首轮即被杀，归属逐条核对，每个判据都由与其同名的用例开火。

### T2 代码质量审查（第二轮不通过）与修复

**Critical：容器不报时长的真实视频被静默判成图片。**

原判据是「`format.duration` 键不存在 → 图片」。用真实文件跑生产代码路径实测，**两个方向都是错的**：

```
pipe_av.mkv   -> kind=image dur=None  64x64 v=h264 a=aac    ← 真实 2 秒 H.264 被判成图片
pipe_v.mkv    -> kind=image dur=None  64x64 v=h264          ← 同上，且无音轨时 Material 照单全收
shot.jpg      -> kind=video dur=40    80x60 v=mjpeg         ← 真实静图被判成 40 毫秒视频
```

复现要点是**输出不可 seek**：写普通文件时 ffmpeg 会回填 duration，只有管道输出才复现
（`ffmpeg ... -f matroska - > pipe.mkv`）。浏览器 `MediaRecorder` 的 WebM、OBS/ffmpeg 管道输出的
MKV 就是这个形状，对内容生产产品是普通用户素材，不冷僻。

两条分支后果相反、都很糟：**带音轨**时 `Material._validate_audio` 对「图片却有声」抛
`InvalidMaterialModel`，调用方 `except MaterialProbeRejected` 接不住，与本模块「拒绝一律走封闭
枚举」的设计冲突；**不带音轨**时 `Material` 完全接受，一条 2 秒视频永久变成一张静帧，全程无错。

同一个信号两种待遇正是漏判的证据：纯音频缺时长**会被拒**（`test_rejects_audio_whose_container_states_no_duration`），
视频缺时长却被悄悄改判成图片。

**修法：改用正向信号。** `_PROBE_ENTRIES` 一直在要 `format_name` 却从不使用（这同时是 I4）。
实测容器名：PNG/BMP 是 `png_pipe`/`bmp_pipe`，JPEG 是 `image2`，而 `mov,mp4,...` 与 `matroska,webm`
都不是图片容器。仅当**无音轨且容器是图片容器**才判 IMAGE，否则一律 VIDEO 并要求可用时长。
「无音轨」这个附加条件挡住「图片容器却带音轨」——那是 `Material` 明令禁止的组合。

修完五个真实文件全部判对，见上方实测。

**I1 编码名端点**：`> MAX` → `>=` 变异体存活，补 `test_accepts_a_codec_name_at_the_length_limit`。
本模块其余上限都有端点接受用例，只有编码名漏了。

**I2 `stdin=subprocess.DEVNULL` 零用例**：它不是卫生习惯——Local Executor 的 stdin 就是 Tauri 下发
bootstrap 与命令的活通道（`executor/cli.py:137`、`:201`），子进程继承它就可能从协议流里吃掉字节。
补用例：父进程给自己 stdin 塞哨兵字节，存根**主动排空**它拿到的 stdin，断言探测后哨兵仍在、且存根
读到的是空。

**I3 stderr 被捕进进程**：模块 docstring 说 ffprobe 诊断「never read back」，实际它被
`capture_output=True` 完整读进内存，只是没人读那个字段。后果三条：`MAX_PROBE_OUTPUT_BYTES` 只守
stdout、stderr 无上限；**完整私有路径留在 traceback 栈帧里**，会被抓 `f_locals` 的崩溃采集器带走。
改为 `stdout=PIPE, stderr=DEVNULL`，三条一起消失，docstring 也才变成真的。

补的用例遍历异常 traceback 中**属于本模块的栈帧**，断言没有任何局部变量的 `repr` 含该路径。
实测确认它对旧行为真红（`CompletedProcess` 的 repr 里就带着那段诊断）、对新行为绿。
（注意作用域：只查本模块栈帧——测试自己的栈帧天然持有它刚写进去的诊断字符串。）

**I5 被信号杀死报成 `UNDECODABLE`**：那是把「工具死了」说成「你的文件坏了」，用户换一百个文件都
没用。**这跟 `UNDECODABLE` 的合并不是一回事**：那两者确实无法区分，而这条区分是免费的——POSIX 上
`returncode < 0` 就是被信号杀死，不读任何英文诊断、不随版本或 locale 漂移。新增 `PROBE_CRASHED`。
诚实的限定：Windows 崩溃给的是大正数，这条只在 POSIX 白拿；macOS 是一等目标平台。

### 测试速度：258 ms → 5 ms

测试用**真实存根可执行文件**而非打桩 subprocess，好处是真正走了参数拼装、`execve`、退出码与两条流。代价一开始很大：整个文件 12 秒。

实测原因是 macOS 对**新建**的可执行文件首次运行要做一次校验：


### stderr 必须读，但不能被任何栈帧持有

T2 为了防路径外泄把 stderr 设成了 `DEVNULL`，而 silencedetect 与 ebur128 的结果**恰恰写在 stderr**。

解法是把 stderr 重定向到**临时文件**而非捕获：`CompletedProcess` 与 `TimeoutExpired` 都不会带上
它，尺寸也能在读之前检查。更关键的是**读完立刻解析成数字**——`_measure_report` 把文本直接传给
解析函数、不绑定成局部变量，解析函数只返回三个数且从不抛异常。等到任何拒绝被抛出时，持有过
文本的栈帧都已经返回，traceback 里带不走文件名。

第一版没做到这点：`read_audio_facts` 把报告文本存成局部再判「没有 `I:` 行」就抛，泄漏用例当场判红。

#### C2 选了哪条修法，为什么（审查单点名要求写明）

审查给了两条路。**先说为什么没选第二条**——「响度落在地板 + 静音覆盖音轨」合并判定，
实测走不通，而且它自己会打自己：

| 素材 | 静音是否覆盖 | `I:` | 想要的答案 |
| --- | --- | --- | --- |
| `partial.m4a` 前半静音后半有声 | 覆盖前半 | **-22.2** | 有声 |
| `faint_45.m4a` 衰减 45 dB | **全覆盖** | **-66.8** | 无有效音频 |
| `short_audio.mp4` 10 秒画面 / 2 秒静音音轨 | **不覆盖**（2.02 < 10） | -70.0 | 无有效音频 |

两处硬伤：一是 `short_audio.mp4` 的静音**根本覆盖不了容器**，AND 起来照样判成有声，
**C2 原地没修**；二是要把 `partial` 和 `faint_45` 分开，只能在 -66.8 和 -22.2 之间凭空
划一条响度线——而 S1 刚刚裁定「地板表示测不出、不表示安静」，再拿响度当有无声音的判据
等于把刚推翻的判据换个位置装回去。

**所以选第一条：读音轨自己的时长（ffprobe `stream=duration`）。** 时长比较这个机制本身没错，
错的是拿错了时长——`silencedetect` 量的是音轨时间轴，`format.duration` 是容器（通常由视频轨
决定）的。

落地细节，三条都是实测决定的：

1. **不是所有容器都报流时长。** 实测：mp4 / mov / m4a / wav / flac / MPEG-TS **报**，
   **Matroska 与 FLV 不报**（只有容器时长）。所以「流时长缺失」是常态不是畸形，
   缺失时退回容器时长——那正是今天的行为，不制造新的拒绝；
2. **取两者中较短的那个**（`min`），不是直接用流时长。理由是流时长来自文件、可伪造：
   取 `min` 让这次改动**只可能把判定往「无有效音频」推，永远不可能往 bug 的方向推**，
   同时把「伪造一个超长音轨时长」这条路直接堵死（`min` 会拿回容器时长）。
   实测 MPEG-TS 正好用得上：容器 2.023 秒里装着 1.904 秒的音轨；
3. **诚实说明一处没有变好也没有变坏的地方**：伪造一个**极短**的音轨时长仍然是一条误拒杠杆
   （任何有 ≥0.3 秒静音的文件都会被判成全程静音）。

   > **⚠️ 这一条当时写错了，第二轮已推翻。** 原文写的是「这条杠杆今天就存在——伪造
   > `format.duration` 有一模一样的效果，不是本次引入的新类别」。**两者不等价**：伪造
   > `format.duration` 会**同时**把 `MediaStreamFacts.duration_ms` 压成 1 ms，一个十分钟的
   > 文件在素材库里显示成 0:00，用户一眼看得出不对；伪造**流**时长时 `duration_ms` 仍是
   > 10000，画幅、编码、时长各项全都正常，只有音频判定错了。**旧杠杆是响的，新杠杆是哑的。**
   > 而且 `min` 让更小的那个永远赢，所以新杠杆的下限比旧的还低。第二轮实测（3 字节改动，
   > 见下文 C2）确认这是一条真实误拒通道，已连同时长比较本身一起删除。

#### M2 的真实二进制结论：是死代码，删掉，并把假设改成有测试守着

审查要求对着真实二进制确认「未闭合静音」分支是防御性还是死代码。**四种形状全部实测，
全部闭合**——silencedetect 在 EOF 无条件冲刷出 `silence_end`，包括容器被从静音中间截断的那种。
再加上 C1 修完之后正则锚到了行首，注入也造不出未闭合的 `silence_start`。

按 T3 自己删 `math.isfinite` 时立的同一条标准（「留着会带着满分伪装成一道检查」），**删掉**：
`_SILENCE_START_PATTERN`、`_SILENCE_END_PATTERN`、`max(0.0, ...)` 夹断，以及被它拖着穿过
`_measure` / `_parse_measurement` 的 `duration_seconds` 参数一并去掉。

**删掉不等于把假设丢了。** 换成一条真实二进制用例顶上：一条 3 秒全程数字静音的 m4a 必须被判
`SILENT_AUDIO`——这个结论**只有在 silencedetect 闭合了那段静音时才成立**，所以哪天 ffmpeg 改了
行为，它会直接判红，而不是悄悄把静音文件报成有声。**把一个进不去的分支换成一条守着的断言**，
比留着死代码强。

#### C1 通道选型：两条候选各自实测到了什么

审查单裁定「换通道，不要再加锚点」，并要求先实测再选。逐条量：

**候选 1 `ametadata=mode=print:file=<独立通道>`——选它。** 量到的四件事：

1. **随包 ffmpeg 支持**，`file=-` 走 stdout，输出形状固定为两种行：
   `frame:<n> pts:<t> pts_time:<s>` 与 `lavfi.<key>=<value>`。实测对一个视频+音频输入，
   stdout 里**不匹配这两种形状的行数为 0**；
2. **stdout 不会被别的东西写**：`-f null` 声明了 `AVFMT_NOFILE`，ffmpeg 根本不打开输出。
   实测把输出写成 `/no/such/directory/out.bin` 仍然 `exit=0`；去掉 `ametadata` 后 stdout
   是 **0 字节**；
3. **`silencedetect` 的结果确实进得去**，但**只进得去一半**——这是全流程最关键的一条实测：
   `silence_start` 在帧上，`silence_end`/`silence_duration` 在**跨越到 EOF 时进不去**，
   因为 EOF 之后没有帧可挂。实测一条 3 秒全程静音的 m4a：stderr 有
   `silence_end: 3.018594 | silence_duration: 3.018594`，**通道里只有 `lavfi.silence_start=0`**；
4. **`ebur128` 的 `metadata=1` 能把 `lavfi.r128.I` 送进同一条通道**，每 100 ms 一条，
   取**最后一条**即最终积分值：440 Hz 正弦波通道里是 `-21.776`，它自己的摘要打的是 `-21.8`。

**候选 2「剥掉 metadata 段再解析」没有选**，理由与审查单倾向一致且被上面第 2 条加强：
界定 metadata 段的边界本身还是一次解析，而键名注入正是让「段的边界」不可靠的那件事。

**由第 3 条实测直接改变了判定方式**（这一点比选哪条候选更重要）：既然闭合信息进不了通道，
就不能再「把静音时长加起来跟音轨时长比」。改成读**形状**：

> silencedetect 一见到声音就闭合当前区间，所以**任何一个闭合区间本身就是有声音的证据**；
> 唯一可能不闭合的是最后一个，它一直延伸到轨尾。**于是「静音覆盖全程」恰好等于
> 「有一个从最开头打开的区间，且没有任何区间闭合过」。**

这个判据**一个时长都不需要**，C2 那条杠杆随之整条消失（见下）。附带三条实测支撑：
ffmpeg 的滤镜时间轴无论容器起始时间为何都从 0 开始（mp4/mov/mkv/flac/ogg/mpegts 六种实测
首帧 `pts_time:0`），所以「最开头」写成 `<= 0`；多区间实测 3 个 start / 2 个 end，形状与
推导一致；编码器补白导致的「静音比文件还长」不再需要 `>=` 容忍——不做减法就没有这个问题。

**响度也一并搬走了**：不再读 stderr 摘要，改取通道里最后一条 `lavfi.r128.I`。

**代价，如实登记**：`ebur128` 每 100 ms 一条，实测 60 秒素材 34,580 字节 = **576 B/s**。

> **这里原先写的「4 小时上限约 8.3 MB」是线性外推，第三轮审查点出后已实测**：真跑一趟
> 四小时（`sine` 直接喂进同一条滤镜链，13.5 秒跑完）得 **9,085,156 字节 = 8.66 MiB**，
> 比按 60 秒外推的 7.91 MiB 高 **9.5%**——帧号与时间戳位数变长，每块就变长。
> 与新加的上限用例里「1.5 倍余量是为了盖住投影看不见的位数增长」是同一个口径，
> 那条外推数字不该单独留在注释里。

所以 `MAX_MEASURE_OUTPUT_BYTES` 从 1 MiB 提到 **16 MiB**（对实测的 8.66 MiB 留 1.85 倍）。
这不是放宽护栏而是换了被守的对象：原来那 1 MiB 守的是**解码诊断**，速率不可控（审查者实测
7 次轮询 0.72 秒就写到 141,798,342 字节 = 上限的 135 倍）；现在诊断整条走 `DEVNULL`，
**磁盘增长这条通道直接没有了**，剩下的通道尺寸是时长的确定函数，上限由时长上限推出来。
顺带把 `ebur128` 六个状态里用不到的五个用 `ametadata=mode=delete:key=...` 删掉——
不删是 1763 B/s，删了 576 B/s。

**另外多做的一步**：滤镜链**第一个**就是 `ametadata=mode=delete`（无 key = 清空整个帧
metadata 字典），把 demuxer/decoder 可能挂上去的东西在两个测量滤镜之前先清掉。这样通道里
的键**只可能**来自这两个滤镜。行首/行尾锚点仍然留着，但它现在是这一层背后的纵深，不是主
防线——实测五个伪造文件的通道里注入命中数均为 **0**。

#### 由 C1 带来的一处行为收窄，与它的补偿

通道里的判定改成「形状」之后，**`lavfi.r128.I` 成了唯一的「这一趟真的跑起来了」证据**，
而实测**短于 100 ms 的音轨一条 `r128.I` 都不打印**（0.05 s、0.09 s 为 0 条，0.10 s 为 1 条）。
若照旧「没有响度就 `PROBE_FAILED`」，一条 50 ms 的真实音频会从今天的「接受、响度 None」
变成硬失败——那正是本单在修的误拒。

故把两种「没有」分开：**通道里一帧都没有** = 音轨短于一个积分窗，接受；**有帧却没有响度**
= 这趟没按要求跑，`PROBE_FAILED`（ebur128 每 100 ms 一条，有帧就意味着它早该报过好几条了）。
两侧各有用例，其中「50 ms 真实素材必须被接受」是随包 ffmpeg 现造的。

#### C2：不是二选一，而是被 C1 的新判定整条消掉

审查单给了两条修法。**先说为什么两条都没选**：

- **修法二「用 report 里最大的 `silence_end` 当音轨长度下界」，实测修不好它自己的反例。**
  `lead1s` 这条素材只有一个从 0 开始的区间，`silence_end = 1.000023`，而静音总量也正好是
  `1.000023`——下界与总量相等，`>=` 一比照样判「全程静音」。**这条修法在给定反例上无效**；
- **修法一「相对容器时长设合理性下界」能缓解但不能关闭。** 实测 `short_sound.mp4` 是
  10 秒画面配 2 秒音轨——**真实素材的合法比值就有 20%**，阈值只能定得比它更松，攻击者把
  伪造值抬到阈值之上照样有一段可用的误拒窗口。

**实际做法是 C1 的形状判定本身不需要任何时长**，于是这条杠杆没有「变窄」而是**不存在了**。
连带删掉的有：`_sound_track_seconds`（含 `min`）、`_optional_duration_ms`、
`MediaStreamFacts.audio_duration_ms`、以及 `-show_entries` 里的 `stream=duration`——
**不再向 ffprobe 要这个字段**，有专门用例断言 argv 里 stream 段不含 duration。

登记两件事：

- **`audio_duration_ms` 是本轮删掉的一个「事实」**，删它的依据是全仓 grep 后它**只有
  `_sound_track_seconds` 一个消费者**，且 `Material` 没有对应字段。若 LE-14 之后真需要
  音轨自身时长，重新加回来是几行的事；留着一个没人读、又由文件说了算的字段不是零成本，
  上面那 3 字节反例就是它的成本；
- 随之删掉的还有 `read_audio_facts` 里对时长的入参校验（`UNUSABLE_DURATION` 那两条）。
  它们存在的唯一理由是保护那个窗口计算，窗口没了就是死守卫——**按 T3 自己删
  `math.isfinite` 时立的同一条标准处理**。现在换成一条参数化用例：`duration_ms` 取
  `None / 0 / 1 / 10_000_000` 四个值，判定必须**逐个相同**。

#### I2：轮询体里抛错时超时保证消失，且 ffmpeg 不被杀

`report.stat()` 在飞行中抛 `OSError`（tmp 清理器、卷消失、EIO）时，异常离开 `with`，
`Popen.__exit__` 调的是**不带 timeout 的 `wait()`**，而子进程**从没被 kill**——审查者实测
超时设 1.0 秒、子进程 sleep 30，整轮 **30.59 秒**。

修法：轮询整体包一层 `except BaseException: process.kill(); raise`。**用例模拟的是飞行中**——
存根在写完输出后、赖着不走**之前**把工作区删掉（失败矩阵「文件在脚下被删」，不是注入异常）。
判据仍是存根的标记文件不存在（= 被杀，不是等出来的）。

**为什么是 `BaseException` 而不是 `Exception`，以及这条用例怎么才有捕捉力**：Ctrl-C 期间
`KeyboardInterrupt` 不是 `Exception`，窄一档就会让它从那个「不带超时地等」的出口溜出去，
把一个正在解码四小时素材的 ffmpeg 变成孤儿进程。第一版用例用「标记文件不存在」来断言，
**变异 `BaseException` → `Exception` 存活**——查出来的原因是 CPython 在 `Popen.__exit__` 里
**对 `KeyboardInterrupt` 有特判**：只等 `_sigint_wait_secs`（0.25 秒）就返回，所以没被杀的
子进程不是「拖慢断言」而是「活过断言」。改成让存根写下自己的 PID、断言事后
`os.kill(pid, 0)` 抛 `ProcessLookupError`，变异当场被杀。

#### C1 回归：`silencedetect` 放在 `ebur128` 上游，闭合事件被合帧丢弃

`ebur128` 在 `config_input` 里把输入链的 `min_samples`/`max_samples` 都设成
`sample_rate/10`，libavfilter 于是把解码帧**并成一个窗口的长度**再交给它；而
`take_samples()` 只做 `av_frame_copy_props(buf, frame0)`——**组内非首帧的 metadata 全部丢弃**。
AAC 一帧 1024 样本、一个窗口 4410 样本，约四帧并一组，于是**放在 ebur128 上游的滤镜，
每四个事件只活一个**。

丢掉的正是证明「声音回来了」的 `silence_end`。没有它，一个前面静音、后面有声的文件
读起来与「一直静到 EOF」完全一样，而后者对 `kind=AUDIO` 就是硬拒。

实测（本机随包 8.1.2，四组编码 × 六个前导静音长度 = 24 个含 4 秒清晰可闻 440 Hz 的文件）：

| 组 | 上游（改前） | 下游（改后） |
| --- | --- | --- |
| AAC 44.1 kHz | **4/6 错** | 0/6 |
| AAC 48 kHz | **3/6 错** | 0/6 |
| FLAC 44.1 kHz | 0/6 | 0/6 |
| PCM s16le 44.1 kHz | 0/6 | 0/6 |
| **合计** | **7/24 被硬拒 `silent_audio`** | **0/24** |

最干净的一对是前导静音 **0.30 秒通过 / 0.31 秒硬拒**，只差 10 毫秒。

**判据是块长，不是编码格式**（第三轮审查纠正了我这里写错的机理，实测复核如下）。
一整帧连同 metadata 被吞掉，只发生在「一组吃进两整帧」时，也就是**解码帧长 ≤ 半个窗口**。
44.1 kHz 下窗口是 4410 样本，实测解码帧长：**AAC 1024、PCM s16le 4096、FLAC 默认 4608**。

我原先写的「FLAC/PCM 的帧本来就 ≥ 一个窗口」**是错的**——PCM 的 4096 比窗口还短，
只是超过半个窗口，所以每组只吃一整帧加下一帧的一小截，那一截成为下一组的首帧，
没有任何整帧被吞。用 `-frame_size` 把 FLAC 块长压下去，八个静音位置逐个实测：

| FLAC 块长 | 两整帧塞得进窗口 | 上游顺序（改前） | 下游顺序（改后） |
| --- | --- | --- | --- |
| 512 | 是 | **8/8 硬拒** | 0/8 |
| 1024 | 是 | **8/8 硬拒** | 0/8 |
| 2048 | 是 | **7/8 硬拒** | 0/8 |
| 4096 | 否 | 0/8 | 0/8 |

2048 那格值得单记：**第一次只测一个素材时它是通过的**，再测八个相位才看出 7/8 会挂——
和这一整条 bug 逃过 168 个用例的原因是同一个（单个样本恰好落在安全相位）。

**结论：外部编码器产出的 1024/2048 块长 FLAC，行为与 AAC 完全相同。** 用户素材不由
本项目的编码器产出，所以「我们的默认块长比较大」不构成任何保护。

> 审查单报的是 17/24，我自己这组测出来是 7/24。**不是分歧，是取的前导静音长度不同**
> （我用 0.30 / 0.31 / 0.35 / 0.55 / 0.77 / 1.00，其中两个恰好在网格上）。分组形态
> 与审查单一致：AAC 两组出错、FLAC 与 PCM 两组不出错。此处记我自己实测到的数。

**修法**：把 `silencedetect` 挪到 `ebur128` **下游**。此时它看到的已经是 4410 定长帧，
自己产生的 metadata 直接进 sink。样本值不变、响度不受影响，24 个文件判定归零错误。

#### 我自己写的用例翻车了一次，一并记

为 `except BaseException` 补的 Ctrl-C 用例，第一版让存根把自己的 PID 写进文件、再断言
事后 `os.kill(pid, 0)` 抛 `ProcessLookupError`。**它是 flaky 的：30 次跑挂 2 次**，因为
父进程在 spawn 后 0.1 秒就抛 `KeyboardInterrupt`，而子进程（`sh` + 一次 `dirname` 子进程）
偶尔还没走到写 PID 那一步，读回来是空串。把写 PID 挪到脚本第一行也没解决——**只要判据
依赖子进程跑到某个位置，就是在跟它的启动赛跑**。

改成断言**父进程自己手里的那个 `Popen`**：记录下它，事后 `wait(timeout=10)` 收尸再断言
`returncode == -SIGKILL`。杀了就是 `-9`，没杀就是存根睡完自己退出的 `0`，两边都确定，
不依赖任何时序。30 次跑 0 次挂，变异 `BaseException` → `Exception` 仍被它杀掉。

（`starts[0]` → `starts[-1]`）是被这条 flaky 用例**误杀**的。修稳之后重跑，它如期存活。

| 64 位小写十六进制（复用 `is_sha256_hex`） | `test_the_digest_is_one_canonical_lowercase_sha256` |
| 与 `hashlib.sha256(read_bytes())` 逐字相等 | `test_the_digest_equals_hashing_the_whole_file_at_once` |
| 大于 1 MiB 跨多块仍正确 | `test_the_digest_is_right_on_and_around_the_chunk_boundary`（6 个尺寸） |
| 超尺寸上限 → 拒绝 | `test_rejects_a_file_over_the_shipped_limit` + 端点对 2 条 |
| 读取中途文件消失 → 拒绝 | `test_rejects_a_file_deleted_while_it_is_being_read`（**真删**） |
| 无读权限 → 拒绝 | `test_rejects_a_source_without_read_permission` |

### 这一 Task 最重要的一件事：计划那条 RED 靠错误处理写不出来

「读取中途文件消失 → 拒绝」看上去是一条 `except` 就能接住的事。**实测不是。**

POSIX 下 unlink 一个已经打开的文件，inode 活在描述符后面：读**不报错、也不短**。
实测 4 MiB 文件读到一半 unlink，剩下的字节一个不少地读完，摘要与原始内容逐字相等，
只有 `fstat().st_nlink` 变成 0。也就是说——**不加守卫这条 RED 根本红不起来**：
函数会安静地返回一个正确的摘要，而那个路径上已经没有文件了。

所以拒绝不是靠接异常，是靠读完之后**再问一次路径**。这条守卫连带管住另外三种
「文件没站住」的形状，四种都实测过，各有一条用例：

| 形状 | 不加守卫会怎样（实测） | 由谁接住 |
| --- | --- | --- |
| 中途被 unlink | 读满且摘要正确，而路径已空 | 读完后 `path.stat()` 抛 ENOENT |
| 中途被追加 | **读到的字节超过描述符报的尺寸**——报 1 MiB 的文件被追加 2 MiB 后交回 3 MiB | 循环内 `read_bytes > opened.st_size` |
| 中途被截断 | 循环提前 EOF，摘要只覆盖前缀 | 循环后 `read_bytes < opened.st_size` |
| 中途被换成另一个文件 | 描述符 `st_ino` 不变，读到的是旧内容，而路径上已是新文件 | `(st_dev, st_ino)` 与开文件时不一致 |

第四种是去重最怕的那一种：**存下的是旧内容的摘要、挂在新文件的路径上**，
以后同一条素材会被判成两条，或两条不同素材判成同一条。

追加那一条顺带是个工作量边界：不停在描述符报的尺寸上，读多久就由写方决定。

四条用例都是**真的**在读的过程中动文件（真 unlink / 真追加 / 真截断 / 真 `os.replace`），
不是打桩。夹具用 256 MiB 稀疏文件（`truncate` 出来，0 磁盘字节），变异动作延迟 15 ms 发出：
实测 160 次，动作最晚落在 24 ms，而调用最短跑 127 ms，160 次全部被接住。

### 守卫缺席补查：三个文件系统调用各自失败时抛什么（实测）

| 调用 | 场景 | 实际抛出 |
| --- | --- | --- |
| `Path.stat()` | 路径段超 `NAME_MAX`（300 字符） | `OSError` errno=63 ENAMETOOLONG，**不是具名子类** |
| `Path.stat()` | 文件不存在 | `FileNotFoundError` errno=2 |
| `Path.stat()` | 目录 | 不抛，正常返回（由 `S_ISREG` 拦） |
| `open()` | 路径段超 `NAME_MAX` | `OSError` errno=63 |
| `open()` | 文件不存在 | `FileNotFoundError` errno=2 |
| `open()` | 目录 | `IsADirectoryError` errno=21 |
| `open()` | 无读权限 | `PermissionError` errno=13（`os.access` 先返回 False，走不到这里） |
| `read()` | 中途 unlink | **不抛，读满** |
| `read()` | 中途截断 | 不抛，提前返回 `b""` |
| `read()` | 中途追加 | 不抛，**多给**追加的字节 |

两条结论：`except` 面就是 `OSError`——ENAMETOOLONG 只以裸 `OSError` 出现，
写 `except FileNotFoundError` 会漏，而它在 `MAX_PATH_CHARACTERS` 以内就够得着；
`read()` 那一列**没有一个是异常**，所以「读取中途出事」全部靠事后比对，不靠 except。

异常消息仍固定为 `material probe rejected`，且**不接链**：拒绝在离开 `except` 之后才发出
（同 `_run_probe` 的做法），`OSError.filename` 就是那条私有路径，`from None` 只挡渲染器、
挡不住顺着 `__context__` 走的人。用例 `test_the_vanishing_file_rejection_chains_nothing`
断言 `__context__ is None`。

### 体积上限：取值、命名，以及接受端点为什么不真读 16 GiB

新增 `MAX_SOURCE_FILE_BYTES = 16 GiB` 与拒绝码 `FILE_TOO_LARGE`。

**为什么另加一个码**：`TOO_LONG` 是时长、`FRAME_TOO_LARGE` 是画幅，都不是字节；
`UNREADABLE` 给用户的下一步是「重新定位文件」，这里的下一步是「先压缩」。
按 §3.1「用户看到它之后知道下一步该干什么」，是两件事。

**为什么不叫 `MAX_MATERIAL_BYTES`**：`MAX_MATERIAL_DURATION_MS` / `MAX_MATERIAL_DIMENSION`
是从 `material.py` 镜像来、由跨层测试钉住的；而 `Material` 没有体积字段，这条上限镜像不了
任何东西，叫 `MATERIAL` 会把 T7 的跨层测试引向一个不存在的对应物。

**取值的两个依据，都有用例钉着**（T3 审查提过「上限的取值没人钉」，这里一并补上）：

- 下界：4 小时是 `Material` 能装的最长素材，4 小时 × 8 Mbps（普通消费级 1080p）= 14.4 GB，
  上限必须盖过它，否则时长门刚放行、体积门就把同一个文件拦下来。**8 GiB 会被这条判红**；
- 上界：实测本机散列吞吐 2.08 GiB/s，16 GiB 值 8.7 秒；用例把它限在 30 秒内，
  **64 GiB 会被这条判红**。（对照：本模块的测量趟本来就允许单文件 15 分钟。）

**接受端点为什么不用真尺寸**：`>` 与 `>=` 只有「恰好等于上限」那个点能分辨，而那个点
必须真读完——实测读满 16 GiB 稀疏文件 8.7 秒，而整个 `test_material_probe.py` 才 8.96 秒。
所以拒绝端用真常量 + 稀疏文件（`truncate` 到 16 GiB + 1，实测 0.2 ms、`st_blocks == 0`，
且尺寸取自描述符、**一个字节都不读**就被拒），接受端把常量 monkeypatch 到 4096 再钉
4096 / 4097。生产代码路径逐字未变，变的只有它比较的那个数，而那个数由拒绝端的用例钉住。
monkeypatch 模块常量是本文件既有做法（T2/T3 的超时用例同款）。

尺寸取自 `os.fstat(handle.fileno())` 而不是路径：查的必须是**即将被读的那个文件**的尺寸，
路径 stat 留着「开的时候已经换了一个」的空档。

### 分块边界与夹具：全零文件测不出块序

分块边界钉六个尺寸：`0`、`1`、`1 MiB - 1`、`1 MiB`、`1 MiB + 1`、`5 MiB + 7`。

夹具内容不能随便取。**chunk 是 2 的幂，任何周期整除它的重复串在块序颠倒后逐字节不变**，
全零文件更是天然不变——拿这种夹具测「跨多块仍正确」，一个把块读反或漏读一块的实现照样满分。
所以夹具用固定种子的 `random.Random(20260729).randbytes()`，**并且这个性质本身有一条用例**
（`test_the_fixture_would_notice_chunks_read_out_of_order`：把 3 个 1 MiB 块倒序拼起来，
断言 sha256 与正序不同），而不是写进注释当保证。

### 复用与跨层

- `is_sha256_hex` 按计划复用 `protocol.safe_text`（本树确认存在，全库 17 处在用），没有另写；

  循环真正散列过的字节数是同一件事更准的检查，且已经比过了。

### 我自己写的用例翻车一次，一并记

变异自证第一轮里 `opened = os.fstat(...)` → `opened = path.stat()` 报「存活」，
单独补跑同一个变异体却报「被杀」。**同一个变异体两次结论相反，说明不稳的是用例不是变异体。**
连跑 6 次带变异 + 4 次干净树，干净树 4 次挂 2 次，问题出在我自己写的计时自检：

自检原本在**执行完变异动作之后**取时间戳，用来断言「变异发生在调用返回之前」。
对 unlink 和换文件没问题（读还要再跑一百多毫秒），但**截断这个动作恰恰会让被计时的那次读
提前结束**：`os.truncate` 一返回，主线程立刻 EOF、走完、记下 `finished`，而工作线程那句赋值
还没轮到——两个 `time.monotonic()` 谁先谁后是真的在抢。

改法：时间戳挪到**变异动作之前**；并且只在守卫**跑在读之后**的两条用例（unlink、换文件）上
断言「变异落在调用前半程」——那两条的读不会被变异缩短，这个比例才有意义。追加与截断的守卫
在循环**内**，能拒本身就证明了循环当时还在跑，不需要也不该再断言比例。改后连跑 15 次全绿。

**这条本身就是那类 bug 的复现**：断言写在一个「看起来当然成立」的顺序上，
而那个顺序恰恰由被测行为自己决定。

### T4 两轮审查（spec ✅ / 质量 2 Important）与修复

spec 审查三处裁决全部支持既有实现（「中途消失改读后复核」判为忠实实现而非扩权、
跨层真构造 `Material` 判为强于常量比对）。质量审查 2 Important，同源——
**读后复核只认 inode，不认字节、不认文件类型**。两条都先真实复现再修。

#### Important 1：原地等长改写穿过全部守卫

同 inode、同尺寸的原地改写，`(st_dev, st_ino)` 与字节数全不变。**实测 5/5 全中**：
返回了改写前内容的摘要，与磁盘上的内容不符，零拒绝。

真实场景不是构造出来的：预分配式写入方（aria2 `--file-allocation=prealloc`、BT 客户端、
录制工具）从第一秒就把文件撑到最终尺寸再逐块填入——**导入抢在下载完成前，
就正好是这个形状**。此前那条 grows 用例想防的就是它，而换成不改尺寸的写法整条穿过。

修法：`with` 内读完后再取一次 `os.fstat`，比 `st_mtime_ns`（实测该场景 dev/ino/size 全同、
mtime_ns 变）。**如实登记边界**：mtime 粒度随文件系统——APFS 纳秒，部分网络文件系统整秒——
所以这是**收窄不是关死**，一次落在同一 tick 内的改写仍然看不见。
`package_manifest._same_file_identity` 也不比 mtime，**这一条不能靠照抄先例得到**。

#### Important 2：`st_mode` 未复核，FIFO 替换后 `open()` 无限阻塞

照搬的先例第一件事就是 `S_ISREG` 双侧检查，此前只声明了 size 那处有意省略，
**S_ISREG 这处丢失没声明**。本入口是三个入口里唯一无时限的（另两个有 ffprobe/ffmpeg 超时兜底）。

**审查单给的一行修法不成立，实测顶回**：`if not stat.S_ISREG(opened.st_mode)` 里的 `opened`
要 `open()` 返回之后才拿得到，而**阻塞正好发生在 `open()` 本身**——实测普通 `O_RDONLY`
打开一个无写方的 FIFO，整整一秒都没返回。只加这一行挡不住挂起。

实际修法是**开文件时就带 `O_NONBLOCK`**（实测 0.165 ms 返回并报 `S_ISFIFO`），
再配 `S_ISREG` 复核。实测 `O_NONBLOCK` 对普通文件的读取无任何影响（同样的字节、同样的分块）。
变异体 `O_NONBLOCK dropped` 的结果是**整套测试挂起**——这条挂起本身就是那个 finding。

#### 连带：`os.fstat → path.stat()` 那个存活变异

按审查意见把 `_require_source_file` 丢弃的那次 stat 传进来比（先例
`_hash_stable_regular_file:127` 同款），使开文件前那次检查变成载荷而不是白做。
**但它并没有如审查预期那样把该变异杀掉**——已实测：mtime 复核补上之后，
`opened` 无论取自描述符还是路径，在所有可构造的用例里读数相同，差异仍只存在于
`open()` 与其后那次 stat 之间的微秒窗口。故仍记为存活，并按审查要求改了定性
（可达、代价不成比例，非「结构性纵深」）。

同轮那条 `re-stat the descriptor not the path` **当时记的「被新用例杀掉」是错的，已更正**：
最终身份检查在 `finally: os.close(descriptor)` **之后**，那个变异体等于对一个已关闭的
描述符做 `fstat`，每次都抛 `EBADF` 从而每次都 UNREADABLE——杀它的是 12 条 happy-path，
与该检查的语义毫无关系，属于**廉价杀**。清单里已换成有意义的形态
（把 `path.stat()` 换成 `after`：同一个描述符的身份不可能变，检查因此永不开火），
实测被「中途被删」与「中途被换」两条用例杀掉。

### 半成品为什么是结构性不可能，而不是靠记得

`MaterialFacts` 九个字段**全部必填、无默认值、`frozen=True`**。于是：

- 最后一步返回之前**造不出这个对象**（少任何一个字段就是 `TypeError`）；
- 造出来之后**填不进第二个值**（frozen）；
- 模块里只有一处构造点，而且它就是 `return` 表达式本身。

所以编排层在某步拒绝时**没有中间状态要回滚**——不存在一个"填了一半"的对象。
两条变异体验证了这一点：`frozen=True` 去掉、给 `content_digest` 加默认值，都被杀。

`repr` 也因此不用重写：**没有字段能装路径**，安全性来自结构而不是渲染函数的自律。

### kind 分派刻意不写在编排层——核对它确实在下层（派工单要求）

- **IMAGE**：`read_stream_facts` 只在**无音轨且容器是图片容器**时判 IMAGE，所以 IMAGE
  必然 `audio_codec is None`；`read_audio_facts` 第一行就据此直接返回，**不启 ffmpeg**；
- **AUDIO 且无有效音频 → 拒**：规则在 `read_audio_facts` 内（`Material` 禁止
  `kind=AUDIO && has_audio=False`）。

编排层**一句都不重复判**。核对方式是四条真实素材用例：真实 ffprobe 定 kind，
存根 ffmpeg 记录是否被 `execve`——`-af` 只出现在测量命令行里，它在不在共享 argv 日志里
就是 ffmpeg 有没有跑。结果：sound ✅跑 / mute ❌不跑 / picture ❌不跑 / audio ✅跑。

### 派工单六条约束的落点

**（1）UNREADABLE 是七个原因的合流口——选了「区分」，新增 `SOURCE_NOT_AT_REST`。**

不区分的代价是给出错误的下一步指令：最常见的真实成因是"下载/录制还没写完"，
而 `UNREADABLE` 的文案是"文件读不了，重新定位它"。判据用的是**「同一个文件原样再导一次会不会成功」**：

| 落到哪个理由 | findings |
| --- | --- |
| `SOURCE_NOT_AT_REST`（可重试，文件会静止） | 开文件前身份不符（被换）、读中增长、读中截断、读中原地改写、读完路径已是另一个文件，**外加本 Task 新增的端到端复核** |
| `UNREADABLE`（不会自己好） | 真实 IO 错误、无读权限、路径不存在、路径不是正规文件 |

FIFO 是这条线最锋利的例子：**等它「静止」会永远等下去**，所以它留在 `UNREADABLE`。
被 unlink 也留在 `UNREADABLE`——路径已经空了，原样重导没有意义。

**（2）可重试性分级：这次分裂本身就是分级，不再写第二份。**

`SOURCE_NOT_AT_REST` = 等一下再导；其余每一个都是"用户得先做点什么"，
`FILE_TOO_LARGE` 与 `UNSAFE_PATH` 从名字就看得出不可重试。**没有再加一个
`retryable` 属性**：目前没有任何调用方会读它（消费方是 LE-18 素材库），
加一份平行编码只是给两份表提供互相矛盾的机会（CLAUDE.md §10 禁止为假设性需求提前抽象）。
重试在这里安全这一点也核过：**拒绝时什么都没落库**——`probe_material` 无副作用、
不写盘、不发请求，不触发 §4「结果不确定不得自动重放」。

**（3）三个时刻不是一张快照——选了「开头 stat 一次，结尾复核一次」，不是「把同一个 stat 传下去」。**

先说清楚**为什么快照做不到**：ffprobe 与 ffmpeg 收的是**文件名**，自己去 open，
不可能共享描述符（macOS 上塞 `/dev/fd/N` 会被路径守卫挡下且不可移植）。
所以能做的只有**事后发现**，不是事前阻止；发现即拒，好过交出一组"从来没有同时为真过"的事实。

窗口有多大：读取 30 s + 测量 **15 分钟** + 摘要约 9 s。摘要自己只管得住"读的时候没动"，
**它前面那一大段此前没有任何人看着**——一次替换就会让事实描述 A 文件、摘要描述 B 文件，
而这是去重最怕的错，且**不以任何错误的形式浮出来**。

两条候选，选了后者：

| 候选 | 为什么不选 / 选 |
| --- | --- |
| 把开头那次 stat 传给摘要当 `expected` | 两条：**(a)** `read_content_digest(source)` 是 T4 已交付并导出的公开签名，塞一个 stat 进去等于改它，或者另开一条平行私有入口；**(b)** 覆盖严格更少——`_digest_stable_file` 拿 `expected` 只跑 `_names_the_same_file`（dev+ino），跨窗口只覆盖**身份一项**，而收尾复核覆盖身份 + `st_mtime_ns` + `st_size` 三项 |
| ✅ 开头 `_require_source_file` 拿 stat，结尾再取一次比 | 窗口是编排层开的，就由编排层关；**不动 T4 一行既有逻辑**；复用现成的 `_require_source_file`（OSError → 已有理由，不会漏出带路径的 `OSError`）与 `_names_the_same_file` |

比什么：`_names_the_same_file`（dev+ino）+ `st_mtime_ns` + `st_size`。**不整体比 stat**
——但**上一版把量级写错了**，实测改准：`stat_result.__eq__` 比的是 10-tuple，
其中时间字段是**整秒整数**（`tuple[7]` 是 `int`），所以整体比是「两个方向同时错」：

| 方向 | 实测 |
| --- | --- |
| **太松** | 亚秒改动看不见——0.4 s 的 atime 位移下 `a == b` 仍为 `True` |
| **太紧（间歇性）** | 只有当一次读把 atime 顶过整秒边界才误拒——1.4 s 位移下 `a == c` 为 `False` |

**间歇性比全灭更该防**：偶尔拒一条、取决于时钟当时落在哪，比条条都拒难诊断得多。
另有一条独立证据：显式加 `st_atime_ns` 比较会让**本文件 12 条真读文件的用例**变红
（上一版写 10，那是修复轮加两条新用例之前的数；已重测改准）。
`st_size` 与 `st_mtime_ns` 都留着，理由同 T4：时间戳精度是文件系统给的，
有些网络文件系统只到整秒。

**残留窗口（明确登记，不粉饰）**：两次 stat 之间开始并结束、且 inode / 长度 / 时间戳

### 派工单与实现的一处出入（实测顶回）

派工单正文写"编排入口串起：`revalidate()` → `read_stream_facts` → …"。

且共享 argv 日志为空，两个工具都没被 `execve`。

**那为什么 `_require_source_file` 就调了 5 次（开头、三步各一次、收尾）没去掉？**
两处的不对称是有理由的，补记清楚：

- **首尾两次不是校验，是取值**——编排层需要 `before` / `after` 才能做快照复核，
  校验只是顺带；`revalidate()` 在编排层再调一次则**没有任何返回值可用**，纯是第二次
  同样的检查；
- **中间三次是重复的，但它们属于那三个公开入口自己的契约**——没有任何东西保证调用方
  是经由 `probe_material` 进来的（T4 的 `TestContentDigestRejectsAnUnusableSource`
  已经把这条理由写死）。要省掉它们得改三个已交付的公开签名，把「已校验的 path + stat」
  串下去，代价是签名而收益是**一次 `stat`**——不值。

即：能省且省下来不改任何签名的（`revalidate`）省了；省不动或省了要改公开签名的

探测结束到下次使用之间没有任何上界。所以每条记录同时存 `dev`、`ino`、`st_mtime_ns`、
`st_size`（与 `_held_still` 同组），`resolve` 出门前重新 stat 比对——**回查拿不到「裸路径」，
只能拿到「还是那个文件的路径」或者一个说明它不是的理由**。裸映射会把 T5 关掉的窗口原样重开，
只是挪到上一层：用 A 文件的事实去开 B 文件，全程不报错。

**第 2 条 → 注册表里没有摘要，也不按内容去重。** 同一素材下载一半与完整给两个不同摘要，
而 duration/宽高逐字相同（T5 第四形态）。摘要只在一个方向成立：**相同才说明内容相同，
不同不说明是两条素材**。所以这里不放摘要、不做「是否已导入」判定——键是 Control Plane 发的
标识符，去重属于素材本身存放的那一层。放一份摘要在这儿，等于给这条非对称事实开第二个解释口。

### 存储位置：先查先例，没有另造

查了 executor 现有的本机状态存储，三个都是同一个形状——`state_directory: Path` 由 bootstrap
传进来，**不搜索、不创建**：`ledger.LedgerStore`（DB 直接放 `state_directory /
EXECUTOR_LEDGER_FILE_NAME`）、`PageDriftArtifactStore`、`LocalArtifactStore`。`cli.py:146`

**特意不自己建目录**：这是 Executor state 根的租户，不是它的主人。自己建目录的话，

`LocalArtifactStore` 看过但**不能复用**：它是 `O_EXCL` 一次性写入 + 保留期驱逐的证据存储，

### 落盘：mkstemp 同目录 + `os.replace`

派工单说照 LE-09 T4b 先例。**LE-09 还没开工**（台账 ⬜ 未开始），仓库里也没有 `mkstemp`
的先例——现成的原子落盘是 `control_plane.bootstrap.local_provisioning._write_private_document`：
同目录临时文件 + `O_EXCL` + `fsync` + `os.replace`。按它的形状写，把临时名换成 `mkstemp`
（唯一性由内核给，不靠拼 pid）。实测：`mkstemp` 建出来就是 0600，`os.replace` 原样带过去，
所以不需要额外 chmod。

目录 fsync **没做**，理由写进 docstring 了：`os.replace` 本身保证「进程被杀不留半个文件」，
目录 fsync 管的是掉电，那位兄弟函数也画在同一条线上。不含糊其辞地写成「原子安全」。

### 损坏的既有文件：拒绝，不重建空表

**丢弃用户映射是数据丢失**，而且是「装作一切正常」的那种：整库一次性变空，用户分不清
「文件坏了」和「我还没导入过素材」，也没有任何东西能再找回来。反过来，拒绝是可恢复的——
文件还在盘上。而且写入走 `os.replace`，**半个文件本来就不是崩溃能产出的东西**，
读不出来说明发生了别的事，那正是最不该将就往下走的时候。

「文件不存在」是完全另一回事，两者绝不能混：没有文件 = 首次运行，读不动 = 失败。
靠 `FileNotFoundError` 分开，所以权限错误永远不会被当成全新开始。

### 守卫缺席补查（实测再写 except）

| 调用 | 实测抛什么 | 结论 |
| --- | --- | --- |
| `json.loads` 截断/空文本 | `JSONDecodeError` ⊂ `ValueError`，`filename=None` | 一条 `except ValueError` |

### 幂等语义与「同 id 不同路径」的决定

| 情形 | 决定 | 理由 |
| --- | --- | --- |
| 同 id 同路径重复登记 | 幂等（同样的字节，不新增条目、不失败） | 序列化是排序定字节的，重写产出逐字相同的文件 |
| **同 id 换一条路径** | **后写覆盖，旧路径直接忘掉** | 这是「素材被移动后重新导入」唯一的活路。拒绝的话素材永远回不来，LE-18 的「缺失素材提示」就成了没有解药的提示。不留历史：没人读，留着就是路径的第二个落脚点 |
| 同 id 但文件本身变了 | 记录刷新成现在观察到的 | 能走到这行的调用方刚刚重新探测过，此刻看到的才是新的事实 |
| **两个 id 指同一个文件** | 允许 | 该不该是一条素材是个关于**内容**的问题，而按第 2 条，内容判定不在这一层。这里强加唯一性只会挡掉恢复路径 |

### 键的类型与跨层钉

键是 `uuid.UUID`（v4 + RFC_4122 + 规范文本往返），不是 `MaterialId`——executor 不得导入产品层
（§4.3）。规则与 `local_artifact._valid_artifact_id` 逐字相同，重写一遍而不是伸手去拿别的模块
的下划线名字。序列化边界是 `str(uuid)` 的规范小写文本。跨层钉一条用例：`MaterialId.new().uuid`
必须被接受，且 `MaterialId.parse` 认得回去——「这边能存、Control Plane 发不出来」的键
等于一行永远查不回来的记录。

### 拒绝类型为什么是两套（有意，非疏忽）

- `register` 的文件检查直接复用 `_require_source_file`，失败原样抛 `MaterialProbeRejected`。
  调用方刚跑完探测，本来就在这个 handler 里；再翻译一遍只会把 `UNSAFE_PATH` 和 `UNREADABLE`
  的区别弄丢；
- `resolve` 说注册表自己的话（`MaterialPathRegistryRejection`）：文件没了要报
  `FILE_MISSING` 而不是 `UNREADABLE`——按交接给 LE-18 的那条，`UNREADABLE` 已经背了太多含义。
  `FILE_MISSING`（去找回来）与 `FILE_CHANGED`（重新导入）是两个不同的下一步，告诉用户错的那个
  会让他去找一个就摆在那儿的文件。

### AST 边界测试与自证

判据是**类定义体**（`ast.ClassDef.body`），不是 `dataclasses.fields`——后者只看到类最后长成

`path/dir/file/location`；注解不含 `Path`/`PathLike`（补上「换个名字的路径字段」那个洞）。

### 第一决策：`resolve` 的消费面收成**一个**公开操作

T6 交接留下的形状是：`resolve` 交回 `(Path, os.stat_result)`，并在 docstring 里说消费方
应当用 `_held_still` 把窗口接着往下传、并把那条路径当用户路径走 `_require_source_file`
全套。问题是**这两个零件都是私有的**，而全仓没有跨模块引私有名的先例——这份说明谁也执行不了。

派工单给了两个选项（注册表加公开操作，或把两个零件导出）。落地选了第三个，理由三条：

1. **注册表关不掉这个窗口。** `resolve` 比的是**登记那一刻**的身份，而窗口在「resolve 之后、
   消费方 open 之前」；只有使用现场能闭合它。所以再给注册表加一个方法，等于又写一遍 `resolve`；
2. **导出两个零件等于让调用方自己拼窗口**，而本模块别处都不这么干（`probe_material` 就是
   「不让调用方自己拼三步」的产物）；
3. **这段代码本来就已经存在**——`probe_material` 结尾那两行逐字就是它。抽出来是**消掉一份重复**，
   不是新增一处公开面。

于是新增 `require_source_unchanged(source, approved) -> tuple[Path, os.stat_result]`，
内部 `_require_source_file` 全套 + `_held_still`，拒绝码沿用 `SOURCE_NOT_AT_REST`，
并让 `probe_material` 调它。**一份实现，两个调用方**，由
`TestProbeMaterialClosesItsWindowThroughThePublicCheck` 钉住（变异「编排层改成自己再比一遍」
已被杀）。交回新 stat 是为了能继续往下串：消费方检查完再打开，还有第三个时刻要闭。

派工单要求的「真正走全套」那条用例也补了：`TestMaterialPathRegistryHandsBackWhatItChecked`
里原来那条**跳过了中段**（直接 `_held_still(before, path.stat())`，没过导入守卫，还引了私有名），
改成走公开操作，且中途换文件必须为假。另外整类 `TestRequireSourceUnchanged`
七条：原地等长改写、换成另一个文件、文件不在了、变成 FIFO、相对路径、以及消息不含路径。

### 必补①：ffprobe 的 stdout 不再无上限读进内存

原状是 `subprocess.run(stdout=PIPE, timeout=30)` 读完再比 `MAX_PROBE_OUTPUT_BYTES`——
与 T3 那个测量 sink 同形，而且更糟一层：无界增长的是**内存**而不是磁盘文件。

修法按台账要求同款，并且是**合并而不是复制**：`_run_measure` 泛化成
`_run_bounded(argv, output, *, seconds, limit)`，输出落进 `tempfile.TemporaryDirectory` 里的
`probe.json`，边写边量、超限即杀，`except BaseException: kill; raise` 原样保留。
两条通道从此共用一个跑法，`_measure` 只是换了参数。

RED 实跑（先红后绿，四条新用例）：

| 用例 | 修前 | 修后 |
| --- | --- | --- |
| 存根写超限 1 KiB 后再赖活 5 秒 | **红**：`.probe-finished` 标记在，即整整等完 5 秒且先把超限字节全读进内存 | 绿：标记不在，进程被杀 |
| 存根写超限**恰好 1 字节**后赖活 | 变异存活时才发现的缺口（见下） | 绿 |
| 停在上限上再赖活 0.4 秒 | 绿 | 绿（端点不许收紧） |
| Ctrl-C 落在轮询体里 | 绿（测量侧已有同款） | 绿，`-SIGKILL` |

顺带删掉 `IO` 导入（`_run_measure` 的 `sink` 参数随之消失），`MEASURE_POLL_SECONDS`
改名 `OUTPUT_POLL_SECONDS`——它现在同时管两条通道，原名是假话。

**改完顺手核了 `_reject` 的那份清单，它已经过期。** 原文写着「两处 subprocess 调用靠先离开
handler 再拒绝把引用丢掉」——新写法是在 handler 里拒绝（与 `_measure` 一致），所以这句不成立了。
实测把链条摸了一遍：注入一次 IO 错误，`__context__` 是 `OSError`，
`filename` 是 `/var/folders/…/automation-tool-probe-…/probe.json`，**本模块自己的临时文件，
不是用户的素材路径**；而 `TimeoutExpired` 现在根本不产生（超时是我们自己的 deadline），
那个曾经携带 argv（内含素材路径）的异常对象不再存在。docstring 按实测改准，
并补一条用例把这个结论钉住（`test_the_chain_behind_a_rejection_names_only_our_own_scratch_file`）——
安全结论写在注释里而没有用例，是本线反复吃过的那种会腐烂的句子。

（这条也是一次自查翻车：第一次测的时候拿了一个非媒体文件，`returncode != 0` 在
`answer.stat()` 之前就把它拒了，于是「`__context__` 是 None」的结论是假的——那条路径压根没跑到。
换成真实素材才看见真正的 `OSError`。）

**一条实测边界值得记**：真实 ffprobe 的输出在实践中有上界。想造一份真超 1 MiB 的真实输出，
试了多流 Matroska——**ffmpeg 拒绝复用超过 1000 条流**（`max_streams` 默认 1000），
1000 条流按本查询约 90 KB。也就是说 1 MiB 这个上限比真实工具在默认限制下能吐出的最大值还高约 11 倍，
它守的是「工具异常或被替换」，不是日常形状。因此这一支的真实二进制用例造不出来，仍由存根覆盖，
理由记在此处而不是让它看起来像漏测。

### 必补②：`probe_material`↔`register` 之间的窗口

不给 `MaterialFacts` 加字段（T5 冻结的无路径类），也没有另开产物类型——**因为不需要**：

| `unusable_frame_size` | 宽度写 0 的 BMP，ffprobe exit=0 且报 `width: 0` | 是 |
| `frame_too_large` | 9000×100 的 PNG（3 KB） | 是 |
| `file_too_large` | 16 GiB + 1 的稀疏文件，不占磁盘 | 是 |
| `silent_audio` | 纯音频全程数字静音 | 是 |
| `probe_failed` | `avc1` 样本条目改名，ffprobe 报出 video 流但**没有 `codec_name`** | 是 |
| `probe_crashed` | 自杀的存根（`kill -9 $$`） | **否，且造不出来** |

`probe_crashed` 这一支考的是「操作系统把被信号杀死的子进程报成负退出码」时我们怎么办，
与 ffprobe 本身无关，随包工具也没法被要求按需去死——存根逐字复现这件事。理由写在用例旁边。

**造这些素材时试错的实测结论**（都是只有真跑才知道的）：

- **MP4 的头改不动时长。** `mvhd`、`tkhd`、`mdhd` 三处 duration 全改成 4 小时，
  ffprobe 照旧报 3.037 秒——它是从 sample table 算的。把 `mdhd` 的 timescale 缩到 1
  也不行（报 2.000000）。**Matroska 的 `SegmentInfo/Duration` 才是「说了就算」的那种**，
  一个 8 字节 double、单位是 timecode scale（默认毫秒），改完真报 14401.000000。
  顺带：同一段 2.041 秒音频装进 Matroska 后容器报 2.064 秒（`seekable.mka`），
  所以定位那个元素时是按「值等于这份文件真实时长」找的，并断言恰好命中一处；
- **`mp4a` 改名不管用**：ffprobe 从码流里把 `aac` 认回来了。`avc1` 改名才会让它交出
  一个没有 `codec_name` 的 video 流；
- **宽度为 0 需要图片容器**：空的 `.h264` 确实报 `width: 0`，但它是 timed 容器，
  时长先被拒（`unusable_duration`），到不了画幅那一步；BMP 走 `bmp_pipe`，不问时长。
  一并留了 `one-pixel.bmp`（58 字节，1×1，判成 IMAGE）作为同一夹具的正向对照；
- **改 `stsd` 里的画幅没用**：把 `avc1` 的 width 写成 0，ffprobe 从 SPS 里把 480×854 读回来了。

### 拿探测产物真造 `Material`：填得满，并且有两条填不进去

审查指出的缺口是「仓库里没有任何用例真的拿探测产物去建一个 `Material`」。
现在六条产出事实的素材逐条经 `_material_from(facts)` 真构造（构造成功即断言，
因为 `Material.__post_init__` 校验的是**组合**而不是范围），并回读六个字段。

**跨层常量相等挡不住形状组合错误**这点也顺手证明了一遍：两层限值一模一样，
照样允许「视频被判成图片」（T2 的 Critical 就是这类），而 `Material` 会当场拒绝
`kind=IMAGE` 带时长、`kind=AUDIO` 带画幅、`kind=AUDIO` 而无有声。

**发现两条事实在 `Material` 里没有家**：`video_codec` 与 `audio_codec`——
`Material` 十六个字段里没有任何编码名字段。不是缺陷（判断要不要转码是在持有文件的这台机器上做的，
属 LE-10/LE-12），但必须显式：`FACTS_WITH_NO_FIELD_IN_THE_DOMAIN` 列出这两个，
并由两条结构测试守着——一条读本测试文件自己的 AST，要求 `MaterialFacts` 每个字段
要么被 `_material_from` 真的读到、要么在豁免集合里（**以后给 `MaterialFacts` 加字段，
不表态就会红**）；另一条反过来核豁免集合，要求这两个名字在 `Material` 里真的不存在
——豁免清单会腐烂成万能通行证，这是本仓库反复吃过的教训。

跨层一致性同时补齐：`ProbedMaterialKind` 与 `MaterialKind` **成员名与取值逐一相同**、
每个 probed kind 都能按值构出 domain kind（`_material_from` 就靠这条按值转换而不是维护映射表），
以及两个上限与 domain 的相等。

### `_require_state_directory` 补齐到私有目录档（Q2 压着的那条不再悬）

T6 修复轮把 `O_NOFOLLOW` 降级成「廉价纵深，承重的是目录权限边界」，可那句话当时**没人守**：
`is_dir()` 收下世界可读的目录，也收下指向它的软链。选择补齐而不是「由启动方保证」，
因为本线还没有启动方可指——那就真悬着了。

补到 `local_artifact._require_private_directory` 同档（重写而非引私有名，与 `_require_tool` 同理）：
`lstat`（软链因此不是目录）→ `S_ISDIR` → POSIX 下 `st_uid == getuid()` 且 mode **恰好** 0700 →
Windows 下问 `windows_acl.validate_private_acl`（**这是公开函数**，`local_artifact` 就在同一位置调它，
所以是复用；它在别的平台连 import 都会失败，`advapi32.dll` 是加载期打开的，故 import 放在分支里）。

**这一档不是新要求**：`ledger` 建的就是同一个 state 根，用的就是 `mkdir(mode=0o700)`；
测试夹具 `_state_directory` 本来也是 0o700——**它的 62 处既有调用一条没改**。祖先目录不走：
建根的人（ledger）已经查过 `_reject_linked_ancestors`，每个注册表再查一遍会把
「数据目录合法地在软链后面」的安装拒之门外。

新用例 11 + 2 条（前者一类、后者一类，逐条实跑）：0o755/0o750/0o701/0o600/0o777 五种模式
（**只写一条 0o755 会被「只看世界位」的实现满足，组位就漏了**）、软链指向私有目录、
非本人所有（`monkeypatch` 掉 `getuid`）、`lstat` 失败（父目录不可进入）、传的是 `str`、
以及正向那条 0o700；另一类是两条 Windows ACL（往 `sys.modules` 注入替身 + 把 `os.name` 改成 `nt`，
接受与拒绝各一条）。
