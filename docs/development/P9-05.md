## 2026-07-31 合并复审：PEM 行尾空白

Codex Review 用 Node/OpenSSL 生成一份真实 PKCS#8 私钥，并把 BEGIN 行改为
`-----BEGIN PRIVATE KEY----- \t\r\n`。`createPrivateKey()` 仍接受它，旧审计却只匹配
header 紧邻 `\n`/`\r\n`，因此坏包错误通过。先补真实私钥 fixture 看到 RED，再把扫描器
改成有界流式状态检查：header 后允许任意空格/Tab，随后遇到 LF/CRLF 即拒绝；header、
空白和换行跨 1 MiB chunk 仍保持状态。NUL 结尾的 FFmpeg 能力字符串继续允许，不会退回
PC-16 已修掉的误报。Node 12 项契约、ESLint 与 TypeScript 全绿。

第二轮 Codex Review 用一个 1 MiB 边界反例推翻了首版状态机：文件前面已有完整
RSA 私钥 header，块尾再放一个未结束的通用 header，后者会让循环提前退出并把前者
遮住。新增 RED 复现后，扫描器改为先遍历所有 header 的全部命中，只在确认没有完整
私钥行后才统一提交跨块状态；同时用真实 OpenSSL fixture 证明 VT/FF 也是它接受的
header 行尾空白并纳入拒绝。块尾的 NUL 能力字符串继续通过，完整私钥不再能借另一条
不完整 header 脱身。

第三轮复审探测又构造出 OpenSSL 接受的 `CR + Tab + LF` header；首版把 CR 单独当成
只能直接接 LF 的状态，导致该私钥漏检。新增真实 `createPrivateKey()` RED 后，CR 与
Tab/VT/FF/Space 一起留在有界的行尾空白状态，直到 LF 才拒绝；状态跨 chunk 时同样
保留。Node 14 项恢复全绿。
