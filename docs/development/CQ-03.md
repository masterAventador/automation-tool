## 任务

两种视频任务、独立剪辑任务、Browser Use、双平台发布与 RPA 共用 Chromium/本机资源并发时
覆盖 CPU、内存、磁盘、网络、取消、紧停、崩溃、休眠和 App 退出；进程/Profile 互不干扰；
B站无凭据时使用 Mock/契约路径并保留待补真实证据。

## 本任务真正要防的事

产品把**一套** Chromium 同时给三条线用：

| 线 | Profile | 输入可信度 |
| --- | --- | --- |
| RPA 运营 | App 私有持久 Profile，装着用户的平台登录态 | 平台网页，不可信 |
| Browser Use | 每次新建的临时 Profile | 网页内容 + 模型输出，不可信 |
| 动效渲染 | 每次新建的临时 Profile | 生成的 HTML，不可信 |

共用二进制是有意的（EB-02 验过一套就够）。危险在于后两条线的输入**都不可信**：
一旦它们能写到运营 Profile，一次渲染崩溃或一段注入网页就能带走用户的平台登录态。

## 第一版判据是错的，跑真实浏览器才发现

判据最初写成"三条线一起跑，运营 Profile 不变"。第一次真跑就红了，而且**不是因为隔离被
破坏**——运营浏览器自己在跑，它当然一直在写自己的缓存、会话和数据库：

```text
added=['Default/AutofillAiModelCache/LOCK', 'Default/BrowsingTopicsState',
       'Default/GCM Store/000003.log', 'Default/Sessions/Session_13429471990385831', …38 项]
changed=['Default/Cache/Cache_Data/sqldb1-wal', 'Default/Web Data', …4 项]
```

「运营 Profile 在并发期间不变」这个假设从一开始就不成立。改成两阶段后判据才问对了问题：

- **阶段一**：运营 Profile **静止**（浏览器不启动，只有磁盘上的登录态），另外两条线并发
  跑，验证它逐文件指纹未变。这才是真实威胁场景——用户没在做 RPA，但登录态在磁盘上，
  此时跑渲染或 Browser Use 不能碰它。
- **阶段二**：三条线全起来，验证进程树互相独立。

**只有把运营线的浏览器停下，才问得出"别人有没有碰它"。**

## 第二个真实发现：进程清理必须按进程组

第二次跑仍然红，这次是残留：

```text
CQ-03 acceptance failed: packaged browser processes survived the run: [5554, 5653]
```

原因是 `stop()` 只 `terminate()` 了主进程，而 Chromium 会 fork 出一串 helper。
`start_new_session=True` 让每条线自成进程组，所以正确做法是按组 `killpg`——**这也正是
产品侧必须保证的语义**，EB-15 的"进程树完全拆除"验的是同一件事。

第三次跑又红在同样的 pid 上：那两个是**上一轮失败遗留**的，不是本次产生的。所以验收改成
只对本次新增的进程判定残留，并在开头报告忽略了几个历史进程——否则一次失败会让之后每一次
运行都失败，而那不是后续运行的问题。遗留的两个进程已确认属于本项目（命令行含包路径）
并单独清理。

## 失败矩阵

| 场景 | 结果 | 覆盖 |
| --- | --- | --- |
| 两条线共用一个 Profile | 拒绝 | 合成 |
| 一条线的 Profile 嵌在另一条里 | 拒绝（路径字符串不同但写入会落进对方的树） | 合成 |
| 只有一条线就谈"隔离" | 拒绝，那是空话 | 合成 |
| 并发期间运营 Profile 被新增文件 | 拒绝 | 合成 + 真实注入 |
| 并发期间运营 Profile 被改写 | 拒绝 | 合成 |
| 并发期间运营 Profile 被删文件 | 拒绝 | 合成 |
| 指纹取自不存在的目录 | 与"存在但为空"可区分 | 合成 |
| `before` 指纹为空 | 拒绝，比较无意义 | 验收脚本内建 |
| 用户取消 Browser Use | 另外两条照常存活 | 发布候选包内 Chromium 真实并发 |
| 渲染进程树硬崩溃 | 运营与 Browser Use 照常存活 | 发布候选包内 Chromium 真实并发 |
| 全局紧停 | 三棵进程树全部退出 | 发布候选包内 Chromium 真实并发 |
| App 退出 | 三棵进程树全部优雅退出 | 发布候选包内 Chromium 真实并发 |
| 动作前已有参与线死亡 | 拒绝，不能拿假基线证明隔离 | 合成 |
| 生命周期动作连带杀死旁路线 | 拒绝并点名旁路线 | 合成 |
| 运行结束仍有本次进程 | 拒绝并列出 pid | 真实并发运行 |
| 上一轮遗留的进程 | 报告并忽略，不算本次失败 | 真实并发运行 |

## 正常用户路径验收

**不适用于用户入口**：CQ-03 是资源与隔离的回归门禁，没有对应的用户页面。本任务的"真实"
体现在真实的正式包、真实的浏览器进程、真实的并发与真实的进程组拆除，而不是模拟对象。

## 真实边界

1. **三条线是浏览器层面的模拟，不是完整业务任务**。跑的是"三个用不同 Profile 的真实
   Chromium 进程"，不是真的在渲染视频、真的在剪辑、真的在发布。隔离与进程独立性这两条
   结论成立，但"两种视频任务 + 独立剪辑任务同时跑"的**资源压力**（CPU、内存、磁盘、网络）
   没有测。
2. **休眠没测**。macOS 休眠需要真实系统事件，本轮没做。
3. **取消、紧停、崩溃、App 退出已在浏览器进程/Profile 层合并进同一并发场景**。这证明
   三棵真实包内 Chromium 进程树的影响范围与清理语义；它仍不等价于把真实视频 RenderJob、
   剪辑任务和平台发布任务同时跑起来，因此不据此声称业务任务级压力已经完成。
4. **只覆盖 macOS arm64**。Windows 正式包尚在构建，同一条验收没在 Windows 上跑过；
   脚本目前显式拒绝非 macOS 主机。
5. **B站相关完全未涉及**。它不走浏览器，与本任务的"共用 Chromium"主线无关。

## 清理

三条线各自成进程组，结束时按组拆除；验收结束再扫一次进程表确认本次新增进程为空。
临时 Profile 在 `/private/tmp` 的临时目录里，退出即删。上一轮失败遗留的两个进程已核对
命令行确属本项目后单独清理，未动用户或其他项目的浏览器。
