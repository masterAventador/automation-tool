## 修复与验证（M1/M2/M3、S1～S5）

**M1**：`build_platform_command_router` 抽成生产装配唯一入口（`cli.py` 与测试共用），
发布操作改用**自己的队列**——它的摘要是给 App 的本地事实，不是 Control Plane 协议
消息。3 条断言分别锁住：摘要进出站队列必被拒、生产装配后出站队列干净、登录健康信封
仍能正常送达。

**M2**：三处一起修，且都在真实链路上验证：

- `PlatformCommandRouter` 在派发登录/注销命令前**先回收**发布侧持有的运营浏览器
  （`release_surface()`），并把**可派发的** ready 回执置空——页面已被收回，提交前回执
  随即失效，PB-06 不可能拿着过期回执去点发布；handoff/blocked 回执保留用于上报（I-α）；
- 新增 `douyin.publish.release` 会话式命令（复用既有 `proof_for_session_command`），
  给用户/App 一个显式归还入口，返回 `publish_released`；
- 登录操作单独捕获 `BrowserLaunchAuthorityRejected`，返回 `browser_busy` 而不是让整个
  执行器退出；
- 浏览器授权竞争与页面租约被借出是两回事，拆成 `browser_busy` 与 `surface_not_owned`
  两个 evidence，PB-06/PB-07 才能给出不同处置。

**M3**：新增 `rpa/douyin/page_anchors.py` 作为可见锚点探测的**单点定义**，并把
`session.py`、`login.py`、`publish_page.py` 三处全部迁移过去。修复过程中发现"把选择器
逗号合并再判可见"这个写法本身不成立：既有 `DOUYIN_RISK_CHALLENGE_SELECTORS` 等混了
Playwright 引擎语法（`text=`、`text=/正则/`），逗号只对纯 CSS 成立，合并会直接报错——
真实浏览器回归立刻暴露（登录链 3 条用例变成 `page_unavailable`）。最终实现：

- `any_visible` **逐 selector** 探测（兼容混合引擎），每个 selector 走
  `locator(s).locator("visible=true").count() > 0`，任一可见即真；
- `unique_visible` 保留纯 CSS 分组（锚点去重、判定冲突），仅用于发布页锚点；
- 探测失败一律抛出，不当作"不存在"。

`session.py` 与 `login.py` 的同类 fail-open 一并修掉，并各补了"隐藏占位不遮蔽真实挑战"
的回归单测。

**S1**：`_bounded_text` 增加 `contains_control_or_bidi` 拒绝，登录命令的
`_require_command_fields` 一并加固——NUL 不可能再挪动证明的字段边界（Rust 侧将来生成
发布证明时也不会因实现出入产生碰撞）。

**S2**：`artifact_input()`/`title_input()`/`description_input()` 不再返回完整
Playwright Locator，改为只读 facade `PublishUploadField`/`PublishTextField`，只暴露
`set_input_files()`/`fill()`，locator 由闭包捕获而不是属性持有。这让"不点提交"从
纯类型约定变成**属性层面不可达**的防误用边界（见 I3 的措辞更正）。

**S3**：账号选择器从流程层移入 `publish_page.py`，流程只调 `page.target_account()`，
脱敏仍在流程层。

**S4**：上传后**再次 `revalidate()`**，回执绑定的摘要在上传前后都被证明一致；上传中
被替换的同名文件在填写正文前即拒绝（新增单测）。TOCTOU 窗口缩小到"Playwright 按路径
打开文件"这一瞬，残留窗口如实登记在下方，措辞不再写成"防路径替换"。

**S5**：见「频控与 ActionGate（当前缺口，已登记）」。

**C1（首轮）**：551 行的 `_close_active()` 改为 `best_effort=True`，与其余三处一致。

**C-1 订正（第二轮复审）**：首轮那句"真正的故障会在紧接着的 `_begin()` 里变成回执"
是**错的**——`_begin()` 只有 `BrowserLaunchAuthorityRejected` / `SurfaceLeaseRejected`
被转成回执，内置 Chromium 起不来、profile 被上一个没关掉的浏览器占用、driver 崩溃、
磁盘满都会落到通用 `except Exception` → `PlatformCommandRejected` → 执行器进程终止。
而这与 `best_effort=True` 是耦合的：关不掉恰恰意味着旧 Chromium 还占着同一个持久
profile，下一次 `start()` 正是最可能失败的那步。现已补上 `BROWSER_UNAVAILABLE`
evidence：`_begin` 的任何意外失败都转成 blocked 回执，注释与本台账一并订正。

**C2**：新增 `BrowserSurfaceOwningOperation` Protocol（继承 `PlatformCommandOperation`
并要求 `release_surface`），router 的 `publish` 参数按它 `isinstance` 校验，`handle`
直接调用而不再做 `getattr` 探测——不合格的实现在**构造时**被拒，M2 的释放不可能被
静默跳过。

**I1**：发布摘要队列在生产没有任何消费方，`PlatformPublishPreflightSummary` 与该队列
一并删除。`latest_receipt()` 成为唯一观察点（归还窗口时只置空可派发的 ready 回执，
handoff/blocked 回执保留用于上报，见 I-α），PB-07 再建 App 侧投影。注释与本台账同步改正，不留"带误导性注释的无界黑洞队列"。

**I2**：Rust `valid_platform_command_state` 加入 `browser_busy` 并补跨语言证明向量
测试；否则登录链返回该状态时用户看到的是"认证被拒"。

**I-A**：只有 `BLOCKED` 才关闭运营浏览器；`HANDOFF_REQUIRED`（验证码/滑块/风控/登录
失效）**保留可见窗口**给用户接管，与 `DouyinLoginCommandOperation` 的既有行为一致
（它也只在 `healthy` 时关）。归还入口是显式的 `douyin.publish.release`。

**I-B**：Artifact 打不开、内容超出 preflight 策略两条路径现在分别落
`ARTIFACT_REJECTED` / `CONTENT_REJECTED` 回执——`latest_receipt()` 真正做到"有状态
就有解释"。`latest_receipt()` 的 docstring 也改成如实描述：只有 *ready* 回执会随
释放失效，blocked/handoff 回执在浏览器关闭后仍保留用于上报。

**I-C**：`kill_held_browser` 改用 `main` 已有的跨平台 helper
`process_ids_matching()` / `terminate_process()`，本文件里另外两处 POSIX 专有实现
（本地 `_browser_processes`、本地 profile 权限断言）一并换成共享的
`assert_private_profile_directory()` / `create_private_profile_directory()`，不再维护
第四份。

**C-A（部分修复 + 部分回退）**：

*保留的部分*：结果帧的 flowVersion 改为按**命令族**查表（`_flow_version_for_command`），
不再从 state 反推。反推只在"每个 state 只属于一个命令族"时成立，一旦两族共用一个
state 就会给结果帧盖错契约——这个缺陷形状是真实的，值得单独堵死。查表是**显式映射
且未登记的命令族直接拒绝**（C-A-2）：留默认分支等于把同一个缺陷从 state 搬到
command_type 上，PB-07 往 Rust 加发布族时漏改就会原样复发。
`write_platform_command_result` 与 `ExecutorProcessReporter.platform_command_result`
新增 `command_type`，由 `PlatformCommandWorker` 从已认证命令传入。

*回退的部分*：登录/注销链路上新增的 `browser_busy` 结果状态**已全部撤回**（Python
`_ALLOWED_COMMAND_RESULTS`、`BROWSER_BUSY_STATE`、登录操作的专门分支、Rust 白名单与
两条跨语言向量测试，`executor_bootstrap.rs` 现已与基线逐字节一致）。原因是第四轮
审查查到这个状态在 App 层根本无法表达：`lib.rs` 对任何非 `logged_out` 的注销结果一律
`authentication_rejected`/`retryable: false`，登录侧
`platform-session-gateway.ts` 的 `.strict()` Zod 枚举也没有它，`PlatformSessions.tsx`
更没有文案（全仓 `.ts/.tsx/contracts` 对 `browser_busy` 零命中，我已复核）。净效果是
**把可恢复错误变成不可恢复错误**：回退前该场景以 `process_unavailable` /
`retryable: true` 暴露，用户重试即可；接了一半之后变成 `protocol_mismatch` /
`retryable: false` 且无文案。PB-05 的范围是发布前流程，不应改登录链的用户可见行为，
因此选择回退而不是半途接线，并补测试锁住"授权竞争仍走原有可重试路径"这一决策。

**发布族内部**的 `BROWSER_BUSY` **evidence** 保留：它是执行器内部事实，只出现在
`latest_receipt()` 上，发布命令族在 Rust 里还没有枚举值、不会穿到 TS。**evidence 是
执行器内部事实，state 才是跨端协议**——这条区别是本次回退的判定依据。

**I-α**：`release_surface()` 只清空**可派发的** ready 回执，blocked/handoff 回执保留
——docstring 因此成真，`latest_receipt()` 在归还后仍能解释"为什么要人接管"。台账里
M2 那句"同时把 `latest_receipt()` 置空"随之订正为"只置空 ready 回执"。

**I-δ**：`chmod(0o000)` 那条不可读用例加 `skipif(os.name == "nt")` 并写明 Windows 上
`chmod(0)` 只置只读属性；两条 symlink 用例改为能力探测 skip（Windows 需开发者模式）。
Windows 清单第 18 节同步改正 helper 名（`assert_private_profile_directory`）并如实
记录这两处平台能力差异。

**I3 措辞改正**：facade 改为**闭包捕获** locator（不再作为属性存在），单测改成有区分度
的断言（`_locator` 不可达、无 `__dict__`、`dir()` 暴露的成员里没有 locator 对象，另加
一条"确实写进真实 locator"的正向断言）。同时如实说明：这是**防误用边界，不是安全
边界**——Python 仍可通过 `__closure__` 反射拿到 locator。

## 失败矩阵

- **页面改版**：入口/表单锚点缺失、锚点重复、路由被改到未知路径、页面不可读 → 分别
  显式暴露，不猜测、不降级；
- **遮罩**：引导遮罩/弹层可见 → `dialog_blocked`；**隐藏占位节点不再能遮蔽真实遮罩**；
- **登录失效**：登录面板可见 → 转人工，不重放；
- **验证码/滑块/风控**：统一转人工，**不实现任何绕过**；上传后才出现的挑战同样在填写
  前拦停；**隐藏占位节点不再能遮蔽真实挑战**（M3 真实浏览器回归）；
- **租约与浏览器竞争**：租约被借出 → `surface_not_owned` 且不启动浏览器；浏览器授权被
  其他流程持有 → `browser_busy`；流程中途失去所有权 → `surface_lost`；登录/注销命令
  先回收发布侧持有的浏览器，绝不出现"发布一次就再也无法注销"；
- **Artifact 受控上传**：相对路径、`..` 段、控制字符/BiDi、目录、缺失、软链接、软链接
  祖先、硬链接、非属主、未知扩展名（含 `.MP4`、双扩展名）、0 字节、超上限、不可读一律
  拒绝；选择后被替换的同名文件在上传前 revalidate 拒绝；**上传后再次 revalidate**，
  上传过程中被替换同样拒绝；
- **内容边界**：标题/简介为空、超字数、含控制字符、含本机路径或 cookie/token 形状文本
  在 Intent 构造即拒绝；
- **不可信页面文本**：账号名经 BU-05 脱敏并再过安全文本策略，超长或不安全直接丢弃；
- **命令认证**：篡改任一被绑定字段立即失败；登录证明不能授权发布命令；控制字符不能
  挪动证明字段边界；发布字段出现在登录/注销/归还命令上被模型层拒绝；
- **出站边界**：发布摘要不是协议信封，绝不进入 Control Plane 出站队列（生产装配级
  回归）；
- **单次性**：一个 `DouyinPublishPreflight` 只能 run 一次；
- **持有期间浏览器意外消失**：用户手动关闭可见运营窗口、浏览器进程被强杀、关闭动作
  本身失败三种情况下，下一条发布命令都正常出回执，**不终止执行器进程**（三条真实
  浏览器用例）；
- **浏览器起不来**：关闭失败导致旧 Chromium 仍占着持久 profile、下一次启动失败时，
  转成 `BROWSER_UNAVAILABLE` blocked 回执而不是终止进程（真实浏览器用例）；
- **转人工时窗口保留**：`HANDOFF_REQUIRED` 不关闭运营浏览器，用户能在可见窗口里完成
  验证码/滑块/风控/登录；`BLOCKED` 才释放窗口（两条真实浏览器用例分别断言开/关）；
- **状态必有解释**：preflight 族每一个返回状态都对应一条 `latest_receipt()` 回执，
  包括 Artifact 打不开（`ARTIFACT_REJECTED`）与内容超限（`CONTENT_REJECTED`）；
  `publish_released` 之后保留的是上一次 preflight 的 handoff/blocked 回执，ready 回执
  按设计失效；
- **结果帧契约**：flowVersion 由命令族决定，`browser_busy` 落在注销上时仍是
  `douyin.session-control.v1`，Rust 侧同时接受（C-A 回归，跨语言证明向量）；
- **接管期占用运营浏览器**（已知代价，见下）：handoff 保留窗口期间，共用同一个
  `BrowserLaunchAuthority` 的 Control Plane 搜索/评论/私信任务会被拒并上报
  `page_unavailable`；此外用户还在做验证码时新发一条发布命令会直接关掉接管窗口
  （新意图覆盖旧意图），当前无测试覆盖；
- **提交前硬边界**：代码里没有点击发布控件的路径（facade 只暴露 `fill`/
  `set_input_files`，locator 闭包捕获、属性层面不可达），真实浏览器上 `__submitClicks`
  始终为 0。

## 频控与 ActionGate（当前缺口，已登记）

preflight 会**真实把整个视频上传到抖音服务器**，属于有出站流量的平台动作。本任务
**没有**接入 ActionGate 的最小间隔、每日上限、连续失败熔断与一键紧停：`ExecutorActionGate`
与副作用账本的准入要求 Control Plane 侧 Ed25519 签名放行，且当前动作枚举只覆盖评论/
私信，发布动作的授权链属于 PB-06。当前仅有的实际约束是：单个执行器进程内浏览器授权
互斥（同一时刻只可能有一条 preflight 在跑），命令之间不会并发上传。

**上传没有幂等键**：`handle()` 全程不对 `publish_job_id` 做任何去重——同一条命令帧
原样重放 N 次就是 N 次完整视频上传。`publishJobId` 虽被绑进 HMAC，但那只防篡改、
不做幂等。CLAUDE.md §4.4 要求"外部副作用必须有幂等键"，这一条在 PB-05 阶段**没有**
满足。浏览器授权互斥只挡并发，不挡连续重放。

**这是一个已知缺口，不是已完成项**：发布动作的 ActionGate 准入、频控、熔断与上传
幂等键必须在 PB-06 与单次 dispatch 一并建设，闭合前 PB-05 保持 `🔍 待验收`。

## 已知代价与未接线守卫（本任务不修，登记待补）

**I-β：转人工保留窗口让共享 `BrowserLaunchAuthority` 的持有变成无界。** 按 §5 转人工
必须保留可见窗口（I-A），代价是持有时间从"一条命令"变成"用户什么时候做完验证码"，
既无上界也无 deadline（对比 `BrowserSurfaceLeaseManager` 有 1 小时上限）。归还出口有
四个且都可达（显式 release 命令、router 在登录/注销前回收、下一条 preflight 开头的
关闭、worker teardown），因此**不存在 M2 那种硬死锁**；但
`ProductionDouyinDiscoveryOperation` / `ProductionDouyinActionOperation` 跑在
`LocalExecutorProcess.run` 线程上、共用同一个 `BrowserLaunchAuthority`，够不到
`release_surface()`。实测后果：接管期间这些任务被拒并上报 `page_unavailable`——诊断
信息是错的（不是页面坏了，是浏览器被占着），还会消耗 §7 的连续失败熔断额度。
后续需要：给 handoff 持有加上限/心跳，并让任务侧能区分"被发布接管占用"与"页面不可用"。

**I-γ：生产装配没有共享 `BrowserSurfaceLeaseManager`。** `cli.py` 没有传
`surface_lease`，发布操作因此新建私有实例，生产里它永远停在 `OWNER_ACTIVE`，
`SURFACE_NOT_OWNED` / `SURFACE_LOST` 两条 evidence 在生产同路径下不可达（集成用例能
覆盖是因为测试注入了 manager）。「真实边界」表里"页面租约｜真实
`BrowserSurfaceLeaseManager`"指的是对象真实，**不代表已共享**。PB-06/BU 接入 Browser
Use 接管时必须把 lease manager 提升为 `build_platform_command_router` 的参数并由
Playwright 执行器与借用方共用，届时才谈得上这两条守卫通过验收。

## 真实边界

- **唯一被替代的是抖音发布页内容**：本机没有可用的真实抖音账号，无法扫码登录，发布页
  由自建 fixture 经 Playwright 路由以真实 `https://creator.douyin.com` origin 提供。除
  页面内容外，浏览器进程、驱动、Profile、租约、命令面、认证、上传与文件系统全部真实；
  测试页证据**不**等于真实平台验收；
- **副作用措辞更正**：preflight **不产生不可逆的发布副作用**，但它会把整个视频真实
  上传到抖音服务器，在平台侧留下上传/草稿态记录，上传本身是可重复的出站动作。之前
  "不产生任何外部副作用"的表述不准确，已更正；
- **本任务不写 side-effect 账本**：该表要求先有 ActionGate 签名放行且动作限于评论/私信。
  为"停在提交前、不会 dispatch 的动作"写 prepared 记录会伪造账本语义，因此幂等键与
  prepare/dispatch/verify 属于 PB-06 真正点击那一次；PB-05 只把 content hash 交给
  `latest_receipt()` 供 PB-06 临界点确认绑定，且该回执在浏览器被回收时立即失效；
- **`scripts/run_pb_05_acceptance.py` 是 Browser Use 受限工具面的契约边界证据，不是本
  任务实现链路证据**：PB-05 交付的是确定性 Playwright 驱动，Browser Use Agent 真正驱动
  识别与操作属于 PB-06/PB-08。该脚本证明的是"发布策略只能到达冻结路由、危险动作不可
  达"，**不能读成"Browser Use 那部分已验收"**；
- **TOCTOU 残留窗口**：上传前后各 revalidate 一次，但 Playwright driver 仍按路径重新
  打开文件，替换窗口被缩小而非关闭；检测到替换即拒绝，不会带着旧摘要进入提交前。彻底
  关闭需要把 Artifact 硬链接/复制进 App 私有暂存目录再上传，登记为后续改进；
- 真实发布页的选择器与路由必然与 v1 冻结值有差异，这正是 `page_drift`/`route_unknown`
  存在的原因：改版会被显式暴露并转人工；
- Windows 侧同链路证据由并行 Windows 会话补齐；本任务新增测试已避免 POSIX 专有断言
  （Profile 私有性按 `os.name` 分支走 Windows ACL，残留进程检查在 Windows 上走
  `Get-CimInstance`）。
