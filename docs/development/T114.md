## 结论先行

派单问的是「能不能在不接真实抖音账号的前提下，把『已登录 → 重启 → 点按钮』确定性地造出来」。
答案分成两半，而且**第一半推翻了 T109 的说法**：

1. **「healthy → 重启 → 点『我已处理，重新检查』」这条路早就有真实 App 覆盖，T109 说它没有，这个说法是错的。**
   `frontend/e2e-tauri/platform-session-reuse.spec.ts` 的 `restart` 相位干的正是这件事：
   `openPlatformPage("登录正常")` 之后 `runRecheck(healthy)`。它由
   `scripts/run_b5_15_acceptance.py` 驱动，**四个相位是四次真正的 App 生命周期**
   （每相位一个独立 wdio 进程，spec 末尾 `exit_app_for_acceptance`，相位之间
   `require_no_residual_project_processes` 核对进程确实死了），共用同一个档案。
   `git log` 显示这个 `restart` 相位自 `c7ecd1a`（2026-07-20）就在，早于 T109（07-27）七天。
   所以答案是：**不需要真实账号，仓库里已经有跑通的机器**——登录页事实由
   `backend/tests/fixtures/b5_15_executor.py` 用 Playwright 路由伪造，
   而 App、Rust 桥、Tauri 命令、内置 Chromium、档案存储、执行器协议全是真的。

2. **真正没有任何覆盖、并且会造成永久失败的，是另一格：租约被弃置。** 这一格不需要登录态，
   本任务补的就是它。

## 一、那一格是什么，为什么它必然会被用户撞到

`executor_platform.rs:614-622` 只在一种情况下归还运营浏览器档案：

```rust
|state| state == "healthy",
```

也就是说，**凡是没到 `healthy` 的登录结果——`awaiting_scan`、`awaiting_confirmation`、
`qr_expired`、`handoff_required`、`login_required`、`unknown`——App 都故意继续持有档案租约、
让浏览器开着**（注释写得很清楚：还在等扫码的登录没结束，必须留住档案）。

而「等扫码」正是产品**主动把用户支开**的时刻：页面说「请在打开的运营浏览器中扫码登录」。
用户这时候关掉 App、强制退出、或者 App 崩了——只要不是走 `RunEvent::Exit`
（`lib.rs:4660-4670` → `shutdown_for_app_exit` → `release_platform_profile`），
`release()` 就永远不会执行，磁盘上留下 `{"state":"active","version":1}`。

此后每一次按这两个按钮，`under_profile_lease` 的 `try_acquire_owned_lock` 都会读到这个标记
（`browser_profiles_unix.rs:102`，`allow_abandoned_active_marker` 为 false）并返回
`RecoveryRequired`——**永久失败，重试一万次都一样**，唯一出路是「安全注销」，
而「安全注销」会**删掉整个档案**，用户的抖音登录态随之消失，必须重新扫码。

`browser_profile_locks.rs` 的 `killed_lock_holder_preserves_marker_and_requires_explicit_recovery`
钉住了「档案存储层会留下这个标记」，但**没有任何测试证明正式 App 会走到这一步、
界面会说什么、以及那条唯一出路真的走得通**。

## 二、RED：先承认第一次就绿了，然后再证明它不是空的

**必须说清楚：这个用例第一次跑就通过了（`RUNNER_EXIT=0`）。** T109 的三层修复在真实
App 上确实生效。但一个从没红过的用例证明不了自己在测什么，所以我用**变异测试**取 RED：
把 T109 的那一处映射改回它修复前的样子（`executor_platform.rs:865-867` 的
`RecoveryRequired` 分支并入 `storage_unavailable`），重跑整套，看它是否失败、
以及**失败时说不说得出产品哪里坏了**。

变异后（`MUTATION_RUNNER_EXIT=1`），阶段一照常通过（被杀的 App 仍然留下了 active 标记），

阶段一让 App 走到 `awaiting_scan`（租约被持有），把自己的 PID 交给 runner；
runner `SIGKILL` 它，等进程真的消失，然后**读磁盘确认标记是产品自己写下的**
（`require_abandoned_lease`，不是我塞进去的——塞一个标记只能证明我会写文件）。
阶段二起一个新 App，两个按钮各点一次，断言：

- 出现「上一次运营浏览器没有正常收尾。请先执行「安全注销」，再重新登录一次抖音。」
- 出现「故障代码：profile_recovery_required」
- **不**出现「请稍后重试」
- 再点「安全注销 → 确认注销」，页面到达「需要登录」，档案目录确实被删除，
  服务端 `platform_session_health` 收敛为 `missing`。

最后一条是本次唯一真正新增的产品事实：**那条唯一出路真的走得通**，此前没人验过。

## 四、为什么这么造，而不是别的造法

派单列的三条里，我没用「档案层播种 healthy」和「执行器协议层给 healthy 应答」：

- 播种 healthy 只能造出「显示登录正常」这个**表象**，而用户的抱怨是**按钮报错**，
  两者之间隔着租约状态——播种 healthy 恰好把租约留在干净状态，反而绕开了故障；
- 直接 stub Rust 命令返回值会把被测对象本身 mock 掉，按判据「宁可不做」。

实际用的是第三条（弃置租约），并且**连这个租约都不是我造的**：由正式 App 在被 SIGKILL 时
自己留下。整条链路上唯一的替身是抖音登录页的 HTML（复用 B5-15 已有的
`automation-tool-executor-b515.spec` 签名执行器），它替掉的是**外部平台**，不是被测产品。

## 五、失败矩阵覆盖

| 格 | 本次覆盖方式 |
| --- | --- |
| App 退出 / 崩溃后的登录态恢复 | 阶段一 SIGKILL 持租约的 App，阶段二核对磁盘标记与界面结果 |
| 非法状态转换 / 多实例竞争 | 弃置租约与 `profile_in_use` 分开：前者 `RecoveryRequired`，后者 `AlreadyRunning`，界面文案不同 |
| 幂等 / 重试上限 | 断言页面**不**出现「请稍后重试」——这是一条永远走不通的建议 |
| 失败补偿 | 「安全注销」被纳入同一条用例：档案删除 + 服务端 `missing` + 页面「需要登录」 |
| 资源清理 | runner 在 `finally` 里终止本次 wdio、执行器进程树、Control Plane、compose 栈，删除隔离 AppData，并 `require_port_closed` 两个端口 |
| 敏感信息泄漏 | 断言只读页面公开文案与 `故障代码`，不读 `message`；`check_user_facing_branding.py` 通过 |
