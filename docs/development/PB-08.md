## 增量在哪：不是再写一遍用例，是换掉它们脚下的浏览器

PB-05/PB-06 已经把发布链路在**构建期暂存**出来的 Chromium 上验过了，
`test_douyin_publish_embedded_browser.py` 有 936 行、十几个用例，覆盖冻结入口路由、
预提交、失败矩阵、页面改版、租约接管、单次调度、结果对账、崩溃恢复。

再写一遍这些没有价值。PB-08 真正缺的是：**用户装到机器上的是安装包，不是暂存目录**。
所以增量是把同一套用例脚下的浏览器换成从正式包的发行物 Manifest 解析出来的那一个，
断言一条不改。

实现是 `conftest.py` 里三行：`AUTOMATION_TOOL_PACKAGED_BROWSER_EXECUTABLE` 存在时用它。
路径由本任务的验收脚本从包里解析并校验落在包内——**测试本身不该知道包长什么样**。

## 非空转验证

"33 passed" 本身证明不了它用的是包内浏览器——万一环境变量没被读，它会静默回退到暂存目录
照样全绿。所以把变量指向一个**存在但不是浏览器**的文件再跑：

```text
AUTOMATION_TOOL_PACKAGED_BROWSER_EXECUTABLE=/bin/echo uv run pytest … -k entry_route
  AssertionError:
    - publish_pre_submit_ready
    + publish_blocked
  1 failed
```

测试确实在用这个变量指定的东西启动浏览器。

包本身在使用前也先过了 EB-17 的两条判据（产品代码不引用系统浏览器位置、包内无浏览器
安装脚本），扫描 195 个文件——**不是 0，扫描没落空**。

## 五个维度的落实

| 维度 | 证据 |
| --- | --- |
| 单一 Chromium | 浏览器路径必须 `is_relative_to(包)`；版本与 `embedded-chromium-staging.v1.json` 锁定值一致；跑完按包路径过滤进程表为空 |
| 单次副作用 | 集成套件里的 at-most-once 账本用例照跑（prepare/dispatch/verify、令牌单次消费、重放被拒） |
| 结果对账 | 发布后独立读作品列表核对的用例照跑 |
| 退出清理 | 进程残留检查；套件自身覆盖 Profile 解锁与崩溃恢复 |
| 风控边界 | 失败矩阵用例照跑（页面改版移除上传锚点、隐藏占位符不掩盖可见挑战、租约接管期拒绝预检、用户关闭运营窗口不终止执行器） |

## 真实边界

1. **没有真实平台投稿**。抖音需要扫码登录，B站需要 API 凭据，两者本机都没有。
   "禁止把 Mock 当真实平台证据"这条要求被严格遵守：本任务不声称任何真实投稿发生过。
2. **只覆盖 macOS arm64**。Windows x86_64 正式包尚在构建（EB-16 Windows 侧），
   同一条验收没在 Windows 包上跑过。验收脚本的进程枚举已按 `os.name` 兼容 Windows，
   但没有实跑验证。
3. **不含 App 界面**。跑的是执行器层的发布链路，不是从 Tauri 界面点进去的。
   界面那一层由 PB-07 的 UI Harness 与真实 App 验收覆盖。
4. **B站 API 投稿完全未验**。相关实现在 `bilibili_archive_publishing.py`，
   本任务没有把它纳入范围——它不依赖浏览器，与"包内 Chromium"这条主线无关。
