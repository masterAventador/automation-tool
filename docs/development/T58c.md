# T58c — 拒绝原因不原样转发给用户

> 日期：2026-07-27
>
> 状态：✅ 否定性决策完成；没有生产代码改动
>
> 结论：当前没有一条拒绝原因适合原样进入界面。保留封闭原因作为进程间分类证据，
> 用户界面继续只按封闭错误码展示产品自己编写的中文说明。

## 一、先回答“哪些转发”

**原样转发：0 条。**

`contracts/video/motion-authoring-refusal.v1.json` 目前有 110 个 `fixedReasons`、18 个
`staticGateCodes`。其中 T90b 指出的 29 个 token 分属 5 个
`nonRefusalOutcomes`：

| 类别 | token 数 | 为什么不能当成模型拒绝理由转发 |
| --- | ---: | --- |
| `app_request_invalid` | 9 | App 发给子进程的请求不合法，是我们的契约或组装问题 |
| `installation_damaged` | 16 | 锁定文件缺失、损坏或漂移，是安装问题 |
| `model_configuration_required` | 2 | 模型未配置或配置不可用，应引导到设置 |
| `model_timed_out` | 1 | 服务已连接但超时，是运行故障 |
| `model_transport_failed` | 1 | 没收到服务回应，是网络、地址或服务故障 |

这 29 条都没有资格进入“模型拒绝了这句话”的文案。T90b 已把它们在 Rust 侧收敛成
不同错误码，React 已按码给出网络检查、模型设置、稍后重试或重新安装等固定指引。

其余 81 个 `fixedReasons` 和封闭静态门禁组合也不原样转发。它们是机器 token，
描述的是以下内部事实，而不是模型面向用户写出的解释：

- 模型答复不是 JSON、字段集合或类型不对；
- 设计、脚本、分镜或合成内容没有通过本机 Schema 与静态门禁；
- 工作区、工具面、锁定契约、资源路径或摘要没有通过本机校验；
- App 本应在提交前拦住的 Brief、时长、语言、画幅或素材路径越界。

这些事实对诊断有用，但把 `agent_first_response_must_carry_the_four_closed_fields`、
`remote_reference` 或 `schema validation failed` 一类内部词汇放到卡片上，既不给用户一个
更明确的动作，也会把我们的校验、模型答复质量或安装缺陷写成“模型认为你的描述不行”。

## 二、为什么“这句话太抽象”现在也不能转发

当前模型协议不允许模型返回自然语言拒绝理由。
`MotionAuthoringAgent._first_message_contract()` 要求首答只能有
`design/script/storyboard/composition_html` 四个字段；修复轮只能有
`composition_html`。`_call()` 只读取这份 JSON，模型的 reasoning 增量被丢弃，
上游异常正文也不进入答复。

因此当前链路里没有可信证据证明模型说过“这句话太抽象，说不出画面”。界面若显示这句话，
会是产品替模型编造理由，而不是转发。以后若产品确实需要这种反馈，必须另立封闭协议：

1. 模型只能选择产品预先定义、可本地化的语义码，不能提供自由文本；
2. 宿主对码做 allowlist、字段精确匹配和长度上限校验；
3. Rust 只转发已知码，未知、冲突、超长或额外字段统一落到我们的固定失败文案；
4. React 只按码读取产品自写文案，绝不渲染模型原文。

在这套协议出现之前，“有界、防注入、限长”的唯一安全实现就是不新增自由文本 wire。

## 三、现有边界已经满足这个决策

链路逐层核对结果：

1. Python 的 `_closed_rejection_reason()` 只把固定消息翻译为契约 token；
   未知文本、模型输出、凭据和本机路径都得不到 `rejectionReason`。
2. 子进程最终序列化前再次调用 `_closed_wire_reason()`，调用方不能通过直接构造异常绕过。
3. Rust 的 `rejection_reason_is_closed()` 再按同一份契约复验；未知原因、互相矛盾的
   `status`/原因或未知类别一律归到 `authoring_crashed`。
4. Rust 的 `MotionVideoStudioError` 只序列化固定 `code` 与 `retryable`；
   原因 token 在分类后被丢弃。
5. TypeScript 的 `nativeCommandErrorFields()` 只返回 `code` 与 `retryable`，
   明确不把原生 `message` 返回给调用方；视频工作台只用 `AUTHORING_ERRORS`
   中产品维护的固定中文文案。

所以本任务不需要修改 Python、Rust 或前端。给错误结构增加 `rejectionReason`、自由文本
`detail` 或把原生 `message` 带到 React，都会扩大现有安全边界，却没有新增用户动作。

## 五、失败矩阵

| 情形 | 决策 |

| 29 个非拒绝 token | 只用于分类；界面按类别给固定动作，不显示 token |

| 未来需要“太抽象”等细分反馈 | 新增产品拥有的封闭语义码；仍不接受模型自由文本 |

## 六、真实边界与清理

这是协议和展示边界的否定性决策，没有新增用户功能，也没有启动 App、浏览器、服务、
数据库或模型请求。它证明的是“现有链路不会原样转发原因”，不能替代 T90b 尚缺的正式签名包
目视验收，也不声称模型已经具备向用户解释拒绝理由的能力。

没有产生运行数据、截图、Profile、端口或后台进程，无需额外清理。

## 七、未覆盖项

- 当前没有“用户可见拒绝语义码”协议；这是有意不实现，不是漏接字段。
- 契约里的细粒度 token 仍是内部诊断词汇，不承诺稳定用户语义。
- 若以后新增封闭语义码，应单独 TDD 覆盖 Python → Rust → TypeScript → React，
  并在正式 App 正常入口验证实际展示；不能复用自由文本 `rejectionReason` 走捷径。
