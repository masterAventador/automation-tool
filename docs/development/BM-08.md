## Windows 化改造清单（2026-07-26 调研，未改代码）

### 拒绝 Windows 的根因不在那一行

`scripts/run_bm_08_acceptance.py:92-97` 显式 `raise` 只是表象。真正的根因在**启动契约**：
验收注入的 Worker 走 `lib.rs` 的 `video-studio-e2e` 分支，`AUTOMATION_TOOL_BM08_WORKER`
被当作**单个可执行文件路径**（`MotionWorkerSource::Executable`），而
`VideoWorkerLaunch::new` 把 `arguments` 固定为空。所以 macOS 只能用一个 `#!/bin/sh`
包装脚本假装成"node worker.mjs"——Windows 没有 shebang，这条路直接断。

### 推荐改法：走 package 方案，别用 `.cmd` 包装

复用 `scripts/build_motion_video_worker_candidate.py` 的 `build_candidate()` 产出
`runtime/node.exe` + `app/worker.mjs`，把 e2e 分支从 `Executable` 改成 `Package` +
`VideoWorkerLaunch::bundled_node`——**这正是 BM-03 已在 Windows 验过的生产路径**
（`local_video_orchestrator_windows.rs`）。

不用 `.cmd` 的理由：Rust 的 `Command` 对 `.bat/.cmd` 转由 `cmd.exe /c` 执行，而
`lib.rs` 对该路径做了 `canonicalize`，Windows 上返回 `\\?\` verbatim 路径，
`cmd.exe` 不接受它。仓库里已有三处 `\\?\` 剥离补丁说明这坑真实存在。
（此条为代码推断，未在 Windows 实测；坚持 `.cmd` 方案必须先实测。）

副作用：`bundled_node` 会置 `isolated_environment = true`，更贴近生产，但**同时改变
macOS 行为**，已通过的 macOS 证据必须整体重跑。

### 两个此前没记录的发现

1. **Windows 侧残留进程检查等于没有**：`run_bm_08_acceptance.py:461-473` 整段被
   `if os.name != "nt"` 包住。macOS 有泄漏检查，Windows 一行都没有。
2. **沙箱预算硬编码可能在 Windows 真机上炸**：`lib.rs:518-528` 对 BM-08 的沙箱请求
   硬编码 `max_duration_seconds = 60, max_cpu_seconds = 60`，而
   `motion-render-sandbox-budget.v1.json` 的 CPU 上限公式是
   `maxDurationSeconds × cpuParallelismMaximum = 480`。BM-16 在 16 核 Windows 真机上
   正是栽在"CPU 秒按整棵进程树累加"这一类（见 `FIX-sandbox-cpu-budget.md`）。
   **BM-08 在 Windows 上很可能触发 `render_resource_exceeded`**，修法与 BM-16 一致：
   把预算从硬编码 60 改成按墙钟预算派生。

### 分档

| 档 | 项 |
| --- | --- |
| 小改（各 < 1 小时） | ffprobe 名称按契约取 `.exe` 后缀；ffmpeg 定位加 `--ffmpeg` 参数（PATH 上的 choco 版本串不匹配 VF-04 锁定格式）；`rmtree` 加重试而不是 `ignore_errors` 吞错 |
| 小到中 | 残留进程检查复用 `conftest.py` 的 `process_ids_matching()`——注意 conftest 已 import BM-08，反向 import 会循环，干净做法是把 helper 上提到 `scripts/` 下共享模块 |
| 中/结构性 | Worker 启动改 package 方案（动 `lib.rs` + 验收脚本，macOS 证据要重跑） |
| 待实测定档 | 浏览器延迟包装——Windows 上 staged Chromium 冷启动 + 90 帧的真实时长可能远超 Apple silicon 的 ~2 秒，取消竞争窗口也许天然成立、零改动 |

### 明确不需要改的（避免浪费时间）

pnpm 解析、AppData 路径、Tauri 二进制名（`wdio.video-studio.conf.ts` 已写死
`automation-tool-desktop.exe`）、Chromium 暂存、Rust 编码链、worker.mjs 的浏览器探测、
RenderJob 工作区权限（Windows 分支不校验属主/ACL，不撞提权限制）、预览推进
（用 `setTimeout` 而非 rAF，隐藏窗口可用）、Logo 上传（现有 spec 用 `browser.execute`
构造 `File`，根本不碰原生选择器）。

### SSH 会话跑不了的部分

**App 启动即失败**：`lib.rs` 无条件 `BrowserProfileStore::initialize`，
`browser_profiles_windows.rs` 的 `verify_private_acl_parts` 要求目录属主等于当前用户，
而 `apply_private_acl_with_flags` **只设 DACL、从不设 owner**。提权令牌下新建目录属主是
`BUILTIN\Administrators` ⇒ 校验失败 ⇒ panic。

BM-08 让情况更糟：它在开跑前和 finally 里各删一次私有 App 数据目录，所以"先用交互式会话
建好正确属主的目录"这种预置手段撑不过一轮。

两条出路：用**非提权令牌**驱动整条链（`schtasks /RL LIMITED`，不碰 sshd/防火墙/代理），
或改机器策略"管理员组成员创建对象的默认属主"——后者属机器级安全策略变更，需用户拍板。

### 仍需 Windows 实测才能定的六项

1. `.cmd` + `canonicalize` 产出的 `\\?\` 路径能否启动（推荐直接绕开）；
2. Windows staged Chromium 冷启动 + 90 帧的真实时长；
3. 隐藏 WebView2 是否真的解码并推进 `data:video/mp4;base64`；
4. `max_cpu_seconds = 60` 在 16 核真机上是否触发 `render_resource_exceeded`；
5. `rmtree` 对 435 MB staged Chromium 树的实际行为（共享冲突/只读属性）；
6. `/RL LIMITED` 任务计划下 WebView2 + msedgedriver 能否正常挂载。
