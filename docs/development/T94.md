# T94 视频剪辑「时间轴编辑」「预览」两个页签的实测

> 日期：2026-07-26
>
> 分支：`editing-tabs`
>
> 范围：`frontend/src/test-harness/main.tsx`、`frontend/e2e/video-editing-tabs.spec.ts`、
> `frontend/src/styles/global.css`（仅 `.video-editing-*` 段落的注释）

## 结论先写：这两个页签没有塌

T88 的推断是「按同一机制，它们很可能也塌成半宽」。**实测下来没有塌。**
1280×800 下两个页签都用满了它们拿到的每一个像素：

| 页签 | 内容列 | 外层卡片 | 卡片内容盒 | 卡片内第一层内容 | 占比 |
| --- | --- | --- | --- | --- | --- |
| 时间轴编辑 | 992px | **992px** | 942px | `.video-editing-timeline` **942px** | **100%** |
| 预览 | 992px | **992px** | 942px | `.video-editing-preview` **942px** | **100%** |

更深一层也满宽：`.video-editing-track` 942px、`.video-editing-clip` 942px、
`.video-editing-preview-clips` 942px。

对照 T88 修之前的「剪辑项目」（568/992 = 57.3%），这两个页签不是同一回事。

## 为什么没塌：T88 自己顺手修好了，然后写下了「没修」

两条结构性原因，都跟 T88 的推断不一样：

1. **这两个页签的最外层是 `Card`，不是 `Space`。** `Card` 渲染成块级 `div`，
   不需要谁告诉它就填满内容列。而「剪辑项目」「提交与任务」的最外层是
   `<Space className="video-editing-projects">`——`inline-flex`，按内容收缩。
   T88 找到的机制是对的，但它只对最外层是 `Space` 的那两个页签成立；
2. **卡片内的那层 `Space` 正好是 `.ant-card-body` 的直接子元素**，因此已经被
   T88 自己加的这条规则覆盖：

   ```css
   .video-editing-panel .ant-card-body > .ant-space { width: 100%; }
   ```

   T88 写这条时特意**按 panel 作用域、而不是逐个卡片点名**，注释里的理由是
   「这样下一个加进来的卡片不会成为被漏掉的那个」。这个防御性选择当场就生效了：
   它把当时还看不见的「时间轴编辑」和「预览」一起兜住了。
   T88 在同一个文件里写下「它们没被验证、故意不改」的时候，其实已经改好了。

**这条规则是承重的，不是冗余的。** 把它删掉重跑，两个页签立刻塌：

| 页签 | 有这条规则 | 删掉这条规则 |
| --- | --- | --- |
| `.video-editing-timeline` | 942px | **718px** |
| `.video-editing-preview` | 942px | **328px** |

所以 T88 的推断「它们会塌」在**反事实意义上是对的**——只是修复已经先一步到位了。

## 根因：UI Harness 为什么建不出剪辑项目

不是缺夹具数据，也不是需要先有成片，而是**一行接线漏了**。

`WorkbenchShell` 给每个 gateway 都准备了一个失败兜底默认值，其中：

```ts
const shellVideoEditingGateway: VideoEditingGateway = {
  async createProject() {
    throw new VideoEditingGatewayError("draft_storage_unavailable", true);
  },
  // ...
};
```

生产入口 `src/main.tsx` 一直传的是真实实现：

```ts
const videoEditingGateway = createLocalVideoEditingGateway(window.sessionStorage);
```

而 `src/test-harness/main.tsx` **从来没传过这个 prop**，于是 `WorkbenchShell` 落到
上面那个必抛的兜底上——`createProject` 永远失败，项目建不出来，
「时间轴编辑」和「预览」永远停在「请先创建或选择一个剪辑项目」。

关键点：`createLocalVideoEditingGateway` 只依赖浏览器的 `sessionStorage`，
**不需要 Tauri、不需要后端、不需要成片**。Harness 本来就跑得动它。
也就是说 Harness 长期比产品本身少一块能力，而且没有任何理由。

**怎么证实的**：不是读代码推断。把接线改好后测试转绿，再把 `main.tsx`
单独 `git checkout` 回去、其余改动原样保留，重跑——立刻回到红：

```
Error: expect(locator).toBeVisible() failed
Locator: getByText('已创建剪辑项目：页签宽度验收项目')
Expected: visible
Error: element(s) not found
```

一去一回，确认变绿的原因是这行接线，不是别的。

## 顺带查实的一件事：所有 Playwright 用例其实跑在 1280×720

`playwright.config.ts` 顶层写着 `viewport: { width: 1280, height: 800 }`，
但唯一的 project 里铺了 `use: { ...devices["Desktop Chrome"] }`，
**project 级 `use` 覆盖顶层**，该预设自带 1280×720。实测确认：

```
VIEWPORT: {"width":1280,"height":720}
INNER: 1280x720
```

这正是台账里 T96 记的那条。对本任务的结论**没有影响**——我量的全是宽度，
两种情况下视窗宽都是 1280。但既然本文写的是 1280×800，
就在**自己这份用例文件里** `test.use` 显式钉住 800，上面所有数字都是钉住之后重测的。
**没有动共享配置**：拉高视窗会同时放松其它每份用例的折叠线，那是 T96 的范围。

## 真实边界

- 本次全部证据来自 **UI Harness + Playwright**，按项目规则只能证明 React 业务交互与版式，
  **不能**证明真实 Tauri App、IPC、Sidecar 或云端剪辑链路；
- 剪辑草稿存的是 `sessionStorage`，云端剪辑 provider（VE-04+）未接入，
  「提交与任务」仍然必定失败——这是既有状态，本次没有改动；
- 因此本任务的性质是**版式实测 + 测试可达性修复**，不涉及外部副作用，
  无需受控平台账号验收。

## 留给你判断的两条（都只报数，没擅自改）

1. **片段编辑行用 718/942px，尾部空 224px。**
   `.video-editing-clip` 本身是满宽 942px 的，里面那层 `Space` 按内容收缩到 718px。
   它是一行控件（时长、素材、转场、上移/下移/删除），收缩对工具行来说是正常行为，
   同一页的轨道按钮行只有 226px 也没有问题。唯一实际影响是素材 UUID 输入框
   210px 显示不全（`6f1a2b3c-4d5e-4f60-8…`）。**这是版式取舍不是塌陷，没改。**
2. **轨道之间没有边框、底色、内边距。**
   实测三条轨道均为 `border=0px / bg=transparent / padding=0 / margin=0`，
   只靠 `Space size="middle"` 的 16px 间距和加粗标题分隔。
   三轨道实拍看下来可读（标题「画面轨道 1 / 音频轨道 2 / 字幕轨道 3」很显眼），
   但轨道多、片段多时会变平。T88 曾预测「轨道没有任何视觉分隔」——
   **字面属实，观感尚可**。加边框属于视觉设计增项，没有缺陷支撑，没改。
