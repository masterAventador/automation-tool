## 2. 分码一轮回本：真实失败码是 profile_identity_changed

分码后的 b5_13 重跑（2026-07-29 晚）三处警告齐报
`故障代码：profile_identity_changed`——不是存储、不是锁。四轮插桩没定位的
一步，其实是删除流程里的某道**目录身份检查**（unix 路径上有四处：布局重验、
锁获取时的目录身份、rename 后重开核对、删除后「原名不得复活」终检）。

嫌疑模型：紧急停止对执行器进程组发 SIGKILL 后即返回，若登录浏览器不在该
进程组（或其写入晚于删除），删除完成后原路径被写回 → 终检报身份变化。
与「标记复活」“254ms 快速失败”两条旧证据相容，但链路上 Playwright 全家
按理同组，模型有裂缝——不猜，已在 b5_13 失败路径加「幸存进程」插桩
（打印命令行含本次 Profile 根路径的存活进程），重跑判真伪中。

## 3. 侦查第二轮：三个假设三种判决（2026-07-29 深夜）

- **浏览器幸存说：证伪。** spec 失败瞬间命令行含 Profile 路径的进程为零；
- **Chromium 文件说：证伪。** 实验室复现测试
  `chromium_touched_profile_still_removes_cleanly`（内置 Chromium 以该
  Profile 起 2.5 秒、SIGKILL 整组、随后删除）——删除干净成功。该测试留档
  （`#[ignore]` 显式运行），永久守住这条假设；
- **轮询赛跑说：现存唯一模型，四种轮次形态全部吻合。** 四轮真实运行的形态
  漂移（spec 内红 identity_changed ×2、spec 绿但盘上残留墓碑 ×1、七警告 ×1）
  是竞态的指纹；残留物是年轻 Chromium profile 骨架（含未清收尾的 sqlite
  journal）；「最近检查」时间戳说明账号与平台页有活跃的会话检查在跑，而
  `current_douyin_profile()` 在标记缺失时会新建 Profile 并写回标记——登出
  删除与这条轮询路径赛跑，谁晚谁赢。

待验证：轮询的驱动源（页面轮询 → Rust → 执行器 recheck 是否拉起浏览器）、
登出流程有没有本地互斥（服务端已有 logout gate，本地似乎没有对应物）。
修复方向预判：登出期间挂本地互斥（暂停轮询/禁止 Profile 新建），与
服务端 gate 对齐。

## 4. 根因到手：删除成功之后有人立刻把目录建了回来（2026-07-30）

补上「首次运行没有日志」这个缺陷（见 §5）之后，b5_13 第一次交出真实时间线：

```
541159 profile.removal.started
541173 profile.removal.staged      ← 暂存改名成功
541234 profile.removal.deleted     ← 目录真的删掉了
541240 profile.removal.rejected    ← 6 毫秒后被拒
```

删除**成功了**。被拒的是删除后的终检——`remove_profile` 最后一步核对
「原名和暂存名都不得再出现」，而它发现原名又回来了，于是报
`identity_changed`。这与四轮观察到的一切吻合：残留物是**年轻的 Chromium
profile 骨架**（`Local State`、`Default`、未收尾的 `first_party_sets.db-journal`），
uuid 与被删的那个相同。

复活者不是 App：`open_child` 走 `openat` 不带 `O_CREAT`，目录不在就报
`profile_not_found`，App 侧没有任何路径会在原 id 上重建目录。**是
Chromium 自己**——`--user-data-dir` 指向的目录不存在时它会重建整棵树。
即：登出删除 Profile 时，用着这个 Profile 的浏览器还活着。

登出流程的顺序本来是对的（先 `emergency_stop` 再删），所以问题在**停止
的覆盖面**：`emergency_stop` 杀的是执行器进程组，而登录浏览器由执行器
经 Playwright 拉起，可能不在同一进程组，于是杀不到。终检 6 毫秒内就抓到
重建，说明那个 Chromium 当时仍在运行。

**产品每一层仍然都对**：删除是原子的、终检是必要的（它挡住的正是「删完
又被写回」这种情况）、报错也确实非用户可修。缺的是登出要等浏览器真的
死透——修复方向：登出前显式关闭登录会话浏览器并确认其进程树退出，
再执行删除；或让 `emergency_stop` 覆盖执行器拉起的浏览器进程树。
（本轮已顺带给登出路径的 emergency_stop 补上事件记录——它此前不记，
时间线里看不到停止发生在哪一刻。）

## 5. 第九个产品真缺陷：首次运行的 App 根本没有事件日志

查本任务的过程中撞出来的，且是「查了五轮看不见删除流程」的元凶：

- `run()` 在 setup 最开头初始化日志，而 App 私有数据目录此刻还不存在
  （它由稍后的 `prepare_data_directory` 建）；
- `create_private_directory` 只建自己那一层，父目录缺失即 `NotFound`；
- 于是首次运行的整份日志从未存在，后续每次 `record()` 全是空转，只在
  stderr 留一行「desktop fixed-event log unavailable」——h8_22 打包 App
  崩溃时 stderr 的第一行正是它，当时没往这个方向想。

RED：`the_fixed_event_log_survives_a_first_run_with_no_app_data_directory`
（空目录起步 → `NotFound`）；GREEN：递归创建，每层仍 0700。控制实验：
撤回修复即红。cargo lib 129 全绿。**留不下痕迹的失败是这个项目反复
遇到的那一类，而这里失效的恰是留痕本身。**
