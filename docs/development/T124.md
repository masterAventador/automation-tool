## 2. 两处缺陷的确切形状

| 位置 | 夹具造出什么 | 被测代码要什么 |
|---|---|---|
| `test_prepare_video_runtime.py` 的 `stamped_motion_worker` | 写死 `runtime/node`；三处断言（`test_the_worker_lands_where_the_rust_test_reads_it`、`test_installing_twice_replaces_rather_than_refusing`、`test_install_replaces_a_linked_resource_root_without_touching_its_target`）也断 `runtime/node` | `prepare_video_runtime.install()` 按 `required_for(host_platform())`，Windows 上是 `runtime/node.exe` |

两处都**没有放宽断言**。守的性质原样保留——产物必须落在契约声明的位置、名字必须对得上——只是「哪一种拼写」改为按平台派生。

## 3. 产物名有没有单一来源：有，而且这次直接用了它

链条是现成的，一路到底只有一份声明：

```
contracts/quality/release-package-resources.v1.json
        ↓  requiredFiles + windowsExecutables
release_assembly.VIDEO_RUNTIME_RESOURCES  （_VideoResource）
        ↓  required_for(platform)          ← 唯一的平台派生点
prepare_video_runtime.install():283
release_assembly.require_packaged_video_runtime():217
run_vf_06_acceptance.require_staged_video_runtime():144
```

生产侧三个消费者早就都在读它。**唯二没读的就是这两个夹具**，它们把 `platform` 写成了常量。所以本次不需要新建来源，也不该新建——新建一份就正好制造出这个仓库反复修的那种「同一个事实两份」。

动效 Worker 的 `runtime/gsap.min.js` 同理有单一来源：`contracts/quality/motion-video-worker-package.v1.json` 的 `packageLayout.authoringRuntimeAsset`，`build_motion_video_worker_candidate.py:205` 就是从这里读的。它不在 `requiredFiles` 里（那份契约管的是「不许缺」，这个资产由 Rust 用例证明），本次也改为从契约读，不再写字面量。

### 3.1 顺带查到、但**只登记不改**的三处

都属于「可派生事实的手抄副本」，正是 C10 那条线在清的东西（`30d1b5a` 就是这个题目），本次不动以免撞车：

| 位置 | 抄了什么 | 为什么不在本次改 |
|---|---|---|
| `test_prepare_video_runtime.py:45` `INSTALLED = ("motion-video-worker", "package")` | 契约的 `installedParts` | 是安装**位置**不是产物名，与本次的 Windows 红无关；形状上正是 C10 owns 的那类清单 |
| `build_motion_video_worker_candidate.py:198-199` | `"node.exe" if os.name == "nt" else "node"` | 契约的 `windowsExecutables` 已经表达了这条映射；但它是生产构建代码，改它会动 `motion-video-worker` 的缓存键（`MOTION_WORKER_INPUTS`），**每台机器都要重编一次 Worker**，代价与本任务范围不成比例 |
| `run_bm_02_acceptance.py:60` | 同上 | 同上一列的前半句；属验收驱动，C7/C9 正在这一片 |

另记一条事实层面的重复：POSIX 名 `runtime/node` 同时写在两份契约里——`release-package-resources.v1.json` 的 `requiredFiles` 与 `motion-video-worker-package.v1.json` 的 `packageLayout.runtimeExecutable`。**只有前者带 Windows 映射**。两者今天一致，靠的是 `run_bm_02_acceptance.py:45` 那条锁断言，不是靠派生。这条同样只登记。

### 3.2 「当前在哪个平台」没有单一来源——判断是不管

`prepare_video_runtime.host_platform()`（不支持的平台直接 raise）与 `run_vf_06_acceptance` 里的 `"windows" if sys.platform == "win32" else "macos"` 是两份写法。但这不是这两个文件的问题：全仓 `scripts/` 下这类判断有二十余处（`sys.platform` / `platform.system()` / `os.name` 三种写法混用）。

**判断：本次不统一。** 它是仓库级模式，统一属于独立任务；而且在本产品只支持的两个平台上，所有写法给出的答案逐一相同，不构成正确性风险。本次夹具取 `host_platform()`——它是既有的、有名字的、对不支持平台 fail-closed 的那一个，且 `prepare_video_runtime` 正是夹具在模仿其输出的脚本。

## 4. RED / GREEN（本机 macOS，真实输出）

## 7. 真实边界与失败矩阵

**真实边界。** 本任务修的是测试脚手架，不存在「正常用户路径验收」这一项——**不适用**，理由：这两个文件不是用户可操作功能，用户不会从 App 里点出它们。它们所守的东西（视频运行时资源必须装进包）的用户路径验收属于 T7，不在本次范围。

验收落在真实终态而非日志：真实解释器、真实文件系统、真实子进程、真实 `install()` / `stage_video_runtime()` 调用、真实 Windows 机器上的真实前后对照退出码。没有 Mock 冒充平台——唯一被搬动的是「当前在哪个平台」这一个事实，而被测代码的判断逻辑原样执行。

本次覆盖到的失败：

| 失败 | 表现 | 处理 |
|---|---|---|
| 夹具与被测代码对产物名不一致（Windows） | 3/9 + 整文件红，报文长得像缺资源 | 夹具改为按平台从契约派生 |
| 同上（macOS 方向） | 在 Windows 上跑 `macos` 分支时会红 | 同一条派生，双向都由新用例覆盖 |
| 夹具「两种拼写都造」以求稳过 | 会让分歧藏起来而不是解决 | 新用例断言暂存集合**恰好等于**契约集合，多造一个也红 |
| 新检查定义了却没登记，跑零次仍显示全绿 | 静默成功 | §6 的自守检查，且已实测抓到 |
| 断言写了却从不执行（集合断言挡住后半段） | 后半段等于没写 | §4 的两条变异探针，各自复现出 Windows 原文 |
| 循环内闭包不绑定循环变量 | 本次侥幸正确，换个写法就错 | ruff B023，改 `return_value=` |
| PowerShell 取码/编码坑 | rc 恒 0、输出乱码 | 哨兵值 + 绝对路径直调 + `iconv` |

未覆盖（如实记）：真实 Windows 出包、GUI 验收、winbox 其余门禁。
