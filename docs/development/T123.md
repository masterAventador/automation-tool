### 3.1 一个会把人带沟里去的陷阱：Git bash 满足守卫但没有编译器

`scripts/build_video_media_toolchain.sh:28` 的守卫是：

```bash
[[ "${MSYSTEM:-}" == "MINGW64" ]] || { echo "windows-x86_64 must be built in an MSYS2 MINGW64 shell" >&2; exit 1; }
```

**Git for Windows 的 bash 也把 `MSYSTEM` 设成 `MINGW64`**，所以它能大摇大摆走过这道
守卫，然后在 x264 的 `./configure` 里以 `No working C compiler found.` 倒下——Git bash
根本不带 gcc。

T116 §5.1 当时把 `C:\Program Files\Git\bin` 前置进 PATH 就是撞的这一条，得出的结论
"机器上装的是 MSVC，需要 MSYS2/MinGW"方向对但落点偏了：**MSYS2 一直都在，只是那次
PATH 指错了地方。**

守卫检查的是"我在哪种 shell 里"，而它真正要保证的是"我有没有 C 编译器"。改成也验一次
`command -v gcc` 能让下一个人少绕一圈，但 `build_video_media_toolchain.sh` 本身是
`MEDIA_TOOLCHAIN_INPUTS` 里的缓存键输入（`prepare_video_runtime.py:76`），动它会让
**每台机器**（含 macOS）的 media-toolchain 缓存全部失效、各自重编一次 ffmpeg。本次
任务的范围是"让 Windows 能构建"，不值得为此付这个代价，所以**只记录不修**。

## 6. 恢复步骤（下一个人照抄即可）

在 winbox 上，`F:\automation-tool` 目录下，**用普通 PowerShell**：

```powershell
$msys = 'F:\automation-tool\.local\vf04-msys2\msys64'
$comspec = $env:ComSpec              # 先存下来，见 §7.1
$env:MSYSTEM = 'MINGW64'
$env:PATH = "$msys\mingw64\bin;$msys\usr\bin;" + $env:PATH

& $comspec /c "uv run --project backend --locked python scripts\prepare_video_runtime.py --platform windows --only media-toolchain > C:\build.txt 2>&1"
$LASTEXITCODE                        # 要 0
```

三个都不能省：

- **`MSYSTEM=MINGW64`** —— `build_video_media_toolchain.sh:28` 的守卫要它；
- **`mingw64\bin` 在前** —— gcc / pkg-config 在这里；
- **`usr\bin` 必须排在 `C:\WINDOWS\system32` 前面** —— builder 在 bash 里把
  `/tmp/...` 这种 POSIX 路径交给 `curl` 和 `tar`。System32 自带的 `curl.exe` 和
  `tar.exe` 是原生 Windows 程序，看不懂这种路径，排在前面会直接把构建打挂。

`prepare_video_runtime.py:138` 是 `["bash", ...]`，走 PATH 解析，所以只能靠 PATH 指向
MSYS2 的 bash，没有别的入口。

**假如哪天 MSYS2 真的没了**，重装就是把 §2 那两条原样再跑一遍：用
`.local\msys2-base-x86_64-20260611.sfx.exe` 解压到 `.local\vf04-msys2\`，然后在
MSYS2 shell 里 `pacman -Syuu --noconfirm` 再
`pacman -S --needed --noconfirm curl diffutils make mingw-w64-x86_64-gcc
mingw-w64-x86_64-pkgconf mingw-w64-x86_64-zlib nasm tar xz python`。
**卸载就是删掉 `.local\vf04-msys2\` 整个目录**（1,171 MB），不需要动注册表或系统 PATH——
它从来没往那儿写过东西。

## 7. 三个会绊人的坑（都是本次实际踩到的）

### 7.1 把 MSYS2 放进 PATH 会让 PowerShell 的 `cmd` 失效，而且失败是静默的

`msys64\usr\bin\` 下有一个**无扩展名**的文件 `cmd`（225 字节），内容是

```bash
#!/usr/bin/env bash
"$COMSPEC" "$@"
```

PowerShell 解析 `cmd` 时会先命中它，然后报
`Program 'cmd' failed to run: The operation attempted is not supported`。

**真正危险的不是这条报错，是它后面那一行**：程序压根没启动，`$LASTEXITCODE`
**保持上一条命令的旧值**。本次第一轮就是这样拿到 `BUILD-RC=0` 的——**构建一秒都没跑，
退出码却是 0**。整轮耗时 0.13 秒，只有看时间戳才发现不对。

对策两条，都要做：

- 用 `& $env:ComSpec /c "..."`（绝对路径），不要写 `cmd /c`；
- 调用前把 `$global:LASTEXITCODE` 设成哨兵值（如 9999），这样"没跑"和"跑了返回 0"
  能区分开。

### 7.2 代理必须留着，但它会偶发 TLS 失败

winbox 上有 `all_proxy=socks5://127.0.0.1:10808`、`http_proxy`/`https_proxy=http://127.0.0.1:10808`。
T116 §4.3 里三条 pytest 失败是**因为**这几个变量，很容易顺手就想清掉它们——**在这里不能清**。
实测（`curl` 直取 `https://ffmpeg.org/releases/ffmpeg-8.1.2.tar.xz`）：

| 环境 | 结果 |
|---|---|
| 带代理变量 | **rc=0**，下载成功 |
| 清掉代理变量 | **rc=28**，40 秒超时 |

builder 要从 ffmpeg.org 和 code.videolan.org 拉源码，**这台机器没有代理就出不去网**。

但代理本身会抖：本次第一轮构建就死在
`curl: (35) TLS connect error: error:0A000126:SSL routines::unexpected eof while reading`。
builder 的 `curl --retry 3` 没能救回来（curl 默认不重试这类连接层错误）。**处理办法就是
重跑一次**——`ensure_cached` 失败时会把半成品和 stamp 一起删掉，重跑是干净的。

### 7.3 T121 的诊断修复确实在起作用

上面那条 `curl: (35)` 能被看见，正是因为 `1ab2892` 已经在检出上了。换成 `b8cd838`
之前的版本，同样的失败只会显示八行 curl 进度条。**先确认检出包含 `1ab2892` 再动手**，
否则任何构建失败都会变成一次瞎猜。
