## 任务

macOS/Windows 正式包使用唯一 Chromium 完成独立 Agent 与租约接管；覆盖 prompt injection、
DOM/截图差异、模型不兼容、断网、超时、并发租约、CDP 暴露、进程清理和零真实副作用。

## 为什么要有这个任务——BU-02..BU-06 已经各自测过了

BU-02..BU-06 每个任务测的是**自己那一个模块**。攻击者不按模块来：一个恶意页面同时打
工具面、域名白名单、脱敏器、确认门禁和租约，漏洞出在两者的接缝上。所以这里的每一条都
驱动**组合后的生产面**——发布链路真正使用的那一套 harness、tools、policy、redactor、
gate、lease 和模型选择器——并断言攻击**失败关闭**，而不是降级成一个更弱但仍在跑的运行。

## 两个真实发现（不是预期内的“跑通”）

### 1. 上游遥测在导入时就已决定，晚设环境变量没用

第一次跑确定性矩阵，测试还没开始断言，上游就打印了
`INFO [service] Using anonymized telemetry`。`harness_environment` 一直存在，但它当时只被
用来构造**子进程**的环境；本进程先导入了 `browser_use`，配置已经读完了。
`scripts/run_pb_05_acceptance.py` 恰好是对的（先 `os.environ.update(...)` 再导入），说明这
是个顺序约定而不是被强制的机制。矩阵现在在任何导入之前应用 harness 环境，并新增一条断言
覆盖"云凭据与代理被剥离而不是被覆盖"。

### 2. 我的第一次注入验证是假绿——扫描器没在扫我以为它在扫的东西

删掉 `sk-` 脱敏规则后重跑，两层**都还是绿的**。原因是 fixture 里那个 key 写成
`Authorization: Bearer sk-live-…`，先被 bearer 规则吃掉了，`sk-` 规则从头到尾没被这条用例
碰过。修的是 fixture 而不是断言：加了一处**裸露**的 key（`旧配置里的密钥 sk-live-…`），
只有 `sk-` 规则能覆盖它。再注入同一个洞：

| 层 | 注入 `sk-` 规则被删 | 结果 |
| --- | --- | --- |
| 确定性矩阵 | 是 | `AssertionError: 'sk-live-9f8e7d6c5b4a' unexpectedly found` |
| 真实浏览器验收 | 是 | `BU-07 acceptance failed: model-facing page text leaked: ['sk-live-9f8e7d6c5b4a']` |

恢复后两层都干净。**一个全绿的用例可能只是没在跑你以为它在跑的路径**，注入验证不能省，
而且注入之后要检查它是不是被另一条规则顺手挡了。

真实浏览器一侧还有一条内建的非空验证：探针先断言
`attack_reached_the_page`（注入文本确实出现在模型可见文本里），再断言脱敏结果无泄漏。
如果哪天 `get_state_as_text()` 不再返回正文，验收会因为"探针什么都没证明"而失败，
不会静默变成一次空跑的绿。

### 「无残留进程」这条断言在 Windows 上不是空转

它依赖 `running_pids()` 用 `wmic` 的定宽表格匹配完整可执行文件路径。如果 wmic 把长
命令行截断，这条断言会**假通过**。所以单独验了一次：从与真实暂存路径同形状的 110
字符深路径拉起进程，检测器能看见它（`detected_pids: [10244]`），杀掉后也能看见它消失
（`after_kill: []`）。这条断言是实的。

### Windows 上的环境障碍（不是产品缺陷）

uv 托管 Python 的目录 `cpython-3.12-windows-x86_64-none` 是指向真实版本目录的
Junction，SSH 会话的提权令牌触发 `ERROR_UNTRUSTED_MOUNT_POINT`（os error 448）拒绝穿越。
改 `pyvenv.cfg` 无效（uv 在 Windows 用 trampoline exe，目标路径编译进了 exe）；
`UV_PYTHON` 直指真实路径也无效（uv 会归一化回 Junction 路径）。最终把真实解释器复制到
无 Junction 的路径再设 `UV_PYTHON` + `UV_PROJECT_ENVIRONMENT` 才通过，`--locked` 装了
102 个包。**没有改动任何脚本逻辑或断言**，原有的 `tools\browser-use-contract\.venv` 未动。

## 第三个真实发现：Windows 主机上恰恰没走到 Windows 路径分支

Windows 验收顺带暴露了一个覆盖缺口：恶意 fixture 里的私有路径样本**只有 POSIX 形态**
（`/Users/operator/.local/secrets`），而 `browser_use_safety.py` 明明有 Windows 路径规则。
也就是说，最该验证这条规则的平台，反而从来没有触发过它。

补法与前两次一致——改 fixture 而不是改断言，然后注入验证：

| 注入 | 确定性矩阵 |
| --- | --- |
| 只删单反斜杠那条 Windows 规则 | **仍绿** → 证明它是冗余的 |
| 两条 Windows 规则都删 | `AssertionError: 'C:\Users\operator\.local\secrets' unexpectedly found` |

于是删掉冗余的那条（`[A-Za-z]:\\Users\\…` 已被 `[A-Za-z]:\\\\?Users\\\\?…` 覆盖，
后者同时匹配单反斜杠和经过一轮 JSON/日志转义的双反斜杠形态），并在保留的那条上写清理由。
两处 fixture（确定性矩阵与真实浏览器探针）都补了裸露的 Windows 路径样本。

## 真实边界

1. **macOS arm64 已从正式 `.app` 包内跑三轮；Windows 正式安装树尚未跑**。Windows
   x86_64 当前证据仍是锁定归档暂存后的真实 Chromium，不冒充安装后的包内路径。
2. **macOS arm64 与 Windows x86_64 的锁定浏览器都跑过**（见「双平台证据」）；
   macOS x86_64 没有该架构机器，仍未跑。
3. **没有真实模型参与**。攻击矩阵证明的是"即使模型被说服，它也没有能力执行"——工具不存在、
   域名被拒、令牌铸不出来。它不证明"模型不会被说服"，那不是能靠代码保证的性质。
4. **页面内 JS 不在本产品的管辖范围**。恶意页面自己的脚本会照常运行（任何浏览器都如此）；
   本任务控制的是 agent 的能力面，不是页面的能力面。
5. **三连跑只在 macOS 正式包完成**。Windows 暂存浏览器仍只有单次记录，不能用 macOS
   稳定性替代 Windows 进程枚举与清理差异。
