## 为什么要有这个任务——BU-02..BU-06 已经各自测过了

BU-02..BU-06 每个任务测的是**自己那一个模块**。攻击者不按模块来：一个恶意页面同时打
工具面、域名白名单、脱敏器、确认门禁和租约，漏洞出在两者的接缝上。所以这里的每一条都
驱动**组合后的生产面**——发布链路真正使用的那一套 harness、tools、policy、redactor、
gate、lease 和模型选择器——并断言攻击**失败关闭**，而不是降级成一个更弱但仍在跑的运行。

## 两个真实发现（不是预期内的“跑通”）

### 1. 上游遥测在导入时就已决定，晚设环境变量没用

第一次跑确定性矩阵，测试还没开始断言，上游就打印了
`INFO [service] Using anonymized telemetry`。`harness_environment` 一直存在，但它当时只被
用来构造**子进程**的环境；本进程先导入了 `browser_use`，配置已经读完了。
`scripts/run_pb_05_acceptance.py` 恰好是对的（先 `os.environ.update(...)` 再导入），说明这
是个顺序约定而不是被强制的机制。矩阵现在在任何导入之前应用 harness 环境，并新增一条断言
覆盖"云凭据与代理被剥离而不是被覆盖"。

### 2. 我的第一次注入验证是假绿——扫描器没在扫我以为它在扫的东西

删掉 `sk-` 脱敏规则后重跑，两层**都还是绿的**。原因是 fixture 里那个 key 写成
`Authorization: Bearer sk-live-…`，先被 bearer 规则吃掉了，`sk-` 规则从头到尾没被这条用例
碰过。修的是 fixture 而不是断言：加了一处**裸露**的 key（`旧配置里的密钥 sk-live-…`），
只有 `sk-` 规则能覆盖它。再注入同一个洞：

| 层 | 注入 `sk-` 规则被删 | 结果 |
| --- | --- | --- |
| 确定性矩阵 | 是 | `AssertionError: 'sk-live-9f8e7d6c5b4a' unexpectedly found` |
| 真实浏览器验收 | 是 | `BU-07 acceptance failed: model-facing page text leaked: ['sk-live-9f8e7d6c5b4a']` |

恢复后两层都干净。**一个全绿的用例可能只是没在跑你以为它在跑的路径**，注入验证不能省，
而且注入之后要检查它是不是被另一条规则顺手挡了。

真实浏览器一侧还有一条内建的非空验证：探针先断言
`attack_reached_the_page`（注入文本确实出现在模型可见文本里），再断言脱敏结果无泄漏。
如果哪天 `get_state_as_text()` 不再返回正文，验收会因为"探针什么都没证明"而失败，
不会静默变成一次空跑的绿。

## 正常用户路径验收

不适用于用户操作入口：BU-07 是安全回归门禁，没有对应的用户页面。用户可见的 Browser Use
入口在 PB-05/PB-07 的发布链路里，正常用户路径验收归那两个任务。本任务的"真实"体现在

## 真实边界

1. **不是从正式安装包里跑的**。矩阵跑在用生产暂存构建器暂存出来的 Chromium 上，不是
   EB-16 产出的签名/公证包内部。"正式包使用唯一 Chromium"这半句还没有证据。
2. **只在 macOS arm64 跑过**。Windows x86_64 一侧同样的矩阵没跑，macOS x86_64 也没有。
3. **没有真实模型参与**。攻击矩阵证明的是"即使模型被说服，它也没有能力执行"——工具不存在、
   域名被拒、令牌铸不出来。它不证明"模型不会被说服"，那不是能靠代码保证的性质。
4. **页面内 JS 不在本产品的管辖范围**。恶意页面自己的脚本会照常运行（任何浏览器都如此）；
   本任务控制的是 agent 的能力面，不是页面的能力面。
5. `scripts/run_bu_02_acceptance.py` 里 macos-arm64 的默认归档路径指向仓库外的
   `ROOT.parent.parent/.local/...`，在本机不存在，重跑 BU-02 验收会直接失败。属于 BU-02 的
   遗留缺陷，本任务没有顺手改（它需要自己的 RED），登记在此。

超时三条路径都走 `finally`）。注入验证改动的 `browser_use_safety.py` 已按备份恢复，
`git status` 复核只剩本任务的预期改动。未新增任何常驻服务。
