# 记录：7739540 夹带了未验收的在途文件

> 日期：2026-07-26
>
> 类型：流程错误记录（不是功能变更）

## 发生了什么

提交 `7739540 feat(pb-08): 发布链路跑在正式安装包内的那一个 Chromium 上` 时用了
`git add -A`，把 Windows 队列子代理**当时仍在运行、尚未跑完验证**的两个文件一起提交了：

| 文件 | 内容 | 当时状态 |
| --- | --- | --- |
| `scripts/run_eb_16_windows_acceptance.py` | 新增 625 行，EB-16 的 Windows NSIS 正式包验收 | 正在用它构建，Rust release 编译未完成 |
| `scripts/run_p9_04_acceptance.py` | 改 17 行，`install_root` 参数化以便 EB-16 Windows 复用 | 同上 |

该提交的说明里完全没有提到这两个文件。

## 为什么是错的

1. **未经验收的代码进了 main**。当时 Windows 包还没构建出来，这两个文件的正确性没有
   任何证据；
2. **提交记录不诚实**。commit message 只讲了 PB-08，读历史的人不会知道里面还有别的东西；
3. 违反项目规则「每个完成的 `[Tn]` 应形成独立、可回滚提交，不夹带无关改动」。

## 为什么没有回滚

子代理当时仍在用这两个文件在 Windows 上跑构建，撤掉会直接打断它。已推送的历史也不做
改写。所以选择保留文件、把错误如实记进历史，并在子代理交付后补齐它们的验收证据与台账。

## 补救（2026-07-26 已完成）

子代理最终跑完，Windows NSIS 正式包构建成功并通过全部包内容门禁。两个文件的验收结果已写进
`docs/development/EB-16.md` 的「Windows x86_64 正式包」小节，包括：包内唯一一套 Chromium
的独立走查、EB-17 两条判据在 Windows 包上的结果、装配顺序（装入 → 逐文件核验 → 封章 →
发布关口 → 才让 bundler 复制）、安装/卸载/残留，以及 Windows 侧与 macOS 不对等的四项缺口。

`run_p9_04_acceptance.py` 那 17 行的实际内容也核实过：把 `install_root()` 与
`windows_registry_installations()` 的 `PRODUCT_NAME` 字面量参数化，默认值保持原值、
参数设为 keyword-only，P9-04 内部 6 个调用点全部不传参，行为逐字不变。属于"改造现有的而不是
新建第二份"的正确做法，约 70 行注册表遍历因此被复用而不是复制。

所以这两个文件留在 main 上是合适的——但那是**事后**确认的，提交当时并不知道。

## 教训

不要用 `git add -A`。有并行子代理在同一个工作树里写文件时，只能逐个文件 `git add`。
