## 失败矩阵

| 场景 | 门禁结果 |
| --- | --- |
| npm command 精确执行驱动 | 派生 `frontend/package.json#<script>` owner |
| Python subprocess 真实传入驱动 | 派生 `python-subprocess:<path>` owner |
| 测试只 `read_text/readFile/import` | 只标 `source-shape-only`，不算 owner |
| 注释、错误提示或普通文本提到驱动 | 只标 `non-executing-reference`，不算读取或 owner |
| 新增驱动但未接执行者/阻塞结论 | 失败 |
| blocker 没有原因、条件或资源 | 失败 |
| blocker 重复登记或仍登记已删除驱动 | 失败 |
| 驱动已有真实 owner 又登记 blocker | 失败 |
| 子进程返回 0 但实际检查为 0 | 本门禁只证明“归属/启动路径”，绝不把它写成“验收通过”；真实运行仍由驱动自身的可数断言负责 |
| 云凭据、真实账号、签名包、Windows GUI、实体 Profile | 显式 profile 阻塞，不静默跳过、不在普通门禁自动消费 |

## 正常用户路径验收

本任务修的是验收基础设施，不是产品 UI。正常维护路径为：

1. 开发者新增或改名一个验收驱动；
2. `run_script_tests.py` 派生发现本测试；
3. 本门禁从 package 命令、Python subprocess 和 blocker registry 重新生成全量结论；
4. 有执行者的驱动显示执行入口；暂时不能自动执行的驱动显示操作者、前置条件和资源；
5. 只有源码文本断言的读者被清楚标成“源码形状”，维护者不会把绿灯误读成真实验收。

`run_vf_01_acceptance.py` 因此不再是全仓不可见孤儿：它明确归入
`manual_deterministic_project_gate`，只有操作者或任务级门禁显式选择且自身 preflight
通过时才运行。

## 真实边界

- 本任务没有串行启动 124 条验收，也没有把“有 owner”声称为“验收已通过”。
- 没有访问云凭据、真实平台账号、用户默认 Profile、签名分发材料或付费 API。
- 没有启动 Docker、Tauri App、浏览器、Executor 或外部服务。
- blocker profile 给出的是执行归属和资源边界；每个驱动的业务成功仍以该驱动自己的真实断言、
  输出计数和清理为准。
- 源码读者数来自当前受控测试目录的静态扫描；文档/README 提及不算执行者，也不计入这个读者
  指标。

## 清理

测试夹具全部使用 `TemporaryDirectory`，结束后自动删除。仓库级审计只读源码和 JSON，
没有创建缓存、构建产物、端口、进程、容器、网络或卷。

## 遗留项

- 85 条 blocker 不是“通过”，也不是永远豁免；具备稳定机器资源后，应把对应驱动接到真实
  package/subprocess owner，再从 registry 删除。
- 真实运行的“零场景/零检查”判据属于每个驱动的输出合同。若后续要做跨驱动批量实跑，应单独
  建立可数结果协议，不能用本归属门禁的退出 0 替代。
- blocker 中的云/实体机/签名条件不会被普通提交门禁自动满足；设备或发布责任人仍须按任务证据
  保存真实运行结果。
