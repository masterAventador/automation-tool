## 二、真正修掉的六处

判据统一为：**启动路径上任何一个「这份持久化文件读不懂」都不允许让 App 起不来。** 要么迁移，要么退回一个安全的已知状态，并留下可观察痕迹。

| # | 位置（改动前） | 触发场景 | 改动后 |
| --- | --- | --- | --- |
| 1 | `executor_platform.rs:366` | 诊断设置版本未知（新版写、回滚后读） | 退回默认 `false` + 重写当前版本文件 + 日志 |
| 2 | `executor_platform.rs:352-353` | 诊断设置 JSON 损坏 / 多字段 | 同上 |
| 3 | `executor_platform.rs:336-343` | 待办紧急停止记录版本未知 / 损坏 | 丢弃记录 + 删文件 + 日志 |
| 4 | `app_update_policy.rs:296` | 策略文档 schema 未知（回滚） | 用当前安装版本重建全新文档 + 日志 |
| 5 | `app_update_policy.rs:284-288` | 策略文档不是文档 / 自身不变量已破 | 同上 |
| 6 | `app_update_cache.rs:478-479, 488-489` | 缓存 manifest 读不懂（新版加字段后回滚） | 当成「没有缓存」丢弃 + 日志 |

同一次改动里顺带收掉的两个同函数内的启动 abort（都在 `validate_disk_state`，对象都是可丢弃的下载缓存）：

- 缓存文件权限过宽（Time Machine / 迁移助理还原的典型结果）→ 删除而不是 abort；
- 缓存路径上是软链或非普通文件 → **unlink 而不是 abort**。unlink 只摘链接不碰目标，比 abort 更彻底：abort 会把链接和一个打不开的 App 一起留给用户。

### 明确不改的两处

- `download()` 运行期（非启动期）遇到软链仍然硬失败。那只是一次下载失败并上报，不会让 App 起不来，测试 `cache_rejects_symlinked_files_and_never_reflects_private_paths` 继续锁着；
- 策略文档写盘失败仍然致命。因为**全新安装本来就必须写一次这个文件**，重置写不进去和全新装写不进去是同一件事，不是版本/格式问题。诊断设置相反：没有文件也能启动，所以它的重写是 best-effort，写不进去不影响启动。

## 四、「逐字节相同」那道校验本来想防什么，用什么替代

先说事实：**这道校验不是我删的，`ee5ecbf` 已经把它从 `return Err` 改成 `needs_save = true`。** 我做的是判断这个改法站不站得住，结论是站得住，理由如下。

它想防的是：文件在 `deny_unknown_fields` 解析和 `validate` 之后**仍然不是本构建序列化器会写出来的那份字节**——键序不同、有空白、数字写法不同。配合 `deny_unknown_fields`，这是一条「规范形式」规则，意图是让存量策略文件对「解析得过、校验得过的篡改」也保持可辨识。

被它保护的东西是有价值的：这份文档里的 `minimum_version` 是「低于此版本一律判为过期」的地板，`decision` 里的 `SkipVersion` 会压掉更新提示。把地板抬到 `99.0.0`，机器就被静默钉死在当前版本上；把安全版本标成 skip，提示就没了。

但**这道校验挡不住上面任何一条**。文件在 App 私有目录（0700/0600）里，能写这个文件的人同样能把它写成规范形式——`serde_json` 的输出是确定的、字段序由结构体决定、无空白，照抄一份毫无难度。所以它只挡住了「顺手用编辑器格式化过」的改动，挡不住任何刻意的改动：**是减速带，不是边界**。代价却是实打实的——序列化库升级、字段增删、`rename_all` 调整，任何一样都会让所有存量文件不匹配。用一条挡不住对手的规则去换「第一次发版打死所有老机器」，不划算。

真正在守的是这些，而且是每次读、每次写都在守：

- `validate_schema`（`app_update_policy.rs:198-228`）：schema 版本、通道字符集、`revision != 0`、semver 规范形式、`highest_observed > minimum`、Forced 与 decision 互斥、`decision.version == observed.version`；
- `observe_release`（`:347-401`）：**每次观察都从 feed 重新推导 `StoredReleaseIdentity` 并比对**，磁盘上那份不作数，对不上直接 `release_mutation`；
- 包体本身：`read_verified_package`（`app_update_cache.rs:213-244`）在安装前重算 sha256 并做 minisign 验签，磁盘上的 manifest 说了不算。

所以这次没有「放宽校验来消灭 abort」，而是把一条不成立的规则从「拒绝」降级为「重写成我们自己的形式」。**并且补了它原本缺的那一半：现在重写会记一条日志。** 原来的改法有个真实副作用——把一份被改过的文件悄悄洗成规范形式，痕迹就没了。这正是本项目反复吃亏的「静默成功」，所以现在它会说话（见下节）。

一处**没有被任何东西守住、这次也没修**的残留：被抬高的 `minimum_version` 无法与「用户从更高版本回滚过」区分——两者在磁盘上长得一模一样，而回滚是合法场景。逐字节校验从来也没能防住它。已如实登记，不算本任务修掉。

用 T69 的有界固定事件桌面日志（`app_logging.rs`，只收闭集枚举，不接受任何字符串/错误内容），新增六个事件：

| 事件字符串 | 含义 |
| --- | --- |
| `app_update.policy_document.migrated` | 策略文档被迁移/规范化/换通道重置后重写 |
| `app_update.policy_document.replaced` | 策略文档读不懂，已按当前安装版本重建 |

| `executor.task_emergency_stop_record.dropped` | 待办紧急停止记录读不懂，已丢弃 |

日志落在 `<app_data>/logs/desktop-<day>-<pid>.log`，单文件 1 MiB、单进程单日 2 轮转、最多 8 个文件、保留 7 天，`0700/0600`。

用户侧看到的：App 正常打开。丢的东西按类型是——被 skip 过的更新会再问一次（安全方向）、成功截图开关回到关（更保守方向）、缓存的更新包要重下一次、待办的紧急停止需要在工作台重新点一次。**没有任何一种是「打不开」。**

## 七、真实边界（`🔍 待验收`）

**这条链路在当前包里是死的**：`app_updates.rs` 的 feed URL 用 `.invalid` 保留域，永远不解析，所以「真的升级一次并在中途强退」在本包上验不了。本次全部证据都是 `cargo test` 层的单元与集成测试，**不冒充升级验收**。

要做真验收，需要同时具备：

1. 一个可解析的隔离 feed URL（自建 HTTP 服务即可，不需要真发布通道），以及与之匹配的 minisign 私钥签名的测试包；
2. 一个能起两次的正式测试版 Tauri App，第一次跑到 `atomic_replace` 与 `save_cache_manifest` 之间强杀（`SIGKILL`，不能是可捕获信号），第二次正常启动；
3. 版本/格式那半边不需要真 feed：只要把上一版 App 装一次、写出持久化文件，再装当前版本启动一次即可；**这半边可以在 T22（自动更新在可发布包里从未配置）完成后立刻做**。

在这些条件具备之前，本任务最多标 `🔍 待验收`。
