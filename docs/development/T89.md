# T89 「更新未启用」不再冒充失败，协调器真坏了也不再冒充「未启用」

- 日期：2026-07-26
- 归属：并行线（worktree `wt/update-state`，分支 `update-state`）
- 提交：`update-state` 分支上的单一提交（合并后以主线 hash 为准）

## 问题

`get_app_update_state` 原来是这么写的：

```rust
coordinator
    .as_ref()
    .and_then(|coordinator| coordinator.state().ok())
    .unwrap_or(UpdateState::Failed {
        stage: Configuration, code: ConfigurationInvalid, retryable: false,
    })
```

`and_then(...ok())` 把两件完全不同的事合并成了同一个结果：

1. **协调器压根不存在** —— 发布构建显式关掉更新（`build.rs:96` 允许 `AUTOMATION_TOOL_UPDATE_DISABLED=1` 且不提供 endpoint/公钥，客户 Demo 包正是这样构建的）。这是**受支持的正常配置**，什么都没坏；
2. **`coordinator.state()` 返回 `Err`** —— 唯一来源是状态互斥锁中毒（`app_update_coordinator.rs:160` 只有 `.lock()` 一处失败源），也就是持锁线程 panic 过，更新子系统内部**真的坏了**。

今晚先修的是第一条的症状：界面挂载即轮询，用户什么都没点就看到红色失败文案，于是前端按错误码把 `configuration_invalid` 降为中性文案「此版本未启用自动更新」（提交 `ff9f660`）。这留下两个反向的谎言：

- **中毒时**界面会说「此版本未启用自动更新」——更新明明启用了，只是坏了；
- **配置真的坏了时**（`UpdateRuntimeConfiguration::load()` 拒绝 endpoint、`UpdatePolicyErrorCode::ConfigurationInvalid`）也走同一个码，同样被降级成中性文案。这是 `ff9f660` 引入的、当时没被点名的第二处降级。

## 方案与理由

**选了「新增状态」而不是「新增错误码」，也没有给中毒那条路发明新码。**

**「未启用」建成独立状态 `UpdateState::Disabled`，不放进 `Failed`：**
`Failed` 带 `stage` 和 `retryable`，对一个受支持的正常配置这两个字段都无意义——没有阶段、没有重试可言。更要紧的是结构性理由：前端的不变式应当是「`failed` 就是出事了，默认红色」。在 `failed` **内部**挖中性豁免，正是这次事故的成因——它顺手把真实的 `configuration_invalid` 一起降级了。把「未启用」搬到 `failed` 之外，这个不变式就恢复了，`configuration_invalid` 也随之回到红色。

**中毒那条路复用已有的 `Storage / StorageUnavailable`，不新增第七个码：**
写入路径 `set_state()` 遇到同一种故障（锁中毒）**本来就报** `Failed { stage: Storage, code: StorageUnavailable, retryable: false }`。读取路径报同一个结论，读写两侧对同一次故障说同一句话；发明一个只有读路径用的新码反而会让两侧对同一个故障产生分歧。语义上 `Storage` 在这里读作「存放状态的地方用不了」，与 `set_state` 已确立的读法一致。用户看到的是红色的「更新当前不可用」（走 `default:` 兜底）。

为避免这个常量在两处各写一遍漂移，抽成 `STATE_STORE_UNAVAILABLE` 单点定义，读写两条路都引用它。

**互斥锁中毒是真造出来的，不是模拟的。** 测试起一个线程持锁 panic，先断言 `panicked.is_err()` 与 `state.lock().is_err()` 确认锁真的中毒了，再断言快照结果。需要说明的是：**协调器自己那把锁无法从任何公开路径中毒**——`set_state`/`state` 的临界区只有一次 clone 与赋值，`backend.check()`、`installation.install()`、下载进度回调都在锁外调用，没有任何用户代码能在持锁期间 panic。所以测试真正中毒的是一把等价的 `Mutex<UpdateState>`，协调器则通过 `observed_state()` 一行委托到同一个 `state_snapshot()`。这是本代码结构下能拿到的最真实覆盖；换句话说，`state()` 的 `Err` 分支在实践中是潜在缺陷而非现行缺陷，但它一旦发生就会说谎，所以照样修。

## 中毒那条路现在显示什么

红色。`storage_unavailable` 不在 `failurePresentation` 的具名分支里，走 `default:`，`retryable: false` → 文案「更新当前不可用」、`color: "red"`。`AppUpdateCenter.test.tsx` 里 `keeps an unreadable update state loudly visible instead of calling updates switched off` 断言了红色 class 且页面上不出现「此版本未启用自动更新」。

## 有没有真实失败被降级

**没有，反而恢复了一个。** 逐条核对六个失败码在本次改动后的呈现：

| 码 | 改前 | 改后 |
|---|---|---|
| `configuration_invalid` | 中性「此版本未启用自动更新」← **真失败被降级** | 红色「更新当前不可用」 |
| `storage_unavailable`（含锁中毒） | 中性（经由 `configuration_invalid` 合流） | 红色「更新当前不可用」 |
| `transport_unavailable` | gold「暂时无法连接更新服务器，可稍后重试」 | 不变 |
| `manifest_rejected` / `signature_rejected` / `installation_failed` | 红色 | 不变 |

`default:` 兜底红色保持原样，未来新增的失败码默认仍是红色。唯一变成中性的是新状态 `disabled`，它不是失败。

## 失败矩阵

| 情况 | 结果 |
|---|---|
| 构建显式关闭更新（协调器为 `None`） | `disabled`，中性文案，界面不报错 |
| 更新已配置但配置非法（endpoint 被拒 / 策略记录损坏） | `failed / configuration / configuration_invalid`，红色 |
| 状态互斥锁中毒（读路径） | `failed / storage / storage_unavailable`，红色，不可重试 |
| 状态互斥锁中毒（写路径 `set_state`） | 同上，读写两侧一致（共用 `STATE_STORE_UNAVAILABLE`） |
| 前端收到未知 `state` | Zod 判别联合 `.strict()` 拒绝 → 网关抛错 → 红色「暂时无法读取或操作 App 更新」 |
| `disabled` 带多余字段 | Zod `.strict()` 拒绝（用例已覆盖） |
| 关闭更新时用户点「检查更新」 | `check_app_update_now` 同样返回 `disabled`，与轮询结果一致 |

## 真实边界与待验收

**状态：`🔍 待验收`。** 缺的是真实 App 纵向证据，两条各自缺一块：

1. **`disabled` 路径**：正式包里更新本来就是关的，所以这条**可以**在真实 App 上验——打开演示包 →「设置与诊断」→「App 更新」应显示中性标签「此版本未启用自动更新」，且不出现红色告警。本轮**没有构建 Tauri 包跑这一步**，只有 Rust 单测（命令层函数）+ Vitest（组件）+ 源码级跨端契约。风险点很具体：如果原生返回的 `{"state":"disabled"}` 与前端 Zod 联合对不上，界面会弹红色的「暂时无法读取或操作 App 更新」。两侧都改了、也都有测试，新增的跨端契约用例还会挡住单边漂移，但**这不等于在真 App 里跑过**。
2. **中毒路径**：在演示机上验不了，因为正式包更新是关的（协调器根本不存在），而且如前所述协调器那把锁没有可达的中毒路径。要有真实证据只能靠故障注入构建，这会引入测试专用产品分支，违反单一构建路径规范，**因此不做**。替代验证方式就是上面那条真实中毒的单元测试 + 一行委托。

补验收依赖：下一次构建桌面包（或跑 `update-ui` 系的 WebdriverIO 场景）时，顺带确认设置页的更新标签为中性且无红色告警。
