# T91b — 渲染阶段失败且用户不在这一页时仍然静默

> 日期：2026-07-27
> 分支：`render-visibility`
> 状态：**🔍 待验收**（组件层 + 真实用户路径 Playwright 无头全绿；正式签名包上的目视确认未做，缺口见第八节）

## 一、这个洞是 T91 自己登记的

`docs/development/T91.md` 第六节原文登记：

> **已知仍未覆盖：渲染阶段失败且用户不在这一页。**
> `refresh()`（每 2 秒轮询 `gateway.motionJobs()`）只在 `VideoStudio` 挂载时跑，外壳一切页就把它卸载了。
> 所以：提交成功 → store 记的是 info 消息「已提交…本机渲染开始了」→ attention 是 `running`（此刻属实）
> → 用户切走 → 渲染失败 → **没有任何东西去查，标记仍是蓝点「正在进行中」**。

它给的不修理由是权衡而不是遗忘：改这个要动共享外壳，而当时四条线在并行改仓库。并行压力已解除。

T91 把**结果**搬出了组件（`motion-run-store.ts`），但**去查结果的那个动作**还留在组件里。
这一条搬的是后者。

## 二、轮询放在哪里，代价是什么

**放在共享外壳 `WorkbenchShell`，作为一个独立的监视器 `motion-run-watch.ts`，
而不是把 `VideoStudio` 那条 2 秒轮询整个搬上去。**

### 为什么不是整条搬上去

`VideoStudio.refresh()` 同时喂着任务卡、进度条、成片列表和取消按钮——那是**页面数据**。
把它搬进外壳意味着外壳持有页面数据、`VideoStudio` 改成受控组件、它的 props 全变；
而 `VideoStudio` 在单测和 Harness 里都是独立挂载的。改动面大得多，且和 T90b 正在改的那一片挨得更近。

监视器只回答一个问题：**这条本会话启动的片子，是不是还欠一个结果。** 它只读 `motionJobs()`，
只写 store，不碰任何页面数据。本次 `VideoStudio.tsx` **一行未改**。

### 代价，逐条讲清楚

| 代价 | 实际情况 |
|---|---|
| 「多一个常驻定时器」 | **它不常驻。** 定时器由 `motionRunNeedsWatch(state)` 门控——这是一个从 store 算出来的事实。本会话没提交过东西，外壳一个定时器都不建、`motionJobs()` 一次都不调（有用例守着：`asks nothing at all when this session has no film outstanding`）。它随渲染开始而起，随**被看着的任务全部到达终态**而自己停，不是等用户回到那一页才停（用例：`stops asking once the film it was watching has ended`） |
| 「多一份状态」 | store 多两样：`OwnMotionJob.ended`（这条任务是否已被观察到终态）和 `tracking: "ok" \| "lost"`（现在还看不看得见）。两者都是纯数据，`motionRunNeedsWatch` 和 `motionRunAttention` 都是纯函数，可以脱离 React 测 |
| 「切页时的清理更容易漏」 | 这是真正的风险，所以清理有**两道**：`clearInterval` 管定时器，`stopped` 旗子管**已经在路上的那次读**——它可能在外壳拆掉之后才 settle，然后把一个过期答案写进 store。这道旗子有专门用例，并做过变异验证（第四节） |
| 页面开着时两个轮询并存 | 是的，故意的。让监视器「页面挂载时就让位」等于让它的正确性重新取决于哪一页挂着——**而那正是一开始就坏掉的性质**。页面 2 秒喂的是有人盯着的进度条，监视器 5 秒喂的是没人盯着的角标，多出来的开销是一次本来就在发生的读的一小部分 |

### 5 秒这个间隔怎么来的

这里**完全没有正确性压力**：终态任务保持终态，慢一点的心跳永远不会漏掉结果，只会晚一点知道。
唯一的压力是「侧边栏最多允许说多久已经不成立的话」，5 秒远小于一个人切页再看一眼的时间。
实测渲染时长（12 秒成片约 10 秒）参与了这个判断，但**没有被写成任何阈值**——代码里没有任何地方
拿实测数字做比较。

## 六、改了什么

1. **新增 `frontend/src/features/video-studio/motion-run-watch.ts`** — `useMotionRunWatch(gateway)`。
   门控在 `motionRunNeedsWatch`；每次读成功后逐个比对本会话启动的任务：`failed` 写错误消息并标记
   已结束，`succeeded`/`cancelled` 只标记已结束（**不是 forget**——成片还欠页面上那次「去看成片」）。
2. **`motion-run-store.ts`** — `OwnMotionJob.ended`、`tracking: "ok" | "lost"`、
   `markMotionJobEnded`、`reportMotionRunTracking`、纯函数 `motionRunNeedsWatch`；
   `MotionRunAttention` 增加第四种 `"unknown"`。
3. **`WorkbenchShell.tsx`** — 调用 `useMotionRunWatch`；三种标记收敛成一张 `VIDEO_STUDIO_MARKS`
   查表（原来是 `failed ? ... : ...` 的二选一，表达不了第三种）。新增 `unknown` 标记：红字角标「未知」，
   `title` 为「读不到视频制作进度，去看看」。
4. **`frontend/src/test-harness/video-studio.ts`（新增）+ `main.tsx` 一处接线** — 新 Harness 场景
   `motion-render-failure`：提交成功、返回一个真实渲染任务、4 秒后该任务变成 `failed`。这是**现有
   Harness 造不出来的时序**（外壳自带的兜底 gateway 是提交那一步就拒绝，那正是 T91 已覆盖的另一半）。
5. **`frontend/e2e/video-studio-render-failure.spec.ts`（新增）** — 真实用户路径。

**`VideoStudio.tsx` 一行未改**，错误文案的分类与映射一处未碰（T90b 的地盘）。

### 轮询自己失败时，用户看到什么——正面回答

**看到侧边栏「视频制作」上一个写着「未知」的角标，悬停是「读不到视频制作进度，去看看」；
不会看到「正在进行中」。**

判定规则是「**我还欠着结果的那些运行，现在是不是全都看得见**」，两种情况都算看不见：

- `motionJobs()` 抛异常（桥断了、命令失败、原生侧没起来）；
- 读成功了，但一条还没到终态的自有任务**不在返回列表里**——它同样欠着结果，而且已经没有办法再知道了。

连续 3 次（约 15 秒）才翻牌，一次抖动不报警；任何一次读成功立刻恢复（有用例：
`goes back to the running mark once it can read the run again`）。

**为什么不是复用「失败」**：那会断言一件这里没有任何东西知道的事。**为什么不是退回蓝点**：
那会把本任务在修的谎原样装回去。看不见本身就是一个答案，它排在真实失败之后（已知结果永远压过未知），
并且只在真的欠着结果时才出现。

## 七、失败矩阵

| 情形 | 现在的行为 |
|---|---|
| 渲染在用户切页之后失败 | 5 秒内侧边栏出现红色「失败」文字，无障碍名变为「视频制作 失败」；回到页面看到红色 Alert（「「X」这条视频没有做出来。」）与任务卡上的具体原因 |
| 渲染成功，用户在别的页面 | 任务被标记已结束，监视器自行停止；页面上的「去看成片」announce 保留到用户回来（与 T91 一致，未变） |
| 用户自己取消了渲染任务 | 标记已结束，不写任何消息（取消是用户自己干的，不需要被告知） |
| `motionJobs()` 连续 3 次抛异常 | 角标变「未知」，`title` 为「读不到视频制作进度，去看看」 |
| 自有任务从返回列表里消失（还没到终态） | 同上，按「看不见」处理，并继续轮询以便恢复 |
| 读恢复正常 | 立刻回到「正在进行中」蓝点 |
| 真实失败 + 同时读不到 | 显示「失败」——已知结果压过未知 |
| App 关闭时有一次读在路上 | `stopped` 旗子挡掉，store 不被写入（变异验证过） |
| 本会话没提交过任何东西 | 一个定时器都不建，`motionJobs()` 一次都不调 |
| 编排阶段（2–3 分钟）失败 | 由提交 Promise 自己写进 store，T91 已覆盖，本次未改 |
| 页面开着时渲染失败 | 顶部一句红色 Alert（只说没做出来）+ 任务卡上的具体原因，两层不重复 |

## 八、真实边界与遗留

**验收层级**：本轮最高只到 UI Harness（Playwright 无头 Chromium + 测试专用 React 页面）。
按项目规则，这只能证明 React 业务交互，**不能**证明正式 App 的 IPC、原生桥和 Sidecar 生命周期。
Harness 里那条渲染任务是 Harness 造出来的，不是真的渲染。

**仍然剩下的静默/不实窗口，如实登记：**

1. **成片做好了，用户在别的页面时，标记仍是「正在进行中」。**
   这是 T91 有意的定义（「running = 在跑，**或结果还没被看过**」），本次**没有改变它**——
   监视器只是内部标记了已结束，屏幕上和以前一模一样。严重性低于失败那一半（用户最终会去看，
   而不是永远等一个已经死掉的东西），但形状同族：那句 `title` 对一条已经做完的片子是假的。
   要修需要第五种 attention 与相应文案，属于独立任务。
2. **编排阶段（2–3 分钟）挂死不返回时，从别的页面看仍然只有蓝点「正在进行中」。**
   严格说这不是谎——原生命令确实还没返回，客户端无法区分「慢」和「卡死」。页面上有 T91 加的
   「已经超过实测最长的 3 分钟」参照物，但那句话只在制作页上。
3. **App 重启后不恢复。** `ownJobs` 在内存里，重启后监视器不知道有任务要看。
   T91 已登记根治办法是原生快照带 `startedAt` 和片长，属原生侧工作。
4. **角标是否被 232px 侧栏裁掉，仍未验证。** T91 就 `失败` 登记过这一条（jsdom 与 Playwright 的
   `toBeVisible()` 都不判定裁剪）；`未知` 同为两个汉字、同一位置，结论通用。按边界要求没有在
   `frontend/e2e/` 下新增几何断言（T96 占着像素基准）。
