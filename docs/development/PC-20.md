## 1. 为什么做

视频创作模型答之前会先推理。用户问「这个功能调用大模型的地方是不是开着深度思考」，
量下来发现推理那一段占了模型往返的绝大部分——演示前赶时间的人有理由把它关掉。

## 2. 实测

四对观测，真实百炼、真实编排 prompt（由 `MotionAuthoringAgent` 自己组装，不是玩具输入）：

| | 开着 | 关掉 |
| --- | --- | --- |
| 观测 | 40.5 / 41.7 / 51.0 / 69.8 秒 | 8.5 / 9.9 / 10.9 / 23.5 秒 |
| 中位 | 46.4 秒 | 10.4 秒 |

典型省下 **36 秒**；能遇到的极端是 **17**（40.5−23.5）到 **61**（69.8−8.5）。
**离散度比中位数还大**，所以界面给的是区间不是点估计——第四对样本来自真实链路验证，
它本身就落在前三对推出的区间之外。

## 3. 界面只报「省多少」，不报「这一步多久」

**初版报了绝对值，被审查抓出来，这是个真错误。**

量到的 41.7 / 10.9 是**模型秒**（一次往返）；而同一张卡片上关于编排的其他话说的是
**编排整段墙钟**（`MOTION_AUTHORING_MEASURED`，T83 实测 136~178 秒）。初版文案写
「编排这一步实测约 42 秒」，正好印在「编排加渲染最长约 …」上面——两个口径的数并排。

`docs/demo-sprint-roadmap.md` 的 T92 那条白纸黑字记过这条规矩：

> 不能凭 T92 的数字直接换——旧常量量的是**编排整段墙钟**（T83 实测 136–178 秒），
> T92 量的是**模型秒**，口径不同；凭猜换一个数比留着旧数更糟

**失败场景很具体**：操作者读到「42 秒」，关掉开关，然后等了一分半到三分钟，
结论是「这开关没用」或「这界面在骗人」——而开关是有用的。

差值是唯一能跨口径的数：关掉推理，从模型秒和墙钟里减掉的是同一段。所以契约现在只
声明 `savedSecondsTypical / Least / Most`，绝对值一个都不存，测试钉着「契约里不许再
出现绝对耗时」。

## 4. 默认保持开着

只量了时间，没量质量。为省半分钟让每条片子悄悄变差，不是这一侧能替操作者做的取舍。
两档文案都直说这一点（「少了这一遍推敲成片会不会变差，我们还没有量过」）——
一个两边说法不一致的开关，是伪装成开关的推荐。

默认值原本硬编码在三处（契约、Rust、Python entry），只有前端真的读契约。现在三侧
都读同一份，因为那条 rationale 本身就写着「一旦量了质量就会改」。

## 5. 一路走到底，每一层都在用它

```
表单 Switch → setMotionThinking → motion-run-store
  → MotionVideoBriefRequest.modelThinking
  → Rust serde（必填，无默认）
  → motion_authoring_request 的 "modelThinking"
  → Python entry
  → MotionAuthoringAgent._model_thinking
  → call_video_creation_model(thinking=)
  → 请求体 enable_thinking: false
```

`#[serde(default)]` **已删掉**：App 自带前端、同一次构建产出，不存在旧调用方，
漏传只可能是漏写。留着默认就会把「操作者关掉了」变成「片子悄悄按开着跑」，
而这正是这条线本周被咬七次的形状。新增测试用前端真会发出的那份 JSON 做反序列化，
少字段必须被拒。

Python 侧只在**关掉**时才发 `enable_thinking` 字段，开着时请求体与今天完全一致。

## 6. 真实链路验收

不是 mock。走 `run_motion_authoring_entry` 这条正式入口，真实百炼、真实工作区：

```
深度思考=False     9.9s  status=authored  段数=5  帧=600
深度思考=True     69.8s  status=authored  段数=5  帧=600
```

两档都产出合法编排，闭合三键校验（`design` / `script` / `storyboard`）都过，
段数与帧数一致。**这证明的是服务端接受 `enable_thinking: false` 且应答仍然可用**——
在此之前唯一的验证是 mock 掉 `urlopen` 断言请求体，那证明不了服务端会怎么回。

## 7. 失败矩阵

| 情形 | 期望 | 结果 |
| --- | --- | --- |
| 请求少了 `modelThinking` | Rust 反序列化拒绝，不静默按默认跑 | 绿 |
| `modelThinking` 不是布尔 | entry 拒绝，且归类为「请求写错」而非「模型拒绝」 | 绿 |
| 关掉后提交 | 请求体带 `enable_thinking: false` | 绿（变异测试验证过） |
| 开着提交 | 请求体不带该字段，与今天完全一致 | 绿 |
| 切页再回来 | 开关状态还在 | 绿 |
| 服务端真实应答（两档） | 都 `authored` 且过闭合三键 | 绿（§6） |

`model_thinking_choice_invalid` 补进了 `nonRefusalOutcomes.app_request_invalid`——
它的同类（`request_shape_invalid`、`duration_not_whole_seconds` 等）都在那里。
不补的话，一个请求写错会被报成「模型读了你这句话并拒绝了，请换一种描述」，
让用户反复改一句本来没问题的话。
