## 结论先行

**用户报的两个按钮必报错，不是执行器坏了。** 派单时的假设是「重启后 sidecar 还没握手完成，所以命令失败」——
这条**被证伪**了，证据见第二节：我用**正式包里那个执行器二进制**，按 Rust 的原样握手、原样算证明、原样下发
`douyin.login.recheck`，**两种档案都成功**：空档案 4.4 秒回 `awaiting_scan`，用户那份**真实已登录**档案 1.8 秒回
`healthy`，执行器全程没退出，结果帧完全合法。执行器、内置 Chromium、跨语言协议、HMAC 证明、Zod 校验，
**全部排除**。

**没能指名道姓说出是哪一行失败的——原因恰恰就是本任务要修的那个缺陷。** 失败原因在三层里被连续丢弃：

| 层 | 丢掉了什么 |
| --- | --- |
| `PlatformSessions.tsx` 的 `catch {}` | 整个错误对象，只留一个布尔 |
| `safeInvoke` | Rust 已经放上线的 `{code, message, retryable}`，一律压成 `transport_unavailable` |
| `map_profile_error` | 把**可恢复**的「档案待恢复」压进通用的 `storage_unavailable` |

所以线上那句「暂时无法读取抖音登录状态，请稍后重试」对**十五种**互不相同的原因是同一句话，
其中至少两种重试一万次也不会好。本次把这三层都改掉了。

顺带修掉一个**同一条路上的真缺陷**：App 持有运营浏览器档案租约时被强杀，磁盘上会留下 `active` 标记
（`tests/browser_profile_locks.rs` 里 `killed_lock_holder_preserves_marker_and_requires_explicit_recovery`
就是专门钉这个行为的）。此后每次按这两个按钮都拿不到租约，**永久失败**，唯一出路是「安全注销」。
而这个状态原本被映射成 `storage_unavailable`，界面再把它翻译成「请稍后重试」——一条永远走不通的建议。

## 一、我推翻了什么

派单里明确要求：如果假设是错的，直说。三条假设/我自己的中间猜想，都是**用证据**推翻的，不是靠推理：

1. **「签名/公证改写了内置 Chromium 的字节，逐文件摘要校验失败」——否。**
   按 `embedded_browser_distribution.rs` 的 `walk_and_verify` 原样复算了 `/Applications/自动化运营工具.app`

   顶层条目也正确。
2. **「档案锁处于陈旧 `active` 状态，所以每次都失败」——否（就当时那次而言）。**
   用户那份档案的 `.automation-tool-profile-lock-v1` 现在是 **0 字节**（= 已释放），
   mtime `07-27 01:24:50`。
3. **「sidecar 没起来 / 那条链路本身是坏的」（派单假设）——否。** 见下一节。

## 二、正式包里的执行器：直接驱动，跑通

复现脚本按 `executor_bootstrap.rs` 的格式手算证明（HMAC-SHA256 over `domain || parts join "\0"`，
base64url、`atlcp1.` 前缀），也就是说**它同时验证了 Rust 侧的线格式能被 Python 侧接受**：

```
STDOUT: {"event":"executor.healthy", ...}
--- sending douyin.login.recheck (headless=True) ---
STDOUT (+1.8s): {"commandId":"f367c9ed-…","event":"platform.command.completed",
                 "flowVersion":"douyin.qr-login.v2","platform":"douyin","state":"healthy"}
--- executor exit code: None      # 没死
--- stderr: []
```

用的是 `/Applications/自动化运营工具.app/Contents/Resources/local-executor/package/automation-tool-executor`
和同一个包里的内置 Chromium；档案是用户真实档案的**副本**（只读登录态检查，未发布/未评论/未私信；用完已删）。

## 三、磁盘取证：那次失败发生在浏览器启动之前

`~/Library/Application Support/com.aventador.automationtool/profiles/demo-xuanbai/` 的 mtime 能把
用户那次操作还原出来：

| 时刻 | 证据 | 含义 |
| --- | --- | --- |
| 07-26 21:35 | 档案内 `Cookies`、`Local State`、`Last Version` 等 | 上一次成功登录 |
| 07-27 01:22:56 | `product-account-session-v1` | App 启动、产品账号登录 |
| 07-27 01:24:50 | `local-executor/state/executor-ledger.sqlite3` | 执行器被拉起 |
| 07-27 01:24:50 | `.automation-tool-profile-lock-v1`（0 字节） | 档案租约**取得并释放** |
| **仍是 07-26 21:35** | `Local State` / `Last Version` / `Variations` / `Default/` | **Chromium 根本没启动** |

最后一行是关键，而且是**先验证过判据才敢用**的：我自己的复现跑完后，副本档案里这几个文件全部被刷新到
`01:57–01:58`。所以「Chromium 启动必然改写它们」成立，用户那次**没有**改写 ⇒ 没启动。

由此可定位到：`ensure_executor_running`（执行器已起）→ `resolve_embedded_browser`（已解析）→
`current_douyin_profile`（已取得）→ 租约已拿到 → **`manager.execute_platform_command` 在浏览器启动前就失败并释放了租约**。
再往里是哪一支，磁盘上没有留下任何东西——因为**产品没有把它写下来**，这就是本次要修的东西。

## 四、RED → GREEN

三轮，每轮都实际跑到**断言失败**（不是 import/编译错误）。

### 第一轮：网关吞掉原生失败原因

RED（`npx vitest run src/platform/tauri/platform-session-gateway.test.ts`）：

```
- { "code": "authentication_rejected", "retryable": false,
+ PlatformSessionGatewayError { "code": "transport_unavailable", "retryable": true,
Tests  6 failed | 1 passed (7)
```

GREEN：`safeInvoke` 改用**仓库里已有的** `nativeCommandErrorFields`（另外六个网关都在用它），
`PlatformSessionGatewayError` 的码集合按 Rust 那四个 mapper 的实际输出补齐为封闭集合。→ `7 passed`。

### 第二轮：页面把所有原因说成同一句话

RED（`PlatformSessions.test.tsx`）：`Tests 4 failed | 5 passed (9)`，四条都是
`Unable to find an element with the text: /运营浏览器组件缺失或损坏/u` 之类的真实断言失败。

GREEN：按 T85 在更新中心立的同一套做法，加**单一分类函数** `failurePresentation`，把失败分成三类：

- `internal`——我们自己的程序/安装包的问题，**明说重试无效**，并给出故障代码；
- `temporary`——确实是暂时的（执行器暂时不可用、超时、连不上服务端），才提「稍后再操作」；
- `needs_user`——有具体动作可做（先关掉占用的运营浏览器窗口 / 先「安全注销」/ 重新登录产品账号）。

默认分支跟随原生侧的 `retryable`，不把未知失败悄悄降级——这条也照抄 T85 的判断。
另外 `readPublishedSnapshot` 超时不再抛裸 `Error`，改抛 `health_publication_timed_out`，
文案是「本机已确认登录正常，但服务端状态还没同步过来」——和「读不到登录状态」正好相反，原来那句是反的。
→ `9 passed`。

`message` 字段仍然**不**进渲染文案（`native-command-error.ts` 定的规矩），页面只按封闭集合的 `code` 映射自己的中文；
原有的「never reflects gateway error details」用例照常通过。

### 第三轮：可恢复的档案状态被压成不可恢复的

RED（`cargo test --lib executor_platform::tests::a_profile_that_needs_explicit_recovery`）：

```
assertion `left != right` failed: a 浏览器档案 awaiting explicit recovery must not arrive as a
generic storage failure: the operator can clear the first with 安全注销 and can do nothing about the second
  left: StorageUnavailable
 right: StorageUnavailable
```

GREEN：`ExecutorPlatformErrorCode` 新增 `RecoveryRequired`，`map_profile_error` 单独映射，
`map_executor_platform_error` 输出 `profile_recovery_required`（前端已经有对应文案：先「安全注销」再重新登录）。

## 五、失败矩阵覆盖

| 格 | 本次覆盖方式 |
| --- | --- |
| Sidecar 未启动 / 崩溃 / 挂起 | `process_unavailable`、`timed_out`、`already_running` 三个码各自有文案与分类，测试钉住 `process_unavailable` |
| 安装包内容缺失 / 版本不匹配 | `browser_component_missing|invalid|version_incompatible`、`package_rejected` → `internal`，测试钉住并断言**不出现**「请稍后重试」 |
| 多实例竞争 | `profile_in_use` → `needs_user`（先关掉已打开的运营浏览器），有测试 |
| App 退出后残留状态恢复 | `profile_recovery_required` → `needs_user`（先安全注销），Rust 侧有测试；对应的磁盘行为由既有 `browser_profile_locks.rs` 钉住 |
| 断网 / 平台超时 | `transport_unavailable` → `temporary` |
| 结果不确定（本机成功、服务端投影滞后） | 新增 `health_publication_timed_out`，明确告知**不需要重复操作**，有测试 |
| 敏感信息泄漏 | `message` 不进渲染文案；既有「never reflects gateway error details」用例继续通过；`check_user_facing_branding.py` 通过 |

**待补**：正式包上，healthy 会话重启后点这两个按钮。届时若仍失败，界面会直接报出故障代码，
