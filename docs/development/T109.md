## 结论先行

**用户报的两个按钮必报错，不是执行器坏了。** 派单时的假设是「重启后 sidecar 还没握手完成，所以命令失败」——
这条**被证伪**了，证据见第二节：我用**正式包里那个执行器二进制**，按 Rust 的原样握手、原样算证明、原样下发
`douyin.login.recheck`，**两种档案都成功**：空档案 4.4 秒回 `awaiting_scan`，用户那份**真实已登录**档案 1.8 秒回
`healthy`，执行器全程没退出，结果帧完全合法。执行器、内置 Chromium、跨语言协议、HMAC 证明、Zod 校验，
**全部排除**。

**没能指名道姓说出是哪一行失败的——原因恰恰就是本任务要修的那个缺陷。** 失败原因在三层里被连续丢弃：

| 层 | 丢掉了什么 |
| --- | --- |
| `PlatformSessions.tsx` 的 `catch {}` | 整个错误对象，只留一个布尔 |
| `safeInvoke` | Rust 已经放上线的 `{code, message, retryable}`，一律压成 `transport_unavailable` |
| `map_profile_error` | 把**可恢复**的「档案待恢复」压进通用的 `storage_unavailable` |

所以线上那句「暂时无法读取抖音登录状态，请稍后重试」对**十五种**互不相同的原因是同一句话，
其中至少两种重试一万次也不会好。本次把这三层都改掉了。

顺带修掉一个**同一条路上的真缺陷**：App 持有运营浏览器档案租约时被强杀，磁盘上会留下 `active` 标记
（`tests/browser_profile_locks.rs` 里 `killed_lock_holder_preserves_marker_and_requires_explicit_recovery`
就是专门钉这个行为的）。此后每次按这两个按钮都拿不到租约，**永久失败**，唯一出路是「安全注销」。
而这个状态原本被映射成 `storage_unavailable`，界面再把它翻译成「请稍后重试」——一条永远走不通的建议。

## 四、RED → GREEN

三轮，每轮都实际跑到**断言失败**（不是 import/编译错误）。

### 第一轮：网关吞掉原生失败原因

RED（`npx vitest run src/platform/tauri/platform-session-gateway.test.ts`）：

```
- { "code": "authentication_rejected", "retryable": false,
+ PlatformSessionGatewayError { "code": "transport_unavailable", "retryable": true,
Tests  6 failed | 1 passed (7)
```

GREEN：`safeInvoke` 改用**仓库里已有的** `nativeCommandErrorFields`（另外六个网关都在用它），
`PlatformSessionGatewayError` 的码集合按 Rust 那四个 mapper 的实际输出补齐为封闭集合。→ `7 passed`。

### 第二轮：页面把所有原因说成同一句话

RED（`PlatformSessions.test.tsx`）：`Tests 4 failed | 5 passed (9)`，四条都是
`Unable to find an element with the text: /运营浏览器组件缺失或损坏/u` 之类的真实断言失败。

GREEN：按 T85 在更新中心立的同一套做法，加**单一分类函数** `failurePresentation`，把失败分成三类：

- `internal`——我们自己的程序/安装包的问题，**明说重试无效**，并给出故障代码；
- `temporary`——确实是暂时的（执行器暂时不可用、超时、连不上服务端），才提「稍后再操作」；
- `needs_user`——有具体动作可做（先关掉占用的运营浏览器窗口 / 先「安全注销」/ 重新登录产品账号）。

默认分支跟随原生侧的 `retryable`，不把未知失败悄悄降级——这条也照抄 T85 的判断。
另外 `readPublishedSnapshot` 超时不再抛裸 `Error`，改抛 `health_publication_timed_out`，
文案是「本机已确认登录正常，但服务端状态还没同步过来」——和「读不到登录状态」正好相反，原来那句是反的。
→ `9 passed`。

`message` 字段仍然**不**进渲染文案（`native-command-error.ts` 定的规矩），页面只按封闭集合的 `code` 映射自己的中文；
原有的「never reflects gateway error details」用例照常通过。

### 第三轮：可恢复的档案状态被压成不可恢复的

RED（`cargo test --lib executor_platform::tests::a_profile_that_needs_explicit_recovery`）：

```
assertion `left != right` failed: a 浏览器档案 awaiting explicit recovery must not arrive as a
generic storage failure: the operator can clear the first with 安全注销 and can do nothing about the second
  left: StorageUnavailable
 right: StorageUnavailable
```

GREEN：`ExecutorPlatformErrorCode` 新增 `RecoveryRequired`，`map_profile_error` 单独映射，
`map_executor_platform_error` 输出 `profile_recovery_required`（前端已经有对应文案：先「安全注销」再重新登录）。

## 十、2026-08-02：真实故障闭环

### 根因与 RED

- 正常启动 `/Applications/自动化运营工具.app`，从“账号与平台”点击“打开登录处理”，
  页面稳定返回 `process_unavailable`；进程追踪确认执行器成功握手后约 1 秒退出，期间没有
  Chromium 进程；
- 诊断冻结包只记录固定 WebSocket 关闭事实，得到
  `4406 Executor protocol is rejected`。本机 ledger 中两条 07-26 的 durable outbox
  (`task.accept`、`task.discovery_completed`) 已超过 30 秒 wire deadline；
- `ExecutorCommandProcessor.recover_outbox()` 原来会在**每次**重连把所有 delivered 行
  重新置为 pending。第一条重复 ACK 可收敛，第二条发现完成事实先命中过期校验并关闭连接，
  所以后续启动永远重复同一失败；
- 先新增 `test_recovery_does_not_replay_outbox_messages_after_their_wire_deadline`，首次运行
  精确失败：两条过期消息仍被恢复。

### GREEN 与同路径浏览器缺陷

- 重连恢复现在只发送 `now < deadline_at` 的 outbox；历史上已经发送过的过期消息保持
  delivered，从未发送的过期消息仍留在 durable ledger，不再伪装成交付，也不进入会被
  控制面拒绝的 WebSocket。恢复读取不再受首批 1000 条历史行遮挡，仍在期限内的后续消息
  会继续进入投递；
- 冻结执行器的独立实测还证明：App 若把 OS 锁文件放进 Chromium `user-data-dir`，
  `launch_persistent_context` 会在浏览器进程出现前失败。因此 Profile 租约保持原排他语义，
  但移动到平台父目录，命名为 `.automation-tool-profile-lease-v1-<profile-id>`；macOS 与
  Windows 的竞争、崩溃标记、替换、删除和权限矩阵均随之迁移；
- Windows 首轮原生测试因相对名校验未识别新固定前缀而 9/9 返回 `UnsafeDirectory`；只给
  固定租约前缀增加 profile ID 解析分支后，原生实体机原矩阵 9/9 通过；
- 首轮 Codex Review 又准确发现“从未发送的过期消息被标成交付”、超过 1000 条历史行时
  后续有效消息滞留，以及 tombstone 删除后崩溃会遗留父目录租约三项功能缺陷。新增相反
  RED 后，ledger 按原 delivered 状态和 deadline 一次扫描全部恢复候选，两个平台的删除重试
  在 Profile/tombstone 均不存在时继续幂等清理租约；macOS、Windows 新矩阵均为 10/10。
- 复审继续发现未发送过期行虽已停止上网，却仍占 1000 条/16 MiB 待投递配额。相反 RED
  证明配额满后新结果无法落账；v9 ledger 现用独立 `expired` 状态保留原 envelope 和
  `delivered = 0` 事实，同时退出待投递计数。另按证据规则把本文件移出历史豁免，新增结论
  由真实 App 时间、线上 revision 和进程终态直接接受门禁检查。
- 第三轮 Review 指出 v8→v9 首次恢复若用 `fetchall()` 载入全部永久历史，老安装可能在
  到达末尾有效消息前耗尽内存或超时。分页 RED 把批量上限压到 2 时只观察到 1 次查询；
  改为按 ordinal 每页读取后，5 条历史精确执行 3 页且顺序不变。
- 提交前 Review 发现 ledger 已升到 v9、抖音单次发布契约仍固定写 v8，现有契约测试精确
  RED（`8 != 9`）；同步 `ledgerSchemaVersion` 后转绿，修后复审无新增可执行问题。
