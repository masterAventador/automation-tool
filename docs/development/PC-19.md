## 0 · 这一项是怎么冒出来的

不是排期排到的。PC-18 收尾时留了一条「第一次真出片」的产物当证据：

```
.local/kept-evidence/2026-07-28-t36-第一次真出片-全模板段.mp4
h264 / 1920×1080 / yuv420p / 30fps / 360 帧 / 12.000 秒 / 966,493 字节

推进片长上限时顺手抽了几帧比对，结果是决定性的：

```
$ ffmpeg -ss <t> -i <film> -frames:v 1 out.png   （t = 1,3,5,7,9,11）
t=1s   b97310bd793e43c12c493e75dc634a80

t=5s   f092c27d4ce64e2e1e50e80d90fdb479

t=9s   725336191c3231f42524f968d887ae23   ← 与 t=3s 相同
t=11s  f092c27d4ce64e2e1e50e80d90fdb479   ← 与 t=5s 相同

周期 6 秒。**那条被当作里程碑的成片，是同一段 6 秒内容倍速播了两遍。**

当时对它做过的检查：编码格式、分辨率、像素格式、帧率、帧数、时长、文件大小，
外加产品自己的静帧门禁（`rendered_film_is_static`，逐段查）。**全部绿。**

## 1 · 根因

`workers/motion_composition/worker.mjs`：

```js
const time = seekableDuration * (index - 1) / spec.frameCount;
```

`seekableDuration` 是**页面自己声明的**总时长（`data-duration`）。段携带的信息只有
「哪个页面、多少帧」，所以 Worker 只剩这一条规则可用：把页面整条时间轴摊到这一段
要的帧数上。

- 一次拍完的片子：`frameCount = duration × fps`，摊出来正好是 1/fps 一帧，对的；
- 路线 A 之后：模板镜头**共用同一份 `composition.html`**（那份文档把每个镜头都画在
  同一条时间轴上），两个模板镜头各拿到 180 帧，于是各自把整条 12 秒压进 6 秒里播了
  一遍。

零件段没这个问题——每个零件是自带时间轴的独立文件，窗口天然就是它自己那条。
**受影响的恰好是最常见的那条路**：一句话出片的镜头多半落在模板上。

## 3 · GREEN

段带上时间窗，全线打通：

```
film_assembly.FilmSegment.source_start_millis / source_end_millis
  → agent.RenderSegment.to_payload() 的 sourceStartMillis / sourceEndMillis
  → Rust RenderSegmentAnswer（deny_unknown_fields，必填）
  → MotionRenderSegment.source_start_millis()
  → VideoWorkerSourceWindow::new（校验）
  → 渲染 spec 的 sourceStartMillis / sourceEndMillis
  → worker.mjs：time = windowStart + (windowEnd - windowStart) × (index-1)/frameCount
```

- **模板段**的窗口是分镜给这一镜的那一截 `[start, start + seconds)`；
- **零件段**的窗口是零件自己的时间轴 `[0, 零件时长)`。旁白比动效长时零件仍被拉长铺满
  整镜（改动前就是这个行为，有意保留，改它是另一件事）。

## 4 · 为什么是毫秒整数，不是秒

**这一条是改的过程中被门禁抓出来的，不是设计时想到的。**

第一版用 `sourceStartSeconds: f64`。`scripts/test_motion_video_render_sandbox.py` 立刻
变红，而且红得莫名其妙：一条本该被判非法的 spec 收到的是 `worker.cancelled` 而不是
`worker.render.failed`——看起来像 Worker 把命令**整个忽略了**。

追下去是这个：渲染命令的 HMAC 绑定在一份「规范化 JSON」上，这份 JSON 要由 Python
（Executor）、Rust（App）、JS（Worker）三侧逐字节产生一致的结果。

```
Python  json.dumps(0.0)      →  "0.0"
JS      JSON.stringify(0.0)  →  "0"
```

签名对不上 → 命令被丢弃 → **一个字都不报**。整份 spec 原本全是整数，浮点是我引入的
第一个。改成毫秒整数后三侧一致。

`workers/motion_composition/worker.mjs`、`local_video_orchestrator.rs`、`film_assembly.py`
三处都把这个理由写在注释里，因为下一个想用秒的人看不到这份文档。

## 5 · 顺带补齐：180 秒上限其实根本走不通

上一个提交（`2aa7706`）把上限从 20 抬到 180，只改了请求校验一处。实测 60 秒的请求：

```
motion authoring rejected: duration exceeds the snapshot frame budget for this fps
```

三处没跟上：

1. **Rust `brief_plan`** 还在拿 `total_seconds_maximum`（20，固定模板那条路的沙箱单次
   上限）卡。后果是最难受的那种：请求校验放行 → 编排真的跑了三分钟 → 然后被拒。
   **用户等三分钟才拿到一句「做不出来」，而他选的正是界面允许他选的长度。**
2. **Python `author()`** 顶上的 `duration × fps ≤ MAX_FRAME_COUNT` 是单次渲染时代的
   遗留。路线 A 下受 600 帧约束的是**段**（`plan_film` 逐段判），整片没有这个限制——
   PC-08 的失败矩阵里就写着「20 镜共 3600 帧 → 放行」。改为：有零件目录时按片长上限判，
   无零件目录时 composition 就是整部片子、仍需塞进一次捕获。
3. **编排 prompt** 建议「每段 2~3 秒」与段数上限 24 在 72 秒（24×3）以上无解——照建议
   切 180 秒要 60~90 段，一律被 `write_storyboard` 拒；照上限切每段 7.5 秒，又和建议
   对不上。改为按片长推导：

   | 片长 | 建议每段 | 最多切成 |
   | --- | --- | --- |
   | 12 秒 | 2~3 秒 | 6 段 |
   | 60 秒 | 3~4 秒 | 20 段 |
   | 180 秒 | 8~12 秒 | 23 段 |

   12 秒那档与原来一致，改的只是长片。

`briefBeatCountMaximum` 与 `briefSecondsPerBeatMinimum` 进 `motion-storyboard-duration.v1.json`，
Python 与前端都从那里读；Rust 的 `duration_limits()` 增加一条不变式：界面允许选的最长
片子，必须能被切成不超过上限的镜头数、且每镜都塞得进一次捕获。

## 6 · 片长控件本身

一句话入口加 `成片时长（秒）`，1~180，默认仍是 12。片长与句子一样存进
`motion-run-store`——两者是同一张表单上的字段，`WorkbenchShell` 一点侧边栏就把页面卸载
掉，句子当年就是这么丢的；片长若留在组件 state 里会出现最难查的那种：设好 180 秒、
去别处看一眼回来，句子还在、数字悄悄退回 12。

耗时预估当场给出，按审查意见重做过（见 §7）。
