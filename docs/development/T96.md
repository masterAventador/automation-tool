## 结论先写

`frontend/e2e/` 下**每一个**用例过去都跑在 1280×**720** 的视窗里，而共享配置和多份
文件头都写着 800。现在实际下发值等于声明值，且由一条断言守住。

**没有任何既有结论因此作废。** 偏差方向是偏严——视窗更矮 ⇒ 折叠线更高 ⇒ 「在折叠线
以下」更容易成立——所以它不可能制造假通过，只可能制造假失败，而实际一条假失败也没有
发生（修正后全量 48 条全绿，没有一条需要调阈值）。错的只是那些文件头声称的测量基准。

## 生产窗口的真实尺寸：1280×800，最小 960×640

读自 `frontend/src-tauri/tauri.conf.json`（`app.windows[label=main]`）：

```json
"width": 1280,
"height": 800,
"minWidth": 960,
"minHeight": 640,
```

Tauri v2 的 `width`/`height` 是 webview 的 **inner size**，也就是视窗本身，不含窗口
装饰，所以它可以和 Playwright 的 `viewport` 直接对齐，不需要扣标题栏。

## 根因：project 级 `use` 整体覆盖顶层 `use`

```ts
use: { viewport: { width: 1280, height: 800 } },   // 顶层，声明了
projects: [{ name: "chromium", use: { ...devices["Desktop Chrome"] } }],  // 覆盖掉
```

`devices["Desktop Chrome"]` 这个预设自带 `viewport: {1280, 720}`。project 级 `use`
不是按字段深合并、而是整体压过顶层，于是顶层那行 800 被丢掉，且**看起来仍然是生效的
配置**。这正是它藏了这么久的原因：没有任何东西会因为它而变红。

## 逐条复核：既有像素断言在新基准下还成不成立

视窗长高 80px，方向上会**放松**每一条「必须在折叠线以上」的断言，所以不能只看跑绿。
下面每一行都是在 720 和 800 两个尺寸下各实测一遍得到的，不是推断。

| 用例 | 断言类型 | 720 实测 | 800 实测 | 结论 |
| --- | --- | --- | --- | --- |
| `screen-density` 内容列 / 卡片宽度 | 宽度 | 992px | 992px | **不变**，与高度无关 |
| `screen-density` 标题行下间距（8 个页面） | 相邻元素间距 | 20/20/24/20/20/20/20/20 | 同左，逐个相同 | **不变**，阈值 16 是固定值不随折叠线走 |
| `video-editing-tabs` 四条 | 全部是宽度 | 992/942 | 992/942 | **不变** |
| `video-studio-density` 两个「选择」按钮在首屏内 | 折叠线 | 底边 589，余 131px | 底边 589，余 **211px** | 仍成立但**变松**；见下 |
| `video-studio-density` 首屏至少一个可按下动作 | 折叠线 | 恰好这两个按钮 | **同一组，一个不多** | **实质不变**：下一个可按元素在 800 之下仍够不着 |
| `video-studio-density` 最小窗口 960×640 | 折叠线 | — | 底边 611 / 折叠 640，余 **29px** | **未受影响**，本次真正的紧边界 |
| `shell-layout` 内容区必须能滚 | 需要溢出 | 溢出 1656px | 溢出 **1576px** | 仍成立；方向上**变难**而非变松，余量充足 |
| `shell-layout` 文档本身不滚 / 导航不动 | 结构 | — | — | 与高度无关；导航那条非空转（仍有 1576px 可滚） |
| `video-studio-one-sentence` 两条 `toBeInViewport` | 是否在视窗内 | 输入框 y=114..190 | **同样 y=114..190** | **完全不变**，见下 |
| `workbench-home` 三条 | 渲染文本 | — | — | 与几何无关 |

三处需要展开说：

1. **「选择」按钮那两条确实变松了**（131px → 211px 余量），但这是应该的：折叠线本来
   就该是客户真实拿到的那条。它现在是「默认窗口下的回归守卫」，而**真正紧的边界由
   960×640 那组承担（29px）**。两者一起才是完整的：一个盯默认尺寸不退化，一个盯用户
   能拖到的最小尺寸。单独看默认尺寸那条会觉得它松，这是分工不是缺陷。
2. **「首屏至少一个可按下动作」没有因为变高而放进新东西。** 实测两个尺寸下命中集合
   逐字相同，都只有这两个按钮——因为再往下的可按元素在 800 处依然在折叠线之外。所以
   这条断言的语义没有被稀释。
3. **`video-studio-one-sentence` 完全没受影响**，而且它本来也不靠折叠线高度。它钉的
   缺陷是滚动锚定把输入框推到 y=**-412**（视窗上方）；`toBeInViewport` 对「跑到顶上去
   了」的检测和视窗多高无关。实测两个尺寸下输入框都落在 y=114，说明这条用例的余量从
   来不是 80px 量级的事。

**没有发现「其实在测无意义的东西」的用例，也没有发现需要收紧阈值的用例。**

## 各线自己文件里的 `test.use` 钉子：删了两个、留了一个

- **删** `video-editing-tabs.spec.ts:30` 的 `{1280, 800}`；
- **删** `video-studio-density.spec.ts:36` 的 `{1280, 800}`；
- **留** `video-studio-density.spec.ts` 里 960×640 那个，但改成读
  `MINIMUM_WINDOW`，不再抄字面量。

理由：这两个被删的钉子，值和现在共享配置下发的值**逐字相同**，删掉不改变它们跑在什么
尺寸下（已实测，全量仍 48 绿）。而留着有实际害处——它们恰好会掩盖本次修好的这个缺陷：
如果将来有人再把 `devices` 预设铺回 `viewport` 之上，钉住的文件照常绿、没钉的文件悄悄
缩回 720，也就是 T96 这次的事故原形。删掉之后所有文件共用同一个基准，
`viewport-baseline.spec.ts` 是唯一守卫，坏了就整体变红。

另外它们原来的注释写的是「**故意**钉在这里，因为改共享配置会放松所有人」——这个前提
现在已经不成立，注释留着会主动误导下一个人，所以连注释一起重写了。

960×640 那个留着，是因为它**故意不同于**默认值：它测的是用户能把窗口拖到的最小尺寸，
不是默认尺寸。改成读 `MINIMUM_WINDOW` 是为了让它和 `tauri.conf.json` 一起变，不会在
产品调整最小尺寸后偷偷测一个不存在的尺寸。

## 防再发：数字只有一处定义

`frontend/e2e/production-window.ts` 从 `tauri.conf.json` 读取并导出
`PRODUCTION_WINDOW` / `MINIMUM_WINDOW`，`playwright.config.ts` 和用例都用它。
所以「测试视窗」和「生产窗口」不再是两个可以各自漂移的数字，而是同一个。
产品改窗口尺寸时，测试基准自动跟着走。

配置里同时留了注释说明**为什么 `viewport` 必须写在预设展开之后**，因为这一点从代码
形态上看不出来（顶层那行看起来完全像是生效的）。

## 失败矩阵

| 情形 | 行为 |
| --- | --- |
| `tauri.conf.json` 里 `app.windows` 不见了 | 抛出带文件绝对路径的错误，配置加载即失败，不静默取默认值 |
| 没有 `label: "main"` 的窗口 | 同上，明确报「没有 label 为 main 的窗口」 |
| `width`/`height` 不是数字（如写成 `"1280"`） | 明确报缺少数字字段，不 `NaN` 传播进视窗 |
| 有人把 `devices` 预设重新铺到 `viewport` 之上 | `viewport-baseline.spec.ts` 第一条变红 |
| 产品调整了生产窗口尺寸 | 测试基准自动跟随；若某页面因此掉到折叠线下，对应 density 用例变红 |
| 页面内实际可视区与 Playwright 下发值不一致（如出现经典滚动条） | `viewport-baseline.spec.ts` 第二条变红 |

## 放大视窗后暴露的界面问题（记录，未修）

按要求只记录不修（本任务不碰产品代码）。1280×800 下逐页测 `.desktop-content` 的
溢出量：

| 页面 | 720 | 800 |
| --- | --- | --- |
| 工作台 | 需滚动 293px | 需滚动 213px |
| 视频制作 | 需滚动 584px | 需滚动 504px |
| **视频剪辑** | 需滚动 87px | **需滚动 7px** |
| 设置与诊断 | 需滚动 1656px | 需滚动 1576px |
| 新建任务 / 任务记录 / 作品发布 / 平台状态 | 放得下 | 放得下 |

**一处值得看一眼：视频剪辑在生产窗口尺寸下只差 7px 放不下整页。** 为了 7px 让整页
出现滚动条，观感上接近「差一点点就正好」，是那种调一处 margin 就能消掉的距离。这不是
功能缺陷，用例也没有断言它，所以按边界要求原样记录、交回给上层判断，未作任何改动。

其余页面没有因为变高而暴露新的塌陷、拉伸或错位——各元素 y 坐标在两个尺寸下实测一致，
布局是顶端对齐的，多出来的 80px 只是让下方内容多露出一截。
