## 0. 这是九个待验收任务缺的同一样东西

`catalog_parts` 从 PC-04 起就在每个 beat 上，而**没有任何东西读它**——合成仍由四个写死
layout 画出来，134 个零件被校验一遍然后丢掉。路线 A 需要的每一块都是绕着这个洞建的：
槽位表（PC-03）、进包的目录（PC-16）、单零件渲染（PC-05）、拼接（PC-06）、
时间轴（PC-08/09）、溢出预算（PC-14/17）。本模块把它们接上。

## 1. 一个 beat 一镜

- **点了零件的 beat**：从那个零件的工作区副本渲，用零件自己声明的舞台
  （目录里 105 个是 1920×1080，三个是 1080×1920）。画在模板舞台上得到的是它自己的
  左上角，就是 `motion-render-canvas.v1.json` 记着的那次事故；
- **没点零件的 beat**：回落到本机模板合成，用模板的舞台（640×360 @2），它整套字号
  体系为那张舞台而写。

**这个混合就是路线图那句「本机 4 layout 模板段与零件段可混排」变成代码做的事。**

零件段的 `deviceScaleFactor` 是 1：零件的舞台本身就是输出分辨率，再放大买不到东西，
而每一帧都要付钱。

## 2. 计划先全部算完，再动工作区

一镜渲不了就在计划阶段失败，此时**一个零件都还没被复制进工作区**。半满的工作区、
装着一部永远不会渲的片子，是后来的人要花时间去理解的状态。

测试里有一条专门钉这个：25 秒的镜头超单次渲染上限，抛错时 `workspace.written == {}`。

## 3. 真数据实跑（真发布树 + 真契约 + 真 AuthoringWorkspace）

三镜，两个零件夹一个本机模板：

```
b1  零件 lt-bold-block   1920x1080@1  186 帧  6.2s   槽预算 2 条
b2  本机模板              640x360@2   102 帧  3.4s   槽预算 0 条
b3  零件 logo-outro      1920x1080@1  180 帧  6.0s   槽预算 2 条

共 3 段 468 帧 15.6 秒    预估渲染 4.6 分钟    工作区 9 文件
```

b1 的旁白 6.2 秒长过动效 4.8 秒，镜头跟着旁白；b3 没有旁白，跟动效的 6 秒。
**PC-08 那条 `max(语音, 动效)` 走到了真正发出去的渲染请求上。**

每段带着它自己的槽预算（PC-14 需要基线在渲染期而不是冻结期）。

## 5. 失败矩阵

| 情形 | 期望 | 实测 |
| --- | --- | --- |
| 点了目录里没有的零件 | 拒绝 | 红 |
| 点了没有冻结槽位的零件 | 拒绝——没人量过它的文案该放哪 | 红 |
| 一镜超单次渲染上限 | 拒绝，且工作区不留任何文件 | 红且 `written == {}` |
| 一个 beat 都没有 | 拒绝 | 红 |
