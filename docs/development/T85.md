# T85 设置页更新区域默认呈现红色失败态

- 状态：🔍 待验收
- 日期：2026-07-26
- 分支：`update-ui`

## 现象

正式签名包的「设置与诊断」页，用户没有点击任何按钮，「App 更新」区域就直接显示红色状态标签「更新当前不可用」。客户 Demo 演示时这是第一眼可见的红字，观感为产品出错。

## 根因（已证实，非推断）

「发布构建显式关闭更新」这一**受支持的正常配置**，被原生命令层伪装成了 `failed / configuration_invalid` 失败态，而界面挂载即轮询，于是无需任何用户操作就渲染红色失败文案。

完整链路，每一步都有代码位置：

1. `frontend/src-tauri/build.rs:96-98` —— release 构建允许 `AUTOMATION_TOOL_UPDATE_DISABLED=1` 且不提供 endpoint/公钥时直接通过。**「关闭更新的发布构建」是一等公民配置，不是错误**；
2. `scripts/test_customer_demo_release.py:331-333` —— 断言没有部署配置的发布构建 `AUTOMATION_TOOL_UPDATE_DISABLED == "1"`，且 `AUTOMATION_TOOL_UPDATE_ENDPOINT`、`AUTOMATION_TOOL_UPDATE_PUBLIC_KEY` 均不存在。**客户 Demo 包正是按这条路径构建的**；
3. `frontend/src-tauri/src/app_update_coordinator.rs:631-641` —— release 分支用 `option_env!` 读取编译期值，两者都缺失时返回 `Ok(None)`，即「未配置」，**不是 `Err`**；
4. `frontend/src-tauri/src/lib.rs:4257,4295` —— 配置为 `None` 时 `update_coordinator` 取 `None`，协调器根本不创建。到这一步语义仍然正确；
5. `frontend/src-tauri/src/lib.rs:137-144` —— **失真点**。`get_app_update_state` 在协调器为 `None` 时 `unwrap_or` 出
   `UpdateState::Failed { stage: Configuration, code: ConfigurationInvalid, retryable: false }`。命令返回类型是 `UpdateState`，状态机里没有「未配置 / 已关闭」这一状态，只能借用 `failed` 表达；
6. `frontend/src/features/app-updates/AppUpdateCenter.tsx:107-131` —— `useEffect` 挂载即 `getState()` 并每秒轮询，**不需要用户点任何按钮**；
7. 同文件 `stateColor` 对 `failed` 一律返回 `red`，`statusText` 在 `retryable === false` 时返回「更新当前不可用」。

证实方式：`grep -rn "AUTOMATION_TOOL_UPDATE_ENDPOINT\|AUTOMATION_TOOL_UPDATE_PUBLIC_KEY"` 定位到 `build.rs` 与 `test_customer_demo_release.py` 的构建期约定，再顺 `option_env!` → `Ok(None)` → `None => None` → `unwrap_or(Failed)` 逐层读取源码确认。这一条链路是代码事实，不含推断。

## 候选排除

| 候选 | 结论 | 依据 |
| --- | --- | --- |
| 更新端点没配置 | ✅ **成立，即根因** | 见上，构建期即刻意不配置 |
| 端点不可达 | ❌ 排除 | 端点根本不存在，协调器未创建，不会发起任何网络请求 |
| 后端启动时自动检查一次并失败 | ❌ 排除 | `coordinator.start_background()` 只在 `Some(configuration)` 分支执行（`lib.rs:4292`），Demo 包走 `None` 分支，后台检查从未启动 |
| 组件自己的 `setFailure` 通道 | ❌ 排除 | 该通道渲染的是 `Alert`（`AppUpdateCenter.tsx:221`）而非红色 Tag，且 `get_app_update_state` 在三套 handler（`lib.rs:4427/4493/4591`）中均已注册，`invoke` 不会 reject；即便偶发 reject，下一次成功轮询会 `setFailure(false)` 自动消除，与「稳定常驻红字」不符。**未改动此通道** |

## 修改范围

只改表现层，**未改状态机、未改契约、未改任何 `.rs`**。

`frontend/src/features/app-updates/AppUpdateCenter.tsx` 新增单一分类函数 `failurePresentation()`，`statusText` 与 `stateColor` 共同引用它，避免同一套分类散落两处：

| `code` | 文案 | 颜色 |
| --- | --- | --- |
| `configuration_invalid` | 此版本未启用自动更新 | `default`（中性） |
| `transport_unavailable` | 暂时无法连接更新服务器，可稍后重试 | `gold`（提示） |
| 其余（`manifest_rejected`、`signature_rejected`、`storage_unavailable`、`installation_failed`）及未来新增码 | 维持原有 `retryable` 文案 | `red`（错误） |

`default:` 分支兜底为红色，新增失败码默认响亮失败，不会被静默降级。

## 是否把真实失败一起藏掉了

**没有，但有一处需要明说的取舍。**

- `signature_rejected`（验签失败，安全关键）、`installation_failed`、`storage_unavailable`、`manifest_rejected` **全部保持红色错误态**，文案一字未改，并已由新增护栏用例锁定；
- `transport_unavailable` 降为提示色，但文案仍明确说明「无法连接更新服务器」，且该状态本身 `retryable`，信息没有丢；
- **取舍**：`configuration_invalid` 一律呈现为中性。在正在运行的 App 里，编译期配置非法会在 `lib.rs:4237-4238` 的 `.expect()` 直接 panic、App 根本起不来，所以该码到达界面时绝大多数就是「本构建关闭了更新」。残留少数情形（协调器状态互斥锁中毒、检查期策略配置错误）会一并按中性呈现。这些情形**文案仍然写明更新不可用，不是静默**，只是不再用红色报警色；
- 根治办法在原生层：`get_app_update_state` 不应把「未配置」洗成 `failed`，状态机应新增独立的「更新未启用」状态。本次不做，因为 `.rs` 由另一条并行线（codex）持有，跨线改同一批文件会冲突。**建议作为后续任务**，届时需同步 `contracts.ts`、`contracts.test.ts` 与所有消费方。

## 失败矩阵

| 情形 | 表现 |
| --- | --- |
| 构建关闭更新（Demo 包） | 中性「此版本未启用自动更新」，无红字 |
| 更新服务器不可达 | 提示色「暂时无法连接更新服务器，可稍后重试」 |
| 更新包验签失败 | **红色**「更新当前不可用」 |
| 安装器失败 | **红色**，`retryable` 决定文案 |
| 存储不可用 / 清单被拒 | **红色** |
| `getState()` 本身 reject | 维持原有 `Alert` + 固定脱敏文案，未改动 |
| 未来新增失败码 | 落入 `default:`，**默认红色** |
