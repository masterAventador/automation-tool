## 任务

仓储层的 `except SQLAlchemyError` 接不住两类真实故障，它们会原样抵达调用方并进日志，
违反 `docs/development-roadmap.md` §4.1 与 CLAUDE.md §7：

1. **连接被拒**是 asyncio 的 `OSError`，消息里带 **host 与端口**；
2. **认证失败 / 角色不存在 / 连接数上限**是 asyncpg 的 `PostgresError`，消息里带
   **角色名与库名**。

两者都不是 `SQLAlchemyError` 的子类。

## 为什么这个缺口能活这么久

**现有用例一律 `raise SQLAlchemyError("private database detail")`。** 注入的异常类型
恰好就是唯一被接住的那一类，所以这些用例**无论实现对不对都会绿**——它们照不出这个缺口。

这与本仓多次记录的同一形状一致：能给出否定答案的检查，它的肯定答案才有意义。

## RED

不注入任何异常。让引擎真去连一个**绑定后立即释放**的 loopback 端口，由真实驱动产生真实
异常：

```text
AssertionError: connection refused escaped the repository unchanged:
ConnectionRefusedError: [Errno 61] Connect call failed ('127.0.0.1', 53360)
```

host 与端口一字不差地到了调用方。

**过程中自己造出过一条假绿**：第三条用例最初调 `repository.snapshot()`，而真实方法名是
`get()`，于是它因 `AttributeError` 而「通过」——断言全部没跑到。改用真名后才变红。
记在这里是因为它和本任务要修的缺陷是同一个道理：**测试通过不等于测试跑到了它要测的东西。**

## 结构断言与变异验证

三条行为断言只覆盖三个入口。另加一条 **AST 结构断言**覆盖整个仓储目录，包括将来新写的：
任何 `except` 只要接了 `SQLAlchemyError` 而没有 `OSError`，逐条报出文件与行号。用 AST
而非 grep，改换行躲不掉。

变异确认它不是摆设：把 `workbench_metrics_repository.py` 的一处改回裸 `SQLAlchemyError`，
断言立刻指名报出该文件与行号；改回即绿。

## 失败矩阵

- 连接被拒（`ConnectionRefusedError`，`OSError` 子类）：三条行为断言逐条核对
  host、角色名、库名均未到达调用方；
- 认证失败 / 角色不存在 / 连接数上限（asyncpg `PostgresError`）：本轮**未以真实错密码
  实跑**——见「真实边界」；
- 将来新增仓储漏接 `OSError`：由结构断言拦截，已变异验证。

## 正常用户路径验收

不适用——这是错误处理边界，不新增用户入口。用户可见的影响是「不再泄漏」，其证据形态
只能是断言而非界面。

## 真实边界

- **连接被拒这一类是用真实故障验的**：真实引擎、真实驱动、真实拒绝连接，不打桩；
- **认证失败那一类没有实跑**。它需要一个真跑着的 PostgreSQL 加一个错密码，本轮只按
  类型层级推断 `PostgresError` 不是 `SQLAlchemyError` 子类，因而与连接被拒同属被
  `(OSError, SQLAlchemyError)` 中的哪一支接住——**这一点尚未观测**。
  `asyncpg.PostgresError` 继承自 `Exception`，SQLAlchemy 通常会把它包成 `DBAPIError`
  （属 `SQLAlchemyError`），但**包不包取决于它在哪一层抛出**：连接建立阶段抛出的不经过
  SQLAlchemy 的包装。留作遗留项，需要真实库时补。

## 清理

测试只创建并立即释放一个 loopback 端口，不留进程、容器或文件。
