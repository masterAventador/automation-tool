# T82 — 以管理员身份运行时，内置浏览器 Profile 子系统整块失效

> 状态：**已修复**。发现于 Windows 验证线，修复于 Windows 缺陷修复线。
> 只能在 Windows 上做：相关代码是 `#[cfg(target_os = "windows")]`，macOS 上根本不参与编译。

## 一、现象

Windows 提权会话里跑 `cargo test`，46 个测试二进制中 23 条失败，其中 **21 条是 `UnsafeDirectory`**，全部集中在 store 构造阶段。

双向证明（验证线实测）：

| 会话 | `browser_profiles` | `browser_profile_locks` |
|---|---|---|
| 提权 | 0/12 | 0/8 |
| 非提权（`runas /trustlevel:0x20000`） | 12/12 | 8/8 |

## 二、根因

一个进程创建的对象归它 token 的**默认 owner** 所有，而不是归 token 用户所有。本机实测：

```
TokenUser  = S-1-5-21-205062978-3073403204-383193140-1002
TokenOwner = S-1-5-32-544   (BUILTIN\Administrators)
```

于是提权会话建出来的目录归 Administrators 所有。而：

- `apply_private_acl_with_flags` 调 `SetSecurityInfo` 时**只传 DACL**，owner 参数是 `null_mut()`；
- `verify_private_acl_parts` 第一件事就是 `EqualSid(owner, TokenUser)`。

**`AclPolicy::Repair` 修不了它唯一检查的那一样东西。** 先 apply 再 verify，apply 不碰 owner，verify 只看 owner —— 必然失败。

## 三、这是产品缺陷，不只是测试环境问题

用户只要用「以管理员身份运行」打开 App，整个内置浏览器 Profile 子系统就不可用（store 构造即失败 → 无法创建/打开任何平台 Profile）。「以管理员身份运行」在 Windows 上远比 UNC 重定向或 SUBST 映射常见。

## 四、方向选择：修创建端，不放宽校验端

两个方向都能让测试变绿：

1. 创建时显式把 owner 设成 TokenUser；
2. 校验时接受 owner ∈ {TokenUser, TokenOwner}。

**选 1。** 理由是安全边界而非美学：object 的 owner **无论 DACL 怎么写**都隐含持有 `READ_CONTROL` 和 `WRITE_DAC`。接受 `owner = BUILTIN\Administrators` 等于承认「这台机器上任何一个管理员账户都能改写这份 DACL，进而读到它保护的平台登录态」——直接违背 `CLAUDE.md` 第 5、7 节「App 私有运营 Profile / 平台会话本地私有」这条前提。方向 2 是把校验放宽到它本来要防的那件事上。

## 五、改动

- `SetSecurityInfo` 增加 `OWNER_SECURITY_INFORMATION`，owner 传 TokenUser 的 SID；
- 写 owner 需要句柄带 `WRITE_OWNER`，因此新增 `AclPolicy::extra_access()`：**只有 `Repair` 多要这一项**，`Require` / `Ignore` 保持原来的窄掩码不变。

### 已知代价（明确记录，不藏）

一个「归当前用户所有、但 DACL 没给用户任何权限」的目录，现在会在**打开阶段**就失败，而不是被修好——因为 owner 隐含权限只含 `READ_CONTROL`/`WRITE_DAC`，不含 `WRITE_OWNER`。

排查所有走 `Repair` 的目录，这条收紧在真实路径上不可达：

| Repair 目标 | 由谁创建 | 用户是否被授予 `WRITE_OWNER` |
|---|---|---|
| `app_data_dir` | Tauri / OS，继承 `%APPDATA%` 的 `user:F` | 是（Full Control 含 `WRITE_OWNER`） |
| `browser-profiles` / `<platform>` | 本代码 `NtCreateFile` + `FILE_ALL_ACCESS` | 是 |
| `douyin/.automation-tool-profile-lease-v1-<profile-id>` | 同上 | 是 |

## 六、测试

`browser_profiles_windows.rs` 此前 **1050 行 0 个 `#[test]`**。本任务补进程内单元测试模块。

关键设计：`repair_takes_ownership_...` 会把 `default owner differs from token user: <bool>` 打印出来，**让提权与非提权两种运行在输出里可区分**——否则两次运行长得一模一样，看不出哪一次真的覆盖了缺陷条件。

临时目录命名为 `automation-tool-browser-profiles-<tag>-<pid>-<seq>`，并沿用集成 fixture 的 `canonicalize()`（`%TEMP%` 可能是 8.3 短路径或被重定向，未解析的根会让被测守卫因环境而非行为失败——scheduler 环境下实测踩到过）。

## 七、RED / GREEN 证据

**RED（提权，ssh 会话 `IsElevated=True`）**，`cargo test --lib browser_profiles_platform::tests`：

```
default owner differs from token user: true
repair_takes_ownership_instead_of_only_rewriting_the_dacl          FAILED  UnsafeDirectory
a_store_initializes_under_the_process_default_owner                FAILED  UnsafeDirectory
a_profile_lock_round_trips_under_the_process_default_owner         FAILED  UnsafeDirectory
```

**GREEN（提权）**：lib 3/3；`browser_profiles` 12/12；`browser_profile_locks` 8/8。

**GREEN（非提权）**：`runas /trustlevel:0x20000`，`whoami /groups` 确认 `BUILTIN\Administrators ... Group used for deny only`，用例自报 `default owner differs from token user: false`。lib 3/3；`browser_profiles` 12/12；`browser_profile_locks` 8/8。

### 拿到非提权会话的方法（踩坑记录）

- `runas /trustlevel:0x20000 "powershell ... -File x.ps1"` 从 ssh 启动**返回 0 但什么都没跑**——受限令牌下 PowerShell 起不来。换成 `cmd /c <batch>` 就正常。
- 计划任务 `-LogonType S4U -RunLevel Limited` 实测仍然 `IsElevated=True`，且 `%TEMP%` 不同导致无关失败，**不可用**。
- `GetTokenInformation(TokenLinkedToken)` 在 ssh 会话上失败：OpenSSH 直接发全权令牌，没有 UAC 配对的 linked token。
- `New-ScheduledTaskPrincipal -UserId "$env:USERDOMAIN\$env:USERNAME"` 会报 "No mapping between account names and security IDs"——ssh 会话里 `USERDOMAIN=WORKGROUP`，要用 `[Security.Principal.WindowsIdentity]::GetCurrent().Name`。

## 八、清理

单元测试的临时目录由 `Drop` 删除；本轮未启动 App、浏览器或任何常驻服务。
