### 3.1 初稿这张表是错的，错法值得记下来

初稿写的是「8 镜、每镜 2.5 秒」，还用一句「本轮 960 帧对应零件那一镜略短」去圆
`7×75 + 450 = 975` 与实测 960 的 15 帧差额。

**那张表根本不是这条片子的**，是同一 brief 另一轮的 `storyboard.json`。逐帧比对
当场戳破：台账写镜2 是 `+27.3%`，产物里是 `+32%`；写镜3 是「新客转化提升」，
产物里是「新客户拓展」。

真结构用亮度采样量出来（零件是浅底、模板是深蓝，切点一目了然）：

```
ffmpeg -i <片子> -vf "fps=10,signalstats,metadata=print:key=lavfi.signalstats.YAVG" -f null -
→ 切点恰好落在 3.0 / 6.0 / 9.0 / 12.0 / 15.0 / 30.0 秒，无一例外
```

15 帧的差额不是「略短」，是**镜数从一开始就数错了**。这是本条线反复出现的同一个
形状：**先有一个对不上的数，然后编一个算术解释盖住它，而不是去量一遍。**
（PC-19 是同一个形状的更贵版本：所有机械读数全绿，而片子是同一段播两遍。）

面向未来的防线见 §4.1——分镜表不再靠人誊抄，由验收脚本从产物里重算并比对。

### 为什么此前一直用不上零件

不是零件缺失，是**片长写死 12 秒**：2026-07-28 对真实模型量过，12 秒预算下最短的
零件也要 4.5 秒、占掉 37%，模型每次都判定放不下——而且判得对，提示词本来就告诉它
零件时长从整片预算里扣。134 个零件在原理上够得着、实际一个都用不上。
片长控件（PC-09 / PC-19）落地之后这一项才可能通过。

## 4. 不重复：这一轮新加的门禁

**上一条被当作里程碑的成片是错的。** PC-19 记着那次抽帧比对：12 秒的片子里
t=1s≡7s、3s≡9s、5s≡11s 逐字节相同——同一段 6 秒倍速播了两遍，而编码、分辨率、
帧数、时长、静帧门禁**当时全绿**。

所以验收脚本加了 `require_no_repeated_stretch`：按 0.5 秒抽帧算指纹，查**整段
周期性复现**。

**第一版判据是错的，被真片子当场纠正。** 它把「任何两帧相同」判成重复，第一次
遇到真实成片就误判：`data-chart` 动十秒、定格五秒，64 个采样 55 个唯一，重复全在
那段定格里——而定格恰恰是动效该有的行为（`film_timeline.py` 的原话：动效是配菜，
让内容不突兀地出现，然后停在最后一帧）。改成查周期性之后拿两条真片子做对照：

| 片子 | 新判据 |
| --- | --- |
| 本轮成片（7 镜、含零件、960 帧） | 通过：63 采样 55 唯一，无周期复现 |
| 2026-07-28 那条已知有病的旧片 | **拒绝**：每 3.0 秒重复一次，17/17 帧对得上 |

两头都夹住了：既要放过好片子，也要拦住已知的坏片子。

## 4.1 镜头结构也不再靠人誊抄（2026-07-29 补）

上面 §3.1 那次错记暴露的是另一类缺口：**重复检测查的是「有没有播两遍」，
没人查「镜头是不是按分镜切的」。** 一份分镜表在证据文件里对不上产物，
当时没有任何机械手段看得见。

判据已经写好并有测试：`scripts/motion_shot_structure.py`。

1. **`describe_shots`** 打印镜头表——序号、起点、时长、合计。证据文件应当引用这段
   输出，而不是由人对着屏幕誊抄。这次错记就是誊抄错的。
2. **`refuse_duplicate_shots`** 按各段时长取每镜中点抽帧，要求任意两镜的中点画面
   不相同。这是精确判据、不需要调阈值，且**正面命中 PC-19 那类缺陷**：那条坏片的
   每个模板镜头都把整部合成重渲了一遍，各镜中点必然雷同。它与周期性检测互补——
   后者查「整段 footage 播了两遍」，这条查「两个镜头画的是同一样东西」。

**中点而不是起点**：实测这部片子的六个模板镜头**全都从同一帧开始**（3.0/6.0/9.0/
12.0 秒处亮度都是 47.26，那是入场动画尚未开始的纯背景）。按起点抽帧会把一条健康的
片子判成重复。

### 4.2 T2.2：镜头结构成为产品数据（2026-07-30 收口）

接上去需要每一镜的时长，而**分段文件在渲染结束时被产品主动删掉**
（`lib.rs` 的 `remove_dir_all(outputs.join(MOTION_SEGMENT_DIRECTORY))`，
它们只是中间产物，删得对）。`segments` 也没有到前端——Rust 侧内部消费掉了，
所以 WebdriverIO 的 spec 同样读不到。T2.2 没有为验收保留中间产物，也没有从
画面猜切点；它把这份结构做成了 `MotionRenderJobSnapshot.shotStructure`。

每一镜现在持久化两组不能互相冒充的事实：

- 授权 answer 给出的 `startFrame` / `frameCount` / `part` /
  `narrationSeconds`，任务创建时即冻结；
- ffmpeg 逐段编码之后由 ffprobe `-count_frames` 读出的
  `renderedStartFrame` / `renderedFrameCount`，不能从声明值复制。

成功任务必须有完整实测表；任一累计镜头边界偏差超过 ±1 帧、逐段数量不一致、
重复写入实测结果或最终成片总帧数不等于逐镜实测之和，任务都不能进入成功态。
旧检查点允许空表只用于读取兼容，不能伪装成一条新成功任务。TypeScript 网关也按
同一组封闭字段和不变量校验，不会把 Rust 内部可信当成前端可信。

T36 从真实 App 的成功任务读取这张表，再由外部 Python 验收器独立复算累计边界。
2026-07-30 真模型、真 TTS、真浏览器、真 ffmpeg 一轮退出 0：

| 读数 | 真实结果 |
| --- | --- |
| 成片 | H.264、1920×1080、640 解码帧、21.333333 秒 |
| 镜头 | 8 镜；声明/实测逐项为 94/94、87/87、75/75、77/77、92/92、68/68、63/63、84/84 |
| 累计边界 | 0、94、181、256、333、425、493、556、640；全部在 ±1 帧内 |
| 旁白 | AAC、21.333000 秒 |
| 画面 | 42 个抽样、42 个不同，无整段周期复现 |

这次模型选择了 8 个模板镜头（`part=null`），所以本轮证明的是结构协议和实测
边界，不重复声称“选中了某个零件”；零件镜头的 `part` 路径由 Rust/Python/前端
契约测试覆盖，PC-10 原始真实成片仍是零件入片证据。

两条不采用的路仍保留结论：为测试保留分段文件会污染产品清理语义；场景检测和
亮度突变无法可靠找出共用蓝底的模板切点。现在验收不再需要这两种推断。
