# T90 — 模型侧三种失败都说同一句话，而且那句话是错的

> 日期：2026-07-26
> 分支：`video-feedback`
> 状态：**🔍 待验收**（分层证据齐全；正式签名包上的目视验收未做，缺口见第六节）

## 一、查证结果（先查证，再动手）

失败注入实测记的现象是：

| 注入的故障 | 用户看到 | 多久之后 |
|---|---|---:|
| 模型服务连不上 | 「自动编排判定这次描述做不出来…**请换一句更具体的描述后重试**」 | 2 秒 |
| 模型连上了但不断流 | **一字不差的同一句** | 363 秒 |

### 1. 那句话在哪里产生

`frontend/src/features/video-studio/VideoStudio.tsx` 的 `AUTHORING_ERRORS.authoring_refused`。
`authoring_refused` 这个码由 `frontend/src-tauri/src/lib.rs:660-665` 产生：

```rust
Err(if motion_video_studio::answer_is_refusal(&answer) {
    motion_video_studio::authoring_refused()
} else {
    motion_video_studio::authoring_crashed()
})
```

也就是说：**编排子进程只要在非零退出时写出一份合法的「拒绝文档」，就一律被判成
`authoring_refused`**，界面于是说「判定这次描述做不出来」。

### 2. 为什么连不上和卡死都走到它——两层漏斗

**第一层（同一个 `except`）**：`backend/src/automation_tool/executor/motion_authoring/agent.py`
的 `call_video_creation_model` 里，建连失败和读超时都是 `OSError`，被同一个分支收成同一句：

```python
except OSError as error:
    raise MotionAuthoringRejected("video creation model transport failed") from error
```

363 秒这个数字对得上：`agent.py:277` 的 `MODEL_TIMEOUT_SECONDS = 360`（流式读的**分块间隔**上限）
加建连开销。Rust 侧自己的 `MOTION_AUTHORING_DEADLINE` 是 600 秒，比它晚，所以先响的是 Python 这个。

**第二层（拒绝通道被当成通用失败信封）**：`entry.py` 的 `run_motion_authoring_entry` 把
`MotionAuthoringRejected` 一律 `raise _reject(str(error))`，`serve_one_motion_authoring_request`
再把它写成 `{"status":"rejected", ...}`。Rust 的 `answer_is_refusal` 认这份文档 → `authoring_refused`。

于是「模型服务根本没被调通」被表述成「代理读完你这句话之后决定做不出来」。**没有任何东西读过那句话。**

## 四、改了什么

1. **`agent.py`**：`except OSError` 拆成两条 `raise`。读超时（裸 `TimeoutError`，或 urllib 包在
   `URLError.reason` 里的那个）走 `"video creation model timed out"`，其余传输失败保持
   `"video creation model transport failed"`。写成两条独立 `raise` 而不是三元表达式，是因为
   `test_every_fixed_upstream_rejection_has_its_own_closed_reason_token` 用 AST 扫的是常量实参——
   三元表达式会让这道门禁扫不到，两个原因就可能悄悄没有各自的 token。
2. **`entry.py`**：新原因进 `_ENTRY_REASON_TOKENS`（顺手删掉原来那条只为传输失败开的 `if` 分支，
   两处合并成同一张表）；新增 `_MODEL_SERVICE_REASONS` 与 `_MODEL_UNUSABLE_STATUS`，模型服务这三类
   原因写出的答复 `status` 不再是 `rejected`，于是 `answer_is_refusal` 不再认它。文档仍然带着自己的
   封闭 token。
3. **`contracts/video/motion-authoring-refusal.v1.json`**：加 `video_creation_model_timed_out`。
4. **`VideoStudio.tsx`**：四条编排失败文案重写。判据是**只有真的读过这句话的失败才有资格让用户去改
   这句话**，所以只有 `authoring_refused` 保留「换一句更具体的描述」。

失败态现在分四类：

| 码 | 说什么 | 用户该做什么 |
|---|---|---|
| `authoring_refused` | 读完之后判定这次描述做不出来；不是网络或模型服务的问题 | 换一句更具体的描述 |
| `authoring_crashed`（现在也含模型服务连不上 / 接上后不再回应） | 没能完成；不是描述的问题 | 检查网络 → 到「设置与诊断」测模型服务 → 重试 |
| `authoring_timed_out` | 超时停下；多半是模型服务一直没回应 | 稍后重试 |
| `authoring_answer_invalid` | 结果没过本机校验；是我们这边的问题 | 重试，反复出现请反馈 |

## 五、失败矩阵

| 情形 | 现在的行为 |
|---|---|
| 模型服务连不上（端口没人听 / DNS / 拒连） | `model_unusable` + `video_creation_model_transport_failed` → `authoring_crashed` → 文案点名网络与模型服务 |
| 模型接上后不再发数据（360 秒分块超时） | `model_unusable` + `video_creation_model_timed_out` → 同上 |
| 模型未配置 | `video_creation_model_unavailable` → 同上 |
| 编排子进程超过 600 秒没退出 | Rust 杀掉 → `authoring_timed_out` |
| 代理读完 brief 后按协议拒绝 | 仍是 `rejected` → `authoring_refused` → 唯一会叫用户改句子的一条 |
| 子进程崩溃、stdout 不是协议文档 | `authoring_crashed`（原行为不变） |
| 子进程退 0 但答复过不了本机校验 | `authoring_answer_invalid`（原行为不变） |
| 密钥泄漏 | 答复只带封闭 token，`test_the_child_process_answers_one_json_document_and_never_echoes_the_key` 仍绿 |

## 六、真实边界与遗留

**没做到「连不上说连不上、超时说超时」。** 两者现在都落在 `authoring_crashed`，说同一句话——
只不过那句话是对的（点名网络和模型服务），不再是错的（叫用户改描述）。

原因是硬的：`MotionVideoStudioError` 只有 `{code, retryable}` 两个字段
（`motion_video_studio.rs:93-96`），`command_error::serialize` 的 `message` 也只由 `code` 推导；
`answer_is_refusal` 把 `rejectionReason` 读出来**只用于判真假，随即丢弃**。子进程能让 Rust 区分的
只有两类：写出合法拒绝文档 → `refused`，其余 → `crashed`。

补齐要动 `.rs`，本轮被明确排除（另一条线正在改 `frontend/src-tauri/src/*.rs` 并会跑一次全局
`cargo fmt`）。改法已经铺好，是机械的：

1. `motion_video_studio.rs`：`MotionVideoStudioErrorCode` 加两个变体
   （如 `AuthoringModelUnreachable` / `AuthoringModelTimedOut`）与对应构造函数；
2. `lib.rs`：`answer_is_refusal` 的分支改成先读回 `rejectionReason`，把
   `video_creation_model_transport_failed` / `video_creation_model_timed_out` 映到新码；
3. 前端 `AUTHORING_ERRORS` 加两条文案，`NATIVE_ERRORS` 与 `MaterialVideoStudioErrorCode` 各加两个码。

Python 侧和契约侧已经把这两个原因分开并有测试守着，第 2 步有东西可读。

**其他遗留：**

- `vendor/hyperframes` 在这棵 worktree 是空的（本树是 `git worktree add` 建的，没走
  `scripts/new_worktree.py`），所以走通模型的完整编排链路跑不起来；本任务的验证都停在
  `call_video_creation_model` 与答复写入这两层，没有跨过 `MotionAuthoringAgent`。
- 同样因为 vendor 为空，`scripts/check_user_facing_branding.py` 在本树直接报
  `configured scan root does not exist: vendor/moneyprinterturbo/webui`，无法作为本轮文案门禁。
  新文案只用了「视频创作模型服务」「设置与诊断」，均为产品已在用的说法。
