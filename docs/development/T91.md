# T91 — 提交后切页等于永远没有任何提示（静默失败），以及等待期间没有文字

> 日期：2026-07-26
> 分支：`video-feedback`
> 状态：**🔍 待验收**（含真实用户路径的 Playwright 无头验收；正式签名包上的目视确认未做，缺口见第六节）

## 一、查证结果（先查证，再动手）

实测记的现象是：任务第 4 秒就失败了，切到别的页面再回来，任务列表显示「还没有真实制作任务」，
**第 12 分钟界面仍然什么都不说**；全屏关键词扫描（做不出来 / 超时 / 出错 / 失败 / 不可用 / 无法）
全阴性。另：等待期间只有一个转圈的按钮，`setSubmitMessage(null)` 清空后不写新提示。

### 1. 三个成因里，两个在 HEAD 上已经不成立了

那次失败注入跑的是 `a109178`（22:04）之前的构建。`a109178`「生成期间切页面不再丢掉任务、句子和失败」
把运行状态搬出了 React 组件（新增 `motion-run-store.ts`），它已经是本分支基线 `515dce1` 的祖先：

```
$ git merge-base --is-ancestor a109178 HEAD && echo "a109178 IS ancestor of HEAD(515dce1)"
a109178 IS ancestor of HEAD(515dce1)
```

- 证据里点名的 `setSubmitMessage` 在 `VideoStudio.tsx` 已经不存在（`git show a109178^:...` 里还有，
  第 1095 行）。**等待期间没有任何文字**这一条，在 HEAD 上已经修掉：提交即写 `pending`，
  自动切到「制作任务」页，卡片上有走字的钟。
- **失败写进已卸载组件因而永久丢失**这一条也修掉了：结果写进 store，回到页面能看到红条。

所以本任务在 HEAD 上要修的不是原样的三条，而是**剩下的两个真洞**。

### 2. 洞一：侧边栏那个标记在说谎（这才是「第 12 分钟什么都不说」的真身）

`WorkbenchShell.tsx` 用 `motionRunNeedsAttention()` 打一个标记，而它只返回布尔：

```ts
export function motionRunNeedsAttention(current: MotionRunState): boolean {
  return current.pending !== null || current.message !== null;
}
```

失败和进行中共用 `true`，于是渲染出来的是同一个东西——一个**蓝点**，外加一句只有悬停才看得见的
`title="视频制作正在进行中"`。跑失败注入的那次全屏关键词扫描之所以全阴性，正是因为：

- 点本身没有文字；
- 唯一那句文字写的是「正在进行中」——它不但没说失败，还在说这条正在跑。

**标记在，只是它在说谎。** 这是本项目反复吃亏的静默失败的标准形状。

`frontend/e2e/video-studio-one-sentence.spec.ts` 还把这个行为写进了断言（该用例走的正是一次失败提交）：

```ts
await expect(videoEntry.locator("[title='视频制作正在进行中']")).toBeVisible();
```

### 3. 洞二：等待期间有钟，但没有参照物

`motionPendingLabel` 给的是「正在自动编排这条视频 · 已用 1 分 34 秒」。钟回答的是「它还活着吗」，
回答不了「这算久吗」。没有参照物，一次正常的 2 分钟等待和一次已经挂掉的等待在屏幕上长得一模一样——
于是要么白等，要么在正常范围内就重新提交，真的再跑一遍编排。演示当天更糟：讲解人得当着客户面盯着
一个不知道要转多久的圈。

## 四、改了什么

1. **`motion-run-store.ts`**：`motionRunNeedsAttention(): boolean` 换成
   `motionRunAttention(): "none" | "running" | "failed"`。一个布尔表达不了两种意思，而
   「用同一个标记表示两种意思」正是这次说谎的根。旧函数已删，四处调用点全部改完。
2. **`WorkbenchShell.tsx`**：进行中仍是蓝点 + `title`；失败改成带文字的红色角标「失败」，
   `title` 改成「视频制作失败了，去看看」。失败态下这一项的无障碍名变成「视频制作 失败」——
   这是要的效果而不是代价（屏幕阅读器正是静默失败最静默的地方），且只在失败分支上发生；
   仓库里选中这一项的写法（Playwright 的 `getByRole` 子串匹配、桌面套件的 `normalize-space()`
   XPath）本来就容忍它。
3. **`VideoStudio.tsx`**：等待卡片的钟后面加实测参照物
   `MOTION_AUTHORING_MEASURED`（中位数 124 秒、最长 178 秒，2026-07-26 连续七次成功）。
   说给人听时取整到分钟——「通常 2 分 4 秒」是七次运行的中位数不配有的假精度。
   超过实测最长的那次之后，改说「已经超过实测最长的 3 分钟，可能是视频创作模型服务没有回应」：
   前半句是事实，后半句是最可能的成因，不是「已经失败了」的断言——这里没有任何东西知道那件事。
4. **`frontend/e2e/video-studio-one-sentence.spec.ts`**：把写进断言的旧行为改成新行为。

刻意**没有**做的事：没有弹窗、没有 toast、没有任何打断性的东西。演示当天弹一堆东西比不说话更难看。
失败就是侧边栏上一个红色的「失败」，加上回到页面后原本就有的那条红色 Alert。

## 五、失败矩阵

| 情形 | 现在的行为 |
|---|---|
| 编排在用户切页之后失败 | 侧边栏出现红色「失败」文字（无需悬停），无障碍名变为「视频制作 失败」；回到页面看到红色 Alert 与原因 |
| 编排正在跑，用户切页 | 蓝点 + `title=视频制作正在进行中`（未变） |
| 用户读过失败并关掉 Alert | `dismissMotionRunMessage` → attention 回到 `none`，标记灭掉 |
| 成片做好，用户点「去看成片」 | `forgetMotionJob` + `dismissMotionRunMessage` → 标记灭掉（未变） |
| 等待处于实测正常范围内 | 钟 + 「通常 2 分钟左右，最长约 3 分钟」，不报警 |
| 等待超过实测最长 178 秒 | 钟 + 「已经超过实测最长的 3 分钟，可能是视频创作模型服务没有回应」 |
| 手工模板提交（非一句话） | 只有钟，不套用编排的实测值——那是本机渲染，时间尺度不同 |
| App 重启 | store 在内存里，标记不跨重启；任务快照仍由原生侧恢复（未变） |

## 六、真实边界与遗留

**已知仍未覆盖：渲染阶段失败且用户不在这一页。**

`refresh()`（每 2 秒轮询 `gateway.motionJobs()`）只在 `VideoStudio` 挂载时跑，外壳一切页就把它卸载了。
所以：提交成功 → store 记的是 info 消息「已提交…本机渲染开始了」→ attention 是 `running`（此刻属实）
→ 用户切走 → 渲染失败 → **没有任何东西去查，标记仍是蓝点「正在进行中」**。回到页面才会在任务卡上
看到失败。

没有修，理由是权衡而不是遗忘：

- 修它要把轮询搬到组件外（store 持有 gateway，或外壳自己起一条），会动共享外壳代码，而当前有四条线
  在并行改这个仓库；
- 窗口很短：实测一段 12 秒的成片渲染约 10 秒，而编排是 2–3 分钟。实测记到的那次失败（第 4 秒）在
  编排阶段，正是本次修掉的那半；
- 半修比不修更危险——真要做就该做成一个明确的、有测试的外壳级监视器。

登记为后续任务的输入，不要当成已解决。

**其他边界：**

- 本轮验收最高只到 UI Harness（Playwright 无头 Chromium + 测试用 React 页面）。按项目规则，这只能
  证明 React 业务交互，不能证明正式 App 的 IPC、原生桥和 Sidecar 生命周期。
- 侧边栏那个红色角标在 232px 宽的侧栏里是否会被 Ant Menu 的 `overflow: hidden` 裁掉，jsdom 与
  Playwright 的 `toBeVisible()` 都不判定裁剪。需要在正式包上看一眼。
