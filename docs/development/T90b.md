## 一、要解决的是什么

T90 把「模型服务用不了」从「你的描述做不出来」里救了出来，但只救到一半：三种失败仍然
落在同一个 `authoring_crashed` 上，说同一句话。它自己写清了原因——
`MotionVideoStudioError` 只有 `{code, retryable}`，`answer_is_refusal` 把 `rejectionReason`
读出来只用于判真假，随即丢弃，所以子进程能让 Rust 区分的只有「拒绝 / 非拒绝」两类。

还有一个比模型这条路更宽的漏斗口：`vendor` 缺文件这种纯打包缺陷，走的是同一条拒绝通道，
界面同样说「请换一句更具体的描述」。**没有任何一句描述的改写能把缺失的文件放回去。**

## 二、最终分成几类，每类说什么

判据只有一条：**只有真的读过这句话的失败，才有资格让用户去改这句话。**

| 码 | 什么情况 | 界面告诉用户去做什么 | 可重试 |
|---|---|---|---|
| `authoring_refused` | 代理读完这句描述之后判定做不出来 | **换一句更具体的描述**（唯一一条） | 是 |
| `authoring_model_transport_failed` | 完全没收到模型服务的回应 | 先查网络，再到「设置与诊断」测试视频创作模型服务 | 是 |
| `authoring_model_timed_out` | 已经接上模型服务，但超过允许的最长等待时间没有再返回内容 | 网络是通的，别去查网络；稍后重试，或换一个模型 | 是 |
| `authoring_installation_damaged` | 我们自己的锁定文件没过完整性校验 | **重新安装 App**；明说重试没有用 | **否** |
| `configuration_required` | 模型没配，或配了但不可用（地址非 https、密钥格式不对等） | 到「设置与诊断」配置并测试视频创作模型服务 | 否 |
| `authoring_timed_out` | 整个编排子进程超过 Rust 的最长时间被杀 | 稍后重试 | 是 |
| `authoring_crashed` | 子进程没写出协议文档就死了；请求本身不合法；答复自相矛盾；本版本不认识的类别 | 是我们这边出错，请重试，反复出现请反馈 | 是 |
| `authoring_answer_invalid` | 答复没过本机校验 | 同上（措辞不同，不与 crashed 撞句） | 是 |

`authoring_installation_damaged` 是这批里唯一 `retryable: false` 的：同样的文件读第二遍
还是过不了校验。**但要说清楚——视频制作这一侧今天没有任何代码读 `retryable`**
（`grep` 过：`material-video-studio-gateway.ts` 只是把它挂在错误对象上，没有消费者）。
所以用户看到的差别**只来自文案本身**——那句话明说了重试没有用。把标志设对是为了将来
真去读它的人拿到的是事实，而不是一个为了跟其他码一致而随手填的值。

### 分类表放在哪里

放在 `contracts/video/motion-authoring-refusal.v1.json` 新增的 `nonRefusalOutcomes`，
Python 和 Rust 都从它读，谁都不留第二份。类名同时就是子进程写出的答复 `status`，
所以不需要再维护一张「类 → status」的对照表。

只认识 `rejected` 的旧 App 看到陌生 status 会退回「我们没能完成」——是错的但无害；
被挡住的是反方向那件事：一个没人读过的失败挂着 `rejected`，会被完全正确地理解成
用户的句子有问题。

## 五、改了什么

1. **`contracts/video/motion-authoring-refusal.v1.json`**：新增 `nonRefusalOutcomes`，
   把 29 个 token 分进 5 个类；`rationale` 增加一段说明为什么这样分。两侧都校验：
   类名是 wire token 且不等于 `rejected`、每类非空、token 有序去重、⊆ `fixedReasons`、
   **类之间不重叠**（重叠会让同一个 token 按迭代顺序随机归类，两侧看起来都自洽，
   而卡片不同日子说不同的话）。
2. **`entry.py`**：删掉写死的 `_MODEL_UNUSABLE_STATUS` 与 `_MODEL_SERVICE_REASONS`，

3. **`motion_video_studio.rs`**：新增三个错误码变体与构造函数；
   `answer_is_refusal` 删除，换成 `classify_failed_authoring_answer`；
   `rejection_reason_is_closed` 改为接受已解析的契约（原来自己重新解析一次）。
4. **`lib.rs`**：子进程非零退出的分支从「二选一」改为调用上面那个分类函数。
5. **前端**：`MaterialVideoStudioErrorCode` 与 `NATIVE_ERRORS` 各加三个码；
   `AUTHORING_ERRORS` 增加三条文案，并改写 `authoring_timed_out` 与 `authoring_crashed`
   （见第七节）；`configuration_required` 的一句话文案从「配置」改为「配置并测试」，
   因为它现在也承接「配了但不可用」。

### 分类逻辑（Rust）

以**原因 token 为准**，status 只做旁证：

1. 文档解析不出来 / `schemaVersion` 不是 1 → `authoring_crashed`；
2. 没有 token → 只按 status 判：`rejected` 就是拒绝，否则 crashed（旧 Executor 只写过拒绝文档）；
3. token 不在封闭词表内 → `authoring_crashed`（原行为不变）；
4. token 属于某个非拒绝类，且 status 等于该类名**或**等于 `rejected` → 该类对应的码
   （允许 `rejected` 是为了 T90 之前的 Executor：那时这些原因还挂在拒绝 status 上）；
5. token 属于某类但 status 指向**另一个**类 → `authoring_crashed`。证据自相矛盾时
   一律往「我们的错」解，绝不往「用户写错了」解；
6. token 是真正的拒绝原因 → 按 status 判拒绝。

## 六、失败矩阵

| 情形 | 现在的行为 |
|---|---|
| 模型服务连不上 / DNS 解析不了 / 拒连 / TLS 失败 / 中途连接被重置 | `model_transport_failed` → `authoring_model_transport_failed` → 文案点名网络与服务地址 |
| 模型接上后不再发数据（360 秒分块超时） | `model_timed_out` → `authoring_model_timed_out` → 文案明说网络是通的 |
| 模型未配置 / 已保存的配置不可用 | `model_configuration_required` → `configuration_required` |
| `vendor` 缺文件、锁定文件摘要漂移、契约文件读不出 | `installation_damaged` → `authoring_installation_damaged` → 唯一一条说「重新安装」且不可重试 |
| App 发出的请求本身不合法（形状、schema 版本、过大、workspace 不可用） | `app_request_invalid` → `authoring_crashed` |
| 代理读完 brief 后按协议拒绝 | 仍是 `rejected` → `authoring_refused` → **唯一**会叫用户改句子的一条 |
| 静态门禁失败（封闭 gate code 子集） | 不属于任何非拒绝类 → `authoring_refused`（模型产出的问题，换个描述确实可能有用） |
| 子进程崩溃、stdout 不是协议文档 / 被截断 | `authoring_crashed`（原行为不变） |
| 原因 token 不在封闭词表内（含试图塞入本机路径） | `authoring_crashed`，且 token 本身不外泄（原有用例仍绿） |
| status 与 token 指向不同类 | `authoring_crashed` |
| 契约里出现本版本不认识的新类 | `authoring_crashed`；Rust 侧 `expected_code_for_class` 会 panic，门禁当场红 |
| 契约被改成两个类共用一个 token | 两侧 `outcomes_are_declared` 都判整份契约无效 |
| 编排子进程超过 Rust 的最长时间没退出 | Rust 杀掉 → `authoring_timed_out` |
| 密钥泄漏 | 答复仍只带封闭 token，`test_the_child_process_answers_one_json_document_and_never_echoes_the_key` 仍绿 |

## 七、判断不了的、以及我没有硬造的区分

**（1）`model_transport_failed` 内部分不出来，所以我没分。**
`call_video_creation_model` 里，除超时以外的所有 `OSError` 走同一条 `raise`：连接被拒、
DNS 解析失败、TLS 握手失败、连上之后连接被重置，到这一层已经是同一个异常类型、
同一个 token。因此**没有**做「连不上」和「连上后断了」的子分类。

这也是为什么这个码叫 `transport_failed` 而不是 `unreachable`：上面四种里有一种是**已经
连上过**的，说「连不上」对那一种就是错的。文案写的是「没有收到……任何回应」——四种都成立。

**（2）`authoring_timed_out` 的成因分不出来，所以文案不猜。**
Rust 的最长时间到了就杀子进程，子进程没写出任何东西，这一侧不知道它当时卡在哪。
原文案写的是「多半是视频创作模型服务一直没有回应」——那是猜的，而且现在那种情况已经
有了自己的码，继续这么猜就是错的。

**（3）`authoring_crashed` 是我**有意**合并的，不是分不出来。**
子进程无输出而死、请求不合法（`app_request_invalid`）、答复自相矛盾、本版本不认识的类，
在内部是能分开的，但**用户能做的事完全一样**（重试，反复出现就反馈），拆成四条文案
只会让人多读三遍同样的话。分开保留在 token 层面，排查时看得到。

## 八、真实边界与遗留（这部分是缺口，不是成绩）

**（a）仍然会被说成「换一句更具体的描述」的失败。**
下面这些 token 不属于任何非拒绝类，因此仍然落在 `authoring_refused`：
`agent_workspace_required`、`agent_workflow_reference_required`、
`agent_not_a_motionauthoringtools_instance`、`agent_tool_surface_does_not_match_the_closed_allowlist`。
它们都是内部编程错误，不是用户的句子。**没有收进来的理由是：** 它们从 `entry.py` 这条路
结构上到不了（构造 `MotionAuthoringAgent` 的参数是本进程自己给的），而为了「分类整齐」
把够不到的东西编进类里，正是这次被明确要求不要做的事。如果将来它们变得可达，这条要补。

**（b）`installation_damaged` 里有一半今天走不到这条通道。**
`agent_locked_motion_catalog_*`、`agent_render_canvas_contract_*`、
`agent_one_sentence_brief_contract_*`、`agent_storyboard_duration_contract_*` 这八个 token
对应的加载函数是**模块导入期**执行的（`agent.py` 的模块级赋值），导入失败会让子进程直接
带 traceback 退出、stdout 为空，于是本来就走 `authoring_crashed`——不冤枉用户。
把它们列进类里是为了这些加载器哪天改成惰性时不至于漏掉，**今天没有被真实路径覆盖**，
只被 Rust 那条契约驱动的用例逐 token 走过（用的是 fixture 子进程，不是真实加载失败）。
真实路径覆盖到的是 `load_locked_authoring_workflow` 那一组，用空 vendor 目录实测过。

**（c）「超时到底是多久」没有写进文案。**
`MODEL_TIMEOUT_SECONDS = 360` 只存在于 `agent.py`，既不在契约里也不在前端。
在 TSX 里写死「6 分钟」会变成一份没人守的副本，改了后端不会有任何东西转红。
所以文案写的是「超过允许的最长等待时间」。要说出具体数字，得先把这个值下沉到契约——
那是另一个任务。

**（d）本 worktree 的 `vendor` 是空的**（用 `git worktree add` 建的，没走
`scripts/new_worktree.py`）。因此：走通模型的完整编排链路跑不起来，本任务的 Python 验证
停在 `call_video_creation_model` 与答复写入两层；`scripts/check_user_facing_branding.py`
直接报 `configured scan root does not exist: vendor/moneyprinterturbo/webui`，无法作为
本轮文案门禁。改用逐条比对 `contracts/quality/user-facing-terminology.v1.json`：
新文案对 `plainLanguageMappings` 的全部禁用词零命中，全部 ASCII 词只有 `App` 一个
（产品既有说法，`protocol_mismatch` 文案早就在用）。

**（e）文案是否有被说得更含糊的。** 有一处，且只有一处：`authoring_timed_out` 去掉了
「多半是视频创作模型服务一直没有回应」。它比原来说得少，但原来那句在拆码之后已经是错的
（真属于模型不回应的情况现在走 `authoring_model_timed_out`）。剩下的每一条都比原来说得更具体。
**没有任何一种真实失败因为这次改动而被隐藏或被说得更含糊。**

## 十、验收缺口（为什么是 🔍 待验收）

正式签名包里没有 WebDriver，本轮拿到的是分层证据：

- ✅ 单元/组件（pytest 1176、vitest 537、cargo 429）
- ✅ 契约（分类表由 Python 与 Rust 双向校验；Rust 侧逐 token 驱动真实子进程）
- ✅ 真实故障注入（真 socket 的连不上/卡死；真实空 vendor 目录触发的锁定文件缺失）
- ❌ **正式 App 正常用户入口的目视确认**：在「视频制作 → 品牌动效成片 → 一句话自动制作」
  提交，分别把模型端点指到 (1) 一个没人监听的端口、(2) 一个接受连接后不回数据的端口，
  确认卡片上分别出现两条**不同**的新文案；再把某个锁定文件改一个字节，确认卡片说的是
  「请重新安装 App」而不是「请换一句更具体的描述」。这三步要在签名包上人工做。
  （第三步只看文案：如上所述，界面目前不因 `retryable` 改变任何控件。）
