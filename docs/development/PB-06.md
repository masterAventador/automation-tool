## 实现要点

### 复用而不是新建

开工前先查了既有可复用件，三处直接接上而不是另起炉灶：

- **临界点确认**：`browser_use_safety.SideEffectConfirmationGate` 在 BU-05 就已建好
  （展示 `目标账号 + 内容摘要` → 用户确认 → 单次派发令牌），此前没有任何生产调用方。
  PB-06 是它上线的地方，不再另写一套确认对象。
- **本地硬门禁**：复用 `LocalActionHardPolicy` 与 `ledger.bind_action_hard_policy`，
  发布与任务动作共用同一份单调收紧的最小间隔绑定；紧急停止直接读既有
  `executor_action_guard` 闩锁，一键紧停同时覆盖任务动作与发布。
- **状态机词汇**：复用 `SideEffectState` 的 `prepared/dispatched/verified/uncertain`
  与 `prepare → begin → settle` 协议形状。

同时收敛了两处重复定义：SHA-256 十六进制形状此前在
`publish_artifact.py`（常量 + 内联 `any(... not in "0123456789abcdef")`）和
`browser_use_safety.py`（`_SHA256_PATTERN` 正则）各有一份，统一为
`protocol/safe_text.is_sha256_hex`。

### 为什么发布不能挂在既有副作用台账上

`executor_side_effects` 要求一条 `executor_action_admissions` 记录（控制面 Ed25519
签名的动作授权）、一条 `executor_attempt_checkpoints`（任务尝试）以及控制面下发的
入站命令。发布是**本地操作员确认**的，没有任务、没有尝试、没有控制面签名。把它塞进去
只能靠伪造这些前置状态，等于为了复用而放宽既有路径的保证。

因此新建 `executor_publish_dispatches` 窄表（schema v8）：同一个 ExecutorLedger 文件、
同一套 0o700/0o600 私有目录与迁移机制、同一个状态机形状，但只存
`publish_job_id + content_hash + 状态 + 三个时间 + 验证指纹 + revision`，
发布正文一个字都不落库。

### 至多一次是怎么保证的

四道闸，任何一道不过都不会有点击：

1. **确认绑定**：回执、填进页面的 intent、用户确认三者的 `content_hash` 必须相等，
   且目标账号必须与回执一致；读不出目标账号的页面根本不产生确认（不向一个叫不出名字的
   账号发视频）。
2. **单次令牌**：只有确认闸门能签发，且只在用户答“是”之后；`consume_dispatch` 单次消费。
   令牌在**台账授权之前**消费——台账拒绝时不会留下一个还能再花的令牌。
3. **持久台账**：`begin_publish_dispatch` 是 `BEGIN IMMEDIATE` 下的
   `prepared → dispatched` 原子跃迁，四线程并发只有一个拿到授权（有并发用例）。
   已结算的 job 再来只回放既有终态，永不重新授权。
4. **界面租约**：点击前最后再校验一次本执行器仍持有可见界面，用户中途接管的页面不会被
   背着点。

### 独立证据

点击后**不看提交页自己的提示**，改为导航到作品管理页 `/creator-micro/content/manage`，
按冻结锚点定位作品标题行，用 `element_handles()` 一次性钉成快照后在进程内比对标题：

- 恰好 1 条可见匹配 → `verified`；
- 0 条 → `work_not_listed` → `outcome_uncertain`；
- ≥2 条 → `work_listed_ambiguously` → `outcome_uncertain`。

标题是用户内容，**绝不拼进选择器**（有专门的注入用例断言请求过的 selector 里不含标题）。
读取上限 50 行，超出即拒绝而不是逐行慢扫。

## 真实边界

1. **同名作品无法区分**。验收按“恰好一条可见的同名作品”判定。若本次发布失败、而账号里
   恰好已存在**一条**同名旧作品，会被误判为 `verified`。严格做法是发布前先取作品列表基线
   再做差集，但发布前那一步已经在 PB-05 结束时占住了填好的表单页，取基线要么再开一个页面
   （破坏单一可见运营窗口的不变式），要么把基线前移到发布任务编排层——归 PB-07。
   **这条是已知缺口，不是已解决问题。**
2. **平台侧标题截断未覆盖**。抖音作品列表若对长标题做省略号截断，`inner_text()` 读到的
   不等于确认的标题，结果会落到 `work_not_listed`（安全方向，转人工），但会误报。
   本期标题上限 30 字符，实际触发概率低，没有真实账号可验证。
3. **确认闸门是进程内状态**。`SideEffectConfirmationGate` 的待确认表在内存里，执行器重启
   后待确认的批准全部消失（表现为 `publish_not_dispatched`，需重新确认）。持久化到台账
   在本期没有价值——重启后填好的页面本来也没了。
4. **一次批准只够一次尝试，哪怕那次没按下去**。批准在派发命令进来时即被花掉，所以
   “表单已改版”“界面被拿走”这类没有点击的失败之后，必须重新走一次发布前流程才能再确认。
   这是有意的：让一个失败过的页面状态被原地重新批准，等于放宽“确认的是我看到的那一页”。
4. **没有真实抖音账号**。发布页、作品管理页、风控页全部由 `tests/fixtures/
   douyin_publish_states.html` 自建 fixture 提供；真实平台最终状态验收未做。
5. **App 入口未接**。`latest_approval()` / `latest_release()` 只是观察点，Tauri 侧投影与
   用户可见的确认界面归 PB-07；本任务没有任何前端改动。
6. **空作品列表在真实浏览器里高度为零**。开发中实测：一个没有任何子节点的列表容器
   会被 Playwright 判为不可见，于是“列表加载了但没有该作品”与“列表没加载”混成一种结果。
   fixture 已按真实创作者页补了空态节点把两条路径分开；真实抖音页是否总是渲染空态
   **未经真实账号验证**。两种结果都落在 `outcome_uncertain`，没有安全方向的差异。

## 开发中发现并修正的两处设计问题

**一、派发失败不该杀掉执行器。** 最初 `_dispatch` 对“找不到可用批准”直接抛
`PlatformCommandRejected`，而 worker 收到它会终止整个命令循环。但“批准已失效”是完全正常的
用户路径（操作员中途做了别的事、界面已归还），把它当协议违规等于白送一个拒绝服务：任何能
发一帧的人都能让执行器退出。改为返回 `publish_not_dispatched` 回执；只有模型根本产生不出的
帧（缺 job/确认标识）才继续抛。

**二、台账 schema 版本号在五处各写了一遍字面量。** 加了 v8 迁移后，三处单元断言当场变红、
很好改；但第四处在集成层（`test_local_executor_process.py`，真实执行器进程启动后核对
`PRAGMA user_version`），单元与相关包测试全绿，**只有全量门禁才抓到**。既然同一个数散在五处
就必然还会再漏，改为导出 `EXECUTOR_LEDGER_SCHEMA_VERSION` 并让所有断言引用它。

**三、`stale_confirmation` 同时存在于两个位置。** 批准是在页面检查之后才消费的（否则一次
瞬时的页面抖动就白白烧掉用户的确认，逼人重新确认），所以陈旧确认可能发生在台账登记前
（无记录）也可能在之后（记录停在 `prepared`）。回执校验器最初只允许前者，被真实用例打红，
按“两种组合都真实可达”放开。
