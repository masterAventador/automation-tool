# T68 登录报「暂时无法完成账号操作，请稍后重试」

日期：2026-07-26

## 症状

用户在 `/Applications/自动化运营工具.app` 里用演示账号登录，界面报「暂时无法完成账号操作，请稍后重试」，进不到工作台。

## 结论先行

失败点**不在设备绑定，而在登录本身**：服务端已返回 201，App 在**校验响应头**时把这次登录判为协议违规，于是登录函数直接返回错误，绑定请求从来没有被发出过。

- 真实错误码：`ControlPlaneErrorCode::ProtocolInvalid` → 命令层 `"operation_unavailable"`
- 产生位置：`frontend/src-tauri/src/control_plane.rs:1822`
  （`validate_response_metadata` 中 `metadata.request_id.as_deref() != Some(expected_request_id)`）
- 根因：边界 nginx `proxy_set_header X-Request-ID $request_id;` 无条件用 nginx 自己生成的 ID
  覆盖了 App 送来的 `x-request-id`，导致服务端回显的值必然与 App 期望的值不一致。

## 证据链

### 1. 静态定位

`control_plane.rs` 的 `execute()` 在每次请求前生成一个 UUID v4 作为 `x-request-id`，并在
`validate_response_metadata` 里要求响应回显同一个值，否则报错：

- `control_plane.rs:1562` `let request_id = new_request_id()?;`
- `control_plane.rs:1578` `.header(REQUEST_ID_HEADER, &request_id)`
- `control_plane.rs:1822` `|| metadata.request_id.as_deref() != Some(expected_request_id)`
- 因为 201 属于 `accepts_status`，走 `control_plane.rs:1827` 的 `ProtocolInvalid` 分支
- `lib.rs:2031` `ProtocolInvalid | RequestRejected => "operation_unavailable"`
- `AccountSessionGate.tsx` 只识别 `authentication_invalid` / `recovery_invalid` /
  `session_invalid` 三个码，`operation_unavailable` 落到兜底文案

服务端行为：`backend/src/automation_tool/control_plane/api/errors.py:104-111`
读取**请求头**里的 `x-request-id` 并原样回写到**响应头**。所以只要入站头被中间层改写，
回显值就一定和 App 期望的不一致。

边界改写点：`deploy/cloud/nginx-site.conf.template:75`
（线上实际文件 `/etc/nginx/sites-available/automation-tool-demo.conf:75`）。

### 2. 运行时取证（真实域名 `at.xuanbai.tech`）

未认证探针，确认头被改写：

```
SENT     x-request-id: aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeeeee
RECEIVED x-request-id: 4c1a6095fc8f82c6fbb49d48baa70c49
```

真实演示账号登录成功（201）时同样被改写，且其余三项校验全部合格：

```
SENT     x-request-id: 12345678-1234-4234-8234-123456789abc
RECEIVED x-request-id: d53bf8c309385a891ae8cf3daa0a3d84
STATUS:  HTTP/2 201
CACHE:   cache-control: no-store          （合格）
CTYPE:   content-type: application/json   （合格）
```

即：状态码、Content-Type、Cache-Control 三项都通过，**只有 request-id 回显对不上**，
这正好是 `control_plane.rs:1822` 的那一个条件。

### 3. 与既有观测完全吻合

- nginx 只有两条登录 201，没有 challenge 请求 —— 因为登录在客户端就判失败了，绑定没被调用；
- 也没有回滚用的 logout —— logout 只在登录成功后的绑定失败分支里才发，登录既然失败就不会走到；
- 账号密码、TLS、服务端绑定端点、token 格式、serde 映射全部正常 —— 它们本来就不是失败点。

### 4. 为什么门禁没拦住

开发与自动化验收里 App 直连 loopback 上的 FastAPI，不经过边界 nginx；
边界 nginx 只存在于云端 Demo 这一条路径上，从来没有被端到端跑过。

## 失败矩阵

| 场景 | 结果 |
| --- | --- |
| 调用方送合法 `x-request-id` | 原样透传，App 回显比对通过 |
| 调用方不送 | nginx `$request_id` 兜底，服务端仍能生成日志关联 ID |
| 调用方送非法字符 / 超长 | 服务端 `_REQUEST_ID_PATTERN` 拒绝并自行生成，不写回污染值 |
| 边界配置写错 | `nginx -t` 在部署脚本 reload 前拦截 |
| 回归到旧写法 | 两份模板各有一条门禁测试直接 fail |
