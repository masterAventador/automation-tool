# T68 登录报「暂时无法完成账号操作，请稍后重试」

日期：2026-07-26

## 症状

用户在 `/Applications/自动化运营工具.app` 里用演示账号登录，界面报「暂时无法完成账号操作，请稍后重试」，进不到工作台。

## 结论先行

失败点**不在设备绑定，而在登录本身**：服务端已返回 201，App 在**校验响应头**时把这次登录判为协议违规，于是登录函数直接返回错误，绑定请求从来没有被发出过。

- 真实错误码：`ControlPlaneErrorCode::ProtocolInvalid` → 命令层 `"operation_unavailable"`
- 产生位置：`frontend/src-tauri/src/control_plane.rs:1822`
  （`validate_response_metadata` 中 `metadata.request_id.as_deref() != Some(expected_request_id)`）
- 根因：边界 nginx `proxy_set_header X-Request-ID $request_id;` 无条件用 nginx 自己生成的 ID
  覆盖了 App 送来的 `x-request-id`，导致服务端回显的值必然与 App 期望的值不一致。

## 证据链

### 1. 静态定位

`control_plane.rs` 的 `execute()` 在每次请求前生成一个 UUID v4 作为 `x-request-id`，并在
`validate_response_metadata` 里要求响应回显同一个值，否则报错：

- `control_plane.rs:1562` `let request_id = new_request_id()?;`
- `control_plane.rs:1578` `.header(REQUEST_ID_HEADER, &request_id)`
- `control_plane.rs:1822` `|| metadata.request_id.as_deref() != Some(expected_request_id)`
- 因为 201 属于 `accepts_status`，走 `control_plane.rs:1827` 的 `ProtocolInvalid` 分支
- `lib.rs:2031` `ProtocolInvalid | RequestRejected => "operation_unavailable"`
- `AccountSessionGate.tsx` 只识别 `authentication_invalid` / `recovery_invalid` /
  `session_invalid` 三个码，`operation_unavailable` 落到兜底文案

服务端行为：`backend/src/automation_tool/control_plane/api/errors.py:104-111`
读取**请求头**里的 `x-request-id` 并原样回写到**响应头**。所以只要入站头被中间层改写，
回显值就一定和 App 期望的不一致。

边界改写点：`deploy/cloud/nginx-site.conf.template:75`
（线上实际文件 `/etc/nginx/sites-available/automation-tool-demo.conf:75`）。

### 2. 运行时取证（真实域名 `at.xuanbai.tech`）

未认证探针，确认头被改写：

```
SENT     x-request-id: aaaaaaaa-bbbb-4ccc-8ddd-eeeeeeeeeeee
RECEIVED x-request-id: 4c1a6095fc8f82c6fbb49d48baa70c49
```

真实演示账号登录成功（201）时同样被改写，且其余三项校验全部合格：

```
SENT     x-request-id: 12345678-1234-4234-8234-123456789abc
RECEIVED x-request-id: d53bf8c309385a891ae8cf3daa0a3d84
STATUS:  HTTP/2 201
CACHE:   cache-control: no-store          （合格）
CTYPE:   content-type: application/json   （合格）
```

即：状态码、Content-Type、Cache-Control 三项都通过，**只有 request-id 回显对不上**，
这正好是 `control_plane.rs:1822` 的那一个条件。

### 3. 与既有观测完全吻合（含「challenge 为什么没进日志」的解释）

曾有一个看似矛盾的观测：*「如果是响应回显比对失败，challenge 请求应该已经打到 nginx 才对，
但日志里一条都没有。」*

这不是矛盾，而是本根因的**直接推论**。该疑问隐含的前提是「回显比对失败发生在 challenge 请求上」，
但它发生在**登录请求**上，也就是整条链路的第一个请求：

1. `POST /api/v1/account-sessions` → nginx 记录 → 201（**这就是日志里那几条**）
2. 响应带回 nginx 的 `x-request-id` ≠ App 自己生成的 UUID
3. `validate_response_metadata` → `Err(ProtocolInvalid)`
4. `lib.rs:2120-2123` 登录那一行的 `?` 就地返回，函数结束
5. `bind_account_installation` 从未被调用 → nginx 里当然没有 challenge
6. 回滚用的 `logout` 也从未被调用（它在绑定失败分支里）→ 日志里当然也没有
7. `installations` 表保持 0 行

一个失败点同时解释全部四项观测。

**已排除「日志轮转丢了」和「走了别的 server 块」**：翻遍全部 15 个轮转文件
（覆盖 `12/Jul/2026:00:42` → `26/Jul/2026:17:57`，无缺口），

- UA=`automation-tool-desktop` 的请求**有且仅有** 6 条 `POST /api/v1/account-sessions`
  （用户 4 次尝试 + 本次排查 2 次探针），**没有任何其他路径**；
- `account-installations*` 的请求只来自 `Python-urllib/3.9`（部署校验脚本）与 `curl/8.7.1`（手工探针），
  **零条来自 App**；
- 部署前 `account_installation_binding_challenges` 表恰好 2 行，与日志里那两条 curl 201 一一对应，
  同样零行来自 App。

### 4. 这条链路从来没有被真实 App 走通过

`installations` 表**自始至终是 0 行**。也就是说这不是「今天坏的」，而是**从来没通过**。
云端那条线交付时判断「App 端接入是硬阻塞」，事后看是准确的。

### 5. 为什么门禁没拦住

开发与自动化验收里 App 直连 loopback 上的 FastAPI，不经过边界 nginx；
边界 nginx 只存在于云端 Demo 这一条路径上，从来没有被端到端跑过。

**归因（诚实说明：未能定案）**

- 已排除 `install_nginx_site`：服务器上那份与本地 HEAD **逐字节相同**，代码里只操作
  `automation-tool-demo` 那两个固定路径，且删除分支仅在 `nginx -t` 失败时触发（本次通过）；
- 已排除 certbot：当日最后一次运行在 14:36，不在窗口内；
- 实测确认 nginx 对 include 通配符里的**悬空符号链接会直接报错**
  （`open() ... failed (2: No such file or directory)`，`nginx -t` 失败）。
  而部署前 `nginx -t` 是通过的、符号链接也在，**因此部署前那一刻目标文件必然还存在**；
- 所以删除发生在 17:56（取基线）到 17:59（发现缺失）这个窗口内，而该窗口内我只执行了
  `install_nginx_site`，它已被排除。系统日志、`who`、`last` 均未找到其他执行者
  （非交互式 ssh 不进 `last`，因此并行会话无法从这里证否）。

**结论**：无法证明是本次部署造成，也无法排除窗口内有并行操作。可确定的是：故障已修复并验证，
且 `/etc/nginx` 目录本身的 mtime 停在 `11:22:41`，与今天更早那次 nginx 备份操作时间吻合。

### 5 行不是缺陷，核对过

`installations` 对 `device_public_key` 有唯一约束，所以 5 行 = 5 个不同的设备密钥。

| `profiles/demo-xuanbai/device-identity-ed25519-v1` | mtime **17:25**，此后未变 |

| `…automationtool.t36acceptance/profiles/demo-xuanbai/device-identity-ed25519-v1` | mtime **22:05** ↔ `14:05:24+00` |

多出来的 Installation 来自**各自独立 bundle identifier 的验收构建**
（`…h822macacceptance` / `…pb07acceptance` / `…t36acceptance` / `…u904acceptance` / `…uiharness`），
每个有自己的 `app_data_dir`，因而各有一把设备密钥。生产 identifier 那把是稳定的。
