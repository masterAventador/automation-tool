### ❌ 验收脚本本身的三处缺陷（EB-11 未闭合的真正原因）

**这三处都不是环境问题。** 包是正式公证包、走的是正常入口、账号是真的，而
`run_eb_11_formal_app_acceptance.py` 仍然跑不完。

**1. 无法从「未登录」冷启动。** `open_account_page()` 死等 `HEALTHY_LABEL="登录正常"`，
拿不到就 `did not expose required UI state: 登录正常`。它验的是「已登录 → 注销 → 重扫 →
重启复用」这条生命周期，**起点必须已有登录态**。干净机上第一次扫码没有任何脚本路径可走
——而干净机正是真实用户的状态，也正是 EB-17 的验收对象。本次前两次失败都源于此。

**2. `press()` 分不清「点了」和「点了个禁用按钮」。** 它按可访问性名字找元素后
`perform action "AXPress"`，而 `PlatformSessions.tsx` 上三个按钮都带
`disabled={pending !== null}`。禁用状态下元素仍有 name，AXPress 照样返回成功，
脚本据此认为点击生效。这与本仓库 `~/.claude/CLAUDE.md`「命令必须能区分『没有』和
『没查』」是同一个根因，只是出在了驱动侧。

**3. 「主动复查」不产生可观察的 Chromium，而脚本硬要求它。**
`require_complete_runtime()` 要 `embedded_browser_observed`，
`require_safe_logout_cleanup()` 还要从 Chromium argv 的 `--user-data-dir` 反查旧 Profile
UUID。实测第三次运行 20 秒即失败于 `EB-11 did not observe the embedded Chromium`，
而同一时段 App 日志里**一个浏览器启动事件都没有**（只有 `startup.local.completed`、
`executor.auto_start.requested`、`executor.process.start.succeeded`）。用户亦确认：
「这个 app 我跑了好几次，从来不会主动弹那个浏览器」——只有手动点「打开登录处理」才会弹。

### 结论

- **产品能力**：正式包上的抖音扫码登录、登录态落盘与界面状态呈现，**已由真实账号验证**；
- **仍不成立**：注销后旧 Profile 是否真删干净、重启是否复用同一 inode、退出后进程树是否
  清零——这三项**只有脚本能验，而脚本跑不完**，因此 EB-11 保持 `🔍 待验收`；
- 修复上述三处缺陷需要改验收脚本（可能还要给 App 加一条「复查时确实启动浏览器」的可观察
  路径），属于独立任务，不在本次范围。**不得因为用户路径跑通就把 EB-11 标完成**——
  那正是本仓库反复出事的那种「验收深度不够」。

## 2026-08-04 下午：修掉验收脚本三处缺陷

三处均先写红再实现，红的措辞就是当天用户实跑时看到的报错。

### ① `press()` 现在区分「点了」和「点了个灰按钮」

`AXPress` 对禁用元素什么也不做，而禁用元素照样带 accessibility name，所以原实现按名字
匹配后把 AppleScript 的返回当作点击生效——两种情况输出完全相同。
`PlatformSessions.tsx` 上三个按钮都带 `disabled={pending !== null}`，即每次上一个动作
在途时都会进入该状态。

现在脚本在按下前先读 `enabled of elementReference`，禁用则报
`App control is present but disabled, so it was not pressed`。

RED：`test_press_refuses_a_control_that_is_only_visible_not_enabled`，实跑报
`'enabled of elementReference' not found in ...`。

### ② 冷启动：`open_account_page()` 改为观察后分流

原实现死等 `登录正常`，于是干净机（真实用户的状态、也是 EB-17 的验收对象）上第一次运行
必然超时于 `did not expose required UI state: 登录正常`，且在超时前不会弹出任何二维码。

现在返回 `(rendered, already_signed_in)`：没有登录态时主流程先走一次
`open_login_for_scan → confirm_scan_checkpoint → recheck`，把登录态建立起来——**这一步
本身就是 EB-11 要求的「首次扫码登录」，不是绕过**——随后照常验证复查、安全注销、重扫、
重启复用整条生命周期。

RED：`ColdStartTests` 两条，一条要求接受 `需要登录`，一条要求**仍然**能识别既有登录态
（否则「兼容冷启动」会退化成永远走冷启动分支）。

### ③ 运行时采样从慢速 UI 读取上摘下来

`observe_instance_runtime()` 原本与 `visible_ui_text()` 在同一个循环里交替执行，而后者
遍历整棵可访问性树，是循环里最慢的一步。登录态复查由执行器经 Playwright 拉起内置
Chromium 完成，进程很短命；当天实测它整个落在两次采样之间，于是
`did not observe the embedded Chromium` —— 而 App 侧一切正常，日志显示执行器进程正常启动。

**把循环采样加密解决不了**：循环阻塞在 AppleScript 里，不是在 sleep。新增
`continuous_runtime_observation()`，用独立线程按 `RUNTIME_SAMPLE_SECONDS = 0.05` 持续采样，
已接入 `open_login_for_scan` 与 `recheck_healthy_session` 两处观察窗口。

RED：`test_short_lived_chromium_between_two_ui_reads_is_still_observed`，实跑报
`module has no attribute 'continuous_runtime_observation'`。

## 2026-08-05：启动、正常退出、强制清理接进 runner

### `signal.SIGKILL` 在 Windows 上不存在

`cleanup_owned_runtime` 从 SIGTERM 升级到 SIGKILL，而**升级这一步正是启动失败路径用来
「什么都不留下」的手段**。直接写 `signal.SIGKILL` 会在这台机器上抛 `AttributeError`
——而且是在清理阶段、在一个已经出过错的异常处理器里抛，第二次失败最难查的位置。
改为 `GRACEFUL_SIGNAL` / `FORCEFUL_SIGNAL`：Windows 上 `os.kill` 对非控制台事件的信号
一律走 `TerminateProcess`，两级于是是同一个动作，但名字不会炸。

`terminate_records` 另外吃掉 `PermissionError`——Windows 对「已退出但 pid 还看得见」
的进程报这个。清理天然与退出赛跑，进程已经没了正是它想要的结果，不是失败。

### 正常退出必须是关窗口，不是杀进程

EB-11 的收尾断言是「**正常**退出之后不留执行器、不留 Chromium」。用 `TerminateProcess`
会让这条断言什么都没验到，而证据长得一模一样。Windows 走 UIA 的 `WindowPattern.Close()`
——和人点关闭按钮同一条路。

### GREEN：真实安装包上的启停

request_quit 后消失:       0.25s，剩余 set()

去杀，结果**没杀掉**：`ProcessRecord` 比较连命令行和启动时间一起比，

**一个坏掉的 kill 会长得像一条通过的用例**。改为从真实快照里取那条记录。

`LaunchCleanupTests` 里两条用 `run_checked` 打断启动的用例，在启动改成按宿主分发之后
根本打断不了任何东西（Windows 上启动不经过 `run_checked`）。改为打断 `start_app`；
另有两条用 macOS 形状固定装置（`.app` / `Contents/MacOS`）的，把宿主钉在 macOS driver 上，
否则 `packaged_process_records` 认不出那个前缀。

### 真实边界

- 启动用 `Popen` 且**不 wait**：`quit_app` 要验的正是「问它一声它自己会退出」，
  在这里 hold 住它等于让本进程变成它的收尸者，而那恰好是被测的关系；

  ——macOS 问的是 bundle identifier。手工另起的第二个实例同样会被看见，这正是这个检查
  真正想要的事实；
- 仍未接线：`lsof` 对应的句柄枚举、`F_GETPATH` 对应的 NTFS file id、
  `read_identity`、`APP_DATA` 路径、target 映射、`require_device_boundary` 的 Windows 分支、

## 2026-08-05：打开的文件（`lsof -p` 的 Windows 对应物）

EB-11 拿它回答一个问题：浏览器进程**真的**握着本轮建的那个 Profile 目录吗，还是只是

**那个类型检查是防挂死的关键**：这里众所周知的挂死方式是去问一个同步管道的名字——
查询会一直阻塞到对端响应，而空闲管道永远不响应。`GetFileType` 从不阻塞，等它说了
「这是磁盘对象」之后再 `GetFinalPathNameByHandle` 就安全了。

## 2026-08-05：私有目录判定——不是删掉，是改成 Windows 真有的那套

一度把这条记成「`st_uid` / `st_mode` 在 Windows 上无意义，换成什么是个真问题」。
**记错了。** 无意义的是那两个**字段**（CPython 对本机每个目录都报 `st_uid=0`、
`S_IMODE=0o777`，所以 macOS 那个比较不是写错了，是**永远不可能为真**），
而那条**性质**在 Windows 上不但成立，产品侧还早就实现了：

`frontend/src-tauri/src/browser_profiles_windows.rs` 的 `PrivateSecurityDescriptor`
建一个只含**当前用户一条 ACE**（`FILE_ALL_ACCESS`）的 ACL，设 owner，
并打上 `SE_DACL_PROTECTED` **断掉继承**；`AclPolicy::Repair` 打开时把 owner 与 DACL
一起写回。所以 EB-11 该做的是把它读回来验，而不是删掉一个恒假的比较。

### 差别不是学术问题，本机就有

```text
…\Roaming\com.aventador.automationtool\embedded-browser-profiles
    AVENTADOR\Aventador:(OI)(CI)(F)                    ← 只此一条，没有 (I)

%LOCALAPPDATA%
    AVENTADOR\CodexSandboxUsers:(I)(OI)(CI)(RX)        ← 另一个组能读
    NT AUTHORITY\SYSTEM:(I)(OI)(CI)(F)
    BUILTIN\Administrators:(I)(OI)(CI)(F)
    AVENTADOR\Aventador:(I)(OI)(CI)(F)
```

一个没断继承就建出来的 Profile 会把那条 `(RX)` 一起继承下来，抖音登录态就能被那个组里
的任何进程读到，而这一轮别处不会有任何反应。

### 身份那一半根本不用翻译

实测：`os.fstat` 拿目录句柄（`CreateFileW` + `FILE_FLAG_BACKUP_SEMANTICS`，
再 `msvcrt.open_osfhandle` 交给 CRT）报 `S_ISDIR` 为真，`(st_dev, st_ino)` 与
`os.stat` 一致、跨调用稳定、不同目录不同。这正是「重启后还是同一个 Profile」和
「删掉的 Profile 再无名称」都要靠的东西。

### GREEN：对着产品真建出来的目录验

```text
✅ Profile 根（产品建的）    identity=(2486687320980114229, 354939945632212107)
✅ App data 根（产品建的）   identity=(2486687320980114229, 9570149208185884)
❌ %LOCALAPPDATA%（继承的）  inherits access from its parent
```

四条断言：是目录、owner 是当前 token 用户、DACL 带 `SE_DACL_PROTECTED`、
且唯一那条 ACE 是给当前用户的 `FILE_ALL_ACCESS`。空 DACL 单独拒绝——
**null DACL 是「所有人全权」，不是「谁都没有」**，两者差一个字。

### 变异确认

去掉 `SE_DACL_PROTECTED` 那一条 → `test_a_directory_that_only_looks_private_is_refused` 变红。
这条用例专为它而写：一个私有目录的**子目录**继承下来恰好也是「一条 ACE、正是当前用户、
全权」，数量和身份都对得上，**只有 protected 位能把它和产品建的那个区分开**。
没有它，将来把 Profile 挪到一个更松的目录下面会悄悄放宽，而所有基于数量的断言仍然全绿。

### 真实边界

- 目录遍历是**逐段检查再整体打开**，不像 macOS 那边 `O_NOFOLLOW` + `dir_fd` 每步原子。
  Windows 的 `openat` 只在 Nt 层有。这个缝隙与 macOS 侧已经声明的威胁模型同类
  （可信流程内的误操作与回归门禁，不是防同用户活跃攻击者），写在
  `open_private_directory` 的 docstring 里而不是留给读者去发现；
- 本机还没有 `douyin/<profile-id>` 子目录（尚未登录过），所以只验到 Profile 根与
  App data 根；单个 profile 目录要等真实扫码那一轮。

## 2026-08-05：运行时身份也换成摘要

制品那一层已经改成摘要绑定，运行时这一层是同一个替换往下走一级：
`verify_runtime_process_identity` 在 macOS 上对**活 PID** 跑 `codesign`，问的是
「此刻加载进内存的代码是什么」。Windows 上没有这个问题可问，于是合并两个较弱的事实：

1. 内核报给这个进程的映像路径，等于验过的那个可执行文件；
2. 该路径上此刻那个文件的摘要，等于验过的摘要。

**弱在哪里写在实现里**：这证明进程是从那堆字节起来的，不证明此刻内存里跑的就是它。
Windows 运行中会把映像保持映射，文件不能被就地替换——但**可以被改名**，
所以比的是摘要而不只是路径。

`CodeIdentity` 与 `ArtifactFacts` 同样的做法：macOS 三个签名字段保持不变、带默认值，
Windows 只填 `image_sha256`。空的签名者字段读作「没建立」。

### GREEN

```text
真实子进程上：
  路径对 + 摘要对        → True
  路径对 + 摘要改一位     → AcceptanceFailed（改名换不掉摘要）
  摘要对 + 路径换一个     → AcceptanceFailed（同样字节的另一份拷贝也不是它）
  进程已退出              → False（重采样，不是不匹配）
```

三条负例是分开的：**只比路径会漏掉「同路径不同字节」，只比摘要会漏掉「另一处的同一份
拷贝」**，两条都得有。

### 顺带

三条 macOS 形状的用例改为点名 `macos_verify_runtime_process_identity`；一条经
`observe_instance_runtime` 间接走到分发的，把宿主钉在 macOS driver 上——它的固定装置
是 `.app` 路径加 codesign 输出，验的是「替换进程会被识别出来」这条性质本身。

## 2026-08-05：已删 Profile「再无名称」的 NTFS 版本

安全注销的磁盘侧证明：本轮握着的那个 Profile 目录，注销之后必须在任何地方都没有名字。
macOS 的做法是 unlink 一个还开着的目录，然后拿 `F_GETPATH` 问描述符现在叫什么。

NTFS 给的答案更直接，实测出来的：

```text
握着句柄时:      \?\C:\…\douyin\a3b06c48
rmtree 同时句柄开着:  成功（句柄带 FILE_SHARE_DELETE，删得掉）
父目录列表:      []                      ← 名字立刻消失
删除后再问路径:  \?\C:\$Extend\$Deleted\00250000002034D9595311E0
os.fstat(fd):    仍可用，inode 与删除前一致
```

`$Extend\$Deleted` 是 NTFS 给「删除挂起但句柄还开着」的文件留的存放区。
**一个最终路径落在那里的句柄，在普通命名空间里没有名字**——正是要证明的那件事。

改名则完全不同：`GetFinalPathNameByHandleW` 继续回答一个真实路径。所以安全注销**不能**
被一次改名满足——旧 Profile 带着平台登录态，把改名当成删除会得出「cookie 没了」
而它就在隔壁换了个名字。两条各有一个用例。

### 一处会让所有身份都相等的陷阱

`os.scandir` 的 `entry.stat(follow_symlinks=False)` 在 Windows 上从目录列表回答，
**而目录列表里没有文件索引**——每一项的 `st_ino` 都是 0，于是任意两个身份比较起来都相等。
第一版就是这样：`(0, 0)`。必须用真正的 `os.stat(entry.path)`。

### GREEN

```text
删除前：句柄身份 == 目录身份，且父目录列表里找得到它
删除后：句柄身份为 None，父目录列表里找不到它
改名后：句柄身份仍 == 目录身份，父目录列表里仍找得到它
```

## 2026-08-05：证据发布与最后那道闸门

### 证据发布这条路 Windows 上一步都没走过

五条证据用例标着「POSIX evidence publication contract」在本机跳过，所以这条路径
**从来没有在 Windows 上执行过**。它整条建立在 `dir_fd` 上——`os.stat(..., dir_fd=)`、
`os.link(..., src_dir_fd=)`、`os.fchmod`、对目录 `os.fsync`——Windows 上这四个要么不存在
要么无意义，而**第一个会在一次已经驱动完真实登录的运行的最末尾抛出来**。

改为四个具名 driver 方法（`stat_in` / `open_in` / `unlink_in` / `replace_in`，
加上 `link_in` / `make_private_file` / `sync_directory`）。Windows 侧把句柄换回路径再操作：
比 macOS 的 `openat` 少一步原子性，与 `open_private_directory` 已声明的那条同类。

两处 `S_IMODE != 0o600` 换成 `require_published_evidence_mode()`。**这不是把断言删掉**：
那条断言的作用是**防替换**——和旁边的 inode 身份比较合起来说「这就是我写的那个文件」。
Windows 没有权限位，而 inode 身份本身的区分度远高于权限位，所以那一半由它承担，
写在方法的 docstring 里。

`make_private_file` 在 Windows 上是空操作，并写明原因：证据目录由操作者用 `--evidence`
指定，谁能读这个文件由那个目录的 ACL 决定。**声明出来，而不是静默跳过。**

### GREEN

```text
真实发布一次：文件落地、内容含中文、(st_dev, st_ino) 与写入时一致
              临时文件不留（目录里只剩证据文件本身）
已存在同名文件 → 拒绝覆盖
```

### 闸门最后才开

`require_device_boundary` 里两条 macOS 专属：`.app` 后缀与 `os.geteuid() == 0`。
分别收进 `require_app_path()` 与 `running_as_administrator()`：

- Windows 包是一个装着可执行文件的目录，没有后缀可要求，**改为要求它恰好含一个产品
  可执行文件**（`windows_product_binary` 拒绝猜）；
- 提权检查换成 `IsUserAnAdmin()`——EB-11 不用比使用者更高的权限去驱动 App；
- 路径不存在时改为具名拒绝，而不是让 `FileNotFoundError` 从整个运行的第一道门里漏出去。

其余（交互式控制台、绝对路径、无重解析点、证据不覆盖且在包外）本来就与平台无关，一字未动。

## 2026-08-05：签名种子的 Windows 权限检查

`load_signing_seed` 要求密钥文件是 `0o600`。**这条在 Windows 上不是「查得松」，是让整个
Windows 发布根本建不起来**——CPython 对本机每个可写文件都报 `S_IMODE` `0o666`，
比较永远不成立，而 `customer_demo_material()` 是客户 Demo 包的必经之路。

它保护的性质是真的：一个给部署 Profile 签名的 Ed25519 种子不能被别人读到。Windows 有
这个性质的表达方式，而且产品侧 Profile 目录已经在用——一条只给当前用户的 DACL。
于是复用 `windows_private_directory.require_private_dacl`（它走 `SE_FILE_OBJECT`，对文件
一样有效）。

固定装置也得跟着改：`write_key()` 里的 `path.chmod(0o600)` 在 Windows 上只翻只读位，
不改 DACL，所以 fixture 要真的写一条私有 DACL，否则**每条用例都会跑到拒绝分支上去**。

## 2026-08-05：「不许碰用户自己的浏览器」这条也得指对地方

## 2026-08-05 晚：重出包读产物，抓到发布身份与执行器互相不认

重新出包（`REAL_EXIT=0`，installer 450,952,363 字节）并**装上**之后，把装好的包读回来：

```text
release identity:          executor_build_id = 'windows-release'
packaged executor manifest: build_id         = 'eb-16-windows-release'
```

**两个名字，一次构建。** `require_release_identity()` 会比对这两者，所以 EB-11 会拒绝
这个包并说「signed release does not match the packaged Executor」——一条准确的错误，
指向一个从出生起就自相矛盾的构建。

原因和当初 `buildId: macos-release` 是同一形状：Windows 的执行器构建函数借自 EB-16
验收脚本，而它把 `"eb-16-windows-release"` 写死进了自己签的清单里，`--build-id` 传不进去。

修：给它一个 `build_id` 参数（默认仍是 EB-16 自己的名字，那条验收照旧），发布路径传自己的；
并加一道出包门禁 `require_executor_build_id()`——**两个名字由两段不同的代码写出来，
在验收运行之前没有任何地方会把它们放在一起看**，所以出包时就查。

### 顺带记一条 50 分钟的坑

安装那步卡了 50 分钟，从外面看和「正在装 450 MB」毫无区别。实际是 `installer.exe /S`
经 Git Bash 时被 MSYS 参数转换改写成了路径，installer 收到不认识的参数就弹了 GUI，
然后不报错、不退出地等着。改从 PowerShell 启动后 `INSTALL_EXIT=0`。

与本仓已记的两条同类（`nohup` 那次退出码来自包装命令）。判据一样：
**看被测的东西自己在干什么，别看包装层说了什么**；卡住时先看有没有窗口在等人。

## 2026-08-05 晚（二）：出包产物回到项目内，顺带挖出真正的路径根因

用户问「为啥门禁还要禁字符数量」，顺着答下去发现默认值本身有问题，再顺下去发现门禁的
常量和模型都是错的，最后发现根因根本不在门禁。

### 三层错，一层比一层深

1. **默认 `--work-dir` 在 Windows 上永远用不了**：`.local/release` 33 字符，当时预算 31。
   而那条拒绝提示里写着 `such as C:\atrel`——**我把自己的临时凑合固化成了给所有人的建议**，
   把人指到项目外面，也违反了「本地资源用 automation-tool 专属可追溯路径」；
2. 改短到 `.local/rel`（29）**仍然出不了包**。量真实失败路径：总长正好 **260**，
   而 `MAX_PATH` 260 是**含结尾 NUL** 的，可用 259 —— 差一个字符。同时
   `WINDOWS_DEEPEST_PAYLOAD_PATH` 写的 229、实测 **231**（「常量要量不要猜」这条我犯了第二遍）；
3. **根因**：Windows 的资源源写成了相对 Tauri 根的路径，于是 `makensis` 看到的是

```text
<work>\source-snapshot-XXXXXXXX\repository\frontend\src-tauri\..\..\..\..\build\payload\…
      └────────────── 67 字符绕一圈，解析回来就是 <work> 本身 ──────────────┘
```

macOS 一直用绝对路径、也一直发得出去；相对路径这个选择当初**没有写下任何必须的理由**。

### 改掉根因，绕过根因的东西一起删

```text
最深载荷路径   231 → 164
工作目录预算    28 → 95
.local/release  被拒 → 通过（富余 62）
```

于是第 1 层加的那个 Windows 专用默认值连同平台分支一并删除——**根因去掉了，绕过根因的
东西就不该留着**，否则等于把绕路固化成设计。

### GREEN：不带 `--work-dir` 出包

```text
REAL_EXIT=0   产物 F:\automation-tool\.local\release\
installer 450,983,234 字节
装好后 require_release_identity: PASSED
  包内 commit af76b74a7ecf == 当前 HEAD    树摘要一致 True
  executor customer-demo-xuanbai          profile demo-xuanbai
```

**「门禁放行」不等于「能出包」**：上一版就是门禁放行、`makensis` 照炸。所以这次是不带
`--work-dir` 真跑一遍，才算默认值可用。`C:\atrel` 已删除。

### 新增用例

- Windows 配置的每个资源源必须是绝对路径且不含 `..`（相对路径会把 bundler 送进快照绕路）
- 两平台共用一个默认工作目录，且该默认必须通过它自己的门禁
- 拒绝信息不得再出现 `C:\atrel`，要指向 `.local`
