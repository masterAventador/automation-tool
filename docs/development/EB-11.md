## 真实边界

- 内置 Chromium 与系统 Chrome 在登录链行为一致性已由同套流程对象在两种浏览器分别证明；
  生产只接受内置路径（EB-10 已删除选择链路）；
- `about:blank` 无持久化存储是浏览器安全语义，登录态证据只在真实 origin 下持久化；
- 真实抖音页面选择器漂移风险由 `DOUYIN_QR_LOGIN_FLOW_VERSION` 版本化覆盖；
- **Windows 包是摘要绑定，不是签名绑定。** 由用户 2026-08-05 拍板。它**证明**：装的就是
  这棵源码树出的那个包（安装目录整树摘要可与出包侧对照），里面的执行器带自己的签名清单。
  它**不证明**：系统信任它（无 Gatekeeper 对应物）、取摘要之前没有第三方改过它。差别写进
  数据本身——`authority`/`team_id`/`bundle_cdhash` 在 Windows 上**留空**，另有 `code_signing`
  记录每次实测到的 Authenticode 状态。空的签名者字段读作「没建立」；填一个像签名的值表示
  「没查」读起来正好相反。哪天真有证书，证据会自己变，由
  `test_a_signed_windows_package_is_not_silently_accepted_as_unsigned` 守着；
- **Windows 的目录遍历是逐段检查再整体打开**，不像 macOS 侧 `O_NOFOLLOW` + `dir_fd` 每步
  原子（`openat` 只在 Nt 层有）。这个缝隙与第 19 轮声明的威胁模型同类——受信流程内的误操作
  与回归门禁，不是防同用户活跃攻击者。写在 `open_private_directory` 与 `NO_FOLLOW_OPEN_FLAG`
  的定义处，不在调用点分叉；
- **Windows 运行时身份是两个较弱事实的合取**：内核报给进程的映像路径等于验过的可执行文件，
  且该路径上此刻的文件摘要等于验过的摘要。这证明进程是从那堆字节起来的，不证明此刻内存里
  跑的就是它。运行中映像被保持映射、文件不能就地替换，但**可以被改名**，所以比的是摘要而
  不只是路径；
- 证据发布在 Windows 上把句柄换回路径再操作（`dir_fd` 那套四个 API 要么不存在要么无意义），
  比 macOS 的 `openat` 少一步原子性。两处 `S_IMODE != 0o600` 换成
  `require_published_evidence_mode()`——那条断言的作用是**防替换**，Windows 没有权限位，
  由旁边的 inode 身份比较承担，区分度更高。`make_private_file` 在 Windows 上是显式空操作
  并写明原因（谁能读证据由 `--evidence` 所指目录的 ACL 决定），**声明出来而不是静默跳过**；
- Windows 进程读取只测了同用户、x64 → x64。跨架构（WOW64）PEB 偏移不同，模块在非 64 位
  指针宽度下直接返回 None 而不是读一个错地址；
- `--user-data-dir` 路径含空格时是否会被加引号未验（本机 `%LOCALAPPDATA%` 不含空格）。
  失败方向是拒绝而非误认，但会是一个难懂的拒绝。登记，未修；
- `start_app` 把工作目录设成安装根，于是 App 会一直握着它。这与 Windows 快捷方式的
  「起始位置」一致，与 macOS `open -n -a` 行为不同；
- 客户 Demo Profile 下**必须先用产品账号登录**才会出现「账号与平台」页，runner 不处理这道
  闸门。这是产品设计（U9），不是缺陷。

### 本任务范围内、仍待处理

  - `test_a_fresh_directory_is_created_owner_only` 断言 `st_mode & 0o077 == 0`，而生产的

  `developerIdSigned` / `gatekeeperAccepted` / `notarizationStapleValid`。同一份证据里
  `codeSigning` 是 `NotSigned`、三个签名者字段为空，**互相矛盾**。这三个键的写法是硬编码

  会误导的证据输出，**下一个动 `scripts/` 的任务顺手改成由实测派生或直接删除**——按
  `codeSigning` 那条注释自己写的设计意图，本来就该由三个字段的空/非空来表达。

### 登记，不在本任务范围（发现于本任务，属设计层面）

- **本地事实绕服务端一圈**：登录状态是在本机浏览器里当场测出来的，却由执行器经 WebSocket
  报给服务端、再由 App 用 HTTPS 读回来显示——轮询窗口正是因此存在。更好的形状是本机结果
  立即上屏、服务端投影异步对账，那样这个等待窗口根本不存在；
- **执行器上报没有应用层 ack**：`mark_delivered` 发生在 socket 写成功之后，所以「已投递」
  = 写进了 socket，不等于服务端存下了。App 因此无从知道投影何时更新，只能轮询——**轮询是
  这个缺口的补丁，不是需求**。用户提出「改成 App 上报、用 HTTP 响应当应答」可行，但代价是
  信任边界：上报消息带着执行器自己发的 `sequence`，服务端靠它与
  `platform_session_gates.session_revision` 排序决定注销时拦哪些在途命令；改成 App 发，
  App 就成了转述一件自己没观察到的事。更贴合现有架构的形状是**服务端对执行器的消息回
  ack，执行器把「已发布 + revision」放进本地命令结果回给 App**，App 拿到即渲染、零轮询、
  信任边界不动。属协议加字段。
  **更大的一处**：这个 outbox 不只送会话健康，**也送任务事件**；在没有 ack 的前提下
  `mark_delivered` 意味着服务端若未处理消息就静默丢失——「持久化 outbox」并不持久。单独登记；
- **产品账号会话有效期**：2026-08-05 夜间过期两次（21:51 登录，00:07 自动续期一次，
  01:0x 再次失效需重新登录），两次都打断了正在进行的验收。对客户 Demo 而言值得单独评估。

订正一处当时的想当然：曾以为「任务无人值守时也要上报，所以必须执行器报」。核查后**今天
不成立**——`health_reporter` 只在平台命令这条 UI 驱动的路径上被调用，任务发现不报。

## 二、2026-08-05：把 macOS 的仪器逐件换成 Windows 的对应物

**不新写一个 Windows runner。** EB-11 的定义（登录、复查、注销并证明旧 Profile 没了、重扫、
重启复用同一 Profile、退出后进程清零）是平台无关的那部分，也是有价值的那部分；分叉它等于
分叉定义。所以平台落在 `DeviceDriver` 后面，逐件替换：

| 事实 | macOS 的问法 | Windows 的对应物 | 换过程中抓到的坑 |
| --- | --- | --- | --- |
| 按下一个控件 | AppleScript `AXPress` | UIA `InvokePattern`，pid 与标签走环境变量、脚本是常量、`-EncodedCommand`(UTF-16LE) | 见证物不用界面用一次 TCP 连接计数（转瞬即逝的界面当见证物，慢一拍就得到「也许」）；`[Console]::OutputEncoding` 不设的话读回来全是乱码（PS 5.1 重定向默认走 OEM 936） |
| 读界面文字 | 遍历 AX 树 | UIA `Name` + `ValuePattern` | `http://tauri.localhost/` 只有 `ValuePattern` 读得到，证明取值那一支真的走到了 |
| 制品可信 | `codesign --deep --strict` + Gatekeeper + staple | **整树摘要绑定**（用户拍板） | `bundle_tree_digest` 用 `os.O_NOFOLLOW`，**Windows 没有这个标志**——一个算不出来的摘要绑不住任何东西 |
| 进程表 | `ps -axo pid,ppid,lstart,command` | Toolhelp 快照 + 受限信息句柄 + PEB | 一切读不到就报「未知」不抛异常（全机快照要走几百个别人的进程）；**创建时间是承重的**——Windows 复用 pid，没有它一个被复用的 pid 会和本轮启动的比相等 |
| 是不是包内进程 | 前缀 `<app>/Contents/` | `driver.packaged_prefix(app)` | 原样搬过去**什么都匹配不上**，于是会得出「刚启动的 App 根本没启动」，**而且一句错都不报** |
| 命令行 | `ps` 原样给 | 从 PEB 读，argv[0] 带引号需按引号规则切掉再拼回 | 三个调用点分别要「以安装目录开头」「抠 `--user-data-dir`」「判断是不是包里那个可执行文件」，带引号的开头一个都过不了 |
| 强制清理 | `SIGTERM` → `SIGKILL` | `GRACEFUL_SIGNAL` / `FORCEFUL_SIGNAL` | 直接写 `signal.SIGKILL` 会在本机抛 `AttributeError`，**而且是在清理阶段、在一个已经出过错的异常处理器里抛** |
| 进程握着哪个目录 | `lsof -p` | `NtQuerySystemInformation` 整表（实测 119,455 行）+ `DuplicateHandle` + `GetFileType` | `GetFileType` 是防挂死的关键：问一个同步管道的名字会一直阻塞到对端响应，而空闲管道永远不响应 |
| 删掉的目录再无名称 | unlink 后 `F_GETPATH` | 最终路径落进 `$Extend\$Deleted` | **改名则完全不同**，`GetFinalPathNameByHandleW` 继续回答一个真实路径——所以安全注销不能被一次改名满足 |
| 目录身份 | `(st_dev, st_ino)` | `os.fstat` 目录句柄（`FILE_FLAG_BACKUP_SEMANTICS` + `open_osfhandle`） | `os.scandir` 的 `entry.stat()` 从目录列表回答，**每项 `st_ino` 都是 0**，于是任意两个身份比较起来都相等 |
| 目录是私有的 | `st_uid` + `S_IMODE == 0o700` | owner + `SE_DACL_PROTECTED` + 唯一一条当前用户 `FILE_ALL_ACCESS` 的 ACE | 一度记成「这条性质在 Windows 上不成立」，**记错了**——无意义的是那两个**字段**，性质产品侧早就实现了（`browser_profiles_windows.rs`）。空 DACL 单独拒绝：**null DACL 是「所有人全权」不是「谁都没有」** |
| App 身份 | `Info.plist` | 可执行文件从制品解析、版本资源读版本、identifier **验证而非读取** | NSIS 安装根里没有清单写着产品是谁，但 identifier 编译进了二进制，所以「什么都不说」蒙混不过去 |
| 产品数据根 | `~/Library/Application Support/<id>` | `%APPDATA%\<id>`（**Roaming 不是 Local**） | 改成函数而非导入时算好的常量，否则模块在没有 driver 的宿主上直接导入失败 |
| 运行中进程可信 | 对活 PID 跑 `codesign` | 映像路径 + 该路径此刻的文件摘要 | 三条负例分开写：只比路径漏掉「同路径不同字节」，只比摘要漏掉「另一处的同一份拷贝」 |
| 不许碰用户日常浏览器 | `~/Library/.../Google/Chrome` | `%LOCALAPPDATA%\Google\Chrome\User Data`（深一层） | 原路径在 Windows 上**永远不会有东西落进去**，那条断言永远不可能触发——**一条不可能失败的断言什么也没禁止** |
| 签名种子私有 | 文件 `0o600` | 复用 `require_private_dacl`（`SE_FILE_OBJECT` 对文件一样有效） | CPython 对本机每个可写文件都报 `S_IMODE 0o666`，比较永远不成立，而这是客户 Demo 包的必经之路 |
| 证据发布 | `dir_fd` 那一套 | `stat_in`/`open_in`/`unlink_in`/`replace_in` 等具名 driver 方法 | 五条证据用例标着「POSIX evidence publication contract」在本机跳过，**这条路从来没在 Windows 上执行过**，而第一个 `dir_fd` 会在一次已驱动完真实登录的运行的最末尾抛出来 |
| 资源布局 / 发布目标 | `Contents/Resources/…`、`macos-arm64` | 由 `release-package-resources.v1.json` 的 `resourceRoot` 派生 | 两处写死各自失败得很难懂：清单读不到报「packaged runtime manifest is unavailable」**看着像包坏了其实是路径错了**；目标映射让任何 Windows 包都被判「does not match this Mac」 |

期间实测开销（255 个进程）：进程表 < 1 ms，113 个映像路径 < 1 ms，86 个命令行 15 ms——
比 macOS 的 `ps`（要 fork）还便宜，连续采样吃得消。

**一次「实现没错、测试错了」的排查**：句柄枚举的两条用例都红，看起来像枚举器漏掉文件句柄。
真实原因是 **uv 虚拟环境的 `python.exe` 是个跳板**——它不 exec 而是再起一个真解释器然后等着，
`Popen.pid` 拿到的是跳板，脚本真正打开的句柄都属于孙进程。让被测进程自己把 `os.getpid()`
打到 stdout 上立刻就对了。这条跳板当天是第二次咬人（第一次是出包时的能力绑定用
`os.getppid()`）。

## 三、2026-08-05～06：真跑抓到的缺陷

分层证据全绿之后，每一次真跑都还在抓到东西。**这正是「生产同路径验收」要防的那件事**：

| # | 症状 | 真正的原因 | 修法 |
| --- | --- | --- | --- |
| 1 | 发布身份写 `windows-release`，包内执行器清单写 `eb-16-windows-release` | Windows 执行器构建函数借自 EB-16 验收脚本，把名字写死进了自己签的清单，`--build-id` 传不进去 | 加 `build_id` 参数，并加一道出包门禁 `require_executor_build_id()`——**两个名字由两段不同的代码写出来，验收之前没有任何地方会把它们放在一起看** |
| 2 | 出包在 `makensis` 阶段炸，且默认 `--work-dir` 在 Windows 上永远用不了 | 三层错：拒绝提示里的 `C:\atrel` 是我把自己的临时凑合固化成了给所有人的建议；`MAX_PATH` 260 是**含结尾 NUL** 的，差一个字符；**根因**是 Windows 资源源写成了相对 Tauri 根的路径，绕一圈 67 字符 | 改绝对路径（最深载荷 231→164，工作目录预算 28→95），**并把为绕过它加的 Windows 专用默认值连同平台分支一并删除**——根因去掉了，绕过根因的东西就不该留着 |
| 3 | `[WinError 2] 系统找不到指定的文件` | `verify_running_release_process` 还在直接调 `codesign`——其余每件仪器都搬到 driver 后面了，唯独这个漏了，因为之前的排查是**按帮助函数的名字** grep 的，而这一处把工具名直接写在参数列表里 | 加 `require_running_release()`；补扫每一处 `codesign`/`/usr/bin/`/`/bin/ps`/`/usr/sbin/` 的行号映射回所在函数 |
| 4 | `settled on neither a signed-in nor a signed-out state` | 账号页有**五**种状态，脚本只认两种（这次差的是 `尚未确认`） | 不再一个个补，改成读 `PlatformSessions.tsx` 的封闭集合 `STATE_LABELS`，另加门禁测试把两份清单钉在一起——**抄写躲不掉，能躲掉的是抄漏了没人发现** |
| 5 | 每条平台命令都报 `process_unavailable`，而执行器一直健康 | Rust 的 `parse_line` 拒绝以 `\r` 结尾的行，而 Windows 的 `sys.stdout` 是文本流，`"\n"` 出去变 `"\r\n"`。**帧的写法有两份**：`ExecutorProcessReporter._write` 走 `output.buffer` 写精确字节 ✅，`write_platform_command_result` 走文本流 ❌ | 收成一处：`executor/frame_output.py::write_protocol_line`，两个写入方都用它。**两份写法各自演化正是这次的根因** |
| 6 | `observed duplicate packaged runtime processes` | 一个浏览器被数成十个：macOS 上 Chromium 子进程跑的是 bundle 里另一个 helper，Windows 上全是同一个 `chrome.exe` | 用 Chromium 自己的约定判别——**浏览器进程不带 `--type=`，带的都是子进程**。这在两个平台都成立，所以是一条规则而不是一处宿主分叉 |
| 7 | `Chromium did not open the App-owned Profile`，**不可复现** | 采到的是浏览器进程树此刻在磁盘上什么都没握住的瞬间，而实现把这个瞬间读成了「没用 App 自己的 Profile」这个**结论** | 空路径集合与 `read_process_open_paths()` 返回 `None` 同等对待（「此刻没看到」不是「没发生」）；`require_complete_runtime()` 仍要求至少一次采样真的观察到 |
| 8 | 写 7 的守护测试时红得意外 | **两个检查的顺序是反的**：真的打开了操作者日常 Chrome/Edge 的 Profile 时——`CLAUDE.md` §5 明令禁止、一次就该终止——只要那一刻还没碰到 App 自己的 Profile，报出来的就是一句时序抱怨。**违规被伪装成了噪音** | 日常 Profile 的证据先判且仍然致命（有证据 = 有结论），App 自有 Profile 的缺席后判且只表示这次采样无结论（没证据 ≠ 有结论） |
| 9 | 所有平台操作报 `operation_unavailable` | App 把自己限流了：`50ms × 100 次` 轮询 = 20 次/秒，而**每次业务请求前都先新建一个设备会话** ⇒ 40 请求/秒，正好是 nginx `rate=10r/s` 的 4 倍，`burst=20` 用完即 429 | 换成退避时刻表 `healthPublicationDelays()`（500ms 起、翻倍、上限 2s、总预算 12s）：速率 40/s → 4/s，而留给服务端投影追赶的时间从 5s **延长**到 12s——更慢的节奏反而给了更多时间 |
| 10 | `Chromium did not use the App-owned Profile`（用户真跑，扫了两次码） | **判据从设计上就依赖运气**：复查浏览器只活约 0.7 秒（执行器开、查、一到 healthy 就 `_close_active()`，关完才返回结果），而有浏览器时单次采样要 ~0.30 秒 | 改成两条不会过期的、都在重启之后读的事实：QR 时绑定的 Profile 目录在父目录里**仍然有名字**；App 自己的 `current-douyin-profile-v1` **仍然指向它** |
| 11 | 10 只修了一半 | `require_same_profile_reuse` 改了，而 `recheck_healthy_session` 内部**仍然**要求完整运行时观察。整条链上有四次复查，任何一次都可能挂在同一个地方，两处失败信息完全一样 | 新增 `require_recheck_runtime()`：复查只要求「打包执行器在跑」+「采到的东西必须正确」。完整链条的证明仍留在 QR 窗口——那里浏览器为等扫码一直开着 |
| 12 | 执行器每次在平台命令后约 3 秒消失，来不及扫码 | 见下一节 | 见下一节 |

几处值得单独说的判断依据：

- **9 与 10 互相独立**：用户 23:41 那次失败的时间窗内**没有 429**（只有两个请求）；
- **10 的失败点我第一次说错了**。凭错误信息推断得到「第二次扫码之后那次复查」，把 App 日志
  按本地时间排成一条线之后，实际死在**重启复用之后那次复查**（`23:40:58 app.setup.started`
  是第二个实例，能重启就说明 qr 复查过了）。**光看错误信息会指错地方，日志时间线才指对**；
- **11 是先在真机上跑通、再复查代码才发现的**。跑通不等于改对——那次跑通只是两次复查都碰巧
  采到了浏览器，硬币连着两次正面；
- 修 9 时顺带修好一条**会悄悄失效**的既有测试：它按写死的 `10_000` 推进假时钟去触发超时分支，
  预算一改就再也到不了那个分支。改成由 `healthPublicationDelays()` 自己算出预算；
- 修 6 时同时新增 `test_a_second_real_browser_is_still_a_duplicate`——**过滤不能把检查关掉**；
  它在修改前就已经绿，证明这条守护不是跟着实现一起写出来的；
- 修 10 做了**变异验证**：把「两个复查窗口也必须完整观察」加回去，7 条里 6 条立刻转红，
  还原后全绿（存活的那条守的是 QR 窗口的严格性，加严不该让它红）。

**关于 Windows 上那 253 条红**（用户问「30 红是啥」）：22 条是我自己造成的（pytest
`--basetemp` 指到很深的 scratchpad 路径，夹具的 UUID 目录顶爆 `MAX_PATH`，报
`WinError 206`）；7 条是 `os.symlink` 需要 `SeCreateSymbolicLinkPrivilege` 而开发者模式没开
——**没有跳过它们**，那 7 条守的正是 Windows 上真实存在的重解析点攻击面，跳过等于在要发布的
平台上关掉 7 道门禁，用户开启开发者模式后 7 条全部真跑并通过；**真正剩下的只有 2 条**，
即「遗留项」里那两条 POSIX 假设。

## 四、根因：一次零容差的跨机器时钟比较

上表第 12 项是最后一个、也是最难查的。症状：**浏览器弹出来就自己关，来不及扫码。**

取证过程本身值得记，因为它昂贵得不必要。执行器把服务端主动关闭判为**不可恢复**
（`_is_recoverable_transport_error`：`ConnectionClosed` 且 `rcvd` 非空即不可恢复），于是
`ExecutorProcessRejected` 退出并带走 Chromium。要知道服务端为什么关，只能：

1. 在服务器 loopback 18800 抓包（nginx→控制面是明文）；
2. 手工解客户端帧的 WebSocket 掩码（掩码键就在帧头里）；
3. 把抓到的原文用服务端**自己的模型和规则**在本地重放。

重放结果是：信封解析通过、三条时间规则通过、类型与身份匹配通过，再拿数据库现状逐条对
`converge()` 的五条规则也全部满足。**按代码它该被接受，实际却被拒了。**

真正的障碍不是这个缺陷难，而是**服务端拒绝执行器消息时只回一句笼统原因、一行日志都不打**。
所以先修可观测性：给 `PlatformSessionHealthRejected` 加 `reason`（固定词表，绝不含消息内容），
十二处 raise 各自命名；WebSocket 处理器每一处「协议被拒」关闭都写出对应日志。

**一条真门禁在这里挡了我一次，挡对了**：
`test_control_plane_production_logging_calls_accept_only_literal_messages` 要求生产日志调用
只能有一个字符串字面量参数——格式化参数会把内容带进日志，而脱敏层会把它换成 `[REDACTED]`，
那行日志等于白写。所以改成一个原因一条整句字面量。

加上日志、部署、复现一次，服务端自己说了：

```text
Executor Session health refused: sent_at is ahead of this server
```

就是这一行，没有任何容差：

```python
if received_at < message.sent_at:      # 客户端快 1 毫秒即被拒
```

实测这台 Windows 的时钟比部署机**快约 110 毫秒**（四次采样 +108 ~ +121ms）。于是执行器每一条
`platform.session_health` 的 `sent_at` 都落在服务端的「未来」，被判协议违规 → 关连接 →
执行器视服务端主动关闭为不可恢复 → 退出 → 运营浏览器被一并带走。

同一套代码别处早就承认时钟会偏——`DEVICE_SESSION_CLOCK_SKEW = 30 秒`，正是为此。这一处漏了。

修：新增 `PLATFORM_SESSION_HEALTH_CLOCK_SKEW = 30 秒`，`sent_at` 与 `deadline_at` 两侧都按它
放宽；低一层的 `updated_at < observed_at` 是同一个问题的另一面，改为把记录的「收到时间」取
服务端时间与观察时间的较大者——「不可能比它被观察到更早收到它」，既真实又保住下游
`converge()` 依赖的不变式。

- RED：`test_a_slightly_fast_executor_clock_is_tolerated`，失败于 110ms 被拒；
- 边界仍在：偏差超过容差（测试用 5 分钟）照样以 `sent_at_is_in_the_future` 拒绝；
- GREEN：control_plane 套件基线 8 红 / 2045 绿 → 8 红 / **2047** 绿（+2 为新增）。

**为什么 macOS 上没暴露**：那台机器的时钟恰好不快于服务器。这类缺陷不看平台，看时钟——
换一台机器、或同一台机器漂移一点，随时会中。

## 五、方法教训

按代价从大到小：

- **对照组要先跑、样本要够大。** 曾断言「验收器的采样线程在杀被测对象」（0/8 vs 4/8），
  关掉采样的对照组一跑，照样失败。结论已在当时更正；
- **`python3` 在本机 Git Bash 里不存在。** 两次用 `python3 - <<'PY'` 做的变异验证**从未执行**，
  错误被吞掉，而后续的「7 绿」被我读成了「变异下仍然通过」。改用
  `backend/.venv/Scripts/python.exe`，让脚本打印 `MUTATION APPLIED`，再 grep 文件确认变异
  真的落地，才拿到可信结论；
- **`git checkout <file>` 被我当成「撤销变异」用，把同一文件里未提交的实现一起删了。**
  撤销临时改动要用备份文件（`cp` 出来再 `cp` 回去）；
- **改了服务端就以为桌面包还有效——错的。** 源码树摘要只排除 `docs/development/**` 与三份
  路线图，**不分前后端**。2026-08-06 因此让用户白跑一次（`App was not built from the current
  reviewed source tree`），代价是一次 11 分钟的重新出包。门禁按设计工作，错的是我的判断；
- **卡住时先看有没有窗口在等人。** `installer.exe /S` 经 Git Bash 时被 MSYS 参数转换改写成
  路径，installer 收到不认识的参数弹了 GUI，然后不报错、不退出地等着——从外面看和「正在装
  450 MB」毫无区别，卡了 50 分钟。改从 PowerShell 启动后 `INSTALL_EXIT=0`；
- **写完就读一遍。** 用 shell heredoc 给用户写启动脚本，反斜杠被吃掉一层，Python 再把
  `\a` `\b` 当转义，写出来的是 `F:utomation-toolackend\.venv\…`。读回来才发现；
- **常量要量不要猜。** `WINDOWS_DEEPEST_PAYLOAD_PATH` 写的 229、实测 231（同一类错误犯了两遍）；
- **「门禁放行」不等于「能出包」。** 有一版是门禁放行、`makensis` 照炸，所以默认工作目录
  必须不带 `--work-dir` 真跑一遍才算可用。
