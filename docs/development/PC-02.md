## 0. 一句话结论

## 1. 为什么需要这个分级

目录契约说的是零件**是什么**，没说这个产品**能不能把用户的话放进去**。读完 134 份源码后，
这个问题有三种不同的答案，而它决定了后面每一步：

- **演示页**：30 个转场零件原样渲染出来是 `SCENE A | SCENE B / Cinematic Zoom / Prompt /
  "use cinematic zoom shader transition"`，它演示的是技术，中间两块是占位面板。要用它得把
  转场机制搬到自己的两个场景之间——那是写代码，不是替字符串；
- **文案在 JavaScript 里**：`caption-kinetic-slam` 把 28 个词放在数组里，每词带 start/end，
  外加一个按下标寻址的关键词集合。它的 `data-duration="8"` 是这些时间戳推出来的，所以换短了
  尾部是静止画面、换长了后面的词没时间播——**而且两种情况 `check_composition` 都判正常**，
  因为声明的时长没变。在这里替文案等于重排动画；
- **文案在 DOM 里**：槽位表可以直接寻址。

## 2. 一个被推翻的中间方案（这是本任务最有价值的部分）

先后推翻两次，都是实测推翻的：

**第一次**：定下路线 A 后曾打算「先小后大」，小 = 零件只当点缀不换文案。
**打开源码后不成立**——「最安全、可原样用」的那批恰恰就是 30 个转场演示页。

**第二次**：改成「按可替换文案槽数量分批」，用正则扫全文件数文本节点。
**这个统计是错的**：15 个字幕零件被排进最容易的一批，而它们的 body 里一段可寻址文案都没有，
正则扫到的 `Kinetic Slam` 是 `<title>`。

所以本任务的计数改用**将来真正做替换的那个解析器**
（`automation_tool.executor.motion_authoring.part_document`），让统计与替换按构造一致。
正则粗测与真解析器的差距可复核：

| | 正则粗测 | 真解析器 |
|---|---:|---:|
| dom | 54 | **52** |
| mixed | 47 | **42** |
| script | 23 | **28** |
| none | 10 | **12** |

## 5. 两个设计选择及其理由

**一、文本节点序号覆盖全部文本，包括 script 与 style 里的。**

只给可见节点编号很诱人——只有可见的才能当槽。但那样序号就依赖「我们对什么算可见的判断」，
而这个判断一旦增加一条（将来跳过 `<template>`、或不再跳过 `<title>`），**所有已冻结的序号会
静默平移一个未知的量**。给解析器报告的每一段文本编号，则序号只依赖文档本身，
`NON_RENDERING_TAGS` 以后可以随便加而不作废任何一条已冻结的槽。

**二、枚举器放在随 Executor 一起打包的模块里，而不是 scripts 下的辅助函数。**

槽位表说的是「`lt-bold-block` 的第 7 个文本节点当前是 `Maya Chen`」。这句话只有在
**冻结时数节点的东西和渲染时数节点的东西是同一份代码**时才成立。两份今天一致的实现，
是一次等待首次分歧的错位替换，而失败形态是文案落到错误的位置——下游没有任何门禁看得见。

## 6. 失败矩阵

篡改矩阵 6 条，全部实测判红：

| 篡改 | 期望 |

| 改某项的 `copyLocation` | 红 |
| 把一个 `deferred` 零件提成 `first`（观察项不变） | 红 |

其中第二条是关键：`batch` 是结论不是独立意见，测试断言它必须能从旁边的观察项推出来，
否则零件可以被悄悄提级。

`check_motion_part_usability.py` 本身对源头失败关闭：零件没有 HTML 文档、文档缺失或是软链、
派生出的项数不是 134，逐条 `fail()`。

## 7. 中文字体查证（PC-02 的验收项之一）

**结论：离线包内中文字体 0 个，中文能显示但靠的是用户操作系统。**

```
contracts/video/offline-motion-dependencies.v1.json
  keptFontSubsets : ["latin", "latin-ext"]
  fontFamilies    : 18 个，全部 OFL-1.1，全部拉丁
  artifacts       : 52 个 woff2，合计 1,031,980 字节（≈1 MB）
```

中文之所以还能渲染，是因为本机模板 `composition_template.py:218` 写的是
`font-family:system-ui,-apple-system,'Helvetica Neue',Arial,sans-serif`，
中文落到系统兜底字体；渲染 worker 也不限制字体，只 `await document.fonts.ready`。

**两个真问题：**

1. **跨平台不一致**：macOS 落苹方、Windows 落微软雅黑，字形字重行高都不同，同一条片子在两台
   机器上排版不同——与专项 Roadmap 的 BM-16「同输入/版本/字体/资源生成稳定结果」直接冲突；
2. **难看**：23/134 个零件用强设计感拉丁显示体（Anton、Bebas Neue、Archivo Black、
   Playfair Display 等），中文没有对应字形，fallback 后设计荡然无存；65/134 个零件用了
   `text-transform: uppercase`，对中文完全无效。

**这是既有缺陷，不是本条路线引入的**——现在的一句话出片就这么跑，BM-08 真实出过片。
产品负责人 2026-07-27 要求解决，已立为 PC-13 并派出独立工作线。

查证时顺带确认了两件对 PC-13 有决定性影响的事实：

- 字体二进制从 `fonts.gstatic.com` 构建期下载、落盘、锁 sha256；`fontFamilies` 那 18 条只是
  许可证台账（指向 google/fonts 仓库的 `ofl/` 目录 + 锁定 commit + 许可证文件摘要）；
- **`stylesheets` 里已经存着 unicode-range 分区**，形如
  `{"family": "Anton", "subset": "latin-ext", "unicodeRange": "U+0100-02BA, …"}`。
  也就是说「按码点选 face」这套机制在本项目已经每帧都在跑，中文字体天然套得进去。

另外 `rewrites.removeLinkDomains` 是 `["fonts.googleapis.com", "fonts.gstatic.com"]`——
构建期把零件里指向 Google 的 `<link>` 删掉换成本地路径；渲染侧 `lint_composition` 的
`_REMOTE_SCHEME` 再拦一道。**运行时取字体在本链路上是结构性做不到的**，国内用户无需联网。

## 8. 交给 PC-03 的三条已知情况

1. **419 个可见文本节点不等于 419 个槽。** 第一批 36 个零件的可见节点合计 419，但分布极不均匀：
   26 个零件 ≤5 个节点（下三分之一、简单卡片，理想形态），长尾是 `ui-3d-reveal` 136、
   `vpn-youtube-spot` 50、`vfx-portal` 45、`app-showcase` 38、`vfx-shatter` 34——
   **那些是假 UI 的布景文字，不是该替换的文案**。槽位表要筛，不能照单全开；
2. **第一批的风险画像很干净**：36 个里只有 4 个 `lengthSensitive`、4 个 `autoFitsFontSize`、
   3 个 `latinDisplayDesign`。确实是最安全的一批；
3. **`maxChars` 必须等 PC-13 定了字体才能测。** 临界字数取决于容器宽度 × 字号 × 字体度量，
   苹方与思源黑体字宽不同，现在测出来的数字换字体后作废。做法是探针二分：无头 Chromium 加载
   零件，逐槽二分替换成 N 个汉字，以 `scrollWidth > clientWidth` 或 bbox 超出 1920×1080 判溢出。
   槽位表的结构与定位机制可以先建，`maxChars` 一栏等字体落地后一次性填。

## 9. 没做什么

- 没有建任何槽位表——那是 PC-03；
- 没有改 prompt——那是 PC-04；
- 没有碰字体——那是 PC-13，独立工作线在跑；
- 分级里的 `lengthSensitive` / `autoFitsFontSize` / `latinDisplayDesign` 是静态信号，
  用来给 PC-03 排优先级和给 PC-04 提示模型，**不是精确判定**；真实的长度上限由 PC-03 的探针测。
